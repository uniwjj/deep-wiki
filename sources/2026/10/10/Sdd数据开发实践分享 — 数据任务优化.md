# Sdd数据开发实践分享 — 数据任务优化

> 基于 Claude Code + 猛犸 EasyData CLI 的端到端数据开发流程

---

## 一、背景

### 需求

反垃圾大宽表 `ads_security_antispam_dd` 每天全量计算耗时 4-5 小时，需要优化为增量计算。

### 挑战

- **表结构复杂**：87 列，10 个 biz_type 分区，116 亿行数据
- **计算逻辑复杂**：7 表 LEFT JOIN，3 个 dwd 子查询扫描 3 年历史数据
- **验证要求高**：必须保证增量结果与全量完全一致
- **平台操作多**：涉及建表、上传任务包、执行、日志分析、数据对比

### AI 辅助方式

使用 Claude Code 作为开发 Copilot，通过 EasyData CLI Skill 直连猛犸平台 API，实现从方案设计到上线准备的全流程自动化辅助。

---

## 二、AI 带来的价值与提效分析

### 2.1 核心价值：从"人干活"到"人做决策"

传统数据开发中，开发者 80% 的时间花在**执行性工作**（写 SQL、调 API、等结果、写文档），只有 20% 花在**思考性工作**（方案设计、问题分析、业务判断）。AI 辅助后这个比例反转：

```
传统模式：
  [████████████████████░░░░] 80% 执行 + 20% 思考

AI 辅助模式：
  [████░░░░░░░░░░░░░░░░░░░░] 20% 确认 + 80% AI 执行
```

开发者的角色从"执行者"变为"决策者"——只需要在关键节点做判断，剩余的执行、验证、文档全部由 AI 完成。

### 2.2 AI 擅长的（详细分析）

#### 2.2.1 SQL 理解与生成


| 场景                | AI 表现                                      | 人工对比                       |
| ------------------- | -------------------------------------------- | ------------------------------ |
| 分析 370 行线上 SQL | 秒级理解全部逻辑，识别 7 个 JOIN 关系        | 人需 30-60 分钟通读理解        |
| 生成增量版 SQL      | 保持 87 列顺序、类型、命名完全一致           | 人手动改容易遗漏列或顺序错误   |
| 生成 test 版本      | 精确替换输出表名，其他逻辑不变               | 人需要仔细比对确保只改了输出表 |
| 修复排序问题        | 精准定位 t4/t5 的 ORDER BY，只改需要改的地方 | 人可能误改 t6 或其他位置       |

**实际案例**：线上 SQL 有 87 个输出列，增量版的 UNION ALL 要求两部分列数和顺序完全一致。AI 自动生成的存量部分 SELECT 列表与增量部分精确匹配，人工对齐 87 列极易出错。

#### 2.2.2 自动化数据验证

**传统验证流程（人工）**：

```
写验证 SQL → 提交执行 → 等待结果 → 手动对比 → 发现差异 → 写定位 SQL → 再等 → 分析根因
每轮约 2-3 小时，3 轮验证需要 1.5-2 天
```

**AI 辅助验证流程**：

```
AI 自动构造全维度验证 SQL → 批量提交 → 自动轮询结果 → 自动分析差异 → 自动定位根因
每轮约 1.5 小时（主要是 Spark 执行时间），人只需看结论确认
```

**本次实际执行的验证 SQL 数量**：22 条 Impala 查询（AI 自动构造+提交+解析）

AI 在验证中的**深层价值**不止是"帮你写 SQL"，而是：

- **验证维度不遗漏**：自动覆盖总行数、分区、唯一性、空值率、字段 diff 5 个维度
- **差异自动下钻**：发现差异后自动构造更细粒度的定位 SQL
- **根因分析能力**：V3 验证中，AI 主动设计了"线上 28 号 vs 29 号对比"实验，证明差异是线上自身不稳定

#### 2.2.3 问题诊断与迭代

本次开发经历了 V1→V2→V3 三轮迭代，AI 在每轮中的表现：

**V1 → V2 的诊断过程**：

```
AI 发现：djradio 分区 +4 行，2 个 gateway_id 重复 4 次（线上只重复 2 次）
AI 分析：边界值 create_time = date_sub(etlDay, 30) 被增量和存量同时覆盖
AI 建议：1. 窗口扩大到 60 天  2. 边界改为严格互斥（>= / <）  3. 存量去掉申诉关联
```

**V2 → V3 的诊断过程**：

```
AI 发现：djradio machine_anti_status 2851 行差异，全在存量部分（create_time 433~1060 天前）
AI 分析：这些记录 version=NULL，ORDER BY version DESC 排序不确定
AI 验证：查询线上 28 号 vs 29 号分区，发现线上自身有 2852 行差异
AI 结论：非增量方案引入，是线上全量自身不稳定，修复排序即可消除
```

如果是纯人工排查，从"2851 行差异"到"version=NULL 排序不确定"这个根因，可能需要数小时的反复验证和思考。AI 能快速构造验证实验并给出结论。

#### 2.2.4 文档生成


| 文档                       | 人工预估 | AI 实际  | 质量                          |
| -------------------------- | -------- | -------- | ----------------------------- |
| DESIGN.md（设计文档）      | 1-2h     | 5min     | 包含决策表、伪代码、表清单    |
| TEST-REPORT.md（测试报告） | 2-3h     | 5min     | 含 3 轮完整数据、diff 分析    |
| README.md（上线文档）      | 2-3h     | 5min     | 含操作步骤、验证SQL、回滚方案 |
| PROGRESS.md（进度追踪）    | 持续维护 | 自动更新 | 每步自动同步                  |

AI 生成文档的优势不只是"快"，更重要的是：

- **一致性**：文档中的数据和代码中的完全一致（不存在人手动抄错 execId 或行数的情况）
- **完整性**：不会遗漏章节（上线文档的回滚方案、异常处理等容易被人忽略）
- **可执行性**：文档中的 SQL 都是真正执行过的，可以直接复制使用

#### 2.2.5 平台 API 编排

**传统方式**：开发者需要记住/查找 API 文档 → 拼参数 → curl/postman 调用 → 解析 JSON 响应 → 处理错误

**AI 辅助方式**：用自然语言描述意图 → AI 自动选择 API → 构造参数 → 调用 → 解析 → 处理异常 → 展示关键信息

```
人：「执行这个 SQL，用 Spark，提交到 music_core 队列」
AI：自动调用 easyolap.execute_sql → 轮询 get_query_result → 展示结果
    如果失败：自动获取日志 → 分析错误 → 建议重试或修改参数
```

本次开发共发起 **32 次 API 调用**，如果每次都手动操作（写命令、等结果、解析输出），保守估计每次 5-10 分钟 = 160-320 分钟。AI 全自动完成，人只需看最终结论。

#### 2.2.6 上下文记忆与状态管理

AI 维护了完整的开发上下文：

- 记住所有 execId 和对应的操作
- 记住每轮测试的差异原因和决策
- 跨天延续开发进度（通过 PROGRESS.md）
- 记住 NeiAPI 认证信息避免重复询问

这在多天开发中尤为重要——人可能忘记"上次跑的那个 execId 是多少"或"V1 的差异根因是什么"，但 AI 通过文档持久化保证了完整的上下文连续性。

## 四、各步骤实践详解

### 步骤 1：方案设计

**AI 做了什么：**

- 分析线上 SQL（370 行），识别性能瓶颈：dwd 三个子查询扫描 2023-05-01 至今约 3 年
- 分析 dim 表结构，确认 `create_time` 可作为增量划界字段
- 评估下游影响（Layer 2 不动），确定只改 1 个文件
- 生成设计文档 `docs/DESIGN.md`

**核心决策：**


| 决策项   | 结论                                                                  |
| -------- | --------------------------------------------------------------------- |
| 增量窗口 | 60 天（覆盖申诉追溯）                                                 |
| 存量处理 | 沿用昨天结果，不做任何 JOIN                                           |
| 合并方式 | UNION ALL，按 create_time 严格互斥                                    |
| 资源配置 | maxExecutors 600→600（不变），executor-memory 16000m→16000m（不变） |

**产出：** `docs/DESIGN.md`

---

### 步骤 2：代码开发

**AI 做了什么：**

- 基于线上 SQL 自动生成 test 版本（输出到 `security_tmp.tmp_xxx_luoxiao01`）
- 生成 production 版本（输出到正式表 `ads.ads_security_antispam_dd`）
- 同时调整 `.job` 配置文件

**关键改动：**

```sql
-- 改动1: dim 表增加 create_time 过滤（只取近60天）
WHERE dt = '${etlDay}' AND create_time >= date_sub('${etlDay}', 60)

-- 改动2: dwd 窗口从3年缩至60天
WHERE dt >= date_sub('${etlDay}', 60) AND dt <= '${etlDay}'

-- 改动3: 排序修复（消除 version=NULL 不确定性）
ORDER BY version DESC, send_time DESC  -- 原来只有 version DESC

-- 改动4: 新增存量部分
UNION ALL
SELECT ... FROM ads.ads_security_antispam_dd
WHERE dt = date_sub('${etlDay}', 1)
  AND create_time < date_sub('${etlDay}', 60)
```

**产出：** `flows/反垃圾大宽表/test/` 和 `flows/反垃圾大宽表/production/`

### 步骤 6-7：测试执行 & 数据验证（3 轮迭代）

这是耗时最长的阶段，经历了 **V1→V2→V3 三轮迭代**。

#### V1：30 天窗口 + 存量关联申诉

```
结果：+4 行，2851 行字段差异
根因：边界值重复 + 30 天窗口不够宽
决策：窗口扩大到 60 天，存量不关联申诉
```

#### V2：60 天窗口 + 存量不关联申诉

```
结果：0 行差异，2851 行 machine_anti_status 差异
根因：version=NULL 排序不确定，线上自身每天结果不同
决策：排序增加 send_time desc 作为二级排序
```

#### V3：修复排序不确定性

```
结果：0 行差异，2851 行差异（线上自身不稳定导致，非增量引入）
验证：线上 28 号 vs 29 号自身有 2852 行差异（确认是线上问题）
结论：通过 ✅
```

**AI 在验证中的工作：**

- 自动构造验证 SQL（总行数、分区对比、唯一性检查、空值率、字段 diff）
- 轮询查询结果直到完成
- 分析差异根因（定位到存量部分 version=NULL 排序不确定）
- 设计验证实验（对比线上自身两天的差异）

**验证 SQL 示例：**

```sql
-- 总行数对比
SELECT 'test' as source, count(1) as cnt
FROM security_tmp.tmp_ads_security_antispam_dd_luoxiao01 WHERE dt='2026-04-29'
UNION ALL
SELECT 'online' as source, count(1) as cnt
FROM ads.ads_security_antispam_dd WHERE dt='2026-04-29';
```

## 六、流程规范

### 核心规则（10 条）

1. **配置隔离** — 只通过 CLI 管理配置，不直接读写配置文件
2. **实现黑盒** — 禁止查看 CLI 内部实现
3. **显式配置** — 配置项只能由用户显式提供
4. **禁止猜测** — 缺参数必须询问用户
5. **Schema 优先** — 先执行 `schema` 命令查询参数定义
6. **敏感确认** — 敏感操作必须用户授权
7. **分区感知** — 查询分区表前先了解分区含义并与用户确认
8. **结果必等** — 同步轮询异步查询结果，禁止异步回调
9. **用户优先** — 用户指定的参数值优先级最高
10. **系统只读** — 禁止修改系统配置
