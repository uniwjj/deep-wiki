AI Agent 五种经典设计模式：Multi-Agent、ReAct、Plan-and-Execute 一篇讲透

作者：智能体AI 发表：2026-11-12 08:00 来源：https://mp.weixin.qq.com/s/7yLkilSr6Y4inh4JtKXT6A 下载：2026-11-12 09:48

回答问题的模型到执行任务的系统，中间隔着五种设计模式。

这两年，AI Agent 越来越火。

从最初的知识库问答，到现在能够调用工具、查询数据库、操作业务系统，AI 正在从一个回答问题的模型，变成一个能够执行任务的系统。

但如果真正开始做 Agent 开发，就会发现一个问题：

「同样是 AI Agent，为什么有的只能回答问题，有的可以调用工具，有的能够拆解复杂任务，还有的可以让多个智能体协同工作？」

背后的原因，很大程度上在于设计模式不同。

很多开发者刚开始接触 Agent，通常会从 RAG入手。后来增加 Memory、Planning、Tools，再往后又接触 Multi-Agent、ReAct、Plan-and-Execute。

这些技术看起来各自独立，实际上解决的是不同层面的问题。


我把目前比较常见的五种设计模式整理了一遍。沿着它们的架构往下看，基本就能理解一个 AI Agent 系统是如何从简单的知识检索，逐渐发展到复杂任务执行的。

01

RAG

RAG：检索增强生成，让大模型访问外部知识

先从最熟悉的 RAG 开始。

大模型有一个很明显的限制：它掌握的知识主要来自训练数据，无法天然访问企业内部的最新业务资料。

例如，一家企业有大量产品手册、技术文档、项目资料和内部制度。直接让大模型回答相关问题，它可能不知道这些资料，也可能根据已有知识生成一个看似合理、实际却不准确的答案。

RAG 就是为了解决这个问题。

它的基本思路很简单：用户提问后，系统先从外部知识库中检索相关资料，再把检索结果交给大模型，让模型结合这些资料生成答案。

1. RAG 的架构是怎样的？

从架构图来看，整个流程可以分为两部分。

第一部分：知识准备。

企业需要先把外部资料接入系统。数据来源可以包括：


文档

PDF、Word、TXT 等。


网页

企业网站、技术博客。


数据库

业务数据、结构化信息。


其他资料

知识库、内部业务文档。

随后，系统对文档进行解析、切分和向量化，将生成的向量存入向量数据库。

第二部分：用户查询。

用户提出问题后，系统首先进行 Query 理解，将问题转换成适合检索的表达，再通过 Embedding 将查询向量化。

接下来，Retriever 从向量数据库中召回相关内容。实际项目中，还可以增加 Reranker，对召回结果进行重新排序。

最后，系统将用户问题与检索到的资料拼接成上下文，交给 LLM 生成回答。整个流程可以概括为：


2. RAG 适合解决什么问题？

RAG 最适合知识相对明确、答案主要来自外部资料的场景。

例如企业知识库问答、产品技术文档查询、内部制度咨询、客服知识检索等。

它解决了大模型无法直接访问私有知识的问题，也让知识更新不必每次都重新训练模型。

不过，RAG 有一个明确的边界。它主要负责检索和生成。即使回答了用户的问题，也不代表它能够自动规划后续任务、调用业务工具或者修改企业系统中的数据。

比如，用户问：

「帮我查一下哪些客户的合同即将到期。」

RAG 可以检索相关制度或合同资料。但如果用户进一步提出：

「把这些客户整理出来，给对应销售人员创建跟进任务。」

这就超出了传统 RAG 的主要职责。接下来就需要 Agent。


02

SINGLE AGENT

单智能体 Agent：从回答问题走向执行任务

如果说 RAG 解决的是知识获取问题，那么单 Agent 要处理的就是任务执行问题。它在 RAG 的基础上增加了几个关键组件：Memory、Planning 和 Tools。这三个组件，让大模型开始具备持续处理任务的能力。

1. 单 Agent 的核心架构

先看三个重要模块。


Memory（记忆）

用于保存历史对话、任务状态和必要的上下文信息。例如用户前面已经指定了客户范围、时间区间，后续就不必每次重复输入。


Planning（规划）

负责分析用户目标，并确定接下来应该做什么。例如用户要求生成一份销售分析报告，Agent 需要判断应该查询哪些数据、进行哪些计算，以及最终输出什么内容。


Tools（工具调用）

是 Agent 与外部世界交互的接口。它可以连接数据库、调用 API、访问搜索引擎，也可以对接 ERP、CRM 等企业业务系统。

2. 单 Agent 是怎样执行任务的？

举个企业场景。用户提出：

「查询本季度销售额最高的十个客户，并整理成一份分析报告。」

Agent 收到任务后，会先理解用户意图，然后读取必要的上下文。接着，它可能执行以下操作：

1

确认本季度的时间范围。

2

调用 CRM 或数据分析接口查询客户数据。

3

调用数据库获取销售订单。

4

对销售额进行统计和排序。

5

整理前十名客户。

6

生成分析报告。

中间如果某个工具返回的数据不完整，Agent 还可以根据返回结果决定是否补充查询。这与传统 RAG 有明显区别：RAG 主要围绕检索结果生成答案，而 Agent 可以根据任务需要选择工具，并根据执行结果继续处理。

3. 单 Agent 的问题在哪里？

当业务越来越复杂，单 Agent 就会遇到一些实际问题。比如，一个 Agent 同时负责销售分析、库存查询、财务核算、客户管理和合同审批。它需要理解大量工具的使用方式，还要处理不同领域的数据和业务规则。

工具越来越多，任务越来越复杂，Agent 的上下文管理和执行调度也会变得困难。这时候，一个 Agent 包揽所有事情未必是最好的选择。企业可以考虑将不同领域的任务交给不同的专业 Agent。这就引出了 Multi-Agent。


03

MULTI-AGENT

Multi-Agent RAG：多个智能体如何协同检索？

企业的数据通常分散在不同系统中。CRM 管客户，ERP 管订单和库存，HR 管员工信息，MES 管生产数据，知识库保存制度和文档。

如果让一个 Agent 同时对接所有数据源，架构很容易变得复杂。Multi-Agent RAG 的思路是：将检索任务拆分，让不同的 Agent 负责不同的数据领域，最后统一汇总结果。

1. Multi-Agent RAG 的核心架构

它通常包含四类组件。


Router Agent：路由智能体

负责理解用户问题，并判断应该把任务分配给哪些专业 Agent。


Retrieval Agent：检索智能体

每个 Agent 负责特定的数据源或专业领域。例如：Agent 1 负责 CRM 客户数据，Agent 2 负责 ERP 订单数据，Agent 3 负责库存数据库，Agent N 负责企业知识库。


Aggregation Agent：聚合智能体

负责接收多个检索 Agent 返回的结果，进行整合和信息汇总。


LLM：大语言模型

根据汇总后的信息生成最终答案。

2. Multi-Agent RAG 的执行过程


举个实际业务例子。用户提出：

「分析本季度华东地区的销售情况，并找出库存不足的重点产品。」

系统可以将任务拆分：

1

销售 Agent 查询 CRM 中的销售数据。

2

订单 Agent 查询 ERP 中的订单数据。

3

库存 Agent 查询库存数据库。

4

汇总 Agent 整合各个 Agent 返回的信息。

最终，大模型根据这些数据生成一份综合分析结果。这样，每个 Agent 只需要专注于自己负责的数据和检索逻辑。

3. Multi-Agent 是否一定比单 Agent 更好？

「不一定。这是开发中很容易出现的一个误区。」

有些项目一上来就设计多个 Agent，认为智能体越多，系统能力就越强。实际上，多一个 Agent，就多一份调度、通信、上下文传递和结果校验的成本。如果任务本身很简单，一个 Agent 就能完成，拆成多个 Agent 反而会增加系统复杂度。

Multi-Agent 真正适合的是专业领域差异明显、数据源分散、任务能够合理拆分的场景。重点不在于有多少个 Agent，而在于每个 Agent 是否有明确的职责。


04

PLAN-EXECUTE

Plan-and-Execute：复杂任务先规划，再执行

前面介绍的单 Agent 和 Multi-Agent，主要解决工具调用和任务分工的问题。但还有一种情况：用户提出的任务本身就很复杂，需要连续执行多个步骤。

例如：

「帮我研究一下国内企业 AI Agent 市场，分析主要竞争对手，比较产品能力和商业模式，最后生成一份市场研究报告。」

如果让大模型直接一次性完成，很容易出现任务遗漏、信息不完整、分析逻辑混乱等问题。Plan-and-Execute 就是针对这类场景设计的模式。

1. 核心思想：把大任务拆成小任务

Plan-and-Execute 通常由两个核心角色构成：


Planner：规划器

负责理解目标、拆解任务、制定执行计划。


Executor：执行器

负责按照计划逐步完成具体任务，并返回执行结果。

此外，还可以增加 Observer 和 Reflection 模块，用于观察执行状态、检查结果，并在必要时调整计划。

2. Plan-and-Execute 的执行流程

假设用户要求生成一份市场研究报告。Planner 首先将任务拆解：

1

收集行业资料。

2

整理主要竞争对手。

3

分析产品技术架构。

4

比较商业模式。

5

整理市场机会和风险。

6

生成最终报告。

接下来，Executor 按照计划逐步执行。每完成一个步骤，系统都会获取执行结果。Observer 负责观察当前进度，Reflection 则根据实际结果判断是否需要补充资料、重新执行某个步骤，或者调整后续计划。最后将所有结果整合，生成完整报告。


3. Plan-and-Execute 适合哪些场景？

这种模式比较适合需要多个步骤、执行顺序相对明确的复杂任务。例如：

·

市场调研和竞品分析。

·

多步骤数据分析。

·

自动化报告生成。

·

项目任务拆解。

·

企业业务流程自动化。

它有一个很重要的特点：任务计划与具体执行相对分离。这样，系统可以先确定要完成什么，再逐步处理每个步骤，而不必要求大模型一次性想清楚所有事情。

！踩坑提示 🕳

Plan-and-Execute 也有代价：任务拆解可能不合理，前一步的错误可能影响后续步骤，执行过程中也可能出现新的情况。所以，执行结果的检查和计划调整非常重要。


05

REACT

ReAct：让 AI 在推理与行动之间不断循环

最后一种模式是 ReAct。它的名字来自两个单词：Reasoning（推理）和 Acting（行动）。

ReAct 的核心思路是，让大模型在推理过程中调用外部工具，再根据工具返回的结果继续推理。它与 Plan-and-Execute 有相似之处，但两者关注点不同：Plan-and-Execute 更强调先制定任务计划，再按计划执行；ReAct 更强调每次行动之后，根据观察到的新信息决定下一步做什么。

1. ReAct 的核心架构

ReAct 最经典的执行循环可以表示为：


这里有三个关键环节。


Reasoning：推理

Agent 分析当前问题，判断需要采取什么行动。


Action：行动

Agent 选择合适的工具，例如搜索、查询数据库、调用 API。


Observation：观察

系统接收外部工具返回的结果，将其作为下一轮推理的输入。

这个循环会持续进行，直到 Agent 判断任务已经完成，或者触发停止条件。

2. 用一个例子理解 ReAct

用户提出：

「帮我查询某个产品的最新价格，并判断它是否值得购买。」

Agent 不会直接根据训练时的知识给出结论。它可能按照以下过程执行：

1

Reasoning：判断需要获取产品的最新价格和相关信息。

2

Action：调用搜索工具，查询产品价格。

3

Observation：获得多个网页返回的价格信息。

4

Reasoning：发现不同平台的价格存在差异，需要进一步核实产品型号和配置。

5

Action：继续查询官方产品信息和其他销售渠道。

6

Observation：获取补充信息。

最后，Agent 综合价格、配置和相关资料，给出分析结果。这就是 ReAct 的基本工作方式。

3. ReAct 的优势和限制

它最大的优势是灵活。Agent 不需要在开始时就确定所有步骤，可以根据每次行动获得的信息调整下一步。但它也有一些问题：

·

可能反复调用相同工具。

·

推理过程可能陷入循环。

·

工具调用次数和执行成本难以预测。

·

如果观察结果不准确，后续推理也可能受到影响。

因此，真正落地时，需要为 ReAct 设置最大执行轮数、工具调用预算、超时机制和结果校验。ReAct 的价值，在于让 Agent 能够根据外部反馈调整行动，而不是机械地执行一条固定流程。


06

HOW TO CHOOSE

五种设计模式，到底应该怎么选？

前面介绍了五种模式。把它们放在一起看，会发现它们解决的其实是不同的问题。

设计模式
核心能力
主要解决的问题
RAG
检索增强
大模型缺少外部知识
单 Agent
记忆、规划、工具调用
如何执行具体任务
Multi-Agent RAG
多智能体分工检索
如何处理多个专业数据源
Plan-and-Execute
任务拆解与执行
如何完成复杂长任务
ReAct
推理、行动、观察
如何根据反馈动态调整

实际项目中，可以根据业务需求选择。


企业知识库问答

RAG 通常就够了。


查询数据库、调用 API、操作业务工具

可以从单 Agent 开始。


跨多个业务系统检索数据

可以考虑 Multi-Agent RAG。


任务需拆成多个明确步骤

可以采用 Plan-and-Execute。


大量不确定性、需按反馈调整

就可以考虑 ReAct。

还有一点值得注意：这些模式完全可以组合。例如：


Multi-Agent RAG + Plan-and-Execute

Planner 先拆解复杂任务，再将不同的数据检索任务分发给专业 Agent。


RAG + ReAct

Agent 根据当前推理需要决定什么时候检索、检索什么内容，以及是否需要再次检索。


Single Agent + ReAct

单个 Agent 通过工具调用和观察反馈，完成动态任务执行。

所以，实际架构设计时，不需要强行在五种模式中选一个。关键是看业务任务到底需要什么能力。


07

ENTERPRISE

企业级 Agent，还需要 Runtime 和 Harness

讲到这里，还有一个问题值得继续思考。即使我们已经掌握了 RAG、Multi-Agent、Plan-and-Execute 和 ReAct，是否就能直接构建一个稳定运行的企业级 Agent？答案显然不是。

这些设计模式主要解决 Agent 如何检索、规划、协作和行动的问题。但进入生产环境后，还要考虑更多工程问题。


Agent Runtime：负责运行管理

管理 Agent 的生命周期、任务状态、上下文、工具调用和执行调度。


Harness Engineering：负责执行控制

管理执行循环、错误处理、重试机制、结果验证和异常恢复。


Memory：负责记忆管理

区分短期上下文、长期记忆和任务状态，避免每次执行都从头开始。


MCP / Tools：负责外部系统连接

通过统一的工具接口连接数据库、业务系统和第三方服务。


Evaluation：负责效果评估

判断 Agent 是否完成了任务，结果是否准确，执行过程是否符合预期。


Security & Governance：负责安全与治理

控制工具权限、数据访问范围、审批流程和操作审计。

尤其是在企业场景中，Agent 能不能调用工具是一回事，能不能在正确的权限范围内执行操作，又是另一回事。

例如，Agent 可以查询客户信息，但是否允许它修改客户资料？是否允许它直接创建订单？是否需要人工审批？这些问题都需要在架构设计阶段考虑清楚。

「企业级 Agent 是一套完整的工程系统：模型负责理解和推理，设计模式负责组织任务，Runtime 和 Harness 负责管理执行，权限与治理机制负责约束操作。」

这几个部分配合起来，Agent 才有机会从一个能够演示的 Demo，变成一个真正能够承担业务任务的系统。

写在最后

回过头来看这五种设计模式，其实可以看出 AI Agent 能力发展的几个方向。

·

RAG 让大模型能够访问外部知识。

·

单 Agent 让大模型能够调用工具、执行任务。

·

Multi-Agent 让不同的智能体能够分工协作。

·

Plan-and-Execute 让复杂任务能够被拆解和逐步完成。

·

ReAct 则让 Agent 能够根据执行反馈不断调整行动。

它们解决的问题不同，也没有哪一种模式能够适用于所有场景。

如果现在开始设计一个企业 Agent，我的建议是：先把业务任务拆清楚，再决定采用什么架构。简单任务不要过度设计，复杂任务不要指望一个 Prompt 就能解决。

Agent 的能力上限取决于模型，能否稳定完成真实业务任务，取决于背后的架构设计与工程体系。

这也是理解 AI Agent 设计模式真正有价值的地方。
