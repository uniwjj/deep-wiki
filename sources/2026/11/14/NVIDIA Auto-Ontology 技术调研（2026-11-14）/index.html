NVIDIA Auto-Ontology 技术调研

调研对象：https://github.com/NVIDIA/auto-ontology　调研日期：2026-11-14　编制：观策·行业与竞品情报

0. 一句话结论

NVIDIA 用 Apache 2.0 开源了一个「从企业元数据自动生成本体、经人工认证后供 Agent 消费」的语义层框架。它把行业正在争论的三条语义层路线中的第三条——「自动生成 + 人工认证」——做成了可复现的开源实现。对我方 L3 指标语义平台的直接含义是：语义层的「生成能力」正在商品化，真正剩下的护城河是「认证与治理流程」，而这恰好是我们过去最不当卖点讲的部分。

1. 项目基本事实

仓库NVIDIA/auto-ontology（配套评测仓 NVIDIA/auto-ontology-eval）
官方描述「一个用于在数据之上构建语义、图结构推理层的 Python 框架，支持确定性查询生成、更好的上下文检索，以及更可解释的 LLM 与 Agent 工作流」
许可Apache License 2.0（可商用、可修改、可再分发）
活跃度最近提交 2026-11-14，持续高频更新；Issues 66 条、PR 54 条，社区关注度上升很快
版本状态尚无正式 Release（Tags 仅有一个 pre-main-merge-backup），属早期项目
贡献政策明确不接受外部贡献（not accepting external contributions）——这不是社区共建项目，是厂商主导的标准卡位
技术栈Next.js 前端 + FastAPI 后端 + PostgreSQL 17 / pgvector + FastMCP + 可选 Vault；Docker Compose 一键起
定位表述「补充客户已有的语义模型」（complements the semantic models customers already own）——不主张替换既有语义层

2. 它解决什么问题

官方开篇的判断很直接：Agent 能检索文档、能查数据库，但可靠性卡住了 Agentic Analytics——一个算得更快的营收指标，如果数字是错的，毫无价值。

所以它要提供一个「上下文层」，回答 Agent 必须知道的六个问题：

数据在哪定位到具体表与列
是什么意思业务术语、同义词、口径说明
该不该用是否经过认证、是否适用当前问题
怎么用受审的 SQL 表达式、join 关系、桥表
从哪来血缘与来源（provenance）
什么相似向量检索出的候选术语与字段

这套问题的表述方式，与我们讲「指标语义层是智能问数可信前提」几乎是同一套逻辑——区别在于它用开源项目把它工程化了。

3. 核心机制：三段式工作流

3.1 Generate（自动生成）

  • 读取源库：抽取 schema、对字段做数据画像（profiling）、采样值写入 catalog。
  • 命名实体：逐表抽取术语（terms），并把每个术语映射到具体列。
  • 解析关系：从主外键与数据分布推断表间 join 与桥表，并从查询历史中建议 SQL 属性。
  • 写入本体：术语、关系、SQL 属性存入 Postgres，向量写入 pgvector 供检索。
  • 官方示例：对 Wide World Importers 数据库执行一次编译，产出 31 个术语。

3.2 Certify（人工认证）——这是全项目最关键的一步

  • 用真实问题在 Chat 里测试，或通过 MCP 的 check_answerable / ask_question 验证。
  • 在 UI 或 API 里修订术语、描述、SQL 属性。
  • 确认无误后逐项认证（certify）——只有认证过的名称、描述、SQL 属性才会被 Agent 当作可信依据。
  • 官方明确：答案必须携带 provenance（来源）。

3.3 Answer（回答）

  1. 意图分类 + 抽取问题中提到的实体。
  2. 按向量检索候选术语、列、SQL 属性。
  3. 用受审的 SQL 属性组装查询，而不是让模型自由发挥。
  4. 对生成的 SQL 做校验与修复；无法从现有数据回答时，明确返回「不可回答」。

3.4 三类定义（本体的最小构成）

Terms（术语）业务概念（如 Customer、Invoice Line），含描述与同义词，映射到承载它的列
SQL attributes术语下经审阅的 SQL 表达式（如毛利率、滚动合计）。Agent 复用同一表达式，保证同一度量每次算法一致
Relationships表如何 join，含桥表；从键与数据推断而来

【推断】SQL attributes 这一设计是「口径统一」的工程化落点——它不是靠文档约束，而是靠可复用的受审表达式强制一致。这比我方常见的「指标定义 + 口径文档」更硬。

4.2 连接器：10 种引擎

PostgreSQL、MySQL、Databricks、Snowflake、ClickHouse、Trino、Apache Kyuubi、HeavyDB、DuckDB、SQLite。

【推断】这个清单值得注意——既覆盖国际主流（Snowflake/Databricks），也覆盖了 Trino、Kyuubi 这类国内大数据栈常见引擎。说明它并非只面向欧美生态，具备进入国内混合数仓环境的现实基础。

4.3 模型角色：四类可替换

角色默认模型用途
REASONINGnemotron-3.5-lightning-30b-a3b构建本体、写答案 SQL 与解释、判定可回答性
NON_REASONING同上意图识别、实体抽取、候选筛选、SQL 校验修复
EMBEDnemotron-3.5-embed-1b索引表/列/术语/SQL 属性并匹配问题
RERANKnemotron-3.5-rerank-8b编译桥表 SQL 属性时对候选表排序

支持替换为自托管 NIM 或任意 OpenAI 兼容端点——这意味着国内客户可以换成国产模型，不受限于 NVIDIA 云。这是它比闭源产品更容易进入国内政企的一点。

4.4 MCP 能力（9 个工具）

就绪检查check_readiness：这个部署到底能不能回答任何问题
术语检索search_terms、get_term、get_term_columns、get_term_sql_attributes、get_sql_attribute、describe_table
可答性判断check_answerable：本体是否覆盖这个问题
提问ask_question：返回答案、SQL 与数据行

MCP 为只读工具，每次调用按登录用户的权限执行。「按用户权限执行」这一点与腾讯 DataBuddy、阿里 DataWorks 的做法一致，是 Agent 上下文服务的事实标配。

4.5 互操作：Apache Ossie

支持 Apache Ossie（语义模型交换开放标准），可经 Settings → Import/Export 或 API 导入导出 Ossie YAML。这直接指向「语义模型可跨工具迁移」。

4.6 可选预测：KumoRFM

配置 KUMO_RFM_API_KEY 后，预测类问题路由到 NVIDIA 托管的 KumoRFM；需把连接的表上传到该服务，默认上限 20 张表。【推断】这一点在数据不出域场景是硬约束，国内政企基本不可用。

5. 与三条语义层路线的对位（本节最重要）

路线代表核心机制人工介入
纯自动生成阿里云 DataWorks Context Graph从数据资产自动扫描推理生成六层语义低（事后修正）
自动 + 人工沉淀数势、Aloudata、我方人工建指标本体与语义层高（事前建设）
自动 + 认证腾讯云（语义模型→本体模型，自动生成后需人工确认）、NVIDIA Auto-Ontology（Generate → Certify）机器生成初稿，人逐项认证后才可信中（生成后认证）

【推断，置信度中高】「自动生成 + 人工认证」已经由两家（一家国内头部云厂商、一家国际芯片与 AI 巨头）独立收敛到同一形态，这基本可以判定为该赛道的主流工程范式。我方如果继续把「人工沉淀」作为核心卖点，会在 POC 里被直接对比下去——因为对手既有人工环节（认证），又省掉了从零建设的时间成本。

可保留的差异化不在「生成」，而在「认证之后」：谁来做认证、认证如何留痕、如何版本化、如何与权限血缘联动、如何跨系统生效。这些是开源项目最薄弱、也最难被抄的部分。

6. 对我方四层能力的含义

层级能力判断
L1数据存储计算中性偏利好。它需要对接 10 种引擎，反向证明「多引擎兼容」是语义层落地的前置条件——我方若能给出更完整的国产库/信创引擎兼容清单，是加分项。
L2数据开发治理压力上升。Certify 环节本质是治理流程（审批、留痕、版本），开源项目把这一环留给了使用方自己补。这恰好是我方治理平台的机会——但要把它做成「语义认证工作流」，而不是通用数据治理。
L3指标语义最大冲击。语义层的「生成能力」被开源商品化，客户技术团队可自建；定价逻辑必须从「卖生成」转向「卖认证、治理、行业资产与交付」。
L4智能问数间接冲击。MCP 让语义层成为「Agent 上下文服务」，任何 Agent 都能接。我方问数产品的价值要往「可信闭环 + 业务动作」上移，而不是停留在「能问」。

7. 必须警惕的五个风险

风险 1：语义层被开源替代，独立语义层模块的定价空间被压缩。

Apache 2.0 许可允许商用与再分发，云厂商可直接包装成托管服务。对技术能力强的客户（互联网、金融科技），“自建替代采购”会成为现实选项。触发信号：客户技术团队在 POC 中提出「先用开源方案跑一版」；竞品宣传中出现「兼容 Auto-Ontology / Ossie」。

风险 2：Apache Ossie 若成为事实标准，语义层的锁定效应消失。

语义模型可导入导出，意味着客户迁移成本大幅下降。过去靠「语义资产沉淀在我们这里所以换不掉」的逻辑会被削弱。触发信号：Ossie 被更多厂商采纳；招标文件要求「支持语义模型标准格式导入导出」。

风险 3：「生成 + 认证」成为主流，我方人工沉淀叙事受压。

腾讯云与 NVIDIA 各自独立走到同一形态，说明这不是个别选择。触发信号：客户问「你们能不能自动生成语义层」；竞品演示「导入数据资产当天可用」。

风险 4：NVIDIA 以开源做生态卡位，后续可能被云厂商集成进托管服务。

「不接受外部贡献」+ 无正式 Release + 高频更新，是典型的厂商主导标准打法。触发信号：主流云厂商推出「一键部署 Auto-Ontology」；NVIDIA 与某云签订联合方案。

风险 5：我方至今没有可对外披露的语义层量化口径。

阿里云 93.24% / 99%，腾讯云 95.9% / 83.5%，NVIDIA 提供了可复现的双盲评测框架（schema-only 对照组 vs 本体组），但官方未公布具体提升数字。如果对手用这个框架自测并公布结果，我方将第三次被迫应战且仍无数字。

8. 一个容易被忽略的加分项：它的安全设计有硬伤

官方 README 自己写明了三条：

  • 摄入服务的 ingest / delete / reset / compile 端点自身没有任何认证。
  • 后端 FastAPI 信任前端转发的 x-auto-ontology-user-id 头来判断用户身份。
  • 必须把 3001 / 3002 端口放在私网，否则等同于裸奔。

【推断，置信度中高】这说明它是「开发者可用、企业生产未就绪」的早期项目。对政企、金融客户而言，身份认证、端点鉴权、审计留痕、私有化交付恰恰是我方可以正面拉开差距的地方——而且这不是话术，是可以逐条验证的技术要求。

9. 可执行建议

① 用官方评测框架做一次双盲自测（最高优先级，2 周内）

Auto-Ontology Eval 的设计很干净：同一批问题、同一个模型、两组对照（仅 schema vs 带本体）、确定性验证器判分。我方可以照搬这套方法，用客户脱敏库或 WWI 样例库跑出自己的「口径增强前后准确率差」。这比自造指标更有说服力，也能直接与对手对话。

② 支持 Ossie 语义模型的导入导出（低成本、高回报）

工程量小，但能在招标中直接应答「语义模型可迁移」类条款，同时把「我们不怕客户迁移」变成信任信号。

③ 提供我方语义层的 MCP Server（对齐三家）

腾讯 DataBuddy、阿里 DataWorks、NVIDIA 都已把语义层通过 MCP 暴露。我方若缺这一层，会在「Agent 能不能直接接你的语义层」这个问题上失分。

④ 把「Certify（语义认证）」做成独立产品能力

这是开源最难补齐、云厂商也最不愿细做的部分：认证人是谁、认证版本、变更留痛、与权限血缘联动、认证失效回收。建议把它从「治理平台的一个子功能」提升为独立卖点。

⑤ 把安全与私有化做成对比清单

针对 NVIDIA 当前的三处短板（端点无认证、信任转发头、预测需上传数据），整理一页「生产就绪度对照表」，用于技术型客户的答疑。

10. 待验证事项

  1. 官方评测数字：README 与 eval 仓均未公布具体的 BIRD / BEAVER 提升幅度，需持续关注其后续发布或论文。
  2. 首次公开发布时间：本文只确认最近提交为 2026-11-14、无正式 Release；仓库首个公开版本的具体日期未核实。
  3. Ossie 标准的归属与成熟度：是否已进入 Apache 基金会正式项目、有哪些厂商支持，需单独核实。
  4. 是否支持国产数据库：连接器清单中未见达梦、人大金仓、OceanBase、GaussDB，对信创场景是明确缺口，需确认是否有社区适配计划。
  5. 中文与中文语义支持：默认模型为 Nemotron 系列，中文业务术语（如「复购率」「动销」）的抽取质量未经验证。
  6. 规模上限：单次编译产出的术语量（示例 31 个）在万级表规模下的表现未知。
