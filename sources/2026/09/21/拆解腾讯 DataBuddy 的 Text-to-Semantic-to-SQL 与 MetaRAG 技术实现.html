01｜先说清楚：Text-to-SQL 在企业里缺的不是 demo，是生产资格

Text-to-SQL 的公开评测（如 BIRD、Spider）分数这些年涨得很快，但企业落地时普遍卡在 60%~70% 的准确率上。这不是模型"不够聪明"的问题，而是"让概率模型直接输出 SQL 字符串"这条路径本身的结构性缺陷。腾讯云在官方材料里把它归纳为三类典型翻车现场：

陷阱一：指标歧义。 系统里一个"收入"有八种口径——含不含退款、含不含内部调拨、按下单时间还是确认收入时间。模型不知道你们公司用的是哪一种，它只能随机选一个，甚至每次选的还不一样。

陷阱二：JOIN 错乱。 关联键靠猜。一个具体的机理是：订单表和订单明细表是一对多关系，模型按直觉把金额字段直接 SUM，SQL 语法完全正确、跑得也快，但每一行订单金额被明细行数膨胀了 N 倍——不报错的错、跑得飞快的错、三天后才被业务发现的错，这是 Text-to-SQL 在生产环境里最贵的一类错误。

陷阱三：查询条件随意匹配。 过滤条件是"上季度"或者"华东区"，大模型很难知道"华东区"在企业数仓里到底对应哪个组织层级、哪张维表的哪个编码。

腾讯云 WeData 产品总监唐晨在 2026 年 6 月的表述更直接："如果底层数据没准备好，上面跑什么 Agent 都是白搭。"腾讯云并据此提出：统一语义正在成为 AI 时代新的数据护城河。

这四个字的背后是一个朴素的判断：口径的答案不在模型参数里，在企业自己的实体、关系、指标和维度定义里。所以解法不是换更大的模型，而是把这些答案显式地、机器可读地沉淀下来——这就是统一语义层。

02｜统一语义层（Unity Semantics）：人和 Agent 共用的"业务语言"层

WeData 的统一语义层（官方称 Unity Semantics / DataBuddy Unity Semantics）是介于"物理数据存储"与"分析应用（包括 AI Agent）"之间的抽象层，目标是 Single Source of Truth——"一次定义、处处可信"。它解决的是"同名不同义、同义不同名"的问题。

注意 Metric 这一格的定义——"在度量上叠加口径、窗口和同环比"。这意味着语义层持有的不是"哪个字段是金额"，而是"GMV = 已支付订单金额之和，按支付时间，不含退款"这种完整计算逻辑。编译 SQL 所需的全部信息，都由语义层显式持有，这是后面"确定性编译"能成立的前提。

2.2 三层架构

  • L1 物理层：原始数据、湖仓引擎、计算引擎；
  • L2 业务层：指标、维度、实体、关系等语义资产；
  • L3 协议层：所有问数请求（无论是 BI、人还是 Agent）统一走这一层出口。

值得强调的一点（来自 DataBuddy 团队在 2026 AICon 的分享）：DataBuddy 自己也是语义层的消费方之一，语义能力不封闭在 DataBuddy 产品里——BI、第三方 Agent 都可以通过 JDBC 或 MCP 消费同一套语义资产。

2.3 语义冷启动：机器出草稿，人来确认

企业普遍没有现成语义资产，这是语义层方案落地的第一个拦路虎。DataBuddy 的冷启动是两条抽取路径：

  1. 从元信息抽：表结构、字段注释、主外键、历史 SQL、BI 配置、血缘 → 表推断实体，主外键和 Join 频次推断关系，聚合列推断度量，高频 group by 推断维度；
  2. 从业务文档抽：数据字典、Wiki、PRD、口径说明 → 推断指标定义和维度。

但有一条线不能越：LLM + 规则统计产出的只是草稿。候选经过冲突检查、去重聚类后，必须由 Owner 审核才能进入权威语义资产库。用官方的原话说："DataBuddy 降的是人工录入的成本，不是人工治理本身。"——这句话对评估此类产品很重要：语义治理的人工环节没有被取消，只是从"从零手写"变成了"审核确认"。

03｜SemQL：把"概率性生成"变成"确定性编译"

3.1 SemQL 是什么

SemQL（Semantic Query Language）是语义层对外的类 SQL 查询语言，以 JDBC 方式提供查询能力。它的核心约束只有一条：标识符（指标 / 维度 / 时间）必须全部来自语义层。模型在生成 SemQL 时不能自由发挥任何字段名、表名、JOIN 逻辑——它只能"点菜"，从语义层召回的资产里选。

Text2Semantic2SQL 即 自然语言 → 标准化语义查询 → 语义层编译为 SQL。替代了 Agent 直接生成 SQL 的概率性猜测"。

一条官方材料里给出的 SemQL 大致长这样：

query(
  metric   = [订单金额],
  where    = [Dimension(订单状态) = '已取消'],
  group_by = [Dimension(性别), TimeOutput(月)]
)

注意这条查询里没有任何物理表名、字段名和 JOIN 条件。"订单金额"是指标资产，"订单状态""性别"是维度资产，时间输出是语义层的时间标识符。JOIN 怎么写、金额要不要去重、按哪张维表关联，全部是语义层编译器的事，模型碰不到。

3.3 完整链路：一个真实案例

官方文章给过一个腾讯系内部的长尾案例，值得完整走一遍，因为它展示了语义层怎么处理"非标准提问"：

用户输入："帮我查一下腾讯视频男性 dau 的变化趋势"

  1. 意图识别：识别出核心诉求是一个趋势查询，对象是"dau"，修饰条件是"男性"；
  2. 语义检索（MetaRAG，下一节展开）：系统并没有去底层找一个叫 "dau" 的字段，而是把 "dau" 对齐为指标库中的 "APP端活跃设备数"，把"男性"解析为维度条件 "性别-男"；
  3. 生成 SemQL：用对齐后的指标 + 维度组装标准化语义查询；
  4. 编译执行：语义层把 SemQL 编译为 SQL——多表 JOIN、口径、同环比都在这一步被确定性展开——并下推执行（Auto Acceleration 层还会做 HBO/CBO 多级缓存、自动物化视图推荐与合并、谓词下推）；
  5. 返回结果：Data Agent 拿到可信的趋势数据，输出分析。官方将此概括为从"表交付"到"知识交付"。

这个例子的关键在于："dau" 这种口语缩写与 "APP端活跃设备数" 这种正式指标名之间的映射，是语义层资产，不是模型的常识。 换任何一个大模型，这个映射都不存在于模型参数里——这也回应了"换大模型提升微乎其微"的判断。

04｜MetaRAG：为结构化元数据设计的双路召回

4.1 为什么传统 RAG 不够用

上一步"语义检索"说起来轻巧，做起来是整条链路里最难的一环。一个中大型企业的语义层可能有成千上万条指标、维度、实体定义，用户一句自然语言，Agent 必须精准召回"用户到底想查哪个指标、配哪几个维度"。

传统 RAG 是为非结构化文档设计的：切 chunk、向量化、按相似度召回。但语义元数据是结构化、组合性的——一次查询 = 指标 × 维度 × 时间粒度 × 过滤条件的组合。组合爆炸之下，单条向量化召回要么召回了指标漏了维度，要么维度拼错了口径。腾讯为此设计了 MetaRAG 混合架构，用两条互补的召回路径分别解决"高频"和"长尾"。

4.2 FlattenedRAG（F-RAG）：把组合"摊平"成问答库

F-RAG 的做法是枚举元数据组合，把结构化元数据转化为非结构化表示：用人工标注的核心模板 + 自动枚举，把"指标 × 维度 × 时间粒度"的组合预先展开成一条条"问题 → 语义组合"的知识条目，构建离线问答知识库。官方给出的规模是亿级别（Billion-level）的离线元数据知识索引。

展开之后，每个组合变成一条普通的可检索知识，传统 RAG 的成熟基建全部可用，所以 F-RAG 准确度高，特别适合覆盖核心高频问题（"GMV 是多少""上月 DAU 趋势"这类）。

它的局限也显而易见：枚举是排列组合，高频组合枚举得起，长尾组合枚举不完——那些由冷门维度、罕见过滤条件拼出来的查询，F-RAG 覆盖不了。

4.3 StructuredRAG（S-RAG）：利用结构特性分层召回

S-RAG 反过来，不预先枚举，而是利用元数据的结构特性在线召回：先定位核心指标（缩小到与问题相关的少数指标），再围绕该指标过滤召回相关维度修饰条件，最后由大模型确定最优组合。因为按结构分层走，冷门指标 + 罕见维度的长尾组合也能被拼出来——代价是对结构化索引的质量依赖更高。

4.4 完整召回链路：千级 → Top 100 → Top 6

两条路召回的候选如何收敛成最终答案？官方材料给出了量化的漏斗：

  1. 意图识别：理解用户问题的核心诉求；
  2. Query 改写与分解：把复杂问题拆成可检索的子问题；
  3. 多路召回：F-RAG 与 S-RAG 同时召回核心候选实体（指标）；
  4. Cross Encoder 在线打分：把候选集从千级别缩小到 100；
  5. 精选策略：进一步从 Top 100 收敛到 Top 6；
  6. LLM 终选：大模型从 Top 6 中选出最符合用户意图的"指标 + 维度"组合，生成 SemQL。

漏斗设计的目的官方说得很直白：从根本上去除噪音、抑制大模型幻觉——进入生成环节的上下文越干净，模型"点错菜"的概率越低。

05｜覆盖度决定路径：不是所有问题都走 SemQL

AICon 演讲里有一个容易被忽略、但工程上最关键的细节：召回之后并不直接生成 SQL，而是先判断语义覆盖度，分三级处理。

处理方式

无论走哪条路，候选 SQL 都要过静态检查、语义对齐、权限收敛三重校验；失败的证据回到 Agent Loop 里修正重试；缺失的 case 离线聚类归因，变成四要素候选进入治理流程。

这套设计的诚实之处在于：它不宣称语义层能覆盖 100% 的提问，而是把"覆盖不到的部分"显式圈出来，降级到受约束的生成路径，并把每一次降级都变成语义资产生长的输入——覆盖度沿 Agent 的 ReAct 循环逐步收敛，越用越准。

配套的还有分层记忆：Session（会话任务态）→ Personal（个人偏好）→ Team（业务空间共识）→ Enterprise（治理后的长期资产）。晋升必须过"去重聚类 + 冲突质量检查"和"Owner 审核"两道关口。官方的原话值得抄录："不能因为一条经验被用得多，就自动把它当成企业真相。"

06｜MCP：语义层的开放出口

语义层指标发布后，会自动生成 MCP（Model Context Protocol）服务。根据腾讯云官方文档（WeData 产品文档 MCP 章节），指标 MCP 服务封装了三个工具：

工具
功能
SearchMetric
指标定义检索：根据关键字语义检索最匹配的指标和对应分析维度；多个匹配时由 Agent 或用户判断选哪个
QueryMetricData
根据 SearchMetric 返回的指标/维度 + 用户查询条件，直接返回指标计算结果
QueryMetricDataBySemQL
直接提交 SemQL 语句查询（与 QueryMetricData 作用相同、请求方式不同，二选一）

服务以 HTTPS 端点形式提供（https://api-{地域}.wedata.cloud.tencent.com/api/mcp/v1/metric）。这意味着任何支持 MCP 的 Agent——不限于 DataBuddy 自己——都能接入同一套口径。业务团队也可以基于这三个工具自行编写 Prompt，搭建自己场景的数据分析智能体，不必依赖数据工程师排期。

这也是"统一语义层是护城河"这个判断的落地形态：模型会换代、Agent 框架会换代，但语义资产和它对外的 MCP 出口是跨代复用的。
