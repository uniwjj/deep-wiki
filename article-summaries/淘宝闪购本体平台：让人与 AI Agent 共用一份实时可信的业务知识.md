## 淘宝闪购本体平台：让人与 AI Agent 共用一份实时可信的业务知识

**文章信息**：
- **原文标题**：淘宝闪购本体平台：让人与 AI Agent 共用一份实时可信的业务知识
- **来源**：https://mp.weixin.qq.com/s/YRzW4duU_YQxl3WRTvedqA
- **作者**：王浩迪（阿里技术公众号）
- **发表时间**：2026-11-18

---

**一段话总结**：

这篇文章讲的是淘宝闪购团队做的一个「本体平台」——一个把业务知识（对象、关系、术语、口径）管理起来、让 AI Agent 也能像人一样查到"可信口径"的系统。出发点是：数据团队对口径，人靠问、Agent 靠猜；Agent 拿到一列数字，不知道它来自哪个指标、哪个版本、谁确认过。平台的做法分三层：知识用「三层元模型」（实体层 3E、关系层 1 Link、策略层 7S）建模，存进 MySQL 作为唯一事实源；变更走完整治理链路（查重 → Owner 确认 → 审批 → 三方合并校验 → 发布 → 对账补偿），上线以来处理了 1477 张确认单、平均 3 天闭环、对象覆盖率 99.6%；查询侧经历了三代引擎演进——从「MySQL + GDB 按日同步」到「加 OpenSearch/Hologres 跨引擎拼装」，再到「CDC → Paimon → Flink → NeuG 单实例多模图数据库（图 + BM25 + HNSW 三索引同源）」。用 2026 年 10 月线上 9511 条真实查询回放评测：旧链路每约 25 次提问就有一次空结果，新链路为零；Top-1 命中率 54.2% 对 42.8%。平台刻意守住一个边界：只提供定义、不承担计算，也不替业务拍板口径——它保证的是「生效的是哪一版、由谁确认、从何时开始生效」都有据可查。

---

**作者判断**：

作者的最终结论落在三点：

1. **知识必须从「文档」演变为「可引用、可追溯的定义」**。过去文档默认"打开就是最新版"，人会自动核对版本；Agent 不会——它可能读到上一版定义却毫无察觉，这个默认假设彻底失效。
2. **判断一套知识是否机器可读，只需追问三个问题**：这一版是谁确认的？发生变更后，引用的上下游是否能感知？超出范围时，它会不会给出错误答案？三个问题能答上几个，就决定这套知识能被信任到哪一步；一问三不知，那不过是把静态文档搬进了数据库。
3. **平台不越界**：Agent 依然查不到"这周该看哪个口径"——这不是能力不足，而是系统分工的必然。业务口径必须由业务侧拍板，平台的核心职责是让每一次拍板都留下审计痕迹。同理，平台只保证定义和版本准确，不承担计算（不回答"这周有效订单数是多少"），因为一旦开始算数，口径变更、上游回刷、时差都会变成平台的责任。

作者还给出两条克制性判断：架构升级的触发条件应当是观测到的真实事故，而非新引擎的跑分；图遍历不等于逻辑推理，本体建模也不直接等于业务判断。

---

**核心内容**：

**一、它要解决的问题**

门店周报要报"这周多少订单"——按下单时间还是支付时间算？两种算法都说得通，报表里写死一种，业务负责人记的是另一种。写下来的总是少数，多数口径靠人记。分析师拿不准问一句就行，但 Agent 没有"问一句"的渠道，只能猜。这就是平台要解决的事：把业务对象、关系、术语、分析方法和约束组织成可版本化的知识，经确认与审批发布，通过 Web、OpenAPI、HSF、MCP 四个入口交给人和 Agent。

**二、平台架构：三层元模型 + 单向派生链路**

平台把元模型压缩成三层，每层只用很少的类型：

- **实体层（3E）**：业务里有什么——业务对象（商户、门店、订单）、语义数据集（指标 + 维度）、表对象（指向真实表）、指标（引用业务对象再落到表）。
- **关系层（1 Link）**：全平台只有一种边，由起点、谓词、终点确定；谓词来自受控词表，改谓词就等于换一条边。
- **策略层（7S）**：业务怎么做——术语、视角、事件、决策、方法论、行动、剧本七类。例：事件是"单店退款率连续三天超过 5%"，决策是"把它放进复核名单"；前者判断要不要处理，后者决定怎么处理。
- 另有**公理**：只划边界，不参与图遍历。

平台整体拆成五个模块：**挖掘、质量、场景、服务、管理**。作者解释了两组"看起来有交集却不合并"的模块：挖掘只产候选、不判对错，质量在候选变成草稿后才介入——若合并，挖掘会自我审查，只抽肯定能过的，覆盖面先垮掉；场景产出"范围"，服务产出"形态"，把范围塞进接口会长出一堆业务参数，把形态塞进场景会退化成固定查询模板。

数据层面是一条**单向链路**：生效定义统一存 MySQL，是全平台唯一事实源（规模已达万级节点与关系），下游读模型全由它派生。图库、倒排索引、向量索引损坏都能从事实源重建；反过来如果把读模型当源头用，改名、合并、回滚就得改两处，两边对不上时没有第三方能判断谁对。

**三、治理链路：让每一次变更留痕**

变更来自两个方向：人工发起（表单、批量导入、接口）和上游语义变更（数据集换来源、指标改口径）。按影响面分流：影响小、规则清晰的自动更新；需人工判断的进草稿流程。关键机制依次是：

- **提交前查重**：已发布定义 + 在途草稿放在一起，按标识和名称双向比对。以"有效订单"为例——它在数仓是字段、在接口文档是参数说明、在指标定义是公式、在业务认知里是不成文约定，同名却边界不同；Agent 拿到任何一份都会全盘接收。
- **Owner 确认**：互动卡片绑定的是最终生效的版本，不是草稿编号（绑错则确认记录挂错版本）。
- **审批时序约束**：先落审批记录、再启动流程；顺序颠倒会产生找不到对应变更的审批单。记录写入失败直接终止。
- **发布前三方合并校验**：线上值、草稿值、基线值三方比对——一致放行；仅草稿变更取草稿值；线上与草稿都改且不一致，列出冲突人工裁决，绝不静默覆盖。字段级合并是并发场景下唯一能清晰界定"改动意图归属"的手段。
- **发布后对账与补偿**：状态仅由回调推进，拒绝前端轮询猜测；对未收到回调的单据定期对账，对停滞中间态的执行发布补偿；对账与补偿必须幂等——版本号只递增一次。
- **稳定标识与外部标识分离**：改名只改外部标识，引用方无需重写。

治理数据：累计 1477 张确认单，提交到闭环平均 3 个自然日；未确认单据每日晨间催办；纳入评分对象覆盖率 99.6%，A 级占 98.3%。治理链路的责任止于发布那一刻——审批通过只代表有人为此变更负责，不保证绝对正确。

**四、查询侧：三代引擎演进**

评价一代架构看四个维度，且优先级固定：**新鲜度**（人和 Agent 看到的是否同一份数据）> **表达力**（能提多复杂的问题）> **一致性**（出错能否快速定位）> **排障与容量**（可用资源投入解决）。

- **第一代（已退出主链路）**：MySQL 既做事实源又做取数入口；DataWorks 在 ODPS 上按 ODS/DWD/ADS 分层加工；DataX 按日同步对象和关系到 GDB。取数查 MySQL，关系查 GDB。代价：数据次日才可见；只支持名称和精确字段匹配，业务口语搜不到；两库没有统一身份，关联查询要应用层两次查询拼接。
- **第二代（现役）**：同步到 GDB + OpenSearch + Hologres 三个读模型——OpenSearch 用 BM25 倒排召回、精排表达式打分，GDB 管关系，Hologres 管明细宽表，应用层按对象标识拼接。代价：向量只参与精排打分、不参与召回（缺稠密召回，语义相近字面对不上就召回不到）；搜索索引和图库刷新不同步时出现新旧混杂，排障要人工比对三处日志。
- **第三代（部分替代）**：MySQL 变更经 CDC 进 Paimon，Flink 分两条作业处理向量与图同步，连接器把节点、关系和向量 MERGE 写入 **NeuG**——图遍历、BM25、HNSW 三种索引建在同一实例上，检索结果直接就是图节点，跨引擎拼装消失。代价转移到数据链路：至少一次语义、节点必须先于边写入、删除要沿链路传播、检查点恢复要核对漏写与重复、读写同实例导致容量硬上限。

切换策略是**双跑**：同一批查询同时发两套链路，比对对象集合与排序，差异收敛后再放量；出问题退回上一代只需改一次路由。目前已切三块（管理台融合检索、场景发布后的闭包重算走影子模式、明细查询），未切两条主干（OpenAPI 检索、MCP/HSF 读接口仍打 OpenSearch 与 GDB，宽表仍打 Hologres）。

**五、第三代引擎的写入难点**

- **节点先于边**：关系落地要先找到两端节点，缺任一端时写入语句可能正常结束但什么都没写进去——不报错，只表现为"这条关系查不到"。规避办法：节点和边共用写入端，同一批先节点后关系。
- **MERGE 三层幂等**：节点（固定标识重复写只有一个）、属性（按原标识读回新值）、边（同一对端点只留一条）三个层面同时成立。
- **写租约**：同一时刻只有一个写入端持独占写权限，避免双写版本错乱；旧端失联到新端接管有空窗期，平台只承诺写入最终恢复、不承诺不中断。
- **漏写陷阱**：作业若跳过首次全量快照直接从增量起点消费，监控一直显示有进度，但已发布对象查不到——"看着在跑、其实漏一截"，比直接报错难排查。

**六、查询怎么融合，以及一个隐蔽的坑**

一次查询三段协同：关键词与向量并行召回候选 → 图扩展以候选集为种子 → 融合后可选精排。融合用 **RRF（倒数排名融合）**：三路原始分尺度不同（BM25 无上限、余弦在 [0,1]、图扩展按跳数衰减），加权求和需要为每路标定参数且只适配特定问法；RRF 只看名次、按倒数名次累加，无需标定，代价是舍弃绝对分差换跨查询稳定性。加权求和保留为对比基线，可按请求切换。

精排超时或失败时**不返回空结果**，而是保留融合顺序并在响应中标记降级状态——这个状态字段是接口契约，向调用方声明"可用性优先于排序质量"。

两跳关联查询：应用层做广度优先需 6 次网络往返、耗时超 5ms；下推到图引擎内做一次变长遍历，1 次往返、1.58ms，性能提升 3 倍。

**截断陷阱**（真实排查案例）：业务人员在图谱页面查相邻对象关联表能看到 381 个表对象，接口查同样两跳、目标类型设为表对象却返回空列表——因为接口只在最后一跳按类型过滤，且先按条数截断，恰好截掉了通往表对象的路径。给 Agent 一个空列表，它无法判断是"图里没有"还是"路径没查完"；性能保护变成了知识检索盲区。

**七、效果评测：9511 条真实回放**

用 2026 年 10 月生产环境的查询原样回放，9511 条（395 条页面检索 + 9116 条 MCP 检索词），融合检索对比全局搜索基线：

- **可用性**：页面检索中旧链路 16 条空列表、融合链路 0 条——旧链路约每 25 次提问就有一次无结果。
- **Top-1 字面命中率**：页面检索 54.2% 对 42.8%；MCP 段 14.5% 对 11.7%。综合评分 0.5103 对 0.4585。
- **失败样本归因**：395 条中 181 条（45.8%）两套链路都没有字面命中，排序策略对它们无效。拆解：中文短语与行业口头叫法 137 条、含空格混排 18、技术串与表名 14、拉丁缩写 12。根因是语料——别名没归一、指标定义缺失，只能回本体补内容，调权重解决不了。

**八、场景圈选：让查询只在允许的范围内**

一次查询要"用对"，需满足范围准确、顺序合理、证据完整、上下文可控。范围由**场景**管理：先在图上圈选策略对象为种子，沿关系扩展至实体对象，固化为**子图快照**，附仅限该子图的访问凭证。快照的价值是稳定性——今天和下周查到的必须是同一批对象，不因底层模型被改而无声偏移。

零售商品定价场景的圈选数据：起点 35 个，907 个实体对象收窄至 51 个，10709 个策略对象收窄至 1488 个，快照合计 1539 个节点、4398 条关系。

两个易错点：条件组之间是并集（OR）、组内是交集（AND），把两条限制写进同一组会整批切掉方法论和行动，且预览仍显示几百个节点，极难察觉；正向扩展不带反向引用，需两跳反向查询补齐，反向侧有 20000 节点封顶、超限静默截断。

超范围的查询直接返回不存在，绝不隐式扩大到全库——Agent 对范围外答案会信以为真。检索顺序固定为"先定位对象 → 沿关系展开 → 取明细"；395 条中纯关键词 258 条无结果、加向量召回全部找回，再叠图扩展找回数反而为 0 甚至挤出已命中目标——图扩展解决的是覆盖面，不是召回率，不能当兜底。

**九、接口定位与实际使用数据**

四个入口对内是一张对齐的能力清单：18 个方法一一对应，7 个只读、11 个写入；四端输出内容、权限点、审计一致，差异只在鉴权、参数解析、响应投影。

28 天窗口的调用数据：12 个业务应用接入生产，业务侧调用 29637 次、占平台总调用 5.4%（流量主体仍是上游语义平台自动同步）；头部两应用（智能洽谈助手、区域经营分析助手）占业务侧 67%（19929 次）；成功率 99.5%。近 28 天高频检索词中 12 个里有 7 个是补贴与价格口径（单品到手价目标匹配 1892 次、出资 628、阶梯暴涨 600、门槛 494）——被高频检索的恰恰是最容易歧义的口径。

**十、四条核心承诺的代价**

- 单一生效版本 → 代价：版本从 Git 仓改存数据库，失去分支与回放能力；
- 每次变更留痕 → 代价：写入口收敛为一个，位于关键路径，必须自带对账补偿；
- 读模型可重建 → 代价：三种索引同一次写入派生，写路径只能串行、无在线只读副本、容量硬上限（压测：空载 p99 54ms，写入端每秒 11.6 条语句时 p99 升至 119ms）；
- 范围可限定 → 代价：场景快照优先，模型修改后要等下一次圈选。

四条可迁移的避坑经验：身份与地址分离（不可变标识做身份）；约定做成构建门禁（在产物出口拦截静默退化）；数字必须带口径（代理指标不能写成相关性结论，不认领业务侧收益）；选型先看场景窗口再看引擎能力。
