# 高德路线推荐：从工业引擎到大模型 Agent 的范式跃迁

> 核心主张：路线推荐正在经历三次范式跃迁——**理解路**（RouteMind 工业引擎）、**理解人**（LLM 增强推荐 + 路线 Agent）、**理解时空**（TransitLM 端到端基座）。三者不是简单的替代关系，而是「三步并进」：工业引擎仍是长期主流，Agent 复用确定性工具、工程可控，端到端模型则把时空知识内化，代表未来的领先方向之一。贯穿始终的判断是：**LLM 与推荐引擎的分工边界决定效果上限；LLM 解不了推荐系统的稀疏性。**

## 背景与问题

### 一个日常规划需求

演讲从一个最小、最常见的需求切入：用户想「开车去公司」。

- 用户在导航应用输入起终点，系统先做 **Route Planning（Recall）**，候选规模约 `10²~10³` 条路线；再做 **Route Recommendation**，最终呈现 `1~10` 条路线。
- 路线推荐的必要性在于：**距离最短 ≠ 时间最快**，而「时间最快」也不一定体验最好。演讲给出两类典型路线：
  - 穿小区、走低级路：可能是一条捷径，运气好确实快，运气不好体验恶劣；
  - 走环路、快速路：更稳定，但未必最短。
- 因此「什么是好路」没有唯一答案。演讲给出的判据是：**用户走的路就是好路**，对应的关键指标是 **路线重合率**。

### 从「开车去公司」到「顺路加个油，不走二环」

第二个需求暴露了工业引擎的边界。用户说「顺路加个油，不走二环」，系统需要同时回答：

- 什么是「顺路」？
- 找到加油站「然后呢」？
- 「二环」是什么？

这条链路被拆成语义理解 → 语义召回 → 语义推荐，并且同时需要 **理解人** 与 **理解时空**。也就是说，自然语言需求不是检索词，而是一组需要被翻译成引擎约束的状态描述。

### 路线推荐为什么不能照搬通用推荐范式

演讲用一张对照图说明「业界推荐范式」与「路线推荐问题」的差异：

| 环节 | 业界推荐范式 | 路线推荐面临的问题 |
|------|-------------|-------------------|
| 召回 | 协同过滤 CF、向量化召回 DSSM | 道路权值计算（Dijkstra、A*、CBR）、召回排序统一性 |
| 粗排 | 蒸馏精排模型、细化召回模型 | 蒸馏精排模型 |
| 精排 | 多任务/场景学习（MMOE、STAR）、特征交叉（DCN、RankMixer）、用户行为序列（DIN、DISN） | 特征交叉要求可解释与效果兼顾；用户行为序列需要非 ID 化序列建模 |
| 重排 | Item 交叉用 attention、多样性用 MRR/DPP/Rule、序列模型用 PRM/NAR4Rec | attention 不适用、需要局部感知；多样性无法直接对齐用户需求；去冗靠规则法/阈值法，无法直接对齐需求 |
| 生成式推荐 | HSTU、One、FORGE | —— |

路线推荐的独特性被概括为三点：**超大规模路网与实时动态信息**、**路线很难唯一 ID 化**、**路线消费是强体验**。这三条决定了通用推荐的 ID 化、全局 attention、规则化去冗等做法不能直接迁移。

## 方案/架构

### 阶段一：理解路——RouteMind 工业引擎

RouteMind 由两部分组成：

- **Part 1**：CCN 全对比网络、SCASRec 生成式列表推荐、DSFNet（类 MOE，解决场景化与个性化）。
- **Part 2**：GenMRP 生成式多路线召回，解决召回与排序的一致性问题。

架构图显示：非 ID 化序列建模（Scene/Positive/Negative 经 Pair DIN，Scene Mode 经 HSTU）进入 DSFNet 做多场景解耦建模；CCN 对候选路线做全对比；SCASRec 以 Stepwise Corrective Reward 做生成式列表推荐；GenMRP 以 Link Memory & Cost Model 与 Correctional Boosting 生成多路线召回；最终输出路线序列并以 `EOR` 结束。

#### CCN：全对比网络（RecSys 2026）

- 核心是适配**非 ID 化、局部感知、可解释**的 item 交叉方法。
- 引入**对比级特征** `N × N × R`，量化任意两条路线的非重叠路段差异，增强局部感知。
- **全对比**假设共现的 item 需要互相对比判断好坏并汇总，在候选 item 交叉上超越传统 self-attention，更适合推荐场景。
- **可解释网络**按特征物理含义划分 Field，Field 内交叉、Field 间独立；可解释性打分用于标签感知和 case 调查。

公开数据集上，CCN（w/o PSN, X^c）的 AUC 为 **76.72%**，高于 DSFNet 的 75.04% 与 DSFNet-SA 的 75.87%。全量落地高德路线规划后：

- 覆盖驾车、新能源、公交、骑行、货车、摩托车等场景；
- 各场景首路线效果提升，例：**公交首选率 +7pct**，**驾车局部差 -10%**；
- 自解释系统成为 case 调查的标准方案。

#### SCASRec：生成式列表推荐

- 以**边际路线重合率**为目标的生成式列表推荐，统一精排、重排、去冗，减少对人工规则的依赖。
- 基于全对比做候选集合的 encoder 与 decoder。
- **时间步修正奖励（SCR）**：在每个时间步，以「继续推荐能带来多少额外路线重合率」为奖励信号，动态平衡质量与多样性。
- **推荐停止符（EOR）**：把 EOR 作为 SCR=0 时的生成目标，自动停止推荐，实现去冗模型化。

公开数据集上，SCASRec 的 HR@2/HR@3、LCR@1/2/3、MRR 均领先对比方法（HR@1 42.64、HR@2 77.65、HR@3 94.92、LCR@1 61.11、LCR@2 79.21、LCR@3 85.23、MRR 0.541）；表中 NAR4Rec 的 HR@1 为 42.70，略高于 SCASRec。全量落地后：

- 驾车下发路线**重合率 +0.6%**；
- **多样性差 -40%**；
- **差路 -50%**。

#### GenMRP：生成式多路线召回（CIKM 2026）

- 演讲称其为**行业首个可落地请求级多路线召回模型**。
- 基于当前环境、用户历史序列、link 动静态属性、用户熟悉度、热力，动态建模道路权值（路权 = 边 cost）。
- **校正提升机制**：以修正权值可能带来的重合度收益为导向，尽量使路线生成过程尽快覆盖用户实走，同时保证召回路线之间的多样性。
- **增量推理优化**：线上推理每轮只更新「复用次数变化」的道路权值，用微小效果损失换取**推理耗时 ↓78%**。

公开数据集上 GenMRP 在 Set1~Set4 取得 84.0/85.9/84.6/85.6，对比 KST 的 79.4/76.8/78.5/76.1；表中 RT 为 173.5ms，KST 为 18.5ms（该表同时暴露了效果与耗时的权衡）。全量落地驾车路线规划后：**路线重合度 +0.54%、路网重合度 +0.67%、路线多样性 +6.5%**。

#### 小结：引擎能优化路，但不理解人

CCN、SCASRec、GenMRP 把「理解路」做到了高水位，但系统仍然：

- 无法直接输入自然语言需求；
- 无法预先枚举复杂的时序、顺路、避让、偏好组合；
- 核心矛盾变成「人话」到「引擎约束」的翻译。

### 阶段二：理解人——从 LLM 轻量增强到路线 Agent

演讲把这一阶段分成两步：**LLM 增强推荐 → 路线 Agent**。

#### LLM 增强推荐：以 query 逆向生成为基础

- 免训法效果差：通用模型缺少路线知识，在效果或效率上较差。
- 模型范式取舍：LLM2Rec / Rec2LLM，本质是效果与效率的平衡。
- **四阶段逆向 query 生成**：由召回路线描述与基于规则的意图 COT，生成 query、answer，再经 judge 与语料生成（input：召回路线描述 + query；output：cot、target、answer），最后用 SFT + DPO + 人工评测训练 LLM，以抑制幻觉。
- 运行时走两条路径：
  - **LLM AS EMBEDDER**：用户 query 经 LLM 做 embedding，输入 RouteMind，负责高频简单 query；命中后返回推荐路线、模板化回复、模板化标签。
  - **LLM AS RECOMMENDER**：上下文对齐到文本，LLM 直接推荐路线并回复，负责复杂 query；未命中高频库时走这条路径。

效果与落地：

- 简单 query 上，**语义推荐优良率 80%**；
- **定制结果接受率比普通动态推荐路线高 50%**；
- 接入上游 Agent，与车企合作。

但该方案有明显缺陷：

- 性能要求高，一步出结果，提升空间小；
- 泛化性差，多样性 query 无法满足；
- 无环境和历史上下文；
- 推荐和感知割裂，无法同步进行推荐解释。

#### 路线 Agent：Agentic 交互式推荐

架构由以下要素组成：

- **全操作 Query 化**：语音、文字、点击、选择都统一成 query；
- **Agent Loop**：根据上下文不断进行必要的信息获取，包含上下文管理、错误处理及恢复、Proactive 追问；
- **Memory**：短期、长期、全域历史；
- **100+ 工具 / Skills**：路线召回、路线推荐（RouteMind）、POI 搜索工具、天气、路况等；
- **扩增工具返回候选数量**，视为高质量召回；
- 最后接 **LLM 推荐头**，同步生成推荐、理由、回复、交互，做到「四合一」。

产品示例（演讲展示的高德 AI 定制路线）：

- 「拎着行李箱出行，选一条不走台阶的路」——全程平路无台阶；
- 「绕景区骑行，选一条起终点相同的路」——骑行兜风、骑行友好；
- 「十一期间走高速，选一条走高速免费的路」——生成省钱的长途路线；
- 「夜里走回酒店，优先照明好、人多一点的道路」——途经繁华路段、照明充足；
- 「十一新能源长途充电，每隔一段路安排一个充电站」——无需手动拼接路线。

「顺路加油，不走二环」的 case 展示了 Agent 的输出：推荐路线全程不走二环、途经新源南路，并顺路经过中国石油首汽 6 号加油站，无需额外绕行；同时给出加油站位置、特点、油品与导航入口。

#### MobilityBench：路线规划 Agent 的评测基准（KDD 2026）

演讲称其为**首个面向真实世界出行场景的路线规划 Agent 基准**，与中科大合作：

- **真实大规模数据**：从海量、脱敏的真实用户 query 中提炼，从最简单的「A 到 B」到带顺路、避让、偏好、时序约束的复杂任务；页面截图显示覆盖 100,000+ 真实用户 query、22 个国家、350+ 城市、4 个任务族下的 11 类任务。
- **多维评测协议**：不仅看最终输出「对不对」，还分别评估指令理解、规划能力、工具使用、决策、效率等子能力；页面列出 5 个评估支柱（Instruction Understanding、Planning、Tool Use、Decision Making、Efficiency）。
- **确定性 API 回放沙箱**：把所有依赖的地图服务「录」下来，评测时做确定性回放，让评测可重现、可对比；截图显示缓存生产 API 响应以冻结交通条件。
- **评测方法**：Outcome-Centered Assessment，超越主观判断，验证可执行正确性与事实依据。

关键发现：

- **最强模型也只做对 60+%**：真实场景下的路线规划 Agent 远没有被解决；页面排行榜中 Gemini-3-Pro-Preview 的 Final Pass Rate 为 69.09%，DeepSeek-V3.2-Exp 为 68.88%，Gemini-3-Flash-Preview 为 67.9%，Qwen3-235B-A22B 为 66.69%（截图仅展示部分行）。
- **真值构造正确性验证**：用真值对 **4B 小模型做 SFT**，最终通过率直接追平 **235B 级通用大模型**。
- **指导线上迭代**：路线 Agent 质量评分累计提升 **28.5%**。
- **持续进化**：Benchmark 本身不断更新，v2、v3，覆盖个性化、长程任务等。

#### 后训练：把 prompt 知识与工具规范内化

- 核心目标：提升稳定性、降低推理成本、提升速度，把大量 prompt 知识与工具调用规范内化到模型。
- 效果：减少工具调用轮次、降低对长 prompt 的依赖，让 Agent 更稳定地完成复杂任务；**质量分提升 10%+，耗时降低 50%+**。
- 演讲给出「后训练收益预期随基模发展」的示意：柱状图随基模发展（横轴 T）呈现「效果类收益递减，稳定、成本、速度类收益递增」的趋势。该图为趋势示意，未给具体坐标数值。

#### Agent 的天花板：仍在「查地图」

Agent 已经能理解人、推荐路线和解释，但上限受工具能力制约：每一步都要调用外部的算路引擎、POI 搜索、ETA 服务。演讲由此提出一个挑衅性的问题：**能不能不查地图，让模型把时空知识内化，直接「想」出路线？**

### 阶段三：理解时空——TransitLM 端到端生成路线

TransitLM（NeurIPS 2026）的定位是**端到端、Map-free、时空知识内化**，并定义配套 benchmark。

- **路线规划传统方法**：多阶段，工业验证充分，但成本高、灵活性差。
- **通用 LLM**：端到端，但缺少评估 benchmark，实验发现时空理解能力很差。
- **TransitLM**：端到端，直接从数据中学习公交路线规划。

数据与训练：

- **数据规模**：4 个城市（北京、上海、深圳、成都），**1300 万+ 真实公交路线记录**，覆盖 **12 万+ 站点**、**1.3 万+ 公交/地铁线路**；页面截图为 120,845 stations、13,666 lines、13M+ route records。
- **训练方法**：Station 作为新 token，**CPT → SFT**，覆盖最优路线、偏好路线、多路线生成 3 个任务；截图显示 CPT 三类数据（route/station/line）按比例对齐，SFT 3 个任务各 30K 样本，基座规模 0.6B/1.7B/4B。
- **评测体系**：连通性、上下车站可达性、路线重合度、数值预测准确性等多个维度；截图列出 3 个评测任务（ORG/PRG/DRG，各 10K）与 5 类 10 项指标。

关键发现：

- **可行**：TransitLM 打平线上工业级规划服务、打平 Agent + 工具范式。
- **时空知识内化**：仅输入 GPS 坐标即可规划，无需任何显式坐标映射或地理数据库。
- **泛化性**：在各任务上，多任务 SFT 优于单任务，证实时空知识是任务无关的。
- 演示地址：`https://transit-lm.amap.com/`；演讲称该工作引起广泛关注。

### 两条路线的辩证：Agent 与端到端

演讲的判断是「**两条都会赢，只是节奏不同**」。

| 维度 | Agent 路线 | 端到端路线 |
|------|-----------|-----------|
| 优点 | 快：复用工具、工程可控；稳：路线由确定性工业引擎产出，安全、可追溯 | 架构极简：模型即系统；天花板高：时空知识内化，涌现能力强大；可成长：和数学、编程领域类似，数据越多、模型越大、效果越强 |
| 局限/硬骨头 | 依赖传统导航服务，解决不了引擎本身的天花板 | 动态信息（拥堵、站点增减）LLM 不擅长；可控性、可解释性、安全性需建立一套护栏 |
| 定位 | 路线规划的长期主流 | 未来的领先方向之一 |

能力演进示意图显示：Agent 路线快速上升后进入平台期；端到端 RLLM 起步较低但加速度更大，远期与 Agent 路线出现交叉点。该图为趋势示意，未给具体时间与数值。

### 三次范式跃迁总表

| 阶段 | 核心矛盾 | 关键技术 | 范式 |
|------|---------|---------|------|
| 理解路 | 非 ID 化 + 强体验 + 多样性 / 召排割裂 | CCN + SCASRec / GenMRP | 工业引擎 |
| 理解人 | 自然语言需求 + Agentic 推荐 + 速度×质量 / 迭代基准 | LLM2Rec + Rec2LLM / Agent / 后训练 / MobilityBench | LLM 增强 + Agent |
| 理解时空 | 模型依赖外部工具 / 时空知识理解 | TransitLM | 端到端基座 |

演讲强调「高德路线推荐，正在从工业引擎、Agent 到时空基座，三步并进」——不是第三代取代前两代，而是三条路线同时推进。

## 关键工程做法

1. **先把评价指标定成「用户实走」**：路线重合率既是 CCN/SCASRec/GenMRP 的训练目标，也是线上迭代的北极星；SCR、EOR、校正提升都围绕它设计。
2. **用「对比级特征」替代通用 attention**：路线是非 ID 化的序列，任意两条路线的非重叠路段差异才是关键信号；CCN 的 `N×N×R` 对比特征与 Field 划分同时服务效果与可解释性。
3. **把精排、重排、去冗统一成生成式列表任务**：SCASRec 用 SCR 在时间步上平衡质量与多样性，用 EOR 把「停止」变成可学习目标，减少人工规则。
4. **召回阶段直接建模路权，而不是给路线打 ID**：GenMRP 用环境、历史、link 属性、熟悉度、热力动态生成路权；线上只更新复用次数变化的道路权值，以微小效果损失换 78% 推理耗时下降。
5. **LLM 增强阶段按 query 难度分流**：高频简单 query 走 LLM as Embedder + RouteMind，复杂 query 走 LLM as Recommender；用四阶段逆向 query 生成 + SFT/DPO 抑制幻觉。
6. **Agent 阶段把「所有操作」都 query 化**：语音、文字、点击、选择统一入口；Agent Loop 负责上下文、纠错、追问；工具返回的候选扩增被视为高质量召回；最后由 LLM 推荐头一次性生成推荐、理由、回复、交互。
7. **先造 benchmark 再谈优化**：MobilityBench 用真实脱敏 query、多维子能力评分、确定性 API 回放沙箱，让 Agent 迭代可重现、可对比；并用真值 SFT 验证「小模型也能追平大模型」。
8. **后训练瞄准稳定性、成本、速度**：把 prompt 知识与工具调用规范内化，减少工具轮次与长 prompt 依赖，而不是只追求效果分数。
9. **端到端路线从「数据 + token 化 + 多任务」入手**：Station 作为新 token，CPT→SFT，三任务联合训练；只输入 GPS 坐标，不依赖显式地理数据库。

## 经验与边界

### 三个 takeaway

1. **矛盾是最好的创新驱动力**：路线推荐的非 ID 化、强体验、召排割裂等矛盾，直接催生了 CCN/SCASRec/GenMRP。
2. **LLM 与推荐引擎的分工边界决定了效果上限**：LLM 负责理解人、生成理由与交互，引擎负责确定性、可追溯的路线产出。
3. **LLM 解不了推荐系统的稀疏性**：覆盖所有场景的推荐基座是理想，但这条路可能比想象中更长。

### 明确的能力边界

- **Agent 的上限受工具制约**：Agent 仍在「查地图」，每一步依赖外部算路引擎、POI、ETA；工具能力不提升，Agent 的效果上限就被锁住。
- **端到端并非全能**：动态信息（拥堵、站点增减）是 LLM 不擅长的硬骨头；可控性、可解释性、安全性需要额外护栏。
- **TransitLM 的验证范围是公交**：4 个城市、公交/地铁线路，不是驾车全场景；演讲未给出跨城市、跨交通方式的泛化数据。
- **GenMRP 的耗时权衡**：公开数据集表中 RT 173.5ms，明显高于 KST 的 18.5ms；线上通过增量推理把耗时降 78%，但未给出降后的绝对值。
- **LLM 增强推荐的缺陷未被完全解决**：一步出结果、泛化性差、无环境与历史上下文、推荐与感知割裂，这些是转向 Agent 的直接动因。
- **原文未提供的细节**：各模型的训练数据规模、线上 A/B 的置信区间、路线 Agent 的端到端延迟与成本、TransitLM 与工业服务的具体差距数值，演讲均未展开（不确定）。

### 未来展望

演讲给出的长期方向是**时空智能：时空领域基座模型**——把地理空间编码进一个统一的大模型，覆盖道路、POI、路线、事件、拥堵等，满足任何时空需求、回答任何时空问题。
