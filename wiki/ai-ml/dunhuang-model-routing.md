# 敦煌网企业模型路由与治理

> **核心主张：** 企业 AI 的竞争力来自"可控的模型组合"，而不是一次采购选出的"最强模型"。应以任务维度建立能力画像，在任务边界内择模并保证单轮次执行不换模，用单位有效任务成本而非 Token 单价衡量 ROI，把成本、风险与体验放进同一治理闭环——把"模型选择"从一次采购决策升级为持续优化的系统能力。

## 背景与问题

### 单模型策略难以同时满足五个目标

模型能力差异扩大后，"一把尺子"会把局部最优放大为系统性约束。原文列出五个必须同时满足的目标：

1. **质量**：高难推理 / 代码 / 多模态
2. **成本**：按任务价值匹配投入
3. **速度**：交互体验与吞吐
4. **可用性**：故障与区域波动
5. **合规**：数据与安全边界

核心问题不是寻找唯一"最强模型"，而是根据性价比，为不同任务边界选择、路由恰当模型，并让选择可解释、可追踪、可治理。

### 已有基础设施：统一大模型网关

敦煌网此前的形态是统一接入层：

- **生产应用**：DHwork、DHcoder、ChatBI
- **AI Gateway**：统一接入 / 鉴权 / 计费 / 审计
- **模型供给**：文本模型（DeepSeek、GLM 等）、多模态（通用视觉模型）、视频模型（Seedance）、声音模型（Minimax、Doubao 等）
- **自研模型**：飞天大模型（跨境电商领域多模态模型）
- **部署形态**：IDC 私有部署、云环境私有部署、公共商用模型接口
- **触达与协同入口**：XX 协同办公、Agent 市场、Skill 市场、MCP 市场

网关解决了"统一接入"，但没有解决"为每个任务选对模型"。

## 方案/架构

### 能力画像：用任务维度而非品牌比较

能力矩阵的行是任务场景，列是模型角色（原文以模型 A/B/C/D 匿名化）：

| 场景 | 模型 A 深度推理 | 模型 B 通用效率 | 模型 C 多模态 | 模型 D 低成本 |
|------|----------------|----------------|--------------|--------------|
| 上下文 / 知识问答 | 4 / 5 | 4 / 4 | 4 / 5 | 4 / 5 |
| 复杂推理 | 5 / 5 | 5 / 4 | 5 / 5 | 5 / 5 |
| 代码 / 工具调用 | 5 / 5 | 5 / 5 | 5 / 5 | 5 / 5 |
| 多模态理解 | 4 / 4 | 4 / 1 | 4 / 4 | 4 / 4 |
| 翻译 / 结构化输出 | 4 / 4 | 4 / 4 | 4 / 4 | 5 / 4 |
| …… | 4 / 4 | 4 / 4 | 4 / 4 | 5 / 1 |

原文明确标注：分值为内部评估维度示意，非外部排名。矩阵的价值在于让"适配"成为可比较的管理语言——**模型能力画像 = 任务选择的共同底座**。

### 模型配置的四个维度

在路由管理界面中，每个模型配置包含：

1. **上下文长度**（如 1,000,000 tokens）
2. **推理 vs 价格**（如 3/5 vs 1/5，表示能力与成本档位）
3. **适用场景说明**（如"轻量模型，响应快，适合中等难度问答与高频轻任务"）
4. **工具能力**（是否支持工具调用、文件、图片、多模态输入）

### 先定义任务边界，再做模型选型

四步法：

| 步骤 | 内容 |
|------|------|
| **1 任务分类** | 推理 · 代码 · 对话 · 多模态 |
| **2 运行约束** | 时延 · 预算 · 地域 · 可用性 |
| **3 风险边界** | 数据分级 · 工具权限 · 合规 |
| **4 模型池匹配** | 能力画像 · 版本 · 降级策略 |

关键原则：**在任务边界内选择模型，在单轮次执行过程中保持模型一致。** 原文强调任务边界是质量、风险和成本的共同控制点，不让"模型品牌"代替业务判断。

### 一次执行只选一次：Redis 粘性绑定

主 / 子智能体各自固定模型；网关工具续请求复用粘性绑定，避免中途切换带来的上下文与行为漂移。

请求链路（大模型网关 SDK 无感智能路由）：

```
标准开放 SDK 请求（OpenAI / Anthropic / …）
        ↓
协议标准化（统一请求语义与格式）
        ↓
model = Auto?
   ├─ 否 → 原有链路 → 匹配 route_key（沿用上游查找/协议转换）
   └─ 是 → 新的真实用户输入? → Router Service（能力画像 + fallback + trace）
                                   ↓
                              Redis（route_key → selected_model，带 TTL）
                                   ↓
                        命中：复用 selected_model
                                   ↓
                        已配置模型 → 按原协议返回结果
```

四个设计要点：

1. **标准 SDK 兼容**：OpenAI / Anthropic / Google 入口与响应协议保持不变
2. **同轮不换模**：只有真实输入算新任务边界；tool_result 不是新意图
3. **Redis 粘性**：route_key + selected_model，设置 TTL 缓存；命中后不重路由
4. **可观测 / 可降级**：trace、version、候选策略；Router 异常可安全回退

### Auto 智能决策与显式选择必须分离

- **Auto 模式**才进入 Router；显式模型保持原有链路，既保障体验，也降低迁移风险。
- 每次新任务或新追问决定一次模型；同一 Agent Loop 内保持模型一致。
- 子智能体以自身任务独立决策，不继承父 Loop 的模型。
- 失败按链路降级（fallback_model 列表兜底）。

### 独立 Router Service

以统一决策内核服务不同入口：

- **端应用（DHwork）**：主 / 子 Agent Auto 路由，Loop 内固定模型
- **独立 Router Service**：能力画像、决策策略、模型池版本、fallback、trace / reason code
- **应用服务（大模型网关）**：跨应用入口，工具续请求 Redis 命中

业务优先级：**先验证"选得对"，再规模化"管得住"**。

### 统一分层治理

治理不是上线后的附加项，而是多模型组合能够规模化运营的前提。原文给出五向治理：

| 方向 | 内容 |
|------|------|
| **应用内部分类分级** | 应用内分类分级，如代码补全等 |
| **应用内部智能路由** | fallback · 限流 · 故障转移 |
| **模型网关统一治理层** | 策略 · 观测 · 审计 · 发布 |
| **可观测** | trace_id · 原因码 · 成本 |
| **安全** | 数据分级 · 权限 · 脱敏 |
| **兼容** | 显式链路 · API 回归 |
| **灰度** | 模型池版本 · 小流量验证 |

### 五项上线验收

1. **有效模型池选择**：任务与能力画像匹配，输出可解释
2. **应用主 / 子 Loop 固定**：同一 Loop 内不因工具调用中途换模
3. **网关续请求 Redis 命中**：命中后不重路由，保留执行一致性
4. **显式模型回归**：用户显式指定模型时，链路行为保持一致
5. **失败可观测、可降级**：trace 追溯原因，fallback / 限流可生效

上线门槛：**可解释 · 可复现 · 可回退**。

### 四阶段实施路径

| 阶段 | 能力目标 |
|------|---------|
| **01 能力评估** | 任务地图、能力画像、模型池准入 |
| **02 路由建设** | Auto / 显式分离、Router、Redis 粘性 |
| **03 治理完善** | 观测、安全、灰度、降级与验收 |
| **04 规模优化** | 成本策略、模型池迭代、运营闭环 |

推进原则：从高价值、低风险的任务开始；每次扩大范围，都以指标与验收作为下一阶段的入口，避免"一次性大改造"。

## 关键工程做法

### 路由管理的数据模型

路由管理界面包含三个视图：**模型池、场景管理、路由日志**。

- **模型池**：模型目录 + 它在哪些场景上被绑定；同一模型可以在 A 场景排第一、在 B 场景当最后一道保险。
- **场景管理**：场景标识是调用方在 `/api/route` 里传的字符串；只能使用字母、数字和 `-`、`_`，最长 64 位；场景说明会进入决策模型的提示词，告诉它"这是哪一类流量"。
- **路由日志**：每一次决策一行，入参全量落库；列表里每个字段带 2000 字符预览，展开时自动拉取完整内容；记录命中模型、决策、来源、上下文长度、附件、候选、耗时、query。

日志中的"决策详情"会拆出候选模型列表与打分依据，例如：

```
候选：5.6-terra-dhwork, deepseek-v4-pro-dhwork, deepseek-v4-flash-dhwork …
决策详情：适合推荐排序与脚本任务
上下文明细：用户 query 124 字符 / system 提示词 22218 字符 / 历史对话 13227 字符
```

原文强调：客户端的超时、取消、错误不进入决策；只有真实用户输入才算新任务。

### 一致性的三个抓手

1. **同轮不换模**：工具调用后的续请求不重新路由。
2. **Redis 粘性**：`route_key` 映射到 `selected_model`，带 TTL；命中即复用。
3. **父 / 子 Loop 独立**：子智能体按自身任务独立绑定，不因父级切换而漂移。

### 评测与观测口径

- 每次路由输出结果、原因码、成本、时延，统一回传。
- trace_id 贯穿请求，便于追溯"为什么选了这个模型"。
- 路由日志支持按场景、模型、会话、只查兜底 / 只查被拒筛选。

## 数据与效果

### 智能路由上线前后（内部案例）

上线时间：**8 月 20 日左右**。

| 指标 | 上线前 | 上线后 |
|------|--------|--------|
| 每百万 Token 花费 | $1.2–$2.3 / 百万 | 明显降至 ~$0.3 / 百万 |
| 每日人均 Token | 2M–6M / 日 | 持续涨至 12M–18M（峰值近 18M） |
| 使用人数 / 调用次数 | 持续增长 | 持续增长 |
| 整体账单 | — | 降至之前的约 60% |

结论：在使用人数、调用次数增加的同时，整体账单反而下降至之前的约 60%；每百万 Token 花费显著下降，在支撑业务规模与人均用量增长的同时实现总成本缩减。

### Auto 路由效果统计（随机抽取一天）

样本：815 轮用户对话；路由选择记录 971 条。

- **Luna 是当前主力模型**：全量记录占 **80.64%**。
- **DeepSeek 在定时任务中占 74.39%（61/82）**，在用户直接请求中仅占 **9.08%（74/815）**。
- 路由选择模型饼图：Luna 81%、deepseek-v4-flash 16%、sol 3%。
- 用户直接请求分类（815 条）：研发测试与技术排障 20%、图片与视觉设计 18%、知识咨询与业务研究 16%、文案与文档整理 15%、数据查询与分析 15%、办公协作与流程操作 13%、信息不足或闲聊 3%、监控巡检与自动日报等其余类别。

原文的解读是：不同任务类型确实被分到了不同模型，定时任务与用户即时请求的模型分布差异明显。

### ROI 口径：相对全量 Sol 的成本

| 方案 | 相对成本（全 Sol = 100） |
|------|------------------------|
| 全部使用 Sol | 100 |
| **智能路由** | **7.39** |
| 全部使用 Luna | 5.00 |

原文结论：相比全部使用 Sol，智能路由估算节省成本 **92.61%**，路由后成本约为原来的 **7.39%**。

### 案例 01：工程任务成本治理

场景：10 个复杂模块自动化重构与单元测试修复；仅 CI/CD 与合规审查均通过才算有效任务。

| 方案 | 首轮通过率 | API 成本 | 返工成本 | 其他 | 总成本 | 单位有效任务成本 |
|------|-----------|---------|---------|------|--------|----------------|
| A 纯低价通用模型 | 35%（平均重试 3.2 次） | ¥160 | 约 ¥13,000 | — | ¥13,160 | **¥13.16** |
| B 智能路由 | 88% | ¥450 | 约 ¥1,200 | 路由 ¥50 | ¥1,700 | **¥1.70** |

结论：一次"看似便宜"的调用，可能换来多轮修复、测试与审查；应以单位有效任务成本决策。工程总账 = 调用成本 + 返工成本 + 审核与风险校正。

### 案例 02：高风险审核路由

场景：每月 10,000 笔高风险客诉与赔付政策智能初审；正确、依据准确且不触发二次仲裁/合规追责才算有效。

| 方案 | 分配方式 | 成本构成 | 总成本 | 单位有效任务成本 | P95 |
|------|---------|---------|--------|----------------|-----|
| A 单一大模型统包 | 所有请求交给同一强模型 | 调用 ¥5,000 + 风险校正 ¥500 | ¥5,500 | **¥0.55** | 5.2 秒 |
| B 智能路由 | 85% 常规走轻量模型 · 15% 疑难走强推理 | 常规 ¥425 + 疑难 ¥1,125 + 风险 ¥700 + 网关 ¥100 | ¥2,350 | **¥0.24** | 1.1 秒 |

结论：ROI 不是单价最低，而是能力、风险、时延与成本的组合最优；轻量模型承接高频常规任务，强推理模型聚焦疑难任务，形成更低的有效成本与更快的 P95。

## 经验与边界

1. **不要用品牌代替业务判断**：能力画像必须落到任务维度（上下文、推理、代码/工具、多模态、结构化输出），而不是"谁最强"。
2. **单轮次不换模是硬约束**：中途换模会带来上下文与行为漂移；一致性优先于"每一步都选最优"。
3. **Auto 与显式选择分离**：显式指定模型的用户链路保持原样，既保障体验，也降低迁移风险。
4. **ROI 要用"单位有效产出"**：公式为 `单位有效任务成本 =（调用成本 + 平台成本 + 返工/风险校正）÷ 可验证的有效任务数`，并搭配质量阈值、P95 时延、失败率、降级率共同观察，避免以低价换低效。
5. **没有真实财务数据时，用可审计的框架建立对话**，而不是用未经验证的数字承诺。
6. **治理必须前置**：可观测、安全、兼容、灰度是规模化运营的前提；上线门槛是可解释、可复现、可回退。
7. **不是所有请求都用最强模型，也不是所有请求都用最便宜模型**：最优组合是按任务难度分配能力。
8. **落地要分阶段**：先能力评估，再路由建设，再治理完善，最后规模优化；从高价值、低风险任务开始。
9. **适用前提**：先厘清数据边界、任务质量标准和人工兜底机制，再定义试点成功条件。
10. **原文未展开的部分**：Router 的具体模型选择算法（如何打分、如何训练）未披露；多模态 / 视频 / 声音模型是否纳入同一路由策略，原文只列出模型供给，未说明路由覆盖范围。
