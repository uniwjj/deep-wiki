# 本体论：从哲学到工程

> **一句话定位：** 本体论走过了一条"从'关于存在的思辨'到'关于知识的建模'"的路：哲学追问"什么是存在"，工程师追问"什么是可计算的业务对象"（2.1.3 节 / PDF 第 26 页）。第 2 章把这条路拆成两段——**哲学史**（亚里士多德 → 康德 → 分析哲学）与**计算机科学四代演进**（术语表与分类体系 → 帧与语义网络 → 描述逻辑与 OWL → 知识图谱与工业本体）；再用三个案例辨析"本体 ≠ 知识图谱"；最后落到国家标准 **GB/T 48000.3—2026** 对本体建模的具体要求（2.5 节 / PDF 第 35 页）。

本页是全书第一篇的第二站：向上承接 [[semantic-gap]] 提出的"语义供给需要本体"，向下引出 [[ontology-semantic-infrastructure]]（本体作为智能体的语义基础设施）。它与 wiki 已有的 [[ontology]] 页互补——后者讲本体论作为 AI 基石的**五要素框架与产业案例**，本页补的是**哲学史脉络、四代技术演进、本体与知识图谱的工程辨析、以及国标对本体建模的硬性要求**。

## 1. 本体论的哲学起源（2.1 节 / PDF 第 25—26 页）

### 1.1 词的来历

"本体论"（Ontology）源自希腊语 **"ontos"（存在）** 与 **"logos"（学问）**，字面意思就是"关于存在的学问"。

### 1.2 亚里士多德：十范畴与"本质 / 属性"之分（PDF 第 25 页）

亚里士多德在《形而上学》中提出：哲学的首要任务是研究"**作为存在的存在**"——即一切存在物之所以为存在的最基本原因和原理。

**十范畴**（原文顺序）：实体、数量、性质、关系、地点、时间、姿态、状态、动作、遭受。原文评价："这可以看作是人类历史上第一个系统化的本体论框架。"

| 亚里士多德的区分 | 回答的问题 | 原文例子（一张桌子） |
|---|---|---|
| **本质** | "是什么" | 用来放置物品的家具 |
| **属性** | "怎么样" | 木制的、棕色的、一米高的 |

原文判断："这种区分，深刻影响了后世的哲学和计算机科学。"

### 1.3 康德：把本体论从"世界"转向"认知框架"（PDF 第 25 页）

| 维度 | 康德的观点（原文） |
|---|---|
| 认识边界 | 人类只能认识"**现象世界**"，无法认识"**物自体**" |
| 本体论任务 | 不是描述"世界本身是什么"，而是描述"**人类理解世界的基本范畴**" |
| 范畴体系 | **十二范畴**，分 **量、质、关系、模态** 四大类 |
| 历史意义 | 把本体论从"关于世界的学问"转向"关于人类认知框架的学问"，"为后来计算机科学中的'知识表示'埋下了伏笔" |

### 1.4 分析哲学与形式化转向（2.1.2 节 / PDF 第 25 页）

20 世纪初分析哲学兴起，弗雷格、罗素、维特根斯坦致力于用逻辑语言精确表达哲学概念；罗素与怀特海在《数学原理》中试图把全部数学建立在逻辑之上。哲学家开始用形式化语言描述"存在"与"关系"：

| 自然语言 | 形式化表达（原文） |
|---|---|
| A 是 B 的一部分 | `PartOf(A, B)` |
| A 导致 B | `Causes(A, B)` |

原文结论："这种形式化表达，使得哲学概念可以被机器处理……为计算机科学中的本体论奠定了方法论基础。后来计算机科学家所说的'本体'，本质上就是用形式化语言表达的知识体系。"

### 1.5 从哲学到计算机科学的跨越（2.1.3 节 / PDF 第 26 页）

| 时间 | 人物 | 贡献（原文） |
|---|---|---|
| 20 世纪 80 年代 | 人工智能进入**知识工程**阶段 | 要让机器"理解"人类知识，首先需要将知识形式化；哲学研究了 2000 多年的"本体论"由此被引入计算机科学 |
| **1980 年** | 约翰·麦卡锡（John McCarthy） | 提出智能系统需要一个"本体"来描述世界："**一个程序要具有常识，就需要一个包含常识知识的形式化本体。**" |
| **1993 年** | 斯坦福大学托马斯·格鲁伯（Thomas Gruber） | 给出计算机科学中"本体"的经典定义 |

**格鲁伯定义**：**"本体是对特定领域知识的形式化、显式化规范说明。"** 定义的关键在于三个词：

| 关键词 | 英文 | 原文要求 |
|---|---|---|
| **形式化** | Formal | 本体必须用**机器可读**的语言表达，不能是自然语言的模糊描述 |
| **显式化** | Explicit | 本体中定义的概念、属性和关系必须是**明确声明**的，不能隐含在代码或文档中 |
| **规范说明** | Specification | 本体是对领域知识的**抽象描述**，不是某一个具体系统的实现细节 |

原文对这次跨越的概括：**"格鲁伯的定义，将哲学本体论从'关于存在的思辨'转变为'关于知识的建模'。哲学家追问'什么是存在'，工程师追问'什么是可计算的业务对象'。"**（PDF 第 26 页）

> 该定义与 wiki 已有的 [[ontology]] 页所载 Tom Gruber 定义是同一句，两页可对照阅读。

## 2. 本体论在计算机科学中的四代演进（2.2 节 / PDF 第 27—29 页）

这一节是本章的主干，按"第一代 → 第四代"递进，每一代都在补上一代的能力缺口。

| 代 | 名称 | 代表技术/知识组织 | 新增能力 | 核心缺陷（原文） |
|---|---|---|---|---|
| **第一代** | 术语表与分类体系 | 杜威十进制分类法、中国图书馆分类法；ICD 疾病分类、ATC 药物分类；林奈物种分类 | 层级结构 + 唯一标识 + 上下位关系 | "通常只定义概念本身，不定义概念的属性和概念之间的关系"；只能回答"手机属于什么类别"，不能回答"手机的屏幕尺寸是多少""手机使用什么操作系统" |
| **第二代** | 帧与语义网络 | 明斯基的"帧"（Frame，70 年代）、索瓦等人的"语义网络"（Semantic Network） | 帧带"槽"（槽名 + 槽值），语义网络用节点/边表示概念与关系 | "缺乏形式化的语义定义"——一个"属于"可以是物理位置的属于，也可以是管理归属的属于，机器无法准确理解 |
| **第三代** | 描述逻辑与 OWL | 描述逻辑（90 年代）、W3C 于 **2004 年**发布 **OWL** | 严格语法语义 + 自动推理；成为本体建模的标准语言 | ——（这一代解决了第二代的形式化缺口） |
| **第四代** | 知识图谱与工业本体 | 谷歌 **2012 年**发布 **Knowledge Graph**；近年工业界的本体 + 知识图谱结合 | 图结构、大规模知识存储与查询；本体定义 Schema、知识图谱存实例 | 知识图谱"通常只存储实例数据，不定义 Schema。没有 Schema 的约束，实体和关系可能混乱、矛盾、不可信" |

### 2.1 第一代：术语表与分类体系（2.2.1 节 / PDF 第 27 页）

原文给出一个**产品分类本体**的树形结构（本书对"第一代本体"的示例）：

```
产品
├── 电子产品
│   ├── 手机
│   ├── 电脑
│   └── 电视
├── 机械产品
│   ├── 机床
│   ├── 机器人
│   └── 传送带
└── 化工产品
    ├── 塑料
    ├── 橡胶
    └── 涂料
```

（该树在 PDF 第 27 页以竖排制表符图呈现，本页转写为等价的缩进树。）

### 2.2 第二代：帧与语义网络（2.2.2 节 / PDF 第 28 页）

**"设备"帧**（原文示例）：

| 槽名 | 槽值 |
|---|---|
| 设备编号 | EQ001 |
| 设备类型 | 数控机床 |
| 设备状态 | 运行中 |
| 所属产线 | A 产线 |
| 加工精度 | 0.01mm |

**语义网络**（原文示例，节点 = 概念，边 = 关系）：

```
设备EQ001 --属于--> A 产线
设备EQ001 --加工--> 零件P001
零件P001 --属于--> 订单O001
```

原文评价："帧和语义网络比分类体系表达了更多的信息，但它们缺乏形式化的语义定义。"

### 2.3 第三代：描述逻辑与 OWL（2.2.3 节 / PDF 第 28—29 页）

**描述逻辑的四个核心概念**：

| 概念 | 对应 | 原文例子 |
|---|---|---|
| 概念（Concept） | 本体中的**类** | "设备"是一个概念 |
| 角色（Role） | 本体中的**对象属性** | "属于"是一个角色 |
| 个体（Individual） | 本体中的**实例** | "EQ001"是一个个体 |
| 公理（Axiom） | 概念与角色之间的**约束** | "设备必须属于至少一条产线" |

**OWL 的四个核心构件**（2004 年 W3C 发布，将描述逻辑与 Web 技术结合）：

| 构件 | 定义（原文） | 原文例子 |
|---|---|---|
| **类**（Class） | 定义一组具有相同属性的个体 | `Equipment` 类 |
| **属性**（Property） | 分**对象属性**（Object Property，描述个体之间的关系）与**数据属性**（Data Property，描述个体的特征） | `belongsToLine`（对象属性）、`equipmentId`（数据属性） |
| **公理**（Axiom） | 定义类和属性的逻辑约束 | `Equipment` 和 `ProductionLine` 是**不相交**的；`belongsToLine` 是**函数性属性**（原文括注："一条产线只能属于一个设备"） |
| **个体**（Individual） | 类的具体实例 | `EQ001` 是 `Equipment` 类的实例 |

原文评价："OWL 的推出，标志着本体论从学术研究走向工程实践。越来越多的企业和组织开始用 OWL 构建本体，用于知识管理、数据集成、语义搜索等领域。"

### 2.4 第四代：知识图谱与工业本体（2.2.4 节 / PDF 第 29 页）

- **2012 年谷歌发布 Knowledge Graph**，把知识图谱推向大众视野；用图结构表示实体和关系，支持大规模知识存储和查询。
- **核心表示**是"实体-关系-实体"三元组：

```
(设备EQ001, 属于, A 产线)
(设备EQ001, 加工, 零件P001)
(零件P001, 属于, 订单O001)
```

- **优点**：存储和查询效率高，支持大规模数据。
- **缺陷**：通常只存储实例数据、不定义 Schema；没有 Schema 约束，实体和关系可能"混乱、矛盾、不可信"。
- **第四代的融合形态**：工业界把本体与知识图谱结合——"**本体定义 Schema，知识图谱存储实例。本体提供语义约束，知识图谱提供数据查询。两者结合，形成'本体驱动的知识图谱'。**"
- **标准落点**：GB/T 48000.3—2026 的发布"标志着本体建模成为国家标准层面的正式技术要求。标准将本体的核心组成明确为**实体类型、属性和公理**三部分"。

## 3. 本体论与知识图谱的本质区别（2.3 节 / PDF 第 30—32 页）

### 3.1 一个贯穿全篇的现场问题（2.3.1 节 / PDF 第 30 页）

原文用一个具体问题检验三种形态：**"这批 PCB 焊点不良，能不能追到是哪批元器件、哪个供应商？"**

| 形态 | 怎么回答 | 原文指出的局限 |
|---|---|---|
| **关系数据库** | 库中存着 **PCB 表、元器件表、供应商表、工单表** 四张表，**四张表之间没有外键关联**，跨表 JOIN 全靠工程师手写 SQL。需查：PCB 表找不良 PCB 编号 → 工单表找工单编号 → 元器件表找该工单用的元器件批次 → 供应商表找供应商 | "如果工程师不了解表结构，或者字段命名不清晰，这个查询几乎无法完成" |
| **知识图谱** | 存着贴片工单、贴片机、元器件、供应商等实体及关系，可用图查询语言沿关系链 `PCB -> 工单 -> 元器件 -> 供应商` 追溯 | "**没有类型、没有约束，查出来对不对很难校验**"。图谱中可能存了错误的关联（如某元器件批次被错连到另一个工单），"没有 Schema 的约束，这种错误很难被发现" |
| **工业本体** | 定义了"PCB""元器件""供应商""工单"等**实体类型**及对象属性；还定义了**约束规则**：一个 PCB 必须属于一个工单；一个工单可以包含多个元器件；一个元器件必须来自一个供应商 | 不仅沿关系链追溯，还**校验追溯路径的合法性**："如果某个关联关系违反了本体约束，系统会提示异常，而不是返回一个看似合理但实际错误的结果" |

### 3.2 本体是 Schema，知识图谱是 Instance（2.3.2 节 / PDF 第 30—31 页）

| 层次 | 内容 | 原文示例 |
|---|---|---|
| **Schema（本体）** | 定义类、属性、关系、公理 | `Equipment` 类有 `equipmentId` 数据属性、`belongsToLine` 对象属性 |
| **Instance（知识图谱）** | 存储具体的实例数据 | `EQ001` 是 `Equipment` 的实例，`equipmentId = "EQ001"`，`belongsToLine = "A 产线"` |

原文类比：**Schema 与 Instance 的关系，类似数据库中的"表结构"和"表数据"**。"没有表结构，表数据就是一堆无意义的字节；**没有本体，知识图谱就是一堆无意义的节点和边**。"

### 3.3 知识图谱解决"怎么连"，本体解决"怎么懂"（2.3.3 节 / PDF 第 31 页）

原文的比喻：

| 比喻对象 | 提供什么 | 缺什么 |
|---|---|---|
| 知识图谱 = **一张地图** | 标出所有地点和道路 | 这条路是高速公路还是乡间小路？限速多少？什么时间段可以通行？——地图上没有标注 |
| 本体 = **一本交通规则手册** | 告诉你路在哪里、哪条路可以走、限速多少、什么情况下必须绕行 | —— |

原文列举本体在**三个方面**提供知识图谱不具备的能力：

| 能力 | 机制 | 原文例子 |
|---|---|---|
| **类型校验** | 本体定义每个实体的类型；实体被错误归类时推理机可发现不一致 | 本体定义 `Equipment` 与 `Material` 不相交，一个实例同时归入两类，推理机会报错 |
| **口径统一** | 本体定义每个属性的**含义、单位、取值范围** | 本体定义"温度"属性单位是摄氏度、取值范围 **0—1500℃**；若某系统是华氏度，本体可通过语义映射转换 |
| **关系约束** | 本体定义关系的**定义域、值域和特征** | 本体定义 `belongsToLine` 是函数性属性（一个设备只能属于一条产线）；设备被关联到两条产线时推理机会报错 |

> 注：2.3.3 节中"温度 0—1500℃"是原文对"口径统一"能力的举例，与第 1 章 1.5 节"回流焊炉温 0—150℃、正常范围 230—250℃"是两个不同的例子，数字不可互换。

### 3.4 本体是"证据链"（2.3.4 节 / PDF 第 32 页）

原文判断："本体还有一个知识图谱不具备的能力：**证据链**。"

- **知识图谱的局限**：一条关系（如"设备 EQ001 属于 A 产线"）只是一个三元组，**没有来源、没有时间、没有置信度**，多源数据冲突时无法判断哪条关系更可信。
- **本体的做法**：为每条关系附加元数据——**来源是什么？什么时候建立的？置信度多少？谁审核的？**冲突时按元数据判断。
- **原文案例**：

| 来源系统 | 说法 | 数据来源性质 | 置信度 |
|---|---|---|---|
| MES 系统 | 属于 **A 产线** | 产线实时采集 | **0.95** |
| 设备管理系统 | 属于 **B 产线** | 人工录入 | **0.8** |

系统据此判断 MES 系统数据更可信，**选择 A 产线作为正确答案**。

原文的收尾句："这种证据链机制，是本体区别于知识图谱的关键特征。**它让本体不仅'知道'，而且'知道自己为什么知道'。**"

## 4. 国标视角下的本体定义：GB/T 48000.3—2026（2.4 节 / PDF 第 32—35 页）

### 4.1 标准基本信息（2.4.1 节 / PDF 第 32 页）

| 项目 | 内容 |
|---|---|
| 标准号/名 | **GB/T 48000.3—2026《标准数字化 第 3 部分：本体建模要求》** |
| 发布 | **2026 年 1 月 28 日**，国家市场监督管理总局、国家标准化管理委员会发布 |
| 实施 | **2026 年 8 月 1 日**起实施 |
| 规定内容 | 标准本体构建的**通用要求、实体类型、属性和公理**，适用于指导标准数字化中的本体建设与应用 |
| 归口 | 全国标准数字化标准化工作组（**SAC/SWG29**）提出并归口 |
| 起草单位（原文列举） | 山东省计算中心（国家超级计算济南中心）、中国标准化研究院、同方知网数字科技有限公司、中国质量标准出版传媒有限公司等 |

### 4.2 本体的核心组成三部分（图 2-1 / PDF 第 33 页，视觉复核）

原文以 **"如图 2-1"** 引出。图 2-1 是一张横向三层叠置图，每一层右侧都给出对应的 OWL 形式化表达：

| 层 | 层定义（图内原话） | 组成（图内） | 示例（图内） | 形式化表达（图内） |
|---|---|---|---|---|
| **公理层**（顶部，橙色） | 定义"**什么不能被违反**" | **实体类型规则、属性规则、关系规则** 三类 | 规则示例："设备与产线不相交"（图标：设备 ✕ 产线）、"设备编号唯一"（"设备编号 12345 ✓"） | `owl:disjointWith`、`owl:FunctionalProperty` |
| **属性层**（中部，绿色） | 定义"**类有什么特征和关系**" | **数据属性**（描述类的特征）、**对象属性**（描述类之间的关系） | `equipmentId`（设备编号）→ `xsd:string`；`belongsToLine`（属于产线）→ `ProductionLine` | `owl:DatatypeProperty`、`owl:ObjectProperty` |
| **实体类型层**（底部，蓝色） | 定义"**有哪些类**" | **核心实体**（领域中最核心的类）、**领域实体**（特定领域的关键类）、**行业实体**（行业特有的类） | `Equipment`（设备）、`ProcessUnit`（工艺单元）、`ProductionLine`（产线）…… | `owl:Class` |

图 2-1 底部另有一条横向链路，把三层与行动串起来：

```
对象（现实世界中的实体或概念）→ 特性（对象的属性与关系）→ 约束（公理规定的约束与规则）→ 行动（基于约束的推理与执行）
```

链路的两端都有虚线回路（从"行动"回到"对象"、从"约束"回到"对象"等，图上为虚线箭头）。

### 4.3 三部分在正文中的定义（2.4.1 节 / PDF 第 33 页）

**① 实体类型（Entity Type）**——对具有相同属性的一组实体的抽象。标准定义的核心实体类型（原文列举）：

> 标准实体、标准化对象、相关方、领域类别、要素、层次、信息单元、对象、特性、约束逻辑、行动、外部约束、制定程序

**② 属性（Attribute）**——分数据属性与对象属性。标准定义的核心**对象属性**（原文列举）：

> 采用、代替、引用、参考、有部分、发布于、提出于、归口于

**③ 公理（Axiom）**——定义实体类型与属性的逻辑约束。标准要求的核心规则：**实体类型不相交规则、属性唯一性约束、日期有效性验证、枚举值约束**等。

### 4.4 实体类型的确定要求（2.4.2 节 / PDF 第 33—34 页）

| 要求 | 原文内容 |
|---|---|
| **知识层次逻辑** | 实体类型应根据标准的知识层次逻辑，将相同或相近语义的知识片段归纳概括为具有**普适性和通用性**的实体类型，以标准中共性必要要素构建实体类型集 |
| **细分程度适度** | 应根据对应实例的细分程度定义，"既要尽可能细化以保证标准的所有语义可展示，又要恰当切分**以避免语义关系缺少和错乱**"；应根据在标准中的作用定义实体类型及层次结构 |
| **语境对齐和映射** | 实体类型应能在语境中实现对齐和映射；**相同实体类型的近义词不应被表示为多个实体类型**。例："标准"与"标准化文件"在狭义上属于相同实体类型，不应作为两个实体类型定义 |
| **复用已有本体** | 现有本体已存在相关实体类型时，应采用现有本体的实体类型。例："提出单位""归口单位""起草单位"均与单位/机构相关，应采用现有"公司""单位"等相关本体中的实体类型及属性 |

### 4.5 属性的定义要求（2.4.3 节 / PDF 第 34 页）

| 要求 | 原文内容 |
|---|---|
| **数据属性仅描述自身** | 某个实体类型的数据属性应仅描述该实体类型自身的属性，**不应包含与其他实体类型直接关联的属性** |
| **明确唯一性和一致性** | 应通过定义数据属性明确实体类型的唯一性、一致性（例：标准编号应保持唯一） |
| **数据属性不具有传递性** | 数据属性不应具有**传递性、对称性或互逆性** |
| **对象属性描述关系** | 对象属性用于描述实体类型之间的关联，其角色类似自然语言中的"**动词**"，通过**定义域和值域**明确关系的方向性和语义边界 |

### 4.6 公理与规则要求（2.4.4 节 / PDF 第 34 页）

| 规则类别 | 具体规则 | 适用对象（原文） |
|---|---|---|
| **实体类型规则** | **实体类型不相交规则** | 具有互斥性的实体类型，如规范性要素与资料性要素是互斥的 |
| 实体类型规则 | **全局唯一标识规则** | 需要唯一标识的实体类型 |
| **属性规则** | **属性唯一性约束规则** | 需要保持唯一值的属性 |
| 属性规则 | **日期有效性验证规则** | 具有时序关系的日期属性 |
| 属性规则 | **枚举值约束规则** | 取值需要限定的属性 |
| **关系规则** | **功能性属性约束规则** | 具有功能性约束的对象属性 |
| 关系规则 | **版本替代关系规则** | 实体间的替代关系 |
| 关系规则 | **层次结构约束规则** | 层次结构关系 |

### 4.7 "对象—特性—约束—行动"的链路（2.4.5 节 / PDF 第 34—35 页）

原文称这是标准中"最值得关注"的部分：

| 环节 | 英文 | 定义（原文） | 标准中的子类 |
|---|---|---|---|
| **对象** | Object | 条款中涉及的人员、设备、材料等对象 | 标准定义了"对象"类，包括**标准对象、指标对象**等子类 |
| **特性** | Property | 描述条款中产品/服务/过程的核心属性特征，包括质量指标、功能参数及约束条件等可量化或可验证的技术要素 | 分**描述型特性、能力型特性、约束型特性**三类 |
| **约束** | Constraint | 承载具体约束参数的条件实体，如阈值、允许偏差等 | 定义了**约束类型、最大值、最小值、阈值范围、测量单位**等数据属性 |
| **行动** | Action | 描述最小可执行模块的程序要素 | 分**动作、路径、判断条件**等子类 |

原文对这一链路意义的判断：**"本体不只是描述世界'是什么'，还要定义世界'怎么变'。对象有特性，特性有约束，约束触发行动。这是一个从静态知识到动态行动的关键跨越。"**

**原文对比示例**：

| 形态 | 能表达什么 |
|---|---|
| 传统知识图谱 | "设备 EQ001 的温度是 85℃" |
| 本体 | "设备 EQ001 的温度是 85℃，**超过了正常范围（60—80℃）**，**需要触发降温行动**" |

原文评价："后者的表达能力更强，因为它不仅描述了状态，还定义了状态的约束和相应的行动。"

### 4.8 形式化要求（2.4.6 节 / PDF 第 35 页）

| 要求 | 原文内容 |
|---|---|
| **本体描述语言** | 应采用 W3C 推荐的本体描述语言（**XML、RDF/RDFS、OWL 等**）进行规范表示 |
| **序列化格式** | 应使用标准化的序列化格式（如 **Turtle、JSON-LD** 等）存储和交换 |
| **约束验证** | 应支持基于 **SHACL** 的约束验证，如标准编号格式校验 |

原文结论："这些形式化要求，确保了本体可以被机器自动处理、推理和验证，而不是停留在自然语言的描述层面。"

## 5. 本章小结：本体论的工程化转向（2.5 节 / PDF 第 35 页）

原文小结分四层：

| 层 | 原文要点 |
|---|---|
| 演进四阶段 | "从亚里士多德的十范畴体系，到分析哲学的形式化转向，到描述逻辑和 OWL 的推出，再到知识图谱和工业本体的结合。" |
| 核心线索 | "本体论从'关于存在的思辨'转向'关于知识的建模'，从'哲学家追问什么是存在'转向'工程师追问什么是可计算的业务对象'。" |
| 标准意义 | GB/T 48000.3—2026 将本体核心组成明确为实体类型、属性和公理三部分，提出"对象—特性—约束—行动"的链路，为本体建模提供规范化方法论。 |
| 遗留问题 | **"标准是通用的方法论，不是具体的工程指南。在实际项目中，企业面临的问题不是'本体是什么'，而是'本体怎么建、谁来用、用了创造什么价值'。"** |

最后一句是本章写给后文的过渡：第 3—15 章就是回答"怎么建、谁来用、创造什么价值"。
