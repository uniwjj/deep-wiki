# 语义层即上下文：理想汽车生产级 Agent 的语义工程实践

> 核心主张：生产级 Agent 的瓶颈不是“能不能生成答案”，而是“结论能不能被证明”。“语义层即上下文”的含义是：语义层不只是给人看的指标字典，而是 Agent 的**上下文基础设施**——本体图定义业务对象与关系，指标图把对象连接到可执行证据，Playbook 收敛专家调查路径，Runtime 按任务装配最小上下文（Semantic Slice）。理想汽车用这套方法支撑诊断 Agent：复杂问题排查修复效率提升 10×+，诊断准确率 97%+，每周完成万级系统级风险扫描。

演讲者：钱瀚，理想汽车大数据平台负责人。曾在百度、京东和字节跳动工作，负责过百万 Core 级计算调度框架和 EB 级数据湖。当前建设方向包括大数据平台云原生化、多模态数据平台、数据语义层建设。平台支撑规模为 180+ 万车、日均处理 10 万亿级车辆信号。

## 背景与问题

### 一个问题背后是六类事实

演讲以一个典型问题开场：“为什么这个数据处理任务失败了？”。用户可能追问：处理的数据变多了？计算资源紧张了？执行过程出异常了？要回答这些问题，需要六类事实：

| 事实类型 | 作用 |
|----------|------|
| 状态 | 任务、阶段、子任务当前处于什么状态 |
| 日志 | 执行过程中记录了什么 |
| 指标 | 耗时、读取量、倾斜度等量化表现 |
| 资源 | CPU、内存、队列配额等资源情况 |
| 事件 | 发布、变更、异常等时间点 |
| 历史对比 | 同类任务、同周期的差异 |

演讲给出的判断标准是：**答案可以生成，结论必须被证明**。证明的公式是：

```
正确对象 × 正确时间窗 × 完整证据链
```

这三者缺一不可。对象错了，指标再准也无意义；时间窗错了，比较基线失真；证据链不完整，结论无法复核。

### 三个阶段：上下文从“临场组装”到“专用固化”再到“回归控制”

#### 第一阶段：Prompt 与通用工具临场组装上下文

做法是“Prompt 专家 + 通用底层工具”：Prompt 里写角色与原则、诊断步骤、工具说明，模型临时选择信息与调用路径；工具包括 K8s / REST、SLS / Logs、StarRocks / SQL、Prometheus / Metrics。

这一阶段的问题是：

- **上下文依赖底层结构**：业务问题要临场翻译为表、字段、关联关系和 SQL。
- **上下文组装不稳定**：同一问题可能选择不同的指标、日志与时间窗。
- **上下文难复用和治理**：经验散落在 Prompt 与查询中，变更影响难以评估。

演讲总结：“上下文足够开放，但缺少统一语义和稳定边界。”

#### 第二阶段：专用工具固化场景上下文

做法是把常用对象、查询模板和判断逻辑封装为稳定上下文，并按 PRIMARY / MID / ATOMIC 三层组织：

| 层级 | 内容 | 作用 |
|------|------|------|
| PRIMARY | 失败诊断、性能分析 | 直接返回结构化结论 |
| MID | 执行阶段、子任务、执行进程 | 按条件继续下钻 |
| ATOMIC | 日志、SQL 与 API | 保留长尾探索入口 |

这一阶段的问题是：

- **一个场景一套上下文**：每出现一条新的调查路径，就要新增或改造工具。
- **上下文随工具膨胀**：职责重叠、参数相近，Agent 的选择成本反而上升。
- **跨领域难共享**：Spark 能力迁移到 Flink，需要重新封装相似上下文。

演讲总结：“专用工具提升已知场景准确性，未封装问题仍缺少可用上下文。”

#### 第三阶段：诊断回归控制上下文变更风险

Prompt 与专用工具持续调整，上下文行为也随之变化，因此引入四步回归：

1. **真实调用录制**：保留真实 LLM 与后端返回。
2. **场景回放**：固定输入与外部依赖。
3. **行为与语义评测**：检查工具调用和诊断结论。
4. **CI 自动回归**：Prompt 或工具变化立即验证。

这一阶段解决了“验证上下文变更是否破坏已有场景”，但留下的问题是：“回归只能发现波动，无法解决上下文分散和场景扩展成本。”

### 早期诊断 Agent 的上下文结构

早期架构分为四层：

- **问题入口**：用户问题。
- **Agent 层**：Coordinator 识别领域并路由问题，下接 Spark Specialist、Flink Specialist、Cluster Specialist，每个专家有自己的 Prompt + 工具说明。
- **上下文工具层**：
  - PRIMARY：Spark 失败/内存不足（失败分类与根因定位）、Spark 性能/负载不均（慢执行阶段与数据分布）、Spark 应用/历史对比（同类作业与多周期差异）、Flink 综合诊断（流式任务失败、卡顿与恢复）。
  - MID：Spark 作业/执行阶段（Job/Stage 执行明细）、Spark 子任务/执行进程（Task/Executor 运行明细）、Flink 运行态查询（状态、指标与恢复检查点）、Flink 历史查询（归档状态、异常与配置）。
  - ATOMIC：SLS Tool、K8s Tool、Prometheus Tool。
- **后端系统**：StarRocks、SLS、Prometheus、K8s/KubeSphere、Spark EventLog、Flink REST。

右侧的研发保障是调用录制、场景回放、行为评测、CI 回归。演讲对这一架构的评价是：“PRIMARY 固化场景结论，MID 提供对象下钻，ATOMIC 暴露原始事实；上下文仍分散在 Prompt、工具和查询中。”

## 方案/架构

### 语义层在 Agent 与工具之间

演讲给出的总体关系是：

```
Agent（理解业务问题 / 选择调查方向 / 自由组合证据）
        ↓
语义层（业务对象 / 对象关系 / 指标口径 / 查询约束 / 数据绑定）
        ↓
通用工具（生成受约束查询 / 访问后端 / 返回结构化事实）
```

语义层把对象、关系、指标和查询边界组织成**可检索、可复用的上下文**。这样 Agent 不需要临场把业务问题翻译成表、字段和 SQL，而是在一个被定义过的语义空间中做选择；通用工具也不再被场景逻辑绑死，只负责生成受约束查询、访问后端、返回结构化事实。

### 语义诊断架构：分层架构 + 治理

理想汽车的语义诊断架构自上而下分为：

| 层次 | 组成 | 说明 |
|------|------|------|
| 接入层 | 运维问答、告警入口、IDE 助手、服务 API、业务系统 | 多入口复用同一套语义能力 |
| Agent Runtime | 场景识别、Playbook 匹配、自主规划、工具编排、证据汇总、结论门禁 | Agent 负责调查策略与结论把关 |
| 语义资产层 | Ontology Definition、OSI / Metric Model、Playbook | 业务对象与关系、数据集/字段/指标与可执行投影、诊断与分析路径 |
| 语义运行时 | 本体检索、指标检索、业务关系图、Playbook 检索、投影选择、指标执行、事实查询、语义缺口 | 把资产装配成当前任务可用的上下文 |
| 后端适配层 | MetricFlow、StarRocks Adapter、SLS Adapter、Prometheus Adapter、K8s Adapter、REST Adapter | 统一访问不同后端 |
| 运行系统 | StarRocks、SLS、Prometheus、Kubernetes、Spark、Flink | 真实数据与执行系统 |

右侧是治理与保障：资产校验、Contract 校验、版本管理、诊断回归、语义缺口。语义资产层下方还有一条“公司级统一托管演进”路径：Gravitino Registry / Metric View · Semantic Package Compiler。

演讲的总结是：“本体图表达业务关系，指标图连接可执行证据，Compiler 与 Gravitino 承接统一治理。”

### 从业务问题到事实的运行链路

运行链路为：

```
业务问题（意图/症状、目标对象）
  → Agent 调查（识别场景、选择调查路径、已知场景复用 Playbook）
  → 语义包（业务本体与关系、指标与可执行投影、Playbook 引用）
  → 通用工具 + 事实（SQL / Logs / Metrics、REST / K8s）
```

关键点在于：**Agent 选择调查路径，语义包同时提供业务关系和可执行指标**。语义包不是一份静态文档，而是当前任务所需的“业务关系 + 指标口径 + 可执行投影 + Playbook 引用”的组合。

### 语义包的两类资产：本体定义与指标定义分别建模

语义包（Semantic Package）由两类资产组成，分别回答不同问题；Playbook 作为独立语义资产被语义包引用，负责调查路径与证据要求。

| 资产 | 定义内容 | 产物 | 回答的问题 |
|------|----------|------|------------|
| Ontology Definition | 业务对象、身份、业务关系 | 业务关系图 | 对象是什么、彼此如何关联 |
| OSI / Metric Model | Dataset、Field、Metric、Projection | 可执行指标图 | 查什么、怎么算、从哪里执行 |

以 Spark 任务诊断为例：

- **业务对象**：任务运行（Application）、执行阶段（Stage）、子任务（Task）、执行进程（Executor）。
- **业务关系**：任务包含执行阶段、阶段包含多个并行子任务、子任务运行于执行进程；只表达稳定业务含义，不包含表名和 SQL。
- **数据集**：执行阶段表、子任务表（`spark_stage`、`spark_task`）。
- **字段**：阶段耗时（毫秒，`stage_duration_ms`）。
- **可执行投影**：物理来源与查询约束（StarRocks、Paimon）。
- **指标**：子任务耗时倾斜比（`task_skew_ratio`）。

本体 YAML 示例（原文节选）：

```yaml
ontology:
- concept:
    name: spark_task
    type: EntityType
    identify_by:
    - dt
    - app_id
    - stage_id
    - task_info_id
  relationships:
  - name: task_to_executor
    roles:
    - concept: spark_executor
      multiplicity: ManyToOne
```

指标 YAML 示例（原文节选）：

```yaml
metrics:
- name: failed_task_count
  description: 失败 Task 数量
  expression:
    dialects:
    - dialect: ANSI_SQL
      expression: COUNT(CASE WHEN task_info_failed = TRUE ... END)
  custom_extensions:
  - vendor_name: COMMON
    data: '{"metric_binding": {
      "target_object_type": "spark_task",
      "evidence_role": "failed_task_count"}}'
```

两者分开建模的意义是：业务概念与表结构、SQL、后端路由解耦。本体只表达稳定业务含义，指标模型负责口径与可执行投影；业务对象可以跨数据集、跨后端复用，而物理实现可以随存储与引擎变化。

### 两类语义资产构建两张图

构建阶段：

| 资产 | 中间索引 | 最终产物 |
|------|----------|----------|
| Ontology Definition（对象、身份、业务关系） | Ontology Index（全文与向量索引、关系映射） | 业务关系图（Application、Stage、Task、Executor） |
| OSI / Metric Model（Dataset、Metric、Projection） | Metric Registry（指标依赖、对象绑定、执行能力） | 可执行指标图（指标口径、对象范围、查询后端） |

运行时：

```
业务问题（识别对象意图）
  → 召回目标对象（Entry Object）
  → 1-hop 关系扩展（双向关联对象）
  → 对象范围内找指标（目标对象 + 关联对象）
  → Semantic Slice（对象、关系、指标）
```

演讲强调顺序：**先确定对象范围，再在范围内找指标，避免把无关指标带入上下文**。这与“先检索全部指标再筛选”的做法相反，目的是控制上下文规模与误选概率。

### Playbook：已知场景用经验收敛，未知场景自由探索

Agent 先识别场景（问题意图、症状、目标对象），再检索并匹配 Diagnosis / Analysis Playbook：

- **匹配成功**：Playbook 约束调查策略，但仍通过语义层选择业务关系、指标和证据。
- **未匹配**：进入语义层自由探索，从 Object / Relationship / Metric 自主规划。

两条路径共享同一语义层和通用工具。调查过程统一为五步：

| 步骤 | 内容 |
|------|------|
| 01 定位对象 | 对象 / ID / 时间窗 |
| 02 选择指标 | 主指标 / 辅助指标 |
| 03 选择证据 | 关系路径 / 日志 |
| 04 动态补查 | REST / K8s / 历史对比 |
| 05 结论门禁 | 证据 / 置信度 / 边界 |

演讲的总结是：“Playbook 提供经验收敛，语义层统一业务关系、指标口径与数据访问。”

## 关键工程做法

### 四个设计取舍

| 取舍 | 理想汽车的选择 | 理由 |
|------|----------------|------|
| 固定定义 vs 动态探索 | 定义对象、关系、指标和查询边界；Agent 动态选择调查路径 | 兼顾数据口径可靠与复杂追问的灵活性 |
| 业务含义 vs 可执行语义 | Ontology 定义对象和业务关系；OSI/Metric 定义数据集、指标和执行投影 | 避免业务概念与表结构、SQL 和后端路由绑死 |
| 业务知识 vs 专家 SOP | 本体与指标跨场景复用；Playbook 管判断步骤与行动路径 | 稳定知识和场景策略需要分别治理 |
| 语义意图 vs 物理可行性 | Physical Spec 与 OSI Projection 管理来源、过滤、时间窗和路由 | 业务上有关联，不代表当前已有可执行证据 |

最后一条尤其重要：本体可以表达“主任管理业代、业代负责线路、线路覆盖门店”这类业务关系，但如果当前没有对应的数据绑定与可执行投影，Agent 不能凭空查询。语义意图与物理可行性必须分开管理。

### 案例一：定时任务为什么越到晚间越慢

用户问题：“每小时运行一次的数据处理任务，为什么越到晚间越慢？”

Agent 匹配 Playbook `spark_resource_tuning`，调查顺序为“历史耗时 → 执行阶段 → 子任务分布”：

1. **对比历史耗时**：凌晨约半小时，晚间超过 6 小时。
2. **定位慢的阶段**：一个执行阶段就耗时约 4 小时。
3. **检查是否有长尾**：子任务处理量较均匀，没有明显的个别拖慢。

Playbook 指导排查，语义层定位对象与指标，继续追查这个阶段为何慢。

### 案例二：根因是反复读取了不需要的数据

继续调查：“子任务没有明显长尾，查询到底读取了哪些数据？”

Playbook 进入“SQL 下钻”分支，语义路径关联“查询执行 → 关联作业 → 执行阶段与子任务”：

1. **预期读取范围**：按小时筛选，只读取需要的时段。
2. **实际执行方式**：小时条件未缩小读取范围，仍读取当天累计数据。
3. **执行指标验证**：每小时反复读取累计数据，该阶段读取量约 12 TB。

演讲的结论是：沿对象关系关联查询、执行计划与指标，确认小时过滤未减少实际读取量。

### 案例三：未命中 Playbook 时，沿语义关系扩展

用户追问：“其他任务也慢，是不是共同占满了可分配的计算资源？”

这一次未命中既有 Playbook，Agent 进入语义层自由探索，探索范围包括当前任务、同源任务、共享资源配额：

1. **发现同类问题**：多个任务读取同一数据源，存在相同的查询缺陷。
2. **任务跨周期堆叠**：上轮未结束，下轮又启动，同一任务最多同时运行 8 份。
3. **共享资源紧张**：申请的资源接近配额上限（资源队列 `resource_queue`）。

演讲的总结是：“超出既有 Playbook 后，Agent 沿语义关系扩展，识别共享资源风险。”这个案例说明 Playbook 与语义层不是二选一：Playbook 收敛已知路径，语义层支撑未知探索。

### 治理与保障

架构右侧的治理能力包括：

- **资产校验**：本体、指标、Playbook 是否符合契约。
- **Contract 校验**：语义包在编译与发布时校验。
- **版本管理**：语义资产的版本与变更。
- **诊断回归**：上下文或资产变化后回归已有诊断场景。
- **语义缺口**：运行时发现“业务需要但语义资产没有”的缺口。

这与前文“诊断回归控制上下文变更风险”一脉相承：回归只能发现波动，真正的可维护性来自统一语义资产与治理链路。

### 语义资产平台化演进

理想汽车给出的平台化路径分四步：

1. **四类资产各归其位**：Ontology、Physical Spec、OSI Projection、Playbook。
2. **Compiler 生成并校验语义包**：Registry Rows、Graph Index、Package Lock。
3. **Gravitino 承接统一治理**：Owner、Version、Permission、Lineage。
4. **Runtime 按任务组装上下文**：业务关系图、指标图、Semantic Slice。

目标是“完整资产统一治理，运行时只装配当前任务需要的上下文”。

| 诊断准确率 | 97%+ | 以受治理语义和真实证据约束诊断过程，减少依赖模型记忆产生的误判 |
| 系统级风险扫描 | 万级/周 | 覆盖 Spark、Flink 失败与性能退化，聚类形成可治理的候选风险 |
| 方法论迁移 | 1 到 N | 从单一诊断 Agent 扩展到其他业务领域，复用语义层、Playbook 与通用工具的建设方法 |

案例中的具体数字：凌晨约半小时 vs 晚间超过 6 小时；单个执行阶段约 4 小时；阶段读取量约 12 TB；同一任务最多同时运行 8 份。

## 经验与边界

### 两个尚未解决的硬问题

演讲明确列出语义资产平台化的两个硬问题：

1. **业务经验如何完成语义抽象**：本体、指标和 Playbook 仍需要较多人工梳理。方向是标准化、辅助生成、数据治理、企业数字化建设。
2. **语义资产如何统一治理**：本体、指标和 Playbook 仍以 YAML 分散维护，缺少统一编译、版本与发布链路。方向是 Compiler、Registry、版本审计、Gravitino 托管。

这两个问题决定了“语义层即上下文”目前仍是工程活，不是买一个模型或一套工具就能解决。

### 边界

- **语义层不是文档库**：它必须能给出可执行投影与查询约束；只有业务描述、没有数据绑定，Agent 仍然查不了。
- **本体不是越全越好**：本体只表达稳定业务含义，不包含表名和 SQL；物理可行性由 Physical Spec 与 OSI Projection 管理。
- **Playbook 不能替代语义层**：Playbook 收敛已知调查路径，未命中时仍要回到 Object / Relationship / Metric 自由探索。
- **回归不等于治理**：诊断回归只能发现行为波动，解决不了上下文分散与场景扩展成本；需要 Compiler、Registry、版本与权限治理。
- **“业务上有关联”不等于“现在可查”**：语义意图与物理可行性之间需要显式投影，否则会制造无法执行的上下文。
