# 构建知识工程：推进高质量 Agent 分析决策

> 核心主张：**改造世界的能力依赖理解世界的能力——不认识世界就不能改造世界。** 数据 Agent 的分析决策质量，取决于它能否消费到「Agent friendly」的语义与数据资产；而 Agent 能否持续变好，取决于是否有一套数字化、可追溯的测评体系。知识工程与 Agent 评测，是同一件事的两面。

演讲来源：DACon 2026 北京站「上下文工程：让 AI 真正懂企业」专场，赵雪波（马上消费金融）。讲者自述有 15 年以上互联网与企业服务经验，当前在消费金融公司大数据团队，关注大数据、数据产品与数据架构。

## 背景与问题

### 三类工作问题

讲者把数据 Agent 落地中的问题归为三类，并用一张「工作问题 → 解决办法」的漏斗图串起来：

| # | 工作问题 | 原文描述 |
|---|---------|---------|
| 1 | 高速迭代支撑不足 | 「3 天引入 → 20 天沉淀 → 30 天使用 → 衰退」；Agent AI 配合 BI，满足支路和毛细需求 |
| 2 | Skill 重复沉淀内容多 | 单个 Skill 交互时间长，经过学习大量沉淀；不同 Skill 之间有知识重复，总体浪费明显 |
| 3 | Agent 运行突发性漂移 | Agent 性能突发下降、无故死锁等；Skill 产出数据波动/重复/缺失 |

这三类问题指向同一个底层缺口：Agent 缺少稳定、可复用、可推理的业务语义知识；同时缺少能持续发现漂移的度量手段。

### 数据分析 Agent 的场景分布

幻灯片给出的数据分析 Agent 场景分布为：

| 场景 | 占比 |
|------|------|
| 需求文档驱动 | 49% |
| SQL 和取数 | 21% |
| 分析/预测 | 15% |
| 其他 | 15% |

也就是说，近一半的需求来自「需求文档驱动」——这类场景既需要理解自然语言需求，又需要把需求映射到指标、实体、表和时间窗口，是知识工程的主战场。

### 两条解决办法

针对上述问题，讲者给出两条互补的路径：

1. **Agent friendly 语义元数据**：让语义 + 数据作为完整业务规则的承载，形成模块化、系统性的知识，使 Agent 可推理。核心判断是「用数字化对抗复杂度，回收价值」。
2. **Agent judge 数字化测评**：可观测是 Agent 可用的必要前提；数字化度量是改进的必要前提；基于 Harness 体系，可追溯才可改进。

> 原文金句：「改造世界能力依赖理解世界的能力（不认识世界就不能改造世界）。」

## 方案/架构

### 知识分层决定决策精度分层

讲者用金字塔图表达「知识附加值升级」与「业务覆盖/适用范围」之间的张力：越往上，知识附加值越高、准确率越高，但覆盖范围越窄；越往下，覆盖越广，但准确率越低。

| 层级 | 知识形态 | 准确率 | 作用范围/定位 |
|------|---------|--------|--------------|
| 第 1 层 | 基于指标提供最优质的数据资产和元数据资产 | >95% | 作用范围：北极星 +1.5；行业强制对齐 |
| 第 2 层 | 复用 BI 工具的数据模型（实体/属性/指标等逻辑要素），映射到相应物理表 + 页面表达 | >70% | 业务覆盖 |
| 第 3 层 | 大数据表作为第三梯队覆盖广；元数据语义为主，表扩展为辅 | 40%–60% | 适用范围 |

> 「北极星 +1.5」为幻灯片原文，具体含义未展开，**不确定**。

金字塔底部的两句判断：

- 「数据是极致的业务知识化压缩，压缩的结果可被推理，把结构化数据承载知识供给推理。」
- 「建立 agent friendly 的数据资产形态（从人用向 agent 用转化）。」

### 知识结构的四类来源

讲者强调知识结构要同时满足三个属性：**兼容性**（全局拉动知识，融合才能覆盖）、**可迭代**（短期场景价值驱动长期迭代）、**面向推理**（知识结构面向 OAG 推理）。「复杂度 vs 效果不均衡是知识库落地企业主要卡点；LLM 和 Harness 体系可以有效提升产能和效果。」

四类知识来源及各自关注点：

| 来源 | 关注内容 |
|------|---------|
| 维度建模 | 粒度和实体定义；星形模型和一致性维度；维度层级和扁平列；复杂维度分桶建模；业务实体权威主物理表 |
| BI 建模 | 物理表抽象逻辑语义（实体/维度/度量等）；指标数据聚合方式；维度层级和钻取；行权限控制 |
| 本体 Ontology | 实体属性定义；对象关联和关系；类/属性的实例；共指消解和等价类；ObjectProperty 对象和值 |
| Skill 实践沉淀 | 指标定义和 sum 计算；物理表主外键和关联；绩效计算归属和看板行权限控制；多级维度归属汇总方式 |

### 知识工程支撑 3 类分析 Agent 场景

幻灯片把分析 Agent 分成三类，并逐一列出「从自然语言/文档到知识与数据」的映射链条：

| 场景 | 知识推理链条 | 旁支知识 |
|------|-------------|---------|
| SQL & 取数 | 意图和长文拆解 → 指标定义（指标 + 公式 + 汇总方式）→ 表字段向指标转化（字段绑定）→ 表字段描述（字段确认）→ 表关联方式（关联）→ 表主外键（粒度）→ 管理范围和权限（输出控制） | 数据对象命名含义、同义词库、维度枚举值 |
| 复杂分析和预测 | 企业黑话 → 指标定义 → 指标关系 → 实体属性定义 → 维度级联关系（下钻）→ 表字段描述（落数）→ 表关联方式（关联） | 分析方法论、归因方法、业务流程定义 |
| 需求文档驱动 | 文档 → 数据对象命名定义（语义归一）→ 指标定义.md（指标口径）→ 指标关系.md（派生关系）→ 分析时间窗口定义.md（时间窗口）→ 实体属性定义（维度对象）→ 维度级联关系（级联校正）→ 表字段向指标转化.md（字段绑定）→ 表关联方式（关联）→ 预警阈值（高亮）→ 管理范围和权限（输出控制） | — |

### 知识分类全景

幻灯片底部把知识分成四层，作为知识工程的「供给侧地图」：

- **业务知识**：业务流程、业务定义、指标定义、实体属性定义、实体关系；另有管理范围和权限、考核管理要求、企业黑话、同义词库。
- **业务-技术转化知识**：实体向表转化、表字段向指标转化、表字段向维度转化、维度级联关系。
- **技术知识**：表字段描述、维度枚举值、表关联方式、表主外键、数据对象命名定义、数据加工字段血缘。
- **分析方法领域知识**：指标关系、分析方法论、分析维度指标拆解、归因等分析方法、分析时间窗口、预警阈值、分析和复盘模板。

### 语义知识（初步）工程化

语义知识工程化的流程是：

```
元数据仓库 & DataOps 服务
企业内部文档和知识        ──→ 平台服务 ──→ Agent 抽取 ──→ 结构迭代 ──→ 集中存储 ──→ 语义知识工程化
Agent skill
日志和测评
```

其中：

- **平台服务**：基于应用考虑存储和更新机制。
- **Agent 抽取**：关注 LLM/Agent 抽取的一致性和稳定性。
- **结构迭代**：自动发现、反思 & 人工巡检，发现必要的知识结构变化。
- **集中存储**：多领域知识汇聚融合 & 应用是按领域过滤。

工程化目标被概括为「构建覆盖领域广泛、可多人协作、持续迭代、可解释的知识工程语义」，并展开为四个要求：

| 要求 | 原文解释 |
|------|---------|
| 覆盖领域广泛 | 从单实验到业务线应用，再扩展到企业数据应用 |
| 可多人协作 | 不同领域知识的收集处理，有边界，可以时间局部更新；针对冲突有单独的数据结构/角色/流程 |
| 持续迭代 | 知识结构以半结构化框架进行组织，细节内容结构化，少量内容引入关系结构，可较快应对变化 |
| 可解释可追溯 | 区分更新周期，对目标知识定期主动更新和本地存储；建设初期多采用快照，降低 MCP/API 调用 |

## 关键工程做法

### 样例：从 OLD skill 到 New skill

幻灯片用一个「周度数据复盘」的样例说明知识工程如何改造 Skill：

- **OLD skill**：`weekly-tupan-new`，通过 `Main func()` 拼接 SQL + Python 计算（by 交互），产出「周度数据复盘-init」报告。
- **NEW skill**：`std-krwg-shizi1`，配合私有知识（30%）+ 公用知识（70%），其中公用知识覆盖「数据元/实体/指标/表 4 大类、17 小类」；通过 `NewMain func()` 拼接 SQL + Python 计算（by agent），产出「周度数据复盘-数据标准测试-1」报告，并与原报告「数据核对一致」。
- 知识库从 **4 → 26**，定位为「结构化/agent 友好/可统一构建」，通过「结构定义 + prompt 抽取」生成。

这条样例的关键不是替换了某个模型，而是把「人机交互时临时拼接的计算逻辑」沉淀为「可被 Agent 复用的标准知识 + 标准 Skill」。

### 数据 Agent 评测：从 LLM 测评到 Agent 测评

讲者先区分两种测评：

| 维度 | LLM 测评 | Agent 测评 |
|------|---------|-----------|
| 目的 | 优化大模型本身 | 优化完整 Agent 链路 |
| 对象 | 单点、单次 | Agent 链路、轨迹、闭环 |
| 特征 | 原子化单项；无上下文；测评间独立；一次回答/评分；无中间过程；无交互无轨迹 | 完整交互轨迹；分步骤执行；中间过程多样；观测视角复杂；闭环任务能力（端到端任务、多能力组合效果、上下步高度依赖） |
| 优化点 | 问题归因在内部；迭代模型内权重等；外部环境固定 | 优化 LLM Provider；优化规划和编排；优化 Tools；优化记忆机制；优化知识供给和推理 |

幻灯片中间的判断是：「不确定性，需要持续测评」；底部把「数字化 judge + 人工标注 + Golden set」作为连接两种测评的公共基础设施。

### 三类数据 Agent 场景的评测差异

| 场景 | 特点 | 典型风险 |
|------|------|---------|
| 数据分析 | 不同人员、能力和场景差异度大；多轮尝试、多次沉淀；数据结果把握度高 | 过度信任 Agent，用峰值体验代替平均感受；持续稳定性输出差，无法生产决策；逐步做到可观测，但无法有效改进；技术视角多，无法复原业务现场 |
| 数据建模/开发 | 整体开发过程前后衔接紧密；交付内容专业化，覆盖模型和语义；数据质量把握度弱 | 评测需覆盖模型与语义交付物 |
| 数据治理 | 非业务属性强，技术元数据要求高；测评结果和治理任务衔接紧密 | 评测需与治理任务闭环 |

幻灯片底部的定位是：**Data by Agent**——数据分析作为 Agent friendly 的消费节点，拉动 DataOps 过程的数据供给，和整体的 Data GOV 底座。

### Skill 生命周期五阶段

| 阶段 | 阶段特点 |
|------|---------|
| 01 需求定义和拆解 | 需求理解容易有歧义；计划和任务拆解随机；一个问题面临多 Skill 备选 |
| 02 Skill 构建 | 确定基本执行框架，形成能力边界；GPU 向 CPU 开始转化（Tools 等） |
| 03 Agent 持续投喂 | 上下文和连续性要求高；知识被理解和分布；前后知识冲突待解决 |
| 04 持续运行交付 | 输入数据确定，边界清晰；交互轨迹确定；稳定性和一致性要求高；治理（安全/质量）要求浮现 |
| 05 优化/迭代 | 内容和能力向前兼容；结构被迭代甚至颠覆；反馈回路有效 |

底部两句判断：「Agent 测评是 Agent 的一部分」；「Agent 迭代的第二发动机」。

### 数据 Agent 测评动态发展

幻灯片用一条「从低成本到高成本」的坐标轴，列出评测项随能力建设逐步展开的顺序（原文顺序）：

- Harness 安装/运行、LLM Provider 稳定、Cron 稳定执行、IM 端打通可见可管、大数据 MCP 齐全、APP CLI 有一定覆盖率；
- 数据权限管理、IM 群意图识别、铁律落实有效性、会话识别和 session 切分、多 Agent 协作；
- 长任务优化、持续稳定/一致交付、Skill 建设提速、Token 消耗管控。

上方四个结果维度是：**结果完成度、产出质量、执行效率、消耗成本**；对应的数据链路是「传输 → 清洗 → 计算 → 存储 → 展现」。底部判断：「测评工作开展和公司数字人推进相关，要解决问题从简单到复杂。」

### 4 大项 13 子项指标体系

基于活跃 Skill，讲者约定「4 大项 13 子项」作为通用数据 Agent 测评指标体系：

| 大项 | 子项 | 目标 |
|------|------|------|
| 结果完成度 | 任务完成率、交付正确率、功能覆盖率 | 高 |
| 产出质量 | 工具调用成功率、结果复现性、证据完备度 | 准确 |
| 执行效率 | 交互轮次、问题交接时长、LLM 调动时间、重复提问率 | 高效 |
| 消耗成本 | Token 消耗、LLM 请求次数、消息次数 | 降低 |
| 持续扩展（扩展项） | 安全方面、稳定性方面、more… | — |

在通用指标之外，幻灯片还给出按 Agent 类型细化的「扩展」指标：

- **数据开发 Agent**：需求理解正确率、抽取知识完备率。
- **数据治理 Agent**：血缘召回率、敏感数据召回率。
- **数据分析 Agent**：SQL 运行时间占比、可视化有效性。

### 数据 Agent 测评工程链路

测评被拆成「执行端运行采集」与「服务端统一运行」两段：

| 环节 | 关键做法 |
|------|---------|
| 采集 skill（适配/统一转化） | 端触发运行；Hermes/Openclaw 等日志采集；进度/断点/补充采集；基于配置进行统一格式转化；解析问题发现和报警 |
| 存储节点（端到云日志传输） | 统一大数据入湖仓；Iceberg 物理表；采集端注册机制和未到齐预警 |
| 评测-LLM（日志预处理） | 基于 LLM 进行语义识别和任务切分；会话粒度 → 任务粒度 → 事件粒度处理；上下文重复问题识别；Skill 性质预判和分类映射；语言类统计（例如质量）输出 |
| 评测-计算（终态指标计算） | 推进大数据平台任务；按维度汇总进行指标计算；计算过程保持明细留底可追溯；默认/无效值填充 |
| 可视化（结果和溯因） | 推送 BI 工具；同环比默认计算；可视化表达（卡片/表/图等）；分类展示和权限管理（暂空） |

最终指向「数字化管理，可追溯」。

### 评测失真的三类问题与改进

| 问题 | 原文描述 | 改进方案 |
|------|---------|---------|
| 评测失真：过度拟合 | 可量化指标直接或间接投喂 Agent，Agent 会主动学习，并投其所好 | 拓展分支场景 judge 指标 |
| 评测失真：覆盖缺失 | 公共指标无法覆盖独立场景（数据开发/数据治理/数据分析）差异，需按领域细化 | 引入人工标注/Golden set；推进产品化，衔接人工参与的测评流程；形成定期测试集更新机制，确保新鲜度和覆盖率 |
| 评测失真：业务体感差异大 | 不从业务场景出发，出现伪成功；缺乏跟随业务场景持续优化的驱动力（尤其业务方能力分化大时） | 拉动组织协同（高成本）：提升能力培训，通过理解原理共同推进机制；推进组织考核，对于知识沉淀和经验共享；形成定期沟通/反馈/更新机制 |

## 数据与效果

### 知识工程样例效果

| 指标 | 效果 |
|------|------|
| 交互轮次 | 目标场景：通过 1–2 轮可以有明确产出，数据比对一致，能快速收敛；扩展场景：针对性抽取 3 次内命中，平均降低 30% 轮次 |
| Skill 复杂度 | 目标场景：Skill 复杂度平均降低 70% 以上；扩展场景：复杂度降低 50%；强提醒新增知识入库；要主动做指标的二次聚拢（并解决结构冲突和升级） |

### 总结页的本体架构

最后一张架构图把「本体」拆成两条消费路径：

- **1. 本体知识构建**：本地知识库 → BY RAG；业务知识（文档/邮件/报告、对话、结构业务数据、非结构数据）→ 知识构建（By Agent Ops：transformer、OCR、LLM、Pipeline）→ Ontology（领域知识库）。
- **2. 本体 for LLM**：Ontology → BY OAG（本体查询、知识图谱检索、Logic、函数、AI 预测）→ Prompt 工程 ↔ LLM。
- **3. 本体 for 决策**：Ontology → OAC/Pipeline/action 等 → 启动流程、生成日程、发送邮件通知、写入本体数据（有审批）、调用接口更改外围系统、MCP 调用外围应用。

这张图把「知识工程」从「给 LLM 喂上下文」扩展到「让本体驱动流程与行动」，与讲者「白盒化决策」的主张一致。

## 经验与边界

- **知识工程不是一次性建库**：讲者给出的演进路径是「试验 POC → 小范围验证 → 大范围应用 → 线上化应用」，并在图中标注「可多人协作」「可多场景应用」两个能力台阶。
- **规模化的三个矛盾**：随着领域范围扩大，多人参与协同成本高（尤其结构一致和跨界内容）；随着应用范围扩大，对存量知识检索复杂度提升，性能和准召均下降；多源头知识聚合，抽取复杂度增加带来确定性风险，需要工程化平台。
- **落地形态**：从「无形载体」到「场景化切片和分领域装载」，再到「DataOps 过程供给高质量语义知识」，最终「链接企业知识平台」，形成「AI Friendly 语义/知识」。讲者的目标是「持续推进规模化，形成/融合为公司知识底座」。
- **评测是第二发动机**：讲者没有把评测当作一次性验收，而是把它放进 Skill 生命周期，强调「Agent 测评是 Agent 的一部分」。
- **边界与未展开项**：
  - 「北极星 +1.5」的具体定义未展开；
  - 「CMD AI friendly（40%–80% 增益）」的 CMD 含义与测算口径未说明；
  - 评测看板中的同比数字为示例截图，未说明统计周期；
  - 讲者未披露具体模型、知识库存储选型与知识抽取的模型规模。
