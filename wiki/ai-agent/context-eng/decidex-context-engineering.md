# DecideX 的上下文工程、证据链与评估闭环

> 核心主张：从 BI 到决策智能，缺的不是一个更强的模型，而是“大模型之外”的两项能力——**行业场景的深度积累**与**企业级数据分析治理能力**。DecideX 用业务本体六要素（对象、指标、关系、风险、行动、问题场景）把存量数据资产组织成按任务装配的上下文，用“结论有依据、指标可核查、查询可追溯”的证据链让建议可回看，再用“分析复核 → 行动反馈 → 结果复盘”把反馈沉淀回上下文与分析方法，形成决策闭环。

演讲者：石凯，观远数据。演讲标题为“从 BI 到决策智能”，副标题为“DecideX 的上下文工程与决策闭环实践”。文件名为“Decidex 的上下文工程、证据链与评估闭环”。

## 背景与问题

### 业务现场：从业绩洞察到分层辅导，再到一线执行追踪

演讲从一个渠道经营现场开始。业务链条是：

```
区域/区经 发现组织短板
  → 主任 定位团队改善机会
  → 业代 把改善落实到门店
  → OA 工作入口 接受、执行、求助、完成与反馈
  → 行为证据回收 → 指标复算 → 改善/未改善 → 有效打法沉淀 → 下一轮辅导
```

现场数据揭示了问题的层次：

| 角色 | 现场情况 | 待办 |
|------|----------|------|
| 区域/区经 | 8 名主任，5 名达成率低于 70% | 主任经营辅导待办：确定重点主任、判断差距与优先级；确认主任改善计划 |
| 主任 | 24 名业代，平均达成 70%，13 名低于 70% | 业代改善辅导待办：拆解目标缺口、安排陪访与店·品·路线；分派业代行动 |
| 业代 | 拜访完成率高，但活跃门店与经营转化偏低 | 个人业绩提升待办：激活门店、SKU 铺货、陈列整改、首单与复购；反馈动作与结果 |

这个现场说明：数据能告诉管理者“谁低”，但未必能告诉一线“去哪家店、补什么货、改哪个陈列、找谁跟进”。从洞察到动作之间，还缺一层可执行的上下文。

### 1000+ 现场原声：既要数据可信，又要转化为经营结果

演讲引用了 1000+ 客户现场的原声：

- 秋田满满合伙人：“一线需要的不是一个工具，而是锦囊，是业绩。”
- 宝洁 CIO：“AI 看起来很强，但不懂企业的经营逻辑，没法放进关键决策流程。”
- 上汽数据分析负责人：“从报表到行动，中间的最后一公里，一直没有被打通。”
- 弘阳地产 CFO：“现在数据治理结构很不规范，AI 跑起来会自动化放大错误数据。”
- 零跑汽车 BI 及数据治理负责人：“当前阶段首要工作是先划分业务域、抽取数据主体，再从核心业务指标出发构造面向 AI 分析的可信分析资产。”

这些原声指向同一组矛盾：业务要的是结果与行动，AI 需要的是企业上下文与可信数据；两者之间既缺业务逻辑，也缺治理基础。

### 决策智能平台的两个核心能力在“大模型之外”

演讲用一个四象限说明市场位置：

| 象限 | 代表 | 能力与局限 |
|------|------|------------|
| 业务系统 / 行业 SaaS | ERP / MES / APS | 懂流程执行，但跨系统分析与决策能力有限 |
| 通用大模型 / Agent 平台 | 通用智能平台 | 有通用智能，但缺少企业数据上下文与业务闭环 |
| 数据平台 / BI / 数仓基础设施 | 数据平台、BI 厂商 | 有企业数据基础，但通常停留在看数与分析 |
| 决策智能平台 | 观远数据 DecideX；Palantir 等决策智能平台厂商 | 连接数据、场景与行动，推动决策闭环 |

纵轴是“行业场景的深度积累”，横轴是“企业级数据分析治理能力”。演讲的判断是：决策智能平台的竞争力不在模型本身，而在两条坐标轴上的积累。

### 四个必须回答的问题

演讲把问题拆成四问，对应四个章节：

1. 现有数据资产，如何变成可用上下文？
2. AI 如何理解企业的业务逻辑？
3. 分析结果，如何转化为业务行动？
4. 如何核查决策依据、复盘行动效果？

这四个问题也构成了 DecideX 的上下文工程、业务本体、行动闭环与评估闭环。

## 方案/架构

### 支撑业务判断需要三类上下文

演讲用一张图说明“支撑这些业务判断，需要哪些上下文？”：

| 业务问题 | 需要的上下文 | 资产来源 |
|----------|--------------|----------|
| 谁负责哪里，事实发生了什么？ | 数据资产表：组织人员·区域路线、门店·SKU·经营目标、拜访·订单·陈列铺货；关联键·数据来源·更新时间 | 客户数仓 / 数据中台（Dataflow：数据开发与供给） |
| 达成与转化，按什么口径比较？ | 统一的指标语义：目标达成率（实际/目标）、拜访完成率、活跃门店、经营转化；统一统计口径、时间窗口与组织层级 | 指标中心（复用已定义口径）、万+ BI 分析卡片（提取指标定义） |
| 差距如何定位，为什么这样辅导？ | 分析知识：结果差距 → 过程短板 → 店·品·路线机会；判断依据、辅导逻辑、适用条件 | 客户 BI 页面 / 分析应用（页面分析与洞察逻辑） |

这三类上下文分别回答“事实”“口径”“判断”。演讲用“数据/知识金矿？”的设问提醒：存量资产很多，但不等于可以直接被 AI 使用；需要把数据、指标与分析知识组织起来。

### 行业经验驱动的 Skill：让存量资产成为可用上下文

DecideX 的第一个关键做法，是用“行业经验驱动的 Skill”把存量资产转成可用上下文。Skill 的上方是“近千家客户实践沉淀的行业方法”：业务问题、指标口径、分析路径、判断条件。

Skill 内部做三件事：

| 步骤 | 做什么 | 具体内容 |
|------|--------|----------|
| 01 语义理解 | 理解字段与业务含义、指标口径与分析路径 | 字段与业务含义；指标口径与分析路径 |
| 02 使用行为分析 | 用真实使用行为辅助排序 | 识别资产使用频次；结合业务重要性排序；热度辅助排序，质量独立核查 |
| 03 质量核查 | 检查资产是否可信 | 冲突、重复、缺失、失效；核对来源与可追溯性 |

输入有两类：存量资产（页面/仪表板、BI 分析卡片、数据集·字段·度量、公式·筛选条件）与使用行为（访问·查询·引用）。输出有三类：指标候选清单（维度、口径与来源）、分析场景（业务问题与分析路径）、洞察知识（判断依据与适用条件）。

输出经过“业务专家确认 + 质量校验（语义、口径与适用条件）”后，才成为 Agent 可用上下文。质量核查发现的“待整改清单”则交给责任人整改。这个设计把“资产热度”和“资产质量”分开：热度可以辅助排序，但不能替代质量判断。

### 准备分析输入：数据、指标与业务知识

演讲把分析输入拆成三块：

- **数据集**：提供业务事实与归属依据。主数据包括人员、区域、线路、门店、SKU；业务事实包括目标、订单、拜访、陈列、稽查；归属关系是人员—线路—门店。
- **指标体系**：提供可引用的计算口径。覆盖目标达成、时间进度、门店活跃与品类表现；指标有定义、计算有口径、使用有适用维度。
- **分析场景知识**：沉淀业务问题与分析方法。业务调研知识库按“问题场景 / 分析逻辑 / 关键口径”整理，例如分销目标达成、拜访与经营转化、主任经营复盘、历史归属与业绩比较。

产品界面中可以看到具体资产：`fact_业代月度目标`、`fact_分销订单明细`、`fact_拜访明细`、`dim_人员主数据`、`dim_门店主数据`、`relation_业代线路服务关系`。指标“水品类目标达成率”的计算公式是 `[水品类分销金额] / [水目标金额]`，适用维度为业代名称、年月。

### 业务本体：关联资产与知识，按任务组织上下文

DecideX 的核心结构是“业务本体”。它先把已有资产（数据集、指标体系、分析知识）关联成一张业务网络，再围绕当前任务选取上下文。

业务本体覆盖的领域包括：拜访执行域、陈列执行域、分销交易域、目标与经营管辖域、组织归属、渠道组织域、商品与陈列基础域、SKU 稽查域。产品领域视图用三种颜色区分：对象（蓝）、风险（红）、行动（橙）。

当前决策任务示例：“诊断 2026 年 8 月业代业绩，定位应提升的门店、商品、路线和陈列动作。”上下文装配示例如下：

| 装配项 | 内容 |
|--------|------|
| 相关对象 | 业代—线路—门店—SKU，按 2026 年 8 月归属限定范围 |
| 指标口径 | 目标达成率、活跃门店目标达成率、拜访完成率及适用维度 |
| 分析路径 | 整体表现 → 低达成人员 → 再定位门店、商品与陈列 |
| 风险规则 | 目标滞后、门店活跃不足、陈列异常及对应判断依据 |
| 行动方法 | 门店激活、SKU 铺货、陈列整改，候选建议由业务确认 |
| 输出要求 | 重点人员、线路、门店与商品，关联指标依据与改善方向 |

演讲的原则是：“口径或范围不清时，先确认再分析。”Agent 的分析路径是“整体表现 → 问题归因 → 行动建议”。总原则是“先把资产关联起来，再围绕任务组织上下文”。

### 让上下文有据可依：绑定数据与指标

业务本体要解决三个“有据”：

| 维度 | 做法 | 示例 |
|------|------|------|
| 对象有来源 | 数据集提供实例与属性；主键识别对象，展示键便于理解 | `dim_商品SKU主数据`，包含商品 SKU 主数据，含品类、品牌、规格、价格和销售分类 |
| 关系有依据 | 按业务键连接对象；历史责任按生效时点匹配 | 起点“主任” → 终点“SKU 稽查”，本体关系描述“主任关联 SKU 稽查” |
| 指标有归属 | 对象引用指标，风险引用依据；保留计算口径与适用维度 | 分销金额、活跃门店目标达成率、目标达成率、目标金额挂到具体业务对象，并标注关联风险与状态 |

演讲用一条链路概括：**业务身份 → 关联范围 → 度量口径**。每个数据要说明：“属于谁、怎么算、按哪个时点解释”。

### 让上下文承载分析经验：问题场景与四类知识

业务知识不能只停留在 Excel 里。DecideX 把“业务调研知识库”整理成“问题场景”：

- 问题场景名称：分销业绩与目标达成。
- 描述：用于识别业代、主任在月度分销目标下的达成进度、排名表现和目标缺口，支持按时间、人员、区域及历史归属口径进行业绩归因。
- 本体对象成员：线路门店覆盖关系、业代主任归属关系、业代线路服务关系、主任月度目标、业代、业代月度目标、主任、分销订单明细。

分析知识按用途分别沉淀为四类：

| 类型 | 作用 |
|------|------|
| 问题场景 | 确定分析范围，定义业务问题与分析边界 |
| 风险定义 | 沉淀判断依据，沉淀业务风险与识别规则 |
| 行动说明 | 沉淀处理方法，沉淀分析方法与执行步骤 |
| Agent 指令 | 约束分析规范，约束分析口径与输出要求 |

这一步把“业务专家脑子里的经验”变成可被 Agent 检索、引用和复用的结构化知识。

### 让分析经验支撑业务判断：证据指标 → 风险判断 → 排查重点 → 建议行动

DecideX 的风险对象把“指标—风险—行动”串起来：

```
证据指标（达成率、目标缺口、时间进度）
  → 风险判断（目标达成滞后）
  → 排查重点（重点业代、门店、品类）
  → 建议行动（目标追赶、经营复盘）
```

以“目标达成滞后”风险为例：

- **判断条件引用明确指标**：业代或主任当前分销进度低于月度目标要求，可能导致月度冲量压力上升。重点关注目标达成率、目标缺口金额和时间进度差，并结合分销金额、目标金额、活跃门店目标达成率、水品类目标达成率判断缺口来源。排查时优先定位低达成业代、低贡献门店和落后品类。
- **指标提供可核查的依据**：`目标缺口金额 = 目标金额 - 分销金额`；示例返回“目标缺口金额 1489563.6000...、目标金额 18433029.6、分销金额 16943466”。适用对象为业代；时间进度差、目标缺口金额、活跃门店目标达成率、分销金额、目标达成率、目标金额、水品类目标达成率均为在线指标。
- **风险关联具体处理方法**：推进业代与主任目标追赶；组织主任辖区经营复盘。

这条链路的关键是：风险不是一句“业绩不好”，而是“哪个指标、什么阈值、缺口多少、找谁、做什么”。

### 产品架构：5A 路径与四层结构

DecideX 所属的观远 AI 决策智能平台（2026 产品架构图）提出 5A 路径：

| 阶段 | 含义 |
|------|------|
| Agile 敏捷化 | 一天完成构建，一周投入试运行 |
| Applied 场景化 | 一个月进入真实业务工作流 |
| Automated 自动化 | 自动生成决策洞察与行动建议 |
| Actionable 行动化 | 落地到可执行、可追踪的业务动作 |
| Adaptive 自进化 | 基于反馈闭环持续学习与优化 |

平台分四层：

- **人机协作层**：通用决策入口（BI、ChatBI、洞察 Agent）与场景化 Agent / 数字员工（电商运营、门店经营、销售分析、供应链、经营分析、财务分析、营销运营、风控审核）。
- **智能中枢层**：DecideX 决策智能体平台，包含决策 Agent 构建（决策分析能力、垂直场景决策模型、Decision & Agent Runtime 运行时）与企业级决策 Agent 运行保障（决策治理、决策评估、发布集成、反馈学习）。
- **决策上下文层**：AI 可信运行的决策上下文治理，包括角色定位、业务本体、指标语义、数据语义、风险定义、策略行动、场景 Skills。
- **企业级数据底座**：数据开发平台、数据治理中心、指标中心。

## 关键工程做法

### 按任务装配上下文，而不是把全库塞给模型

DecideX 的上下文不是“全量知识库检索”，而是围绕当前决策任务装配：

1. 先明确分析范围（问题场景、描述、本体对象成员）。
2. 再按任务选取相关对象、指标口径、分析路径、风险规则、行动方法与输出要求。
3. 口径或范围不清时，先确认再分析。

这与“把整份 YAML、全库 Schema 或所有指标都放进上下文”的做法相反。上下文装配的目标是“足够支撑当前判断”，而不是“尽量多”。

### 证据链：结论有依据、指标可核查、查询可追溯

DecideX 把“事后回看”做成三层证据：

| 层次 | 回答的问题 | 案例内容 |
|------|------------|----------|
| 01 结论有依据 | 回看当时的判断与风险提示 | 核心判断：低达成业代的优先提升对象已落到具体线路和门店；共性问题是活跃门店达成低、到店质量未完全闭环和冰柜陈列不合格，部分门店还存在重点 SKU 未铺货。风险与边界：目标达成滞后（13 名业代在 2026-08 的目标达成率低于 70%，且均有明确目标缺口）；拜访执行不足（拜访完成率均超过 100%，但优先门店中标准距离内拜访通常为 5 至 6 次/8 次，需提升到店质量和转化闭环） |
| 02 指标可核查 | 引用指标与关键返回是否一一对应 | 活跃门店目标达成率（指标标识 `9610398f4e644497ebffa01f`）：13 名低达成业代的活跃门店目标达成率介于 10.00% 和 11.11% 之间；拜访完成率（指标标识 `te9bad3b472c545749a9c8c7`）：低达成业代的拜访完成率均超过 100%，拜访数量不是主要短板 |
| 03 查询可追溯 | 回看指标查询的维度与筛选范围 | 指标“拜访完成率”：`guancli metric get te9bad3b472c545749a9c8c7 --brief -f json`；按主任名称、业代名称查询：`guancli metric query te9bad3b472c545749a9c8c7 --dim 主任名称 --dim 业代名称 --filter 拜访日期 BT 2026-08`；拜访日期范围为 2026-08-01 至 08-31 |

演讲的总结是：“留下的不只是建议，还有形成建议的依据。”这使建议可以被业务复核，也便于后续定位“是判断错了、指标错了，还是查询范围错了”。

### 行动闭环：建议 → 业务确认 → 执行 → 复检 → 观察

分析建议不是终点。DecideX 把行动落到门店、商品与业务跟进：

- **优先范围如何确定**：比较各线路、门店的签收表现，结合陈列检查确认。
- **方宇**：上海重点线路 3、上海 17 号店、清源饮用水 350ml；核查店品签收金额及排名、陈列重点位是否合格；待确认建议是“整改重点位”。
- **梁辰**：北京重点线路 3、北京 46/22 号店、清源运动水 600ml；核查两店分别的店品签收金额、各店冰柜陈列是否合格；待确认建议是“补齐冰柜陈列”。
- **吴楠**：成都重点线路 1、成都 07 号店、轻享果味饮桃味；核查店品签收金额及排名、标准陈列是否合格；待确认建议是“补齐标准陈列”。

建议确认后的业务跟进分四步：1 业务确认（核对指标与现场情况）→ 2 陈列整改（明确责任人与期限）→ 3 复检验收（检查对应陈列项）→ 4 经营观察（跟踪同店同品签收表现）。

### 评估闭环：分析复核 → 行动反馈 → 结果复盘

DecideX 的“评估闭环”不是模型离线评测，而是业务决策与行动效果的复盘：

| 环节 | 内容 | 案例数据 |
|------|------|----------|
| 01 分析复核 | 复核分析结论与口径 | 2026 年 8 月，13 名低达成业代；拜访完成率 >100%；活跃门店目标达成率 10.00%—11.11%；从拜访数量转向到店转化，聚焦门店激活、铺货与陈列 |
| 02 行动反馈 | 建议有没有落地 | 整改推进中；建议采纳：门店激活、SKU 铺货、陈列整改；执行情况：按重点门店逐项跟进；责任与时间：主任统筹、业代执行；整改周期 9 月 16—22 日；复核日期 9 月 23 日；反馈说明：已观察到阶段改善，持续记录现场动作与结果 |
| 03 结果复盘 | 业务有没有改善 | 9 月 23 日复核；同一批重点门店、相同活跃口径；门店激活 10 家 → 15 家，增加 5 家；SKU 铺货覆盖情况有所改善；陈列执行重点位执行有所改善；复核结论：本轮复核已见改善，持续跟踪改善幅度与稳定性 |

复盘之后还有一步“把有效做法沉淀为下一次分析的参考”：门店覆盖、SKU 铺货、陈列质量 → 业务确认 → 更新分析知识与行动方法 → 供下一次分析使用。演讲的总结是：“把每次分析与行动的反馈，沉淀为下一次决策的参考。”

### 跨对象复用：业务本体让关系成为可查询的网络

演讲用一个问题说明本体的价值：“某主任业绩滞后，需要排查哪些门店的陈列？”

**未建立本体**时，关系写在知识与步骤中（知识库、Skill、Prompt），需要显式描述四步：1 找到主任管理的业代；2 找到业代负责的线路；3 找到线路覆盖的门店；4 查询这些门店的陈列数据。问题或分析范围变化时，往往需要调整路径说明。

**建立业务本体**后，关系形成可查询的业务网络（对象 + 关系 + 数据绑定）：

```
主任 → 管理 → 业代 → 负责 → 线路 → 覆盖 → 门店 → 关联 → 陈列数据
```

Agent 按问题选择入口与范围，沿已定义关系查找数据、组织分析；问题变化时，可复用关系并调整检索范围。本体带来三个价值：减少关系重复描述（关联语义可在多个任务中复用）、帮助圈定相关数据（按问题调整关联范围与取数路径）、辅助跨对象分析（为关联检索与分析推理提供线索）。

演讲同时给出边界：“本体提供关联线索，判断仍需结合业务规则与数据证据。”

## 经验与边界

### 上下文的质量取决于底层数据治理

演讲引用弘阳地产 CFO 的原声：“现在数据治理结构很不规范，AI 跑起来会自动化放大错误数据。”零跑汽车的判断则是“先划分业务域、抽取数据主体，再从核心业务指标出发构造面向 AI 分析的可信分析资产”。这说明上下文工程不是把现有报表接上模型，而是要先完成业务域、数据主体与核心指标的组织。

### 本体提供线索，判断仍要靠业务规则与证据

演讲明确边界：“本体提供关联线索，判断仍需结合业务规则与数据证据。”业务本体能告诉 Agent“主任—业代—线路—门店—陈列数据”的关联路径，但不能替代风险阈值、业务规则与现场判断。因此 DecideX 在风险对象里保留“判断条件、引用指标、适用对象、应对行动”，在行动侧保留“候选建议由业务确认”。

### 建议必须经过业务确认，行动才算闭环

从案例可以看到，系统给出的是“待确认建议”（整改重点位、补齐冰柜陈列、补齐标准陈列），业务确认后才进入“陈列整改（明确责任人与期限）→ 复检验收 → 经营观察”。这避免把模型建议直接当成执行指令，也把“分析正确”与“行动有效”分开评估。

### 评估闭环是业务效果复核，不是模型离线评测

本演讲中的“评估闭环”由分析复核、行动反馈、结果复盘构成，核心是“建议有没有落地、业务有没有改善”，并以门店激活 10 家 → 15 家等业务指标验证。它不同于 [[agent-evaluation-framework]] 中的模型/Agent 离线评测（评分器、Trace、回归集）；两者可以互补，但不应混为一谈。

### 跨平台数据与单条履约链

世界 500 强消费品企业的仓库履约案例说明：数据分布在 Databricks、PostgreSQL、观远 BI / SmartETL 等不同平台，但问题发生在同一条履约链上（订单承诺 → 库存分配 → 拣选复核包装 → 发运交接 → 履约结果）。DecideX 的做法是“跨平台获取上下文 → 围绕订单履约还原仓库运转 → 联合判断形成处置方向”，并强调“关联对象、对齐口径、校验时效”“复用不同平台上的现有资产”“处置建议由业务确认”。

### 方法边界

- 业务本体不是数据库 schema：它表达对象、关系、风险、行动与问题场景，物理数据通过数据集与指标绑定。
- 分析知识需要持续维护：问题场景、风险定义、行动说明、Agent 指令四类知识都要随业务变化更新。
- 行动闭环依赖组织配合：责任与时间、整改周期、复核日期、复检与观察都需要业务角色参与。
- 案例数据存在演示成分：带星号或标注“场景示意”的数值不能当作真实效果承诺。
