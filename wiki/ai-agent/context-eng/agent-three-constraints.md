# 业务 Agent 的三重约束：角色 · 知识 · 动作

> 核心主张：业务 Agent 的价值不是「让模型更聪明」，而是**吸纳业务资产，把 How（如何完成任务）的认知负担降下来**。落地的抓手是把 Harness 拆成业务侧的三道约束——角色（它是谁）、知识（它能调用什么）、动作（它能做什么），并且「模型只在生成候选处自由；越靠近副作用，越是代码说了算」。

来源：DACon 2026 北京站「模型适配与效果优化：从语义上下文、Harness 到后训练」分论坛，孟垂实（京东科技集团算法总监、京东智能城市研究院高级研究员）《给模型立规矩，业务 Agent 的三重约束——角色·知识·动作，以营销策略 Agent 与数据分析 Agent 为例》，共 32 页。

讲者背景（原文）：计算机科学博士（纽约州立大学布法罗分校），研究方向为时空机器学习、城市计算与智能 Agent；顶会论文 20+ 篇、累计被引 1800+ 次；北京市科技新星、北京市经开区优秀人才、CCF 人工智能专委会执行委员；主导南通、大同、南京、上海普陀等地城市数字基础设施建设；负责智能研判、智能营销等垂类业务 Agent 产品设计与研发。

## 背景与问题

### 两个痛点场景：都「知道 What」，都不知道 How

| | 营销侧场景 | 分析侧场景 |
|---|-----------|-----------|
| 知道 What | 清楚策略逻辑：唤醒沉睡、发提醒、促复购、给优惠 | 经营人员分析需求：取数、分析、汇总、建议 |
| 不知道 How | 强制手工完成长串动作 | 存在断点困境 |
| 具体表现 | 选客群、拖节点、配分支、找标签、填模板、设时间、校验端口、发布 | 不会找表、不会写 SQL、说不清计算口径 |

**共性启示**（原文）：

- 传统系统要求用户将业务意图翻译成操作流程；
- AI 应消除翻译的**认知负担 & 操作负担**，让用户专注业务目标。

### 三条核心判断

| # | 主题 | 判断 |
|---|------|------|
| 01 | 改造对象 | AI 改造的对象不是页面，而是业务流程中的**认知负担**；核心本质是降低人的操作难度 |
| 02 | 产品哲学 | 好的 AI 产品是**可控性与灵活性的平衡**：正确的地方自由（赋予模型灵活性）、危险的地方受限（确保业务可控性） |
| 03 | 工具定义 | **Harness 是给模型立规矩的约束体系**：角色约束明确 Agent 的身份定位与能力边界；知识约束注入企业特有的领域专业资产；动作约束规范任务执行的标准路径与权限 |

> 原文：「业务 Agent 的价值：吸纳业务资产，把 How（如何完成任务）的认知负担降下来。」

### Harness 的广义概念：两层

原文把 Harness 分成两层，并明确本讲的定位是上面那层：

| 层 | 定义 | 组成 |
|----|------|------|
| **业务约束层**（本讲聚焦） | 在具体业务里约束模型的那套规矩，补充只有业务才能给的核心要素 | 角色（判定标准，决定行为准则）、知识（专属资产，提供业务语境）、动作（副作用前的业务校验） |
| **基础设施 Harness** | 运行 Agent 的通用运行时（如 codex、deepseek-harness） | Agent Loop、工具路由、审批·沙箱、权限模型、上下文管理、资源检索 |

> 原文：「缺基础设施层，跑不起来；缺业务约束层，不可发布。」

### 对比通用 Agent：垂直业务的要求更高

| | Coding 编码场景 | 垂直业务场景 |
|---|----------------|-------------|
| 判断标准在哪 | 在仓库里 | 在人脑与规则里 |
| 什么算对 | 能编译、能跑完就算对 | 通用 Agent 看不见它 |

通用 Agent 在垂直业务里的三个缺口：

- **没有身位**：不知道自己是谁、对什么负责；
- **没有专属资产**：知识是全网通识，答得漂亮却错得优雅；
- **不承担副作用**：业务要的那个「对」，它不负责。

> 原文：「通用 Agent 不是弱，是垂直业务场景的要求更高。」

## 方案/架构

### 一句话定义：Harness = 三道约束

| 约束 | 要回答的问题 | 落地物 | 对应认知 |
|------|------------|--------|---------|
| **角色约束** | 它是谁 · 怎么判断 · 何时拒绝 | 角色宪章（明确职责与拒绝线） | 怎么思考 |
| **知识约束** | 能调用哪些事实 · 口径 · 经验 | 资产能力化：图谱 · 指标库 · 案例库 · 文案库 | 知道什么 |
| **动作约束** | 能执行哪些动作 · 副作用前验证 | 业务原语 + 确定性校验 | 能做什么 |

### 三道约束怎么装起来：注入 · 检索 · 收口

| 层 | 装载方式 | 运行时特征 |
|----|---------|-----------|
| 角色层 | 注入提示词栈 | 每次循环都在场；不变的是身份与拒绝线 |
| 知识层 | 检索即服务 | 需要时才召回；取数粒度由业务定义 |
| 动作层 | 代码收口 | 模型碰不到；执行全由代码校验函数接管 |

原文把「槽」和「内容」分开：

- **基础设施 Harness 给槽**——提供「怎么防」的机制：提示词槽、知识检索口、工具闸；
- **业务层 Harness 把规矩装进槽**——定义「防什么」的内容：身份与拒绝线、业务取数粒度、代码校验函数。

> 两者「互为补充，非替代」。总原则：「模型只在生成候选处自由；越靠近副作用，越是代码说了算。」

## 关键工程做法

### 案例一 · 智能营销 Agent

#### 先认识营销系统

原文定义：营销系统是**一套流量分发与状态改变机制**，链路为「流量 → 筛选 → 触达 → 状态判断」。

状态判断的例子：已下单 → 复购；已加购未下单 → 优惠提醒；反复浏览 → 优惠实验 & 换触达渠道；未打开 → 人工跟进。

过去全靠手工，一步都省不掉：选客群 → 拖节点 → 配分支 → 找标签 → 填模板 → 设时间 → 校验端口 → 发布。

> 产品发心（原文）：「让业务人员描述业务目标，系统把它变成可检查、可编辑、可执行的策略。」

#### 第一重约束 · 角色：营销专家宪章

宪章的定义（原文）：由一线岗位凝练的端到端营销专家——「我是谁、承担哪些职责、通过哪些途径获得支持、什么算完成什么必须拒绝」。

四个岗位职责：

| 岗位 | 一句话职责 | 具体内容 |
|------|-----------|---------|
| 活动策划者 | 目标译成路径 | 经营目标 → 主题 · 人群 · 路径 · 成功标准 |
| 数据分析者 | 定人群口径 | 人群口径 · 可用数据 · 效果观察 |
| 文案脚本工作者 | 出可审阅候选 | 给可审阅候选文案，不直接发送 |
| 运营风控者 | 不完整不发布 | 检查资源、频控、触达资格、库存、合规和停止条件 |

**好宪章 vs 坏宪章**（原文对照）：

| | 好宪章 | 坏宪章 |
|---|--------|--------|
| 结构 | ① 身份（它是谁）：营销增长策略专家；② 使命（对什么结果负责）：「把经营目标转成可验证、可编辑、可执行的营销策略，并对人群口径、流量状态、触达表达和结果观察负责」；③ 六条原则（怎么工作、何时拒绝） | 「你是一名营销专家。请灵活使用 Push、优惠券、AB 测试和文案生成工具，帮助用户提升转化率。遇到问题时自行决定下一步。」 |
| 问题 | — | 仅有身份口号与工具清单；未说明要承担哪些原本由人完成的职责；缺乏拒绝线与完成标准；业务判断留白、盲目试错 |
| 结论 | — | 「看似自由，实为空白」 |

六条原则（好宪章的核心）：

1. **确认目标与标准**：确认目标、人群、业务主题和成功标准，再设计路径；
2. **把人群看作流量**：把触达、等待、筛选、实验看作改变状态的动作；
3. **行动前先召回资产**：每次行动前先召回人群口径、组件关系、配置规则、历史策略和文案经验；
4. **检查合规与频控**：同时检查数据口径、资源条件、触达限制、频控和合规要求；
5. **缺信息先澄清阻断**：少必要信息时先澄清或阻断，不编造人群、指标、资源和效果；
6. **说明状态与窗口**：每一步都说明当前状态、下一步目的和观察窗口，最终交付可编辑、可校验、可回放的策略。

#### 第二重约束 · 知识：策略画布 + 历史策略 + 文案库

**策略画布**的四要素：

| 要素 | 含义 | 内容 |
|------|------|------|
| 节点：组件 | 画布上的动作单元 | 条件筛选 · 触达 · 等待 · 实验 |
| 边：业务控制流 | 状态转移 | 什么状态的人，为什么走下一步 |
| 约束：前置条件 | 能不能发 | Push 需可触达标签，缺一即不可发 |
| 目的：这条路径要完成什么 | 目标 | 召回 · 促活 · 转化 |

业务人员看到的是分群与分流（原文示例）：黑金走短信、钻石走 PUSH、铂金走人工电话、黄金走智能电话、白银走微信消息。

**经验的能力化**——把非结构化经验转成带 Schema 的标准化条目：

| 资产 | 原来 | 现在 | 卡片字段 |
|------|------|------|---------|
| 历史策略 | 依靠人工翻阅的活动文档 | 按主题、目标和结果精准检索的案例条目 | 基本骨架：策略主题、目标人群、关键路径；边界与成效：适用条件、结果摘要 |
| 文案经验 | 散落在个人脑海中的碎片 | 包含适用状态、语气等字段的结构化数据 | 场景与风格：适用状态（例：已触达但未下单前）、语气；红线与优化：禁用表达（例：夸大折扣、性别刻板印象）、效果反馈 |

> 能力沉淀的三大标准：**可理解 · 可比较 · 可检索**。

#### 第三重约束 · 动作：原语与确定性校验

原文强调：「确定性校验不是模型自判，而是代码兜底。」

**一次原语执行**：读状态与缺口 → 选一个原语（例如：绑定触达标签、连接组件）→ 代码校验 → 三种结果（允许 / 拒绝 / 需要补充）。

**代码里的前置校验**（这些校验在代码里执行，模型碰不到）——五项：

| 校验项 | 检查内容 |
|--------|---------|
| 资源 | 优惠券库存 |
| 权限 | 可触达标签 |
| 端口 | 触达通道 |
| 比例 | 实验分流比例 |
| 时间 | 频控窗口 |

> 原文：「模型只提候选，落到画布、触发发送由代码执行」「确定性校验由代码兜底·缺一即阻断」。

### 案例二 · 经营研判 Agent

#### 第一重约束 · 角色：业务分析专家宪章

宪章目标（原文）：**让每个结论都有口径、有证据、可复核**。

五个岗位，串成一条「先澄清 · 定口径 · 选路径 · 选对比 · 讲来源」的链：

| 岗位 | 动作 | 职责 |
|------|------|------|
| 问题分析者 | 先澄清 | 时间范围和判断目的 |
| 指标管理者 | 定口径 | 说明粒度、维度和范围 |
| 数据建模者 | 选路径 | 选表、选列、选关联路径 |
| 分析研究者 | 选对比 | 分组、排序、趋势和对比 |
| 结果解释者 | 讲来源 | 数据血缘、结果溯源 |

> 原文：「第一重约束在研判场景里还是角色。」

#### 第二重约束 · 知识：语义层六类元素

「五类节点 + 一类关系」，把「业务的说法」与「库里的表列」接起来：

| 元素 | 定义 |
|------|------|
| 表节点 | 业务主题、粒度和生命周期 |
| 列节点 | 字段语义、数据类型、枚举解释和可用范围 |
| 业务概念节点 | 业务术语、同义词、定义和计算逻辑 |
| 指标节点 | 带粒度、维度和过滤条件 |
| 分析逻辑节点 | 聚合、过滤、同比、窗口和排名 |
| 关系边 | 依赖 · 同指 · Join |

实际下钻路径（原文示例）：完成产值 →（依赖）订单金额列 →（组成）项目表 →（引用）SQL 模板 →（组合出）Top N。

**指标库：可引用的业务逻辑接口**。原文给出一个完整条目：

| 字段 | 内容 |
|------|------|
| 名称 · 定义 | 项目月度完成产值：按项目汇总当月已确认的产值金额 |
| 粒度 | 项目 · 月 |
| 维度 | 项目、月份 |
| 过滤 | 订单状态＝已确认，统计日期在目标月内 |
| SQL 模板 · 版本 · 责任人 | `metric_project_monthly_output_v2`；版本 v2；责任人 经营分析团队（可被执行） |

**分析 Skill：承载用户偏好**（原文四条）：

1. 先结论后过程——先给答案，再展开推理过程；
2. Top N 与同比——常用排名与同比分析；
3. 默认柱状图——比较项目时默认用柱状图；
4. 列出异常项——结论里习惯列异常项与后续建议。

> 原文：「语义层管事实，Skill 管怎么看。」「Agent 复用统一口径，再结合当前问题决定筛选、分组和排序方式。」

#### 第三重约束 · 动作：原语 & 权限 & 证据

**三道硬校验**（执行前完成，缺一即阻断）：

| 校验 | 要求 |
|------|------|
| 只读 | 查询原语是类型化的只读计算动作，不允许隐式写操作 |
| 权限 | 权限与字段校验在查询执行前完成，过滤越权字段和表 |
| 证据 | 每个关键数字都带来源、计算逻辑和血缘，缺一不可 |

**查询七步流水线**：① 业务问题 → ② 召回语义子图 → ③ 引用指标库 → ④ 启用分析 Skill → ⑤ 形成分析计划 → ⑥ 校验权限·字段·只读 → ⑦ 执行并绑定引用 → 输出结论·图表·过程。

> 原文标注：「第 6 步是这条流水线上唯一的拦截点。」「口径可引、权限可控、数字有血缘。」

原文的现场演示（视频占位）给出的分工骨架：理解问题 → 选择口径 → 组织路径 → 选择分析 → 执行解释，整条分析链路每一步都可追溯。演示画面为产品 **JoyAnalysis**（工作空间「中汇人寿」）。

## 经验与边界

### 企业落地路线：五步

原文把三道约束拆成一条「企业照着就能走」的路线：

1. **立角色约束** —— 角色宪章
2. **立知识约束** —— 资产盘点
3. **立动作约束** —— 业务原语
4. **接入 loop**
5. **回到产品闭环**

### 两个落地挑战与对策

| 挑战 | 表现 | 对策（原文） |
|------|------|-------------|
| **隐性知识显性化** | 角色宪章、业务图、指标库都依赖对资深员工经验的一手抽取；初期投入重、见效慢 | 用业务闭环画布锁闭环；小切口把资产盘点做扎实；用复用率、越权拦截率证明价值 |
| **生成式与验证式边界** | 边界定松了会出事，定紧了会丧失灵活性 | 以副作用梯度为原则；生成式只在提出候选处自由；最终由代码收口；客户、产品、研发对齐测试数据集 |

### 三个可带走的模板

**模板一 · 角色宪章模板**——把岗位职责和拒绝线，写成八行可以直接填的表单：

1. 角色名称 · 服务对象
2. 对什么结果负责
3. 如何理解对象状态
4. 承担哪些岗位职责
5. 从哪些工具得反馈
6. 工具能解决什么
7. **何时必须澄清或拒绝**
8. **什么状态才算完成**

> 原文：「最后两行是全页最该高亮的：何时必须澄清或拒绝。」

**模板二 · 业务资产卡片**——「业务面三枚 · 结构面两枚 · 元信息一枚」：

| 面 | 字段 |
|----|------|
| 业务面 | 资产名称 · 主题；解决什么问题；适用人群 / 场景 |
| 结构面 | 图谱节点或边；前置条件与约束 |
| 元信息 | 来源 / 版本 / 责任人 |

**模板三 · 业务原语与校验清单**——三步：

1. **列动作**：列出闭环里所有有副作用的动作（发送、发布、写入、外呼、退款…）；
2. **收原语**：把有副作用的动作收成业务原语——名称、输入参数、前置条件、写回状态与证据；
3. **挂校验**：再给每个原语挂上五项校验——资源、权限、端口、比例、时间。

### 边界与未展开的部分

- **没有量化验证**：全部效果表述为定性；「发布过闸」「不找表·只读·血缘」是产品行为描述，不是效果指标。
- **依赖资深员工经验抽取**：原文自认「初期投入重、见效慢」，没有给出缩短周期的具体工期或人力估算。
- **生成式/验证式边界靠人判断**：以副作用梯度为原则是原则性回答，原文未给出可操作的划线标准或分级表。
- **行业与场景限定**：两个案例对应讲者团队的产品（智能营销中台、JoyAnalysis 工作空间「中汇人寿」），原文未说明跨行业复用的验证情况。
- **与基础设施 Harness 的接口**：只说明「给槽 / 装规矩」的分工，未给出槽的具体协议、工具闸实现、Trace 与 eval 的接入方式。
