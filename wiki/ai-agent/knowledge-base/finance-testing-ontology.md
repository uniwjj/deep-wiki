# 金融测试本体工程：测试工艺 × 分层本体

> 来源：DACon 2026 北京站「企业本体与知识工程」专场，讲者杨冬瑞（江苏润和软件股份有限公司·人工智能中心）。PDF 共 27 页。

> 核心主张：金融测试的难点不在执行，而在知识——缺、贵、杂、隐。本体不是要建一座大而全的语义宫殿，而是把判断依据变成可关联、可追溯、可复用的知识资产；先有场景再建模，按知识的来源和变化节奏切三层，让本体跟着测试工作一点点长出来。**本体是手段，不是目的。**

## 背景与问题

### 一条金融测试案例的"一生"

讲者用一条脱敏的真实案例开场：交易一致性 | 超时专项。

测试内容：本机构处理超时，钱包 APP 断开连接。

1. 前置：本机构或对手机构处理时间较长
2. APP 发起，本机构向对手机构发一笔报文
3. 本机构 4 秒内未把结果返回 APP
4. 钱包 APP 显示该笔交易超时
5. 用户进入交易记录查看最终结果

这条看似简单的用例，在完整通信链路上有四处分歧：

- 本机构、对手机构"处理时间较长"——"较长"多长才算长？
- APP 发起时就开始计时，还是对手响应到达后才开始计时？"4 秒"从哪一刻开始算？
- "4 秒内不返回"这个异常怎么造？
- 超时后的最终结果怎么判？

一条用例还要经过八个环节：案例理解、数据准备、跨系统操作、日志查询、报文提取、挡板制作、结果比对、证据回填。讲者给出的复杂度公式是：

```
复杂度 = 业务规则 × 系统关系 × 专家经验 × 历史资产
```

"每个部分都可能引入经验或关联知识。"

### 测试的难点在知识：缺、贵、杂、隐

| 困境 | 具体表现 |
|------|---------|
| **缺**：业务知识难共享 | 测试和开发往往由不同厂商参与，需求背后的规则和系统关系难以共享 |
| **贵**：获取成本高 | 文档散、老员工忙，联调记录翻不到；专家忙、没时间 |
| **杂**：关联系统复杂 | APP、本机构、对手机构、挡板、日志，一个案例牵动多方 |
| **隐**：经验信息多 | "较长"多长、异常怎么造、结果怎么判，都没写下来 |

引入本体的目标，是把判断依据变成知识，具体落在三件事：

1. **可关联**：对象—关系—规则，把需求连到系统和案例。
2. **可追溯**：每条知识带来源和版本，结论讲得清依据。
3. **可复用**：一次澄清，下次直接用；人走知识在。

讲者补充：运维、客服、合规等知识密集领域同理。核心是让跨系统的知识能够沉淀、关联和复用，支撑具体测试任务。

### 为什么选择本体：能快速用的不好复用，好复用的建不起

| 方案 | 周期短 | 投入少 | 可复用 | 可追溯 | 结论可信 | 讲者评价 |
|------|--------|--------|--------|--------|----------|---------|
| RAG 知识库 | 强 | 强 | 一般 | 弱 | 弱 | 只管找到，不管对错与时效 |
| 提示词 / Dify / Skill | 强 | 一般 | 弱 | 弱 | 一般 | 取决于写的人，换个场景就失效 |
| FIBO 类参考本体 | 弱 | 弱 | 强 | 强 | 一般 | 定义最准，但测试场景不好用 |
| 场景轻量本体（本方案） | 一般 | 一般 | 一般 | 强 | 强 | 带来源和版本，面向测试意图 |

> 本体的价值在最后一列：结论可信——带来源、可追溯、面向测试意图。但大而全的本体，建得起吗？

### 大而全的本体：建不起、等不起、调不动

讲者列了四个行业级本体作为参照：

| 本体 | 起点 | 规模与节奏 |
|------|------|-----------|
| Cyc | 1984 起 | 通用常识推理；150 万+概念、2500 万+公理 |
| Gene Ontology | 1998 起 | 基因功能注释；约 3.8 万术语（2026） |
| SNOMED CT | 2002 发布 | 临床术语体系；36 万+概念，按月发布 |
| FIBO | 持续维护 | 金融业务语义；数百个本体文件，季度发布 |

共同点：**长期建设、专家协作、持续维护**。而测试项目的现实是：

- **等不起**：项目按周排期，需求下周就要测；行业本体建设周期以年计，需求周期按周推进。
- **调不动**：跨团队协调专家，难以随时到位。
- **定不了**：业务口径需要协同确认。

所以讲者的选择是：**不做大而全，从一个测试场景切小，让本体跟着测试工作一点点长出来。**

### 切小怎么切：按知识的来源和节奏，分三层

一个测试场景里混着三类知识——来源不同、变化节奏不同、维护的人也不同：

| 维度 | 业务知识 | 测试方法 | 执行知识 |
|------|---------|---------|---------|
| 从哪来 | 需求、规范、接口 | 专家经验 | APP、环境、轨迹 |
| 多久变 | 随需求版本变 | 相对稳定 | 随应用版本和环境变 |
| 谁维护 | 业务分析 + 测试 | 测试专家 | 自动化与执行人员 |
| 像什么 | 典型本体 | 方法论 | 知识图谱 |
| 超时专项例子 | 超时阈值 4 秒 | 边界值怎么取 | 挡板延迟怎么配 |

如果硬塞进一个本体会怎样？讲者给了三个后果：

- 需求一改，方法和执行一起受牵连；
- 边界和维护责任说不清；
- 只能一次建完，没法分段交付。

因此分成三层，分别对应测试流程的不同工序：

```
业务本体 → 测试本体 → 应用本体
需求理解 → 测试分析 → 案例生成 → 案例执行
```

分层积累、各自维护，在测试流程中协同使用。

## 方案/架构

### 怎么建：业务本体按层长出来，AI 提候选、人来定

业务本体分五层，自下而上：

| 层 | 内容 | 超时专项示例 |
|----|------|-------------|
| S0 证据 | 需求、规范、接口文档原文，每条知识都能追回来 | 需求文档、接口规范 |
| S1 结构 | 实体、属性、数据契约 | "交易""报文" |
| S2 行为 | 动作、流程、状态 | "发起支付""查询结果" |
| S3 策略 | 规则、条件、例外 | "超时阈值 4 秒" |
| S4 场景 | 端到端业务场景 | "钱包支付超时" |

讲者特别强调：**部分层或信息可以为空，不为填满层级而补造规则和场景。**

构建循环是四步：

1. **AI 提取候选**：从需求、规范、历史案例识别概念、关系、条件。
2. **工具校验**：引用是否存在、类型是否兼容、有无冲突。
3. **人：校准与补建**：确认、修正，也可手动新建实体、关系、属性。
4. **发布版本**：带来源与版本号，可回溯。

使用反馈再进入增量修订，形成闭环。讲者还区分了两类本体：

- **测试本体**：经验和方法论为主，专家方法沉淀成工艺卡与知识包。
- **业务本体**：存量材料和事实为主，功能需求与设计、存量系统知识等。

### 测试工艺：把测试拆成四道工序

| 工序 | 使用的本体 | 做什么 | 产物与要求 |
|------|-----------|--------|-----------|
| 需求理解 | 业务本体 | 澄清业务含义、明确被测要素、绑定测试数据 | 分析链路的起点，问题可追溯、可澄清 |
| 测试分析 | 测试本体 | 消费需求、业务本体，生成案例 | 设计有依据，案例可操作，问题可溯源 |
| 案例生成 | 测试本体 | 把规则与要素组合成检查点与案例 | 可理解、可操作的案例 |
| 案例执行 | 应用本体 | Agent 探索、Agent 使用 | 弥补需求和开发落地的部分 gap |

每道工序写清：输入 · 方法 · 产出 · 检验。业务含义在生成案例前澄清，执行按案例与应用知识开展。

### 完整语义与形式化需结合实际：三版演进

| 版本 | 做法 | 遇到的问题 |
|------|------|-----------|
| 第一版 | 完整语义归纳：参考 FIBO，十余个阶段逐层归纳 | 一个定义讨论半天、一个边界划分半天；耗时久、用途不明 |
| 第二版 | 规则全形式化：规则全部结构化，Test IR 也很重 | 维护成本上去了，模型反而没法用自然语言推理 |
| 现在 | "四句话"：概念够用、关系面向影响、规则面向测试、事实保留证据 | 本体刻画业务本质与规律，面向任务按需提取，随业务演进持续更新 |

怎么判断要不要结构化？讲者给了两个对照：

- "本机构处理超时阈值 4 秒"——需要确定性校验 → **结构化**。
- "超时后最终结果以本机构处理为准"——口径与例外需要人来解释 → **自然语言 + 来源 + 版本**。

### Test IR：把需求"编译"成案例

讲者用编译器类比测试：

```
源代码 → 词法/语法/语义 → IR → 优化 → 目标代码 → 运行
需求   → 需求理解/业务本体 → Test IR → 测试分析 → 可执行案例 → 执行（人/Agent）
```

传统上，这场"编译"全靠测试人员的脑子：需求读进去，案例写出来，再亲手执行。Test IR 把这个过程显式化，有三个作用：

1. **前后端解耦**：需求理解一次，分析、生成、执行都读同一份 IR；换执行方式不必重做分析。
2. **多个 Agent 的通用语言**：事实、规则、条件、检查点、问题都在 IR 里，各阶段读写同一份记录，不传长文报告。
3. **隔离一次性信息**：单次需求的事实先留在 IR，确认后才回流本体，不污染长期知识。

### 怎么用：案例挂到本体上，变更沿关系传播

使用闭环六步：

1. **案例绑定本体**：已有案例按测试意图挂到本体元素。
2. **解析变更需求**：拆成事实与覆盖责任。
3. **定位受影响元素**：哪些对象、规则、行为变了。
4. **沿关系找案例**：精确引用 → 关系一跳 → 语义复核。
5. **处置案例**：修改 / 补充 / 原样 / 范围外。
6. **变更回流本体**：补充新规则，发布新版本。

> 零命中 ≠ 无影响：召回不到的也要标出来，交给人看。

## 关键工程做法

### 案例一：一份增量需求的影响分析（示意样例）

需求：支付类报文超时阈值 4 秒 → 3 秒；超时提示改为"处理中"；超时后主动查询；迟到响应不重复记账；非支付类不变。

从需求识别覆盖目标，拆成三类：

| 类别 | 内容 |
|------|------|
| 已有变化 | 阈值变化、提示变化 |
| 新增要求 | 主动查询、迟到响应不重复记账 |
| 保持不变 | 非支付类规则 |

已有 10 条案例的处置（示意）：

| 处置 | 数量 |
|------|------|
| 修改后重跑 | 3 |
| 补充后重跑 | 2 |
| 原样重跑 | 4 |
| 范围外 | 1 |

仍需补齐的 2 项测试目标：

| # | 测试目标 | 依据 | 现状 | 下一步 |
|---|---------|------|------|--------|
| 1 | 主动查询失效时如何处理 | 由主动查询要求推导的异常方向 | 预期行为待澄清 | 确认规则后补充检查点 |
| 2 | 迟到响应不重复记账 | 需求明确要求 | 现有案例缺少对应断言 | 补充不重复记账检查 |

讲者强调统计口径：**案例处置按案例计数；覆盖缺口按测试目标计数，两者分别核对。**

追踪链示例（超时专项-07）：

```
需求片段：超时阈值 4 秒 → 3 秒
  → IR 责任 R1：已有变化
  → 业务本体规则：支付类报文处理超时阈值
  → 案例断言：4 秒未返回 → APP 显示超时
  → 处置：修改后重跑
```

同批案例中，"查询-02"字面同为"超时 4s"，但属于非支付类不变，因此原样重跑；"设置-09"无结构影响路径，判为范围外。这两个例子说明本体做的是语义匹配，不是字符串匹配。

### 案例二：让测试工艺贯穿需求到案例（理想状态·目标流程示意）

五步流程，每一步都有明确产物：

| 步骤 | 动作 | 产物 |
|------|------|------|
| 1. 需求进入 | 导入需求、规范与业务背景 | 可定位的原文 |
| 2. 识别问题与测试意图 | 发现歧义、缺失和需验证的目标 | 问题清单、测试意图 |
| 3. 分解规则与要素 | 保留条件、分支、约束和依据 | 规则、业务要素 |
| 4. 组合检查点 | 运用规则组合条件，补充独立检查 | 覆盖目标、检查点 |
| 5. 自动生成案例 | 展开准备、操作与逐步预期 | 可理解、可操作的案例 |

业务本体负责对象、关系、业务规则与来源；测试本体负责设计方法、条件组合与覆盖关系；第 2 步到第 3 步之间传递"业务事实与待澄清项"。

案例节选：转账授权未通过拒绝。

- 规则原文：转账必须授权通过才能提交，否则交易报错。
- 测试意图：验证授权对交易提交的控制。
- 条件：通行方式 = 转账。
- 要素：授权结果（通过/未通过）、单笔金额（超限/不超限）。
- 组合：转账 × 授权通过 → 满足授权条件；转账 × 授权未通过 → 交易报错。
- 案例准备：人民币 5000 元转账，付款账户正常、余额充足，支付条件可验证通过。
- 关键步骤：进入跨行存款并选择转账 → 刷卡或存折读取付款账号 → 录入收款账号、人民币及 5000 元 → 提交交易 → 授权环节选择不通过。
- 预期：交易报错，回显授权未通过的失败原因。

需求未完备时的影响追踪：问题"日累计按客户还是按账户计算？"→ 累计金额要素 → 限额检查点 → 关联案例的数据准备；澄清后沿关联定位并更新。讲者的原则是：**明确的规则形成设计；未明确的问题保留影响关系。**

**本篇没有生产环境的量化效果数据。** 这是本页必须明确的事实边界：

- 第 18、19 页的两个案例页均标注"示意样例"；
- 第 21、22 页的案例二标注"理想状态·目标流程示意"；
- 全文没有给出准确率、召回率、用例生成节省工时、缺陷检出率、覆盖率提升等指标；
- 唯一可核对的数字是示意性的案例处置计数：10 条已有案例 → 3 条修改后重跑、2 条补充后重跑、4 条原样重跑、1 条范围外；另需补齐 2 项测试目标。

讲者给出的评价维度（而非实测值）是：

- 结果正确性
- 覆盖完整性
- 依据可追溯性
- 人工修订成本

并强调"能运行、结果正确、能够复用，分别评估"。

## 经验与边界

- **本体是手段，不是目的**。讲者的原话是："本体是当前弥补 LLM 领域业务知识不足的一种解法，未必是最优解。"本体知识、领域模型、领域超级智能体能否逐步融合，仍待探索。
- **先有场景，再建模**。围绕任务提取对象、关系与业务规律；不要为填满 S0–S4 的层级而补造规则。
- **AI 提候选，专家校准**。阈值、口径、适用范围与例外需要业务依据；"不能全靠人建，也不能完全指望 AI 自动化"。
- **表达方式由任务决定**。自然语言 + 结构化规则 + 关系并存；需要确定性结论时使用规则校验或专用推理。第一版追求完整语义、第二版追求规则全形式化，都因维护成本或可用性受挫，才收敛到"四句话"。
- **分层的必要性来自变更节奏**。业务知识随需求版本变、测试方法相对稳定、执行知识随应用版本变；混在一起会导致需求一改、方法和执行一起受牵连，且无法分段交付。
- **Test IR 的核心价值是隔离一次性事实**。单次需求的事实先留在 IR，确认后才回流本体；否则一次性信息会污染长期知识。
- **零命中不等于无影响**。关系召回有边界，必须把召回不到的案例标出来交给人复核；这是对"本体可以自动影响分析"的重要限制。
- **落地的现实约束**：测试项目按周排期、专家难以随时到位、业务口径需要协同确认；大而全本体的建设周期以年计，与测试现场节奏不匹配。
- **是否上本体有判据**：Q1 同一个问题每来一个新人是否都要问一遍（知识会被反复用 → 值得沉淀）；Q2 需求一改是否没人说得清该重测哪些（有变更分析的刚需 → 值得建关系）；Q3 老师傅一休假是否没人会造这个异常（经验只在人脑里 → 值得写成工艺）。一次性、规则简单、复用价值低时，先完善文档与流程。
- **落地需要的基础**：可定位的业务材料、可遵循的工艺规则、可确认口径的业务与测试人员、用于实测的代表样例；缺一项，本体就容易变成"定义很漂亮但没人用"的文档工程。
- **证据边界**：本页所有"效果"均为示意或目标流程，不能当作生产收益；讲者未披露本体规模、构建耗时、参与专家人数、案例库规模与线上使用量。
