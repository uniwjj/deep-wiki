# LiveX Wiki

> 来源：公众号「大淘宝技术」，作者翎捷（淘天集团 · 直播互动团队），2026-11-20。一手实践自述（未开源）。核心主张：Coding Agent 落地的瓶颈不在模型编程能力，而在**业务知识能否被准确供给**；知识库要做的是把跨端跨仓的业务理解，变成「按场景组织、可回源核验、随代码演进」的机器上下文。

## 一句话拆解

| 组件 | 承担什么 | 原文措辞 |
|------|---------|---------|
| **LLM Wiki** | 编纂业务理解 | 「用 LLM Wiki 编纂业务理解」——让模型把跨来源的理解编纂成持续维护的知识 |
| **OKF 思想** | 表达知识身份与关系 | 「用 Markdown 保存业务解释，用 YAML frontmatter 和引用声明身份、来源与依赖」 |
| **Git** | 管理版本与受控发布 | 「用 Git 管理版本、修订与受控发布」 |
| **域—场景—知识** | 决定知识怎么切 | 「按『域—场景—知识』组织跨端、跨仓关系」 |

## 背景：RAG 之后还差什么

### 现象与痛点

给通用 Coding Agent 一个函数签名、一段局部逻辑或一组测试，它能较快进入实现；但复杂业务需求跨仓跨端、带业务黑话、关联复杂配置与实验设计——原文的判断是：给通用 Coding Agent 原始 PRD 而不补任何背景，产出的方案和代码往往处于不可用的状态。团队侧的表现是：AI 代码采纳率低、对话轮次与返工频次高、交付周期提效不明显。

两个痛点：

- **上下文完备度**：隐性规则、历史兼容要求、跨仓跨端依赖散在代码、配置和人的经验里，代码满足了表面需求却漏掉实际业务约束。
- **上下文准确性**：Agent 缺少判断「哪些信息有歧义、哪些结论需查证、何时查代码、何时问人」的依据——猜着写增加返工，频繁确认又抵消提效。

### 早期 RAG 方案的实测天花板

机制：知识检索 Skill 识别任务缺什么 → 检索架构规范、平台接入方式、类/方法/字段等代码知识 → Agent 判断每条结果的相关性与采纳 → 未命中则读本地代码或补资料 → 检索与使用结果进观测记录。

团队统计 **2026 年 7–9 月**（知识检索与使用记录）：

| 指标 | 变化 |
|------|------|
| 知识相关率 | 25.45% → 42.20% |
| 知识库支撑占比（已上报任务中） | 44.23% → 55.87% |
| 知识采纳率 | 在 20.54%～28.05% 之间波动 |

结论：召回之后的**筛选、关联与核验**才是关键环节——「RAG 可以扩大召回范围，但返回『语义相似』的材料，不等于已经取得『当前业务真正需要』的上下文」。

四条局限（原文归纳）：

1. **知识是点状的，缺少整体视角**——返回规范、类、方法或局部实现，页面/组件/接口/依赖之间的整体关系要额外补齐。
2. **业务视角需要临时拼装**——知道若干条目，仍要判断它们属于哪个页面、哪项业务行为、哪条实现链路。
3. **影响分析依赖进一步调查**——检索能找候选，但核心链路、共享能力、正反向依赖需单独建模核验。
4. **知识新鲜度需要额外约束**——检索结果若不关联来源版本与核验依据，旧知识与现状冲突时 Agent 只能自己猜。

原文特别声明：「这些问题来自当时的知识组织与消费方式，并不意味着所有 RAG 方案都有相同限制。」

### 四条设计约束（第一性原理）

知识库的读者从人扩展到 Agent 后，要回答的是「机器可解析的身份与边界、确定的路由入口和可回溯的证据」：

| 约束 | 原文表述 |
|------|---------|
| 按需供给，而非全量堆给 | 「装得下」不等于「理解得好」；无关信息、相似干扰、过期规则越多，筛选负担越重 |
| 按业务结构组织，而非按条目堆积 | 业务事实有归属与关系，脱离结构的点状知识等于让 Agent 在任务内临时重建关系 |
| 给可核验的路径，而非只给可引用的结论 | 知识库存结构与定位信息，当前事实回原始来源确认 |
| 有生命周期，随变更演进 | 与代码变更脱钩的知识会持续误导；知识要像代码一样版本化 |

## 选型：四个维度

| 维度 | 技术选型 | 核心职责 |
|------|---------|---------|
| 知识建模 | 场景模型 + OKF 式轻量表达 | 明确知识身份、边界、归属与依赖 |
| 知识生产 | LLM Wiki 编纂 + 人工定界与回源核验 | 把跨来源调查沉淀为有依据的场景知识 |
| 知识消费 | 层次索引 + Agentic Search | 按需定位和展开知识，核验当前事实 |
| 知识迭代 | LLM 增量更新与全量审查 + Git 治理 | 跟踪变化、检查遗漏并受控发布 |

选型时被放弃的路线（原文对照表）：

- **建模**：LLM Wiki 编纂解决「跨来源理解如何沉淀、关联、持续修订」，代价是确定编纂粒度并保留核验路径；OKF 式表达解决「可读、可解析、可迁移」，代价是项目仍需自定义身份/字段/引用的一致性约束；Ontology 解决「对象、属性、关系、动作的语义一致」，代价是建模范围与维护成本要让位于「知识导航」这个当前目标——**当前阶段不把全部业务对象与操作纳入统一运行模型**。
- **消费**：RAG 向量检索适合找材料，场景边界/依赖/版本仍需组织；GraphRAG、LightRAG 强化关系检索，但抽取的关系是否对应真实实现仍需核验；PageIndex 保留文档层次，跨文档跨仓的业务关系仍需另行表达；Agentic Search 能回代码与文档确认细节，但每次从零调查重复劳动多。最终取**层次索引 + Agentic Search 的组合**。
- **维护**：人工维护能解释业务意图但依赖人工触发；重建索引不等于跨来源业务关系已核实；LLM 编纂 + 回源审查需要来源权限与质量检查；Git 保存差异与版本，但不能判断业务事实是否正确。两者组合才成立。

## 知识建模：域—场景—共享知识

| 知识对象 | 负责表达 | 工程约束 |
|---------|---------|---------|
| **业务域** | 一组能力的职责、边界、维护人和场景入口 | 场景有唯一归属，先确认域边界再进入场景 |
| **业务场景** | 页面/系统职责的全景、核心接口链及查证路径 | 一个场景保存一份权威地图，源码变化按场景汇总 |
| **共享知识** | 平台接入、规范、共用概念和约束 | 独立维护，由场景通过已核实的直接依赖引用 |

- **场景粒度**是核心取舍：场景过大则每次变化都扩大核验范围，过小则退化成需要临时拼装的碎片。划分标准是「可独立理解、可明确归责、可单独核验」，粒度控制到「足以支持业务判断」。
- **场景内的查证路径**：真实接口 → 服务编排 → 核心模块 → 底部依赖。
- **两层配合**：页面聚合负责确定业务范围，真实接口链负责落到技术事实——「两者配合，才能既保持完整语义，又保留准确的实现入口」。
- **共享知识**独立维护、被场景引用，避免被复制后各自过期。

### 双视图：树给入口，图给关系

「渐进披露」控制何时展开哪些范围；选中场景后仍须全文理解其边界，**不能拿摘要替代上下文**。知识图谱的两种布局：有机布局看整体聚集，依赖层次布局把域/场景/知识纵向展开、按域分列——虚线表达领域归属，实线表达直接依赖，沿连线可检查「一个共享能力被哪些场景引用、依赖是否跨越领域边界」。

配图（脱敏示例）右上角统计：**8 领域 / 47 场景 / 37 知识 / 244 依赖**。原文同时提醒：归属回答「由谁维护」，依赖回答「变化后还要调查哪里」；图中的层次是知识组织关系，实际调用与变更影响仍需沿接口链核验。

概览配图列出的六块基石：Git（版本·差异·审阅·追溯）、LLM Wiki（编纂证据，复用业务理解）、OKF 思想（稳定身份·元数据·关系）、PageIndex 思想（树形导航·按需展开）、Domain（划分业务域与责任边界）、Scene Index（划分业务场景与接口链）。

## 知识生命周期

三类角色分工：**LLM 负责理解与核验，程序负责结构与范围，Git 负责版本与发布记录**。冷启、自动更新、全量审查共用同一套生产契约与发布门禁；消费只读已发布知识，发现失配要报告，**取得维护授权后才产生修订**。

规则落在仓库级文件里：`AGENTS.md` 定义入口、读取顺序与行为边界，`MAINTENANCE.md` 定义生产/维护/发布流程（原文配图显示仓库还有 `CONTEXT.md`、`domains/`、`knowledge-graph/`、`tools/`、`tests/` 等），能力统一封装为 Skill 供 Agent 调用。

`MAINTENANCE.md` 的自述定位（截图原文）：「场景知识地图不是业务事实的副本。它是在指定 revision 上验证过的知识图谱导航」——Agent 读完一份场景 `index.md`，应能从业务背景选中真实核心接口，再沿该接口的四层……（截图在此处截断）。

### 组装：从场景边界到可审阅的 Git 变更

| 阶段 | 步骤 |
|------|------|
| 人工冷启 | 明确业务边界（域 / 场景 / 维护人）→ 准备权威来源（需求、方案、多端源码）→ 固定核验范围（源码版本 / 环境 / 单元） |
| Agent 核验 | 术语桥接与入口枚举（业务词 → 代码词 → 真实入口）→ 逐链正反向核验（调用 / 分支 / 配置 / 数据）→ 编纂已核实知识（身份 / 链路 / 依赖 / 来源）→ Git 候选分支（差异与核验记录） |
| 受控发布 | 统一发布门禁（结构 / 范围 / 待确认项 / 回归检查与平台约束）→ 满足条件自动审批合入，其余交 Maintainer 评审 → 合入 main |

两个约束原句：**来源只读；证据不足继续补查，业务歧义交由维护人确认**；**事实正确性来自逐链回源核验，结构检查与 CI 不替代事实核验**。

冷启的四个关键动作：

1. **固定来源与版本**：每个源码仓绑定本轮提交，明确配置的平台、环境与单元，避免调查中混用版本。
2. **两轮搜索跨术语差异**：先用业务行为、页面文案、需求字段找候选；再用已确认的接口、类、字段、事件与配置标识反查，补齐第一轮没找到的端与模块。
3. **从入口向下追，从消费者反向查**：枚举 API、消息、调度与扩展点沿真实调用展开，再检查调用方、注册点与策略实现族，确认主链之外有无补偿或特殊分支。
4. **LLM 核实后编纂**：已核实的关系写成接口链，同步配置、实验与数据库依赖；未闭合的证据单独列出。

原文的异步任务例子：找到提交接口还不够——若任务状态由消息处理推进，要解释另一条入口；若处理采用策略分发，还要核对选择条件与适用实现。「找到一个实现只能证明它存在，正反向调查才帮助判断场景是否完整。」

### 消费：五步 + 终止条件

| 步骤 | 读取与处理 | 解决的问题 |
|------|-----------|-----------|
| 1. 发现域 | 结构检查通过后，读取每域一行的名称、别名与摘要 | 用少量上下文选定业务范围 |
| 2. 选择场景 | 展开候选域清单，完整读取域边界与命中场景 | 避免关键词片段脱离业务语义 |
| 3. 按需求选链 | 从接口清单定位相关核心链，读取节点、边与控制项 | 把业务问题落到实现入口 |
| 4. 展开必要依赖 | 查询已声明的直接依赖，按需读取目标域与场景 | 补齐共享知识，避免全图加载 |
| 5. 回源核验 | 逐项建立「导航断言—当前事实—核验结论」对应关系 | 判断知识对当前任务是否成立 |

消费图补齐的细节：域级发现只看 frontmatter 的轻量字段，选中后才展开完整上下文；核验阶段读取「当前 checkout + 目标环境与平台响应」；依赖展开要记录已访问对象以避免重复。**终止条件**：证据齐备 → 停止扩展；重复或未命中 → 停止消费并报告缺口；证据不足或来源不可达 → 停止确定性结论、报告问题（「查不到」不能推断成「没有影响」）。底线是「**消费始终只读 Wiki**，待确认项不作为事实或依赖，当前事实以原始来源为准」。

### 迭代：自更新 + 自审查 + Git 治理

- **知识自更新（每日 · 增量）**：从场景登记的仓库与核验提交出发 → 读 diff、定位直接命中链 → 按共享定位符与直接依赖有限扩展 → 按场景汇总跨仓变化，形成一次候选修订。只有知识表达确实需要变化时才产生提交。差异复用条件是「同仓库 + 同起始提交」，调查深度由业务语义决定。
- **知识自审查（每周 · 全量）**：固定全部场景与核验版本 → 重查入口、注册点、调用方与实现族 → 核验核心链、配置、实验与数据依赖 → 检查已有事实、补查地图遗漏。**近期没有代码提交的场景也要检查**（运行控制仍可能变化），每个场景都须给出明确的核验结果。
- **Git 治理**：候选分支 + 独立工作区 + CR，提交只含授权范围内的修订；五道门禁依次为语义证据 → 结构与范围 → 待确认项 → 工具回归 → 平台合入（统一发布门禁）。常规场景候选满足 **confidence ≥ 0.9、无待确认项、全部门禁通过** 即可受控自动发布；共享知识、场景删除等特殊候选交维护人评审。合入后更新知识版本，做到可审阅、可追溯、可回退。核验评分取四项最低值：架构与跨端边界、核心链、配置、实验；**自动改写仅限 Scene Index，共享知识由负责人发起维护**。

生命周期全景（配图）：生产与发布（事实核验与编纂 → 候选知识 CR → 统一质量门禁 → 发布分流 → 已发布知识）→ Agent 消费（需求路由 → 按需展开 → 执行期事实核验 → 任务结论与实施）→ 持续维护（每日增量更新 / 定时全量 Review / Owner 授权修订）。消费侧失配（事实冲突、锚点失效、证据不可达）上报后取得维护授权才产生修订；核验一致且无变化则记为 `no_change`。原始证据被归为五类：需求文档、多端源码/IDL/测试、配置与实验、数据库元数据、接口平台。

## 效果验证

两类测评共用一套基础设施：**数据集**（说明任务与预期结果）、**被测系统**（执行任务）、**测评器**（按规则评分），三者分别管理版本，便于知识或消费流程调整后复跑。

### 端到端生码测评

- 样本：历史真实需求、技术方案与实际变更，构造输入与参考答案（GT），GT 描述应满足的业务行为、关键约束与验收要点。
- 控制变量：同批次固定 Agent 运行时与工作流，隔离任务上下文与环境，唯一变量是知识供给方式（无知识库 / RAG 向量知识库 / LiveX Wiki）。
- 评分四维：功能正确性、实现契合度、兼容安全性、工程质量。
- 防泄漏：检查输入是否泄露目标实现，避免把答案提示误判为知识收益。

|------|-----------------|--------------|-----------------|--------------|
| 综合得分 | +54.5% | +44.3% | +23.8% | +15.9% |
| 功能正确性 | +52.9% | +57.2% | +18.4% | +10.9% |

| 兼容安全性 | +57.1% | +34.5% | +25.2% | +4.4% |
| 工程质量 | +16.3% | +7.0% | +31.9% | +33.5% |

摘要里的 39.15% 与 30.1% 即两批综合得分的均值（54.5 与 23.8 平均 39.15；44.3 与 15.9 平均 30.1）。原文强调只做同批次对照、不跨批次或跨时间论述差异，且不展示原始得分、需求数量与具体业务样本。

### 需求路由测评

被测 Agent 只执行路由定位，逐条比对四类目标集合——**业务域、场景、仓库、核心链路**，算精确率、召回率与 F1。为分离「知识覆盖缺口」与「定位能力」，把需求分成两组：GT 全部已覆盖组、GT 含未覆盖组。配图给出各组各维度的归一化 F1（全量任务同维度 F1 = 1）：

| 维度 | GT 全部已覆盖组 | GT 含未覆盖组 |
|------|----------------|--------------|
| 业务域 | 1.28 | 0.34 |
| 场景 | 1.36 | 0.16 |
| 仓库 | 1.05 | 0.88 |
| 链路 | 1.38 | 0.10 |

结论：在已覆盖场景上，定位准确率与召回率提升显著——链路 F1 为 **1.38 : 0.10**，验证了场景覆盖建设的投入收益；未覆盖组的低分对应知识覆盖缺口——分组的意义就是把「覆盖缺口」与「已有知识的定位问题」分开观察。摘要另给一个口径：**线上仓库定位准确率从 60% 升至 90%**。

### 改进矩阵

| 问题 | 改进策略 |
|------|---------|
| 知识广度：目标场景未覆盖，或业务用语无法命中 | 补充场景覆盖度，校准场景索引文件 frontmatter 相关字段与别名 |
| 知识准确度：定位符失效，或地图与代码、平台不一致 | 完善知识的时效与自动维护、事实层证据关联 |
| 知识新鲜度：知识获取充分但与事实源不一致 | 完善自更新能力，先验事实源追溯 + 后验评测校准 |
| Agent 行为：场景选对了却仍用错或忽略知识 | 建立在线与离线知识消费观测体系，针对性调优 |
| 评测噪音：同批次评分不稳定，或 GT 有歧义 | 标注、评估规则与人工复核 GT 与评测结果，引入 LLM 辅助分析 |

原文的判断：**最终分数帮助判断是否值得继续投入，执行轨迹决定接下来改哪里**——沿需求理解、知识路由、链路核验、方案实现逐段检查，优先找最早的偏差。后续还计划用「关闭依赖展开、调整回源核验」等受控对照，分离质量与成本的来源。

## 适用边界与三条可迁移方法

适合的形态：**跨仓、跨端、持续变化、会被反复开发**的业务。前期调查沉淀为场景后，后续任务复用路径、维护有明确范围。

1. **以需求如何变化，决定知识如何划分**——先确定哪些入口、规则和依赖共同支撑一次业务行为，再选场景边界；按仓库或技术主题自动分组补不上这一层。
2. **复用已经理解的结构，重新确认当前事实**——业务地图缩小调查范围，源码与运行平台决定本次实现依据；知识版本与事实版本分别管理。
3. **让生产、消费、维护和评测指向同一对象**——同一个场景承担路由、核验、责任与修订单位，评测失分能落回具体场景与接口链。

局限也落在同一设计上：场景边界需要人参与，覆盖补齐需要投入；依赖图可能遗漏未建模关系；模型核验依赖来源可达；Git 与 CI 提供可追溯性与确定性检查，**并不能保证所有业务判断正确**，必须由人为知识准确性负责兜底。
