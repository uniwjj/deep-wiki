# 软件是被固化的知识

> 出自天猫技术团队书牧《重构协同：关于AI Native团队的思考》的"顺带厘清"一节——回答在 AI Native 形态里，我们熟悉的"软件"到底还算什么。原文说明：这是往更抽象一层看的理解性框架。

## 知识底座的 TBox / ABox 拆解

一个完整的业务闭环，知识底座至少包含两类东西：

- **业务规则 + 业务流程**：这个业务"怎么运转"的定义。借用本体论的区分，这是类型层面的定义（**TBox**）——规则是"是什么、要遵守什么"的**陈述性知识**，流程是"按什么次序做"的**程序性知识**，两者都是知识。
- **数据**：业务运转起来之后产生的事实（**ABox**）——一笔笔订单、一个个商家和用户。

一个完整的知识底座，应同时包含 TBox 和 ABox 两部分。

## 软件产品在这个模型里的位置

**软件不是一个必需品**——就像现实世界业务本身可以脱离软件存在一样，抽象地看，业务完全可以由 Agent 直接在知识底座上运转起来。软件之所以需要，是因为 Agent 的动态运转在某些地方还不够用：要**交互体验、确定性、性能、成本、安全、合规审计**等。于是把其中一部分业务规则和业务流程"固化"下来，做成**产品规则和产品流程**，落到软件研发流程上（也包括 AI Coding）。

推论链：

1. **软件是被固化的知识**——源头始终是知识底座。
2. "把知识固化成软件"这件事本身又是一条业务流程（研发流程），同样可以由 Agent（Code Agent）在知识底座上运转完成——**AI Coding，本质就是这个固化动作**。
3. 生产侧被重构后不会被清空：那些为确定性、性能、成本、合规必须保留的"确定性逻辑"，最终以产品规则和产品流程的形态固化在软件这一层。面向"人来串联"的 GUI 也许不再重要（见 [[ai-native-team-refactor]]），但确定性逻辑的固化层仍在。

## 沉淀 / 交付形态的迁移

"沉淀"这个动作本身也在变：

- 过去一个业务把经验沉淀下来，交付的是一套**软件**；往后，交付的更多会是**知识**（也包括 Skill）。
- 过去做集成是交付一个端到端的软件系统；往后更多是给 Agent 交付**一件件工具**。
