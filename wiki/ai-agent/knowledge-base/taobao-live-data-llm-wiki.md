# 直播数据 LLM Wiki 实践（大淘宝技术）

> 来源：公众号「大淘宝技术」，楚翎、程知微，2026-11-16。一手实践自述（未开源）。核心主张：把 LLM Wiki 当**编译器**——源材料是 DDL、任务代码、文档、接口配置，产物是结构化页面 + 显式关系图，供 Agent 做选表、取数、生码和影响分析。文中 `imgs/imgNN.png` 均相对来源目录 `sources/2026/11/16/构建 AI 时代的知识底座：直播数据 LLM Wiki 实践/`。

## 起点：知识散落，RAG 治不了

原文的立论：任何 AI 系统都由**模型、知识、架构**三部分组成——模型由供应商提供只能被动接受；架构常因模型能力升级而失效重做；只有领域知识必须从内部积累，不可替代且随业务持续变化，因此最值得长期投入。

数据团队的知识散落在代码与注释、配置、钉钉文档、沟通记录里，没有统一载体，带来两层后果：

| 后果 | 原文描述 |
|------|---------|
| 知识质量退化 | 传播靠口口相传，人走知识就断；同一指标在不同文档里定义矛盾，没人能仲裁；文档无人持续维护，三个月后与线上对不上 |
| 工程熵增 | 缺乏全局视图，无法判断一张表是否已存在、一条链路是否已有人建过，重复建设累积数据负债 |

于是"口径答疑、问题排查、代码生成"这些本可被 AI 极大提效的场景，都卡在"知识喂不进去"。

**为什么 RAG 不行**：RAG 每次查询都到原始文档碎片里现找现拼（chunk 召回、上下文拼接、模型生成），但不改变原始材料本身的状态——散落的还是散落的，矛盾的还是矛盾的，过期的还是过期的，只是多了一层向量索引。原文的形容是"只是把'人找不到'变成了'AI 找到了但答不准'"。所以要在检索之前加一道**编译过程**。

配图把两类知识并排对照（`imgs/img00.png`）：左侧"没编译"的散落载体 → 两层后果 → RAG 只能检索 → 问题依旧；右侧"有编译"经 采集 → 清洗去重/规范 → 对齐统一口径 → 建模结构化 → 编译发布持续维护，得到统一口径、结构化、可追溯、时效性、全局视图五项属性，落到口径答疑、问题排查、代码生成、分析洞察四类应用。

## 案例：从选表到模型迭代

### 指标与维度召回

- "主播 xxx 分用哪张表"：先用 `index.md` 定位到 `basic/审核打标` 域，再全域搜索召回候选表，再逐张读详情页判断覆盖度与相关性；最终推荐 xxx 分维表，并区分 DWD 增量明细表（追溯变更历史）与主播画像宽表（同时需要 xxx 分和其他属性），主动排除名称相似但实为"讲解 xxx 分"的干扰项。
- "xxx 交易指标怎么取"：域推断 → 多路搜索 → 详情验证三步，推荐 DIM 层标签表（直接有 xxx 字段）与 DWD 层明细表（xxx 标记字段可自行聚合），并附判定逻辑、SQL 示例和血缘链路。

检索结果截图（`imgs/img01.png`、`imgs/img02.png`）给出输出形态：**最推荐表**（分层 / 域 / 覆盖度·通用性·相关性 / 推荐理由 / 查询示例）+ **其他结果表**（表名、分层、域、覆盖度、通用性、相关性、职责）+ **血缘链路** + 补充说明（例如说明为何排除同名干扰项）。截图里通用性以 `generality` 计（示例值 12、2、30）。

### SQL 代码生成

"不同主播等级的开播场次数怎么算"：系统跨维表域与供给开播域，定位到主播基础信息宽表（主播等级）+ 主播标签预聚合表（预聚合多窗口场次数）或主播开播日汇总表（按天累加自定义范围），输出 JOIN 关联的 SQL 骨架，同时标注废弃字段、xx 开播口径和多套分级体系的差异。

### 数据模型迭代

原文把这件事定为"高频且高风险"：变更沿血缘传导可影响数十张下游表；字段参与 WHERE 条件、CASE WHEN 分档，改错会导致业务判定失效；新旧口径差异需双跑验证。传统链路全人工：需求理解 → 查表结构 → 查血缘 → 判影响 → 估风险 → 写 SQL → 验数据，对应 grep 搜索、手动递归、看代码、凭经验、逐表改写、手写 SQL。

基于 Wiki 的编排把需求拆成 6 步，按序调用子 Skill，关键节点由用户确认：

| 步骤 | 做什么 | 输入 → 输出 |
|------|--------|-------------|
| 需求拆解 | 理解需求，识别需求类型 | 需求描述 → 需求类型 + 指标口径 |
| 知识库召回 | 从 Wiki 查目标表，拉 DDL 和口径定义 | 表名 → 表结构 + 口径说明 |
| 血缘查询 | 用 `graph.json` 查全链路下游，强制完整性校验 | 目标表 → 下游表完整列表 |
| 风险评级 | 看下游 SQL，判断业务影响（高/中/低）+ 风险类型 | 下游表 → 二维风险矩阵 |
| SQL 生成 | 批量生成 DDL + ETL + 验证 SQL + 回滚 SQL | 影响分析 → 全套 SQL 文件 |
| 报告输出 | 整合分析结果，生成影响分析报告 | 全流程结果 → 可交付报告 |

两个场景：

- **数据源切换**（`data_source_switch`）：先确认切换含义（直接引用 vs 重新计算）；查全链路下游血缘发现 **12 张间接下游表**；看下游 SQL 发现阈值判定 → 业务影响=高；生成目标表改造 SQL + 12 张下游表适配 SQL + 口径对比 SQL。关键发现：间接下游中有 **3 张参与准入判定**，切换后阈值需调整。
- **新增字段**（`addition`）：确认指标一一映射；列出候选下游表并由用户确认传播范围；逐表判断血缘 JOIN 状态后生成适配 SQL。路径 B 强制用户确认，避免遗漏或过度传播。

实测（原文表）：

| 事项 | 传统人工 | AI 编排 | 提效 |
|------|---------|---------|------|
| 血缘查询时间 | 30min（手动递归） | 2min（--impact） | 15× |
| 下游表遗漏率 | 20%（间接下游易遗漏） | 0%（强制完整性校验） | 100% |
| SQL 生成时间 | 0.5天（逐表改写） | 10min（批量生成） | 72× |
| 风险判定一致性 | 低（凭经验） | 高（二维矩阵标准化） | 质变 |

原文结论：模型迭代影响分析从半天缩短到小时级，人工只做"三道确认"，工程师从"查代码、写 SQL"转向"决策确认"。

## 知识资产的四个性质

原文强调 LLM Wiki 不是"用 LLM 写出来的文档"，而是结构化、有约束、可验证的知识资产，与传统文档的区别在四层：

| 性质 | 层级 | 机制 |
|------|------|------|
| 结构可解析 | 单页内部 | frontmatter（脚本可解析的 YAML）+ 正文双层；frontmatter 承载关系字段（type、domain、upstream、computed_by 等），脚本直接读关系，不必 LLM 反复解析正文 |
| 层级可下钻 | 跨页层级 | 域按业务主题嵌套成树；Agent 检索时从根域渐进披露，避免一次灌入全部上下文 |
| 关系可遍历 | 跨页关系 | 血缘、归属、消费、引用以边显式记录成有向图；脚本可遍历、可算影响范围、可做多跳召回 |
| 正确性可度量 | 校验体系 | 结构层机械规则、语义层 LLM 评审（描述准确性、口径一致性、域归属合理性）、人工层关键节点确认兜底 |

原文的口号：**让 LLM 来建，不是让人来建**——人工维护的核心问题是成本高、腐化快、难持续；LLM 当编译器，人只在关键节点确认。

## 编译六步与编译器的对应

原文把构建过程抽象为六步，逐一对编译器阶段（配图 `imgs/img05.png` 有细项）：

| 步 | Wiki 构建 | 编译器对应 | 图上细项（编译器侧） |
|----|-----------|-----------|---------------------|
| 1 提取 | 从源材料（DDL/代码/文档/接口）抽取片段 | 词法分析 | 扫描字符流、生成 Token、过滤注释/空白 |
| 2 生成 | 生成结构化页面 | 语法分析 + 代码生成 | 构建 AST、语法检查、生成中间代码 IR |
| 3 归类 | 确定页面归属域 | 作用域解析 | 符号表构建、作用域确定、引用绑定 |
| 4 聚合 | 合并同类项，形成域/指标/维度/概念等标准页面 | IR 构建 | 合并单元、构建统一 IR、优化表示 |
| 5 链接 | 解析引用、构建血缘图 | 链接 | 符号解析、依赖链接、生成可执行体 |
| 6 验证 | 检查一致性与正确性 | 静态分析 | 类型检查、规则校验、死代码/未定义检查 |

## Wiki 与 RAG：编译时 vs 运行时

原文明确：有了 Wiki 仍需 RAG，两者定位不同——Wiki 是**编译时产物**，RAG 是**运行时手段**。

- Wiki 在构建阶段把散落材料固化为完整语义单元：血缘显式记录、口径以代码为准做仲裁、层级结构支持渐进披露、每页自带 frontmatter 元数据。
- RAG 在查询时刻基于这些页面做精准召回：frontmatter 用于硬过滤（按层级、域、血缘），正文用于语义匹配；Wiki 未覆盖的长尾知识仍可回退到原始材料检索。

原文的一句话：Wiki 提供高质量语料，RAG 提供精准召回，组合起来才是完整的检索栈。

## 知识来源：广度与深度

一个业务问题往往跨越多种知识载体——表定义结构、接口定义契约、看板定义消费场景、文档承载业务背景。缺一类就有盲区：只有 DDL 没有任务代码，AI 知道字段叫什么但不知道怎么算；有表没有看板，AI 知道数据存在哪但不知道谁在用。

| 维度 | 内容 |
|------|------|
| 编译时知识（广度） | 构建阶段固化的 5 类载体：表（DDL）、接口（Config + Version）、文档（钉钉文档）、任务（独立任务代码）、看板（看板元数据） |
| 运行时知识 | 查询那一刻才能确定的信息（物理表数据、任务日志、监控指标等），通过 Agent 工具调用现取，**不进 Wiki** |
| 深度 | 每张表不只抓 DDL 还要抓产出任务代码：DDL 给结构（字段、类型、注释），任务代码给逻辑（计算方式、过滤条件、聚合维度、上游依赖）；只有 DDL 的 Wiki 仅是骨架，加上任务代码才构成完整知识 |

## 准确性：四条工程纪律

源材料自带噪音（注释长期未更新、文档写错口径、不同来源相互矛盾），LLM 生成有幻觉，域归属与指标聚类本身带主观性。原文用四条纪律覆盖事前、事中、事后：

- **噪音过滤**：入口粗筛（剔除明显过期、低质量材料，降低后续冲突量）+ 生成细筛（LLM 写 Wiki 时识别并跳过任务代码里的调试残留、文档里的过期片段）。
- **代码即真相**：不同来源对同一对象描述不一致时，以任务代码为权威——注释和文档可能长期失修，但任务代码每天在生产上跑，代表系统当下的真实行为。
- **生成与判断分离**：生成基础 Wiki 时需推断的字段强制留空，只写有源材料直接支撑的内容；全部基础页面落盘后再独立跑一轮判断阶段、基于已写入内容输出候选。判断结果过两道门禁：机械门禁（结构、链接、格式，未通过阻断发布）+ 人工门禁（域归属、聚类归并）。代价是多一轮处理，收益是把两类易错动作解耦。
- **证据链可追溯**：每页 frontmatter 保留 `sources` 字段，逐项指向原始 DDL／任务代码／文档片段；可疑信息可立即定位原材料，用户校验 AI 答案时可沿证据链反查依据。

## 骨架是关系：8 种节点、8 种边

单页只解决"一张表是什么"，而业务问题多是关系问题——改了这张表影响哪些下游、这个指标从哪些表算出来、这个域下有多少资产。关系若只隐含在正文段落里，每次回答都要 LLM 重新从文本中抽取，既不稳定也不高效。所以关系要抽出正文、显式存储为图：血缘、归属、消费、引用等语义落到 frontmatter 字段，由构建流水线统一扫描提取，沉淀为全局关系图 `graph.json`。

显式建图带来三个能力：影响范围可计算（沿图向下游遍历得到完整影响面）、归属关系可聚合（一次查询拿到一个域的全部资产）、枢纽节点可识别（按引用频次/入度排序发现公共依赖与关键路径）。它同时是多路召回的基础——命中图上任一节点后沿边扩展关联节点。

节点 8 种：table、domain、concept、metric、dimension、dashboard、dataset、api（各带路径前缀；节点不存冗余信息，详情按需读对应页面 frontmatter）。

边 8 种，按语义分四类：

| 类 | 边 | 含义 | 方向 | 来源字段 |
|----|----|------|------|---------|
| 血缘 | has_upstream | ODPS 离线血缘 | 当前表 → 上游表 | upstream（task_type=odps） |
| 血缘 | syncs_from | 同步任务血缘 | 当前表 → 来源表 | upstream（task_type=sync） |
| 血缘 | writes_from | Flink 实时血缘 | 当前表 → 来源表 | upstream（task_type=flink） |
| 归属 | belongs_to | 归属关系 | 表/接口/看板/子域 → 父域 | domain / parent |
| 消费 | computed_by | 指标/维度来源 | 指标/维度 → 表 | computed_by |
| 消费 | uses | 看板使用 | 看板 → 数据集 | uses_datasets |
| 消费 | queries | 接口/数据集查询 | 接口/数据集 → 表 | queries_tables |
| 兜底 | wikilink | 兜底引用 | 引用页 → 被引页 | 正文 Wikilink |

三条工程判断：

1. **只存正向边**：反向边信息完全冗余，存两份必然带来双向同步的一致性负担；只存正向边使存储减半、一致性问题消失，运行时按需建索引，开销 O(E)。
2. **反填关键反向字段**：图构建后按血缘正边反向计算下游列表，回填 `downstream` 字段，让只读 Wiki 不读图的工具也能直接拿到下游。
3. **单文件存储**：`graph.json` 无需部署和维护图数据库，任何工具直接读，可随代码仓库版本管理。

## 为检索而组织

构建和组织不是独立环节，而是为检索服务的。原文给出三个工程支点：

- **知识聚合**：字段聚合为指标和维度，表/接口/看板聚合为域，域按业务主题嵌套——检索面从数百个分散页面收敛到少数几个域入口。
- **渐进式披露**：从全景概览定位相关域，从域定位关键页面，从页面取字段与逻辑细节，每层按需加载，在上下文预算内传入最相关信息。
- **多路召回**：聚合与渐进披露解决纵向定位（从全局收敛到目标页），关系图提供横向第二条路径——命中一个节点后沿边扩展到血缘相关但关键词未命中的知识。

三者分工：聚合解决信息爆炸，渐进式披露解决上下文有限，多路召回解决召回不全。

## 架构：存储层 / Schema 层 / 计算层

三层主干（配图 `imgs/img07.png`）。原文用数据库系统做类比：

| 数据库系统 | Wiki 系统 | 对应关系 |
|-----------|-----------|---------|
| 存储引擎 | 多级文件系统 | 知识的物理组织和生命周期管理 |
| 索引 | 图索引 + 树索引 | 加速检索的辅助结构 |
| DDL（建表） | Schema 定义 | 定义知识结构与约束 |
| 写表（INSERT/UPDATE） | Wiki 生成 | 按 Schema 写入结构化页面 |
| 查询（SELECT） | Wiki 检索 | 按索引和条件读取知识 |
| 约束检查 | 健康检查 + 验证机制 | 保证数据一致性与正确性 |
| 事务可恢复性 | 断点续传 + 增量构建 | 中断后幂等重跑，已有正确产物跳过，只补未完成部分 |
| 执行引擎 | Agent 编排 | 调度计算任务，管理并行与串行 |

### 存储层：目录即状态

`KB_ROOT` 环境变量指定根目录；主流程目录承载"清单 → 原始材料 → 结构化页面"的状态流，支撑目录服务编译过程本身。

```
${KB_ROOT}/
├── pre/                  # 待处理清单 + 临时下载产物（验证后移入 raw/）
├── raw/                  # ready/ 完整可用；pending/ 需治理；archive/ 已下线
├── wiki/                 # tables/{db_type} domains/{parent} concepts metrics
│                         # dimensions dashboards apis datasets
│   ├── graph.json  index.md  overview.md
├── log/                  # 构建日志、域候选、健康检查报告
├── tmp/                  # 跨 skill 协作的中间状态
└── schema/               # 5 个页面模板（定义 frontmatter 与正文契约）
```

要点：不同生命周期的物料分目录隔离，**由目录承担状态语义**；`raw/` 三态中只有 `ready/` 进编译，把"材料是否可用"从隐藏字段变成目录归属的物理事实。

### Schema 即契约

多个环节要读写同一页面（生成器写、图构建器提取关系、健康检查校验结构、query 检索内容）。若每个环节对"页面长什么样"各有理解，就会出现生成器写了但检查器读不出的情况。Schema 是对所有环节的唯一结构约定，类似微服务间的接口协议——生产者按它写、消费者按它读，任何工具用同一个 parser 就能拿到一致视图。

- frontmatter：共性字段（title、type、description、sources、created、updated）+ 页面特有字段（table 的 upstream/downstream/domain/layer，metric 的 computed_by，dashboard 的 uses_datasets 等）。
- 正文：每种页面类型固定章节模板，如 table 页含"业务背景 / 加工逻辑 / 字段说明 / 下游 / 使用建议"五节。
- 正文里的 Wikilink（双链）引用是 frontmatter 之外的兜底：frontmatter 记显式强关系（血缘、归属、消费），wikilink 覆盖行文中提到但未落到字段的弱关联，图构建器扫描后生成 wikilink 边。

### 计算层：编排层与干活层分离

7 个 skill：`wiki-orchestrator`（编排）+ 6 个干活 skill。

- 编排层只做四件事：意图路由（识别用户在做哪个 Phase）、用户确认（域归属、看板归属、生成范围等关键决策点）、子 Agent 调度（spawn 并行或串行）、结果汇报；**不读原始材料、不写 Wiki 文件、不做 LLM 内容生成**。
- 干活层按"高内聚、低耦合"切分：每个 skill 内部子任务输入输出来源相同、执行模式相近；skill 之间不直接调用，只通过文件系统约定目录交互，任何 skill 都可独立运行。
- 粒度判断：把基础生成的 4 种页面拆成 4 个 skill，相同调度框架要重复实现 4 遍（太细破坏内聚）；把基础生成与高阶生成合并，两者输入、依赖、生成方式都不同（太粗也破坏内聚）。

| Skill | 覆盖阶段 | 职责 |
|-------|---------|------|
| wiki-material-prep | Phase 0 材料预处理 | 维护清单、抓取 DDL 和任务代码、验证分流 |
| wiki-base-generator | Phase 1 基础生成 | 生成表、接口、数据集、概念四种基础页面 |
| wiki-advanced-generator | Phase 1 高阶生成 | 生成域、看板、指标、维度、index、overview |
| wiki-graph-builder | Phase 1 图构建 | 扫描 frontmatter 和 Wikilink，沉淀关系图 |
| wiki-health-check | Phase 2 健康检查 | 执行结构、链接、格式等多项校验 |
| wiki-query | 运行时检索 | 检索页面、查询血缘、关键词搜索 |

基础 Wiki 与高阶 Wiki 的分界，是干活层切分中最关键的一刀：

| 维度 | 基础 Wiki | 高阶 Wiki |
|------|-----------|-----------|
| 性质 | 原子知识单元 | 聚合知识单元 |
| 类型 | 表、接口、数据集、概念 | 域、看板、指标、维度、index、overview |
| 输入来源 | `raw/ready/` 中的源材料 | 已落盘的基础 Wiki |
| 生成方式 | 一对一映射（每个对象生成一页） | 多对一聚合（多对象按主题归并成一页） |
| 依赖关系 | 不依赖其他 Wiki | 必须等基础 Wiki 全部落盘 |

三个收益：**可并行**（数据不依赖的步骤 spawn 并行，如基础生成批内并行、高阶生成"域 + 看板 + 指标维度"三路并发）、**可独立调试**（出错只重跑对应 skill）、**可单独复用**（只跑健康检查或只跑 query，不必触发完整构建）。

## 编译流水线

三阶段：Phase 0 材料预处理、Phase 1 Wiki 生成（基础 + 高阶 + 图构建）、Phase 2 健康检查（配图 `imgs/img08.png`）。

### Phase 0：材料预处理

五步：用户提供 5 类对象清单（表、任务、看板、接口、文档）→ LLM 解析清单写入 CSV（**仅此一步有 LLM**）→ 脚本批量调元数据接口抓 DDL／任务代码／看板配置／接口配置／文档原文 → 脚本验证材料完整性 → 三态分流。

三个设计考量：**全脚本化**（抓取、验证、分流都是确定性逻辑，不依赖 LLM，避免幻觉、结果可重放、不耗 token；Phase 0 本就是机械性高、判断性低的任务）；**脚本验证前置**（如表必须同时有 DDL 和任务代码、命名规范、内容非空，未通过进 `pending` 等待治理）；**断点续传**（网络异常与接口限流难以避免，从上次中断位置继续）。分流决策由用户确认后进入 Phase 1。

### Phase 1 基础：批间串行、批内并行

三步：扫描现状（对比已有 Wiki、新增材料、`sources` 一致性，确定生成/修复/跳过的对象集合）→ 按"批间串行、批内并行"生成 → 全部生成完后跑统一校验，未通过标记重生成；基础 Wiki 落盘后独立做域候选判断，用户确认后回填 `domain`。

四个关键设计：

- **每批 5 个对象，批内 spawn 5 个子 Agent**：既并发提速，又做上下文隔离——每个子 Agent 的上下文只承载一个对象，避免多对象拼接时张冠李戴；批大小 5 是 LLM 配额、错误恢复成本、并发收益的工程折中。
- **生成后统一校验**：frontmatter 字段是否符合 Schema（必填齐全、枚举合法、类型正确），正文表结构列出的字段是否真实存在于 DDL（防 LLM 幻觉出不存在的列）。
- **生成与判断分离**：基础阶段 `domain` 等需推断字段留空，落盘后独立判断、用户确认回填。
- **增量感知**：只对真正发生变化的对象（新增材料、`sources` 不一致）触发生成。

### Phase 1 高阶：一条 DAG，三路并行 + 串行汇聚

一阶段三路并行：**域页面**（从基础 Wiki 的 `domain` 字段反查抽出域列表，按层级生成 `domains/{parent}/{leaf}.md`）、**看板页面**（基于数据集 Wiki 生成，域归属候选由用户确认）、**指标与维度**（脚本字段聚类 → 子 Agent DWD 分析 → 用户确认归并 → Wiki 生成 → 脚本一致性校验五步）。二阶段串行：`index.md`（各一级域并行写章节再合并）、`overview.md`（基于域页面 + 表 frontmatter）。

两层设计意图：**并发最大化**（无依赖步骤齐头并进，有依赖的等齐再跑）；**关键节点嵌入审核**（看板域归属、指标维度聚类归并、一致性校验都嵌在 DAG 节点里，由用户确认或脚本兜底，而不是事后补丁）。高阶页面能这样组织，关键在于聚合靠 frontmatter 字段反查，不必重新解析正文。

### Phase 2：健康检查

6 项全局对账：

| 检查项 | 检查内容 |
|--------|---------|
| 数量一致性 | DDL、Wiki 页面、graph.json 节点三方对账，确保对象数量对齐 |
| 结构完整性 | 按页面类型校验 frontmatter 字段集（必填、类型、枚举值） |
| 链接有效性 | Wikilink 断链检测、孤岛页面检测（无入边） |
| Domain 格式 | 域字段是否符合层级正则（一级域/二级域/…） |
| YAML 语法 | graph.json 与所有页面 frontmatter 的 YAML 合法性 |
| Graph 完整性 | 节点路径合法、边类型在白名单、边两端节点存在 |

任一项未通过即视为本次编译失败，输出诊断报告到 `log/wiki-health-check-{timestamp}.md`，未通过的编译产物不对外发布。它与 Phase 1 基础阶段的统一校验互补：前者是页面级、生成时的字段一致性（保证单页正确），后者是全局、构建后的对账与契约检查（保证整体一致）。

## 检索栈：意图 → 多路召回 → 重排序

### 意图识别（三类路由）

| 类型 | 特征 | 走法 |
|------|------|------|
| 精确查询 | 明确实体名（表名、域名、指标名） | 直接读目标页面详情与血缘，无需召回 |
| 关系查询 | 实体名 + 方向词（上游、下游、影响、归属） | 走 `graph.json` 遍历，沿对应方向边扩展 |
| 模糊搜索 | 关键词、业务概念、筛选条件 | 走完整的召回 + 重排链路 |

模糊搜索前**强制做域推断**：先读 `index.md`，按关键词语义匹配相关域（同时考虑生产方域和消费方域），把搜索范围从全库收敛到 2~3 个相关域。原文强调这一步不可跳过——它在召回阶段就大幅缩小搜索空间，是后续召回质量的前提，也是渐进式披露在检索侧的落地。

### 多路召回（两阶段）

- 阶段一，两路并行：**域召回**（按推断出的域读域页面，召回域下挂载的相关表，用业务主题硬过滤）+ **关键词召回**（在 frontmatter 字段和正文上做加权匹配，标题、描述、域、上下游等结构化字段权重高于正文；用户提到具体字段名时退化为精确匹配）。
- 阶段二，**图扩展**：对阶段一命中的候选沿血缘边向上下游扩展，把"用户搜了 ADS 表、但答案在它的 DWS 上游"这类跨节点场景兜进来。
- 两阶段产出合并去重，输出 4~6 张候选表交精排。

### 重排序（粗排脚本 + 精排 LLM）

粗排由脚本完成：按关键词命中权重与通用性指标算分，排序输出 4~6 张候选，只做确定性初筛、不做语义判断。精排由 LLM 完成：逐张读详情（frontmatter + 正文）判断是否真正满足需求。

精排的硬约束：**每张候选表都必须读详情**，不允许前几张匹配度高时提前停止——靠后的候选可能因覆盖度、通用性更高而成为最终推荐。

| 维度 | 判断依据 |
|------|---------|
| 覆盖度 | 表的实际字段和数据是否覆盖需求（LLM 读详情判断，不依赖关键词命中位置）——**硬门槛**，不满足直接淘汰 |
| 相关性 | 表的主题与用户搜索意图的语义贴合度 |
| 通用性 | 被大量下游消费的枢纽表。单独成维是对抗重复建设：用户不知道的公共表往往被另建一张高度相似的表，把通用性纳入排序能让用户感知现有公共依赖，提升资产复用率 |

排序逻辑两层：覆盖度不合格直接淘汰，无论其他维度多突出；在覆盖度合格的候选中按意图权衡——意图明确具体（"我要查某个特定指标"）相关性优先，意图偏探索（"这个域有哪些常用表"）通用性优先。最终输出三件套：最推荐表 + 候选列表（4~6 张）+ 血缘链路。

## 增量编译与持续 Lint

目标：构建成本只和变化量相关，不与总规模相关——未变化的部分跳过，变化的部分按依赖关系局部重跑。

增量识别的关键是**扫描现状对账**，比对三方：源材料目录（新增、删除、内容变化）、已有 Wiki 页面、Wiki 中记录的 `sources` 字段。差异决定本次触发哪些阶段的子集。

| 场景 | 处理 |
|------|------|
| 新材料入库 | 预处理拉取新增对象 → 基础生成只为新增对象产出（已有页面不动）→ 域判断只对新增对象做归属候选 → 图构建全量重建（O(E)，相对生成可忽略） |
| 知识腐化更新 | 上游 DDL 或任务代码变更 → 重跑预处理与基础生成覆盖对应页面 → 图构建重建并自动回填 `downstream` → 健康检查 |
| 结构性修复 | 少量校验失败页面或规则升级后存量不合规 → 直接调对应阶段（基础生成/高阶生成/图构建）局部重跑，不必从预处理重走全程 |

**Lint** 把健康检查从"构建后一次性兜底"扩展为"持续性质量巡检"：6 项规则变成 Lint 规则集，每周或重大变更后跑一次，发现断链、孤岛、格式退化、节点冗余；不通过的进治理待办，由对应阶段触发生成。构建期 + 运维期双重保障。

## 原文总结的设计决策

1. 源材料用**代码即真相**做仲裁，解决多源冲突。
2. 生成阶段坚持**生成与判断分离**，让 LLM 不做主观推断。
3. 产出经结构、语义、人工**三层校验**，使正确性可度量。
4. 所有页面遵循 **Schema 即契约**，跨工具消费时按字段直接读取。
5. 页面之间的关系显式存为**图**，业务主题聚合为**树**并支持渐进式披露。
6. 编排与干活**分层协作**，高内聚低耦合，让流水线可并行、可调试、可单独复用。
