# 企查查智能文档解析

> 核心主张：**文档解析这个基础能力如果错误，下游任务不可能处理得好。** 企查查的路径是「开源 VLM 底座 + 业务/行业数据训练」做专属模型，再用工程手段修正 VLM 的幻觉、印章干扰与超长图片问题，最后从调度、算子、投机解码三层做加速。模型无法解决所有问题——特定场景下，深入定制化开发可能比训练模型更高效；但数据仍然决定模型上限。

演讲来源：DACon 2026 北京站「非结构化数据处理与知识获取」专场，陈汝龙（企查查）。讲者未在幻灯片中展开个人履历，页面内容以业务场景与工程链路为主。

## 背景与问题

### 业务链路：从海量非结构化文档到结构化 JSON

企查查的业务输入是海量非结构化文档，经「企查查智能处理引擎」后输出结构化信息：

| 环节 | 内容 |
|------|------|
| 海量非结构化文档 | 上市公司公告、专利文书、招投标公告、债券发行说明、声明函、行政处罚决定书；格式包括 PDF、Word、Excel |
| 企查查智能处理引擎 | 文档解析（Document Parsing）→ 领域模型信息抽取（Domain Model Extraction） |
| 结构化信息输出 | 营收数据、利润数据、招标信息、中标信息、信用信息；以 JSON 输出 |

这条链路的业务目标是「自动识别、提取、结构化多维文档数据」，服务于企查查的核心业务场景。

### 一个具体的失败链：无边框表格

幻灯片用一张财务表格说明问题如何逐级放大：

1. **原始输入（无边框表格）**：表格包含「项目 / 附注 / 2026 年 1-6 月 / 2025 年 1-6 月」等列，营业收入、营业成本、税金及附加、管理费用、研发费用、财务费用等行；没有可见边框。
2. **解析缺失表格信息**：解析异常，提示「缺乏表格结构」，输出退化为按阅读顺序拼接的文本：「一、营业收入十七、3 197,926 201,731 减：营业成本十七、3 -- …」。
3. **业务无法抽取正确结果**：字段映射丢失 & 指标缺失，JSON 中出现「营业收入: null（未检测到）」「营业成本: null（解析失败）」「2026年1-6月: 无匹配数据」等错误。

讲者的结论是：**「文档解析这个基础能力都错误的话，下游任务如何能处理的好？」**

### 四类典型挑战

| 挑战 | 原文描述 |
|------|---------|
| 跨页表格断裂 | 表格受页面大小限制被截断为多张，跨页后结构难以恢复 |
| OCR 语义缺失 | 扫描件 OCR 只给出文字，缺少表格/段落等语义结构 |
| 复杂表格解析错误 | 无边框、嵌套、纵向、复杂样式等表格解析错误 |
| 协作与共享挑战 | 串联任务定位问题复杂，文档处理经验缺少共享和共用 |

> 「协作与共享挑战」卡片上标有 90% 与 80% 两个数字，但原文未解释其含义与统计口径，**不确定**。

## 对比与选型

### 三类方案的能力边界

| 方案 | 代表 | 特点 |
|------|------|------|
| 基础工具 | pypdfium2 | 速度快、精度低 |
| 传统 pipeline | 开源文档解析流水线（版面分析 → 表格识别 → 文本识别） | 复杂度高、精度中等 |
| 开源 VLM 方案 | 简化版 VLM 文档解析流程（统一 VLM 模型为核心组件） | 速度慢、精度高，场景适配不足 |

### 选型的三个约束

| 约束 | 原文描述 |
|------|---------|
| 精度要求 | 金融表格、招标中标信息，解析精度对后续的信息抽取至关重要 |
| 解析速度 | 金融公告文档、招投标文书，海量的文档需要结构化 |
| 场景适配 | 一些特殊场景要求，需要进行场景适配 |

### 最终路线：开源 VLM + 业务数据训练

幻灯片给出的路线是：

```
开源 VLM 模型（基础能力、通用性强）
        +
业务/行业数据
        ↓ 进行训练（Training）
专属业务模型（场景适配、精度提升）
```

也就是说，不直接在通用开源 VLM 上做业务，也不从零训练，而是以开源 VLM 为底座，用业务/行业数据做领域适配，得到「专属业务模型」。

## 数据准备和模型训练

### 系统架构流程

```
文档输入
  → 场景化预处理
      → 主流程：版面分析 layout
          → 文本识别
          → 表格解析
          → OCR 更正
          → 跨页合并
          → 结果输出
      → 分支：目录层级（消费目录树数据）
```

其中：

- **业务标注数据**同时供给「版面分析 layout」与「表格解析」，是监督信号的核心来源。
- **目录树数据**供给「目录层级」分支，用于恢复文档的章节结构。
- **场景化预处理**位于最前，承接不同来源、不同质量的文档。

### 数据标注：四种找难例的方法

| 方法 | 做法 |
|------|------|
| 01 数据筛选 | 关注金融公告、招投标公告、债券发行公告等 |
| 02 多模型校验 | 使用多个开源模型进行数据标注，筛选多个模型不一致的数据，并且也引入商业 VLM 大模型审查对比 |
| 03 不稳定数据 | 通过调大 temperature，同模型同输入多次预测，筛选出不稳定数据 |
| 04 专家标注 | 对于少数的最终无法确认的困难样本，引入专家进行标注和确认 |

两张流程图进一步说明：

- **多模型校验**：输入数据 → 多个开源模型预测 → 预测一致 = 简单数据；预测不一致 = 困难数据 → 引入商业 VLM 进行评审。
- **不稳定数据（寻找困难样本）**：相同输入数据 → 相同模型（调大 Temperature 参数）→ 多次预测 → 预测结果不一致 → 获得困难样本。

这套方法的核心是「用模型之间的分歧和模型自身的不稳定性，自动发现值得人工标注的样本」，把专家时间集中在真正困难的样本上。

### 样例：表格结构是标注的重点

幻灯片展示了两类真实表格样例：

1. **股本变动表**：列包括「本次变动前（数量/比例）」「本次变动增减（其它/小计）」「本次变动后（数量/比例）」，行包括「一、有限售条件股份」「二、无限售条件股份」「三、股份总数」，并细分国家持股、国有法人持股、其他内资持股、外资持股、高管股份等。
2. **控股公司表**：列包括「单位名称 / 注册地 / 法定代表人 / 注册资本 / 经营范围 / 投资额 / 权益比例」，行是各子公司。

这两类表格共同说明：业务需要的不是「一张图」，而是「单元格级别的结构 + 行列语义 + 合并关系」，否则后续字段映射无法完成。

### 模型结构：675M 视觉编码器 + 0.5B LLM 解码器

幻灯片给出的模型结构如下：

```
Image & Text Input
  → Visual Processing Pipeline
      → Naive Dynamic Resolution
      → 675M NaViT Vision Encoder（Full Attention + 2D-RoPE）
      → 2x2 Pixel-Unshuffle Patch Merger（4x Token Compression）
  → Multimodal Fusion
      → M-RoPE（Upgraded from 1D-RoPE for Diverse Aspect Ratios）
      → 1D Temporal / 2D Height / 3D Width
  → Generation
      → Lightweight 0.5B LLM Decoder
  → Structured Outputs
      → Layout Boxes, Text, OTSL, Tables & LaTeX Formulas
```

其中 **OTSL** 是表格结构的序列化表示之一（原文只写 OTSL，未展开全称，**不确定**其具体定义）。模型同时输出版面框、文本、表格与 LaTeX 公式，说明它是一个「统一文档解析 VLM」，而不是只做表格识别的单任务模型。幻灯片未点名具体开源底座模型。

### 分阶段训练：SFT → GRPO

| 阶段 | 做法 | 目标 |
|------|------|------|
| STAGE 01：SFT 微调训练 | 强化模型针对领域数据的适配 | 让模型学会业务/行业文档的分布 |
| STAGE 02：GRPO 强化学习 | 设计 Layout & Table 相关奖励函数；针对 SFT 之后仍然不稳定的数据，继续强化训练 | 用奖励函数压不稳定样本，提升版面与表格的结构正确性 |
| 最终模型 | 迭代渐进 | 保证通用能力不退化；解决领域数据问题 |

这里值得注意的是：强化学习不是笼统地优化「答案质量」，而是明确针对 **Layout & Table** 设计奖励函数，说明表格结构识别是这一阶段的核心优化对象。

## 场景应用

### 1. VLM 幻觉与繁简问题

幻灯片先展示错误样例：VLM 输出中的公司名/实体名出现错字或繁简混用，例如：

- 「苏州全心」中的「心」被标红；
- 「南粤控股」中的「粤」被标红；
- 「上海誠勸」中的「勸」被标红；
- 「花様年」中的「様」被标红；
- 「墨生命」中的「墨」被标红。

这些错误对企查查是致命的：公司名匹配、实体对齐、公告检索都依赖字符级正确性。

**解决方案**：用 **pdfium2** 提取 PDF 的文本层，对 VLM 输出做校正。幻灯片右侧给出港股公告场景的成果：

- 标题：「优化后匹配准确率达成」；
- 图表：「港股公告实体提取匹配准确率优化成果」；
- 指标：**匹配准确率提升 +2.8%**；
- 维度：Company Names | 公司名匹配。

也就是说，VLM 负责「看懂版式与结构」，PDF 文本层负责「字符级校对」，两者互补。

### 2. 印章干扰

幻灯片展示印章覆盖导致的识别错误：

| 场景 | 错误表现 |
|------|---------|
| 联系方式 | `xxx-xx073xxxxxx`，印章遮住部分数字 |
| 公司名 | 「泽普县清和管家城市服务有限公司」中的「管」被印章覆盖 |
| 地址 | 「……批发市场第三层……」中的「三」被印章覆盖 |
| 电话 | `133xxxx688`，印章遮住部分数字 |

**解决方案**：

```
原文件
  → 提取底版 → 无印章文档
  → 提取元素 → 印章识别 → 独立印章
```

即把「无印章的底版」和「独立印章」分离，分别处理，避免印章像素污染文字识别。幻灯片右侧给出招投标场景的成果：

- 标题：「优化后联系方式准确率达成」；
- 图表：「招投标公告联系方式提取准确率优化成果」；
- 指标：**提取准确率提升 +5.2%**；
- 维度：Tendering Contact | 招投标联系方式。

### 3. 超长图片（面条图）切割

**问题**：文档中存在宽高比 **1:17** 的超长「面条图」，示例宽度约 **900px**、高度约 **17000px**。直接输入 VLM 做归一化会导致数字字迹模糊、无法看清。幻灯片用「Y 轴投影」展示长图中的文字像素密度分布。

**三种切割方案对比**：

| 方案 | 做法 | 问题/效果 |
|------|------|----------|
| 方案一：固定高度硬切 | 按固定高度直接切 | 容易切碎文字、破坏语义 |
| 方案二：Y 轴投影浮动切割 | 按 Y 轴投影的空白位置浮动切 | 贪心算法，局部切点非最优 |
| 方案三：全局最优解切割（我们的解法） | 多维加权寻优 | 全局视野寻优，完整保留表格与语义块 |

**方案三的多维加权寻优算法**：

| 因子 | 作用 | 权重 |
|------|------|------|
| Y 轴投影密度 | 优先在文字稀疏处切 | w1 |
| 穿过连续竖线 | 避免截断表格内容 | w2 |
| 目标图像高度 | 符合长度/比例限制 | w3 |

最终输出「加权全局最优解」。示例中切出的语义块包括「大消费(8)(32.01 亿)」「有色金属(6)(76.69 亿)」「农业(5)(14.87 亿)」等分组，每个分组保留「股票代码 / 股票名称 / 打板时间 / 第几板 / 成交块」等表格列。

## 加速方案落地

### 1. 模型加速-调度：Serial → Parallel & Pipelined（+3%）

| 调度方式 | 流程 | 效果 |
|---------|------|------|
| 原调度（Serial） | Layout 任务 → Text/Table 任务，串行等待，前置任务完成后才进行下一阶段 | 存在串行等待 |
| 新调度（Parallel & Pipelined） | Layout 任务前置（4 页）→ Text/Table 任务 1/2/3 并行 | 打破串行等待，后续任务无须等待，直接并行处理，实现持续批输入；标注 **+3%** |

### 2. 模型加速-算子

| 优化 | 做法 | 收益 |
|------|------|------|
| 图像 Attention 优化 | 1 工作组每 SM → 2 工作组每 SM，调整线程寄存器；特征数 256–6448，图片数 1–12 张（其余回退默认） | **+6%** |
| CUTLASS 算子融合 | FC1 Matrix + QuickGELU 操作 → 融合 kernel；输入特征总数 2048–33000 | **+6%** |

### 3. 模型加速-Dflash 投机解码

**背景**：

- Dflash 是今年发布的新算法；
- 讲者其他业务上已用上，提速约 30%；
- 在此也引入此算法。

**核心工作 1：多任务 Draft 模型训练**

| 任务 | 加速比 |
|------|-------|
| Layout | 1.7x |
| Table | 1.6x |
| Text | 1.5x |

**核心工作 2：模型结构简化**

- 降低 Hidden Layer 层数：4 → 3；
- 接受率：50%–60%（几乎未变）；
- Draft 输出：3 tokens。

**成果与测试**：

| 测试 | 结果 |
|------|------|
| 并发 24 测试 | -2%（Target Verify 成本抵消了收益） |
| 并发 4 测试 | +8% |
| 最终实际收益 | 大约 2–3% |

这里的边界很清楚：Dflash 在单任务上能带来 1.5–1.7x 的加速，但端到端实际收益只有 2–3%，原因是 Target Verify 的成本会抵消一部分收益，且收益随并发度变化。

### 总结页的两层架构

幻灯片最后用一张分层图收束：

- **上层：业务字段抽取与赋能（企查查核心业务场景）**——核心内容：自动识别、提取、结构化，用于核心业务需求。
- **底层：解析核心技术**——核心内容：布局分析、文字识别、表格解析；关键前提：提供高置信度的结构化基础。
- **中间：智能文档解析服务引擎**——核心驱动：自动识别、提取、结构化多维文档数据。

输出四类业务数据：

1. 财务数据（如资产负债）；
2. 招投标信息（如中标公示）；
3. 行政处罚（如罚款金额）；
4. 限制高消费（如限消名单）。

讲者的关键观点是：**「企查查所需的精准业务赋能，建立在底层文档解析的精准程度之上，确保全链路数据的准确性。」**

### 边界判断

- 这是一套**业务驱动的文档解析工程**，不是通用文档解析 Benchmark 研究；其价值在于把「解析 → 抽取 → 业务字段」串成闭环。
- 表格识别在本页中主要体现为「无边框表格结构恢复 + OTSL 输出 + Layout & Table 奖励 + 长图切割保留表格语义」，原文没有单独披露表格识别模型的精度对比。
- VLM 幻觉修正依赖 PDF 文本层；对纯扫描件（没有文本层）是否同样适用，原文未说明，**不确定**。
- 印章处理方案假设印章可以被识别并分离；对严重遮挡、印章与文字颜色接近等极端情况，原文未给出失败率，**不确定**。
- Dflash 的端到端收益只有 2–3%，讲者也明确「没有完全发挥」，因此不能把 1.7x 的单任务加速比当作整体吞吐提升。
