# 从数据工程到知识工程

> **核心主张：知识是数据领域的第三次革命，也是企业在 AI 三要素中最大的差异化来源。** 过去 20 年完成的是"数据 → 信息"，未来 5 年是"信息 → 知识"；而知识的表达（本体）目前没有统一标准，存在五条不同的路线。Raw Data 不等于 AI-ready Data——知识需要一个生产过程；知识工程的本质是非结构化到结构化的过程，因此结构化数据的管线、分层、增量、评估都能复用；构建知识工程平台最终依赖一套整体基础设施，而不是另起炉灶。

**演讲信息**：关涛，云器科技联合创始人 & CTO。DACon 2026 北京站（PDF 页脚带 DACon 标识、第 2 页带"DACon 北京站"角标；PDF 元数据创建于 2026-10-21）。本页依据 30 页幻灯片逐页取文本层 + 逐页渲染视觉复核（含概念地图、对比表、架构图与案例数字页）整理；正文未标注具体分论坛场次。

## 一张概念地图：数据、信息、知识、本体与语义

演讲按本体论的方式把核心概念画成类图：节点是类，框内是该类的定义或属性，虚线是子类（分类），实线是带名字的对象属性，右侧是公理。

| 类 | 定义 | 与其他类的关系 |
|----|------|--------------|
| 数据 Data | 原始素材：记录、日志、文档、对话 | 加工为 → 信息 |
| 非结构化数据 | 提供上下文 Context | 数据 的子类；抽取出 → 实例 |
| 结构化数据 | 提供事实 Truth | 数据 的子类；加工为 → 关系表 |
| 信息 Information | 加工处理后、有逻辑的数据 | 数据 加工为 信息；组织为 → 知识 |
| 关系表 Table | 列 · 主键 · 行（事实） | 是一种 信息；被语义视图绑定 |
| 知识 Knowledge | 组织化的信息：关系 · 规则 · 口径 · 流程 | 表达为 → 表达形式；表达为 → 本体 |
| 语义视图 Semantic View | 逻辑表 · 指标 · 维度 · 验证查询 | 定义为 绑定到关系表的本体（结构化数据之上的本体） |
| 知识图谱 Knowledge Graph | 面向通用对象与非结构化知识 | 定义为 含实例的本体（本体 + 实例）；hasPart → 实例 |
| 本体 Ontology | 概念 · 属性 · 关系 · 规则（TBox） | 是一种 知识；被知识图谱实例化 |
| 实例 Instances | 对象 · 属性值（ABox） | 知识图谱 hasPart 实例；非结构化数据抽取出实例 |
| 表达形式 Representation | 可检索 · 可推理 · 可校验 | 知识 表达为 表达形式 |

图右侧写了五条公理（原文以"定义 / 推出"形式给出）：

1. **关系表 是一种 信息**（表 = 信息）
2. **语义视图 定义为 绑定到关系表的本体**（结构化数据之上的本体）
3. **知识图谱 定义为 含实例的本体**（本体 + 实例）
4. **关系表 + 语义视图 推出 知识**（表 + 语义 = 知识）
5. **数据的形态 互斥且完备**：结构化 / 非结构化

图例还强调了一件容易被混淆的事——**子类与对象属性是两种层级不同的关系**：

> 子类（虚线）是概念之间的包含：每个 X 都是 Y，例如"关系表是一种信息"；对象属性（实线）是实例之间的联系：X 经过某种动作或关联得到 Y，例如 加工为 / 绑定到 / hasPart。两种线都是关系，但不是同一层。

## 知识的表达：同一份知识，可以有多种形态

演讲用同一个事实——Meta 2023 年总营收 1,349 亿美元——演示它在五种载体上的写法。同一件事可以写成一句叙述（约 100 字节）、一张二维表（约 10–20 字节）、一张图（约 33,000 字节的 PNG），也可以编码成向量、点边图或模型参数。**表达方式决定可读、可检索、可推理的能力与代价。**

| 维度 | 二维关系表 | 标量 / 倒排索引 | 向量 | 点边（图） | 模型参数 |
|------|-----------|----------------|------|-----------|---------|
| 表达能力 | 中（结构化数据） | 中（半结构化数据） | 高（任何数据） | 高（关系与路径） | 高 |
| 存储方式 | 二维表、行存 / 列存 | 倒排索引 | 向量索引 | 图存储 / KV | 大模型内（通过训练） |
| 计算方式 | 关系代数 | 匹配检索 | 距离计算 | 图计算 | 提示词查询（Prompt） |
| 使用难度 | 中，灵活 | 低，不灵活 | 低，不灵活 | 高，灵活 | 极低，非常灵活 |
| 准确度 | 高 | 高 | 中 | 高 | 低 |
| 信息密度 | 高 | 中 | 低 | 高 | 中 |
| 可解释性 | 高 | 中 | 低 | 高 | 低 |
| 可控性 | 高 | 高 | 低 | 高 | 低 |
| 建模难度 | 中 | 低 | 低 | 高 | 极高 |

读表提醒：底色按该维度的好坏方向着色——"建模难度：高"是差，"可解释性：高"是好——不是数值高低。

演讲的落点是**没有一种形态包打天下**：

> 数据表达，向高准确性、高信息密度、高可解释性、高可控性流动（从数据到知识），但没有一种形态包打天下。

这也解释了为什么后续需要"五条路线"而不是"一个标准答案"。

## 知识（本体）建模有标准吗？——有标准，但不统一

演讲用一句话概括现状：**有表达、查询和约束规范，但没有产业共同接受的企业本体建模、运行与维护标准。** 当前没有任何一套标准同时规定四件事：**建什么 · 怎么运行 · 如何裁决 · 怎样持续维护**。

三个证据：

- **W3C 标准化的是表达**：RDF / OWL / SHACL 规定机器如何表达、推理和校验；不规定企业应该采用哪一种业务对象与运行模型。
- **产业实现彼此不同**：Palantir 建对象与 Action；Semantic View 建指标与 SQL；Genie 建知识片段并排序——并非同一标准的实现。
- **开放交换仍在形成**：Apache Ossie 仍处 Incubating，当前重点是跨工具交换；它也不提供统一运行时与企业本体方法论。

因此演讲明确了一个前提：后面的五类系统**不是同一标准下的五个实现，而是五种不同的本体 / 语义建模模型**。

### 五条路线速览

| 路线 | 建模中心 | 强项 | 边界 | 路线判断 |
|------|---------|------|------|---------|
| Palantir Ontology | 属性式对象模型 · 通用建模：Object / Property / Link / Action，连行动一起建，实例物化为可操作对象 | 全面建模、行动包含层、本体运行引擎——语义、实例、权限、Action 与写回统一在一个平台 | 垂直领域、不开放、高成本；实施重、实例规模大、平台封闭 | 适合高治理的运营闭环；**不是起点** |
| Semantic View 家族 | 属性式对象模型 · 分析语义：对象 = 逻辑表（Logical Table + Relationship + Fact / Metric / Dimension），实例留在源表 | 确定性 + 准确性；查询时编译 SQL，原生 RBAC 与审计，对 NL2SQL 直接有效 | 仅在结构化数据领域；不承担业务实例写回与行动编排 | 结构化分析语义的**主流起点** |
| [[apache-ossie\|Apache Ossie]] | 实体模型（事实式）：本体层 EntityType / Role / Relationship，核心语义层仍是属性式（与 Semantic View 同构） | 确定、准确，且是厂商中立的开放标准，一次编写、各处查询 | 仍限结构化；本体层刚起步；不是查询引擎，也不是语义运行时 | 企业的**另一个起点**：开放、无锁定 |
| [[genie-ontology\|Databricks Genie Ontology]] | 混合模型：结构化 Semantic（Metric View）+ 企业知识（Knowledge Snippet + 资产 / 用量关系） | 覆盖面广；大量自动化生成能力，能从真实使用持续学习与更新，建模成本低 | 排序不等于验证，难以表达非可加、基数等需要强契约的约束 | 比较普适的模式：适合补齐长尾上下文；认证真值仍需语义内核 |
| Agent Memory | 情景 / 语义记忆（episodic / semantic）：自由文本、个体偏好与经验，无 Schema | 覆盖广、低建模、弱保证 | 无结构校验、无冲突发现、无口径裁决；不承担组织级真值 | 个体记忆；不能承担组织真值 |

### 一条轴：每向右一步，用保证换自由

演讲把这五条路线排成一条从"强保证"到"高灵活"的轴：

| 位置 | 路线 | 换来的是 |
|------|------|---------|
| 强保证 | Palantir Ontology | 口径唯一 · 可验证 · 可写回 |
| 开放接口 | Apache Ossie（居中） | 跨工具交换 · 不绑定引擎 |
| 高灵活 | Agent Memory | 覆盖广 · 低建模 · 弱保证 |

> 每向右一步：用一种保证，换一种自由。

核心总结也落在这条轴上：**不同方案的设计目标和方向不同，所以在不同场景上会采用不同的知识建模形态。既然知识有多种建模形态，企业就需要一个通用的框架来建设知识。**

## 挑战一：知识的获取——最难的知识不在文档里，在人脑子里

知识获取的目标被定义为"让 dump 知识的代价趋近于零"：**尽量不要求人写文档，只要求人正常工作**。

### 知识的三层供给

| 难度 | 知识的形态 | 载体 | 拿到它的方式 |
|------|-----------|------|-------------|
| 容易 | 已经写下来的 | 文档、Wiki、制度、SOP | 蒸馏不难——案例二 |
| 中等 | 在系统里的 | 查询、Dashboard、代码、配置 | 从使用痕迹归纳——Genie 路线、验证查询（案例一） |
| 最难 | 在人脑子里的 | 口径、经验、判断、习惯性流程 | 量最大、最难；人自己也没意识到该写出来 |

### 解法：Trace

> 人和 AI 的每一次交互，都是知识的原料。提问、纠正、确认、选择，甚至日常沟通，都被 trace 下来；从 trace 里蒸馏口径、偏好、流程，验证后入库。

演讲给了一段真实 Trace 的样例：用户问"本月 GMV 是多少"，Agent 答"1,200 万"，用户纠正"不对，GMV 不应该包含退款订单"——系统识别为**指标口径纠偏**，生成候选规则「GMV 扣减退款」，经管理员确认、评测后语义版本 +1。

Trace 里常见的五类线索：

| 线索类型 | 例子 |
|----------|------|
| 指标口径纠偏 | "GMV 不应该包含退款" |
| 时间口径纠偏 | "按支付时间，不是创建时间" |
| 过滤条件补充 | "要排除测试商家" |
| 同义词补充 | "成交额就是 GMV" |
| 关联关系补充 | "订单表按 store_id 关联门店表" |

两张"革命原料"的对照是这一节的口号：**第二次数据革命的原料是 Log（人的行为），第三次数据革命的原料是 Trace（人的认知）。**

### 知识不只是语义和问答

演讲特别指出还有大量**程序性知识**：流程、经验、技能、工具用法。它给出的判断是——**流程是人做出来的，不是写出来的，它几乎只在 Trace 里才看得见。** 保鲜也在同一个机制里完成：Trace 持续发生，知识持续更新。

## 挑战二：知识的加工——有了 Raw Data，不等于 AI-Ready，也不等于知识

演讲用一份业务文档演示"从文档里抽出来的东西还不是知识"。

**Raw**：《交易指标口径说明 v3》写"GMV：用户下单成功的商品金额合计，按下单时间统计"；《2025 Q3 口径勘误》写"GMV 自 Q3 起剔除退款，改按支付时间统计；报表里的'成交额'即 GMV"，另附一段 SQL 示例（`SUM(dgmv) … WHERE is_test_seller = 0`）。

**大模型抽出来的三条候选**：

1. GMV = SUM(金额)，按下单时间
2. GMV = SUM(金额) − 退款，按支付时间
3. 别名：成交额 = GMV

三条互相冲突；没有绑定到表和列；没有证据编号；不知道哪条还有效——**这还不是知识**。

**要成为知识，还差四步**：

| 步骤 | 要做的事 |
|------|---------|
| 绑定 | GMV 对应哪张表、哪一列 |
| 裁决 | 两个版本哪个有效、从何时起 |
| 校验 | 金标题库、证据校验，错了能发现 |
| 发布 | 带版本、可追溯，Agent 才敢用 |

**走五步的管线**（同一例子）：抽取 → 转换 → 索引 → 评估 → 服务。其中抽取、转换、服务三步明确标注为"AI / 大模型驱动"：

| 阶段 | 做什么 |
|------|--------|
| 抽取 | 读两段话和 SQL 示例 → 三条候选（指标、表达式、别名），每条带来源段落编号 |
| 转换 | 归并同名对象；绑定到 `dm_trade_order_1d.dgmv`；冲突只标不裁；补单位（元）、别名（成交额） |
| 索引 | 结构化部分进语义视图（指标 / 维度 / 过滤）；原文进全文与向量索引；中文业务词 ↔ 英文标识符桥接 |
| 评估 | 金标题库跑一遍：口径正确率、越界拒答；证据校验器：引用的表列必须有据可查；冲突交人工裁决 |
| 服务 | 证书 PASS → 语义视图 v+1：GMV = SUM(dgmv)，剔除退款、按支付时间，带证据编号，供 NL2SQL / Agent 调用 |

> Raw 的文档抽取出来，并不等于有了知识——**绑定、裁决、校验、发布之后**，才是 Agent 能可信消费的知识。

## 案例一：从"验证查询"蒸馏语义视图

**为什么做**：语义视图是 NL2SQL 与语义层的地基，目前靠专家手写——贵、慢，是冷启动的第一瓶颈。而每家企业都天然沉淀着验证查询：业务问题携带语义，确认过的 SQL 携带结构事实。

**怎么做**：让大模型阅读企业已有的「业务问题 + SQL」，自动生成数据的业务说明书。关键约束是：**大模型只把 SQL 当文本阅读、不执行；按表分批蒸馏再机械合并；每条结论带证据编号，证据不足就留空待人工复核。**

真实样例（MIT 校园数据仓库查询 q039）：「秋季学期开设了哪些科目？授课教师和邮箱是什么？」对应的 SQL 是 `EMPLOYEE_DIRECTORY` 与 `COURSE_CATALOG_SUBJECT_OFFERED` 的 join。蒸馏产物是一条语义视图条目：

- 关系：开课记录表 →（多对一）→ 教师目录表
- 连接键：`RESPONSIBLE_FACULTY_MIT_ID = MIT_ID`
- 业务含义：每条开课记录对应一位负责教师；教师可负责多门课
- 置信度：高（连接条件在查询中显式出现）

**效果**（3 个公开基准 · 4 轮实验 · 2 轮独立数据审计）：

| 指标 | 读数 | 说明 |
|------|------|------|
| 关系结构完整还原 | **F1 = 1.0** | 表名列名全部换成陌生代号仍全对（TPC-H）；与保险专家手工建模逐条一致（44 组问答 → 13 张表） |
| 精确率 · 零编造 | **97–100%** | MIT 真实数仓；不给查询、只给表名的对照组才出现编造（85%） |
| 覆盖 | **×2.3** | 分批蒸馏、按表蒸馏再合并，突破单次输出约 50 条的瓶颈；"两端一致"过滤后精确率 95.8%，达到自动入库标准 |

**两条设计原则**：一是"高精确"——SQL 里出现过的几乎全部蒸出，没出现的绝对不碰；不确定就不猜（订单明细表的复合主键证据不足，模型留空待人工确认，而不是编一个）。二是"可持续迭代"——语料攒多少、蒸多少；哪张表缺语料自动记账、定向补充，知识随使用不断长全，而不是一次性工程。

**理论上限 50.8%**：查询里出现过的关系才可能被蒸出（MIT 标准答案共 197 条关系）——所以这条路线必须和 Trace、文档互补。产物遵循 Apache Ossie 格式。

## 案例二：把业务文档蒸馏成语义视图，而不是直接检索

**为什么做**：某头部内容平台的文档已经整理得很好，RAG 召回的效果却不好。原因不是知识不够，而是**知识太多**：同一个指标三四种相似描述散落在 25 篇文档里，召回一次带出一堆相似信息。同一个 Agent 既要写 SQL，又要在相似指标里甄别，还要做归因分析——注意力被分散，在相似信息干扰下判断出错。

**怎么做**：把整理好的业务文档再蒸馏一层，成为结构化的 Semantic View。大模型读散文、sqlglot 解析 SQL，确定性校验器裁决：引用的表和列必须有据可查。样例输入是"客单价（ATV）= 成交金额 ÷ 日活跃购买用户，按支付日统计，剔除测试商家"加一段 SQL；产物是：

- 指标 `atv · 客单价（元） = SUM(dgmv) / SUM(dab)`
- 表 `dm_trade_order_1d`，观测列 `dgmv · dab · dt · is_test_seller`
- 常用过滤 `is_test_seller = 0`，别名 客单价 / ATV
- 越界提问"碳排放是多少？"→ 不在 SV 中，拒答，不编造

两个工程判断：**进了语义视图，命中即唯一**——指标、维度一旦蒸进 SV，Agent 不再需要在相似描述里甄别，每条带证据，越界允许拒答。**同一指标多种描述，交给专门的阶段**——语料里 7 个指标各有 2 套以上合法写法，蒸馏平台用变体组归并 + 多次投票（n = 3）处理，冲突只标不裁，交人工确认。

**效果**（25 篇业务文档 · 32 道正向题 + 14 道负向题 · 文档检索 vs 结构化语义视图，同尺对照）：

| 指标 | 读数 |
|------|------|
| 准确率 | **≈2×**：指标口径正确率 38.1 → 73.4；选表 F1 80.3 → 85.7（向量文档检索 → 语义视图） |
| Token 成本 · 每条正确口径 | **−52%**：24.5k → 11.7k token；每题 token −8%，其中输出 −17% |
| 执行效率 · 长尾耗时 p90 | **−21%**：38.7 → 30.5 s；p75 −29%，均值 −16% |

值得注意的是：**数据来源没有增加，反而变少了**——同一批 25 篇文档，SV 上下文比召回的文档块还短（≈ 3.3k vs 3.9k token）。整理之后，准确率、效率、token 三项同时达标，294 次越界生成零编造。

## 四条架构共识

### 共识一：蒸馏过程用 Agent Loop，还是 Pipeline？——Agents in Dev, Artifacts in Prod

| 对比维度 | Agent Loop（开发期 · 本地） | 确定性 Pipeline（生产期 · 平台） |
|----------|---------------------------|-------------------------------|
| 谁做决策 | 模型自主循环：下一步做什么由模型决定 | 编译产物（DAG）决定；循环由确定性校验器控制 |
| 适合做什么 | 探索语料、标定提示词、定契约与校验规则 | 批量抽取、调度重跑、分片重试、审计 |
| 模型的角色 | 既做抽取，也做流程决策 | 只做抽取（AI_EXTRACT 有界算子：投票 + 修复上限） |
| 可控性 | 不可预测：成本、时延、结果都随模型波动 | 可压测、可复现、可回滚；同一产物两套执行器 |

实施分四步：**探索**（Agent Loop 读语料、试提示词）→ **编译**（manifest：DAG + 契约 + 内容哈希 + 钉死的提示词）→ **校验**（金标评测、证据校验、人工确认）→ **生产**（调度执行同一产物；决策权不在模型）。

演讲给出的自有实验证据很直接：**把决策权交给模型自主循环的尝试，全部负效**；有界修复环（校验失败带错误反馈重试，有硬上限）可以展开成固定 DAG——这是"可编译"的前提；同一份编译产物，本地 runner（开发态）和平台工作流（生产态）执行同一个 DAG，和 dbt 一个道理。

行业参考两条：Anthropic《Building effective agents》区分 workflow（预定义代码路径）与 agent（模型自主决定过程），能用 workflow 就不要用 agent；dbt 的 compile → manifest → run，开发与生产执行同一份产物。

### 共识二：知识工程 / 蒸馏管线用奖牌架构（Medallion Model）

前提判断是：知识工程本质上是非结构化到结构化的过程，所以整套结构化数据处理技术栈（管线、分层、增量、评估）都能复用。

四条设计要点：三层覆盖全部数据（Bronze / Silver / Gold 兼顾管理性与灵活性）；统一元数据（底层只有一套元数据）；AI 成为新引擎（AI 函数与分析引擎并行）；增量计算让持续更新成为可能（兼顾新鲜度与成本效率）。

收益四句话：灵活性（从原始数据存储到高级分析）；数据质量（每一层逐步提升可信度）；成本效率（把资源花在高价值的 Gold 层转换上）；增量 ETL（分阶段处理，降低复杂度，提升扩展性）。

行业参考是 2024 年 Databricks / Snowflake 面向数据与 AI 的参考架构：同一条 Bronze / Silver / Gold 管道同时处理结构化与非结构化数据，AI 作为新引擎与分析引擎并行——结构化侧走 Delta 持续摄入 + Data Transformation（Snowpark DataFrames / dbt / SQL / UDFs），非结构化侧（Text / Docs / Audio / Images / Videos）走 External Volume → Extract（Document AI / Snowpark / Doc Parse）→ Enrich（Cortex LLM Inference / Sentiment / Categorize），两侧最终汇入 Sharing、Analytics & BI、ML、AI 与 Other Engines（Iceberg REST API）。

### 共识三：评估驱动 + 持续更新——知识平台不是一次性交付

> 没有"今天建成、以后一直对"的知识平台：输出是概率性的，业务又在变——**评估是门禁，更新是常态**。

**从 TDD 到 EDD**：

| | TDD · 测试驱动 | EDD · 评估驱动 |
|--|---------------|----------------|
| 核心逻辑 | 确定性输入 → 确定性输出 | 自然语言输入 → 概率性、动态输出 |
| 时机 | 发布前一次性静态测试，通过即完成 | 覆盖离线开发与线上运行的持续治理 |
| 解决的痛点 | 代码错误、崩溃、性能瓶颈 | "口径对不对""任务完成没有""升级后变好还是变差" |

评估的三件套（案例一、二都在用）：**金标题库**（正向 + 负向双套件，32 + 14 题；等价类 / 变体组评分，消除约定伪影）；**证据校验器**（每条知识引用的表和列必须有据可查；证据不足留空，不猜）；**质量证书**（证书 PASS 才能物化、发布；同尺对照，升级后可比）。

**持续更新的四步**：发现（Trace 持续发生：新文档、新查询、一句"不对，GMV 不含退款"）→ 候选（增量重抽：改 1 篇文档只重抽 1 篇；内容哈希钉住未变的结果）→ 评估（语义变更回标定：金标回归 + 证据校验 + 同尺对照）→ 发布（证书 PASS → 版本 +1；可回滚、可审计、可比较）。

### 共识四：Eco-loop——知识在使用中被持续生产

一个环：**使用 → Trace → 蒸馏 → 评估验证 → 认证入库 → 服务 → 回到使用**。它把前三条共识串成一个运营闭环——越用越准，越用越全。环的三个要点（入口是 Trace 而不是文档；验证是门禁而不是排序；增量而非全量重跑）以及它和 EDD、数据管道的对应关系，见 [[knowledge-eco-loop]]。

## 平台：云器 V2 AI 知识平台

演讲把产品定位为"数据平台的演进，不是另起炉灶"：管线、分层、增量、评估一脉相承，**结构化数据本身就是知识的一部分**。

### V1 → V2

V1 数据基座包括：统一数据基座（Lakehouse）、高性能引擎（10 倍）、通用增量计算（GIC）、解决性能成本与实时性瓶颈、企业级平台全托管。V2 在此基础上叠加六个模块：

| 模块 | 职责 |
|------|------|
| 1 AI-ETL | 持续把原始数据加工成 AI-ready 数据：抽取、清洗、结构化与语义增强 |
| 2 SingSight | AI 可观测与持续评估：Trace、数据集、实验与自动化评估闭环 |
| 3 知识工程 / 蒸馏 | 把数据、文档和 Trace 蒸馏为结构化知识资产，供 Agent 使用、治理与审计 |
| 4 AI 网关 | 统一、模型中立的大模型接入，具备权限、成本控制与审计 |
| 5 Agent 入口 | Data Agent + Analytics Agent 作为主要入口 |
| 6 MCP / CLI 接口 | 标准接口，接入企业已有 Agent 生态 |

V2 架构图里的关键链路是：AI / Agent 数据源（Agent as Co-worker、Agent as Service）与结构化 / 非结构化数据源经 OTel 上报或 mount / upload 接入 → AI-ETL（AI Func / LLM / Embedding / OCR）与 Single Engine 加工 → Knowledge 层（Knowledge Base、Vector Store、Inverted Index、Dynamic Tables，以及 CoALA 三层：Profile / Preference / Entities / Skills / Procedural / Semantic / Episodic Store 与 Semantic Layer：Semantic View、Semantic File Generate）→ BI Tools、Data Analytics Agent（DataGPT）、Data Engineering Agent（in Studio）、SingWork Agent、User Agent 与终端用户消费；底座是 Lakehouse Studio、AI Gateway、Lakehouse MCP Server 与 Lakehouse CZ-CLI。

### 知识的三种服务模式

参考架构是 CoALA（Cognitive Architectures for Language Agents，Sumers 等，TMLR 2024，图 4，CC BY 4.0）——把知识视为 Agent 的显式上下文。演讲把它改写成企业知识三层模型：

| 层 | 内容 | 回答 |
|----|------|------|
| 程序性知识 | 可复用的流程、规则、技能与工具使用模式 | 企业如何行动 |
| 语义知识 | 实体、概念、关系与业务上下文 | 企业知道什么 |
| 情景（原始）证据 | 文档、对话、表、事件与多模态来源 | 让每个抽象都有证据可依 |

对外提供三种服务模式：**语义视图**（面向结构化数据，兼容 Ossie，为分析、BI 和 AI Agent 定义共享的数据集、指标、维度与关系）、**知识图谱**（面向共享的通用对象，领域实体、关系与血缘，支持遍历与推理）、**混合检索**（面向通用知识，向量与标量索引支持抽取、排序与上下文召回）。

### 三个模块，一个闭环

产品映射回 Eco-loop：**AI-ETL 是基础能力**（结构化与非结构化数据的转换和清洗，为上层的可观测与知识建设提供加工引擎）；**SingSight 是数据入口**（全链路可观测与评估，实时捕获交互上下文与真实评估反馈）；**知识工程**用 SingSight 的数据、由 AI-ETL 加工提炼，闭环完成企业知识建设。最佳切入场景：客服 / 销售 Agent、企业知识问答、运维 / 日志分析、产品 / 内容运营。

## 五个观点（Key Takeaways）

1. 知识是数据领域的**第三次革命**，也是企业在 AI 三要素中最大的差异化来源。
2. 知识的表达（本体）目前**没有统一标准**，有五条不同的路线。
3. **Raw Data 不等于 AI-ready Data**：知识需要一个生产的过程。
4. **知识工程的本质，是一个从非结构化到结构化的过程。**
5. 构建知识工程平台，依赖一套**整体的基础设施**。

## 经验与边界

- **路线不是标准**：五类系统是五种建模模型，不是同一标准的五个实现；把它们放在一条"保证 ↔ 自由"的轴上比较才有意义。
- **排序不等于验证**：Genie 路线用排序补长尾上下文，但认证真值仍需强 Schema 的语义内核；Agent Memory 同理，只能承担个体上下文。
- **验证查询路线的天花板**：理论上限 50.8%（查询里出现过的关系才可能被蒸出），必须与 Trace、文档互补。
- **案例口径**：案例一读数为公开基准实测（experiments/OVERALL_REPORT.md）；案例二读数为内部评估（V2_REPORT §3.10 及生成缓存 gen_runs_v2.jsonl，repeats = 3，2026-09），实验中模型直读 SV 文本并自写 SQL、未走引擎编译路径，属保守下限，客户名称与表名按约定脱敏。演讲未说明两案例的样本选取方式与统计显著性。
- **演讲未标注的信息**：本 PDF 未写具体分论坛场次、日期与客户名单；案例二客户仅以"某头部内容平台"出现。上述空白不做推断。
