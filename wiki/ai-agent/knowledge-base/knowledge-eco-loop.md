# Eco-loop：知识在使用中被持续生产

> **核心主张：知识不是一个"建成之后就一直对"的项目，而是一个环——使用产生 Trace，Trace 蒸馏为知识，知识回到使用，越用越准、越用越全。** 环的入口是 Trace 而不是文档；评估是门禁而不是排序；更新是增量而不是全量重跑。

本页整理自关涛（云器科技）在 DACon 2026 北京站的演讲《从数据工程到知识工程》第三、四章，是该演讲提出的第四条架构共识，也是第五章三个产品模块的映射依据。

## 环的六个节点

| # | 节点 | 做什么 |
|---|------|--------|
| 1 | 使用 | 人 / Agent 提问、纠正、确认 |
| 2 | Trace | 全链路记录交互与上下文 |
| 3 | 蒸馏 | AI-ETL：抽取口径、关系、流程 |
| 4 | 评估验证 | 金标、证据校验、人工裁决 |
| 5 | 认证入库 | 语义视图 / 图谱 / 记忆 |
| 6 | 服务 | BI、Agent、RAG 消费 |

第 6 步的消费又回到第 1 步的使用，环闭合。演讲用一张六节点环图表达"越用越准，越用越全"，并给出三个要点。

## 三个要点

### 1. 入口是 Trace，不是文档

> 知识的供给来自真实使用，不要求人额外写东西；**程序性知识只在这里看得见**。

这与"知识的三层供给"一致：已经写下来的（文档、Wiki、制度、SOP）蒸馏不难；在系统里的（查询、Dashboard、代码、配置）要从使用痕迹归纳；在**人脑子里的**（口径、经验、判断、习惯性流程）量最大、最难，人自己也没意识到该写出来。Trace 是唯一能覆盖第三层的原料。

演讲的原句把两次革命并列：

> 第二次数据革命的原料是 Log（人的行为），第三次数据革命的原料是 Trace（人的认知）。

Trace 里常见的五类线索，正是蒸馏的输入信号：

| 线索类型 | 例子 |
|----------|------|
| 指标口径纠偏 | "GMV 不应该包含退款" |
| 时间口径纠偏 | "按支付时间，不是创建时间" |
| 过滤条件补充 | "要排除测试商家" |
| 同义词补充 | "成交额就是 GMV" |
| 关联关系补充 | "订单表按 store_id 关联门店表" |

### 2. 验证是门禁，不是排序

> 金标题库 + 证据校验 + 质量证书：通过才发布。**排序（Genie 路线）补长尾，不裁决真值。**

评估三件套与环上的第 4 个节点一一对应：

| 组件 | 作用 |
|------|------|
| 金标题库 | 正向 + 负向双套件（案例中为 32 + 14 题）；等价类 / 变体组评分，消除约定伪影 |
| 证据校验器 | 每条知识引用的表和列必须有据可查；证据不足留空，不猜 |
| 质量证书 | 证书 PASS 才能物化、发布；同尺对照，升级后可比 |

这也解释了为什么"评估驱动（EDD）"是知识平台的默认开发范式，而不是可选项——见 [[edd-evaluation-driven-development]]。

### 3. 增量，而非全量重跑

> 改一篇文档只重抽一篇；语义变更回标定、重编译、版本 +1——和数据管道一样。

这与奖牌架构（Bronze / Silver / Gold）和通用增量计算是同一套思路：内容哈希钉住未变的结果，只重算变化的部分；版本、回滚、审计沿用数据工程的做法。知识平台因此可以和数据管道共用一套调度与治理，而不是另建一个"AI 系统"。

## 与数据管道同构的四个动作

演讲把"持续更新"拆成四步，每一步都能在数据工程里找到对应物：

| 步骤 | 做什么 | 数据工程里的类比 |
|------|--------|-----------------|
| 发现 | Trace 持续发生：新文档、新查询、一句"不对，GMV 不含退款" | 新分区到达 |
| 候选 | 增量重抽：改 1 篇文档只重抽 1 篇；内容哈希钉住未变的结果 | 增量 ETL |
| 评估 | 语义变更回标定：金标回归 + 证据校验 + 同尺对照 | 数据质量门禁 / 回归测试 |
| 发布 | 证书 PASS → 版本 +1；可回滚、可审计、可比较 | 表版本 / 快照发布 |

一句话总结：

> 知识平台不是一次性的软件交付：没有"建成之后就一直对"——**评估是门禁，更新是常态**，和数据管道一样增量、版本化、可回滚。

## 开发期与生产期的分界

环上的"蒸馏"节点在开发期与生产期是两种形态（详见 [[data-to-knowledge-engineering]] 的"共识一"）：

- **开发期**用 Agent Loop 探索语料、标定提示词、定契约与校验规则；
- **生产期**跑确定性 Pipeline：模型只做抽取（有界算子：投票 + 修复上限），流程由编译产物（DAG）决定，同一份产物在本地 runner 与平台工作流上执行同一个 DAG。

也就是说：**模型仍在管线里工作，但不再做流程决策。** 这是环能稳定运转的前提——否则环上的成本、时延与结果都不可预测。

## 产品映射：三个模块，一个闭环

演讲把环映射到三个产品模块：

| 环上的职责 | 模块 | 说明 |
|-----------|------|------|
| 使用 → Trace → 评估 | **SingSight** | 数据入口：全链路可观测与评估，实时捕获交互上下文与真实的评估反馈 |
| 蒸馏 | **AI-ETL** | 基础能力：结构化与非结构化数据的转换和清洗，为上层的可观测与知识建设提供加工引擎 |
| 认证入库 → 服务 | **知识工程** | 利用 SingSight 的数据，由 AI-ETL 高效加工提炼，闭环完成企业知识建设，形成核心数字大脑 |

三个模块的关系：SingSight **提供反馈数据入口**给知识工程；知识工程**反哺优化引擎**（回到 AI-ETL）；AI-ETL **支撑观测与评估**。

> 为什么是这三个模块？因为 Trace（SingSight）、蒸馏（AI-ETL）、认证与服务（知识）正好构成 Eco-loop。

最佳切入场景：客服 / 销售 Agent、企业知识问答、运维 / 日志分析、产品 / 内容运营。

## 两个实例在环上的位置

演讲的两个案例正好演示环的两端：

- **案例一（验证查询 → 语义视图）**：原料是"业务问题 + SQL"这类使用痕迹，属于第 2 个节点；产物是语义视图条目，进入第 5 个节点。它的理论上限是 50.8%（只能蒸出查询里出现过的关系），说明单靠存量痕迹不够，必须叠加 Trace 与文档。
- **案例二（业务文档 → 语义视图）**：原料是已写下来的文档（三层供给里"最容易"的一层），走的是"抽取 → 转换 → 索引 → 评估 → 服务"管线；它证明整理成结构化语义视图后，准确率、token、时延可以同时变好。

两个案例的完整数字与边界见 [[data-to-knowledge-engineering]]。

## 经验与边界

- **环的入口决定知识结构**：以文档为入口，得到的是"文档摘要"；以 Trace 为入口，才能拿到口径、偏好与程序性知识。两者不可互相替代。
- **门禁与排序是两种保证**：排序能补长尾覆盖，但它"不等于验证"；把排序当裁决，等于把组织真值交给一个相关性分数。
- **增量依赖内容哈希与契约**：没有钉死的提示词、契约与哈希，所谓"只重抽一篇"就无法保证结果一致。
- **演讲未给出的内容**：环的运转指标（如 Trace 覆盖率、候选采纳率、知识更新周期）、单条知识的成本模型、以及多租户下的权限与隔离方案。本页不做推断。
