# 非结构化文档解析与样式还原

> 核心主张：**解析决定知识库的天花板，还原决定二次编辑的体验。** 通用文档解析与页面样式还原都可以用偏工程的 Pipeline 方法，也可以用侧重模型能力的多模态方法；孰优孰劣要看具体场景。解析没有万能流水线，只有随场景重排的协同组合拳；还原样式不是复刻像素，而是重建结构。

演讲来源：DACon 2026 北京站「非结构化数据处理与知识获取」专场，常鸿宇（360 人工智能研究院 算法资深工程师）。讲者从事 NLP 研究 6 年，方向为信息抽取、多模态内容理解、非结构化文档解析；参与文档智能工作 2 年余，相关系统支撑集团内部多项业务及航空、制药、交通等政企项目十余项。

## 背景与问题

### 两个应用场景：服务对象不同，结构化目标不同

| 维度 | 知识库问答 | 文档二次编辑 |
|------|-----------|-------------|
| 场景定义 | 根据用户提供的场景（文档），为 LLM 提供相关信息以对用户 Query 进行响应 | 将一个 PDF 文档转为可以编辑的 Docx 文档，以供用户二次编辑，或支持文档原位翻译等后续处理能力 |
| 结构化服务对象 | LLM | 人类 |
| 文档结构化目标 | 内容信息完整；结构化表示恰当 | 内容完整；样式准确 |
| 挑战 | 解析的内容完整准确；内容信息的完整性，结构化过程中不能丢失原本蕴含的信息；不同元素如何进行恰当的结构化表示，如表格、公式、图片 | 如何保障生成的 Docx 文档「结构合规」；如何保障生成的 Docx 文档「视觉相似」 |

两者共享同一个底层能力，但优化目标相反：知识库问答追求「语义可检索、结构可拼接」，二次编辑追求「版式可还原、结构可编辑」。

### 元素/场景差异：同一元素，两种处理策略

| 元素 \ 场景 | 知识库问答 | 文档二次编辑 |
|------------|-----------|-------------|
| 文本样式 | 不需要保留 | 需要保留 |
| 图片 | 需要对图片内容提炼 | 原位插入即可 |
| 表格 | 表达表格结构即可（HTML） | 需要表格样式（色彩边框） |
| 公式 | LaTeX 表达式 | 需要将公式渲染 |
| 页眉页脚/侧边文字 | 去除 | 按格式恢复 |
| 线条/LOGO/ICON | 去除 | 按位置插入 |
| 水印 | 去除 | 作为背景插入 |
| 层次结构/阅读顺序 | 需要 | 不需要 |

这张表是后续所有组件取舍的依据：同一个版式分析模型，面向 RAG 时只关心「正文/标题/表格/图片」等语义块；面向 Docx 还原时还要保留线条、LOGO、ICON、下划线文本、删除线文本等「对人重要、对 LLM 无关」的细节。

### 在 RAG 链路中的位置

讲者把通用文档解析放进一条 8 步 RAG 流水线：

- 离线阶段：1. 文档解析（Data Ingestion）→ 2. 文本分块（Chunking）→ 3. 向量化嵌入（Embedding）→ 4. 向量索引存储（Vector Database）。
- 在线阶段：5. 查询处理与路由（Query Processing）→ 6. 检索召回（Retrieval）→ 7. 上下文注入/提示构造（Prompt Engineering）→ 8. 大模型生成（LLM Generation）。

通用文档解析的目标被定义为「将非结构化的输入结构化、序列化」，技术要求是「文档转 Markdown」。讲者用一句话强调其权重：**「解析错一厘，生成误千里。」**

## 方案/架构

### 三条技术路线

| 路线 | 架构 |
|------|------|
| Pipeline 式 | 输入文档 → 布局分析组件 → 图片处理/表格处理/公式处理/文本处理等子模块 → Markdown 结果 |
| End2End 式 | 输入文档 → 内容生成组件 → Markdown 结果 |
| 复合式 | 输入文档 → 布局分析组件 → 内容生成组件（统一模型利用不同 Prompt 生成对应 Markdown）→ Markdown 结果 |

### 三条路线对比

| 对比维度 | Pipeline 式 | End2End 式 | 复合式 |
|---------|------------|-----------|--------|
| 技术方案 | 多模块串联：布局分析 → 各子模块处理 → 拼接成完整 Markdown | 端到端生成：页面图片直接生成 Markdown | 布局分析模块与统一生成模型配合：布局分析 → 统一模型利用不同 Prompt 生成对应 Markdown |
| 优点 | 各模块独立，可分别优化；效果总体可控，通常不会出现灾难性错误；各子模块可并行处理，执行效率高；可采用小模型快速搭建流程，对计算资源要求通常较低 | 流程简单，易于维护；生成式 LLM 对零样本的泛化能力，可以处理复杂场景；避免长流程导致的错误累积风险 | 布局分析模型和生成模型独立；可通过部署多节点，同时处理一个页面的不同组件，效率优于 End2End；生成式模型可以直接处理复杂场景，如文本中混杂公式 |
| 缺点 | 存在错误累积风险；系统相对复杂，维护成本高；处理逻辑复杂，如文本中混杂公式、表格嵌套图片、表格嵌套表格的逻辑处理 | 极大依赖 LLM 自身效果，存在幻觉风险，复杂场景下效果不可控；内容生成模型兼具布局分析任务，优化难度高；计算资源要求较高 | 存在错误累积风险；生成模型组件同样存在幻觉风险；计算资源要求较高 |

## 关键工程做法

### 1. 预处理增强与去水印

- **拍照版文档**：会出现褶皱、透视等问题，直接接入后续处理会出问题，因此往往需要先做文档增强预处理。流程图给出「图像输入 → 文档提取 → 手指去除 → 形变矫正 → 图像增强」。
- **水印去除**：水印会对页面 OCR 等步骤构成干扰，对 RAG 来说属于无效信息，因此在预处理阶段需要去除。
- 效果：在 **828 个页面**构成的 Benchmark 中评测，水印去除给文本 CER 带来的收益为 **0.092 → 0.071**；错误识别到的水印图片数量为 **32 → 0**。

### 2. 页面布局分析

- 版式分析本质上是一个**目标检测任务**，用于对文档进行区域划分，核心在于标签的定义：正文、标题、图片、图片标题、表格、表格标题、页眉、页脚、注释、公式。
- 真实文档错综复杂，包括无线表、跨页表格、页眉、页脚、公式、图像、印章、流程图、目录树等，需要做到**不漏检、不错检、识别准确**。
- 主流方案包括 doclayout、pdftool-kit。
- 讲者给出开源地址：
  - `https://github.com/360AILAB-NLP/360LayoutAnalysis`
  - `https://huggingface.co/qihoo360/360LayoutAnalysis`
- 核心问题：「版式分析模型与文档类型强相关，本质上需要文档标注的多样性以及粒度控制。」

### 3. OCR 与公式解析

**Pipeline 方案**：

1. Layout 解析出文本行、行内公式和行间公式；
2. 文本行交给 OCR 模块处理；
3. 行内公式和行间公式交给公式解析模块处理；
4. 按照坐标对解析出来的内容进行排序，拼接成完整 Markdown。

**End2End 方案**：直接将整段图片提供给多模态模型，多模态模型直接给出完整 Markdown 结果。

Benchmark 上 formulaNER 指标表现（幻灯片标注为「参考」）：

| 方案 | formulaNER |
|------|-----------|
| Pipeline 方案 | 0.178 |
| End2End 方案 | 0.182 |

### 4. 表格解析

**Pipeline 方案（传统方案）**：

1. 表格检测与表格分类（有线/无线/缺线）；
2. 表格单元格检测/框线检测；
3. 单元格文字 OCR；
4. 单元格内容与结构匹配；
5. 生成 HTML。

**End2End 方案（多模态方案）**：输入表格图片，模型直接生成对应的 HTML。

Benchmark 上 TEDS 指标效果表现（幻灯片标注为「参考」）：

| 方案 | TEDS |
|------|------|
| Pipeline 方案 | 0.753 |
| End2End 方案 | 0.921 |

讲者的判断：「从指标上看，后者由于没有误差累积，效果明显优于前者，但前者在一些复杂场景上（表格嵌套、纵向表格、图片插入、复杂样式等）定制化更加灵活。」

幻灯片左侧还展示了一张表格识别模型对比表，按 **OCR-based Models、Expert VLMs、General VLMs** 分组，列出 PaddleOCR、RapidTable、StructEqTable、GOT-OCR、Qwen2.5-VL-7B、InternVL2-8B 等模型在 Language、Table Frame Type、Special Situation、Overall 等维度的得分；该表为引用截图，讲者未逐项解读。

### 5. 阅读顺序与层次结构分析

**阅读顺序分析**：对每个元素的先后顺序进行排序，对于多栏文档和复杂样式场景至关重要。在 Benchmark 的多栏场景文档中，**若不进行阅读顺序分析，会导致 CER 从 0.130 → 0.479**。

**层次结构分析**：判断每个元素的父节点，可用于文档结构分析、层次结构召回等。在保持准确率的基础上，**可减少约 15%–40% 的召回上下文篇幅**，召回的相关段落从「位置上的上下文」变为「逻辑上的上下文」。幻灯片引用 DocHieNet（Xing, et al., 2024）。

### 6. 段落/表格跨页合并

- **表格合并**：相邻两页中表格因受限于页面大小而被截断为多张。关键特征：表格坐标位置、单元格宽度、表头检测、内容语义连贯性。
- **段落合并**：多见于多栏场景、跨页场景，或论文中正文内容被图表分隔。关键特征：阅读顺序连贯、内容语义连贯性。
- 效果：Benchmark 中涉及跨页段落和表格的样本，采用合并策略后：
  - 文字 CER：**0.120 → 0.082**
  - 表格 TEDS：**0.770 → 0.881**

### 7. 图片处理与垂直场景定制

讲者按图片种类给出不同处理策略：

| 图片类型 | 处理方式 |
|---------|---------|
| 文字型图片 | 提取其中的序列化文字内容 |
| 普通图片 | 生成图片 Caption |
| 图表型图片 | 解析成结构化 JSON 以表示图表中蕴含的信息 |
| 特定场景（例如电路图） | 元器件识别 → 属性识别 → 属性元器件匹配 → Netlist 生成 → Netlist 提供给 LLM |

实现上，在 Layout 阶段对不同图片设置不同的标签，或增加一个图片分类路由。讲者强调「解析没有万能流水线，只有随场景重排的协同组合拳」。

**Bad case**：图片处理不当导致内容丢失。PDF 中以图片类型插入了部分内容（例如地形分类的正文），若将其视作普通图片处理，则会导致关键参考信息缺失，从而无法正确回答用户的问题。

## 从 PDF 到 Docx：页面样式还原

### 三条路线：视觉相似 vs 结构合规

| 对比维度 | 原位插入式 | Pipeline 式 | End2End 式 |
|---------|-----------|-------------|-----------|
| 技术方案 | 直接 PyMuPDF 之类的工具，读取 PDF 文档中各元素的坐标信息和内容，按照规则插入到对应位置 | 多阶段处理：先做布局分析，用布局分析的结果对 PDF 本身的信息进行重组 | 页面图片直接生成 Docx 对应的代码，由代码执行生成文档 |
| 优点 | 视觉还原度高；整体方案较轻，效率高 | 页面布局分析得到确定性坐标，视觉还原度有一定保证；对于扫描件，仍然可以采用 OCR 等技术获取其中文字内容；执行效率通常比生成式方法高 | 流程简单，易于维护；生成式 LLM 对零样本的泛化能力，可以处理复杂场景；避免长流程导致的错误累积风险；可以处理扫描件 |
| 缺点 | 无法处理扫描件（图片型 PDF）；依赖 PDF 本身信息的丰富程度和准确性；无法保证二次编辑结构合规 | 流程过长会导致误差累积；为了追求还原细节，加入过多规则会造成规则之间的互相干扰，维护难度大；无法保证生成的 docx 保持一页 | 推理时间较长；生成模型存在幻觉风险；计算资源要求较高 |

讲者的判断是：「还原样式，不是复刻像素，而是重建结构。」

### Pipeline 式方法：内容组件

- **布局分析**：区别于面向 RAG 系统的文档解析，页面样式还原对布局分析的要求更加细节。例如：需要将页面中的线条、LOGO、ICON 等元素保留，需要对下划线文本、删除线文本等特殊样式的文本进行标记。
- **背景分离**：将页面的背景单独生成图片置于 Docx 底层。
- **字体匹配/预测**：文字型 PDF 读取字体信息，与可用字体进行匹配；扫描型 PDF 对字体进行分类预测。
- **色彩预测**：对文本或表格单元的前景色、背景色进行预测。

### End2End 方法：生成内容的选择

| 方式 | 优点 | 缺点 |
|------|------|------|
| python-docx | 封装了常用的 docx 操作接口，例如插入段落、插入图片、段落样式、文本样式设置等；语言简练 | 很多功能不支持，如图片悬浮格式设置等 |
| XML | 每个 docx 文档都是一个 zip 文件，可以解压看到其中的文件内容，由若干 XML 文件构成；可以进行非常细节的设置 | 内容过长，不适合直接用于 LLM 生成 |

**融合方案**：大部分操作采用 python-docx，不支持的操作自定义函数封装 XML。与此同时，自定义方法可以减少训练和推理过程中的 token 数量，加速训练和推理。

幻灯片列出的自定义方法包括：

| 自定义方法 | 功能 |
|-----------|------|
| clear_table_borders | 清除表格边框 |
| set_cell_margins | 设置单元格边距 |
| set_run_format | 设置 run 格式 |
| insert_line | 插入线条 |
| insert_toc | 插入目录 |
| insert_inner_table | 插入嵌套表格 |
| … | … |

## 数据与效果

### 页面样式还原 Benchmark

- **规模**：1450 个页面，10 类文档。
- **语言分布**：Chinese 665、English 669、Mixed 82。
- **栏数分布**：Single 1031、Double 369、Multi 50。
- **文本样式统计**：Bold 1047、Italic 387、Underline 161、Colored 429。
- **页面元素统计**：Tables 440、Images 656、Headers 593、Footers 710。
- **评估维度**：内容、样式、结构、全局（栏数、还原成功率等）4 个大维度。
- **评估难点**：标准统一难；GT 构建难；权重设置存在主观性。

|---------|---------|
| Gemini 3.1 Pro | 0.429 |
| GPT-5.6 Terra | 0.479 |

## 经验与边界

### 样式还原的四个 case

| Case | 问题 | 解决方法 |
|------|------|---------|
| case1：段落划分错误 | 即便还原效果看起来与原 PDF 相似，但逻辑上却将本应是同一段的文本划分为多段 | 针对特定场景优化 layout 模型 |
| case2：下划线文本难以恢复 | 原 PDF 中部分文字带有下划线，但通过 PyMuPDF 读取到的信息丢失了该信息，将其记录为普通文字 | 在 layout 模型类别中增加一类「下划线文本」类型 |
| case3：页眉页脚的位置难以控制 | 页眉/页脚区域只能插入一个 paragraph，元素过多时位置难以精确控制 | 插入表格，以表格单元格宽度控制文本的位置 |
| case4：流式插入文本 vs 绝对位置图片 | Docx 中段落的插入是流式的，很难做到百分百位置对齐；图片/线条若以绝对坐标插入，则会与段落之间存在高度差 | 在插入图片/线条时锚定邻近的段落，计算相对位置 |

### 两个困难 case

| 困难 case | 问题 | 边界 |
|----------|------|------|
| 困难 case1：加粗文本信息丢失 | 如果 PDF 内置信息中丢失了加粗信息，难以对加粗文本进行恢复；逐个文字进行分类判断计算成本大，并且在扫描件场景下会出现大量错判 | 属于 PDF 源信息缺失导致的不可逆问题 |
| 困难 case2：文本框的使用在所难免 | 受限于 Docx 本身的能力，对于一些复杂文档（例如杂志、报纸），只能采用文本框来控制字体的位置 | 属于目标格式能力边界 |

### 总结判断

- **通用文档解析**：
  - Pipeline 方案：可针对性优化各子模块，但模块间误差累积问题突出；
  - 多模态方案：端到端能力强，但在细粒度结构还原（如表格单元格坐标属性等）上仍有不足。
- **页面样式还原**：
  - 工程化方法：生成的 Word 文档在视觉上与原始 PDF 相似，但 Word 文档的底层结构规范合规性较差；
  - 多模态方案：流程简单、易于维护、避免误差累积，但还原度细节对模型能力要求较高。
