# 双层架构：Super-agent 的 Router 层与 Worker 层

[[super-agent]] 要同时做到跨信道的连续交互与多任务的高效并发，底层会话组织就必须回答一个根本权衡：**连续性与吞吐量**。

## 权衡：为什么必须分层

| 方案 | 连续性 | 吞吐 | 问题 |
|------|--------|------|------|
| 所有事件交给同一个 Session | 最高 | 低 | 受单个 ReAct Loop 串行速度上限约束，任务耗时长；多任务中间细节混杂，影响完成效果 |
| 每条事件新开独立 Session | 低 | 最高 | 任务之间不完全独立时缺少全局上下文，结果彼此割裂；多个 Session 各自向用户响应造成交互混乱 |
| **双层：Router + Worker** | 由 Router 统一维护 | 由 Worker 并发提供 | 把"维护全局连续性"与"高并发执行"拆到两个层级 |

```
IM ─┐
GitHub ──┼──► Router 层（共享上下文，路由与交互）──┬──► Worker Session 1（隔离上下文）
邮件/日程 ──┘                                      ├──► Worker Session 2（隔离上下文）
                                                   └──► Worker Session 3（隔离上下文）
```

通过双层架构，系统在底层接管了上下文管理与并发执行，从而在用户侧**淡化 Session 的存在**：用户面对的始终是同一个 Super-agent。

> 让用户手动管理 Session，在很大程度上是从底层 LLM API 延续下来的设计惯性；Session 应当是系统的实现细节，而不应是用户的认知负担。

原文进一步指出：现有设计中 Session 同时承载了技术上的上下文管理与面向用户的项目管理；把产品形态与底层 Session 解耦后，**向用户暴露怎样的交互与任务管理方式成为一个独立的产品问题**（见 [[super-agent]] 的开放问题 8.2）。

注意："双层"是**逻辑上的职责划分**，每一层在实现上都不必局限于单个 Session，可以各有内部结构。

## Router 层：常驻的全局序点

| 属性 | 设计 |
|------|------|
| 定位 | 常驻的全局路由层，承接**所有入口**的人类交互 |
| 职责 | 所有跨任务的信息与决策在此汇总，充当全局的**序点（Sequence Point）、协调点和记忆** |
| 边界 | 设计上**不直接执行具体任务**，只负责人类交互与任务分派；甚至可以不配备 Bash 工具——避免这个全局节点成为性能瓶颈 |
| 模型选择 | 任务常常没有想象中复杂，**较轻量的模型**往往就能兼顾速度与效果 |
| 实现 | 原文选择最直接的**单个常驻 LLM Session** 作为 Router 层的核心实现 |
| 扩展 | 规模扩大后可设计为多层过滤结构，或水平切分（Sharding）为多个会话 |

### 与 Agent Team 的区别

同样是"中心节点 + 多个执行节点"，两者侧重不同：

| 维度 | 常见 Agent Team | Super-agent 的 Router 层 |
|------|----------------|--------------------------|
| 用途 | 单个复杂任务内部的步骤拆解与角色协作 | 多个任务之间的高层关联与分派 |
| Lead 负载 | 子步骤耦合紧，Team Lead 需深入理解任务细节、规划子任务、高频协调，自身承担很重的推理负载 | 不介入单任务内部拆解，只做高层分派 |
| 关系 | — | 如果用提示词约束 Agent Team 的主会话"不亲自执行、只对外交互并把任务分派给各成员独立推进"，它也可以视为这种双层架构 |

### 批处理：为什么单个 Router Session 不一定是瓶颈

上一轮推理期间到达的环境事件（Trigger）会**积压下来、在下一轮一并处理**，形成批处理（Batching）：

- 事件流平稳时，Trigger 逐条进入 Router Session，单次响应延迟低；
- 事件密集涌入时，积压的多条 Trigger 在下次 LLM 调用中一并注入。Router 每步通常是"长输入、短输出"，多条 Trigger 合并进一次 API 调用会在 **Prefill 阶段并行计算**，单次请求耗时的增长远慢于批处理大小。

因此在一定范围内，**积压越多，单个决定分摊的推理时间越低**；上限取决于上下文长度，以及模型在一轮中能准确处理多少条 Trigger。加上订阅直通（见 [[agent-event-driven-triggering]]）与链式召回（见 [[inline-and-spill]]），单个常驻 Router Session 在原文团队规模下已经够用。

### 切分的代价

当规模进一步扩大、单个会话确实不足以承载时，Router 层内部可以多层过滤或水平切分。此时 Router 层的内部设计本质仍是连续性与吞吐量的权衡：**切分粒度越细，并发吞吐越高，但分片之间的记忆与上下文连续性越低**。原文判断：在全局记忆问题被解决之前，这一权衡始终存在。

## Worker 层：隔离上下文的具体执行者

| 属性 | 设计 |
|------|------|
| 定位 | 负责具体执行的会话，彼此上下文隔离，挂载**完整的执行工具**，在独立上下文中专注完成单一任务 |
| 模型选择 | Worker Session 直接决定任务结果与代码质量，通常配置**能力最强的模型** |
| 对外交互 | **不直接与人类交互**：推理过程和工具调用不直接输出到外部信道，而是向 Router 层汇报状态，由 Router 统一向用户回复——既保障并发度与交付质量，又避免多个会话各自回复造成混乱 |
| 同层通信 | 同层 Worker 之间通常**不需要直接通信**。冲突多出现在同一个 Pull Request 等共享工作环境中，只要它们都订阅了对应 Thread，就会收到相同事件通知，从而有机会自行发现和解决冲突；少数跨任务协同由 Router 中转 |
| 内部结构 | 每个 Worker 内部可以再创建 Subagent，本身也可以是一个 Agent Team，这些对上层 Router 保持透明 |

适用面覆盖两类场景：

- **代码协作**：同时推进多个独立的问题复现、Pull Request 评审与特性开发而互不阻塞；
- **个人助手**：界面通常只给一个单会话聊天页，但当用户在同一对话框里同时讨论多个话题时，前端单一聊天页维持交互连续性，底层为每个话题分别分派 Worker，并行推进任务、起草回复。

## 实验 7.1：四方案消融

**设置**：用群聊和 GitHub CI 消息流同时驱动四种端到端方案。单次实验约 300 条消息，其中约 20 条是工作请求，其余是闲聊、跟进、叫停和 CI 消息。编码工作用一个只消耗时间的工具代替——**实验衡量的是系统的调度与协作能力，而非对单个任务的执行能力**。每种方案重复运行 5 次；消息间隔与工作时长按 1/4 缩放，模型调用耗时为真实值；任务完成时间指从工作请求到结果消息的耗时。

四种方案：Super-agent、去掉直通的 Super-agent、单 Session + Subagent 工具（中性提示）、单 Session + Subagent 工具（提示优先委派）。两段提示词原文：

> 中性提示：`Use a subagent for a piece of work when appropriate...`
>
> 提示优先委派：`Every message of the chat reaches you, so work you run yourself keeps stopping for new messages. Prefer handing each piece of work to a subagent of its own, and do only small things yourself...`

| 方案 | 任务完成时间 P50 / P95（分钟） | 单次实验读缓存 Token（全部 Session） |
|------|-------------------------------|--------------------------------------|
| **Super-agent** | **12.4 / 15.7** | 2323 万 |
| Super-agent，去掉直通 | 12.6 / 15.5 | 3177 万 |
| 单 Session + Subagent 工具，中性提示 | 20.4 / 29.5 | 605 万 |
| 单 Session + Subagent 工具，提示优先委派 | 13.8 / 29.0 | 1082 万 |

**为什么带 Subagent 的单 Session 更慢**：它受提示词影响极大。中性提示下，模型 5 次运行中**一次都没有调用 Subagent**，所有工作都在主 Session 中进行并不断被新消息打断，p95 达到 29.5 分钟；改为优先委派后，5 次中有 4 次进行了委派，完成时间有所缩短但仍慢于 Super-agent，剩下的 1 次它判断工作"很小"而选择自己执行，形成原文图中那条紫色长尾。

> 相比于在单 Session 中依赖提示词工程和模型临场判断分不分工，双层架构通过让 Router 不直接执行具体工作、Worker 仅接收所订阅 Thread 的消息，在系统层面上缓解了这一问题。

**开销上的取舍**：由于维护了多个独立会话，Super-agent 单次实验的读缓存 token 高于单 Session（2323 万 vs 605 万 / 1082 万）——是**以更多的 token 消耗换取更短且更稳定的完成时间**。

**直通机制的价值**：在 Super-agent 内部去掉直通后，任务完成时间与完整版基本一致（12.6 / 15.5 vs 12.4 / 15.7），但单次实验中 Router 需要做出的决定增加了约 **30%**，总读缓存 token 从 **2323 万增加到 3177 万，增幅约 37%**。原文结论：在实验负载下，直通机制不提高任务完成质量与速度，但为 Router Session 节省了可观的 token 与推理开销。

## 实验 7.2：Router 层批处理压测

**设置**：Router 调用真实模型、Worker 使用 Mock 模型，把需要决定的 Trigger 到达速率从每分钟约 1 条逐步提升至约 40 条，观察平均 batch 大小、单次请求耗时与单个决定分摊的推理时间。

| 指标 | 约 1 条/分钟 | 约 40 条/分钟 |
|------|-------------|--------------|
| 平均 batch 大小 | 1.0 | 2.8 |
| 单次请求耗时 | 2.5 秒 | 3.9 秒 |
| 单个决定分摊的推理时间 | 6.4 秒 | 1.6 秒 |

单次请求耗时的增长明显慢于 batch 增长，于是**单个决定的分摊推理时间随拥堵反而下降**。这解释了 7.1 中即使去掉直通使 Router 峰值负载增加，仍未触及单 Router 的吞吐瓶颈；原文据此判断：在其团队规模下，无需过早对 Router 层做水平切分而牺牲全局上下文的连续性。

## 实验的边界

两节实验都基于**合成负载与简化环境**，原文自述"部分设置还可以更加严谨，以下结果仅作为初步参考"。其中：任务执行能力被一个只消耗时间的工具替代，因此不反映真实编码任务的耗时分布；消息间隔与工作时长按 1/4 缩放。
