# 从 Harness 到后训练：GUI 测试执行 Agent 的领域优化实践

> 来源：DACon 2026 北京站「模型适配与效果优化：从语义上下文、Harness 到后训练」专场，讲者詹伶俐。PDF 共 38 页。

> 核心主张：领域 Agent 优化不是"Harness 还是后训练"的二选一。先定位问题落在哪一层——知识不知道用 RAG/本体，编排、约束、状态、校验不成立用 Harness，跨页面复用的行为模式才交给后训练。模型不是 Agent，闭环才是 Agent；Harness 是把输入、动作、状态、验证和恢复变成可控工程接口的脚手架。

## 背景与问题

演讲开篇即声明：**"用 Harness 还是后训练"是一个开放性、且在持续技术演进的问题——不同时间点、场景与需求，答案并不相同**。本分享不聚焦"如何做 GUI 测试执行 Agent"，而是借这一案例提供领域 Agent 优化的思考与经验参考。

选择 GUI 测试执行 Agent 作为案例，有两个原因：

1. **GUI Agent 是典型倚重 Harness 的任务**：操作链路长、界面反馈即时，能力上限很大程度由提示、工具与流程编排等 Harness 决定。
2. **测试任务天然具备丰富场景数据**：相比单纯 GUI Agent，测试案例天然沉淀了大量真实、可复用的场景（测试案例）数据。

分享的两条主线：

- **主线一**：通过 Harness Engineering 优化领域 Agent——从提示、工具、记忆与流程编排入手，系统性打磨领域 Agent 的工程外壳。
- **主线二**：领域 Agent 如何做模型后训练——破局"你先给我十万条优质数据"，探索低成本、可落地的数据与训练路径。

### Agent 的本质：模型不是 Agent，闭环才是 Agent

讲者给出的定义：

```
Agent = 模型能力 + 上下文 + 工具 + 状态 + 反馈 + 约束
Harness = Loop Maintenance：循环调用模型，直到模型不再调用工具并返回文本
```

- Harness 是 Agent 的脚手架，把输入、动作、状态、验证和恢复变成可控的工程接口。
- 模型每一轮只有两个决定：**调用工具 / 不调用工具**。
- 参考架构图（第 11 页）把环境、Agent Loop 与自进化模块画在一起：Manager（A_M）接收输入并做高层计划，Operator（A_O）执行，Action Reflector（A_R）判定动作是否有效，Notetaker（A_N）记录进度与笔记；连续错误时向上 escalate 给 Manager；Self-Evolution Module 通过 Experience Reflectors（A_ES、A_ET）把完整动作历史沉淀为 Shortcuts 与 Tips 长期记忆，再更新回 Agent。图中还标出 Mobile Device 的 `s_t` / `s_t+1` 状态与低层动作 `a_t`。该页只有架构图，讲者未逐模块展开。

### 三类能力，三种优化位置

| 方案 | 主要解决什么 | GUI Agent 测试执行中的典型问题 |
|------|-------------|------------------------------|
| RAG / 本体 | 知道什么 | 业务规则、页面语义、测试数据、领域知识如何被检索和注入 |
| Harness | 怎么被约束地执行 | 任务编排、工具 schema、状态同步、动作校验、异常恢复、输出验证 |
| 后训练 | 模型内化什么行为模式 | 跨页面复用的任务分解、工具策略、状态判断和恢复能力 |

讲者的判断规则：

- **如果问题来自编排、约束、状态或校验，优先在 Harness 侧解决。**
- 知识库再完备，仍然是静态的；Agent 的稳定性来自可观察、可验证、可恢复的交互闭环。
- "loop 相当于 rollout"：真实环境反馈驱动策略调整，本身就是一种 Agent 式强化学习。

## 方案/架构

### Harness 干预的 10 个节点

讲者用 Trace 与 Turn 区分粒度：**Trace 是一次完整任务，Turn 是其中一次模型调用**；Harness 贯穿两者之间的每个工程钩子。

| 序号 | 节点 | 典型动作 | 阶段分类 |
|------|------|---------|---------|
| 1 | Trace 开始 | 任务接收 / 意图澄清 | 任务与上下文 |
| 2 | Turn 开始 | 场景识别 / 任务分解 | 任务与上下文 |
| 3 | 调用模型前 | 上下文选择 / 压缩 | 任务与上下文 |
| 4 | 调用模型时 | 参数与输出 / 协议约束 | 模型与动作 |
| 5 | 调用模型后 | 输出解析 / 动作空间约束 | 模型与动作 |
| 6 | 工具执行前 | 工具选择 / 执行前校验 | 模型与动作 |
| 7 | 工具执行时 | 执行监控 / 过程保护 | 执行与反馈 |
| 8 | 工具执行后 | 执行后 / 状态验证 | 执行与反馈 |
| 9 | Turn 结束 | 异常恢复 / 下一轮决策 | 执行与反馈 |
| 10 | Trace 结束 | 轨迹记录 / 评测反馈 | 执行与反馈 |

> Harness 不是一个单点模块，而是贯穿 Trace 和每个 Turn 的工程控制层。

### 在原有 Harness 上优化适配：六个维度

| 维度 | 核心要点 |
|------|---------|
| 1 日志 | 按测试场景重新设计元数据和索引；以便于观测为原则可冗余记录；配套检测和格式转换脚本 |
| 2 提示词 | 模仿大模型官方示例表述风格；考虑 KV 缓存，分清共性/个性位置；整体抽象简练，易错点反复强调 |
| 3 工具与调用 | 根据场景构建自己的执行工具；基于场景语义封装组合工具代替推理；不同 action 之间尽量保持正交；对调用结果做后处理，保成功率可监控 |
| 4 上下文构建 | 适配自己的执行工具接口；调控历史帧/轨迹/goal/subgoal 投放；保留明确记忆，删除不确定记忆；可做小型检索知识库动态加载 |
| 5 多智能体设定 | 控制数量，能一个做别设计成两个；角色/工具差异大又聚焦的可拆分；串行依赖低、可异步的可拆开；降低附属体置信度，冲突以执行体为主 |
| 6 loop 控制与人在回路 | 设置异常触发机制；人机协同，一人维护多台设备；以效率为优先设置重试机制；结果校验与规则兜底 |

配套的三条实践经验：

1. **建立固定测试集**：固定评测样本与评价标准，效果可衡量可比较。
2. **完善日志系统**：记录执行轨迹与工具调用，定位失败节点。
3. **控制变量**：每次聚焦一个变量，对照评测验证后保留或回退。

### 上下文工程：决定 Agent 的上限

讲者给出的公式是：

```
Agent 效果 = 模型能力 × 上下文质量
```

两条基本原则：**该给的信息要给齐**（让模型知道目标、状态和边界），**不用给的信息不要给**（减少噪声，保护模型注意力）。结论是"上下文不是越多越好，而是与当前任务刚好匹配"。

三个具体做法：

1. **长输出先落盘，再把选择权交给模型**：工具输出过长（如 read 读取文档、bash 执行命令一次撑爆上下文）时，把完整结果保存到本地，给模型"截断文本 + 文件路径"；模型先处理摘要和关键尾部，需要时再按路径读取完整内容，不牺牲调试能力。
2. **压缩提前触发，保留可继续的摘要**：在模型完成上一轮任务后即判断剩余空间主动压缩，防止超限并保持性能。压缩结果按结构化模板保留五项：用户目标、约束条件、工作流程、关键决策、下一步计划。"不是删历史，而是按结构化模板提炼下一轮真正需要的信息。"
3. **稳定提示词的前缀，才能稳定命中缓存**：把系统提示词、工具与规则放在稳定区，当前任务、历史上下文放在变化区；合理编排分区，尽量避免前缀变化，提高 prompt cache 命中率。讲者称"Context Engineering 的核心，是把有限上下文变成可复用的工作记忆"。

### 后训练：五种范式与奖励信号四级迁移

| 范式 | 做法 | 局限/特征 |
|------|------|----------|
| SFT 监督微调 | 用"输入—理想输出"示范直接教学，快速打底 | 只学固定套路，不优化偏好与决策 |
| RLHF 人类反馈强化学习 | 人工逐条比较答案、训练奖励模型，再做 RL 对齐 | 奖励昂贵、信号粗，只校准"语气是否像人" |
| RLAIF AI 反馈强化学习 | 把成文"宪法"（原则清单）交给模型，由模型按宪法自我批判、修订、监督，替代逐条人工标注 | 用原则替代逐条标注 |
| RLVR 可验证奖励强化学习 | 不训练打分模型，用客观、可程序化校验的规则（断言）直接给对错 | 用 GRPO 在单步静态任务上激发推理 |
| Agentic RL 智能体强化学习 | 训练单位从单轮答案变为几十上百步的工具/环境交互轨迹，奖励由环境终态与多组件构成 | 讲者判断其成为主战场 |

**奖励信号的四级迁移**（讲者标注为"更便宜、更客观、更稠密、可规模化"）：

- L1 人类偏好（RLHF）：人工标注 → 训练奖励模型
- L2 宪法原则（RLAIF）：模型据成文原则自批判、自监督
- L3 可验证规则（RLVR）：程序断言直接判对错，无需打分模型
- L4 环境反馈（Agentic RL）：终态断言 + per-turn 过程奖励，作用于整条轨迹

讲者的结论：**Agentic RL 成为主战场**——多轮工具使用 RL 进入旗舰模型后训练主线，训练栈开源化，能力沿轨迹向小模型/端侧下沉。

### Agentic RL 的定义与关键差异

定义：Agentic RL 是在多轮轨迹上、以环境交互与终态结果为奖励信号来训练 LLM 智能体的方法。

| 维度 | 普通 RL（RLHF / RLVR） | Agentic RL |
|------|----------------------|------------|
| 交互结构 | 单轮：prompt → 回答 → 打分 | 多轮：观察 → 动作 → 观察……多步循环，直到任务结束 |
| 环境 | 基本静态、无状态（题库） | 动态、有状态、会被模型改变（OS、浏览器、仓库、工具 API） |
| 动作空间 | 输出 token（一段文本/答案） | token + 工具调用/环境动作（搜索、执行代码、编辑文件、点按钮） |
| 奖励 | 结果对不对/人类偏好，多在终点给一次 | 终点目标奖励 + 每步环境反馈（dense per-turn） |
| Horizon | 短（一条回答） | 长（几十～上百步，稀疏奖励、轨迹爆炸） |
| 信用分配 | 相对简单（整段一个分） | 很难：终点失败要回溯是哪一步、哪个工具决策错 |
| 数据来源 | 静态数据集 | 训练时现场 rollout 产生的交互轨迹 |
| 主要风险 | RM 偏见、蒙对答案 | 环境漏洞被 reward hacking、不可复现、多轮误差累积 |

### 长 horizon 的两个核心难题与解法

**难题一：信用分配（Credit Assignment）**——双重层级归因：哪一轮（turn）是关键？该轮内又是哪些 token 的决策关键？典型困境是任务最后失败，很难判断是第 3 步的搜索关键词错了，还是第 40 步的编辑错了；一个 terminal 信号很难回溯归因到具体某一步。

**难题二：奖励稀疏 + 轨迹爆炸**——正奖励极少，绝大多数路径走不到目标；可选动作随步数组合增长，轨迹数量爆炸；信号稀疏 + 空间巨大，训练极易学不动、不收敛。

讲者小结："长 horizon 的本质矛盾——一个稀疏终点分，既要回溯归因，又撑不起指数级的轨迹搜索。"

解法是三项组合：

1. **三级奖励结构**：terminal 终点一次 / delayed 阶段反馈 / per-turn 逐轮稠密；奖励越密、越逐 turn、且与终局一致，训练越稳、收敛越快。
2. **Rollout Harness**：rollout 与 trainer 解耦的异步基础设施，生成轨迹、算奖励、供策略更新。它不直接更新模型权重，核心组件包括采样调度、环境/工具沙箱、多轮状态、奖励计算、异步引擎；规模为成千上万并发轨迹、长期运行；代表有 veRL 等异步 RL 框架与自研 rollout 系统；主要风险是环境漏洞被 reward hacking、不可复现、训练-推理失配。
3. **可复现沙箱**：容器/虚拟桌面并发，环境可重置、过程可审计。

## 关键工程做法

### 场景一：效率/延迟约束，用蒸馏换时延

**痛点**：一条 GUI 用例几十上百步，每步"看截图 → 定位元素 → 生成动作"都调云端大模型；回归套件要求上千桌面并发。

| | 蒸馏前 | 蒸馏后目标态 |
|---|--------|-------------|
| 形态 | 云端大模型 + 长 harness prompt | 本地小模型（3B–9B，边缘常驻） |
| 延迟 | 单步秒级延迟，一条用例数十次往返 | 单步百毫秒级，可离线/私有化部署 |
| 成本 | token 成本随用例步数线性增长 | 成本数量级下降 |
| 并发 | 受 API 配额与网络约束 | 支撑上千虚拟桌面并发 |

**蒸馏对象有两类**：一是大模型的感知与决策能力（截图理解、元素定位、键鼠动作与断言判断）；二是 harness prompt 中的工程规则（定位优先级、显式等待/重试、弹窗处理、断言模板、失败恢复）。讲者强调后者的重要性：把反复调用外部 harness 的模式内化进策略，即 **harness annealing（harness 内化）**。

### 场景二：能力缺口、逻辑固定，用 Agentic RL 学固定套路

为什么提示词会触顶：动态渲染、自定义控件、懒加载；随机弹窗、组件频繁改版；定位策略 × 异常分支组合爆炸；SFT 只背固定示范，易过拟合特定界面。

为什么适合 Agentic RL：登录/下单/表单/CRUD 等流程目标明确（逻辑固定）；奖励可由多组件构成——可验证终态断言（fail-to-pass、页面/DB 比对）只是 reward 的一部分，配合 per-turn 过程奖励/ORM。

落地做法三步：

1. **沙箱化并发环境**：自动产出可交互轨迹，讲者引用 CUA-Gym 3.2 万条 / 110 环境。
2. **Agentic RL 轨迹优化**：GRPO / GSPO 更新整条轨迹；可验证断言 + per-turn 过程奖励组成 reward。
3. **失败轨迹变新题**：WebRL 自进化课程，密集奖励防长轨迹不收敛。

### 构建 Agentic RL 数据集：四步法

讲者把"执行过程"变成"可学习的轨迹"，四步为：

```
标注平台 → 执行日志设计 → 日志转训练数据 → 程序化环境合成
```

#### Step 1：标注平台，人在回路的数据起点

标注平台是整条数据飞轮的"种子"——贵但准。它产出高质量成功轨迹用于 SFT 冷启动，并把专家操作习惯显式化为 tips / shortcut。平台四职：

- 冷启动轨迹：人工/半自动示范"怎么完成一个测试任务"
- 多模态对齐：截图 + OCR + 坐标 + 操作意图一一对应
- 质量闸门：人工校验轨迹、纠正感知/规划错误
- 经验显式化：专家习惯沉淀为可复用 shortcut

每条样本的字段：`instruction`（自然语言任务指令）、`screenshot`（每步屏幕证据）、`action_object`（结构化动作，如 Tap/Type）、`action_thought`（操作意图与理由）、`subgoal`（当前子目标）、`outcome`（动作反思结果）。

#### Step 2：执行日志设计，不是文本日志，是事件 + 状态 + 证据

日志面向智能体执行过程，采用**事件溯源 + 状态快照 + 多模态证据**三位一体，支撑可追溯、可调试、可重放。

事件流：

```
init 初始化 → perception 感知 → planning 规划 → action 动作 → reflection 反思
→ notetaking 笔记 → experience 经验沉淀 → finish 结束
```

中段"感知 → 规划 → 动作 → 反思"构成闭环，反思结果反馈给下一轮规划；`max_itr` / `max_consecutive_failures` 防止无限循环。

三个设计要点：

- **事件 vs 状态分离**：事件描述"做了什么"（`action_object`），状态快照描述"当时知道什么"（`info_pool`：历史、计划、子目标、错误、进度）。既能分析轨迹，也能还原任一时刻上下文。
- **三层记忆**：① 当前轮上下文（summary / action_history）；② 任务状态（important_notes / progress）；③ 跨任务经验（`tips.txt` / `shortcuts.json`，如把 Tap→Type→Enter 封装为快捷动作）。
- **冗余字段的可审计性**：`prompt_*`、`raw_response`、结构化字段并存，可定位错误究竟发生在感知/规划/格式/解析/执行/判定哪一环；动作结构化保存支持离线重放。

#### Step 3：日志转训练数据，从执行轨迹到 GRPO 样本

脚本把 MobileAgent 的成功执行日志转换为 GRPO planning 数据集：**只采成功轨迹作正样本**，按"最近截图 + 规划 prompt + 模型原始回复 + 子目标/思维链/计划"结构抽取。

| 字段 | 来源 | 用途 |
|------|------|------|
| `picture_file` | 最近 perception 截图 | 多模态图像输入 |
| `action_prompt` | `prompt_planning` | 模型输入 X |
| `response` | `raw_response` | 教师信号 Y |
| `current_subgoal` | `current_subgoal` | 当前子目标 |
| `planning_thought` | `thought` | 思维链 CoT |
| `planning_description` | `plan` | 规划描述 |

代码的关键设计是**聚焦 planning 而非 action**（注释掉了 action 分支），训练目标是子目标规划能力；`(picture_file + action_prompt, response)` 构成标准 SFT 式 (X, Y) 对，可作 GRPO 的 base / reference 初始化。同时利用状态延续：planning 借最近一次 perception 的截图。

#### Step 4：程序化环境合成，让任务"造"出来，而非"标"出来

人工标注贵、静态基准易被背、RL 需要成千上万可执行任务——环境本身必须流水线化。三条路线把"题库"变成"题厂"：

1. **任务模板参数化**：一个模板换实例说法无限生成；每任务配 init / success / teardown 脚本，保证可复现、可自动判分；同一模板可无限换实例，对抗"背答案"。参考 AndroidWorld 的参数化动态生成。
2. **环境生成流水线**：讲者以代码任务类比——从真实 PR / issue 反向"反译"成任务，LLM agent 自动克隆仓库、推断依赖、生成可复现 Docker 镜像并把测试跑通，把"手工配环境"自动化。
3. **自进化课程**：把智能体失败尝试自动改写成新任务，源源不断造题；结果奖励模型在稀疏反馈下给出可训练信号，在线更新对抗分布漂移。

测试执行的映射：测试用例模板化 → 参数化生成大量"点击 → 输入 → 断言"任务；init/success/teardown 保证可复现 + 可判分；**每实例带生产日期标签，只拿晚于模型训练截止日的题做干净评测**。"考核题（评测）与练习题（训练）共用同一套验收标准——训练场即考场。"

### 数据观：轨迹即数据，训练场即考场

- 训练单位 = 多轮轨迹：一条轨迹含几十到上百个 turn（思考 → 行动 → 观察），长 horizon 决定能否学会复杂策略。
- 奖励来自环境终态："对不对"要把世界跑完才知道——fail-to-pass 测试转绿、页面/DB 状态达标。
- 训练场 = 考场：同一份镜像与断言，既当 rollout 奖励、也当评测分，训练与评测共用一套验收。

数据飞轮：标注/人工轨迹（SFT 冷启动）→ 在线 RL rollout 轨迹 → 经验沉淀（tips / shortcuts）→ 回灌课程。讲者指出，GUI Agent 每轮"感知-规划-动作-反思"即是天然轨迹样本。

### 趋势总览（2025–2026）

讲者判断后训练正在从"对齐回答"转向"训练可执行的智能体"：奖励从人类偏好迁移到程序验证与环境反馈，训练单位从单轮答案升级为多轮交互轨迹。

1. **轨迹化训练与 turn 级奖励**：dense、逐 turn 且与终局一致的奖励通常更稳；代表 SWEET-RL / iStar / TRACE。
2. **全异步训练栈成默认基础设施**：rollout 与 trainer 拆池、队列解耦、容忍陈旧数据，解决工具等待和长尾轨迹造成的 GPU 空转；代表 AReaL、veRL、ROLL、Qwen3.5。
3. **动态环境与任务生成军备竞赛**：新题持续收割、环境自动生成、终态自动验收，用于防污染与规模化 rollout；代表 SWE-bench-Live、WebGym、SIMA 2。
4. **GUI / Computer Use 新边疆**：视觉观察 + 鼠标键盘动作进入 RL，GUI 逐步与命令行共享统一动作空间；代表 OpenAI CUA、UI-TARS-2、Qwen-UI。
5. **自进化、自博弈与世界模型内生化**：模型同时生成任务、经验或过程监督，形成更强的自举闭环；代表 SIMA 2、ECHO、MiMo-V2.6。
6. **RL 算力向预训练量级靠拢**：Live RL、长时训练和大规模 rollout 正重写后训练的成本结构；代表 Grok 4、混元-T1、MiMo-V2.6。
7. **"小模型 + Agent"下沉端侧**：能力蒸馏、工具调用和端侧推理结合，降低实时 agent 的延迟与部署成本；代表 Nemotron、MiniCPM5-2B、Step 3.5。

### 四句话带走

1. 测试执行天然契合 Agentic RL：多轮、有状态、奖励可验证、轨迹现场产生——四特征同时满足，是 long-horizon RL 的理想试验田。
2. 数据观：轨迹即数据，训练场即考场——数据来自 rollout 而非静态集；同一份镜像与断言，既是奖励信号也是评测分数。
3. 日志设计是地基：事件 + 状态快照 + 多模态证据三位一体，支撑可追溯、可调试、可重放与跨任务经验沉淀。
4. 规模化靠程序化：任务参数化 + 环境生成流水线 + 自进化课程，配生产日期标签防污染，把"题库"变成"题厂"。

## 经验与边界

- **选型是动态问题，不是教条**。讲者明确说答案随时间、场景与需求变化；本页给出的"知识→RAG/本体、执行→Harness、行为模式→后训练"是定位问题的框架，不是固定配方。
- **Harness 优先的边界**：只有当问题确属编排、约束、状态或校验时才优先 Harness；如果缺的是领域知识，知识库/本体仍然必要，但知识库本身是静态的，不能替代闭环。
- **蒸馏的适用条件**：有明确的延迟/成本/并发约束，且任务可被小模型承载（3B–9B 边缘常驻）。代价是要把感知决策与 harness 规则一起蒸进去，harness annealing 并非只蒸答案。
- **Agentic RL 的适用条件**：能力缺口存在、流程逻辑相对固定、奖励可多组件构成；若奖励无法验证或环境不可复现，训练会被 reward hacking 与不收敛支配。
- **数据成本的真实约束**：标注平台"贵但准"，是冷启动种子；规模化必须靠日志标准化与程序化环境合成，否则回到"先给我十万条优质数据"的死结。
- **评测污染风险**：静态基准易被背；必须用生产日期标签、镜像哈希、轨迹核验把污染挡在环境层。训练场与考场同源不同题。
- **工程风险**：环境漏洞导致 reward hacking、不可复现、训练-推理失配；rollout harness 与 trainer 解耦后还要处理陈旧数据与异步一致性。
- **证据边界**：第 25、26 页的效果数字来自外部论文/项目（Qwen3-8B、CUA-Gym、WebServ、WebRL），不是本案例的 GUI 测试生产指标；第 33 页是本案例的"部分实验结果"，只有 1.5B/3B 小模型与单一 planning 任务，不能外推为通用领域 Agent 的收益。原文未披露完整测试集规模、失败率、线上回归套件覆盖率与成本节省金额。
- **原文笔误**：第 33 页表格中的 `GPRO` 与通行写法 `GRPO` 不一致，本页按原文保留并标注，未擅自更正。
