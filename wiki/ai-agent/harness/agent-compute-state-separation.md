# 计算、状态与环境的分离：Agent 的两层解耦

[[super-agent]] 要做到"持久"——始终在线、直接接入真实工作环境、长期运行遇异常自动恢复——需要先解开一个默认绑定。

## 问题：三样东西被绑在同一台设备上

现有的本地 Agent 默认把三样东西绑在一起：

| 被绑定的对象 | 性质 |
|--------------|------|
| 推进 Agent Loop 的计算 | 可无状态、可水平扩展 |
| 需要持久保存的会话状态（Session） | 有状态、需持久化 |
| 代码仓库与本地工具链等**执行环境** | 重状态、难以复制 |

后果很直接：**一旦设备休眠或离线，Agent 就会停止运行，且无法访问其他设备上的环境。**

原文借鉴计算机系统中的**存算分离（Compute-Storage Separation）**思想，分两步解耦。

## 第一层：计算与状态分离

| 部分 | 放在哪里 | 特性 |
|------|---------|------|
| 推进 Agent Loop 的计算 | 云端**无状态弹性计算容器** | 可水平扩展、重启或替换 |
| Session 等持久化状态 | **数据库** | 会话与任务的连续性由持久化存储保障 |

计算本身可以做成无状态的，需要持久保存的只是会话状态。这样 Agent 便摆脱了单台本地设备的生命周期限制，实现**云端持久在线**。

## 第二层：计算与执行环境分离

Agent Loop 与会话状态常驻云端后，下一个问题是**如何访问任务所需的执行环境**。原文的一个关键判断是：

> 模型工作所需的上下文很大一部分要通过工具调用从代码仓库、本地文件、依赖服务等执行环境中获取，从这个意义上说，广义的上下文也包含了执行环境本身。

围绕这个问题，常见的两种思路都不够：

| 常见思路 | 问题 |
|---------|------|
| 在云端启动沙箱、拉取代码并尝试重建和同步环境 | 真实工作环境往往包含**未提交的本地修改、私有凭据、内网服务依赖以及特定的硬件或工具链**；技术上同步成本很高，还容易信息遗漏 |
| 直接要求用户放弃本地环境、迁往云端工作 | 对很多用户来说**迁移成本过高** |

原文的解法是：**既然难以复制和同步的是环境本身，就不必让执行环境跟着 Agent Loop 上云**。

```
              ┌──────────────────┐        ┌──────────────────┐
              │    Agent Loop    │◄──────►│   Session 数据库  │
              │ 云端无状态弹性容器 │        │   持久化状态存储   │
              └────────┬─────────┘        └──────────────────┘
                       │
       ┌───────────────┼────────────────┬──────────────────────┐
       ▼               ▼                ▼                      ▼
  个人开发机      云端托管 / 按需环境   间歇在线的个人设备
  （端侧 daemon） （端侧 daemon）      （端侧 daemon）
```

Agent Loop 在云端运行，**重状态的执行环境留在原地**，仅在端侧部署一个**不保存会话状态的轻量 daemon**，它只负责执行命令与返回结果。相当于把执行环境留在云端之外，由 Agent 按需读取其中的上下文。

## 与 Anthropic"脑手分离"的关系

原文明确说明这一思路与 Anthropic 提出的**"脑手分离"（Decoupling the brain from the hands）**一致：同样让 harness 保持无状态，把会话日志存放在 harness 之外，并通过统一接口按需接入执行环境。

| 维度 | Anthropic 的脑手分离（据原文转述） | 本文的两层解耦 |
|------|-----------------------------------|----------------|
| 共同点 | harness 无状态、会话日志外置、统一接口接入执行环境 | 同左 |
| 场景 | 托管服务，主要讨论**按需创建的沙箱**和客户 VPC 内的资源 | 首先接入的是**用户日常使用、可能间歇在线的个人机器**，上面有未提交的修改和本地凭据 |

两种场景的差异决定了接入对象的差异，因此本文的方案**既支持 BYOM（Bring Your Own Machine）**——把用户日常使用的开发机或个人电脑接入云端 Agent——**也支持接入云端托管机器或按需创建的计算环境**。

相关对照见 [[claude-managed-agents]]；另一条从"单体自管"走向"分布式托管"的路径见 [[distributed-agent-hosting]]。

## 解耦之后得到什么

- **跨设备切换**：一个 Agent 不再受限于单台机器，可以根据任务需要选择环境来执行命令并获取环境中的上下文；
- **间歇在线设备可用**：在用户的某台个人设备重新上线后，由云端 Agent 自动触发并完成需要在该设备上执行的任务；
- **状态与计算独立演进**：计算容器可以随意重启或替换，会话连续性由存储保障。

## 代价：安全与隐私前提

这一设计**默认建立在云端与端侧环境彼此受信任的前提之上**。原文在开放问题中给出两条风险：

1. 云端 Agent Loop 持续接入外部环境事件、端侧设备又存有私有代码、敏感数据与本地凭据——一旦云端遭遇服务端入侵或提示词注入而被攻破，**其连接的全部端侧设备都面临被控制的潜在风险**；
2. 即使云端未被攻破，只要端侧环境中的凭据进入模型上下文，正常执行过程中同样存在**凭据泄露风险**；因此还需要设计机制，让 Agent **在完全不接触凭据本身的情况下使用凭据**。
