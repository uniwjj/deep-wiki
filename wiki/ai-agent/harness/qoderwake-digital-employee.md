# QoderWake：企业群聊里的数字员工架构

QoderWake 把自己定位为**数字员工**，即时通信（IM）的单聊与群聊是它与用户日常交互的高频场所。这篇文章借 DeepSeek Harness《Super-agent 设计探索》（2026-10-31）引发的讨论，回看它围绕企业任务管理、调度、多 Agent 协作与人类专家协助的既有实践。

它处理的与 Super-agent 是同一个问题：**信息和要求不断变化，一件工作怎样继续推进？** 代码写完了、分析有结果了，工作却未必结束——用户补充条件、有新反馈、原要求被修改、结果还要送回对应的工作入口。Agent 承担了更多具体执行，这些协调工作仍可能占用人的大量注意力。

## 问题：一件工作穿过群聊时的三个断点

企业群聊里，一件工作可能经过多次补充和调整，同一个群也可能同时讨论别的事情。聊天窗口按消息组织，用户发来新要求时往往没有先选中对应任务。文章把它拆成三个断点：

1. **消息与任务能否关联** —— 新消息属于哪件事？
2. **协作之后能否接续** —— 向专家求助后，反馈回到哪里？
3. **结果能否回到原处** —— 做完的东西送回哪个入口？

原文用一个简化情境串起来：Agent 正在分析一次数据导出失败，群里补进一句「只影响昨天新增的账户，旧账户正常」；它向业务专家求助，得到「这批账户使用了新的权限配置」；发起人紧接着改要求——「先不改配置，只补一份核查清单」。此时分析已开始，专家回复来自另一次交互，群里还在讨论版本发布风险。新线索要回到原分析，最新要求要约束后续动作，清单完成后还得送回最初的业务群。

## 分工：Router 分派、Coordinator 控运行、Waker 推进

| 角色 | 职责 | 是否推理 |
|------|------|---------|
| Task Router | 理解意图、匹配任务、选择 Waker，也处理轻量直答 | 是（模型） |
| Task Coordinator | 任务锁、队列、执行准入、状态、取消与恢复 | 否（程序实现的运行控制组件，不是第三个推理 Agent） |
| Work 层 / Waker | 用必要背景、专业能力、记忆和已授权工具推进具体任务 | 是 |

判定要点：

- Router 先判断一条消息是**发起新任务、补充信息、查进度，还是取消工作**；意图不清先澄清，需要执行再分派。新任务按请求、Waker 职责与能力、业务规则选执行者；已有任务的补充回到原 Task 和负责它的 Waker。
- 「任务交给谁」与「现在能不能开始」是两件事——后者由 Coordinator 管。
- 耗时分析交出去以后，消息入口可以继续接收新输入；执行者只需知道自身任务相关的背景，不必理解群里全部讨论。
- 一个 Waker 不等于只能处理一项任务；数据分析、研发排查、测试核查可分别组织。

这与 Super-agent 的 Router / Worker 分工不谋而合。**差异在交接方式**：Super-agent 让 Router 统一对外回复，QoderWake 按消息与工作类型安排回流；Super-agent 还提出 Worker 订阅某个 Thread 后事件由程序直接送达以减少 Router 转发，QoderWake 未采用这种订阅直通——文章的说法是「是否采用订阅直通，取决于各自的任务关联和运行机制」。

## Context：既要保留背景，也要反映最新要求

只保存完整聊天记录仍可能做错事：报错、账户信息、专家回复都在，但「先不改配置，只补一份核查清单」没有影响正在运行的任务，旧执行就继续按原要求推进。文章指出的两种常见做法都不够：

- 单 Session 串行处理 @ 消息：新要求可能排队等到下一轮；
- 把群里所有新消息灌进当前执行：容易混入无关讨论。

QoderWake 的做法是**先判断消息的归属和作用，再选择处理方式**；在运行时支持追加输入的情况下，补充信息可在工具调用之间的安全时机交给模型。

Context 被拆成六组，围绕「谁需要什么」组织，原则是**关联、分层、按需、隔离**：

- Router 侧：候选任务 + 近期摘要 → 判断归属；
- 执行 Waker 侧：当前目标、已有结论、本轮要求 → 继续推进；
- 求助的专家：只需足以回答该问题的背景，不默认读整群聊天记录。

配套的边界：

- 历史和记忆按需取用，**来源与适用时间也要核查**——旧约定不能覆盖当前要求；
- **内容相关不等于访问授权**：向一位专家求助，不意味着可以读他参与的其他讨论；
- 取消可以停止后续执行、阻止旧产物交付，**但不能撤销已经发生的外部操作**；
- 判断上下文是否生效，看「发起人改了要求以后后续动作是否随之调整」，而不是看存了多少信息。

Super-agent 用 Inline & Spill 与链式召回讨论信息如何按需进入上下文（见 [[inline-and-spill]]），QoderWake 这里给出的是同样的取舍在任务维度上的落法。

## 主动响应：先确认「这是不是我的工作」

群里有人说「导出又失败了，有谁能帮忙看一下吗」——若排查属于数字员工职责，可以成为主动响应的候选。但「请业务同事查一下，查完把结果发给 Waker」只是在**指定结果接收者**，不能因为提到了 Waker 就认领工作。

三层判断：

1. **程序检查**来源、时效和明确的定向关系；
2. **轻量模型初筛**是否值得继续——不规划、不回复；
3. **Router** 结合群策略、响应身份和有限背景，确认职责与任务归属。

三条硬约束：初筛不代表授权；评分不能读成「该由当前 Waker 接手」的概率；未过初筛或 Router 判定不属于当前执行者，**都应保持安静**。确认接手后，工作进入独立上下文，按队列与并发约束执行。文章明确说这部分仍是需要检验效果与成本的设计方案——**即使最终静默，筛选也会消耗资源**。

## 权限：落实到「实际能做的事」

分析原因、整理清单、修改账户配置，需要的权限不同。理解了问题不等于获得修改权限；讨论中有人提出建议，也不能当作授权。权限约束落在四个层面：**数据访问、工具调用、实际操作、结果发送**；允许、需要确认、不允许各有路径——支持审批的场景请求确认，没有权限时说明限制或交由有权限的人处理。

历史消息、任务摘要、专家反馈都不能覆盖这些边界；等待、拒绝、中断有不同处理机制；**某类审批支持恢复执行，也不能据此推导所有操作都能自动续跑**。

## 工作形态：按依赖与确定性选，不是能力等级

| 形态 | 运行单元 | 适用 | 结构 |
|------|---------|------|------|
| Waker | Task | 单角色目标清晰 | 目标 → 执行 → 交付 |
| Waker Group | Mission | 多角色需协调与复核 | 角色 → 协调 → 复核 |
| Waker Flow | Run | 规则明确，预设条件与人工点 | 规则步骤 → 条件 → 人工点/下一步 |

三种形态都可以有多个实例，分别负责各自的任务、协作目标或流程运行。文章强调它们是**工作组织上的选择，不代表能力等级**：能独立完成的工作保持简单，存在角色依赖再引入协作，已经确定的规则交给流程。判断标准也很实在——**如果增加 Agent 以后用户反而要连接更多会话，协调负担就没有减少**；分工是否合适要看实际交接成本。

## 评测：多轮连续性是最突出的差异

依据 QoderWake 2026 年 8 月内部评测报告：覆盖三类场景、合计 300 个脚本案例，对比「普通 Waker」与「QoderWake（有 Router 的 @Waker 配置）」。任务完成与上下文利用由大模型对照金标评分，多轮连续性与投递结合执行证据，及时性按耗时规则计分；各维度 0—100 分，**不代表任务成功率**。

| 维度 | 结果 |
|------|------|
| 多轮连续性 | QoderWake 86.56 / 普通 Waker 0.00（相差 86.56 个评分点，0.00 是本次评测中普通 Waker 的连续性得分） |
| 任务完成、上下文利用、投递可靠性 | QoderWake 更高 |
| 及时性 | QoderWake 比普通 Waker 低近 7 个评分点 |

文章自己给了限制条件：这组结果反映的是**两种整体配置**的表现，不能把差异全部归因于 Router；连续性改善的同时，还要结合执行质量、交付可靠性和等待成本判断是否满足业务要求。

## 与 Super-agent 的对照要点

| 议题 | Super-agent | QoderWake |
|------|-------------|-----------|
| 分工 | Router / Worker 双层 | Task Router / Waker，另加程序化的 Task Coordinator |
| 对外回复 | Router 统一回复 | 按消息与工作类型安排回流 |
| 后续消息 | Worker 订阅 Thread 后由程序直送 | 未采用订阅直通，靠 Router 判断归属 |
| 上下文 | Inline & Spill、链式召回 | 六组分层 Context + 关联/分层/按需/隔离 |
| 主动性的边界 | 由设计原则约束 | 三层判断 + 「初筛不代表授权」 |

文章结尾的判断：设计持续工作的 Agent，先要分清**模型与系统各自负责什么**——变化的要求需要模型理解，任务归属、执行状态与授权范围需要系统维护；理清这层分工，再决定在哪里引入路由、协作或流程。数字员工的真正挑战不只在完成多少任务，而在**一件工作经过补充、调整和协作之后，能否继续按新的要求推进**。
