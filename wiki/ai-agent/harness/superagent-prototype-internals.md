# SuperAgent 原型的实现级拆解

[[super-agent]] 原文给的是设计与实验，`dsh-superagent-prototype`（约 1.6 万行）给的是另一层东西：**怎么让一个会出错的模型长期稳定地推进工作**。以下要点来自郑天（阿里云）对该原型的源码级分析，是原文之外的一手解读。

## 核心对象

| 对象 | 对应的现实问题 |
|------|---------------|
| Trigger / Thread | 世界上发生了什么？哪些属于同一回事——同一个 PR 或同一个群话题下的一串事件就是一条 Thread |
| Ticket（工单） | 一份获准开工的工作。系统里最稳定的东西：会话可以断、执行者可以换，Ticket 不变 |
| Policy（规则） | 团队定的规矩，比如谁能发起工作、什么情况下允许主动做。规则会改，所以有版本 |
| Mandate（授权） | 这份 Ticket「凭什么可以做」——谁要求的、范围多大、依据哪版规则 |

**为什么 Ticket 和 Mandate 要分开**：一个修复已经合并、Ticket 结束了，一周后有人在那个 PR 下说「这里还有个问题」。重新走一遍评估太慢，直接开工又可能越权；有独立的 Mandate，就可以沿用当时的授权恢复工作，但先对照最新规则检查它是否仍然有效。**一件工作能不能继续，和它现在是什么状态，是两个问题。**

## 一条消息进系统的五步

1. **进门登记**：不管有没有用先落库，重复的只算一次（Append Only）——重启后不会重放消息，事后也能查「这条消息去哪了」。
2. **查 owner**：人的后续消息如果落在某张 Ticket 跟进的 Thread 上，这张 Ticket 就是它的 owner，直接交给对应 Worker 判断，Router 不用介入。
3. **Gate 门禁**：用代码判断发消息的人有没有资格。
4. **Router 研判**：走到这一步才调模型，按规则逐条判断。
5. **一次性开单**：Ticket、Mandate、订阅、确认回复一次生成，不会出现「单开了但没人知道」的中间状态。

整条链路只有第 4 步用模型，其余都是确定性代码。

## 五条设计判断

### 一、模型提议，程序裁决

系统中有一个确定性核心，是 Ticket 状态**唯一**的写入者。Router 模型「接单」本质上是提交申请，核心校验权限、规则、参数和当前状态，不合格就拒绝。好处是：模型错了、被注入了，最坏也只是提交了一个被拒绝的申请。**模型负责灵活，程序负责可靠。**这也和 [[super-agent-dual-layer-architecture]] 的实验结论对得上——既然模型总有一次会「觉得这活很小、我自己干」，就不能靠它自觉。

### 二、先记账，再动手

把要做的外部动作也当成数据，与状态改动记在同一笔账里，提交之后由后台逐条执行（即 Outbox 模式）：启动 Worker 失败就退避重试，发消息确认优先于结果，崩溃重启后没做完的接着做。启动 Worker、投递消息、发 IM 全部走这一条路。模型的工作无法完全重放，所以重启后 Worker 会收到一条提示：先看代码目录和 PR 的实际状态，再决定要不要重做。

### 三、外部文本永远只是数据

优先级从高到低：**代码强制**（身份、权限、工具参数、消息长度）> 系统提示词（角色、工作方式、当前生效的规则）> 命中的规则（只对该 Ticket 的 Worker 生效）> 团队约定（沟通方式、交付要求）> **外部文本**（聊天、评论、文档）。另有一个防「传话失真」的细节：Router 转交任务时备注最多 30 个词，且不许写实现计划和验收标准，Worker 必须自己去读原始消息。

### 四、主动能力要能灰度

新规则默认试运行：模型照常判断，但只记录「如果放开，我会接这个单」，不真的开工；团队看记录觉得判断准确，再放开执行。判断时还必须对每条规则逐一给结论，接单要引用消息原文作为证据。

### 五、人的优先级最高

三个落点：状态按「在等谁」计算，等人的排在最前面；并发名额留一个给人（Worker 全忙时，人的消息仍能唤醒已有工作，新活不能把人挤掉）；区分「送到了」和「读到了」——消息进入 Worker 的会话不算数，真正进入模型历史才算，Ticket 结束时还没读到的人类消息会退回重新评估。

## 原型的边界

原文之外的这层解读还校正了几件事，接入生产前必须知道：

- 状态在单机数据库，一个部署只对应一个仓库和一套账号；
- Worker 以运维者的系统身份运行，文档明说**命令包装不是安全边界**；
- 原文提到的 **Watchdog 与投机执行，在原型代码、文档和提示词里都搜不到**；
- 完成判定主要靠外部事实（如 PR 已合并），这对研发自然，换到业务工作就不够。
