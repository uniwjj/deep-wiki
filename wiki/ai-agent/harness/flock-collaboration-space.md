# 协同空间 Flock：一群人和一群 Agent 对一件事负责

[[super-agent]] 回答的是「一个 Agent 怎样同时做很多事」；阿里云的协同空间 Flock 回答的是「**一群人和一群 Agent 怎样对一件事负责到底**」。两者的任务对象（Ticket / Quest）、控制面与执行面分离的思路高度相似，差别在切分方式与验收机制。以下内容来自郑天（阿里云）对这套系统的实践总结。

## 四层架构

| 层 | 内容 |
|----|------|
| 产品层 | 人（提目标、验收）→ Channel（一个项目一个空间）→ 跨 Channel 协作（消息与任务，双方授权） |
| 协作控制面 | Quest 账本（责任、依赖、状态、版本）→ 收件箱（谁该被叫醒）→ 派发器（选用哪种会话、防重复执行）→ 血缘（谁长出了谁） |
| 执行面 | 对话会话（同话题续接）、任务会话（每轮一个）、验收会话（每次新建）、Agent 引擎（循环与恢复）、本地执行端（跑在用户电脑上） |
| 基础能力 | 上下文压缩、文件与产物、沙箱与工具、模型 |

一次运行的七步：人提目标 → 协调者或人写入 Quest 账本 → 状态变化产生唤醒 → 派发器认领并决定怎么跑 → Agent 在对应会话执行 → 结果写回账本、可能唤醒下一个 → 人看到结果，验收或打回。

**控制面与执行面分离**是这套架构的支点：控制面装业务事实（谁负责、做到哪了、结果是哪一版），执行面只负责把这一轮跑完（模型调用、工具执行、断点恢复）。执行可以失败、可以重来、可以换人，责任和进度都在控制面不会丢——与 DSH 的「Ticket 不跟随会话」是同一个想法，区别是这里把它做成了人也能直接看到和操作的产品。

## Channel：一张由空间组成的网

- 每个 Channel 对应一个项目或业务场景，里面有人、协调者和各种 Agent，甚至包括跑在用户电脑上的本地 Qoder；共享一条时间线，上下文和权限默认不出这个空间。
- **跨边界协作不是把对方拉进来，而是在对方的 Channel 里建一个任务**，由对方在自己的空间执行。同一条交互线往返超过上限（默认 6 轮）会被拒绝，并建议合并空间——「如果两边要聊这么多轮，很可能是边界划错了」。
- 本地 Qoder 被做成 Channel 里的一个成员，与平台 Agent 用同一套任务与验收，只是它主动来领任务、在用户电脑上执行。

## Sessionless：把会话藏起来

「不会每次找同事说事，都先『新建一个同事』。」Sessionless 不是底层没有会话，而是**会话不再代表身份和任务，只是一次执行的耗材**。不同用途的会话规则不同：

| 会话 | 规则 | 原因 |
|------|------|------|
| 对话会话 | 续接 | 聊天要连续 |
| 任务执行 | 每轮尽量新开 | 继承旧会话会让上下文跨轮累积；只有子任务收口回父任务、人工断点重启才续接 |
| 验收 | 每次新建 | 验收者不该带着执行者的上下文，也没有执行权 |

用户端没有「新建会话」按钮：系统把几个事实算成一个键，键相同就接着聊。其中「谁能看见」是容易被忽略的隐私边界——Channel 换了成员，新对话会自动切到新会话，新人读不到之前的上下文。会话藏起来之后要解决「出了事怎么查」，所以补了一张血缘表：节点可以是会话也可以是任务，每条边记录是谁触发的，人 @ 了一下之后长出了什么，一次查询能看全。

## Quest：比会话活得更久的东西

Quest 建表时的注释是三个字：**责任状**——一件可以分配、可以追踪、可以验收的工作，有目标、验收标准和唯一责任人。

生命周期：待开始 →（指派）执行中 ⇄ 等人回复 →（提交）待验收 →（通过）已完成；待验收被要求修改则再执行一次，上一版留着。

最关键的设计是「待验收」这个状态：**Agent 跑成功不等于任务完成**，它只代表提交了一版结果，要由人或指定的验收 Agent 认可才算完。「在企业里，『做完了』必须有人认。」

## 任务链：DAG 不是规划出来的

很多编排系统要求先画好流程图再执行，但复杂任务往往事先画不出来。这里的做法反过来：每个动作只记录自己和谁有关，图是做事时自然长出来的。机制只有三条：

1. Agent 执行某任务时新建任务，默认就是当前任务的子任务；
2. 建任务时写明依赖谁，上游完成了才唤醒下游；
3. 子任务全部结束，平台唤醒父任务，并把已验收的结果带给它汇总。

管理者看到的「执行全景」就是把这些关系展开成一张 DAG，系统并不单独维护流程图。但「长出来」不等于放任：**如果 Agent 说不清新任务属于谁，平台会拒绝创建**，否则游离的任务会让父任务永远等不到收口。

副产品是上下文召回：任务链本身就是引用图，边是工作关系，比事件关系更稳定——答案分散在两周前某版批注、上游失败明细和业务人员一句答复里时，Agent 不需要记住，只要沿着工作关系走过去。

## 主动推进：踩过的最大坑是互相唤醒

实现很朴素：任务状态存在账本里，状态一变就算出该叫醒谁，有事才调用模型；一次执行的产出又成为下一次执行的触发。

但这个循环踩过一个大坑。预发环境有个「组织一次报数」的任务，理想是 3 次执行：协调者 @ 两个 Agent、各回一句、汇总。实际跑了 10 多次，同一个任务产生了 8 个执行实例，甚至有 Agent @ 了自己。根因不是模型笨，而是平台把「被点名」和「任务落到头上」放进了同一条链路——被 @ 的 Agent 拿到的指令是「完成后必须提交交付物」，于是它认真地开始拆任务、发通知。

修法是把语义分开：**@ 只是沟通，Quest 才是委派**——被 @ 只回应、不领执行权，要干活就先建任务；再加抄送不唤醒、Agent 之间连续唤醒默认最多 3 次、人一介入就清零。结论与 DSH 相同：**平台的硬约束比提示词可靠**。

## 记忆：从推到拉

早期做法很自然：每次唤醒都把成员名单、今天的消息、最近动态拼进去，生怕它不知道。结果是上下文越来越胖，还总有废话。后来全部删掉，改成只推任务内容、唤醒消息和文件清单，其余用工具自查：翻频道记录（长消息保留头尾、中间折叠并标明怎么取回，因为截断会让它把残缺内容当成全部）、查任务状态、取上游文件。

再往前是 MDC（Meta-Dance-Context）的思路：**不要让 Agent 记住，让 Agent 能找到**——记忆不放在模型脑子里，也不靠无限长的会话，而是放在一个可以自己翻阅的文件接口后面，每次唤醒编译出一个干净窗口。这与 DSH 的 Inline / Spill 是同一个结论，只是被线上问题逼出来的。

## 与 DSH 的两处分歧

**一、常驻 Router 可以拆开。** Router 实际打包了三份工作：对人的前台交互、判断路由、全局记忆。这三件事不必放在同一个常驻会话里——前台就是 Channel 时间线（人和 Agent 看同一份），确定性的路由由程序根据任务状态计算，需要判断的部分交给 Coordinator（Channel 里的普通成员，职责是拆解、指派、跟踪、汇总，不亲自执行），记忆放在 Quest 与文件里。换来的是：协调者不用常驻、上下文不会无限膨胀、权限边界更清楚；失去的是常驻 Router 那种连续感，以及「积压事件下一轮一起处理」的批处理红利——目前基本是一条唤醒对应一次执行，这正是要向 DSH 学的地方。

**二、中心化仍有瓶颈，只是位置变了。** DSH 的压测显示事件从每分钟 1 条涨到 40 条时，单个决定的平均推理时间反而从 6.4 秒降到 1.6 秒（Router 思考期间积压的事件下一轮合并处理）。但这不能外推到任意规模（压测里 Worker 是假模型）：

| 瓶颈 | 为什么会有 | DSH 的应对 | Flock 的应对 |
|------|-----------|-----------|-------------|
| 上下文容量 | 什么都经过中心，窗口迟早装不下 | 后续消息直通 Worker + 链式召回；承认跨月是瓶颈 | 协调者不常驻，按 Channel 切分，用时才查 |
| 判断质量 | 一轮判断太多事容易错，错一次影响面大 | 只有消息明确指向某 Ticket 时才归到这张 Ticket | @ 只算沟通，正式建单才算委派 |
| 成本 | 每次都要重新读一遍大上下文 | 接受 3.8 倍读缓存 Token | 有事才调模型，但还没做合并唤醒 |
| 爆炸半径 | 所有事件和权限汇于一点，被注入则影响全局 | 外部文本只算数据，权限由代码强制 | 按 Channel 隔离，跨 Channel 需双方授权 |

## 中心只该关心结果

中心一旦开始关心「怎么做」，就要读细节、做规划，马上退化成很重的 Team Lead，瓶颈也回来了。所以 Flock 的任务只定义目标、验收标准、责任人和依赖，**没有「实现计划」这一项**：拿到任务的 Agent 自己决定怎么读资料、用不用子 Agent、跑什么工作流；协调者拆完任务就结束这一轮，不轮询，子任务全部结束时平台再把它叫醒。DSH 走得更极端：Router 连验收标准都不许写，Worker 要回到原始需求自己判断。

「只看结果」有个前提，正好碰上业界的一场争论：2025 年 6 月 Anthropic 公开的 Research 系统让主 Agent 拆任务、子 Agent 并行搜索；几乎同时 Cognition 发《Don't Build Multi-Agents》反对，例子是做 Flappy Bird——一个子 Agent 做了超级玛丽风格的背景，另一个做了对不上的鸟，因为每个行动都带着隐含决策、彼此却看不到。作者的理解是两边都对：调研可以切开，一个游戏的美术风格切不开。所以问题不是该不该用多 Agent，而是**切分的边界在哪里：只有能被独立验收的工作才能分出去**。
