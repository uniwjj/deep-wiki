# 腾讯云 DataBuddy

> 来源：DataFunTalk《腾讯云DataBuddy让Agent接手数仓开发》（2026-11-03 13:00 发布），报道 **2026-10-20 腾讯云 DataBuddy 产品发布会**。原文为发布会报道，产品能力以演示与厂商口径为主，多数能力背后的实现细节未公开——本页只写原文明确说了的内容。
> 手把手的电商演示细节见 [[databuddy-ecs-demo]]。

## 定位

DataBuddy 被定义为腾讯云推出的 **Agent Native 大数据智能体工作台**：把 Agent 带入 **数据工程、数据治理、数据分析、数据科学** 四类日常场景，用户提出目标、审核关键步骤，具体执行尽量在平台内完成。

与「在数据平台上挂一个对话入口」的区别在于**交付物**：原文的落点是"从接到需求开始，直到交付一个能够运行、维护和继续使用的结果"——Agent 交付的是已编排、可维护的工程资产、已建成的指标与看板、已注册上线的模型，而不只是一段 SQL 或一个回答。

产品定位宣讲截图中给出的路线是"**第三次演进**"（与"什么是DataBuddy / 实机演示 / 核心架构"并列，作为发布会四个议程），截图中的产品内助手名为 **Hi Buddy**，页脚标注 Powered by WorkBuddy。

## 两类底座：统一语义层与 OneOps

### 统一语义层（截图标注为 Unity Semantics）

原文的表述是"腾讯云把这套能力组织成统一语义层"，自下而上三层（来自架构图）：

| 层 | 定位 | 内容 | 回答什么 |
|----|------|------|---------|
| **统一 Catalog** | 基础底座 · 全域元数据 | 元数据、全链路血缘 | 向下衔接物理数据、向上托起语义主线 |
| **语义模型** | 基础语义 · 统一口径 | 指标 Metric、维度 Dimension、Join 关系 | "过去有多少" |
| **本体模型** | 业务骨架 · 认知与决策 | 实体 Object、关系 Link、行动 Action、规则 Rule | "是什么 / 为什么 / 会怎样 / 该怎么办" |

架构图右侧把 **质量治理** 与 **安全治理** 标为「AI 驱动」的横切能力。原文对此的说明是：Agent 理解"高价值客户"这类业务概念时"有机会利用企业沉淀的定义，而不必临时猜测"。

> 注意：原文与图示均未给出三层的实现细节（指标如何定义、本体如何建模、血缘如何采集），只给出了分层职责与典型字段。与 [[data-agent-semantic-stack]] 的 8 层语义栈、[[ontological-semantic-layer]] 的"业务语义控制面"、[[apache-ossie]] 的 YAML 语义层是同一定位的不同实现，比较见下文。

### OneOps 架构

OneOps 把 **DataOps、MLOps、AIOps** 所需的环境、工作流与数据计算能力放进同一平台，让数据治理、特征开发、模型训练、部署与监控相互衔接。原文用一张架构示意说明它要解决的问题：**过去"数据在数仓、模型在 ML 平台"，中间横着"烟囱"，精力全耗在搬数据、写胶水代码上**。

演示中的模型用的是新上传的数据集，但建设与上线操作都在 DataBuddy 内完成——体现的是"数据资产与模型资产统一管理"。

## 四类 Agent 与对应场景

| Agent / 能力 | 场景 | 在演示中的具体产出（详见 [[databuddy-ecs-demo]]） |
|-------------|------|------------------------------------|
| **数据工程 Agent** | 数仓建设与运维 | ODS/DWD/DWS/ADS 四层方案（表结构、字段含义、ER 图）→ 9 接入 + 9 SQL = 18 节点 Pipeline；读日志定位字段改名故障并修复重跑 |
| **数据治理 Agent** | 质量与口径 | 数据画像识别唯一性/一致性问题 → 推荐 8 条质量监控规则 → 建成持续监控任务；沿血缘排查影响并给修复建议 |
| **数据分析 Agent** | 指标与看板 | 从 Catalog 事实表生成三个指标的定义、维度映射、说明与负责人 → 语义模型；45 个字段 → 9 张图表 / 7 种可视化类型的零售看板，数字可下钻到定义、字段、聚合维度与 SQL |
| **数据科学平台能力** | 建模与上线 | 数据集与特征注册为 Catalog 资产 → Notebook 生成清洗/相似度/Top-N 代码 → 物品协同过滤模型 → 实验追踪、评估、注册、在线特征表、推理服务与 API |

原文在介绍接入路径时把"四类 Agent"表述为"数据工程、数据治理、数据分析三类 Agent 与数据科学平台能力组成的工作链路"，即第四类（数据科学）在原文的措辞里是**平台能力**而非独立 Agent。

## Agent 进入生产的三层安全（Agent Runtime）

Agent 的操作面从"生成报表"扩大到"读日志、改 SQL、发布任务、接触客户信息"，原文把安全要求交给 **Agent Runtime**，并在「核心架构」议程中给出三层（来自架构图）：

| 层 | 管什么 | 机制 |
|----|--------|------|
| **第一层 · Agent 安全** | 管住 AI 的「行为」 | 双向 Agent Guardrails（实时拦截提示注入）、OBO 权限强绑定（绑定真实用户身份）、高危 SQL 拦截（执行前意图校验） |
| **第二层 · 数据安全** | 管住 AI 能「看到」什么 | 数据权限管控（统一授权、集中管理库表）、行列级权限、敏感数据识别（手机号/身份证等自动扫描打标）、动态脱敏（查询那一刻脱敏，不落地、不改原表） |
| **第三层 · 运行时兜底** | 管住每一次「运行」与「留痕」 | 会话级沙箱隔离（每次会话独立、互不串数据）、全链路可审计（每一步查了什么都留痕） |

架构图的收束句是："**Agent 完全继承人的数据权限：人看不到的，它一个字都碰不到**"；正文的表达是"Agent 按照实际用户的权限访问数据，不能借由自动化绕过原有边界"。Runtime 另提供**业务隔离**与**会话沙箱**。

与之配套的是**关键步骤人工审批**：故障恢复演示中，Agent 可以分析日志、找到字段变化并提出方案，但修改与重跑要等用户确认，执行结束还要检查新任务的运行结果。原文的推论是："Agent 承担的环节越长，平台对过程可见性、回滚和审计的要求就越高。"

## 两条接入路径

原文先回答了最现实的问题：用 DataBuddy 是否必须先把现有数仓迁走？答案是**不必**，提供两种路径（来自架构图）：

| 模式 | 结构 | 数据归属 | 适合 |
|------|------|---------|------|
| **一 · 直连已有 OLAP 引擎** | 数据分析 Agent（对话式取数/分析/洞察，单点切入）→ Unity Semantics → 客户已有存算引擎（数据库/数仓/湖仓保持不动） | 自己（数据不出境，就地跑 AI，*run AI in place*） | 多地合规、已有基建、只想先用起来 |
| **二 · 迁入统一存算引擎** | 四大 Agent 完整场景 → Unity Semantics → 统一计算与存储（**DLC** 批处理 / **OLAP** 交互分析 / **Setats** 流计算；底层 **TCLake** 统一存储，湖仓一体） | DataBuddy 全栈（存算一体、数据与 AI 同源） | 数据零散、想从 0 到 1 直接建齐 |

原文的归纳是：**"上层语义与 Agent 完全一致，差别只在底座归属"**——前一条改造范围集中，后一条覆盖任务更广，企业按现有基础设施与目标场景决定从哪里起步。

模式二涉及的 DLC、TCLake、Setats 是腾讯云大数据既有的存算产品（背景见 [[tencent-ai-dlc]]、[[workbuddy-data-practice]]）。

## 接入办公入口：WorkBuddy

发布会宣布 DataBuddy 已以**专家能力和连接器形式接入 [[workbuddy-context-engineering|WorkBuddy]]**。典型的串联流程是：提问"某区域销售额为什么下滑" → 完成指标分析 → **生成周报 → 整理汇报文档 → 通知相关人员 → 安排后续事项**，数据结论与业务协同在一个入口内衔接。

架构图把 DataBuddy 标为"数据超能力内核"，以**标准连接器**对外开放（图中标识企业数据超能力"可控、可信、开放接入"），WorkBuddy 之上 ChatGPT、Claude、Gemini 三项标为"即将接入"。正文对这一点只说"面向其他主流平台的标准连接器则属于后续规划"——**图中三家外部模型的"即将接入"是截图信息，原文正文未点名**。

## 效率与准确率数据（厂商口径）

| 指标 | 数值 | 原文附带的限定 |
|------|------|--------------|
| 基于语义层的分析准确率 vs 纯自然语言转 SQL | **95.9% vs 83.5%** | "仍需结合测试条件理解"；表结构与业务规则持续变化，语义层需靠治理 Agent 不断校验更新 |
| 数据工作效率提升 | **5 至 10 倍** | 不同企业原始系统、数据质量、审批要求不一致，实际效果要回到具体场景评估 |
| 模型上线周期 | **30 天 → 7 天** | 同上 |

原文给的建议路径是"从一条每天运行的业务管线、一个高频经营指标开始"，检验权限、结果追溯与长期运维是否跟得上。

## 边界与不确定项（原文未说明）

- **模型的参与程度**：演示截图中助手可选 Agent、模型（可见 ZLM-0.5-L1、DeepSeek-V4-Flash）、Skills，且页脚标注 Powered by WorkBuddy；但原文**未说明** DataBuddy 的 Agent 与 WorkBuddy 的产品/运行时关系，也未说明各 Agent 由何种模型驱动。
- **本体模型如何建设**：原文只说"本体模型进一步描述业务对象、关系、规则和可执行动作"，未给出建设方法、与语义模型的边界、与既有指标平台的关系。
- **Studio / Notebook 的具体产品形态**与 DataBuddy 的套餐、计费、私有化部署方式均未提及（离线副本末尾的官网二维码与试用配额属页面推广，未纳入 wiki）。
- **95.9% / 83.5% 的测试集、题目规模、评分方式**原文未披露。
- **Demo 的可复现性**：所有数据来自一场发布会演示，故障为演示中人为制造的下游报错，不代表真实企业环境下的表现。
