# 去哪儿 OTA 业务 Data Agent：从分析闭环到行动闭环

> 核心主张：**一次正规业务分析 = 取数 → 分析 → 决策 → 动作**；多数团队的 AI 投入只补上第一段，后两段仍靠人肉，价值流失最严重的地方就在这里。关键判据是 **LLM 推理、MCP 出数、人做决策**——**LLM 只负责「想」和「调度」，业务计算全部交给 MCP，LLM 不碰业务计算**。

来源：DACon 2026 北京站演讲《从分析闭环到行动闭环：OTA 业务 DataAgent 的边界突破与规模化落地》，演讲人郑吉敏（去哪儿网），2026 年 10 月 24 日。

## 背景与问题

### 三段断裂

| 断裂 | 表现 |
|------|------|
| ① 取数 × 分析断裂 | 数据散落各系统，取数靠商分排期，维度受限 |
| ② 分析 × 决策断裂 | 报告产出靠人读靠会推，洞察难沉淀为策略 |
| ③ 决策 × 动作断裂 | 执行靠人跟、效果无统一回验，闭环停在「已建议」 |

原文判断：多数团队的 AI 投入只补上第一段，后两段仍靠人肉——价值流失最严重的地方。

### 先想清：提效率，还是增业绩

| 导向 | 典型任务 | 姿态 | 产出 |
|------|---------|------|------|
| 日常提效 | T-1 / T-7 异动排查、日报、临时取数 | KPI 被动、让异常恢复 | 省时间（小时级 → 分钟级） |
| 业绩增量 | MoM / YoY 机会洞察、增长因子拆解 | OKR 主动、让指标正向增长 | 出结果 |

原文判断：提效故事好讲，但增长故事更有价值；目标是两类都覆盖，重点是可复用的搭建方法。

## 方案/架构

### 路线选型：Agent 原生，口径锁死在业务系统

| 对比维度 | 规则引擎 / 固定报表 | BI + LLM（Text2SQL） | Agent 原生（最终选择） |
|---------|-------------------|---------------------|----------------------|
| 交互方式 | 固定入口、被动查询 | 自然语言取数 | 自然语言全链路分析与动作 |
| 分析灵活性 | 低，仅覆盖预设切片 | 中，单轮查询为主 | 高，多步推理、维度叉乘 |
| 口径准确性 | 高，但靠硬编码 | 不稳定，SQL 生成易漂移 | 高，数据由业务系统经 MCP 给出 |
| 行动闭环 | 无 | 基本无 | Skill / 工具化，可延伸到动作 |

关键判据拆成三方职责：

- **LLM 做推理**：理解意图、拆解问题、规划路径；不碰业务计算、不改口径。
- **业务系统 MCP 出数**：按固定口径返回、承担确定性计算；口径唯一、可审计。
- **人做决策**：判断结论、拍板取舍、审批动作；对最终结果负责。

原文强调：确定性计算、关键口径、需要担责的动作，不交给 LLM 自由发挥；更关键的是，一个实际的业务分析需要多次的数据查询与分析。

### 双系统认知理论 + 双层规划

| 系统 | 定位 | 负责 | 能力 | 壁垒判断 |
|------|------|------|------|---------|
| System1 · 控场层（直觉快思考） | 把整件事做对 | 想清问题与步骤，结合数据边做边想下一步 | 业务直觉、模糊需求、异常应变、全局权衡 | 最难攻克，是真正的壁垒 |
| System2 · 执行层（审慎慢思考） | 把单点做对 | 每步具体取数，输出精准、可核对 | 逻辑推理、数学、代码 | 快速同质化，很难形成根本壁垒 |

工程落地为双层规划：

- **内层 · 思维过程规划**：CoT 思维链 → ToT 思维树 → GoT 思维图，让推理结构化，逐步推导、不直接拍答案。
- **外层 · 行动序列规划**：ReAct + Plan-and-Execute → Reflexion，调工具、看观察、自我修正。

理论依据是莫拉维克悖论：难的脑力活 AI 轻松，不费脑的常识与控场反而最难。双层规划正是双系统认知理论的工程化落地——持续增强 System1，同时把 System2 做准确。

### 整体架构：AI 能力 × 业务知识 × 数据底座

- **输入**：具体业务分析问题；**输出**：具体分析文档。
- **① 业务 + AI · 业务分析模型**（核心）：
  - ReAct 为主：模拟业务逻辑，多轮思考、分析与下钻；
  - Plan-Execute：每次规划 + 调用 MCP 获取数据；
  - Multi-Agent：特殊维度 / 场景拆开。
- **② AI 能力**：LLM 大模型（GLM-5.3-Flash）、AI 能力框架、think 工具、Harness Engineering。
- **③ 业务知识 · Skills**：业务概念与归因逻辑、Workflow 分析框架、Few-Shot 范例。
- **④ 数据底座 · 业务数字化**（MCP 统一口径，保证业务指标准确）：流量、产品力、订单、定价、供应链、外部数据源/报表。
  - 各模块 ES（请求 trace 实际连通、维度筛选一致）← 1:1 Hive / DB / 核心报表（原始数据治理、多维查询关联）；
  - 数据流：Hive / DB → ES → 数字化系统 → Agent；T-1 大盘一次 5–10 分钟，当日支持 H+1。

### 核心引擎：单次分析的闭环

`Thought → Planner → Action · Executor → Observation → Result`

| 步骤 | 做什么 |
|------|--------|
| 01 Thought | 想清问题与核心步骤；think tool 停下来深想 |
| 02 Planner | 按业务分析框架规划；调 Skills 归因 / Workflow |
| 03 Action · Executor | 经 MCP 调业务数字化取数；运行 Skill |
| 04 Observation | 读取结果；判断是否充分、有无异常 |
| 05 Result | 结论 + 数据支撑，结构化输出 |

信息不足 / 发现新线索，回到 Thought 继续下钻。

框架、知识、数据、兜底分别在哪一步注入：

| 注入点 | 承载 | 决定什么 |
|--------|------|---------|
| AI 能力框架 | 承载整个 Loop 与 think | 每步怎么想、怎么调 |
| Skills 业务知识 | 在 Planner 注入归因逻辑 | 按什么业务框架拆 |
| MCP + 业务数字化 | 在 Executor 取数、回算口径 | 数据与业务口径对齐 |
| Harness Engineering | 全程记录、质检、重试 | 模型出错，系统也能拦住 |

## 关键工程做法

### 模型选型与演进：能力先行跑通，国产替代降本

| 阶段 | 模型 | 依据 |
|------|------|------|
| 起步 · 海外大模型跑通场景 | Claude Sonnet 4.5 → 4.6 | SWE-bench Verified 领先，真实工程/编程任务成功率高；TAU-bench 工具调用可靠，电信/零售/航空 Agent 场景领先；200K → 1M 长上下文，复杂任务连续执行数十小时不跑偏 |
| 降本 · 国产大模型全量替代 | GLM 5.1 → 5.2 → 5.3-Flash | 推理/编程/Agentic 对标一线，长程任务开源 SOTA、1M 上下文；中文与本土场景好，国产算力、数据合规；Token 成本 -95%+，Flash 档把单价进一步压到零头 |

替代路径：用最强能力从 0 到 1 跑通，建立业务信任；真实业务平行评测、归因结论一致后全量替代。

业务分析 Agent 选模型，重点实测 6 项：工具调用成功率（少漏调、错调、重复调）、长上下文承载（多轮取数不丢目标）、复杂推理与归因准确率（结论可复算）、单 token 成本与缓存命中、响应时延与并发吞吐、数据合规（境内、权限可控）。

统一 MCP 工具协议：工具与模型解耦，底座可平滑替换、不被单一厂商绑定。

### 业务分析能力：概念、公式、Workflow + Few-Shot

核心指标拆解：**间夜 = 流量 × 转化 × 单订单间夜**（每个因子继续独立拆解）。

| 因子 | 含义 |
|------|------|
| 流量 | 请求流量规模，= Σ 各渠道 |
| 转化 | 漏斗 L2D · D2B · B2O，≈ 产品力 |
| 单订单间夜 | 人均连住，受目的地 / 客群结构影响 |

- **纵向：大盘逐级下钻**——大盘 → 区域 → 国家 → 城市 → 酒店；Δ 本级 = Σ 下一级贡献 ≈ Δ 产品力。
- **横向：三因子继续拆**——流量 = Σ 渠道；转化 = 新客 + 老客 = 高/中/低星 = Σ 价格段 ≈ 产品力；单订单间夜 ≈ 连住；结构项：目的地结构 / 新老客 gap / 预售占比。

Workflow 保证过程不跳步、可复算（ReAct + Plan/Execute 按公式下钻：思考/规划 → 调 MCP 取数 → 分析每级算贡献 pp → 再思考；Σ 下级贡献 ≈ 上级变化）；Few-Shot 固化高手下钻范例：

- Case1 日环比跌 → 某海岛产品力变差 +1% → 代理商未分销；
- Case2 周同比跌 → 某区域老客产品力变差 +2% → 外部临时发券。

两者共同增强 System1：同类问题知往哪拆、结论给依据；缩短探索、减少误判。

### 三套分析逻辑 × 可下钻维度树

| 逻辑 | 做法 | 作用 |
|------|------|------|
| ① 双基准对比 | 日环比（vs 昨天）· 周同比（vs 上周同日）；两基准交叉验证 | 排除星期周期，避免把周期波动误判成异常 |
| ② 贡献度归因 | 每个维度计算对大盘波动的贡献 pp；Σ 各维度贡献 ≈ 大盘实际变化 | 谁拉动、谁拖累可逐维复算 |
| ③ σ 异常检测 | 均值 ± 标准差设阈值，2σ 关注、3σ 重点排查 | 量化异动程度；挖出被大盘平均掩盖的小场景隐藏异动 |

判定顺序：双基准判「是不是异常」→ 贡献度归因「谁造成的」→ σ 检测补「漏掉的小场景」。

可下钻维度：基础（目的地 / 新老客 / 星级 / 酒店 / ADR / 入离分布）、货（直采 · 代理）、流量（站内交叉 · 站外渠道 · 自然流量）、产品力（支持多级归因）；核心指标覆盖间夜 / 流量 / 转化率 / 取消率 / 收入 / 佣金率 / 赔付；维度自由叉乘，如某海岛 × 老客 × 高星 × 产品力。

### 七大模块数字化全景

| 模块 | 核心指标 | 特有查询 / 筛选维度 | 下钻能力 |
|------|---------|-------------------|---------|
| 订单 | 间夜、GMV、佣金率、补贴率、ADR、取消率 | 货源渠道、会员级别、新老客、支付方式 | 实时组合 |
| 产品力 | Lose 率 / 归因、Beat 深度 | 价格段、比价类型、抓取身份、代理商 | 三级归因 |
| 流量 | UV、PV、U2O | 渠道、新老客、客户端、搜索类型 | 实时组合 |
| 定价 | 佣金差、补贴差、补贴率、变现率 | 用户身份、支付方式、价格段、连住/提前天数 | 多级归因 |
| 供应链 | 底价优势率、禁售量 | 代理商马甲、主体 | 实时组合 |
| 搜索 | S2O/S2D/D2B/B2O、搜索效率、失衡率 | 渠道、新老客、特色酒店、位置 | 实时组合 |
| 服务 | 单间夜赔付、赔付占比、缺陷率、顺畅度 | 赔付类型、渠道、ADR 范围、用户 ID | 实时组合 |

通用可拆解维度：时间（日/周/月 · 环比/同比）、目的地（区域/国家/城市/酒店）、星级/档次、新客/老客、渠道/货源（站内/站外 · 直采/代理）。

### 业务口径准确逻辑：数字化 4 大优势 + 数据连通 + 组织协同

四大优势：扩展性（指标、模块任意增加，理论上无限）、口径准确（与业务完全对齐，拿到数免再核对）、动态计算（佣金率等指标按需计算，不写死）、实时性（实时 H+1；T-1 大盘 5–10 分钟可得）。

数据分层与连通机制：

```
原始数据源 DB / Hive / SQL → 1:1 存储（不丢、不重）
各模块 1:1 请求/定价/间夜/赔付 → trace 关联
各模块 ES → 数据治理、多维查询 → 业务视角加工
业务数字化系统（统一口径）→ MCP → Agent
数据流：Hive / DB → ES → 数字化系统 → Agent
```

两个组织前提：

1. **数据治理是重投入**：指标逐一覆盖，前期做口径对齐、验数；细节决定口径能否被信任。
2. **运营高度配合**：日常系统取指标、做功，否则口径逐渐对不齐；系统要持续被使用。

### 幻觉治理：不靠「更强的模型」，靠 Harness Engineering

原文判断：幻觉是工程问题，用脚手架约束，而不是祈祷模型不犯错。下表均为线上真实踩过的坑（P13）：

| 工程脚手架（Harness） | 约束住的典型幻觉 |
|---------------------|----------------|
| 工具结果完整化：大 JSON 转存文件并强制读取，限制单次行数分批获取 | 数据被截断预览，模型基于不完整数据，编造不存在的结论 |
| 关键动作工程化：上传、出图走固定工程通道，不让 LLM 写代码 | 编造图片 URL（文档 404/空白），编造不存在的上传工具名 |
| 外部事实注入：注入当前时间、节假日查询工具，think tool 强制推理 | 「最近一周/30 天」理解不一致，节假日同比日期对齐错误 |
| 多层兜底：链接质检、接口重试与异常打点，结论必须引用数据来源 | 接口空返回导致分析不全，结论缺乏支撑、trace 不可追溯 |

本质：**把「相信模型不会错」换成「即使模型出错，系统也能拦住」——能力边界要诚实，结论要可追溯。**

### 分析规模化：拆分 Skill + 勾选 / 自定义

Before（单场景分析）：间夜 · 赔付 · 定价 · 收入 · 信息 · 营销全部耦合在一条主链路——Prompt 臃肿、能力互相干扰；要改主链路仅研发能维护。

After：Master Agent · 多场景组合 + 勾选/定制 Skill（间夜分析 Skill、赔付分析 Skill、定价分析 Skill、流量分析 Skill、……、自定义 Skill）。每个 Skill 独立定义口径、输入输出与分析流程；新增业务 = 新增一个 Skill；热插拔、可独立迭代，业务同学可自行共建，不再只依赖研发。

规模化关键升级：角色、场景、技能三大管理——

- **角色管理**：不同角色看到不同场景、技能，权限按角色分配；
- **场景管理**：分析场景可配置、可沉淀，支持跨场景组合复用；
- **技能管理**：勾选 Skill、在线调试、自定义与个人 Skill 沉淀。

配套机制：业务自己「教」Agent（运营在线调试、经验沉淀复用，无需研发发版）；读写分离（只读分析自动执行，写动作审批/灰度/回退，最小权限、全程留痕）。本质：把「增强 System1」开放给业务，能力扩展与数据安全同时成立。

### 使用方式：自动报告 · 随问随答 · 定制分析页面

| 场景 | 做法 |
|------|------|
| 主动 · 每日自动巡检报告 | 每日早晨定时运行，各模块报告自动推送核心业务群；今日 Highlight：大盘双基准对比 + 异动区域贡献 pp（例：大盘间夜环比 +1.01pp，某国 +0.53pp、某区域 -0.37pp）；异常即时播报，附原因与建议动作 |
| 被动 · 临时提问 | 临时业务思考直接提问，快速取数、分析，结果直接使用；例：尝试分析业务增长洼地，Agent 扫描最近一年数据，直接给出业务洼地及数据支撑；支持追问、下钻、修正、导出飞书文档 |

两个操作入口：

- **飞书机器人（单场景）**：主动定时推送 + 被动多轮对话；多轮追问/下钻/修正/导出，会话上下文保持 4 小时；过程与结论沉淀在飞书，可追溯、可协作。
- **定制分析页面（多场景）**：多场景组合 + 勾选 Skill + 自定义 Skill、在线调试；按「场景 + Skill」分配权限；业务可自助共建。

### 案例一：税费赔付跨平台治理

- 现象：每周赔付过万，连续多周；根因是系统性信息缺失——城市税 / 旅游税 / 目的地税未在页面展示；集中欧美目的地，用户到店补费引发赔付。
- 动作链（AI 定位，跨团队执行）：聚合赔付 Case → AI 定位缺失税费科目与酒店清单 → 反向 push 供应链团队 / 用户体验团队补全 → 新订单页面正确展示，同类赔付持续收敛。
- 价值：从「单笔 Case」治理为「一类问题」，转向事前预防。

### 案例二：分析业务增长洼地

主动提问 AI（开放、长周期、跨区域）：去年 x 月到今年 y 月离店间夜，分析核心区域寻找增长洼地。Agent 自动跑完 4 步：

1. 解析问题（13 个月范围 / 区域维度）；
2. 区域扫描（双基准 + 贡献 pp + σ）；
3. 逐层下钻（客群 / 星级 / 货 / 价格段）；
4. 汇总结论（洼地清单 + 数据支撑）。

直接给出的洼地及归因（原文称与实际分析完全一致）：区域——某目的地占比偏低、跑输大盘；客群——新客转化弱、老客复购低；供给——某类货与低星 / 中段覆盖不足；根因——有流量、缺转化，卡在货与价格段供给。

### 案例三：赔付风险双向治理

**B 端供给（某目的地聚合算法）**：AI 巡检赔付额 / 佣金异常交叉点——赔付率：代理商 A、B 约为大盘的数倍；代理商 C 在另一目的地约 100%、单均赔付约大盘 5 倍，问题藏在多维度交叉定位异常点里。

行动闭环：发现（特定代理商 × 目的地下系统性产生高额赔付）→ T+1 决策（A、B 在该目的地禁用问题房型聚合，按风险维度灰度）→ T+8 扩大（C 在另一目的地同步禁用）→ T+14 回验（未再发现聚合导致的赔付，零复发）。

**C 端用户（风险用户分层）**：主动提问 AI，分析出小额高频，叠加多维识别高风险用户——约 60+% 赔付 < x 百元、约 80+% < y 千元（原文以 x/y 占位，具体金额不确定）。分层管控（人确认口径与力度）：高风险限制自动赔付、转人工复核并标记；中风险预警、审核加严、要求凭证；低风险保持正常流程、不增加摩擦。

治理成果（截至 9 月）：拉黑数百名高频高风险用户、限制访问报价；预计每月再省数万元。

原文总结：B 端供给 + C 端用户双向治理——AI 定位与分层，人做小范围灰度决策，数据回验，行动闭环、可回退、可追溯。

## 经验与边界

### 能力边界（P18）

| 边界 | 应对 |
|------|------|
| 依赖数据底座、前期接入治理成本高 | 先接高价值数据源，边用边治、滚动沉淀 |
| 写动作需人审批、尚非全自动 | 高危动作人审，低风险动作灰度放开 |
| 长尾、强外部常识问题仍可能出错 | 双基准 + σ 检测 + 人审兜底，结论必给依据 |

什么场景该交给 Agent：

- **适合**：口径清晰、可结构化、需多维交叉、高频重复的分析；
- **不适合**：无数据支撑、强主观判断、需无审批跨系统写操作。

### 三条收束（P19）

1. **数据治理，决定系统的下限**——口径统一、数据完整；底座不干净，再强的模型也只是更快地产生错误结论；每新接一个数据源，Agent 的分析边界就外扩一圈。
2. **业务架构，决定系统的上限**——持续沉淀与提升 System1（业务直觉与控场能力），让新人尽早变成老员工；模型可整体替换，壁垒长在自己手里。
3. **行动闭环，决定系统的价值**——AI 项目本质还是项目：业务 Owner、标准 SOP、明确动作、结果回验，一个都不能少。
