# 小世界网络：从被动响应到主动协同

> **核心主张**：单个 Agent 会理解业务并执行行动之后，下一个问题是"多个 Agent 如何自主发现彼此、自主协商分工、自主协调行动"。第 9 章的回答是小世界网络（Small World Network，SWN）——"由**可信智能体**基于**共享本体**、**内置合约**和 **OBAC 使用控制矩阵**，围绕**场景目标**自主结伴、自主协同、自主执行而形成的**动态协同网络**"（9.1.3、9.3.1 / PDF 第 149、151 页）。

本页覆盖第 9 章第 9.1–9.10 节（PDF 第 148–168 页）。定位一句话：**互联是手段，协同是目的**——向下区别于静态语义底座，向上区别于开放域互联（9.3.4 / PDF 第 155 页）。上游脉络见 [[ontology-driven-action-loop]]（第 8 章的单 Agent 行动闭环），下游去向见 [[data-asset-operation-2]]（第 10 章）与 [[trusted-ai-infrastructure]]（第 15 章）。

**本章在全书中的位置（原文自述）**：本章"为后续章节讨论数据资产运营 2.0 和可信 AI 基础设施提供协同机制的理论基础"（9.1.3 / PDF 第 149 页）。

## 1 问题的提出：智能体协同的最后一公里

### 1.1 从单点智能到群体智能

原文先复述第 8 章的核心结论：本体让 Agent 不仅"知道"数据是什么，而且"理解"数据意味着什么；不仅"看到"对象的状态，而且"推理"状态变化的影响；不仅"执行"行动，而且"理解"行动的约束和后果（9.1.1 / PDF 第 148 页）。

但这一结论"回答的是单个 Agent 如何理解业务世界并执行行动的问题"。多 Agent 协同随之出现三个新问题：**Agent 之间如何自主发现彼此、自主协商分工、自主协调行动？**（9.1.1 / PDF 第 148 页）

**传统做法及其局限**（9.1.1 / PDF 第 148 页）：

| 维度 | 原文内容 |
|---|---|
| 传统协同方式 | 通过预定义的工作流引擎实现；业务流程建模工具定义好每一步的调用关系和参数传递规则，系统按流程定义依次调用各服务 |
| 仍然有效的场景 | 流程稳定、参与方固定 |
| 失效的原因 | 智能体时代业务流程越来越动态，参与方越来越多元，协同关系越来越复杂，预定义工作流的局限性日益凸显 |

### 1.2 工业场景中的协同困境

**工业互联网十年成就（原文引用的数据，逐项保留 / 9.1.2 / PDF 第 148 页）**

| 指标 | 数值 |
|---|---|
| 工业 5G 专网数 | 超 **2.5 万个** |
| 标识注册量 | 超 **7400 亿个** |
| 具有一定影响力的工业互联网平台 | 超 **340 家** |
| 融合应用覆盖 | **41 个**工业大类全覆盖 |

**"最后一公里"的三个错位**（原文用三组对仗表述 / 9.1.2 / PDF 第 148 页）：

1. 数据上云了，但**智能体用不起来**；
2. 平台建好了，但**业务闭环跑不通**；
3. 模型训练了，但**行动执行不了**。

**困境之一：根源在语义**（9.1.2 / PDF 第 148 页）

| 数据对象 | 系统 A 的口径 | 系统 B 的口径 | 冲突性质 |
|---|---|---|---|
| 设备数据 | MES 中一套编码 | ERP 中是另一套编码 | 编码不一致 |
| 质量数据 | QMS 中的口径 | MES 中的口径不同 | 口径不同 |
| 供应链数据 | WMS 中的定义 | SCM 中的定义不一致 | 定义不一致 |

结论句："跨系统的数据虽然'传得到'，但智能体'读不懂'。"（PDF 第 148 页）

**困境之二：更深层在协同机制**——原文连设五问，句句指向"Agent 之间的对等协商"，而非"人对系统下指令"（9.1.2 / PDF 第 148 页）：

| # | 原文问题 | 隐含的能力缺口 |
|---|---|---|
| 1 | 设备监测 Agent 检测到异常后，它怎么知道**该通知谁**？ | 伙伴发现 |
| 2 | 诊断 Agent 怎么确认设备监测 Agent 的**身份和权限**？ | 身份可信 |
| 3 | 决策 Agent 生成的切换方案怎么**传递给**执行 Agent？ | 语义传递 |
| 4 | 执行 Agent 怎么确认自己**有权调用 MES 接口**？ | 权限边界 |
| 5 | 维保 Agent 怎么知道**该创建什么样的工单**？ | 行动规则 |

原文强调这五个问题"**不在身份码里，不在词元计量里，也不在最小世界模型里**。它们需要一个更高层次的协同机制"（9.1.2 / PDF 第 149 页）。

### 1.3 本章的定位：向下与向上的两条分界线

原文用"向下 / 向上"两条分界线给本章定位（9.1.3 / PDF 第 149 页；另见 PDF 第 152 页的图）：

| 方向 | 对照概念 | 解决的问题 | 性质 |
|---|---|---|---|
| 向下 | [[minimal-world-model]] | 本体怎么建、一个闭环怎么跑通 | 静态的语义底座 |
| 本章 | 小世界网络 | 多个智能体怎么围绕场景目标自主协同 | 动态的协同机制，或"具有聚类效应的最小世界模型矩阵" |
| 向上 | [[foundation-protocol]] 所代表的智能体互联网 | 任何智能体在任何场景下如何发现、通信、协作 | 开放域的概念（受控域 vs 开放域，详 4.3 节） |

## 2 理论基础：小世界网络理论与多智能体协同

### 2.1 小世界网络理论的起源与核心发现

原文对理论来源的表述（9.2.1 / PDF 第 149 页）：

- 小世界网络理论**起源于复杂网络研究领域**；
- **1998 年**，Watts 和 Strogatz 在《自然》杂志发表了开创性论文，提出了小世界网络模型；
- 核心发现：**在规则网络和随机网络之间，存在一类特殊的网络结构，它同时具备高聚类系数和短平均路径长度**。

**两个特征的原文释义**（9.2.1 / PDF 第 149 页）

| 特征 | 原文释义 | 工程含义 |
|---|---|---|
| 高聚类系数 | 网络中的节点倾向于与其邻居的邻居也相互连接，形成**局部密集的簇** | 簇内强连接 |
| 短平均路径长度 | 任意两个节点之间的最短路径长度随节点数量增加仅呈**对数增长**，而非线性增长 | 全局低延迟 |

**三种网络的对照**（9.2.1 / PDF 第 149 页）

| 网络类型 | 聚类 | 路径 | 原文判断 |
|---|---|---|---|
| 规则网络 | 高 | 长 | — |
| 随机网络 | 低 | 短 | — |
| 小世界网络 | 高 | 短 | 通过**引入少量长程连接**同时实现高聚类和短路径 |

原文对这一发现的评价是"揭示了一种介于完全有序和完全随机之间的网络组织原则"（PDF 第 149 页）。

> **引用边界**：以上理论叙述即原文全部内容。原文未给出聚类系数与平均路径长度的数学定义、公式或阈值，也未引用 Watts–Strogatz 之外的任何文献，**本页不补充**。

### 2.2 小世界结构在多智能体系统中的研究进展

原文引述"一项发表于 arXiv 的研究"（9.2.2 / PDF 第 150 页）——**原文只写"一项发表于 arXiv 的研究"，未给出论文标题、作者、编号或年份**。

| 项 | 原文内容 |
|---|---|
| 研究定位 | 系统探讨了将**小世界连接作为多智能体系统设计先验**的可能性 |
| 核心论点 | 小世界结构平衡了**局部聚类**和**长程整合**；这种结构在生物神经系统中已被证明能够促进**快速信息流和鲁棒集体行为** |
| 实验平台 | **多智能体辩论**（multi-agent debate） |
| 关键结果 | 小世界连接在**保持几乎相同准确率和词元成本**的同时，能够**显著稳定共识轨迹** |
| 提出的方案 | **不确定性引导的重连方案**：在**认知差异较大**的 Agent 之间添加**长程捷径**，构建能够适应任务难度和 Agent 异质性的**可控**小世界结构 |
| 概括的四重意义 | ①推理的**稳定器** ②鲁棒性的**增强器** ③可扩展的**协调器** ④涌现认知角色的**归纳偏置** |

原文把该研究迁移到工业场景的方式是一句类比的因果链（9.2.2 / PDF 第 150 页）：在多智能体辩论中，小世界结构通过少量长程连接让不同知识背景的 Agent 快速交换信息，同时通过局部高聚类保持每个 Agent 群体的内部一致性——"这一机制同样适用于工业场景中的多 Agent 协同"。原文未提供工业场景的对应实验或数据。

### 2.3 从理论到工程：三种组织模式

原文把方法论意义概括为"为多智能体协同提供了一种**介于集中式编排和完全分布式之间**的组织原则"（9.2.3 / PDF 第 150 页）。三种组织模式的完整对照见 PDF 第 151 页的图"多智能体协同的三种组织模式"（原文正文只给了前两种的优缺点，**小世界网络的"缺点"一项只出现在图中**）：

| 维度 | 集中式编排 | 小世界网络（中间路径） | 完全分布式 |
|---|---|---|---|
| 图形结构（图） | 一个"中心节点"向四周辐射的连接 | 三个虚线圆环簇，簇内密集、簇间由橙色**长程连接**串起 | 全连接图，每个节点与所有其他节点相连 |
| 分工方式 | 由中心节点负责发现伙伴、分配任务、协调行动 | 局部高密度协同 + 全局少量长程连接 | 每个 Agent 自主发现伙伴、自主协商分工 |
| 优点（图/文） | 全局可控 | 高效协同、兼顾效率与灵活性 | 灵活性强 |
| 缺点（图/文） | 中心节点成为瓶颈，且难以适应动态变化的环境 | 设计与治理要求较高（**见于图，正文未列出**） | 协调成本高，且难以保证全局一致性 |
| 原文结论 | — | 既不需要全局的中央调度，也不需要每个 Agent 与所有其他 Agent 直接连接 | — |

同一张图的下半部分是"**小世界网络的结构特征**"（PDF 第 151 页）：

- 图例：**局部连接（域内）**、**长程连接（域间）**；
- 演进链：**局部高聚类**（域内 Agent 紧密协同、高频交互）→ **全局短路径**（少量长程连接实现跨域快速触达）→ **高效协同**（兼顾局部效率与全局响应速度）；
- 工业场景的适用性一节以四域并列呈现：**设备域、生产域、质量域、供应链域**，每域一个虚线圆环簇，域间用橙色长程连接串成一条链；右侧说明"**域内高聚类协同**（专业深入、响应快速）"与"**域间长程连接**（跨域触达、信息流通）"。

原文对此的适用性论证是（9.2.3 / PDF 第 150–151 页）：工业业务域之间天然存在边界——**设备域、生产域、质量域、供应链域**各有其专业知识和业务逻辑；域内 Agent 需要紧密协同，域间 Agent 需要快速触达——小世界结构恰好匹配这种"域内高聚类 + 域间短路径"的协同需求。

## 3 形式定义与拓扑特征

### 3.1 形式定义与五个要素

**定义**（9.3.1 / PDF 第 151 页；同一表述也在 9.1.3、9.10 与图 3 中出现）：小世界网络是**由可信智能体基于共享本体、内置合约和 OBAC 使用控制矩阵，围绕场景目标自主结伴、自主协同、自主执行而形成的动态协同网络**。

| # | 要素 | 原文规定 |
|---|---|---|
| 1 | **可信智能体** | 节点是经过**身份验证和能力验证**的可信智能体；每个智能体拥有**唯一身份码**，身份码关联**能力、权限、委托关系**；依据 **GB/Z 185.2—2026**，智能体身份码采用 **OID 分层编码体系**，具备**全球唯一性、可解析性和可追溯性** |
| 2 | **共享本体** | 智能体**共享同一个本体**；本体定义**业务对象、关系、状态、行动和公理**；共享本体是智能体相互理解的**语义基础** |
| 3 | **内置合约** | 智能体遵循**同一套内置合约**；合约定义行动规则——**什么条件下谁该行动、触发什么行动、行动的参数是什么、预期结果是什么**；合约是**机器可读的、可自动执行的** |
| 4 | **OBAC 使用控制矩阵** | 受同一套权限边界约束；**语义级访问控制**，精确到**概念、实体、实例、属性**级别 |
| 5 | **动态协同网络** | **不是**静态的组织架构，而是动态的协同网络；智能体根据场景目标**自主结伴**，**场景结束后网络自然解散** |

图上对四个要素另有一句短标签（PDF 第 152 页，"小世界网络定义"面板）：共享本体——"**统一语义、统一模型、统一接口**"；内置合约——"**合约驱动、规则透明、自动执行**"；OBAC 使用控制矩阵——"**基于主体（O）、客体（B）、动作（A）、条件（C）的精细化授权与控制**"。

> **需注意的口径冲突**：正文 9.6.3 把 OBAC 解释为 **Ontology-Based Access Control（基于本体的访问控制）**，并明确"以本体中的概念、对象、属性及关系为控制对象"；而图上把 O/B/A/C 解为"主体/客体/动作/条件"。两种解释原文并列存在，本页并录，见第 10 节。

### 3.2 拓扑特征："局部高聚类 + 全局短路径"

原文的拓扑特征就是这一句话，并给出两个层面的具体例子（9.3.2 / PDF 第 152 页）：

| 层面 | 原文内容 | 具体实例 |
|---|---|---|
| **局部高聚类** | 同一业务域内的智能体紧密协同、连接密集 | 设备域形成一个高聚类簇，生产域形成第二个，供应链域形成第三个 |
| **全局短路径** | 不同业务域之间通过**少量长程连接**快速触达 | 设备域的**诊断 Agent**↔生产域的**排产 Agent** 有一条长程连接；排产 Agent↔供应链域的**采购 Agent** 有一条长程连接；通过这些长程连接，设备故障的影响可以"**在几步之内传播到供应链**" |

补充说明：原文称"在学术研究中，这种结构已被证明能够促进快速信息流和鲁棒集体行为"；对多智能体系统而言，"小世界结构在保持局部协同一致性的同时，实现了全局信息的高效传播"（9.3.2 / PDF 第 152 页）。

**PDF 第 152 页复合图的其余内容**（正文未文字化）：

- 左上"**最小世界模型**"面板，副题"回答：本体怎么建、怎么跑通一个闭环"；环形四节点：**感知**（获取状态）→**推理**（理解与决策）→**执行**（采取行动）→**反馈**（结果评估），中心为"**本体**"，底部标"**闭环运行**"；
- 右上"**从'最小世界模型'走向'小世界网络'**"面板，副题"当多个最小世界模型、多个智能体围绕同一个场景目标自主结伴、自主协同、自主执行时，形成'小世界网络'"；三个业务域（**业务域 A / B / C**）簇由长程连接串起，顶端是"**场景目标**"；下方三个动作标签：**自主结伴 → 自主协同 → 自主执行**；
- 中部"**拓扑特征：局部高聚类 + 全局短路径**"三连面板：**局部高聚类（同域紧密协同）**——"同一业务域内智能体高密度互联、信息与资源高效共享"→**全局短路径（跨域快速触达）**——"跨业务域通过少量长程连接，快速到达任意目标"→**小世界效应**——"既保持局部紧密协同，又具备全局高效可达"；
- 下部"**小世界网络运行机制**"六步条带：**目标驱动**（场景目标拆解与对齐）→**自主发现**（发现可协作的智能体）→**合约协商**（达成合约并建立信任）→**协同执行**（按合约自主协同执行）→**结果验证**（验证结果与信誉更新）→**动态演化**（网络结构持续优化）。

> **口径冲突（重要）**：正文 9.7 节的运行机制是**四步**（场景识别→伙伴发现→网络构建→自主执行），而这张图的条带是**六步**（目标驱动→自主发现→合约协商→协同执行→结果验证→动态演化）。图上多出"合约协商""结果验证""动态演化"三个环节，正文未展开这三项。本页以正文四步为主叙述，六步条带单列于此，见第 10 节。

### 3.3 与传统服务的区别：从"人找服务"到"服务找人"

原文的核心逻辑对比（9.3.3 / PDF 第 152–153 页）：传统网络服务与 APP 服务的核心是"**人找服务**"——用户登录、浏览、选择、输入、点击，系统**被动响应**；小世界网络的核心是"**服务找人**"——系统**主动感知场景，自主发现伙伴，自主构建网络，自主执行任务**，人从**操作者**变为**监督者和例外处理者**。

**七维对照表（PDF 第 153 页，原表七行完整复述）**

| 维度 | 传统网络服务 | APP 服务 | 小世界网络 |

| 行动发起者 | 人 | 人 | **系统（本体/智能体）** |

| 核心机制 | 页面路由、API 调用 | 功能菜单、参数传递 | **本体语义 + 合约 + 使用控制** |
| 协同方式 | 人协调多个系统 | 人协调多个 APP | **智能体自主结伴、自主协同** |
| 人的角色 | 操作者 | 操作者 | **监督者、例外处理者** |

原文的一句话总结："传统网络是你去找服务，小世界网络是服务来找你。"（PDF 第 153 页）

**同一页的三栏示意图**（PDF 第 153 页下半部分，正文未文字化）：

## 4 三组区别：与最小世界模型、与智能体互联网

### 4.1 与最小世界模型（MWM）的区别

原文立场："小世界网络与最小世界模型是两个不同层次的概念"（9.3.3 / PDF 第 154 页，原文此处小节号与 9.3.3"与传统服务的区别"重号）。

**七维对照表（PDF 第 154 页，原表完整复述）**

| 维度 | 最小世界模型 | 小世界网络 |
|---|---|---|
| 核心问题 | 本体怎么建、**一个闭环**怎么跑通 | **多个智能体**怎么自主协同 |
| 本质 | **静态**的语义底座 | **动态**的协同网络 |
| 节点 | 对象、关系、状态、行动 | **可信智能体** |
| 连接 | 对象之间的**语义关系** | 智能体之间的**协同关系** |
| 运行方式 | 本体推理、影响传播 | 自主结伴、自主执行 |
| 目标 | 跑通一个业务闭环 | 实现群体智能协同 |
| 关系 | 小世界网络的**语义基础** | 最小世界模型的**协同跃迁** |

**原文的三段递进论证**（PDF 第 154 页）：

1. **触发条件**：当**多个最小世界模型、多个智能体**围绕同一个场景目标自主结伴、自主协同、自主执行时，系统就从"最小世界模型"走向"小世界网络"。
2. **定位比喻**："最小世界模型是'**本体定义世界**'的起点，小世界网络是'**本体驱动协同**'的跃迁。"
3. **相互依赖**："没有最小世界模型，小世界网络就没有语义基础；有了小世界网络，最小世界模型的价值才能从**单点智能**走向**群体智能**。"

详见 [[minimal-world-model]]（第 5 章）。

### 6.1 前提一：本体构建完成

原文要点（9.5.1 / PDF 第 158 页）：

1. **本体定义五元组**：业务**对象、关系、状态、行动和公理**；
2. **"语义宪法"规定了四件事**：业务世界中有哪些对象、对象之间有什么关系、对象处于什么状态、可以执行什么行动、**什么行动不能被违反**（原文实为五问，见原文措辞）；
3. **反面例子（EQ003）**：设备监测 Agent 发送"设备 EQ003 故障"消息时，诊断 Agent 需要知道 EQ003 是什么、故障是什么、故障会触发什么行动。**如果没有本体**，诊断 Agent 面对的只是字符串"EQ003"和状态值"故障"，它无法理解：EQ003 **属于哪条产线**、故障会**影响哪些订单**、应该**触发什么行动**；
4. **升级判断**：本体让智能体之间的通信从"**数据交换**"升级为"**语义交换**"；
5. **标准依据**：依据 **TC609-6-2026-XX《数据基础设施语义描述和互操作要求（征求意见稿）》**，跨节点交换数据或提供智能服务时，**应携带或可解析对应的语义描述**；节点经 **MCP、A2A、API** 等协议对外提供工具或智能服务时，**宜**在协议消息体中携带语义描述，包括**概念映射、口径、语义标识及本体引用**等；
6. **共识基础**："没有共享本体，每个智能体都有自己的**数据世界观**，协同就变成了语义层面的**鸡同鸭讲**。"

### 6.2 前提二：智能体身份可信

原文要点（9.5.2 / PDF 第 158–159 页）：

| 项 | 原文内容 |
|---|---|
| 身份码的作用 | 每个智能体都有**唯一身份码**，身份码关联**能力、权限、委托关系**；协作从"**黑户对话**"走向"**可信互操作**" |
| 标准发布 | **2026 年 5 月 22 日**，在工业和信息化部指导下，由**中国电子技术标准化研究院**组织**七十余家**产学研用单位共同研制的 **GB/Z 185—2026《人工智能智能体互联》系列国家标准**正式发布 |
| 标准地位 | 国内**首个覆盖智能体全生命周期**的互联标准体系；其定义的智能体身份码基于 **OID 分层编码体系**，为智能体建立**全局唯一身份标识**，为**跨厂商、跨平台、跨系统**的身份识别与**可信互认**提供统一基础 |
| 节点授权 | **国家 OID 注册中心**授权的智能体身份码节点（**OID：1.2.156.3088.1.0，高颂数科**），依据 **GB/Z 185.2—2026**，为每个 Agent 分配唯一身份码 |
| 身份码内涵 | 不仅标识"这个智能体是**谁**"，还关联"这个智能体的**能力范围、权限边界和委托关系**" |

**TAV（Trusted Agent Verification，可信智能体验证）三级验证框架**（9.5.2 / PDF 第 159 页）。依据：**GB/Z 185—2026 系列、GB/Z 242—2026、GB/T 47475—2026**。

| 级别 | 解决什么问题 |
|---|---|
| **身份验证** | 智能体身份是否**真实、有效、可追溯** |
| **能力验证** | 智能体**具备哪些能力、能力等级如何** |
| **价值验证** | 智能体**创造了多少价值、价值是否可计量** |
| **否决项** | **安全合规为否决项** |

详见 [[trusted-ai-infrastructure]]、[[effective-token-economy]]（词元是价值验证的计量基础）。

### 6.3 前提三：词元计量可用

原文要点（9.5.3 / PDF 第 159 页）：

1. **词元是价值单元**：每一次智能体调用都产生词元；词元为智能体服务提供价值单元，让每一次服务**可计量、可定价、可交易**；
2. **链式消耗例子**：设备监测 Agent 调用诊断 Agent 的服务，消耗词元；诊断 Agent 调用决策 Agent，消耗词元；决策 Agent 调用执行 Agent，消耗词元——"每一次调用都产生词元，每一次词元消耗都产生价值"；
3. **词元需要本体提供语义锚点**（关键的两个量化例子，原文数字完整保留）：

| 服务 | 词元数 | 本体锚点 | 词元代表的业务含义 |
|---|---|---|---|
| 设备监测 Agent 调用的"**数据访问服务**" | **1000** 个 | 关联到 **Equipment 实体**和 **equipmentStatus 属性** | "查询设备状态"这一服务 |
| 诊断 Agent 调用的"**模型推理服务**" | **2000** 个 | 关联到 **EquipmentFailureDiagnosis 模型**和 **diagnoseFailure 任务** | "执行设备故障诊断"这一服务 |

4. **"有效词元"概念**（高颂数科口径）："**没有本体，词元就只是一个数字**。有了本体，词元就有了语义含义，可以精确识别其代表的业务含义。"只有**同时满足时延、可用性、准确率等服务等级要求**、**最终被用户实际使用**的输出词元，才进入**商业计量**——为词元经济提供了可操作的计量范式。

详见 [[effective-token-economy]]（第 12 章专章展开）。

## 7 三个核心机制

原文的总纲："本体（**语义宪法**）、内置合约（**行动规则**）、OBAC 矩阵（**权限边界**）"（9.4.3 / PDF 第 157 页；9.6 / PDF 第 160 页）。

| 机制 | 角色 | 回答的问题 | 依据 |
|---|---|---|---|
| **本体** | **语义宪法** | 业务世界由哪些概念组成？概念之间是什么关系？什么条件下该执行什么行动？ | 9.6.1 |
| **内置合约** | **行动规则** | 谁该行动？触发什么行动？行动的参数是什么？预期结果是什么？ | 9.6.2 |
| **OBAC 矩阵** | **权限边界** | 这个 Agent 有没有权限执行这个操作？方案在不在安全边界内？ | 9.6.3 |

### 7.1 机制一：本体作为语义宪法

原文明确："本体作为'语义宪法'，为小世界网络提供了**三样东西**"（9.6.1 / PDF 第 160 页）：

| 提供的东西 | 原文释义 | 智能体因此知道 |
|---|---|---|
| **概念的地图** | 本体定义了业务世界中有哪些概念 | 业务世界**不是由字段组成的，而是由概念组成的** |
| **关系的指南** | 本体定义了概念之间的关系 | 概念**不是孤立的，而是相互关联的** |
| **行动的规则** | 本体定义了概念的约束和行动 | 在什么情况下**应该执行什么行动** |

**设备故障处置的例子**（9.6.1 / PDF 第 160–161 页）

| 项 | 原文内容 |
|---|---|
| 对象类型 | **Equipment、ProcessUnit、ProductionLine、Order、Risk、Action**，以及它们之间的**对象属性** |
| 约束规则一 | 一个设备**必须属于一条产线** |
| 约束规则二 | 一个设备**只能有一个设备编号** |
| 约束规则三 | 设备故障时**必须触发影响分析** |
| 语义上下文传播链 | 当设备监测 Agent 发现 **EQ003** 故障时，诊断 Agent 通过本体查询自动获取完整语义上下文：**EQ003 属于工艺单元 PU001，PU001 供给工艺单元 PU002，PU002 属于产线 PL001，PL001 生产订单 O001** |
| 用途 | 让诊断 Agent 能够**沿着关系链传播影响**，判断故障的**影响范围** |

> 原文在本机制中没有讨论本体的版本管理、构建方法。构建方法见 [[ontology-six-step-method]]、[[semi-auto-ontology-and-lightning-action]]；治理见 [[ontology-governance]]。

### 7.2 机制二：内置合约作为行动规则

原文明确："内置合约是小世界网络的'行动规则'，为智能体之间的协同提供**执行依据**。"（9.6.2 / PDF 第 161 页）

**内置合约 vs 传统法律合同（原文对比）**

| 维度 | 传统法律合同 | 内置合约 |
|---|---|---|
| 书写语言 | 自然语言 | **机器可读的语言** |
| 执行依赖 | **法律体系** | **技术系统** |
| 执行方式 | 依赖人工主张与司法救济 | **自动执行** |

**内置合约的五项内容（原文完整列出 / PDF 第 161 页）**

| # | 内容项 | 原文规定的范围 |
|---|---|---|
| 1 | **数据内容** | 哪些数据、数据范围是什么 |
| 2 | **数据使用者** | 谁可以使用、使用者的身份是什么 |
| 3 | **使用方式** | 怎么使用——查询、分析、建模、训练 |
| 4 | **使用次数** | 使用多少次——一次性、限量、不限量 |
| 5 | **使用环境** | 在什么环境下使用——**数据沙箱、隐私计算环境** |

> 注意：这五项是原文在"内置合约"名下给出的完整清单，与 [[ontology-data-circulation-obac]]（第 13 章）讨论的使用控制要素同构——但原文在本章**没有**明确说这两者是同一套机制，本页不作合并断言。

**设备故障处置的合约规则（六个 Agent 的"必须"义务 / PDF 第 161 页）**

| 角色 | 合约规定的义务 |
|---|---|
| 设备监测 Agent | 设备故障时，**必须生成告警** |
| 诊断 Agent | **必须基于本体推理**判断故障类型和影响范围 |
| 决策 Agent | **必须沿关系链传播影响**并判断风险等级 |
| 执行 Agent | **必须在权限范围内**调用 MES 接口执行切换 |
| 维保 Agent | **必须创建维保工单** |
| 协同 Agent | **必须协调各智能体并更新状态** |

原文强调"这些规则是机器可读的、可自动执行的"（PDF 第 161 页）。

### 7.3 机制三：OBAC 矩阵作为权限边界

原文开局两问界定问题："执行 Agent 有没有权限调用 MES 接口？决策 Agent 生成的方案在不在安全边界内？"（9.6.3 / PDF 第 161 页）

**OBAC 是什么**（原文定义 / PDF 第 161 页）：**OBAC（Ontology-Based Access Control）**，即**基于本体的访问控制**，是一种利用**语义网技术**，通过**领域本体中的概念和关系**实现**细粒度访问控制**的方法。

**与传统访问控制的差别（原文对照）**

| 对比维度 | 传统访问控制 | OBAC |
|---|---|---|
| 控制对象 | **资源** | 本体中的**概念、对象、属性及关系** |
| 表达粒度 | "用户 A 可以访问资源 B" | "用户 A 可以访问**属于 Equipment 类的、且位于 ProductionLine(A) 上的、状态为 Running 的 Equipment 实例**" |

这一例句是原文给出的完整 OBAC 表达，其特点是**三重条件叠加**（类 + 所属产线 + 状态）才定位到实例。

**OBAC 的三个核心功能（原文 / PDF 第 162 页）**

| 功能 | 原文内容 |
|---|---|
| **本体建模与语义约束** | 构建领域本体库，将设备、工艺、产品、订单等核心实体及其关系**形式化建模** |
| **语义级准入校验** | 基于本体规则实现**任务级**的权限验证 |
| **合规规则嵌入** | 将**数据安全法规、行业标准**转化为**机器可读的本体约束** |

**"五层 + 两库 + 两接口"架构（正文文字 + PDF 第 162 页图的组合复述）**

| 层 / 组件 | 组成（原文） |
|---|---|
| **接口层** | **PDP 接口**、**PEP 接口** |
| **决策层** | 请求解析、语义推理、决策引擎、合规检查、冲突消解 |
| **策略层** | 策略定义、策略存储、策略匹配、策略组合、策略冲突 |
| **本体层** | 本体加载、本体校验、本体推理、本体查询、本体版本 |
| **基础层** | 身份管理、凭证管理、令牌管理、审计存证、**国密算法** |
| **两库** | **策略库**、**本体库** |
| **两接口** | **PDP 接口**、**PEP 接口**（原文重复强调） |

图中补充了正文未列出的两库内部条目与接口侧动作（PDF 第 162 页，"OBAC 组件'五层 + 两库 + 两接口'架构"图）：

| 组件 | 图中条目 |
|---|---|
| **PDP 接口**（图左侧竖条，四个动作） | 请求接收、决策请求、决策响应、结果返回 |
| **PEP 接口**（图右侧竖条，四个动作） | 策略执行、访问控制、策略下发、执行反馈 |
| **策略库** | 策略规则存储、策略版本管理、策略元数据、**策略生命周期管理** |
| **本体库** | 本体模型存储、本体版本管理、**本体实例数据**、**本体索引管理** |

箭头方向（图）：左条 ↔ 主体内容区（**双向箭头**）；各层自 1 基础层 → 2 本体层 → 3 策略层 → 4 决策层 → 5 接口层**自下而上**；策略库指向 PEP 侧、本体库与 PEP 之间**双向箭头**。

**在小世界网络中的实际用法**（PDF 第 162 页）：执行 Agent 调用 MES 接口时，OBAC 检查执行 Agent 的**身份码、能力等级、委托关系**，确认其是否有权限执行切换操作。**如果权限不足，OBAC 会拦截请求，并通知协同 Agent**。

详见 [[ontology-data-circulation-obac]]（第 13 章）。

## 8 四步运行机制

原文："小世界网络的四步运行：**场景识别、伙伴发现、网络构建、自主执行**。四步运行构成完整的协同闭环。"（9.10 / PDF 第 167 页）

### 8.1 第一步：场景识别

原文定位："场景识别是小世界网络运行的**起点**。"（9.7.1 / PDF 第 162 页）

| 项 | 原文内容 |
|---|---|
| **输入（触发）** | 设备故障告警触发时，系统自动识别当前场景；也可由设备监测 Agent 检测到**振动值超标**触发 |
| **依据** | **本体中的事件定义**（不是规则匹配） |
| **具体判定** | 本体中定义了 **EquipmentFailure 事件**，该事件由 **Alarm 触发**，涉及 **Equipment、ProcessUnit、ProductionLine** 等对象 |
| **动作（原文关键判断）** | 场景识别"**不是简单的规则匹配，而是基于本体的语义推理**" |
| **输出（语义信息）** | 系统不仅知道"**发生了故障**"，还知道：①故障**发生在哪台设备上** ②设备**属于哪条产线** ③产线**正在生产哪些订单** |
| **对下一步的作用** | 这些语义信息为后续的**伙伴发现和网络构建**提供基础 |

### 8.2 第二步：伙伴发现

原文定位："伙伴发现是小世界网络运行的**关键步骤**。"（9.7.2 / PDF 第 163 页）

| 项 | 原文内容 |
|---|---|
| **输入** | 上一步识别出的场景语义信息 |
| **依据** | **本体中的协同关系定义** |
| **目标伙伴** | 诊断 Agent、决策 Agent、执行 Agent、维保 Agent、协同 Agent |
| **动作机制** | 沿着协同关系链**自动发现**需要参与协同的智能体 |
| **关键性质** | "伙伴发现是**定向式**的发现，不是**广播式**的邀请"——系统不会邀请所有智能体，而是沿着协同关系链**定向邀请**需要参与的智能体 |
| **输出** | 一份"应按何种关系参与协同"的智能体清单；原文称这种定向发现机制"确保了小世界网络的**效率和精准性**" |

**本体中定义的协同关系（原文全部列出 / PDF 第 163 页）**

| 源 Agent | 关系 | 目标 Agent |
|---|---|---|
| 设备监测 Agent | **Diagnoses** | 诊断 Agent |
| 诊断 Agent | **Informs** | 决策 Agent |
| 决策 Agent | **Commands** | 执行 Agent |
| 执行 Agent | **Triggers** | 维保 Agent |
| 协同 Agent | **Coordinates** | **所有其他 Agent** |

### 8.3 第三步：网络构建

原文定位："网络构建是小世界网络运行的**核心步骤**。"（9.7.3 / PDF 第 163 页）

| 项 | 原文内容 |
|---|---|
| **输入** | 场景语义信息 + 伙伴清单 |
| **依据（三重）** | ①本体中的**协同关系** ②内置合约中的**协同规则** ③OBAC 矩阵中的**权限边界** |
| **动作机制** | 多个智能体根据本体中的协同关系**自主结伴**；每个智能体根据协同关系**自主发现需要协同的伙伴，自主建立连接** |
| **关键性质** | "**去中心化的结伴，不是中心化的编排**" |
| **原文的连接动作序列** | 设备监测 Agent 发现需要诊断 Agent 的协助，主动建立连接 → 诊断 Agent 发现需要决策 Agent 的协助，主动建立连接 → 决策 Agent 发现需要执行 Agent 的协助，主动建立连接 |
| **输出（拓扑）** | 智能体之间形成"**局部高聚类 + 全局短路径**"的拓扑：设备域智能体形成高聚类簇，生产域智能体形成另一个高聚类簇，**协同 Agent 作为长程连接**，连接设备域和生产域 |

> 注意：此处的"协同 Agent 作为长程连接"是对 3.2 节"诊断 Agent↔排产 Agent 有一条长程连接"的具体化，两处举例不同但结构一致。

### 8.4 第四步：自主执行

原文定位："自主执行是小世界网络运行的**收口步骤**。"（9.7.4 / PDF 第 164 页）

| 项 | 原文内容 |
|---|---|
| **输入** | 已构建的网络 + 内置合约 + OBAC 矩阵 |
| **动作原则** | 智能体根据内置合约和 OBAC 矩阵自主执行行动，**不需要人的实时指令** |
| **输出** | 业务行动完成 + 状态更新 + 重新计算（见下表执行链） |

**六个 Agent 的完整执行链（原文顺序 / PDF 第 164 页）**

| 序 | Agent | 动作 |
|---|---|---|
| 1 | 设备监测 Agent | 生成告警 |
| 2 | 诊断 Agent | 基于本体推理判断**故障类型和影响范围** |
| 3 | 决策 Agent | 沿关系链传播影响并判断**风险等级** |
| 4 | 决策 Agent | 决定执行设备切换并**查询可替代设备** |
| 5 | 执行 Agent | 调用 **MES 接口**执行设备切换 |
| 6 | 维保 Agent | 创建**维保工单** |
| 7 | 协同 Agent | 协调各智能体并**更新状态** |

**"每一步自主、每一步都在权限边界内"的三处校验（原文 / PDF 第 164 页）**

| 动作 | 谁在检查 | 检查什么 |
|---|---|---|
| 执行 Agent 调用 MES 接口 | **OBAC** | 其**权限** |
| 决策 Agent 生成切换方案 | **内置合约** | 是否符合**行动规则** |
| 协同 Agent 更新状态 | **本体** | 是否符合**语义约束** |

## 11 本页分析（归纳，非原文）

> 以下为跨章串联与概念对照，不属于原文叙述。

1. **本章是第 8 章"行动闭环"的横向复制**：[[ontology-driven-action-loop]] 的闭环是**一个** Agent 沿"对象→查询→计算→规则→判断→Agent→行动→状态更新→重新计算"走一圈；第 9 章把这一圈的**每一环换成一个 Agent**——场景识别对应"对象"，伙伴发现对应"Agent 选择"，网络构建对应"Agent 之间接管调用"，自主执行对应"行动+状态更新"。据此（本页归纳），小世界网络的"四步"可视为**把行动闭环的主体从 1 个扩展到 N 个**。
2. **三个前提恰是前三篇的交付物**：本体（第 2–7 章）、智能体身份码与 TAV（第 15 章、[[trusted-ai-infrastructure]]）、词元计量（第 12 章、[[effective-token-economy]]）。第 9 章本身**不生产**这三个前提，只消费它们——这解释了为什么本章大量使用"如果……尚未完成，需先完成……"的句式。
3. **"协同 Agent"是本页认为最需要追问的角色**：它在四步中被反复引用（伙伴发现的对象、长程连接、协调与更新状态、被 OBAC 通知），但**它不是被伙伴发现机制发现的**（本体关系中它是 `Coordinates` 到"所有其他 Agent"的源端），也没有自己的触发条件说明。它有中心节点的功能（协调、通知、更新状态），却没有中心节点的名称——这与本章"去中心化结伴，不是中心化编排"的主张之间存在张力（本页归纳）。
4. **与 SORA 的"记录系统"互补**：[[sora-system-of-record-for-agents]] 讨论的是智能体行动需要可追溯的记录系统；本章的 OBAC **审计存证**与协同 Agent 的"更新状态"提供了同一诉求的一段实现，但原文未引用或对比 SORA。
5. **政策引用的时效性**：本章引用的事件（2026-04 政治局会议部署"六张网"、2026-06 八部门印发工业互联网实施意见、2026-05-22 GB/Z 185 发布）均发生在 2026 年上半年，与本书 2026 年 10 月的成书时间相距很近。原文未说明这些政策与标准在成书时是否已有配套细则，读者引用时宜回原始文件核对。
6. **与"智能体互联网"的关系被原文自己定义为"手段与目的"**：这意味着按原文的框架，IoA 类协议（AIP、MCP、A2A、ANP）在小世界网络中只承担**传输层**职责，真正的协同语义来自本体+合约+OBAC。对做协议选型的读者，这是一个明确的定位判断——但它也意味着本章的方案**无法脱离具体行业本体复用**（本页归纳）。
