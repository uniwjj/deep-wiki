# EasyData 冷表治理——以"表"为锚反向定位"任务"

> 来源：DataFunSummit《为 Agent 重建数据层：网易智企产品 AI Native 演进路径》（蒋鸿翔，2026-11-03）第 3 节"以存量表治理为例"部分与两张配图《怎么做的：以「表」为锚，反向定位「任务」》《最终效果：从 36,996 到 177 条精准动作》。

## 困境：为什么近 3.7 万个存量任务"没人敢动"

原文："难点在于无法轻易确认一张表已经无人使用。"配图把它拆成四个并列的障碍：

| 障碍 | 配图原话 |
|---|---|
| 目标模糊 | 下游的任务还是表？处置动作、风险、成功标准全不同 |
| 使用方法无法穷举 | 猛犸血缘之外还有云村、算法平台、第三方、报表 / API |
| 证据工具盲区 | HDFS 审计只有数据读写，看不到元数据依赖与外部调用 |
| 人工不现实 | 3.7 万任务、每个多节点，SQL 逐个判断不可承受 |

配图另加一条**特别警示**："「先回收权限」此路不通：撞上真实使用（任务 / 基线失效，风险不对称）；回收不可逆（自动回收也可能失败，回滚 ≠ 恢复原状）；权限状态漂移（ACL / 角色被清理，原始状态可能永远找不回）。"

## 破局思路：把不可穷举的问题，转换成可精确定位的问题

```
① 现成信号              ② 反向定位              ③ 过滤判定
平台「推荐下线表」清单  →  解析节点 SQL        →  剔除没在跑的节点 / 任务
数据治理 360 已有，无需新建   找出仍在写这些冷表的任务      输出任务级动作清单
```

配图"核心转换"一栏写作：

```
「判断表有没有人用」  不可穷举
                    ↓
「谁在写已判定冷掉的表」可精确定位
```

原文对应表述："数帆从数据治理 360 已有的'推荐下线表'清单出发，反向解析任务 SQL，定位仍在写这些表的活跃任务。"

## 核心规则设计：三步走——识别产出表 → 三重过滤 → 四类动作判定

### Step 1 · 产出表识别

- 与平台对齐：解析规则须与平台 **EasyParser（ANTLR AST）** 逐条对照，配图写作 **28/28 一致**
- 识别 8 类写入：`INSERT OVERWRITE` / `INSERT INTO` / `CREATE AS SELECT` / `MERGE INTO` 等
- 排除 6 类误判：`CREATE LIKE`、`VIEW`、`TRUNCATE`、`REFRESH`、导出目录、纯 `SELECT`

### Step 2 · 三重过滤

| 过滤 | 规则（配图原文） |
|---|---|
| ① 先过滤再判定 | 不过滤会严重虚增命中——**禁用节点已占约 26%** |
| ② 四道剔除 | 禁用节点 · 已暂停调度（以运维实例为准）· 虚拟节点 · 无产出表节点（DQC / 纯查询 / mscK） |
| ③ 淘汰判定 | 配图第 3 栏标题为"淘汰节点"，其具体规则在缩略图中未展开到可辨识程度，此处不作推断 |

### Step 3 · 四类调整动作

| 动作 | 判定条件（配图原文） |
|---|---|
| 任务下线 | 活跃 SQL 节点产出全部命中 + 非 SQL 仅 noop + 无下游依赖 |
| 暂停调度 | 同上但有下游依赖 → 暂停不删断 |
| 节点禁用 / 调整 | 单节点全部命中 → 禁用；部分命中 → 则对应 SQL 调整 |

### 关键洞察：强推荐 ≠ 弱推荐，是两件事

配图原文（已按放大图逐字核对）：

- **强推荐表（无读无写）**：平台侧没有任何活跃任务在产出。之前看似有 **419 条匹配**，全是禁用节点 / 已暂停任务造成的统计假象，**严格过滤后活跃命中为 0** → 表层面直接下线，无需任务协调
- **弱推荐表（无读有写）**：写入方就是仍在正常调度的任务 → 这才是任务治理的真正战场。**没有这套过滤规则，功夫就会花在"已经死掉的任务"上**

## 最终效果：从 36,996 到 177 条精准动作

| 指标 | 数值 |
|---|---|
| 精准治理动作 | **177 条**（任务级粒度，按负责人归口分配，每个动作有依据与理由） |
| 涉及推荐下线表 | **226 张**（每条标注推荐原因与节点明细） |
| 可执行调整动作 | **4 类**（下线 / 暂停 / 禁用 / 调整） |
| SQL 解析对照一致 | **28/28**（与平台 EasyParser 逐条验证） |

**漏斗（配图原文）**：

```
36,996  全量调度任务          （涉及 348 位负责人）
17,045  单任务（可解析 SQL）  （get_task 可拉取节点）
 7,320  已调度任务            （本次分析范围）
   177  精准治理动作          （可直接分派执行）
```

另有 **19,951 个任务组**（1 个项目多 flow）无只读详情接口，**无法分析 SQL**——原文强调这部分"不能计入已覆盖范围"。

**动作构成**：节点禁用 98 条 + 暂停调度 59 条 + 任务下线 18 条 + 节点调整 2 条 = 177 条。

**跨项目复用**：同一套规则——业务 A 177 条 / 业务 B 60 条 / 业务 C 3 条（配图注：合计 240 条，`--project` / `--clusterId` 一键切换，无需改代码）。原文对应："相同规则在另两个业务集群分别给出 60 条、3 条建议。"

## 交付形态

- **按负责人汇总**：配图示例"TOP 负责人：周 xx 43 · 郭 xx 17 · 董 xx 11 · 田 xx 10"，每条含 8 类字段：任务名 / seq / 负责人 / 调整类型 / 依赖数 / 涉及下线表 / 节点明细 / 推荐原因；"负责人拿到即可判断怎么动手，无需二次排查"
- **封装为 Skill**：`easydata-recommend-task-offline`——全程只读、只产出建议清单不执行任何变更；支持双数据源（CLI 直连拉取或本地离线分析）；跨项目 / 跨集群（集群 A / B / C 一套流程）；范围可配置（全部 / 指定任务 / 清单文件 / 负责人）；结果明细可追溯
- **结果分布**：原文配图另有"当前占比 2.4%"的标注（177 / 7,320），其余分段比例未逐字确认，不作记录

## 安全边界（原文）

- 分析**全程只读**
- 实际变更**由负责人决定**
- 配图："只调只读接口 · 只产出建议清单 / 不执行任何下线 / 暂停 / 删除动作 / 把'该做什么'算清楚，负责人确认动手"

## 自动化链路（规划 vs 现状）

配图给出 6 步闭环：① 每月自动触发 → ② 自动拉取最新清单 → ③ 自动解析 + 过滤 + 判定 → ④ 自动对比上月 → ⑤ 自动通知负责人 → ⑥ 自动生成月度报告。但配图同时标注"今天的成果是'一次专项分析'，真正的价值在于变成每月自动运行的常驻能力"，且 ④ 及之后以虚线框呈现。

正文口径更保守：**"结果按负责人汇总，并封装为 easydata-recommend-task-offline Skill；每月自动比对与通知仍属规划。"**

## 原文未说明

- 177 条建议中实际被采纳并执行的比例
- "推荐下线表"清单本身的产生方式与准确率（原文只说来自数据治理 360 已有能力）
- 19,951 个任务组缺只读详情接口的补齐计划
