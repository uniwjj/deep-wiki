# 从多云底座到 Agent-Ready：企业 DataAgent 架构与高端零售落地

> 核心主张：模型不是瓶颈，底座才是。企业 DataAgent 的落地失败往往不是某一步卡住，而是探数、建模、开发、测试、发布、运维六个环节每一个都卡；因此需要按「多云可用、语义可懂、执行可控、效果可迭代」四条判据重建 Agent-Ready 底座，再用 Harness 分层操作系统把语义、工具、上下文、权限与评测闭环工程化。

> 演讲嘉宾：谈总（某全球头部高端零售集团 · 中国数据技术负责人）× 原攀峰（数新智能 CTO）
> 场合：DACon 2026 北京站「AI Ready 到 Agent Ready：Data+AI 平台架构升级」
> 注：PDF 文件名写作「原礬峰」，正文标题页与结尾均写作「原攀峰」，本页以正文为准。

## 背景与问题

### 趋势一：数据分析能力大大加强，数据「饥饿」

- AI 最强的地方，恰好是分析最苦的地方：大批量、重复性的脑力活——画像、关联、对账、找异常、扫假设、写结论。
- 人一天验三个假设，智能体集群一晚上验三百个，而且从不厌倦。
- 稀缺能力从「你会不会写查询」，变成「问题问得对不对、数字可不可信、接下来怎么办」。
- 分析不再是工单队列，而变成一直在跑的后台服务。

结论：对答案的需求爆发，对可直接分析的数据的需求涨得更快。

### 趋势二：行业数据痛点——数据合规与准备

- 智能体又贪吃又浪费：读的数据量是人类分析师的 **10–100×**。
- 它要的不是看板，而是一块准备充分的底座：
  - 语义口径机器可读、契约与表结构稳定
  - 新鲜度、血缘、质量以数据形式暴露，而不是口口相传
  - 文档、日志、事件、表，收进同一个可寻址平面
  - 读路径便宜、高吞吐、高并发（列式与开放表格式）
- 交付物随之改变：从给人看的报表，到给智能体用的数据产品。

结论：数据搬运不会变少，它会变成产品本身。

### 趋势三：现实世界的限制——跨云带宽与跨境法规

- 算力弹性了，字节没有。距离、带宽、出网费重新成为硬约束。
- 为什么现在疼：算力在一朵云，底账数据在另一朵云；叠加数据驻留要求和 GPU 紧缺，跨云成了默认。
- 把 100 TB 搬过云，是时间和钱的问题，不是一个配置开关。图中标注：一次全量约 30 小时，另有出网账单；演讲者的选择是用 CDC 改增量。
- 工程重新回到基本功：
  - 能把算力搬到数据边就搬，只复制值得复制的
  - 用 CDC 和增量同步，替代整份全量拷贝
  - 压缩、列裁剪、去重、分层缓存、错峰窗口
  - 把数据引力写成明确决策，并定期复盘

结论：架构师的核心问题又变回「字节在哪里，搬一次值多少钱」。

### 解决方案：数据团队专注交付数据

治理一直正确，也一直太贵。AI 改变了成本曲线：识别 PII、从代码日志推血缘、生成策略与测试、发现漂移——持续、跨云。跨云统一的策略与目录平面覆盖身份、访问、驻留、留存、审计；治理变成在跑的软件，而不是一个委员会。

| 过去 | 现在 |
|------|------|
| 我们交付分析 | 我们交付受治理的数据 |
| 看板与报表 | 数据产品、契约、API |
| 消费者是人 | 主要消费者是智能体 |
| 治理 = 评审会 | 治理 = 自动化策略平面 |

收束语：软件让 AI 写，分析让 AI 做。我们的活，是把数据做到可用、可搬、可信。

### 小结：请记住三件事

1. 软件正在成为公共基础建设——数据变得不足
2. 智能体规模的分析，需要智能体规模的数据准备
3. 带宽与治理是新的硬约束——也是我们新的产品

### 多云部署，只是多云底座最基本的要求

多云底座的五类挑战：

| 挑战 | 具体内容 |
|------|----------|
| 多云适配与部署 | 异构数据源和引擎适配；不同云的数据中心之间形成新的数据孤岛 |
| 多云数据传输 | 离线 / 实时 / 全量 / 增量；跨云跨区域数据传输控制与加速 |
| 跨区域数据稳定生产 | 任务编排和稳定调度；任务代码版本管理；跨区域任务发布与依赖管理 |
| 数据资产管理与共享 | 数据指标口径管理，血缘与质量分析；逻辑模型与物理模型协同管理 |
| 数据安全与合规要求 | 平台权限、数据权限、数据加密、数据脱敏、平台审计等；不同国家地区的数据合规要求 |

结论：多云底座是解决 AI 时代数据「可用、可搬、可信」难题的必经之路。

### Agent 不是某一步卡住，是六个环节每一个都卡

真实企业研发全生命周期：一个简单需求，Agent 到处断链。贯穿示例是产出《跨区调货异常损耗监控看板》。

| 环节 | 断点表现 | 归因 |
|------|----------|------|
| ① 探数 | 不知道口径是否存在；搜出 20 张同名表，不知道哪张是生产源，直接用废弃临时表 | 语义可懂缺失 |
| ② 建模 | 不知道如何复用维度；重复新建地区维表，导致烟囱膨胀，同一客户在两表 ID 不一致 | 语义可懂缺失 |
| ③ 开发 | 幻觉 SQL 与方言错误；自己臆造字段名，多表 JOIN 发生 Fan-out 扇出，指标被放大 10 倍 | 语义可懂缺失 |
| ④ 测试 | 不知道「什么叫正确」；无法自动生成基线对账断言，无法识别退货场景的负值合法性 | 语义可懂缺失 |
| ⑤ 发布 | 不敢发布、影响面不明；不知下游有哪些关键报表依赖，且无沙箱防护，可能误删生产表 | 执行可控缺失 |
| ⑥ 运维 | 报错看不懂、无法自愈；底层引擎抛出千万行栈，无归因闭环，失败即任务终止 | 效果可迭代缺失 |

归因统计：**语义可懂缺失 4 次 · 执行可控缺失 1 次 · 效果可迭代缺失 1 次**。结论：「语义可懂」在 6 个环节中连续断掉 4 次，它是 DataAgent 落地失败的重要原因之一；单靠 Prompt 无法挽救系统性缺陷。

### Agent-Ready 的四条判据，缺一不可

| 判据 | 技术内涵 | 回扣业务诉求 |
|------|----------|--------------|
| 多云可用 | 异构寻址与计算下推：算力与数据必须能够被 Agent 统一透明寻址，算子按引擎能力自适应映射 | 多云多中心，拒绝烟囱 |
| 语义可懂 | 口径显式化与确定性编译：业务口径与关系拓扑被显式定义，检索子图组装，编译器消灭毒 SQL | 口径机器读懂，拒绝幻觉 |
| 执行可控 | 沙箱隔离与生产底线防线：人机权限等效，编译期注入行级权限，生产高危动作强制触发卡点审批 | 合规是硬边界，不是配置项 |
| 效果可迭代 | 失败归因与语义资产反哺：失败具备明确归因分流回路，自动化反哺语义模型与技能库，持续演进 | 不能上线即巅峰，持续复利 |

收束语：模型不是瓶颈，底座才是——这四条判据是每一个想做 DataAgent 的企业必须回填的答卷。

## 方案/架构

### 判据一 · 多云可用：统一纳管与任务编排调度

管理中心包含管理控制台、数据开发平台、资产管理平台、统一任务调度引擎、统一元数据服务；通过「元数据访问 / 任务联邦调度」向下连接五个云域，每个云域各有统一引擎网关：

| 云域 | 引擎 |
|------|------|
| 私有云 | Hadoop · StarRocks · Doris |
| 华为云 | MRS · GaussDB |
| AWS | EMR · Redshift |
| 阿里云 | MaxCompute · Hologres · EMR |
| GCP | Dataproc · BigQuery |

### 判据一 · 跨云数据同步带宽流量控制

架构把 B 云当作纯数据源（只提供数据源、不部署控制组件），A 云承担调度、执行与指标治理：

- **控制面**：Platform → 策略 → Coordinator → 任务派发 → Worker → 创建 Pod → DataX Operator → 创建与生命周期回执
- **运行 / 数据面**：DataX Pod，一个任务一个 Pod，Reader / Writer；B→A Reader、A→B Writer，Pod 网络接口
- **指标面（两条独立采集路径）**：
  - Worker 5s 采集 Pod rx/tx → Redis 账本（Observed / freshness）→ 供槽位调整
  - Prometheus 采集历史 rx/tx → 看板查询
  - 指标过期时批次回退默认槽位；Worker 高频链路供槽位调整，Prometheus 链路供历史查询

### 判据一 · 多云全域资产：集中式和联邦式融合治理

管理中心做指标定义分析、逻辑数据实体、逻辑模型、任务发布管理；向下「元数据上报 / 模型 & 任务下发」到各云域的物理模型、数据生产、元数据采集层。云域同上五类。融合集中式与联邦式，适配企业既有资产管理基础与组织架构。

### 判据一 · 多云的解法：集散控制架构

承认异构现实：**Agent 只发出逻辑意图，多云多中心底座负责纳管、集成、调度、查询与治理。**

- DataAgent 逻辑意图输出（Logical Query Intent），声明式 JSON，例如「计算北美区近 30 天退货率与跨仓调拨延迟，按渠道聚合」，无需声明物理方言与底层库表结构。
- 底座五项能力：
  1. **多云数据底座纳管**——开放式插件架构，适配主流大数据与 MPP 底座，覆盖云厂商、三方厂商及开源自建场景
  2. **统一任务编排调度**——统一编排、多区域运行；中心区域统一管理任务代码版本与多区域发布
  3. **多源异构数据集成**——插件化多同步引擎；离线 / 实时 / 全量 / 增量 / 整库 / 多表；跨区域传输加速
  4. **全域数据资产管理**——中心治理、边缘计算；融合集中式与联邦式管理优势
  5. **跨源查询分析**——跨数据中心、跨异构源一次查询完成分析，解决数据安全合规访问
- 系统调用机制：网关先探测引擎能力再原生下推，失败自动回退 ANSI SQL 降级执行，绝不中断 Agent 会话。Agent 只面对一个入口。

### 判据二 · 语义可懂：检索的不是文档，是 Schema 与口径

全链路：自然语言意图 → 双通道图检索 → 确定性编译器流水线 → 生产 SQL 交付。左上角引用 Spider 2.0：裸 SQL <20% → 语义层 54%~90%。

五个阶段：

1. **查询理解 NLU（LLM）**：实体识别、字面值提取、时间表达式、HyDE；产出种子实体
2. **双通道召回（Hybrid RRF）**：A 实体链接——name / synonym 精确命中；B 混合召回——Dense + BM25 + ValueIndex；RRF + 精排
3. **GraphRAG 子图扩展（Apache Ossie）**：Model → Dataset → Field → Metric；PPR 补 Join 中间表；PCST 最小连通子图；LLM Selector
4. **确定性编译引擎（Zero LLM SQL）**：把语义查询编译为可执行 SQL——① 校验归一化 ② Join Path 求解 ③ Fan-out 保护 ④ 时间语义展开 ⑤ 行权物理注入 ⑥ 方言模板渲染
5. **生产级 SQL 交付**：语法自校验通过、口径幻觉消灭；代码准确率 30% → 90%

编译期自校验公式：结构匹配率 − 执行准确率 = 编译器自身错误率。

核心分工原则：LLM 只负责理解意图，双通道召回锁定实体锚点，GraphRAG 保障拓扑连通，编译器 100% 确定性生成 SQL——彻底消灭毒 SQL。

### 判据三 · 执行可控｜核心能力一：流程工具

「API 是给人调的，工具是给 Agent 想的。」经验值：建表挂调度从 8 步降到 1 步。

**反模式**：API 1:1 包成 MCP——一次建表变成 8 步工具轨迹，Step 3 出错后，Step 4–8 全部受污染。

**分层工具体系**（会变的进 Memory · 不变的进 Skill · 能执行的进 Tool）：

- **Skills SOP · 渐进披露**：description / SKILL.md / scripts，不变的经验，触发后才载入
- **流程工具 · 存储过程式**：建表 + 挂依赖 + 配调度固化为一个工具，8 步 → 1 步，单次往返
- **原子工具 & CLI**：底层 API，复杂入参封装为 CLI 风格，配 few-shot
- **第三方 MCP 隔离沙箱**：独立容器、禁宿主网络、网关鉴权、版本锁定、返回内容注入清洗；一律视作不可信输入
- **search_tools 动态发现**：启动只注入核心工具 + 搜索路由；语义检索命中当前意图；按需注入 Top-K 完整 Schema；猜中未加载工具时引导先检索

结论：把后端 API 一对一包成 MCP 是行业最普遍的反模式——高频链路固化在服务端，让模型专注决策。

### 判据三 · 执行可控｜核心能力二：上下文工程

「通用摘要会把表名压没，数据场景不允许。」

**同一个会话，两种压缩**：

| 方案 | 做法 | 结果 |
|------|------|------|
| L1 同步摘要（行业常规） | 把前 20 轮已确认的 5 个事实压成一段话 | 表名、`_v2`、`REFUNDED` 全部丢失；第 24 轮追问「按月拆」时猜回废弃的 `dim_region`，SQL 能跑但数字全错 |
| L2 异步笔记（现网主力，用户无感） | 保留带编号的笔记：`[n07] dwd_ord_detail_di ← msg#7`、`[n09] dim_region_v2 (v1 废弃)`、`[n12] ship_dt (非 order_dt)`、`[n15] NOT IN (CANCELLED, REFUNDED)`、`[n19] region×brand×day` | 复用笔记仅改 day → month，100% 正确 |

三级压缩进化：L1 同步摘要 → L2 异步笔记·现网主力 → L3 向量化·前沿预留。

**推理闭环（两跳检索 · 记忆防污染）**：

1. 第一跳·查本体口径——先命中 Apache Ossie 度量与事实表
2. 第二跳·查数据样本——ValueIndex 校验取值 + 历史成功 SQL

会话沙箱随任务销毁；失败的中间 SQL 与报错信息禁止写入组织长期记忆。原话：「没有治理的记忆，就是 Agent 的谣言库。」压缩最高境界：用户无感。

### 判据三 · 执行可控｜核心能力三：五层防护

「Agent 的权限永远是发起人权限的子集。」

**权限等效**：开发者权限 · RBAC；Agent 权限 ⊂ 发起人权限子集；透传开发者 Token；继承数仓 RBAC 权限；系统不提供任何提权路径。原话：「放权是挣来的，不是默认给的。」

**漏斗式五层防护栏**（逐层收窄、层层留痕）：

| 层 | 防护 | 内容 |
|----|------|------|
| L1 | Input Guard · 输入防护 | 提示词注入拦截、越权意图预检 |
| L2 | Tool Guard · 参数校验 | 入参类型校验、操作白名单 |
| L3 | SQL Guard · 编译期注入 | `row_filter injected @ compile` |
| L4 | Harness 容器沙箱 | 1 Task = 1 容器、只读、断公网、短 TTL |
| L5 | Output Guard · 脱敏审计 | PII 遮蔽、出境阻断、Trace 回放 |

**生产红线（HITL）**：高危动作 Agent 无权自动执行——DROP / TRUNCATE 高危 DDL、生产调度作业上下线、跨集群核心维表覆写。强制拦截后进入审批卡片：3 秒呈现改动与影响面，负责开发者显式放行（拒绝 / 批准放行）。原则：先紧后松、授权留痕。

### 判据四 · 效果可迭代：每一次失败都变成语义资产

人在环的闭环迭代飞轮：轨迹采集 → 失败归因 → 分流修复 → 评测门禁 → 灰度上架。

1. **轨迹采集**：复用 LLM 网关既有 Trace，覆盖 Token、Tool、全链路
2. **失败归因**：语义、技能、权限、引擎、幻觉五类
3. **三分支精准修复**：
   - 分支 1·语义缺失 → 回写 Apache Ossie 本体，补同义词 / 字段映射，Owner 审核
   - 分支 2·技能缺失 → 提炼 SOP、沉淀新 Skill；高频错误轨迹 → 服务端流程工具
   - 分支 3·引擎差异 → 方言规则与回退补丁，补兼容模板、更新能力探测表
4. **评测门禁**：分层回归——检索 / 编译 / 端到端；不过门禁，不准上架
5. **灰度上架**：通过后进入团队共享库，「下一个人不再踩同一个坑」

平台语义资产指标：30% → 90%（标准评测集 200 条 · 代码准确率）。原话：没有评测门禁的迭代，不是进步是随机漫步；Agent 不是缺表，是缺「这张表到底是什么意思」。

**数新智能 CyberOS** 定位为一站式跨云、多中心、多模态 AI + DATA 智能操作系统，打通「算力—数据—AI—Agent—业务执行」的智能闭环。分层：

| CyberOntology · 赛博本体平台 | 语义建模与设计、语义图谱与检索、仿真推演、服务开放 |
| 赛博数据平台 CyberData | 集成 · 开发 · 运维 · 治理 · 分析 · 服务；数据资产、建模、开发、分析、服务；异构数据源/引擎管理 |
| 赛博智能平台 CyberAI | 机器学习 · 大模型 · MaaS；机器学习训推、大模型训推、算力管理、智能体构建 |
| 赛博数智底座 CyberEngine | 统一元数据服务、统一数据集成、统一任务调度、统一引擎网关服务；覆盖私有云、华为云、AWS、阿里云、Google Cloud |

**基于 Harness 框架的企业级 DataAgent 分层操作系统**：

- **L1 用户交互与编排管控层**：Data Studio / Chat UI（全屏代码沉浸编辑、Step-by-Step 方案图谱确认、侧边多轮对话）；Task Router 开发任务路由器（解析开发意图、动态 Skills 路由分发、规范与规则规约中心）；4 段 Guardrail 拦截面（Input / Tool / SQL / Output）；ACP 流式协议（JSON-RPC 2.0 + SSE）；生产红线强卡点（HITL）
- **垂直可信调用总线**：透传开发者 Token 身份、继承 RBAC 权限、零提权通道；1 Task = 1 Runtime = 1 Container Sandbox
- **L2 Harness 智能体引擎与核心能力层**：
  - 4 大数据开发 AI 核心模块池：SQL 全生命周期（生成/纠错/优化/Linter）、资产智能推荐（指标反查/缺表诊断/ODS）、巡检诊断自愈（StackTrace/根因推演）、质量规则推荐（双跑对账/断言阈值生成）
  - 受控执行外壳与 LLM 网关：Skills SOP 三层渐进披露、search_tools 动态按需加载、LLM 网关与可观测 Trace、Token 计量归因

- **L3 CyberData 数据底座**：统一 Auth 鉴权（OAuth2/JWT 透传、行级权限、Quota 管控）、CyberKernel 内核服务、CyberEngine 多云引擎（私有云/开源自建、华为云 MRS、亚马逊云 EMR、阿里云 MaxCompute、Google Cloud BigQuery）；持久化解耦存储（State / Trace / Logs 异步落盘 · NAS / S3）

设计原话：「手机 OS 不是把 PC OS 缩小一圈——应用形态变了，底座操作系统就必须重写。」收束为「底层统一 · 中间可懂 · 上面可控」。

### 数新智能 × 华为云：跨云多中心 AI 数据平台

- **一主二卫星 · 统一纳管**：新加坡华为云 MRS 主集群 + 俄罗斯华为云、印度 AWS 卫星集群，一套界面跨云跨地域调度、运维、查询
- **零学习成本 · 无感切换**：页面布局、开发流程、运维操作全场景对齐主流平台逻辑，脚本编写、发布、补数操作无改动
- **自动化迁移 · 双跑校验**：四大自动化迁移能力，85% 脚本免人工修改；新旧平台双轨并行 + 数据自动校验，割接任务不停
- **AI 赋能 · Data Agent**：平台内置 Agent 覆盖代码生成、纠错、优化与日志诊断，结合 MaaS 大模型服务持续提效

### 一条真实任务链：从提问到上线

中企出海 / 全球品牌入华真实场景，从自然语言到生产级发布：

- **Step 1 · 意图与探数**：用户输入「统计北美区近 30 天各渠道退货损耗，关联区域维表与 SKU 主数据」；Agent 探数决策——检索 Ossie 模型命中 `Metric[return_loss]`，维表对齐选用 `dim_region_v2`（Match: 98%），判定缺表触发 ODS 接入 SOP 引导
- **Step 2 · 方案图谱确认**：《ETL 加工方案图谱》——目标表 `dws_return_loss_di`（按天分区）；Join 路径 `store_sales → store`（多对一）；过滤规则 `status NOT IN ('CANCELLED')`；HITL 卡点，开发人员点击放行后触发编译器
- **Step 3 · 编译与发布**：编译器生成 SparkSQL（带 Fan-out 保护）；发布前 Dry-run——语法自校验 Linter PASS、行权注入 `region IN ('NA_WEST','NA_EAST')`、影响面分析覆盖下游 3 个报表；结果任务安全上线，总耗时从 3 天降至 30 分钟

三个关键观察：第一步引用标准口径，不是凭空猜表；口径在写代码前 100% 达成共识；引用了显式口径，没有黑盒生成，人随时在驾驶位掌握方向盘。

## 经验与边界

### 什么场景现在就能上（SWEET SPOT）

- **口径相对清晰**：有基本的数据字典或资深业务分析师可做 Owner 核对
- **有存量 SQL 代码可挖**：运行超过 1 年的成熟数仓，可利用 CodeWiki 提取语义
- **企业内部研发与分析提效**：内部工程师人在环使用，容错空间充足
- **多引擎异构开发**：需要跨 Hive / Spark / Doris 抹平方言差异的场景

### 什么场景建议再等等（DON'T TOUCH YET）

- **口径零沉淀的冷启动项目**：业务方自己都没想好定义，模型只会放大人性混乱
- **对外强实时端到端服务客户**：零人在环直接暴露给消费端用户（容错极低）
- **缺乏沙箱防护的生产裸跑**：没有容器隔离与 HITL 审批，随时面临删库风险
- **无评测门禁的盲目自迭代**：缺乏回归基准，自进化极易沦为自污染

### 三条实操方法论

1. **先补语义，再谈自动化**：口径未收敛前，不要妄想让大模型写代码
2. **高频低风险切入**：从 SQL 补全、语法改错、质量规则推荐等单点逐渐泛化
3. **没有评测门禁不开自动化**：不设基线回归的发布等于随机漫步

### 未来规划：RSI 递归自我改进

RSI 递归改进的是能力集，而非模型权重。Agent 递归优化的是自己下次执行依赖的 Skill 脚本、语义图谱与调度策略。三个前提：① 评测集门禁 ② 沙箱试运行 ③ 人在环审批。

### 边界与口径提示

- 「谈总」为演讲嘉宾署名，所属集团未具名；奢侈品集团与安踏案例均为脱敏展示。
- 探数环节「约 70%」原文明确标注为定性评估，不能当作与其他环节同口径的定量指标。
- 华为云案例中的 85% 指「脚本免人工修改」比例；发布会环节 <5% 为 3 个月质量统计口径，原文未展开定义。
- 安踏案例的六个环节（正文）与图上五个应用入口（选品优化、库存优化、营销推荐、智能客服、智能物流）并非一一对应，正文另列智能定价与售后服务；此处按原文分别记录。
- 全篇收束：「模型不是瓶颈，底座才是」「底座越 Agent-Ready，上面的 Agent 自我改进的空间就越大」。
