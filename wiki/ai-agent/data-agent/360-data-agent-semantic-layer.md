# 奇虎 360 企业级 Data Agent 语义层演进与量化评测

> **核心主张：** 原文把语义层建设的失败形态写得很直接：数十万张表、上百万字段之下，用户抵触语义层建设、无从下手、不了了之。360 的解法不是一次建全覆盖的语义层，而是三件事同时做：用**统一 BlockPlan 契约**把运行时收敛成一条主链，用**物料完备度 / 编译器算子集 / 业务风险策略**三个独立维度把"缺口"分型处理，用**分层命中 + 双路径混合路由**把结构化语义的确定性留给已验证部分、把模糊语义限制在可标注的兜底路径里。终局不是全覆盖语义层，而是在明确覆盖边界内可靠回答，边界外显式澄清、降级或拒答。

## 背景与问题

### 数据底盘规模

奇麟湖仓的体量是问题的起点：

| 维度 | 规模 |
|------|------|
| 表 | 数十万张表（日常运维的企业级数仓规模） |
| 字段 | 上百万字段（口径散落其中的字段资产） |
| 业务线 | 数十条核心业务线（支撑业务运转的数据底盘） |

技术栈混布：hive、iceberg、paimon、archer、starrocks、mysql。

Agent 已支撑的业务包括：大数据集群运维、S3/PoleFS 存储运维、Ops 机房运维、文库、会员中台等。

### 三个真实的组织性痛点

原文把语义层建设中最常见的失败写在最前面：

- **用户抵触语义层建设**
- **无从下手**
- **不了了之**

原文给出的演进路线是四段：`NL2SQL → 语义层冷启动 → Agent 能力体系 → 本体化转型`。也就是说，语义层不是起点，而是"NL2SQL 走到瓶颈之后必须补的一层"；本体化转型则是语义层之后的下一站。

### 奇麟 Agent 架构概览

上层入口：对话入口、OpenAPI、Skill 与插件、MCP 工具、BI 报表嵌入。

在线主链六步：

1. **意图路由**：意图分类、slots 合并、澄清反问、拆分
2. **双路召回**：结构化召回（OSI 精确匹配）/ 非结构化召回（RAG 检索）
3. **程序化编译**：BlockPlan 块计划（5 类块 + compose）/ AST 编译（sqlglot 全 AST）
4. **多层防护**：静态防护（白名单、只读）/ 运行时防护（权限、脱敏）
5. **执行与自愈**：执行编排（Trino、StarRocks）/ 自愈与降级（回喂、Fallback），自愈环节复用主链
6. **结果交付**：置信度、口径解释、洞察、点赞点踩

四个支撑面：

- **能力编排**：归因分析（delta 分解）、下钻（维度拆解）、What-If（假设推演）、综合分析（假设验证）、洞察引擎（零 LLM）、复合 DAG（顺序编排）
- **本体推理与用户剧本**：本体推理 Ontology（概念图谱、下钻路径、维度兼容性推理）、用户自定义 Runbook（分析剧本、分步算子、团队共享、版本）
- **对外集成**：Skill / 工具注册表（能力注册、参数契约、版本管理）、对外 API / MCP（OpenAPI、事件回调、多租户隔离）
- **运行时支撑**：提示词管理（版本化、A/B）、异常处理（降级、重试）、Trace 可观测（耗时、审计）、语义缓存（命中复用）、多轮会话（slots 继承）、成本限额（扫描、频次）

### 语义层治理与评测反哺闭环

原文把治理链画成五段加一个回流环：

**原材料（八路）** → **知识库 RAG** → **语义升维** → **OSI 语义平台** → **同步分发**

- 原材料八路：库表元数据、Schema 映射、ETL 血缘、业务文档、SQL 日志、BI 报表、运行时反馈、权限·质量
- 知识库 RAG：切片·向量化、混合检索、重排 Rerank、Top-K 融合
- 语义升维：LLM 抽取候选、人工确认、审核转正
- OSI 语义平台：OSI 语义模型（dataset · field · metric）、录入与维护、版本与血缘、归属与权限
- 同步分发：增量推送（缓存失效、版本切换）、变更影响回归、权限·脱敏下发

回流环（评测·反馈·反哺闭环）四块：

- **评测体系**：Golden 集、准确率、回归门禁 CI
- **失败归因**：错误分类、聚类（幻觉、方言、Join）
- **用户反馈**：点赞点踩、采纳率、低置信转人工
- **反哺闭环**：候选转正、口径修正、Prompt 与示例库

在线产出数据向上回流到"原材料"，评测结论向上"反哺语义层"——这是一个闭环，不是单向流水线。

## 方案/架构

### NL2SQL 范式的光谱：五级抽象

原文按「模型自由度递减、前置语义约束递增」排列五个层级：

| 层级 | 形态 | 代表 |
|------|------|------|
| 01 NL2SQL | 无中间层，自然语言直出 SQL | CHASE-SQL、XiYan-SQL、Arctic-Text2SQL-R1 |
| 02 NL2IR2SQL | 类 SQL 语法中间表示 | SemQL(IRNet)、NatSQL、QPL、QDMR |
| 03 NL2DSL2SQL | 结构化查询描述语言（JSON/YAML） | Cube、LookML、dbt MetricFlow、网易有数 |
| 04 NL2LF2SQL / NL2LG2SQL | 业务意图 + 对象关系 + 口径全部抽象 | arXiv:2606.31041、亿问 LogicForm、本体化语义层 |
| 05 NL2MQL2SQL、SMQ | 指标语义层，只认 metric / dimension / time | Aloudata CAN、Snowflake Cortex Analyst、润乾 NLQ |

原文对这条光谱的判断非常明确：

- **往上走会发生什么**：模型要猜的东西越来越少，幻觉空间越来越小。
- **代价是什么**：你要提前建模的东西越来越多，冷启动越来越贵。
- 模型从「猜映射」变成「做选择」——列名、JOIN、口径的翻译被外置给人工建模的语义层 + 确定性编译器，模型的输出只剩封闭集合里的引用。

两个必须同时记住的限制：

1. **白名单只能拒绝未知引用，不能拒绝"合法但选错的指标"。**
2. 五个层级是"职责和抽象程度的比较，不是严格互斥的产业分类"。

原文还指出，02 层的纯学术 IR 名称（SemQL、NatSQL、QPL、QDMR）在当前企业产品叙事中的可见度正在下降——企业更愿意用 03/04 层的产品化语言描述自己。

### 命名混乱的根源：名字不重要，三件事决定能力

原文的判断是：中间层叫 DSL / MQL / LF / LP / Semantic Query / SMQ 其实不重要，真正决定系统能力的是三件事——

1. **中间层的表达上界**（能表达哪些查询结构）
2. **有没有确定性编译器兜底**
3. **语义建模的人工成本**（"用名字吵架是浪费时间"）

它用一张表区分"地图"和"订单"：

| 对象 | 谁生成的 | 什么时候 | 内容 |
|------|---------|---------|------|
| 语义层定义（地图） | 人工（越来越多用 LLM 辅助起草，但人工审核确认才生效） | 离线，长期维护 | 业务对象、关系、事件、时间锚点、权限、指标口径 |
| 查询实例（订单） | 模型 | 用户提问的那一刻 | "我要指标 X、按维度 Y、时间 Z"——一个引用封闭集合的 JSON |

### 演进：按业务成熟度分层分治，以及它的反噬

用户需求天然分布在一条光谱上：一端是"中心化语义仓（资产持续沉淀）"，另一端是"本体级严苛"。360 的第一版应对是按业务成熟度分三档：

| 档位 | 语义形态 | 运行时 |
|------|---------|--------|
| L1 字段级 | DSL：表·列直查 | 独立提示词与编译路径 |
| L2 指标级 | MQL：指标引用，口径进入独立编译路径 | 同上 |
| L3 本体级 | LF：实体·属性·关系 | 同上 |

三套运行时并行维护：Prompt · Validator · Compiler · Regression。

原文随后自我批判了这种分档，指出三个结构性缺陷：

- **层级是业务平均值**，而查询命中的是具体元素
- **缺口风险不对称**：指标自拼聚合偏差 **87%**
- **语义越完善，边界越交错**：跨格式与多轮上下文档断裂

结论是：分档初衷是让物料少的业务也能用，却把业务平均属性带进了单次查询。

原文还专门列了四条"错误想法"作为反模式：

- "L3 编译器不能编译 L1 语义"
- "LF 天生比 DSL 有更强表达能力"
- "统一契约后所有缺口都可以自动补齐"
- "业务是 L3，所以本次查询一定具备 L3 保障"

核心判断：**语义能力取决于实际登记的物料和编译器算子能力，而不是契约记法本身。统一契约解决的是运行时分裂问题，不替代语义治理，也不绕过风险控制。**

### 分级治理、统一运行时：把混在一起的三件事拆开

这是全文的架构核心。做法是：用统一的 **BlockPlan 契约**承接所有业务、所有问题，同一入口、同一解析、同一编译主链；然后把原来混在 L1–L3 里的三件事拆成三个**独立维度**：

| 维度 | 内容 | 回答 |
|------|------|------|
| 物料完备度 | 指标、维度、关联、枚举、时间锚点、主键 | 能问什么 |
| 编译器算子集 | 聚合、窗口、否定存在、递归 | 能表达什么 |
| 业务风险策略 | strict / standard / exploratory | 敢不敢直接出数 |

原文的原则是："能力来自物料，不来自契约记法。" 三个维度各自独立演进。

同时明确"统一入口，不等于无条件放行"的四条规则：

| 情况 | 处理 |
|------|------|
| 维度缺定义 | 可执行，但标注 |
| 指标缺口 | 回显假设，确认后执行 |
| 关联未声明 | 拒绝，不推断 JOIN |
| 算子超出 | 受控兜底并标记 L0 |

原文标注的上线状态：**已上线**——统一契约、元素级处理、缺口分型、引用级保障标注；**待持续验证完善**。

### 面向信任：从"通过/失败"到可解释的结果责任

原文把结果分成六类，每类对应一种处理，而不是简单的成功/失败：

| 发现的问题 | 分类 | 处理 |
|-----------|------|------|
| 正式指标、正式维度、已声明关联 | `hit` | 正常编译 |
| 字段存在，但只有物理信息 | `raw_dim` | 可执行，但标注 |
| 没有正式指标，只能临时 `SUM(amount)` | `ad_hoc_measure` | 回显假设，确认后执行 |
| 用户要求跨表，但没有声明关联 | `undeclared_join` | 拒绝 |
| 字段和物料都存在，但 Builder 不支持窗口操作 | `unsupported_op` | 受控兜底或拒绝 |
| 引用的字段在 OSI 中完全不存在 | `unknown` | 走幻觉处理 |

两个报告构成"可解释的结果责任"：

- **ConfidenceReport**：我有没有理解对用户的问题？（意图、字段选择、多轮继承、计划结构）
- **GuaranteeReport**：这个结果的口径受保障吗？（指标、关联、时间锚点、枚举映射）

原文的目标是让用户知道：为什么这样答、哪里需要确认、结果能承担什么责任。

### 选型第一步：分清三层概念

原文用一张表把最容易混的三个问题拆开：

| 层 | 回答的问题 | 典型承载 |
|----|-----------|---------|
| 指标层（管理） | 这个指标什么意思、谁负责、怎么审批变更 | 指标目录、OpenMetadata Glossary |
| 指标语义层（执行） | 这次查询怎么编译成正确的 Join / 聚合 / 过滤 | MetricFlow、Cube Core、自研编译器 |
| 元数据语义层（治理） | 术语、资产、标签、血缘、影响分析 | OpenMetadata |

原文特别注明："不同厂商边界不同，本文按职责拆分。"

### 开源组件选型：五项对照

| 工具 | 定位 | 强项 | 代价 |
|------|------|------|------|
| MetricFlow | dbt 体系指标编译库 | 复杂指标、时间语义、定义随 dbt 进 Git | 绑定 dbt 工作流，服务化要自建 |
| Cube Core | 独立无头语义服务 | SQL / REST / GraphQL 多消费端 + 预聚合缓存 | 要运营一个语义服务（容量 / 缓存 / HA） |
| Lightdash | 语义层 + BI + 目录一体 | 定义 / 目录 / 探索 / 仪表盘一条流水线 | 与 Lightdash 使用方式绑定较紧 |
| Apache Superset | BI 内置轻量语义能力 | 主要服务 Superset 内部分析 | 外部语义层集成仍在演进，不宜与完整 headless 语义服务等价比较 |
| OpenMetadata | 元数据与业务语义治理 | 术语 / 负责人 / 血缘 / 影响分析 | 不做指标计算，须与执行层组合 |

场景速配（原文）：

- dbt 主干 → MetricFlow
- 服务多端 / AI Agent → Cube Core
- 快速目录 + 自助分析 → Lightdash
- 仅 Superset、规模小 → 轻量语义层
- 指标算得出但没人负责 → OpenMetadata + 执行层

### 双通道：结构化语义 × Data Agent 端到端架构

这是全书最复杂的一张图，原文的定位是"结构化语义主干 · 模糊语义补给 · 三个合流点 · 显式覆盖边界"。

**① 语义供给与治理（离线闭环）**

- 七类语义原料：库表元数据、术语映射、ETL 血缘、业务文档、SQL 日志、BI 报表、运行时
- 抽取与派生：LLM 批量抽取、血缘 DAG 自动派生
- 结构化语义存储：OSI SemanticModel，实时拼装
- 模糊语义存储：弱参考资产库，带 provenance、已验证答案、Golden Queries
- 人工确认闸 / 转正入库：精度达标才入库、降级 SQL 审核转正、**P4 硬闸：负收益即停止**

**② Agent 在线主链**

用户问题 + 表清单 + 多轮上下文同时进入两条通道：

- **结构化通道（强语义）**：resolve 拼装 SemanticModel → 裁剪（A 关键词、C 打分、D 种子 + BFS、E 不变式）→ 越界整体回退全量 → OSI 白名单校验 · 幻觉检测
- **模糊通道（弱参考）**：资产检索（报表·日志·文档·运行时）→ 相关度排序 → 预算裁剪 → 安全净化 → 输出带 provenance 的弱参考候选 → `reject-only`：只拒绝、不改 SQL

三个合流点：

1. **术语映射注入检索词典**（只提召回）——同时明确"模糊语义永不进 AST"
2. **弱参考块注入**：业务语义补充、历史问答、未锚定术语
3. **评测反哺回流语义层**（被采纳 SQL 人工审核 → 转正入库）

**路由判决 PreMatch**：top-1 打分 + 实词锚定；未过则直通模糊路径，省 1 次意图 LLM。

两条执行路径：

- **结构化路径**：意图解析 LLM（1 次）→ BlockPlan 规划 + 白名单校验 → 5 类 Builder 确定性编译 → 编译失败降级至模糊路径
- **模糊路径（fallback）**：合流点 2 弱参考块注入 → 合法标识符白名单（硬约束）→ LLM 直出 SQL

统一防护与出口：

- 统一防护：安全校验、EXPLAIN、执行
- 自愈：结构化错误三元组（类型·标识符·相似列）回喂重试（cap 3）
- 统一出口：结果 + 置信度 + `dispatch_path` 标注 + 语义覆盖报告；`dropped` / `bare` / `unresolved` 显式暴露，不静默降级

原文的四条铁律：**模糊语义永不进 AST · 降级必须可见 · 漏召回必须可逆 · 答不了就别答。**

### 分层命中逻辑：L0–L4

原文用一条纵向漏斗把"每一层能给出什么置信度的答案"讲清楚，原则是：**每往下一层，置信度降一档，且降档必须让用户看见。**

| 层 | 做什么 | 命中出口 | 置信特征 |
|----|-------|---------|---------|
| L0 入口分类 | 在问数据吗？（意图分类，轻量） | 婉拒（闲聊、与数据无关） | — |
| 歧义检测 | 同名指标组 n 问题确实涉及 n 用户未选 | 反问用户（列出候选口径，由用户选择） | — |
| L1 Verified 层 | 两扇门、同一出口：门 A 字面门（归一化后完全相等，零概率参与）/ 门 B 语义门（向量相似度 ≥ 高阈值，槽位一致：时间/过滤/维度/指标） | 执行已验证 SQL → 直返（现场执行，不返旧数） | 最高 · 零概率门 |
| L2 结构化层 | 三关全过才放行：①锚定关（指标打分达阈值 + 实词全锚定，无 LLM）②意图关（LLM 出 slots，未知字段进 ambiguities）③编译关（BlockPlan + 白名单 + Builder 确定性编译） | 确定性 SQL（程序编译，LLM 不碰 SQL） | 高 · 一道概率门 |
| L3 模糊通道 | 此刻才检索弱参考（懒加载）：检索报表·反馈·日志·文档（毫秒级）→ 净化 `reject-only` → 注入带 provenance → LLM 直出 → 安全校验 + EXPLAIN + 重试（cap 3） | 带标注答案（明示「LLM 直接生成」） | 中低 · ≥两道概率门 |
| L4 显式拒答 | 绝不静默给错答案 | 显式不可答 | 显式不可答 |

一个细节：**门 B 未过 → 报表资产转入 L3 作参考书，问题继续走 L2**——即 L3 的弱参考不是主路径的替代，而是"继续往下走时的补给"。

## 关键工程做法

### 语义层冷启动：七路原材料

原文把冷启动的原材料分成四组七路，并指出最容易被忽视的一路：

| 组 | 路 | 内容 |
|----|----|------|
| 存量资产 | 01 库表元数据 | 字段 / 类型 / 注释——裸表自动生成 dataset 保底可查 |
| 存量资产 | 02 Schema Linking 资产 | BI 数据集映射、检索索引、历史问答对 |
| 活教材（最易被忽视） | 03 调度平台 ETL | Flink / Spark SQL 血缘 DAG、隐式 Join、指标加工逻辑——**上万条作业 = 上万份活教材** |
| 活教材 | 04 查询平台 SQL 日志 | 真实问题分布、高频表 / 列、常用 Join |
| 认证精品 + 零散知识 | 05 BI 报表 / 驾驶舱定义 | 业务认过账的口径 + 维度 + 责任人，优先级最高的"精品矿" |
| 认证精品 + 零散知识 | 06 业务零散文档 | wiki / 口径说明，LLM 批量抽取 + 人工抽检 |
| 运行时转化 | 07 Agent 运行时反馈 | 被采纳的降级 SQL，审核后"转正"进语义层 |

横向机制：冲突检测、来源优先级、有效期、责任人、冲突解决机制。

加速器：LLM 智能导入——批量从 schema、血缘和文档起草初版语义；低风险描述可抽检，核心指标、Join、粒度和权限必须审核后转正。

### 结构性防幻觉：从"prompt 恳求"到"流程闸门"

| 维度 | prompt 恳求（概率性防御） | lift-only（结构性防御） |
|------|--------------------------|------------------------|
| 做法 | "请只使用真实存在的表名" | 标识符不在编译器输出集合 → 拒绝执行 |
| 保证 | 大概率听话，无硬保证 | 错的标识符物理上到不了数据库 |
| 依赖 | 模型自觉 | 流程闸门，换什么模型都成立 |

原文同时给了一个反向警告：**标识符安全 ≠ 语义正确**。它用 `description` 的漂移举例：

```
# 第一版（健康的）
description: 订购收入，下单口径的销售额

# 打磨到第 N 版（drift 了）
description: 订购收入，下单口径的销售额。
              当问题出现"趋势/月度"时选本元素而非 shippedRevenue；
              若提到"净"字需先扣退款 ……
```

当 description 被调优成"泄漏答案的文本"，它就不再是语义定义，而是过拟合的补丁——这也是后面 hold-out 题集要解决的问题。

### 三级评估漏斗：只看结果集，不看 SQL 文本

原文的评测链路分五段：

**① 测试数据集（三源归一）**

- 人工标注黄金集：`10_questions.jsonl` · 10 条
- 用户点赞反馈集：三层过滤 + 四阶采样 · DB 直连
- 异常边界 + 多轮对话：`anomaly_cases` + YAML

**② 三种测试模式**：Mock 框架自检 / Live 快速评估 / Live+Semantic 精确评估

**③ SQL 执行与结果集比对**

```
pred_sql → pred_rows  vs  gold_sql → gold_rows  → compare() → L1 多集精确比对（Counter）
```

**④ 三级评估漏斗**

| 级别 | 判定 | 后续 |
|------|------|------|
| L1 精确匹配 | Counter 多集比对，忽略列序/行序，1e-6 容差 | 通过 |
| L2 语义确认 | 结构相似、值不同 | LLM Judge 语义判定 |
| L3 不匹配 | 无共享列 / 多出额外列 | 人工审核 |

并行校验五项：ExpectedFacts、Hallucination、SchemaLinking、Calibration、Multi-Turn。

**⑤ 指标汇总 & 失败归因**

- 核心指标：`EX = (L1+L2) / 总数`、三级占比、VES 效率分、ECE 校准
- 失败归因（7 类 AST 对比）：`table → column → filter → join → agg → syntax → timeout`

原文的三条工程纪律：只看结果集、不看 SQL 文本；参考 Databricks Genie Benchmarks；**程序能判的不浪费 LLM，LLM 能判的不浪费人。**

### 评测反哺语义层：阻断漏斗 + 四阶采样 + 飞轮

**反馈三层阻断漏斗**（从用户点击·点赞到纯净落库）：

1. 高频异常过滤
2. SQL AST 语法校验
3. AI 审计语义等价

阻断核心原则：**宁可漏掉，不可错收**——确保进入飞轮的每一条数据都是高质量资产。

**四阶自适应采样**：

1. 时间滑动窗口（N 天）
2. 语法骨架指纹去重
3. 分层权重采样：AST 0.6 : Fallback 0.3 : Other 0.1
4. 差额自动补足

目标：在控制测试成本的前提下，最大化数据分布的多样性，生成代表性回归测试集。

**持续改进循环（飞轮引擎）**：执行评测（发现性能短板）→ 定位根因（AST 差异分析）→ 修复优化（Prompt / 逻辑调优）→ 重新验证（防回归测试）→ 回到执行评测。

原文描述的飞轮效应：每一次循环都在积累势能——测试集越丰富 → 归因越精准 → 修复越高效 → 模型越智能 → 最终实现系统的自动进化。

### 两块常开仪表

原文把评测拆成"每天都要看"的两块仪表，而不是一次性的大评测：

**仪表一 · 分层命中率——用户真实问题接住没有**

- 四层分布：L1 Verified 直返 / L2 结构化编译 / L3 LLM 直出 / L4 显式拒答，`dispatch_path` 逐条落库
- 语义路径命中率 = L1 + L2 占比
- 聚合即得：不跑评测、基于已有日志可低成本聚合
- **一鱼两吃**：对上，是"语义层到底有没有用"的唯一诚实答案；对内，≥70% 弱参考懒加载、<30% 意图期并行预取，直接当执行开关
- 业界锚点：Snowflake 官方 Routing Mode 文档披露的语义 SQL 路由占比约 10%

**仪表二 · 语义层质量信号——不依赖下游准确率，地图画得怎么样**

- 四个刻度（模型表直接统计，零成本随时可算）：缺 synonyms 指标占比、孤立 dataset、join 路径覆盖率、零引用表占比
- **hold-out 题集·防「押题」漂移**：description 会 drift 成泄漏答案的文本——调优集与留出集分数一对照就现形
- 出身：SMQ 论文自承「独立于准确率的语义信号」是开放问题，这里把它做成每天自动跑的工程仪表

两块仪表的关系：命中率答"用户的问题接住没有"，质量信号答"地图画得怎么样"。命中率掉了，去质量信号找病因；质量补上了，看命中率涨回来。

## 经验与边界

### 三条诚实边界

1. **可编译 ≠ 业务正确**：合法指标也可能选错，Join 粒度、过滤和时间口径仍需验证。
2. **已建模 ≠ 全覆盖**：超出表达或语义范围时，澄清、受控降级或显式拒答。
3. **外部高分 ≠ 本地收益**：必须在自己的问题、数据、权限和版本条件下重测。

### 三个必盯指标

1. **覆盖与正确性**：分路径命中率 + 各路径业务正确率 + 合理澄清 / 拒答率
2. **泛化与可维护性**：独立留出集 + 语义缺陷诊断 + 维护成本
3. **一致性与稳定性**：等价改写一致 + 固定条件下重复运行稳定

原文的终局判断：**不是全覆盖语义层，而是在明确覆盖边界内可靠回答，边界外显式澄清、降级或拒答。**

### 分档治理的反面教训（可直接复用的坑）

- 按业务分档会引入"业务平均属性"污染单次查询——原文的原话是"层级是业务平均值，查询命中的是具体元素"。
- 缺口风险不对称：指标自拼聚合偏差 87%，而字段级缺口只是"可执行但标注"；原文把"业务风险策略"（strict / standard / exploratory）列为与物料、算子并列的独立维度。
- 语义越完善，边界越交错：原文对应的问题是"跨格式与多轮上下文档断裂"（原文措辞如此，疑为"上下文断裂"）。
- 统一契约只解决运行时分裂，不替代语义治理，也不绕过风险控制——把契约当成治理是典型误判。
