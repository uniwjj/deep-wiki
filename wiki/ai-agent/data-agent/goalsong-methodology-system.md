## 十套方法论逐项

### 1. 本体识别方法论（B.2）

**适用场景**：企业已有数据资源和业务场景，但不确定哪些业务对象、关系、状态应纳入本体；需要从现有系统、文档、流程中系统识别本体候选元素。

**核心步骤**（六步，每步都有"关键要点"与"输出"）：

| 步骤 | 名称 | 关键要点 | 输出 |
|------|------|---------|------|
| 第一步 | 业务场景扫描 | 三问判断：不是查字段能解决？有业务上下文？能形成闭环？ | 候选场景清单 |
| 第二步 | 业务对象识别 | 只识别参与当前闭环的对象；不参与的对象暂不建 | 候选对象清单 |
| 第三步 | 关系识别 | 关系要能参与计算；不用于计算的关系暂不建 | 候选关系清单 |
| 第四步 | 状态识别 | 对象不是静态的；状态变化驱动业务过程 | 候选状态清单 |
| 第五步 | 行动识别 | 行动有前置条件、参数、后置影响 | 候选行动清单 |
| 第六步 | 边界确认 | 由业务闭环决定边界；业务方确认 | 本体边界说明书 |

**七要素框架**——附录注明其来源是"中国信通院提出的工业对象信息抽取框架"：

| 要素 | 说明 | 示例 |
|------|------|------|
| 对象 | 业务世界中的实体 | 设备、物料、订单、人员 |
| 属性 | 对象的特征 | 设备编号、设备类型、设备状态 |
| 关系 | 对象之间的关联 | 设备属于产线，产线生产订单 |
| 事件 | 业务过程中的事件 | 设备故障、订单延迟、质量异常 |
| 状态 | 对象的当前状态 | 设备运行中、订单生产中 |
| 规则 | 业务规则 | 设备故障时必须停机 |
| 行动 | 可执行的行动 | 设备切换、订单取消、质量返工 |

**术语歧义处理决策树**（四条分支，每条都给了示例与处理）：

- **同名不同义** → 分别定义，通过语义标识区分。MES 中"工单"= 生产任务单，ERP 中"工单"= 销售订单 → 分别定义 `ProductionWorkOrder` 与 `SalesOrder`
- **同义不同名** → 统一标准术语。"设备"与"机器"多数场景同义 → 统一为 `Equipment`
- **上下位混淆** → 归并到上位概念。"数控机床"是"设备"的子类 → 归并到 `Equipment` 下，定义 `CNCMachine` 作为子类
- **近似但不等价** → 标注为近似映射，**运行时不作等价替换**。MES 中"直通率"与本体中"良率" → 近似映射并标注差异（直通率不计返修，良率包含返修件）

**交付物**：《本体识别清单》= 候选场景清单、候选对象清单、候选关系清单、候选状态清单、候选行动清单、本体边界说明书。

### 2. 最小世界模型构建方法论（B.3）

**适用场景**：已有明确业务场景，需要构建一个能跑通业务闭环的最小本体，而非大而全的企业本体。

**核心定义**：最小世界模型（Minimum World Model，MWM）"是一个能跑通业务闭环的最小本体。它不是'大而全的企业本体'，而是'为解决一个具体业务问题而构建的最小业务世界'"。

**三要素与判断标准**：

| 要素 | 含义 | 判断标准 |
|------|------|---------|
| 最小 | 最小可运行闭环 | 问题不是查字段能解决？有业务上下文？能形成闭环？ |
| 世界 | 业务对象及其关系的可计算世界 | 对象是什么？现在什么状态？状态为什么变化？ |
| 模型 | 动态可运行的业务模型 | 数据结构 + 业务逻辑 + 执行引擎 |

**最小单元是闭环而非类**：`问题 → 对象 → 关系 → 状态 → 计算 → 判断 → 行动 → 结果`。以"设备故障影响分析"为例：

| 环节 | 内容 |
|------|------|
| 问题 | 设备 EQ003 故障后，会影响哪些生产环节？ |
| 对象 | Equipment、ProcessUnit、ProductionLine、Order、Risk、Action |
| 关系 | BELONGS_TO、AFFECTS、FEEDS、PRODUCES |
| 状态 | 故障、能力下降、产能受限、交付风险上升 |
| 计算 | 沿关系链传播：设备 → 工艺单元 → 产线 → 订单 |
| 判断 | 订单 O001 交付风险从低上升为高 |
| 行动 | 执行设备切换，将任务从 EQ003 切换到 EQ007 |
| 结果 | EQ007 承担生产，产能恢复，风险下降 |

**SmallWorld-小世界**（高颂数科对最小世界模型方法论的命名，定位"可信数据空间的最小世界模型"）：

三句话——一个能够回答问题的本体，是模型；一个能够解释问题的本体，是业务世界；一个能够判断、行动，并在行动后重新计算状态的本体，才开始真正成为企业运行的一部分。

四条核心原则——先做小闭环，再做大本体；先证明价值，再扩展世界；先接入数据，再优化模型；先解决业务问题，再追求技术完美。

**交付物**：《最小世界模型 V1.0》= 本体草案、业务闭环图、实例数据、验证报告。

### 3. 闪电建模方法论 / 闪电行动（B.4）

**适用场景**：刚开始做本体、缺经验和数据积累；业务部门对本体价值存疑、需要结果证明；项目周期紧张；数据源不完善、需要在使用中完善。

**核心逻辑**：不等条件完备，先用最小代价跑通一个闭环，用结果说话。

**五步法**：

| 步骤 | 时间 | 核心任务 | 关键要点 | 交付物 |
|------|------|---------|---------|--------|
| 第一步 | 第 1 周 | 快速锁定切入场景 | 不要等，主动找；三问判断；场景评估矩阵 | 场景定义书 |
| 第二步 | 第 2 周 | 画业务闭环，不画类图 | 先画流程，再建模型；用白板不用建模工具 | 业务闭环图 |
| 第三步 | 第 3–4 周 | 建立最小对象集 | 只建参与闭环的对象和关系；够用即可 | 本体草案 |
| 第四步 | 第 5–6 周 | 定义状态与关系，让本体可计算 | 对象不是静态的；关系要能参与计算 | 本体 V0.5 |
| 第五步 | 第 7–8 周 | 接入数据，让对象"活起来" | 不要继续扩充 Schema；尽快连接真实数据 | 本体 V1.0 + 实例数据 |

**场景评估矩阵**（五维，每维 1–5 分）：

| 评估维度 | 评估问题 | 评分标准（5 分 / 1 分） |
|---------|---------|----------------------|
| 业务紧迫性 | 业务方是否面临明确痛点？ | 5 分 = 业务方主动提出；1 分 = 业务方无感知 |
| 数据可得性 | 是否已有可接入的数据源？ | 5 分 = 已有数据库且可对接；1 分 = 数据完全不可得 |
| 边界清晰度 | 场景范围是否可控？ | 5 分 = 可明确界定范围；1 分 = 范围模糊 |
| 效果可量化 | 是否有可量化的验证指标？ | 5 分 = 有明确成功标准；1 分 = 无法量化 |
| 合作方意愿 | 合作方是否愿意配合？ | 5 分 = 已有合作基础且意愿明确；1 分 = 无合作方 |

**八周甘特图**（附录中以方块条形图给出）：第 1 周锁定场景 → 第 2 周画闭环 → 第 3–4 周建对象集 → 第 5–6 周定义状态 → 第 7–8 周接入数据。

**适用 / 不适用**：

| 适用场景 | 不适用场景 |
|---------|-----------|
| 企业刚开始做本体，缺乏经验 | 企业已有成熟本体库，需大规模扩展 |
| 业务部门对本体价值存疑 | 本体需覆盖多个业务领域，需全局设计 |
| 项目周期紧张，需短期看到成果 | 本体需跨组织协作，需多方协商 |
| 数据源不完善，需在使用中完善 | 数据安全要求极高，不能快速接入 |

**交付物**：《闪电行动成果包》= 场景定义书、业务闭环图、本体草案、本体 V0.5、本体 V1.0 + 实例数据。

### 4. OBAC 访问控制梳理方法论（B.5）

**适用场景**：可信数据空间里需要精确到概念、实体、实例、属性级别的细粒度访问控制；需要把数据安全法规、行业标准转化为机器可读的本体约束。

**定义**：OBAC（Ontology-Based Access Control，基于本体的访问控制）"是一种利用语义网技术，通过领域本体中的概念和关系实现细粒度访问控制的方法"。

**与传统访问控制的区别**：

| 方法 | 控制对象 | 示例 |
|------|---------|------|
| 传统访问控制 | 资源 | 用户 A 可以访问资源 B |
| OBAC | 本体中的概念、对象、属性及关系 | 用户 A 可以访问属于 Equipment 类的、位于 ProductionLine(A) 上的、状态为 Running 的 Equipment 实例 |

**三项核心功能**：

| 功能 | 说明 | 具体内容 |
|------|------|---------|
| 本体建模与语义约束 | 构建领域本体库，将核心实体及关系形式化建模 | 实体类型定义、属性定义、公理定义 |
| 语义级准入校验 | 基于本体规则实现任务级权限验证 | 任务级 / 数据级 / 操作级权限验证 |
| 合规规则嵌入 | 将法规、标准转化为机器可读本体约束 | 数据安全法规嵌入、行业标准嵌入、企业内部制度嵌入 |

**五层 + 两库 + 两接口架构**：

| 层次 | 组件 | 功能 |
|------|------|------|
| 接口层 | PDP 接口、PEP 接口 | 接收访问请求、返回决策结果；执行决策，拦截/放行 |
| 决策层 | 请求解析、语义推理、决策引擎、合规检查、冲突消解 | 解析主体/客体/操作/上下文；基于本体推理；做出决策 |
| 策略层 | 策略定义、策略存储、策略匹配、策略组合、策略冲突 | 定义和管理访问控制策略 |
| 本体层 | 本体加载、本体校验、本体推理、本体查询、本体版本 | 加载和维护本体 |
| 基础层 | 身份管理、凭证管理、令牌管理、审计存证、国密算法 | 提供基础安全服务 |
| 两库 | 策略库、本体库 | 存储策略和本体 |
| 两接口 | PDP 接口、PEP 接口 | 策略决策点与策略执行点 |

**使用控制语义规则**（五条，原文以逻辑表达式给出）：

| 规则 | 语义表达 |
|------|---------|
| 谁可以使用 | `Organization(A) ∧ DataResource(D) → canAccess(A, D)` |
| 什么条件下可以使用 | `Organization(A) ∧ DataResource(D) ∧ UserConsent(A, D) → canAccess(A, D)` |
| 可以使用什么操作 | `Organization(A) ∧ DataResource(D) → canQuery(A, D) ∧ ¬canModify(A, D)` |
| 使用次数限制 | `Organization(A) ∧ DataResource(D) → queryCount(A, D) ≤ 100` |
| 使用时间限制 | `Organization(A) ∧ DataResource(D) → accessTime(A, D) ≤ 2027-12-31` |

**与 RBAC、ABAC 的关系**：

| 方法 | 解决问题 | 与 OBAC 结合 |
|------|---------|-------------|
| RBAC | 谁有什么角色 | OBAC + RBAC：角色到本体对象权限的映射 |
| ABAC | 满足什么条件可以访问 | OBAC + ABAC：基于语义属性的访问控制 |
| OBAC | 访问的对象在业务语义上是什么 | 语义级访问控制 |

**交付物**：《OBAC 访问控制配置表》= 本体模型、策略库、PDP/PEP 接口配置、合规规则清单、审计存证方案。

### 5. 有效词元判定方法论（B.6）

**适用场景**：智能体服务进入商业计量阶段，需要判定哪些词元应进入商业计量，避免"刷词元"，激励高质量服务，实现公平交易。

**定义**：只有同时满足时延、可用性、准确率等服务等级要求、**最终被用户实际使用**的输出词元，才进入商业计量。

**判定流程**（顺序判定，任一环节不通过即不计入商业计量）：

```
总词元
 → 时延是否满足 SLA？  否 → 不计入商业计量
 → 可用性是否达标？    否 → 不计入商业计量
 → 准确率是否达标？    否 → 不计入商业计量
 → 是否被用户实际使用？否 → 不计入商业计量
 → 有效词元 → 商业计量
```

**计算公式**：

```
有效词元 = 总词元 × 服务等级系数 × 实际使用系数
```

| 系数 | 判定标准 | 取值 |
|------|---------|------|
| 服务等级系数 | 时延、可用性、准确率全部满足 SLA | 1 |
| 服务等级系数 | 部分满足 SLA | 0.5—1 |
| 服务等级系数 | 不满足 SLA | 0 |
| 实际使用系数 | 被用户实际使用 | 1 |
| 实际使用系数 | 未被用户实际使用 | 0 |

**本体依赖**（判定项靠什么本体约束落地）：

| 判定项 | 本体依赖 |
|--------|---------|
| 时延是否满足 SLA | 本体中的服务等级约束 |
| 准确率是否达标 | 本体中的质量指标约束 |
| 是否被用户实际使用 | 本体中的业务闭环验证 |

**词元语义锚点四层**：

| 层次 | 锚点 | 示例 |
|------|------|------|
| 第一层 | 实体锚点 | 数据访问词元关联到数据实体 |
| 第二层 | 属性锚点 | 查询设备状态的词元关联到 `equipmentStatus` 属性 |
| 第三层 | 关系锚点 | 查询设备所属产线的词元关联到 `belongsToLine` 关系 |
| 第四层 | 行动锚点 | 执行设备切换的词元关联到 `switchEquipment` 行动 |

**词元定价模型**：`词元价格 = 成本加成 + 市场供需 + 质量分级 + 场景差异化`

| 因素 | 说明 |
|------|------|
| 成本加成 | 算力成本、数据成本、模型成本、人力成本 |
| 市场供需 | 需求旺盛时价格上升，需求不足时价格下降 |
| 质量分级 | 质量高价格高，质量低价格低 |
| 场景差异化 | 高风险场景价格高，低风险场景价格低 |

**交付物**：《有效词元判定规则》= 服务等级约束清单、质量指标约束清单、业务闭环验证规则、有效词元计算表、词元定价表。

### 6. Xsensus 全域数据智能感知方法论（B.7）

**适用场景**：需要把多源异构数据实时映射为业务世界中的对象，让本体对象"活起来"，支撑智能体的感知闭环。

**定义**：Xsensus 是高颂数科的全域数据智能感知技术，负责将**传感器数据、业务系统数据、文档数据**实时解析并映射为本体中的对象实例和状态更新。

**支撑的闭环**：最小世界模型三层闭环中的第一层——感知闭环：

```
数据采集 → 数据解析 → 状态更新 → 本体实例更新 → 触发认知闭环
```

**数据接入三步骤**：

| 步骤 | 工作内容 | 关键要点 | 示例 |
|------|---------|---------|------|
| 第一步 | 数据源接入 | 连接 MES、ERP、设备管理系统等数据源 | 连接 MES 设备表、ERP 订单表 |
| 第二步 | 数据映射 | 将数据库表、字段映射到本体中的类、属性 | `equipment_master` 表 → Equipment 类；`equipment_id` 字段 → `equipmentId` 属性 |
| 第三步 | 实例生成 | 根据映射规则，从原始数据生成 RDF 实例 | EQ003 是 Equipment 实例，状态 = 故障，振动 = 6.8 |

**四类映射**：

| 映射类型 | 说明 | 示例 |
|---------|------|------|
| 表到类映射 | 数据库表映射到本体类 | `equipment_master` 表 → Equipment 类 |
| 字段到属性映射 | 数据库字段映射到本体属性 | `equipment_id` 字段 → `equipmentId` 数据属性 |
| 外键到对象属性映射 | 数据库外键映射到本体对象属性 | `equipment.line_id` 外键 → `belongsToLine` 对象属性 |
| 枚举值到个体映射 | 数据库枚举值映射到本体个体 | `equipment_status='运行'` → `EquipmentStatus_Running` 个体 |

**运行时对三种"语义关系"的区别对待**（这条对工程设计很关键）：

| 映射类型 | 含义 | 运行时处理 |
|---------|------|-----------|
| 等价映射 | 两个概念含义完全相同 | 可作等价替换 |
| 上下位映射 | 一个概念是另一个概念的子类 | 可作上下位推理 |
| 近似映射 | 两个概念含义相近但不完全相同 | **不应**在运行时作等价替换 |

**状态更新机制**：

| 更新类型 | 触发条件 | 更新内容 |
|---------|---------|---------|
| 设备状态更新 | 传感器数据变化 | 运行中 → 故障 → 维修中 → 运行中 |
| 订单状态更新 | 业务系统数据变化 | 待确认 → 生产中 → 延迟 → 部分交付 |
| 风险状态更新 | 规则推理结果 | 正常 → 关注 → 预警 → 高风险 → 已处置 |

**交付物**：《Xsensus 数据接入方案》= 数据源清单、映射规则清单、实例生成规则、状态更新规则、数据质量报告。

### 7. 本体治理方法论（B.8）

**治理架构**（四层 + 一个旁挂委员会）：

| 层次 | 角色 | 职责 |
|------|------|------|
| 决策层 | 本体 Owner | 审批变更、主持评审、监控质量、裁决争议、对外沟通 |
| 执行层 | 本体运营工程师 | 日常维护、版本发布、质量监控、变更实施、消费方支持 |
| 评审层 | 业务评审组 | 评审概念定义、关系准确性、业务规则合理性 |
| 消费层 | AI 消费方 | 使用本体库、反馈消费问题、提出变更需求 |
| 旁挂 | 技术委员会 | 审定重大变更、仲裁争议、审查标准符合性 |

**语义化版本规则** `MAJOR.MINOR.PATCH`：

| 版本类型 | 触发条件 | 示例 |
|---------|---------|------|
| MAJOR | 不兼容变更 | 删除类、删除属性、修改 Domain/Range |
| MINOR | 向后兼容的功能新增 | 新增类、新增属性、新增关系 |
| PATCH | 向后兼容的缺陷修复 | 修正标签、修正注释、调整 SHACL 约束 |

**Git 工作流**：`main`（稳定版本）、`develop`（开发主分支）、`feature/`（功能开发）、`release/`（版本发布准备）、`hotfix/*`（紧急修复）。

**变更管理**：RFC 五步法 = 提案 → 影响分析 → 评审 → 灰度生效 → 正式发布。

**影响分析五问**：

| 问题 | 查询内容 | 输出 |
|------|---------|------|
| 下游 Agent 影响 | 哪些智能体引用了被变更的类/属性 | 受影响 Agent 清单 |
| 映射规则影响 | 哪些 R2RML 映射引用了被变更的类/属性 | 受影响映射清单 |
| SHACL 约束影响 | 哪些 SHACL 形状引用了被变更的类/属性 | 受影响约束清单 |
| 实例数据影响 | 有多少实例使用了被变更的类/属性 | 受影响实例数量 |
| 跨行业本体影响 | 行业本体包是否引用了被变更的通用级概念 | 跨行业影响清单 |

**质量监控指标**（目标值 / 告警阈值）：

| 指标类别 | 指标名称 | 目标值 | 告警阈值 |
|---------|---------|--------|---------|
| 一致性 | 推理一致性 | 通过 | 不通过即告警 |
| 完整性 | 孤儿概念比例 | ≤ 5% | ≥ 10% 告警 |
| 完整性 | 属性覆盖率 | ≥ 90% | ≤ 80% 告警 |
| 准确性 | 标签缺失率 | ≤ 2% | ≥ 5% 告警 |
| 规范性 | SHACL 违规数 | 0 | ≥ 1 即告警 |
| 可溯源性 | 变更记录覆盖率 | ≥ 95% | ≤ 90% 告警 |
| 消费活跃度 | 月引用次数 | 持续增长 | 环比下降 20% 告警 |

**交付物**：《本体治理手册》= 治理架构图、版本管理规范、RFC 流程文档、质量监控仪表盘配置、变更通知模板。

### 8. 消费方生态运营方法论（B.9）
