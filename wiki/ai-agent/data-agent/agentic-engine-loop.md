# 从洞察到行动：Agentic Engine 的闭环架构与工程实践

> 核心主张：ROI 下降不是"分析能力不够"的问题，而是分析、决策、执行、复用四段彼此脱节的问题。解法不是再做一个更强的问数工具，而是三层叠加——**分析运营一体化**（找到原因并让方案落地）、**Agent 友好**（让 Agent 串联分析与执行）、**企业级 Agent 平台**（沉淀方法与知识让团队复用），三层共同支撑"从洞察到行动"的业务闭环。

演讲信息：DACon 2026 北京站「从分析闭环到行动闭环：Data Agent 的边界突破」专场，演讲嘉宾王浩强（ThinkingAI，产品为 Agentic Engine / AgentOS）。

## 背景与问题

### 引子：ROI 下降了，接下来怎么办

场景示例：某电商 App 最近一周 **ROI 下降 10%**。演讲用这一个场景引出三问：

| 问题 | 追问 | 对应能力 |
|------|------|---------|
| **01 为什么下降？** | 原因能否找准，解决方案能否落地？ | 分析运营一体化 |
| **02 多久能行动？** | 分析、决策与执行，能否更快衔接？ | Agent 友好 |
| **03 下次能复用吗？** | 这次经验，能否成为团队的共同能力？ | 企业级 Agent 平台 |

这三问构成了整场演讲的目录骨架：01 分析运营一体化、02 Agent 友好、03 企业级 Agent 平台、04 整体架构回顾（回到案例，看三部分如何共同发挥作用）。

### 问题的本质

原文的隐含结构是：Data Agent 的短板不在"算得准不准"，而在**从结论到动作的链条断了**——原因定位完，方案落不了地；方案有了，执行要跨系统、跨角色、耗时数天；这次解决了，下次同类问题仍从零开始。三问分别对应"落地"、"速度"、"复用"三个断点。

## 方案/架构

### 总体：开放融合的数据底座

定位：复用企业现有数仓与基础设施，支撑分析、运营和 Agent 应用。整体是"底座 + 平台 + 治理"的纵向分层结构，右侧统一治理贯穿。

| 层次 | 内容 |
|------|------|
| **企业业务生态** | 办公入口 / Agent；业务系统 / 自建应用 |
| **AgentOS 平台** | 构建 / 发布 / 运行；系统 Agent / 自定义 Agent / Agent Team；业务上下文 · 工具驱动 · 模型 / Skill · 动态沙箱 |
| **业务应用** | 行为分析、BI 看板、用户运营、A/B 实验 |
| **能力开放与业务语义** | OpenAPI / CLI / MCP；事件 / 实体 / 标签 / 指标；业务语义 / Workflow；统一资产与业务方法 |
| **开放引擎（查询与计算）** | 查询抽象 / SQL 网关 / 引擎适配与任务路由；Trino 跨源联合查询；StarRocks 分析查询加速 |
| **多仓融合** | 外源仓（企业数仓）、内置仓（存算分离）、应用库（StarRocks / ADS） |
| **接入与加工** | SDK / API / CDC 数据接入；Flink / SQL / ETL 加工 · 落仓 · 回传 |
| **基础设施共建** | 计算 / 存储 / 中间件 / 监控；基础组件复用；多云 / 私有部署；弹性伸缩 · 资源隔离 |

左侧企业侧输入：企业现有数仓（数据湖 / 外部引擎，直连映射 · 共享）、全域业务数据（行为 / 业务库、广告 / 归因 / 社区）。

右侧**统一治理**四项：权限与审计、数据与资产、观测与评测、用量与成本。

### 数据底座的四段能力

**1. 全域数据采集**

| 来源 | 采集方式 |
|------|---------|
| 客户端（App、游戏、PC、小程序） | 自动采集 |
| 服务端（Java、Go 等） | 服务端 SDK |
| 数据库（MySQL、ClickHouse 等） | 直连 / 跨源映射 / 数据流加工 |
| 广告与归因（腾讯广告、AppsFlyer 等） | Pull / Push API |
| 社区（抖音、小红书等） | 官方 API |

五路汇入 Agentic Engine 全域数据。

**2. 数据计算与存储**（三件事：开放引擎、弹性计算、分层存储）

- 开放引擎：统一查询入口 → 按配置路由 → Trino（跨源联合查询）/ StarRocks（分析查询加速）。统一查询入口兼容分析模型；按需配置路由适配查询场景
- 弹性计算：高峰扩容、低峰回收；项目资源隔离，降低调用干扰
- 分层存储：HDFS（近期数据）↔ 统一查询 ↔ 对象存储（历史数据）；热数据保性能，冷数据降成本；统一查询接口兼容不同存储

**3. 全域数据洞察**

- 应用内行为分析：分析模型覆盖事件、留存、漏斗、会话、归因等 **12 个模型**；用户与 Agent 一体化分析，追踪转化与流失
- 性能分析：崩溃、卡顿、异常、内存、电量等指标监控
- 广告投放与归因：评估渠道价值与投入产出；接入 Adjust（Report Service API）与 AppsFlyer（Push API），覆盖成本、收益、曝光、点击、转化、归因
- 社区洞察：识别舆情风险与异常讨论；整体趋势图例区分重大事故、黑产、公关事件、引流引战

**4. 会话回放**

以用户视角还原操作过程，四个维度：页面浏览（页面滚动、内容浏览）、表单交互（表单填写、提交操作）、视频体验（视频播放、进度拖动）、数据安全（可控采集、加密脱敏）。

### 运营能力：从圈选到效果回流的闭环

**左侧：运营对象与圈选** —— 对象为用户 / 商品 / 活动；圈选规则基于用户属性 / 行为条件、标签 / 分群。

**右侧三条能力线**：

| 能力 | 配置内容 | 形态示意 |
|------|---------|---------|
| **运营任务** | 定时 / 触发式；通道与内容配置 | 触发式：业务事件 → 条件判断 → 执行任务；流程画布：任务 A → 任务 B / 任务 C |
| **A/B 实验** | 流量分组与变量配置；实验指标评估 | 分流到 A / B 两支 |
| **配置中心** | 配置模板与参数 | Webhook 下发 / SDK 拉取 |

**底部：效果反馈** —— 执行与效果数据回流，支持策略迭代。

### 安全合规

| 维度 | 内容 |
|------|------|
| **私有部署** | 企业内网部署；数据进出可控；存储自主掌握（平台与存储同在企业内网） |
| **数据保护** | 数据按需采集；全链路加密；用户身份匿名（采集 → 加密 → 匿名） |
| **权限管控** | 角色功能授权；细粒度访问控制；敏感属性脱敏。示意：角色 A 可查看、不可配置；角色 B 可查看、可配置 |
| **操作审计** | 用户操作追溯；**Agent 操作追溯**；敏感操作审计 |

### Agent 友好：让 Agent 理解业务、调用能力

四层能力栈（自上而下）：

1. **Agent 客户端**：ChatGPT、Cursor、Claude Code、WorkBuddy、豆包工作、千问办公
2. **能力服务**：CLI & MCP（统一调用入口）、Skill（行业经验沉淀）、Workflow（编排业务流程）、语义层（理解业务含义）
3. **AE 产品能力**：数据接入、数据治理、数据洞察、用户运营

#### AE-CLI：面向 Agent 的统一能力入口

把原本面向不同角色的入口统一开放给 Agent 调用与编排：

| 原有角色 | 原有入口 |
|------|------|
| 应用研发 | SDK |
| 数据开发 | 二开工具 |
| 分析师 | 分析界面 |
| 运营人员 | 运营界面 |

统一为 **AE-CLI**：统一调用入口，具备分层命令、能力发现、组合编排三项能力，底层仍是数据接入、数据治理、数据洞察、用户运营四类产品能力。

案例：电商 App 从埋点设计到分析与运营落地——埋点设计（埋点方案）→ 接入与验收（验收结果）→ 指标分析（分析结论）→ 人群圈选（目标人群）→ 策略执行（运营任务）→ 效果评估（评估报告）。

#### 语义层：三类知识来源 → 项目语义 → Agent

| 知识来源 | 处理方式 |
|------|------|
| **权威资产** | 自动发现与推荐关键资产；识别矛盾、沉淀可信知识 |
| **个人语义** | 自动整理偏好与工作经验；持续召回、沉淀项目语义 |
| **业务知识** | 自动整理资料、分析代码；融合背景、形成业务上下文 |

中间层**项目语义**：知识组织（汇集资产与业务知识）、持续更新（自动更新主题 Wiki）。

面向 **Agent** 的两项输出：业务理解（结合背景理解业务）、知识检索（提升检索效率与质量）。

### 企业级 Agent 平台：ThinkingAI AgentOS

平台六块能力：

| 模块 | 内容 |
|------|------|
| **开放连接**（Agent 互联 · A2A） | 国内：飞书 · 钉钉 · 企业微信；海外：Slack · Discord · WhatsApp · Lark |
| **Agent 与协作** | 系统 Agent（分析 · 运营 · A/B 实验）、自定义 Agent（角色与工具按需配置）、Agent Team（多 Agent 协同执行）、共享空间（目标 · 进度 · 知识共享） |
| **运行环境** | 沙箱隔离 · 弹性扩缩 |
| **模型与能力** | 模型 · Skill · MCP |
| **知识与记忆** | 分级知识库 · 空间记忆 |
| **观测与治理** | AI Monitor、安全审计、成本控制、ROI |

## 关键工程做法

### 1. 运行环境：沙箱与工作空间

| 机制 | 实现 |
|------|------|
| **弹性扩缩** | 1C2G ↔ 2C4G，按需扩容 / 缩容 |
| **回收恢复** | 运行 ↔ 已回收：自动回收、按需恢复 |
| **沙箱预热** | 预热准备 → 环境就绪 |
| **一人一沙箱** | 个人沙箱内含分析空间、研发空间 |
| **空间配置** | Skills / MCP / 模型 三项可配 |

内置工具：Claude Code、OpenClaw、Hermes、AE-CLI、Lark-CLI、Python、Node 等。

### 2. 模型与能力：模型、Skill、MCP 三件套

**模型**：用户 / Agent 级配置；智能路由按问题复杂度自动选模。截图中的配置项与取值（演示界面）：

- 分类模型：kimi-k2.7-code（系统模型），分类超时 3 秒
- 简单任务模型：glm-5.1
- 常规问题模型：glm-5.1
- 复杂问题模型：qwen3.7-plus
- 图片模型（可选）：kimi-k2.7-code

**Skill**：复用业务方法。Skill 市场按「全部 / 系统 / 公司 / 个人」四级管理。截图示例：AE 分析（/ae-analysis，AE 6.1，ThinkingAI 系统）——查询、创建和治理报表、看板、指标等 AE/TE 分析资产；生成埋点方案（/ae-generate-tracking-plan）。

**MCP**：连接业务工具。MCP 市场同样分「全部 / 系统 / 公司 / 个人」。截图示例：分析（ThinkingAI 系统，TA 分析核心服务，提供模型分析能力，如事件分析、漏斗分析、留存分析、归因分析、分布分析、区间分析、路径分析、热力图分析、排…）；运营流程画布服务（ThinkingAI 系统，运营流程画布工具提供自动化触达流程的查询、编辑、校验与分析能力）。

> 截图底部文字被裁切，上述服务描述为可辨识部分的转写，完整措辞「不确定」。

### 3. 知识与记忆

| 模块 | 链路 |
|------|------|
| **知识库**（统一知识入口） | 知识来源：文件资料、飞书文档、代码仓库 → 智能整理与构建 → RAG + LLMWiki 按需检索。定位：效果好 · 消耗低 · 编译快 |
| **空间记忆**（记住背景 · 延续上下文） | 记忆沉淀：会话中的背景与约定 → 提取 · 整理 · 确认 → 偏好、背景、边界。特性：空间隔离 · 多 Agent 复用 |

### 4. Agent 配置与协作

系统 Agent（分析 / 运营 / A/B 实验等预置角色）与自定义 Agent（角色与工具按需配置）都可以**编组**为 Agent Team（多 Agent 协同执行）；也可以**个人选用**后进入共享空间（目标 · 进度 · 知识共享）。

### 5. 开放连接：A2A 双向

办公入口（飞书、钉钉、企业微信）发起任务 → ThinkingAI AgentOS → 经 **A2A 协议**调用外部 Agent（业务 Agent、研发 Agent、第三方 Agent）；反向支持外部调用企业 Agent。

### 6. 观测与治理

| 运行管控 | 内容 |
|------|------|
| 运行观测 | 查看会话与 Trace 的消耗及错误；监控工具、模型与 Skill 调用异常 |
| 安全审计 | 检查敏感信息泄露与高风险工具操作；支持预置规则与企业自定义检查 |
| 费用管控 | 按用户、Agent 管理用量与费用；按任务难度自动选择合适模型 |

| ROI 评估 | 内容 |
|------|------|
| 使用成本 | 统计 Token 用量与实际费用；汇总用户与 Agent 的使用成本 |
| 工作成果 | 跟踪业务事项的进展与完成结果；查看知识沉淀与 Skill 复用价值 |
| 智能评估 | 按用户、Agent 综合评估投入产出；价值等级：高 / 中 / 低 |

### 7. 三部分如何协同：ROI 异常处理闭环

回到开场的案例（某电商 App 最近一周 ROI 下降 10%，场景示例），闭环由四个动作组成：

1. **数据接入**：广告成本、行为与订单
2. **数据洞察**：定位 ROI 下降原因
3. **策略执行**：圈选人群，执行干预与实验
4. **效果反馈**：评估效果并调整 → 回到"从洞察到行动"

三部分的分工与映射：

| 能力 | 在闭环中的职责 |
|------|------|
| **分析运营一体化** | 找到原因，让策略执行和效果验证形成闭环 |
| **Agent 友好** | 串联分析、圈选与执行，提升方案落地效率 |
| **企业级 Agent 平台** | 沉淀排查方法与知识，让团队持续复用 |

## 经验与边界

### 方法论层面的三个判断

1. **底座不替换，只融合**——"复用企业现有数仓与基础设施"是明确前提；通过外源仓 / 内置仓 / 应用库的多仓融合与 Trino + StarRocks 双引擎路由接入，而不是要求企业迁仓
2. **Agent 友好是接口问题，不是模型问题**——四层能力栈里，CLI & MCP、Skill、Workflow、语义层都是"让 Agent 能调用、能理解"的接口层，模型本身不在讨论范围内
3. **复用要靠平台沉淀，不靠个人**——第三问"下次能复用吗"由企业级 Agent 平台回答：知识库、空间记忆、Skill 市场、Agent Team、共享空间、ROI 评估共同构成组织记忆

### 边界与不确定处

- 案例是"场景示例"（原文标注），ROI 10% 不是真实客户数据；演讲未说明该案例是否来自实际项目
- 原文未给出任何效果指标，因此无法判断三层能力的实际收益；本页不补推
- 模型名称（kimi-k2.7-code、glm-5.1、qwen3.7-plus）来自演示界面截图，属于示例配置，不代表产品绑定关系
- Skill / MCP 市场截图中部分描述文字被裁切，转写以可辨识部分为准，完整措辞「不确定」
- 与同场黄达的演讲分工不同：本篇不涉及 Agent 运行时的身份、策略判定与凭证托管（那部分由 Amazon Bedrock AgentCore 一侧承担）；本篇的"沙箱隔离"只到规格与生命周期层面，未展开隔离实现
- 原文未提及：多租户下的数据隔离粒度、Agent 操作的权限模型细节、跨云部署的支持范围、Agent Team 的调度与失败恢复机制
