# 本体驱动的数据流通与使用控制（OBAC）

> **一句话定位**：数据流通的根本障碍是"**传得到，读不懂**"——字段名对得上、含义对不上。第 13 章的答案是：数据流通需要的不是"**统一**"而是"**对齐**"，本体是语义对齐的核心技术；TC609 的四层语义互操作体系给出标准化框架，数字合约、使用控制、OBAC 访问控制构成三个核心机制——"数字合约让数据流通有'**约**'可依。使用控制让数据流通有'**规**'可循。OBAC 让数据流通有'**权**'可控"（13.7 / PDF 第 232 页）。

本章对应 PDF 物理页 219–232（书内页码 211–224），是第六篇的开篇章。

---

## 1. 根本障碍：传得到，读不懂（13.1 / PDF 第 219–221 页）

### 1.1 一个跨企业数据流通的真实场景（13.1.1）

原文设定（PDF 第 219 页）：某汽车零部件制造商（**甲方**）与其上游钢材供应商（**乙方**）签署数据共享协议。甲方希望获取乙方的**钢材批次质量数据**，用于优化自身的**热处理工艺参数**。乙方同意共享，但提出条件：**数据必须在甲方脱敏后使用**，不能泄露乙方的核心工艺信息。

双方技术团队逐问对接，话题依次落到术语、字段名、单位、延伸率、屈服强度、覆盖时长、取样标准（PDF 第 219–220 页）：

| # | 甲方问 | 乙方答 | 冲突点 |
|---|---|---|---|
| 1 | 需要"抗拉强度""屈服强度""延伸率"数据 | 有"拉伸试验"数据，含 **Rm / ReL / A** 三个指标 | 术语层：中文名与符号名不同 |
| 2 | 系统字段为 `tensile_strength`、`yield_strength`、`elongation` | 系统字段为 `Rm`、`ReL`、`A` | 字段名不同 |
| 3 | 问"抗拉强度"单位 | **MPa**；甲方也是 MPa | 这一项**对上了** |
| 4 | 问"延伸率"是断后延伸率还是均匀延伸率 | 记录的是**断后延伸率**；甲方需要**均匀延伸率** | 口径冲突 |
| 5 | 问"屈服强度"是上屈服强度还是下屈服强度 | 记录的是**下屈服强度**；甲方用**上屈服强度** | 口径冲突 |
| 6 | 问批次数据覆盖多长时间 | **2024 年 1 月到现在**；甲方工艺优化需要**至少三年**的数据 | 语境/时间范围冲突 |
| 7 | 问取样标准 | **GB/T 228.1**；甲方用 **ASTM E8** | 标准不同，"数据可比性存疑" |

> **照录差异**：对谈展开实为七问（含单位一问），原文紧接着的判词却是"**六个问题，全部对不上**"；其中单位一问双方同为 MPa（"我们的也是 MPa"）。本页不替原文统一。

原文的结论：这不是技术问题，而是**语义问题**——"双方的字段名可能对得上，但字段背后的含义完全不一样"。甲方以为"延伸率"就是延伸率，乙方也这么认为，但一个是断后延伸率、一个是均匀延伸率。"这就是数据流通的根本障碍：**传得到，读不懂**。"

### 1.2 三种"语义断裂"（13.1.2 / PDF 第 220 页）

| 断裂类型 | 原文定义 | 原文例子 |
|---|---|---|
| **术语断裂** | 同一个词，在不同系统、不同行业、不同标准中含义不同 | "客户"：ERP 中=签了合同的交易对象，CRM 中=有交互记录的潜在客户，财务系统中=应收账款的对象；"工单"：MES 中=生产任务单，ERP 中=销售订单，PLM 中=设计变更单 |
| **口径断裂** | 同一个指标，计算方式不同 | "直通率"=一次合格数除以投入数，不计返修；"良率"=最终合格数除以投入数，包含返修件——分子分母完全不同；"库存周转率"可按数量或金额计算、可按月末库存或平均库存计算，"口径不同，结果可能相差数倍" |
| **语境断裂** | 同一个数据，在不同业务语境下含义不同 | "温度 85℃"在回流焊工艺中可能是正常值，在冷链物流中可能是异常值；"设备故障"在预防性维护场景中是需要立即处置的事件，在设备健康评估场景中是需要分析的历史记录 |

### 1.3 传统数据交换的局限（13.1.3 / PDF 第 221 页）

三种方法及其失效原因：

| 方法 | 做法 | 原文指出的问题 |
|---|---|---|
| 方法一：统一字段名 | 要求所有系统使用相同字段名，"`tensile_strength` 就是 `tensile_strength`，不许叫 `Rm`" | 字段名统一了，含义可能仍不同：甲方用 `tensile_strength` 表示 **MPa** 单位的抗拉强度，乙方也用 `tensile_strength` 但表示 **ksi** 单位的抗拉强度 |
| 方法二：统一数据字典 | 要求所有系统使用相同数据字典，定义每个字段的含义、类型、取值范围 | 数据字典维护成本很高，很难覆盖所有业务场景；一个字典可能有**数千个字段**，"定义可能不准确、不一致、不完整" |
| 方法三：统一数据模型 | 要求所有系统使用相同数据模型，定义实体、属性、关系 | 协调成本巨大（涉及多个部门、多个系统、多个标准），且"往往赶不上业务变化的速度" |

共同局限："它们都试图通过'**统一**'来解决语义问题，但'统一'本身就是一个难以完成的任务。"原文由此转向——数据流通需要的不是"统一"，而是"**对齐**"——不要求所有系统使用相同字段名、相同数据字典、相同数据模型，而是要求不同系统之间能够**建立语义映射**，让数据"传得到，也读得懂"。"**本体，正是实现'语义对齐'的核心技术。**"

## 2. 语义互操作：TC609 标准的框架（13.2 / PDF 第 221–223 页）

### 2.1 四层层次体系（13.2.1 / PDF 第 222 页，图）

原文引用的标准是 **TC609-6-2026-XX《数据基础设施语义描述和互操作要求（征求意见稿）》**，它提出语义互操作的层次体系，**自下而上**包括四层。

PDF 第 222 页插图为"**语义互操作四层体系图**"，图顶注释为"注：TC609 标准提出语义互操作四层体系，逐级递进"。图的画面由三部分组成：左侧**四层堆叠平台**（自下而上编号 **01 智能体互操作层 → 02 语义互操作层 → 03 语法互操作层 → 04 互联互通层**，堆叠底部与左侧各标"**本体（Ontology）**"，左侧另有向上箭头配"**逐级递进**"）；中部三列表格"**层次｜解决｜关键要求**"；右侧一块卡片"**本体（Ontology）——是语义互操作的核心载体**"（与主图之间用双箭头连接）。逐层内容如下：

| 层（图中编号） | 原文名称与要求（正文） | 图中"解决"列 | 图中"关键要求"列 |
|---|---|---|---|
| 第一层（图中 **04**，最上层） | **互联互通层**：统一互联与连接器接入规则，确保"**传输可达**" | 传得到 | 统一互联与连接器接入规则 |
| 第二层（图中 **03**） | **语法互操作层**：统一语义描述项结构与机器可读交换格式，确保"**结构可读**" | 可解析 | 统一语义描述项结构与机器可读格式 |
| 第三层（图中 **02**） | **语义互操作层**：实现语义标识、映射等对齐机制，实现节点间语义互操作，确保"**含义一致**" | 读得懂 | 语义标识、映射等对齐机制 |
| 第四层（图中 **01**，最下层） | **智能体互操作层**：支撑智能体等新型智能应用对数据与智能服务的可信使用，实现基于语义的权限与使用控制，确保"**可信用数**" | 可信用数 | 基于语义的权限与使用控制 |

四层逐级递进：互联互通层解决"**传得到**"，语法互操作层解决"**可解析**"，语义互操作层解决"**读得懂**"，智能体互操作层解决"**用得好**"。注意最后一句的措辞并存——该层的"确保"句与图中"解决"列写的是"**可信用数**"，而小结句写"**用得好**"，原文两词并用。

> **图示与正文编号的差异（照录，不解释）**：正文把**互联互通层列为"第一层"、智能体互操作层列为"第四层"**（"自下而上包括四层"）；插图堆叠自下而上是"智能体互操作层 → 语义互操作层 → 语法互操作层 → 互联互通层"，编号分别为 01/02/03/04，左侧箭头标注"逐级递进"并**向上**。本页按正文章节逻辑（自下而上：互联互通→语法→语义→智能体）叙述，并在表中注明图中编号。

### 2.2 语义互操作的核心要求（13.2.2 / PDF 第 222–223 页）

| 要求 | 原文要求（逐字要点） | 原文给的解释 |
|---|---|---|
| **要求一** | 跨节点交换数据或提供智能服务时，**应**携带或可解析对应的语义描述 | "数据不仅要携带值，还要携带含义"：不能只传一个 **85.5**，还要传**温度=85.5℃、单位=摄氏度、业务含义=回流焊炉温、正常范围=230—250℃** |
| **要求二** | 节点经 **MCP、A2A、API** 等协议对外提供工具或智能服务时，**宜**在协议消息体中携带对应的语义描述，包括**概念映射、口径、语义标识及本体引用**等 | Agent A 告诉 Agent B"设备 **EQ003** 故障"，不仅要传"EQ003"和"故障"两个值，还要传"EQ003 属于 **Equipment 类**，**equipmentStatus** 属性的值为 **Fault**，设备故障时的标准处理流程是 **switchEquipment**" |
| **要求三** | 不同来源的语义描述应可通过语义对齐建立对应关系，对齐关系**宜**标注其所依据的**语义版本**等信息 | 本体的语义映射需要**版本管理**：甲方用的"延伸率"可能对应乙方本体的 **V1.0**，也可能对应 **V2.0**，不同版本之间的语义映射可能不同 |
| **要求四** | 语义描述项应**符合统一规定、不重复定义**；各层次互操作应**复用通用级、行业级已发布的语义标识与语义资产**，不应另建并行语义体系 | 本体建设应遵循"**复用优先**"原则，优先使用已有的国家标准、行业标准、通用本体，而不是各自为政 |

> **注**：本章 13.2.2 在原文里编号到**要求一—要求四**共四条（部分二手线索只提到"三条"），本页按原文保留全部四条。

### 2.3 本体在语义互操作中的三个核心作用（13.2.3 / PDF 第 223 页）

| 作用 | 原文内容 |
|---|---|
| **作用一：提供统一的语义模型** | 本体定义了业务世界的概念、属性、关系和公理。不同系统可以基于同一个本体来描述数据，确保语义一致 |
| **作用二：提供语义标识和语义映射** | 本体为每个概念、属性、关系分配**唯一的语义标识（IRI）**。不同系统之间可以通过语义映射建立对应关系 |
| **作用三：提供语义推理能力** | 本体中的公理和规则支持语义推理。通过推理可以**发现隐含的语义关系、验证语义的一致性、支持跨系统的语义查询** |

原文结论句："**没有本体，语义互操作就只是一句空话。**"

## 3. 数字合约中的语义约束（13.3 / PDF 第 223–225 页）

### 3.1 本质（13.3.1 / PDF 第 223–224 页）

**定义**：可信数据空间的数字合约，是数据流通参与方之间**就数据使用达成的协议**。与传统法律合同的区别在于：传统合同用**自然语言**写、依赖**法律体系**执行；数字合约用**机器可读的语言**写、依赖**技术系统**自动执行。其内容原文列七项：

| 维度 | 原文的追问 |
|---|---|
| 数据内容 | 哪些数据？数据范围是什么？ |
| 数据使用者 | 谁可以使用？使用者的身份是什么？ |
| 使用方式 | 怎么使用？查询、分析、建模、训练？ |
| 使用次数 | 使用多少次？一次性、限量、不限量？ |
| 使用范围 | 在什么范围内使用？地域范围、时间范围、业务范围？ |
| 使用环境 | 在什么环境下使用？数据沙箱、隐私计算环境？ |
| 使用条件 | 什么条件下可以使用？需要用户授权？需要脱敏？ |

### 3.2 语义表达（13.3.2）

合约内容**必须语义化表达**才能被机器自动理解和执行，原文给出"条款 → 本体构件"的对应：

| 合约维度 | 对应的本体构件 | 原文举例 |
|---|---|---|
| 数据内容 | 本体中的**数据实体** | 涉及"设备运行数据"→ 本体应有 **EquipmentOperationData** 实体，定义设备运行数据的范围、格式、更新频率 |
| 数据使用者 | 本体中的**机构/个人实体** | 涉及"甲方可以使用乙方数据"→ 本体应有 **Organization** 实体，甲方和乙方都是其实例 |
| 使用方式 | 本体中的**行动实体** | 涉及"甲方可以查询乙方数据"→ 本体应有 **QueryData** 行动，定义查询的参数、前置条件、后置影响 |
| 使用次数 | 本体中的**约束逻辑** | 涉及"甲方可以查询 100 次"→ 本体应有 **QueryLimit** 约束，定义查询次数的最大值 |
| 使用环境 | 本体中的**环境实体** | 涉及"数据只能在沙箱中使用"→ 本体应有 **DataSandbox** 环境实体，定义沙箱的安全等级、隔离要求 |

> 上表七项合约内容中，原文只对**五个维度**给出了对应的本体构件（数据内容、数据使用者、使用方式、使用次数、使用环境）；**使用范围**与**使用条件**的语义表达原文未单独展开。

### 3.3 生命周期（13.3.3 / PDF 第 224 页）

六个环节：

| 环节 | 原文内容 |
|---|---|
| **创建** | 数据提供方创建数字合约草案，填写数据内容、使用者、使用方式、使用次数、使用范围、使用环境、使用条件 |
| **协商** | 数据使用方审阅草案、提出修改意见，双方通过多轮协商达成一致 |
| **签署** | 双方签署，数字合约正式生效 |
| **备案** | 在**可信数据空间**备案，获得**备案编号**，支持**审计追溯** |
| **履行** | 进入履行阶段，数据使用方按照合约规定使用数据 |
| **解除** | 数字合约到期或双方协商解除 |

> 13.3.4 "作用三"另给一套六项**状态取值**：草稿、待签署、已生效、履行中、已完成、已解除——与 13.3.3 的六环节并列，原文未说明二者如何对应。

### 3.4 本体在数字合约中的三个作用（13.3.4 / PDF 第 225 页）

| 作用 | 原文内容 |
|---|---|
| **作用一：合约内容的语义化表达** | 数据内容对应数据实体，使用方式对应行动实体，使用次数对应约束逻辑，使用环境对应环境实体 |
| **作用二：合约条款的自动化执行** | 本体中的公理和规则支持条款自动执行。若合约规定"查询次数不超过 100 次"，则**每次查询时**系统都会检查本体中的 **QueryLimit** 约束，**超过 100 次时自动拒绝** |
| **作用三：合约状态的动态跟踪** | 本体中的状态定义支持状态动态跟踪；状态可取"草稿""待签署""已生效""履行中""已完成""已解除"；本体定义了**状态转换规则**，支持状态的自动更新 |

## 4. 使用控制中的语义规则（13.4 / PDF 第 225–226 页）

### 4.1 核心需求（13.4.1 / PDF 第 225 页）

| 需求 | 原文内容 |
|---|---|
| **需求一：数据使用环境构建** | 根据策略要求构建多类型运行环境，如**明文计算环境、数据沙箱环境或隐私计算环境、密态计算环境**等，确保不同任务间的**数据、内存、进程安全隔离** |
| **需求二：控制策略执行** | 具备**策略解析、行为校验、操作执行**等策略全生命周期的监控和记录能力，**实时监控**数据使用行为 |
| **需求三：使用存证** | 实现数据流通的**日志存证、查验、追溯和上报**功能，为**策略执行情况反馈、异常中止及履约证明**提供支撑 |
| **需求四：接口标准化** | 支持**服务平台策略下发接口、策略执行情况反馈接口、异常中止控制接口、履约证明发送接口**等标准化接口 |

### 4.2 语义规则五条（13.4.2 / PDF 第 226 页）

"使用控制的策略，需要用语义化的方式表达"——五条规则，每条一句自然语言 + 一条语义表达（逐字照录）：

| 规则 | 自然语言 | 语义表达 |
|---|---|---|
| 规则一：谁可以使用 | "机构 A 可以使用数据 D。" | `Organization(A) ∧ DataResource(D) → canAccess(A, D)` |
| 规则二：什么条件下可以使用 | "机构 A 在获得用户授权后可以使用数据 D。" | `Organization(A) ∧ DataResource(D) ∧ UserConsent(A, D) → canAccess(A, D)` |
| 规则三：可以使用什么操作 | "机构 A 可以查询数据 D，但不能修改数据 D。" | `Organization(A) ∧ DataResource(D) → canQuery(A, D) ∧ ¬canModify(A, D)` |
| 规则四：使用次数限制 | "机构 A 最多可以查询数据 D 100 次。" | `Organization(A) ∧ DataResource(D) → queryCount(A, D) ≤ 100` |
| 规则五：使用时间限制 | "机构 A 只能在 2027 年 12 月 31 日之前使用数据 D。" | `Organization(A) ∧ DataResource(D) → accessTime(A, D) ≤ 2027-12-31` |

### 4.3 本体在使用控制中的三个作用（13.4.3）

| 作用 | 原文内容 |
|---|---|
| **作用一：控制对象的语义定义** | 控制对象可以是**概念、实体、实例、属性**；本体定义这些控制对象的类型、关系和约束 |
| **作用二：控制策略的语义表达** | 控制策略可以用本体中的公理和规则表达，支持自动化执行 |
| **作用三：控制执行的语义推理** | 系统可以基于本体中的公理和规则，**自动判断某个操作是否被允许** |

> **注**：13.4 节正文**没有**出现"五层+两库+两接口"——该结构在本章属于 **13.5.3 的 OBAC 架构**（见下节）；附录 B.5.5 也以 OBAC 的名义复述同一架构（PDF 第 306–307 页）。

## 5. OBAC：基于本体的访问控制（13.5 / PDF 第 227–230 页）

### 5.1 定义与和传统访问控制的区别（13.5.1 / PDF 第 227 页）

- **定义**：OBAC（Ontology-Based Access Control），即基于本体的访问控制，是一种**利用语义网技术、通过领域本体中的概念和关系实现细粒度访问控制**的方法。
- **与传统访问控制的区别**：传统访问控制以"**资源**"为控制对象；OBAC 以"**本体中的概念、对象、属性及关系**"为控制对象。

| 方法 | 原文示例 |
|---|---|
| 传统访问控制 | 用户 A 可以访问资源 B |
| OBAC | 用户 A 可以访问**属于 Equipment 类的、且位于 ProductionLine(A) 上的、状态为 Running 的** Equipment **实例** |

原文判词："OBAC 的控制粒度更细，控制语义更丰富。"

### 5.2 核心功能（13.5.2 / PDF 第 227 页）

| 功能 | 说明 | 原文列出的具体内容 |
|---|---|---|
| **本体建模与语义约束** | 构建领域**本体库**，将**设备、工艺、产品、订单**等核心实体及其关系形式化建模；需满足**实体类型定义、属性定义、公理定义**等要求 | —— |
| **语义级准入校验** | 基于本体规则实现**任务级**的权限验证，"确保智能体在正确的场景下调用正确的数据" | 任务级权限验证、数据级权限验证、操作级权限验证 |
| **合规规则嵌入** | 将**数据安全法规、行业标准**转化为机器可读的本体约束，实现合规审查的自动化执行 | 数据安全法规嵌入、行业标准嵌入、企业内部制度嵌入 |

### 5.3 架构与关键技术（13.5.3 / PDF 第 227–228 页）

### 5.4 OBAC 与 RBAC、ABAC 的关系（13.5.4 / PDF 第 229 页）

### 5.5 OBAC 在数据流通中的三个应用场景（13.5.5 / PDF 第 229–230 页）

## 7. 本章小结（13.7 / PDF 第 231–232 页）

1. 根本障碍是"传得到，读不懂"——"不同系统之间，术语可能对不上，口径可能不一致，语境可能不同"。
2. 传统方法试图用"标准化"解决语义问题，但"'统一'本身就是一个难以完成的任务"。
3. 需要的是"对齐"而非"统一"；"**本体，正是实现'语义对齐'的核心技术。**"
4. 本体在数据流通中的三个核心作用（提供统一的语义模型 / 提供语义标识和语义映射（IRI）/ 提供语义推理能力）与 2.3 节三作用**逐字相同**。
5. TC609 四层体系（互联互通层、语法互操作层、语义互操作层、智能体互操作层）"为本体驱动的数据流通提供了标准化框架"；**数字合约、使用控制、OBAC 访问控制是本体驱动数据流通的三个核心机制**——"数字合约让数据流通有'约'可依。使用控制让数据流通有'规'可循。OBAC 让数据流通有'权'可控。"

收束句："**本体让数据'传得到，也读得懂'。**"
