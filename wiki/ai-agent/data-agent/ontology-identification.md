# 本体识别：七要素框架与歧义处理

> **定位：** 第 4 章把"建什么本体"变成工序：**三原则 → 七要素抽取 → 六步法推进 → 决策树消歧 → 边界说明书收口**，落点是"识别的本质是聚焦"（4.8 节 / PDF 第 70 页）。承接 [[ontology-semantic-infrastructure]]，引出 [[minimal-world-model]]、[[ontology-six-step-method]]。

---

## 1. 定义与原则（4.1 节 / PDF 第 48–50 页）

> **本体识别（Ontology Identification）**：在构建本体之前，从业务场景、信息系统、文档资料、行业标准中系统性识别本体候选元素的过程；候选元素即业务对象、对象属性、对象关系、业务事件、动态状态、业务规则、可执行行动（PDF 第 48 页）。

| 对比 | 回答 | 产出 |
|------|------|------|
| 本体构建 | "怎么建"：定义类、属性、关系、公理，选形式化语言、映射数据源 | 本体库 |
| **本体识别** | "建什么"：哪些对象纳入、关系定义、状态跟踪、行动支持，边界在哪 | 本体候选元素清单 |
| 需求调研 | "用户想要什么功能" | 功能清单 |

**代价**：范围太宽→"大而全"陷阱；太窄→闭环跑不通；粒度太粗→语义理解不准；太细→维护成本急升。**与需求界定**：前者关注"业务需要什么"，后者关注"业务世界中有什么"；"需求界定为本体识别提供输入，本体识别为需求界定提供验证"，对象数据不可得则回退调整范围（PDF 第 49 页）。

| 原则 | 原文表述 | 论证 / 示例 |
|------|---------|------------|
| 一：业务驱动，不是技术驱动 | 不要问"我们能建什么本体"，要问"业务需要解决什么问题" | 反例是从数据表出发：表结构"面向存储，不是面向业务"，设备表上百字段中只有编号、状态、所属产线等少数与故障影响分析相关。"业务闭环决定本体边界，本体边界决定识别范围" |
| 二：闭环优先，不是概念完整 | "本体识别的最小单元不是'类'，而是'闭环'" | 问"没有它闭环能不能跑通"：不能→纳入；"能，但不够完整"→暂不纳入（如供应商、备件可后置） |
| 三：窄而深，不是宽而浅 | 优先覆盖 **1—2 个核心业务场景** | "宽而浅"三害：短期难证明价值、概念太多难深入、边界易失控；一场景跑通再扩展，"多个场景共享对象和关系后自然形成更大的本体" |

**常见误区**（4.1.4 节 / PDF 第 50 页；原文实为**五条**）：

| 误区 | 辨析 | 示例 |
|------|------|------|
| 把数据表当对象 | 表是存储结构，对象是概念 | 设备表含"所属产线"，产线却是独立对象 |
| 把字段当属性 | 一个字段可能对应多个属性 | `status` 取运行/停机/故障，"设备状态"是一个枚举属性 |
| 把外键当关系 | "外键只告诉数据库这两张表有关系，但不告诉业务系统这是什么关系" | `line_id` 或为"属于产线""安装在产线上""由产线管理" |
| 把状态当属性值 | 状态动态，属性值静态 | "额定功率"是属性，"当前状态"是状态 |
| 把行动当流程 | 流程是行动序列，行动是单个操作 | 处置流程"发现异常→…→重新观察"；要识别的是"设备切换""维修调度" |

## 2. 七要素框架（4.2 节 / PDF 第 50–55 页）

**来源**：中国信息通信研究院 2019 年起研究工业本体语义建模，2026 年 6 月发布《工业本体语义建模方法》，"一框架、两技术"体系中"一框架"即七要素框架（PDF 第 50 页）。**价值**：把"从文本抽取概念"的模糊任务，转为"按七个维度系统性识别"的清晰任务（PDF 第 51 页）。

| # | 要素 | 原文定义 | 识别标准 | 示例（设备故障影响分析） |
|---|------|---------|---------|------------------------|
| 1 | 对象 Object | 业务世界的实体，七要素核心；物理实体（设备、物料、产品、人员）或逻辑实体（订单、工单、项目） | ①唯一标识？②属性？③参与闭环？ | 设备 Equipment、工艺单元 ProcessUnit、产线 ProductionLine、订单 Order、风险 Risk、行动 Action |
| 2 | 属性 Attribute | 对象的特征；分**数据属性**（描述自身）与**对象属性**（描述关系） | ①自身还是关系？②类型？③范围？④参与计算？ | 设备编号、设备类型、设备状态（枚举：运行/停机/维护/故障/待机）、温度（℃）、振动（mm/s） |
| 3 | 关系 Relation | 对象间关联，"本体区别于数据表的关键要素"，需明确**定义域、值域、语义** | ①连接哪两对象？②方向？③基数？④参与计算？ | `belongsToProcessUnit`、`affectsProductionLine`、`hasAlarm`、`canReplace`、`feeds`、`produces` |
| 4 | 事件 Event | 业务过程中的事件；"对象是'谁'，事件是'发生了什么'" | ①由什么触发？②涉及哪些对象？③后果？④需要什么行动？ | 设备报警 Alarm、设备故障 EquipmentFailure、订单延迟 OrderDelay、质量异常 QualityAnomaly |
| 5 | 状态 State | 对象的动态特征（"额定功率"是属性，"当前状态"是状态） | ①有哪些？②如何转换？③什么触发？④如何传播？ | 运行中、降额、故障、维修中、停机；运行中→故障（报警）、故障→维修中（工单创建）、维修中→运行中（维修完成）、运行中→停机（计划停机） |
| 6 | 规则 Rule | 何时该做、不能做；"规则是本体中'公理'的来源" | ①约束谁？②触发条件？③执行结果？④硬/软约束？ | 故障必须触发影响分析、必须停机；一个设备只能属于一条产线；一个设备只有一个编号；故障则工艺单元能力下降 |
| 7 | 行动 Action | 可执行的业务操作；"规则是判断，行动是执行" | ①触发？②前置条件？③参数？④后置影响？⑤谁执行？ | `switchEquipment` 设备切换、`scheduleMaintenance` 维修调度、`adjustOrder` 订单调整、`reworkQuality` 质量返工 |

属性取值类型示例（PDF 第 51 页）：字符串、整数、枚举、日期；范围示例：正常范围、告警阈值、枚举值。

**应用三步**（PDF 第 54 页）：①**逐要素识别**——按对象→属性→关系→事件→状态→规则→行动次序，各用其标准筛选；②**交叉验证**——对象有属性？关系连接两个已识别对象？事件、状态、规则、行动是否挂接已识别对象？③**闭环验证**——问"闭环能不能跑通？缺哪个要素？"

**扩展到八环节**（PDF 第 54–55 页）：七要素答"世界有什么"，[[minimal-world-model]] 答"世界怎么运行"；八环节 = 问题、对象、关系、状态、计算、判断、行动、结果。

| 七要素 | → 八环节 | 七要素 | → 八环节 |
|--------|---------|--------|---------|
| 对象 | 对象 | 状态 | 状态 |
| 属性 | 状态（部分）、计算（部分） | 规则 | 判断 |
| 关系 | 关系、计算 | 行动 | 行动、结果 |
| 事件 | 问题（触发） | | |

"先用七要素识别业务世界的构成，再用八环节验证业务闭环的完整性。"（PDF 第 55 页）

## 3. 识别六步法（4.3 节 / PDF 第 55–62 页）

> "六步法不是线性的，而是迭代的。每一步都可能回溯到前一步，每一步都可能需要业务方参与。"（PDF 第 55 页）

**总览表（原文表格，PDF 第 56 页，整页渲染核对）：**

**六步法总览图（PDF 第 55 页下半页，图内文字已读出）**：六边形环绕布局——①业务场景扫描（"明确业务场景和核心场景"）②业务对象识别（"识别关键业务对象及其属性"）③关系识别（"识别对象之间的关联关系"）④状态识别（"识别对象的生命周期状态及转换"）⑤行动识别（"识别业务动作、操作及触发条件"）⑥边界确认（"确定业务边界和适用范围"）。中心圆"**迭代优化**"，副标"非线性·可回溯·协同共创"。图例：实线=主流程，双向虚线=回溯迭代。右侧"关键特征"：**迭代性**（每一步都可能回溯到前一步）、**协作性**（每一步都需要业务方参与）、**渐进优化**（在迭代中不断收敛本体定义）。说明："六步法不是线性的流程，而是一个持续迭代、协同共创的循环过程。"

**各步目标 / 方法 / 输入输出 / 示例：**

| 步骤 | 方法（原文） | 示例（设备故障影响分析） |
|------|-------------|------------------------|
| **一 场景扫描**（目标：找到值得解决的业务问题） | 三来源：①已有数字化项目痛点（验收报告、用户反馈、运维记录）②生态伙伴或行业用户（"不要问'你们需要什么数据'，要问'你们最近在解决什么问题'"）③政策与标准（国家数据局"数据要素×"行动明确工业制造、现代农业、商贸流通等**十二个重点方向**）；多场景用**场景选择评估矩阵**排序 | ①某企业设备故障诊断需**跨五个系统**查询、**平均耗时 30 分钟**，多项目提及未解决；②供应链伙伴"风险预警项目，但数据来源太杂，不知道怎么统一" |
| **二 对象识别**（核心步骤） | 四法：①从业务闭环倒推②从数据源扫描③从业务术语表提取④从行业标准复用（**GB/Z 195—2026** 定义工业智能体功能模块与交互对象，含设备、产线、物料、环境、工业软件） | ①闭环"设备报警→确认状态→分析影响→寻找方案→执行切换→重新观察"→设备、工艺单元、产线、订单、风险、行动；②MES `equipment_master`→设备、ERP `production_order`→订单（"一张表可能对应多个对象，一个对象可能对应多张表"） |
| **三 关系识别**（"最容易被忽视的步骤"） | 三法：①从业务动作倒推②从数据关联发现（"数据库关联不等于业务关系"）③从业务规则提取 | ①"判断是否影响生产"隐含"设备影响产线"；"寻找替代设备"隐含"设备可以替代设备"；③"一个设备只能属于一条产线"隐含"设备属于产线"，该关系是**函数性的** |
| **四 状态识别**（"最小世界模型区别于传统知识图谱的关键步骤"） | 三法：①从业务过程提取②从数据字典提取（"枚举值往往没有业务含义，需要业务专家解读"）③从业务规则提取 | ①设备"运行中"→"故障"触发处置流程；②`equipment_status` 的"1""2""3"对应运行/停机/故障；③"设备故障必须停机"隐含两个状态。转换四元组：**源状态、目标状态、触发条件、执行行动**——"运行中→故障"由"**振动值超标**"触发 |
| **五 行动识别**（"最具工程价值的步骤"） | 三法：①从业务闭环提取②从业务规则提取③从系统接口提取（API 往往对应可执行行动） | ①"执行切换"→设备切换；②"订单延迟必须通知客户"→通知客户；③MES"工单调整"接口→调整工单，ERP"采购订单创建"接口→创建采购订单 |
| **六 边界确认**（收口步骤） | 见 §5 | 见 §5 清单 |

**补充判据**：对象标准在 4.3.3 节为**四条**（PDF 第 59 页）——①唯一标识？②属性？③参与闭环？④与已识别对象有关系？"有一个不满足，暂时不纳入。"关系上"'参与业务计算'是关键标准"：不用于查询、规则、推理、影响分析或行动的关系"只是为了完整而存在"。行动语义模型七字段（以"设备切换"为例，PDF 第 61 页）：名称 `switchEquipment`／类型 设备操作／前置条件 源设备故障、目标设备可用、能力匹配／参数 源、目标设备编号、切换原因／后置影响 源设备改为"维修中"、目标设备改为"运行中"、产能与交付风险更新／执行者 维护决策 Agent／执行方式 调用 MES 接口。

## 4. 术语歧义处理（4.4 节 / PDF 第 62–65 页）

> "术语歧义是本体识别中最常见的难题。不同系统、不同部门、不同行业对同一个词可能有不同的理解。"

**四类型 + 决策树**（4.4.1–4.4.2 节）：第一步判类型 → 第二步 A/B/C/D，哲学是 A **拆**、B **并**、C **分层**、D **存疑不替换**。

| 类型 / 分支 | 定义 | 处理方法（原文） | 原文示例 → 标识 |
|------------|------|----------------|-----------------|
| **同名不同义**（A） | 同一个词在不同系统、行业、标准中含义不同 | **分别定义**，以语义标识区分；"不能因为都叫'客户'就合并" | "客户"：ERP=签约交易对象，CRM=潜在客户，财务=应收账款对象；"工单"：MES=生产任务单，ERP=销售订单，PLM=设计变更单。处理：`SalesCustomer`（销售客户）与 `EndUser`（终端用户）用**不同 IRI**；MES 工单→`ProductionWorkOrder`、ERP 工单→`SalesOrder` |
| **同义不同名**（B） | 不同的词指向同一概念 | **统一标准术语**：选最符合行业标准、最广泛使用的一个，其余作别名 | "设备"/"机器"（另有"生产设备""加工设备"）→`Equipment`，"机器"作别名；"直通率"/"一次合格率"（另有"FPY""一次通过率"） |
| **上下位混淆**（C） | 上位或下位概念被当同级概念使用 | **归并到上位概念**，用类层次结构表达 | "设备"与"数控机床""工业机器人""AGV"并列、"订单"与"销售订单/采购订单/生产订单"混用。处理："数控机床"并入 `Equipment`，`CNCMachine` 为其子类 |
| **近似但不等价**（D） | 含义相近但不完全相同 | **标注近似映射，运行时不作等价替换**，记录差异点 | 直通率=一次合格数÷投入数（不计返修），良率=最终合格数÷投入数（含返修件）；库存周转率可按数量或金额、月末或平均库存计，"相差数倍"。处理：近似映射并标注差异，"不能直接用'直通率'替代" |

**术语定义模板（10 字段，PDF 第 65 页，逐行核对；示例为"设备"）：**

| 字段 | 内容 / 示例 | 字段 | 内容 / 示例 |
|------|------------|------|------------|
| 名称 | 中文名+英文名：设备（Equipment） | 下位概念 | 子类：机床、机器人、AGV、传感器、PLC |
| 语义标识 | IRI：`http://iochina.com/industry-ontology#Equipment` | 别名和同义词 | 机器、生产设备、加工设备 |
| 定义 | 用描述性陈述表示概念：工业物理空间中的生产设备 | 示例 | 具体实例：数控机床 EQ003 |
| 适用范围 | 制造业生产场景 | 来源依据 | 标准或文档：GB/Z 195—2026 |
| 上位概念 | 父类：工业物理实体 | 责任主体 | 定义维护者：高颂数科 |

**工程实践四机制**：①**术语表维护**——记名称、定义、别名、来源、责任人，随本体版本更新；②**术语评审**——业务评审组审查（定义是否准确？是否与已有术语冲突？是否与国标一致？）；③**术语映射**——等价、上下位、近似，记入《语义映射与权限配置表》；④**术语变更管理**——走 **RFC 流程**（新增/改定义/删除/改映射），发布后通知消费方。

## 5. 本体边界确认（4.5 节 / PDF 第 66–67 页）

**标准**：边界"由业务闭环决定"——"它是否参与当前业务闭环？如果参与，纳入；如果不参与，暂时不建。"以"设备故障影响分析"为例：

| 类别 | 纳入 | 不纳入 |
|------|------|--------|
| 对象 | 设备（故障主体）、工艺单元（能力）、产线（产能）、订单（交付风险）、风险（判断结果）、行动（手段） | 供应商、客户、财务、人力、产品、物料 |
| 关系 | 属于工艺单元、影响产线、有报警、可以替代设备、供给、生产订单 | 供应、交付、结算、考核 |
| 状态 | 设备状态、工艺单元能力、产线产能、订单交付风险 | 供应商信用、客户满意度、员工绩效 |

**三法**：①**业务闭环验证法**——画闭环图沿环节标记，未标记的暂不纳入；②**影响传播验证法**——设备故障→工艺单元能力下降→下游工艺单元受影响→产线产能受限→订单交付风险上升；传播到的纳入，传播不到的（供应商、客户、财务、人力）不纳入；③**行动验证法**——"设备切换"操作源设备、目标设备、产线、订单，这些纳入。

**输出《本体边界说明书》四项**：纳入的概念列表（对象、属性、关系、状态、行动）、不纳入的概念列表、边界判定依据、后续扩展计划。**须业务专家参与**："备件"是否参与取决于处置方案——"切换替代设备"则不参与，"更换备件"则参与（PDF 第 62 页）。

**常见问题**：①**边界模糊**→用闭环图与影响传播图辅助，让专家在图上标记；②**边界争议**→以业务闭环与业务问题为判据；③**边界扩展压力**→建需求变更管理机制，每次扩展评估影响并经业务方与项目组确认，"避免边界无限膨胀"。

| 交付物 | 原文包含内容 |
|--------|-------------|
| 《**本体识别清单**》 | 候选场景清单、候选对象清单、候选关系清单、候选状态清单、候选行动清单 |
| 《**本体边界说明书**》 | 纳入的概念列表、不纳入的概念列表、边界判定依据、后续扩展计划 |
| 《**术语歧义处理清单**》 | 歧义术语列表、歧义类型、处理方式、映射关系 |
| 《**业务闭环图**》 | 业务闭环的图形表达，包括问题、对象、关系、状态、计算、判断、行动、结果 |

| 验证标准（问题即判据） |
|----------------------|
| **完整性**：识别出的对象、关系、状态、行动是否覆盖业务闭环所有环节？业务闭环能不能跑通？ |
| **准确性**：是否准确反映业务实际？业务专家是否认可？ |
| **一致性**：术语是否一致？是否存在同名不同义、同义不同名、上下位混淆、近似不等价？ |
| **可追溯性**：每个识别出的元素是否有来源依据？能否追溯到标准、文档、系统或业务专家？ |

**业务方确认**："本体识别不能是 IT 部门的闭门造车"，识别清单与边界说明书需**业务方签字确认**。七问：①场景是否准确？②闭环是否完整？③对象是否遗漏？④关系是否准确？⑤状态是否完整？⑥行动是否可执行？⑦边界是否合理？（PDF 第 69 页）

## 8. 章末小结与归纳（4.8 节 / PDF 第 70 页）

**原文小结**：起点错了后面全错；三原则为业务驱动、闭环优先、窄而深；七要素与八环节配合，"确保识别既不遗漏关键要素，也不脱离业务闭环"；六步法"不是线性的，而是迭代的"；四种歧义需不同处理，术语模板与管理机制是"工程保障"；边界确认是收口，"边界由业务闭环决定，由业务方确认"。结论句：**"识别的本质是聚焦。不是'把所有概念都列出来'，而是'聚焦当前业务闭环'。不是'建一个大而全的本体'，而是'建一个能跑通闭环的最小世界'。"** PDF 第 71 页篇封："**推理与构建：从 0 到 1 的本体工程路径**——先做小闭环，再做大本体；先证明价值，再扩展世界。"

**本页分析（归纳，非原文）**：①本章是全书方法层最密集的一章——第 2–3 章论证"为什么建"，本章首次给出可执行工序与判据；②同一判据条数不一致（对象标准 4.2.2.1 三条、4.3.3 四条），本页分别收录未合并；③"窄而深"与[[minimal-world-model]]"先做小闭环再做大本体"（[[semi-auto-ontology-and-lightning-action]]）是同一主张在不同层的表述。
