# DataBuddy 电商端到端演示拆解

> 本页只还原 **2026-10-20 腾讯云 DataBuddy 发布会**上的一场演示，所有数字与流程均为原文所述。产品整体定位、架构与接入路径见 [[databuddy]]。
> 演示共分五段，原文对应 5 个小节；以下按"数据流向"重排为 6 步，便于看清 Agent 接力关系。

## 起点：业务只想要答案

场景设定：一条**新的电商业务线已经开始产生订单**，经营会上却拿不出完整分析报表——销售趋势怎么看、哪些商品卖得好、客户为什么没有再次购买。

原文对问题的刻画是**角色接力成本**：数据就在业务库里，但回答这些问题要完成接入、清洗、数仓设计、任务调度、指标建设，"业务只想知道结果，背后的工作却需要多个角色接力"。演示把这一整套工作交给 Agent。

## 第 1 步：数据工程 Agent 从目标到 18 节点 Pipeline

用户只给了业务目标：接入现有业务库，准备**销售与交易趋势、客户购买与复购行为、商品与卖家表现**所需数据，每天早上更新。Agent 的动作链：

1. **探查**已有表、字段与可复用资产
2. 设计 **ODS → DWD → DWS → ADS 四层数仓**
3. 输出**表结构、字段含义、ER 图**——工程师在实施前核对业务实体、加工关系与数据粒度，有问题可直接改方案
4. **方案通过审核后**才开始创建生产任务：**9 个离线接入任务**（从业务源库取数）+ **9 个 SQL 任务**（清洗与转换），按上下游依赖连成 **18 节点 Pipeline**，运行周期与资源配置一并设置
5. 生成的 SQL 与任务产物进入 **Studio** 供继续检查、编辑——"开发者拿到的是一套已经编排好的工程资产，后续仍能按原来的方式维护"

演示截图（发布会议程"实机演示"）中的工作流构建界面显示上游 9 个接入节点、下游 9 个加工节点及其连线，右侧面板为运行记录/任务编排、调度配置、参数、报警、计算资源等属性区。

原文强调这一步为什么难：**"SQL 写完了，任务还远没有结束"**——源表字段逐个确认、加工层之间建依赖、调度/运行资源/失败重试都要配置；业务侧一个字段改名就可能让整条下游管线报错。

## 第 2 步：故障定位与经审批的自愈

演示人为制造故障：**上游 9 个接入任务全部成功，下游加工连续报错**。Agent 的处理顺序：

| 环节 | 动作 |
|------|------|
| 读证据 | 读取运行记录、任务配置、SQL 文件 |
| 定位根因 | 发现**业务方把字段名从全称改成了缩写**，旧 SQL 仍在引用原字段 |
| 圈影响面 | 列出受影响的下游任务 |
| 提方案 | 提出修复方案 |
| **等审批** | 等待用户批准 |
| 执行并验收 | 修改、重新发布、重跑；新运行记录显示任务恢复成功 |

原文的落点："从开发到故障恢复，Agent 都沿着同一条工作链路处理问题。"

截图中的运维对话呈现的是分层路由的形态：用户问"帮我看看这个工作流为什么运行失败了"，系统说明"这个需求属于调度运维诊断场景，我先路由到对应的数据工程子 Agent 处理"，随后由子 Agent 依次读取技能说明与文件（principle、诊断模式参考），并在第一次按工作流名查询失败后自行纠正参数口径重试。

## 第 3 步：数据治理 Agent 先管质量

原文的观点是"管线能够稳定产出数据，经营问题却不一定随之解决"：管理者问 **30 天复购率**，平台里可能只有客户、订单、商品明细；复购按客户还是按订单算、统计周期怎么划、哪些订单应计入，都需要清晰定义——"口径一旦含糊，查询执行得再快，分析结果仍可能对不上"。

所以在生成经营分析**之前**，先让数据治理 Agent 检查数仓质量：

- 通过**数据画像**识别唯一性、一致性问题
- 演示中推荐 **8 条质量监控规则**，并附相应 SQL 模板
- 用户确认后，规则被创建为**持续运行的监控任务**
- 出现异常时，Agent 沿**数据血缘**检查上下游影响，给出修复建议

原文的评价："治理工作由此跟进到数据日常运行中，而不必等报表出错才回头补查。"

截图中的质量诊断界面对应的产出包括任务完成回顾（数据探查、数据画像、业务规则梳理、质量任务创建、质量报告、问题清单等分项状态）与一份带注释的 SQL（步骤分区：规则去重、异常检测、抽样等），右侧为完整 SQL 编辑区。

## 第 4 步：三个指标 → 语义模型

演示人员提出建立 **30 天复购率、客单价、转化率** 三个指标，Agent 的动作是：

1. 从 **Catalog** 中查找已有事实表
2. 梳理**订单、客户、卖家**等实体的关联关系
3. 生成**指标定义、维度映射、业务说明、负责人信息**
4. 方案确认后**形成语义模型**
5. 后续生成看板或追问数字时，系统可以回到这些定义，查明指标所用的表、字段与计算方式

截图中的对话产出物是一段 **YAML 配置**（`version: 1.0`，`model.name: weshp_ecommerce_model`，`type: DEF`，`source:` 指向数仓表，`joins:` 列出关联）——即演示中语义模型的落地形态是可带版本号的配置文件，原文正文未对此形态作展开说明。

## 第 5 步：数据分析 Agent 出经营看板

有了治理过的数据与统一指标，报表终于能生成：

- 数据分析 Agent 从**订单、客户、商品、财务、满意度等领域共 45 个字段**中挑选所需内容
- 自行组织 **KPI、分析维度、图表**，形成一张 **9 张图表、7 种可视化类型**的零售运营看板，集中呈现收入、毛利、品类与渠道表现
- 看板可随新数据**定时刷新**
- 追问某个数字时，使用者可查看其**指标定义、来源字段、聚合维度、SQL**——省去反复向数据团队确认口径

截图中的看板实例叫"零售电商智能看板"，核心 KPI 为 GMV、订单量、客单价、复购率，配月度销售趋势（双轴柱线）、品类 GMV 占比（环形）、城市等级 GMV 对比、会员等级消费分析等图表；右侧"月度销售趋势"面板展开后正好是**指标口径 → 使用维度 → 数据来源 → 运行信息（耗时）→ SQL** 五段，对应正文所说的"可下钻到定义"。

## 第 6 步：从报表到模型服务（数据科学）

### 一条待验证的干预假设

复购偏低，发布会提出的**可能解释**是"部分客户完成首次购买后，没有发现更多符合兴趣的商品"。演示人员**没有直接把它认定为流失原因**，而是把推荐服务作为一项**待验证的干预**，计划通过后续转化率与复购率观察效果——数据工作由此从报表分析延伸到模型应用。

### 物品协同过滤推荐

| 阶段 | Agent 产出 |
|------|-----------|
| 资产注册 | 上传本地电商数据集，把商品、订单、客户及相关特征注册为 **Catalog 资产** |
| 代码生成 | 在 **Notebook** 中生成数据探索、交互记录处理、长尾过滤、物品相似度计算、Top-N 推荐代码 |
| 建模 | 构建**基于物品协同过滤**的推荐模型 |
| 训练 | 训练过程接入**实验追踪** |
| 治理 | 模型评估后**注册入库** |
| 上线 | 发布**在线特征表** → 部署**推理服务** → 通过 **API** 供业务系统调用 |
| 管理 | 模型**版本、运行环境、推理结果**纳入管理 |

原文对边界的表述很克制：推荐服务能带来多少复购改善，"仍需上线后的业务指标验证"；平台提供的是"把分析结果推进到可部署服务的工具链"。

## 贯穿全程的三类辅助动作

原文把这套演示归纳为几条贯穿性做法，可在同一页面上作为"如何衡量一个端到端 Data Agent 演示"的检查表：

1. **人工审批门控**：方案审核后才创建生产任务；故障修复要等用户批准；关键步骤保留人工审批——"自动化才更容易进入生产环境"
2. **专业工具保留**：Studio、Notebook 仍在，工程师把重复操作交给 Agent，把精力放在业务规则、方案审核、权限控制、结果验收
3. **结论可追溯**：看板数字可下钻到指标定义、来源字段、聚合维度与 SQL；模型有版本、运行环境与推理结果记录

## 边界与不确定项

- 演示为发布会现场设计，故障是**人为制造**的下游报错，不代表全量真实的脏数据场景。
- 原文未给出每一步的耗时、自动通过率、人工介入次数等量化过程指标；"5 至 10 倍效率提升""模型上线 30 天 → 7 天"是厂商整体口径，未绑定本演示（见 [[databuddy]] 的数据表）。
- 原文**未覆盖**数据研发的测试与发布环节（测试用例、上线审批、回滚演练），演示的交付物止于"方案审核 → 创建任务 → 运行"。
- 第 1 步截图中的界面区域文字较小，本页只引用可辨识的节点结构信息；无法确认的小字未作推断。
- 演示中的实体命名（如 `weshp_ecommerce_model`、表名前缀 `databuddy_showtime_donot_delete_customer360`）为演示环境命名，非通用约定。
