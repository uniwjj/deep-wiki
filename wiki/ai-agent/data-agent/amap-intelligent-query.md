# 高德智能问数：从 BI 底座到 Agent 底座

> 核心主张：「答得对」只是起点，「看得透」才是价值增量。用户要完成的是一段完整的数据工作——提问、取数、跟踪、解释、判断；产品必须从「检索后生成」的 RAG 路线，升级为「规划、执行、校验」的 CodeAgent 式 DataAgent 闭环，并用语义资产、评测体系与 Harness 三类护栏约束每一次任务结果。

> 演讲者：林宇航，高德商业智能部 · 数据产品高级专家
> 场合：DACon 2026 北京站「AI Ready 到 Agent Ready：Data+AI 平台架构升级」
> 时间：2026 年 10 月 24 日

## 背景与问题

### 用户要完成的，是一段完整的数据工作

演讲把用户的数据工作拆成五步链路：

| 步骤 | 用户动作 | 具体内容 |
|------|----------|----------|
| 01 | 提出问题 | 明确目标与范围 |
| 02 | 拿到数据 | 找到口径与结果 |
| 03 | 持续跟踪 | 观察变化与节奏 |
| 04 | 解释变化 | 拆维度、找证据 |
| 05 | 形成判断 | 交付可讨论结论 |

关键判断：**即时取数只是起点，工作要在判断与交付中完成**。一次数据工作往往经历多轮追问与修正，价值随链路向右递增。

### L0–L4：AI 承担的判断逐级增加

| 层级 | 形态 | 能力 | 行业位置 | 高德的服务与进展 |
|------|------|------|----------|------------------|
| L0 | 手动取数 | 写 SQL、导出 Excel、人工跑数 | 已淘汰 | — |
| L1 | 自助看数 | 报表看板、拖拽分析、自助 BI | 已成熟 | BI 看板与数据集（我们的起点） |
| L2 | 智能问数 | 自然语言问数、可靠取数、口径命中 | 当前主流 | 即时问数、报告撰写；100% 业务域覆盖 |
| L3 | 智能诊断 | 诊断归因、趋势预测、风险预警 | 前沿阵地 | 风险预警、钉钉推送归因诊断报告；W35 部分场景验证、9 月全域覆盖 |
| L4 | 自主决策 | Agent BI、处方性分析、自主执行 | 共同空白 | 经营大脑；场景验证中 |

贯穿逻辑：AI 承担的判断逐级增加，人从操作者转为把关者。页脚注明：行业分级在下，高德的服务与进展在上（截至 W35；L3 全域覆盖截至 2026 年 9 月）。

### 早期路线：RAG + NL2SQL + OLAP 引擎

在范围明确的阶段，优先复用已有 BI 资产。早期 L2 链路：

**BI 看板 / 数据集 → RAG → NL2SQL → OLAP 引擎 → 数据结果**

- BI 看板 / 数据集：资产起点
- RAG：补充报表、指标与业务知识
- NL2SQL：生成 SQL，查询数据
- OLAP 引擎：承接复杂指标与同环比计算
- 数据结果：回答用户问题

即「知识补全、查询生成与指标计算各自承担明确责任」。

### MVP 验证与规模化边界

明确范围内，MVP 验证了早期路线：

| 资产范围 | 阶段结果 |
|----------|----------|
| 39 张 ADS 表、15 张看板 | L2 回答成功率 89.4%、端到端准确率 90% |

但规模扩展暴露了路线边界（两组独立阶段快照，对应不同业务范围与评测批次）：

| 业务经营单元 | 表规模 | 端到端准确率 |
|--------------|--------|--------------|
| 业务经营单元 A | 331 张表 | 50% |
| 业务经营单元 B | 70 张表 | 80% |

结论：**单域 MVP 的成功，没有自然复制到更大范围。**

### 四类规模化瓶颈

阶段复盘识别出四类瓶颈，都指向「复杂问数：一次召回装不下，中途也补不进」：

1. **一次性召回**——复杂问题需要的知识难以在开场一次拿全
2. **多步链路**——实体、口径与约束在步骤间逐渐损失
3. **复杂跨表计算**——任务超出预设链路后，扩展成本上升
4. **逐 case 维护**——业务扩展持续增加规则与特殊处理

关键判断：复杂问数无法由单次任务完成。

### 路线选择：继续修补 RAG，还是重构为 Agent

| 继续修补 RAG 路线 | 基于 CodeAgent 架构的 DataAgent |
|-------------------|--------------------------------|
| 01 扩展召回与规则 | 01 拆解多步任务 |
| 02 复杂计算依赖预设能力 | 02 生成代码并执行 |
| 03 中间状态难以复用 | 03 保存并复用中间结果 |
| 04 新 case 持续增加维护 | 04 根据执行反馈继续调整 |

决策标准：多步任务、复杂计算、中间结果复用、执行反馈与规模化维护。

**从 RAG 到 Agent，换的不是一个更强的模型，而是技术路线：从「检索后生成」，到「规划、执行、校验」的闭环。**

## 方案/架构

### 新方案总览：执行闭环、知识供给与质量控制

分两步走：先换执行方式（执行闭环 + 知识供给），再补质量护栏（语义 · 评测 · Harness）。

整体分层：

- **业务触点与服务**（从一次回答到持续交付）：即时问数（问题进入，结果返回）、报告（按固定节奏交付）、告警（监测异常，主动触达）
- **Skill 与知识（KNOWLEDGE）**：按任务装入当前步骤需要的方法、口径和操作经验；含领域路由、步骤方法、例外处理
- **DataAgent 工作层（TASK LOOP）**：组织步骤、调用工具、管理任务状态；循环为规划 → 执行 → 检查 → 再规划
- **证据与过程（TRACE）**：让每一步都能回到来源与上下文；含数据来源、时间范围与口径、结构化中间结果、执行记录与修正；目标是过程可回看、结果可解释
- **业务语义层（SEMANTIC）**：统一指标、实体、关系和校验规则；口径一致、对象清晰、规则可用
- **数据与执行底座（DATA & RUNTIME）**：保留 BI 看板，并提供受治理的数据资产、查询计算和受控运行环境；稳定观察、数据集、查询工具、受控执行
- **质量与治理（HARNESS，贯穿每一层）**：权限与审计、Trace 追踪、Verify 验证、评测回归、人工纠偏

页脚状态：问数执行底座已覆盖全部业务域，归因诊断全域覆盖；L4 自主决策场景验证中。

### 执行闭环：基于 CodeAgent 架构的 DataAgent

把一次回答改造成可执行、可观察、可回环的任务循环，七个环节：

| 环节 | 动作 | 产出 |
|------|------|------|
| 01 | 业务问题 | 目标、范围与约束 |
| 02 | TODO 任务拆解 | 拆成可执行步骤 |
| 03 | 代码生成 | 写成计算逻辑 |
| 04 | 安全沙箱执行 | 受控环境运行 |
| 05 | DataFrame 流转 | 传递中间结果 |
| 06 | 检查与再规划 | 校验并决定修正 |
| 07 | 答案与证据 | 结论、口径与来源 |

回环条件：证据不足或检查未通过——修正 TODO / 代码后继续执行。「复杂任务被拆成可执行、可检查、可回到前序步骤修正的链路。」

### 知识供给：Skill 让知识按任务逐步展开

知识随着任务逐层展开，当前步骤只加载当前所需：

**统一入口 → 业务域路由 → 表级路由 → 按需加载 → 歧义处理 → 执行与解释**

- 统一入口：识别问题与目标
- 业务域路由：定位业务范围
- 表级路由：收敛候选数据
- 按需加载：表、指标与规则
- 歧义处理：扩展上下文或澄清
- 执行与解释：查询、检查与说明

核心公式：**Skill = 知识路由 + 程序性方法**。语义告诉 Agent 需要理解什么，Skill 告诉 Agent 去哪里找、按什么步骤做。示例是团队取数 Skill：定位业务域与数据表，补齐口径，生成并检查 SQL，执行后说明来源与范围。

## 关键工程做法

### 同一批数据表上复测：平滑迁移

| 范围 | 改造前 | 新路线阶段性准确率 |
|------|--------|--------------------|
| 业务经营单元 A（331 张表） | 50% | 93.6% |
| 业务经营单元 B（70 张表） | 80% | 96.7% |
| 整体 | — | 约 95%（问答准确率） |

5 月底架构升级：平滑迁移，整体用户未发生流失。页脚说明经营单元 A、B 与 P7 为同一业务范围前后对比。

### 代码运行成功，还要经过业务语义校验

代码执行解决计算正确，语义底座解决上下文正确，两侧共同产出「可验证答案」：

| 计算侧｜代码执行 | 上下文侧｜语义底座 |
|------------------|--------------------|
| 01 计算逻辑可运行 | 01 实体与角色选对 |
| 02 跨表步骤可复现 | 02 指标口径一致 |
| 03 中间结果可传递 | 03 时间、维度与证据匹配 |

页脚说明：「解决」指主要责任分工；最终结果共同经过上下文、计算与证据检查。

### 语义从知识片段变成生产资产

三阶段演进：

1. **早期供给**：元数据、业务知识、路由规则；零散知识进入任务
2. **文档 MVP**：约两个月运行；验证分级、生产、质检、准入与消费
3. **平台化**：8 月 31 日首版；连接知识库，承载版本与持续消费

期间「供给侧语义工程与智能问数产品并行推进」。平台化让语义具备来源、质量门槛、版本和消费方式。

### 质量控制：三类护栏

| 护栏 | 回答的问题 | 内容 |
|------|------------|------|
| 语义资产 | 理解什么 | 实体、指标、口径与业务规则 |
| 评测体系 | 怎么判断对错 | 看任务结果；扩域和改底座都靠它回归 |
| Agent+Skill Harness | 执行过程怎么控制 | 编排、权限、状态、重试、观测、降级与转人工 |

三条共同指向「可靠任务结果」。页脚特别说明：评测看的是整体——模型、语义资产、Skill 与运行系统共同工作的任务结果；Skill 属于 Agent 内部的知识路由层（见 P12），不单列为护栏。

### L2 持续服务：同一个问题，每次都算对

把问答固化成任务：问什么、用什么口径、怎么算，一次定义。三种交付方式背后是同一个数据任务：

| 交付方式 | 说明 |
|----------|------|
| 即时问数 | 用户临时提问，一次交付 |
| 报告 | 按主题、按周期定时交付 |
| 告警 | 条件触发（见 L3） |

任务固定下来的三项内容：

- **问什么**：对象、指标与判断标准
- **口径**：实体、时间范围、过滤条件
- **怎么算**：步骤、代码与中间结果

每次更新都要稳定算对：评测回归（改底座、扩业务域都重测）、Harness（状态保存、失败重试、异常降级）、每次交付都带上口径与来源。示例截图展示回答附带口径标注（已打码）。下一步：通过 MCP / Skill 把这些任务带进办公工作流（外部参考：千问办公）。

### L3 主动告警：指标越线，系统先找到人

一段话定义规则，系统每天盯数，命中条件就推送，并附上口径。两步：

1. 用一段话写清口径、阈值和接收人
2. 命中条件，钉钉机器人推送，并附上数据口径

截图均已脱敏，仅展示规则配置与推送形式。示例规则里可见：按活动 `act_id` 粒度逐个判断，量值/率值取 T-1 单日（不跨天求和），留存率有 T+7 延迟，从 T-1 往前回溯最近有效值（最多 14 天）；指标为 null 跳过不判定，零值正常参与；预警规则共 9 条，命中即报警；消息用 Markdown 格式，每条预警带活动名称、指标当前值、阈值，末尾附数据口径说明；按对接人归类，同一负责人负责的多条预警合并成一段。

### L3 归因诊断：从发现异常到解释原因

五步链路，每一步留下任务、数据与判断证据，用户可以回看和纠偏：

1. **问题拆解**——形成可验证子问题
2. **任务规划**——确定顺序与所需数据
3. **多步取证**——保留来源、范围与口径
4. **分析判断**——在证据范围内形成结论
5. **证据回溯**——回到数据与中间步骤

人工纠偏：把修正送回对应步骤，更新后续计划与判断。页脚原则：结论与证据强度匹配；高风险判断保留人工复核。

### L3 实践：一次经营分析的完整链路

同一套分析链路：生成前校验，过程中验证，证据不足就回退。

**三层报告，同一方法**：

| 报告 | 回答的问题 | 内容 |
|------|------------|------|
| 日报·快 | 昨天发生了什么？ | 现象描述 + 异常标记 |
| 周报·准 | 为什么偏离目标？ | 根因定位 + 维度拆解 |
| 月报·全 | 经营是否健康？ | 全面归因 + 行动建议 |

**五步分析链路**：

1. **看大盘**——环比、目标完成率、是否触发阈值
2. **拆结构**——沿主要业务维度交叉定位
3. **做归因**——规模效应 + 效率效应 = 总变动
4. **做验证**——关联指标：正向 / 负向 / 无联动 / 背离
5. **给结论**——现象 · 主因 · 验证 · 置信度高 / 中 / 低

校验规则：生成前做数据校验——子项加总 = 总量、跨维度对齐、指标合理区间、上下游层级、基数异常；生成后做输出扫描——按敏感表述与合规规则过滤，保证输出干净。校验失败或指标背离时退回「拆结构」；证据不足转成验证任务。

**归因规矩**：只用数据集内的维度，不从外部编原因；已知政策带来的变化，不做归因；基期过小，标注「受基数影响」。

**人工纠偏**：补充业务背景，排除已知例外；修正回到后续拆解与验证；证据不足时保留不确定性。

页脚说明该实践不含经营数值；方法是「报告（触点）+ Skill（方法）+ 业务语义层（口径）+ Harness（质量门）」。

## 经验与边界

演讲把三条复盘判断都归为「真实踩坑」：

### 单域成功 ≠ 规模化成功

- 判断：效果依赖知识边界；范围一变，原来的验证结论就要重来。
- 不注意会怎样：沿用小范围的成功经验，扩域后准确率明显下滑，规则和 case 越补越重。
- 应该怎么做：扩域前重新评测，按任务复杂度分层看结果。

### 计算正确 ≠ 业务理解正确

- 判断：SQL 能跑通，只证明计算可复现，不证明实体、口径和时间理解对了。
- 不注意会怎样：答案可执行、看起来合理，却答非所问，错误更难被发现。
- 应该怎么做：语义资产校准上下文，关键结论回到证据，Harness 管住执行。

### 独立入口 ≠ 高频工作入口

- 判断：用户用不用，取决于产品是否进入他已有的工作节奏。
- 不注意会怎样：用户偶尔来问一次，产品停在尝鲜阶段，难以成为日常工具。
- 应该怎么做：把能力做成报告、告警等持续服务，再进入办公工作流。

三条判断按不同成熟度落地，并继续用真实任务与阶段评测校验。

### 边界与下一程

- L2 已 100% 业务域覆盖；L3 全域覆盖（2026 年 9 月）；L4 仍处场景验证中。
- L4 方向：通过 MCP / Skill 进入办公工作流，在人工把关下辅助决策与执行；演讲明确「千问办公」仅作外部参考。
- 最终总结三条：从 RAG 到 Agent，换的不是更强的模型，而是技术路线；代码执行解决计算正确，语义底座解决上下文正确；Agent 让模型有了手脚，语义资产、评测体系和 Harness 决定它会不会走错路。
- 原话收束：「从答对一个数到看透一个问题，底座决定上限，我们仍在路上。」
