# 企业级可信问数：让 Data Agent 的每个回答都有据可查

> 核心主张：**查询成功只是起点**。企业级可信问数还要明确业务口径、授权范围、结果可追溯、并能持续维护。**"可信，不是人人得到同一个数，而是答案符合明确的业务口径与授权范围。"** 有据可查，才能核验；执行成功，不等于业务理解正确。

来源：DACon 2026 北京站演讲《让 Data Agent 的每个回答都有据可查：企业级可信问数的工程闭环》，演讲人李明皇（Datastrato 资深软件工程师、Apache Gravitino PMC Member）。

## 背景与问题

### 一个公开的 BIRD 问数案例

演讲用 BIRD #1493 贯穿全篇：

- 问题：**2012 年 2 月，消费超过 528.3 的客户占比是多少？**
- 英文原题：In February 2012, what percentage of customers consumed more than 528.3?
- BIRD evidence（原题附加提示）：February 2012 refers to '201202' in yearmonth.date；The first 4 strings of the Date values in the yearmonth table can represent year；The 5th and 6th string of the date can refer to month.
- 来源标注：BIRD #1493，公开 Text-to-SQL 评测基准。

### 基础问数链路

`业务问题 → 通用 Agent → MCP 数据工具 → 数据平台`

| 环节 | 构成 | 职责 |
|------|------|------|
| 业务问题 | 自然语言问题（含原题提示） | 输入 |
| 通用 Agent | LLM / Agent Runtime、问数 Skill（可选：查询步骤 / 检查规则 / 输出规范）、MCP Client、Memory / Reasoning | 理解问题、规划步骤、组织查询、整理答案 |
| MCP 数据工具 | MCP Server、Schema Explorer（表结构/字段/示例）、Query Execution（执行 SQL）、Metadata & Catalog（元数据/权限/审计） | 查看表结构、执行查询、返回结果 |
| 数据平台（示例） | Hive、Trino、Iceberg、MySQL、PostgreSQL、…… | 执行 SQL、返回结果 |

典型执行流程四步：

1. **了解数据**：发现相关表和字段、理解业务上下文；
2. **生成并检查 SQL**：基于 schema 和问数 Skill 生成 SQL，检查语法与逻辑，必要时修正；
3. **调用查询工具**：通过 MCP 调用工具执行，获取查询结果（必要时基于错误修正）；
4. **整理回答**：将结果转为用户可理解的自然语言回答，补充关键数据与说明。

原文随即抛出问题：**查询成功，是否就满足企业使用要求？**

### 企业级可信问数的四个问题

| 问题 | 内涵 | 具体要求 |
|------|------|---------|
| ① 统计谁？ | 业务口径要明确 | 同一个问题，不同的口径会得到不同的结果 |
| ② 谁在查？ | 授权范围要落实 | 同一份定义，不同用户看到的结果可能不同，但都可以正确 |
| ③ 如何核对？ | 结果需要可追溯 | 这个占比的分子、分母分别是多少？依据的是哪份已确认的业务定义？能否找到实际使用的 SQL、数据范围和计算结果？ |
| ④ 怎么维护？ | 口径与权限变化后如何生效 | 业务口径调整后，哪些报表和使用方需要更新？用户授权范围变化后，如何确认新权限已在查询中生效并完成回归验证？ |

口径示例：口径 A「当月消费客户中的占比」——分子为当月消费超过 528.3 的客户数，分母为当月有消费的客户数；口径 B「全部客户中的占比」——分子同上，分母为截至当月的全部客户数（包含当月未消费的客户）。

授权示例：华东区域经理只能查看华东区域客户，按相同口径得到华东占比；华南区域经理得到华南占比；总部人员可查看全国客户，得到全国占比。

## 方案/架构

整体方案由四块构成：**语义与治理（Gravitino Semantic Model）→ 可信执行与结果证据（Data Agent）→ 构建、审核与维护（Semantic Generator）→ 评测与业务共建**。

### Apache Gravitino：统一元数据管理

定位：连接多源数据资产，提供统一的元数据模型、接口与治理能力。

| 层次 | 内容 |
|------|------|
| 使用方 | Data Agent（问数应用 / 智能助手）、BI / 分析应用（数据分析 / 数据产品） |
| 查询与处理引擎 | Spark、Trino、Flink、Daft |
| 元数据访问与管理 | REST API、Iceberg REST、Lance REST、MCP Server、Java / Python SDK |
| 平台能力 | 多源接入（目录联邦、连接器、跨系统元数据访问）；统一管理（统一对象模型与接口、表/分区统计、血缘事件集成）；统一治理（所有者、角色与授权、标签、策略关联、元数据审计） |
| 对象模型 | Metalake → Catalog → Schema → Table / View / Function / Fileset / ML Model / Topic / SemanticModel |
| 数据来源 | 湖仓与表格式：Hive、Iceberg、Paimon、Hudi、Lance、AWS Glue、Delta Lake；关系型与分析数据库：MySQL、PostgreSQL、ClickHouse、Doris、StarRocks；文件与对象存储：HDFS、Amazon S3、GCS、ADLS、阿里云 OSS、腾讯云 COS；消息队列：Apache Kafka |

带来的价值：减少重复适配（应用共享统一元数据入口）、统一管理入口（一致的对象模型与访问方式）、支撑可信问数（为语义定义、权限管理和审计提供基础）。

原文过渡问题：**在统一元数据管理的基础上，如何进一步管理业务语义？**

### Gravitino Semantic Model：以 Ossie 兼容结构表达业务语义

Semantic Model 包含五类内容：**Datasets / Fields、Relationships、Metrics、AI Context、Custom Extensions**；治理复用 Gravitino 的统一治理机制：所有者 Owner、版本与变更 Version、标签 Tag、授权 Policy / RBAC、审计 Audit。

以 `customer_spend` 为例（P7）：

- **数据集与维度**：`yearmonth` 为客户 × 月份，主键 Date + CustomerID；字段 CustomerID（Integer，客户唯一标识）、Date（String，统计月份 YYYYMM，时间维度）、Consumption（Float，客户月度消费金额）。
- **指标 1：客户月记录数** `customer_month_count`，计算表达式 `COUNT(yearmonth.CustomerID)`，业务含义"每个客户每月计一次，不同月份分别计数"；AI Context：使用说明"用于客户月记录规模，按月统计时表示该月有记录的客户数"、同义词"客户月记录数、客户月数"、示例"各月份分别有多少客户记录？"。
- **指标 2：独立客户数** `distinct_customer_count`，计算表达式 `COUNT(DISTINCT yearmonth.CustomerID)`，业务含义"所选范围内有记录的客户，同一客户只计一次"；AI Context：使用说明"用于单月或跨月的独立客户规模，期间去重数不能由各月去重数直接相加"、同义词"独立客户数、去重客户数"、示例"这个季度有记录的独立客户有多少？"。
- **Relationships**：`yearmonth.CustomerID → customers.CustomerID`（多对一）。
- **Custom Extensions**：`vendor_name + data`，厂商特定扩展信息（结构说明）。

设计要点：语义不是只有计算公式，还带**业务含义、使用说明、同义词、示例**——这些正是供 Agent 选择与解释的上下文。

### 从自然语言到可执行 SQL：职责分工

| 角色 | 做什么 | 由谁保证 |
|------|--------|---------|
| Data Agent | 理解问题与发现语义；选择指标、维度与过滤条件；形成结构化查询请求 | LLM：语义选择与任务规划 |
| Semantic Compiler | 校验请求与模型成员引用；依据语义定义组织计算与关联；生成引擎可执行 SQL | 程序：确定性编译 |
| Query Engine | 执行查询与计算；返回数据与执行状态；保留查询记录 | 引擎：数据计算 |

链路：用户问题 → Data Agent（结构化请求）→ Semantic Compiler（SQL）→ Query Engine → 查询结果返回 Agent。

BIRD 示例的两段结构化请求（P8）：

- **分子（同月且满足金额条件）**：filters.logic = all；`Date = "201202"`；`Consumption > 528.3`；measures = `customer_month_count`。
- **分母（同月客户范围）**：filters.logic = all；`Date = "201202"`；measures = `customer_month_count`。

两次查询返回计数 → Python 计算「分子 ÷ 分母 × 100」→ Agent 组织答案。

链路观测与执行记录覆盖：工具调用、请求参数、实际 SQL、结果引用、耗时与错误。

### Data Agent 的流程编排：在约束中保留探索能力

**① 业务域上下文**：数据资产与语义模型（可用数据表、语义关系与计算逻辑）、业务术语与指标口径（业务定义、口径规则与指标体系）、分析范围与可访问资源（可分析的业务域、数据范围与工具资源）；限定候选范围、按需加载定义。

**② 分层识别与流程路由**：

- 能力范围识别：判断问题是否在业务域与能力范围内；超出则给语义解释、产品帮助与闲聊、超出职责提示；
- 问数分析：在业务范围内的分析问题；
- 分析任务识别：将问题拆解为可执行的分析任务——指标取数、对比与拆解、诊断与探索；复杂问题可组合多个任务；
- 执行策略选择：基于任务类型、上下文与资源选择——**已验证回答**（匹配 → 确认与填参 → 既定流程）、**即时分析**（组织查询 → 编译与计算）、**探索式分析**（动态选择下一步）。

**③ 受约束的探索**：选择下一步（基于当前问题、上下文与证据）→ 执行分析步骤（调用工具、生成并执行查询）→ 更新证据与状态（收集结果、记录推理与中间结论）→ 继续 / 结束 → 输出已有发现（给出可解释的结论与依据）。

配套约束：工具按任务提供，继承业务范围；执行使用语义口径与程序计算；收敛依据证据、预算与停止条件。原文强调：**业务域不替代权限校验；权限约束贯穿发现与执行。** 原则是"让 LLM 决定分析方向，让程序保证执行，让证据支撑结论"。

### 把约束落到工具与执行流程

| 约束 | 示例 | 机制 |
|------|------|------|
| ① 明确操作与输入 | 月度去重计数 → 季度独立客户数：计数不能直接相加，需回源重算 | 工具契约 + 语义校验：区分指标查询、结果转换、派生计算；使用结果引用，保留来源与分组粒度；依据指标定义校验聚合与关联 |
| ② 显式维护分析状态 | 二月消费占比 → 再看三月：同步更新分子、分母及派生结果 | 结构化上下文 + 依赖管理：保存指标、时间、过滤条件与结果引用；LLM 提出变更，程序更新任务状态；标记受影响结果失效，沿依赖补算 |
| ③ 控制执行与回退 | "语义不支持" ≠ "执行超时"，不同错误进入不同处理路径 | 工具网关 + 错误分流：执行超时 → 限次重试或优化；语义不支持 → 调整分析或澄清；权限拒绝 → 停止越权执行；SQL / Python 权限、隔离与资源限制 |

两条边界判断：**模型提出请求，程序检查合法性**；**安全执行不等于业务计算正确**。

### 让答案关联到实际工具调用（证据链）

BIRD #1493 的最终答案：2012 年 2 月，在当月有月度记录的客户中，月度消费金额超过 528.3 的客户约占 **66.62%**。

三层证据（P11）：

| 层 | 输入 | 输出 / 依据 |
|----|------|------------|
| ① 语义定义读取 | 模型 `yearmonth`；指标 `customer_month_count` | 粒度：每客户、每月一条记录；金额：客户月度消费金额；计数：`COUNT(CustomerID)`；单月主键唯一，对应当月有记录的客户 |
| ② 查询调用 | 分子：`Date='201202'`、`Consumption > 528.3`；分母：`Date='201202'` | 分子 R1 = 12,208；分母 R2 = 18,324；两次查询均使用 `customer_month_count` |
| ③ 计算调用 | 结果引用 A ← R1、B ← R2，计算 A ÷ B | 输出 0.66623008…，百分比展示 66.62%；计算结果同样是工具输出 |

关联记录包含：语义定义版本、查询参数与 SQL、结果引用、调用依赖。原文结论：**有据可查，才能核验；执行成功，不等于业务理解正确。**

### 从一次可信回答到更多业务场景

| 场景变化 | 用户问法 | 处理 | 结果 |
|---------|---------|------|------|
| ① 换个时间与维度 | "把二月改成三月，再按客户类型拆一下" | 已有定义可复用：使用已支持的指标与维度，调整参数，沿用同一业务口径 | 不必重新解释计算逻辑 |
| ② 换一个业务问题 | "我们业务里的授信客户占比，也能直接问吗？" | 尚未覆盖，需要补充定义：定位业务口径与数据关系，构建并审核缺失的语义定义 | 数据接入之后，还要理解业务 |
| ③ 业务口径发生变化 | "口径已经改了，下个月还能放心问吗？" | 定义变化，需要维护：更新定义，定位受影响的分析，回归检查，明确新口径适用范围 | 不必每次提醒系统口径已变 |

由此提出核心问题：**如何让更多问题进入可信执行路径，而不是每扩一个场景都重新手工建模？**

## 关键工程做法

### Semantic Generator：LLM 与确定性程序协同建模

流水线（P13）：

```
多源业务材料 → 确定性处理 → LLM 语义推断 → 程序校验与反馈 → 人工审核 → 已发布语义资产
```

| 环节 | 做什么 |
|------|--------|
| 多源业务材料 | Schema 与字段说明、历史 SQL 与报表定义、业务文档、已有语义模型 |
| 确定性处理 | 解析材料，提取计算事实；组织对象引用与来源证据 |
| LLM 语义推断 | 归纳业务含义、对齐对象；提出候选定义与待确认项 |
| 程序校验与反馈 | 检查结构、引用与定义；保留冲突和未决项；支持受限修复回环 |
| 人工审核 | 确认业务口径、处理冲突、批准合格候选 |
| 已发布语义资产 | Gravitino Semantic Model（指标、维度、关系、AI Context），供 Semantic Compiler 与 Data Agent 消费 |

持续维护：元数据变更事件（Gravitino Event Listener）/ 业务反馈 → 影响定位（分析影响范围）→ 候选更新（生成并调整语义候选）→ 审核发布（人工审核并发布）。

原则：**程序提取事实，LLM 归纳语义，校验与审核控制发布。**

### 从多源材料到可复用的业务定义

以 BIRD #1493 的材料为例：

- **输入材料**：表结构（yearmonth：CustomerID、Date、Consumption，PRIMARY KEY (Date, CustomerID)）；查询片段（`COUNT(CustomerID) WHERE Date = '201202'`，注明"查询片段，非完整 SQL"）；问题与说明（2012 年 2 月，消费金额超过 528.3 的客户占比；Date 使用 YYYYMM 表示月份）。
- **确定性事实抽取**：表与字段引用、复合主键与计数表达式、查询中的时间和金额条件。
- **LLM 业务语义对齐**：把计数解释为"客户月记录数"；关联时间、金额与业务概念；形成名称、说明和待确认项。
- **可复用候选**：指标 `customer_month_count = COUNT(CustomerID)`；维度 CustomerID（客户标识）、Date（月份，YYYYMM）；字段语义 Consumption（客户月度消费金额）；候选保留来源，进入校验与审核。

区分两类信息：**沉淀为语义**（计数定义、客户月粒度、字段业务含义）vs **留在查询中**（月份 201202、金额阈值 528.3）。原则：**复用业务定义，不把单次问法固化成指标。**

### 大批量材料如何拆分、恢复与核对

| 步骤 | 做法 |
|------|------|
| 01 去重与引用 | SQL 规范化生成 `sql_ref`；相同查询合并来源证据 |
| 02 按证据分任务 | 表与字段（结构和局部说明）、指标（SQL 观测 / 报表需求）、关系（有观测信号的表对）；文档全文不在每张表重复广播 |
| 03 按预算递归拆分 | 预算包含 System Prompt 与 JSON Schema；超限继续拆分，保留输出预算；原子任务仍超限则明确失败 |
| 04 恢复与汇总 | 兼容的检查点复用；失败任务继续执行；核对计划叶子与完成集合 |

检查点复用，先核对请求指纹：输入内容、任务类型、模型、Prompt 版本、输出 Schema、预算策略。边界：核对缺失、重复与意外结果；**覆盖完整不等于语义正确**。

### 候选不完整或有冲突：受限修复

`结构化候选 → 程序反馈 → 受限修复 → 候选与未决项`

- 结构化候选示例：candidate_index = 2；expression = `COUNT(CustomerNo)`；source_model = yearmonth；标记"字段引用待校验"。
- 程序反馈：CustomerNo 不在可用字段中；可用字段 CustomerID；允许修复候选 2；有效候选保持不变。
- 受限修复：只修改指定项或补缺失项；修复后重新校验。
- 候选与未决项：通过检查的进入审核；仍缺口径的保留 `definition_gaps`，需要补充依据或业务确认。

原则：**指标生成支持一次有界修复，未解决问题不靠反复猜测填满**；让模型修复明确的问题，让缺口保持可见。

对象归并时按字段限定修改权限：`description`、`label` 可综合表达（基于来源归纳业务含义）；`expression`、`unit` 保持计算定义整体（从已有候选中选择，实质分歧留待审）。边界提醒：引用真实存在，仍需判断是否足以支持业务结论。

### 带着字段依据完成审核

审核界面把"重新读材料、逐项编写"转成"对具体建议和差异的核对"（P17）：

- 对象 `customer_month_count`，字段「计算定义」当前值 `COUNT(CustomerID)`，建议值相同 → 保持原定义；
- 字段「说明」当前值"客户数"，建议值"按客户月记录计数；单月每客户一条记录" → 查看依据 / 采用建议；
- 字段「适用范围」待补充 → 建议"单月查询对应当月有记录的客户；跨月需区分记录数与去重客户数"。

字段依据面板：来源对象 yearmonth；结构化位置 主键与字段定义 `PRIMARY KEY (Date, CustomerID)`；查询依据 `COUNT(CustomerID)`；建议理由——复合主键约束客户月唯一性，跨月计数不等于去重客户数；待确认——业务需要记录数，还是跨月去重客户数？

流程：查看依据 → 采用或修改 → 重新校验（检查受影响的定义与冲突）→ 批准发布。无变化保留比较记录；实质差异和证据缺口进入审核。原则：**建议可追溯，修改可核对，批准与发布有明确边界**；保存与批准分开。

### 变更后如何维护并确认生效

变更驱动的维护设计：

```
元数据变更事件（Gravitino Event Listener）/ 业务反馈
  → 影响定位（表、字段及关联定义）
  → 与基线比较（无变化 / 更新 / 冲突；当前定义来自已有资产快照）
  → 生成变更候选（保留差异与来源）
  → 校验与人工审核
```

分阶段发布与消费核对：准备发布 → 发布生效 → 同步更新索引 → 读回核对；失败记录阶段，按状态重试。原文强调：**发布完成后，还要确认消费端读到了正确版本**；读回一致性不替代问数结果回归。

### 业务共识是可信问数的起点

围绕"客户数是多少？"三种统计范围：全量客户（客户主数据中的唯一客户）、当月客户（当月有记录的唯一客户）、跨月客户（指定期间内去重后的客户）。原文判断：同一个词，可能对应不同的统计范围。

技术与业务共同确认的四项：对象与粒度（统计对象、粒度层级）、时间与范围（统计周期、时间范围）、权威依据（数据来源、表与字段）、正确答案与待确认项（期望结果、需澄清的问题）。确认产出两件资产：**语义定义**（指标、维度、口径说明）与**评测约定**（预期结果、等价表达、澄清条件）。原则：**业务口径形成共识，生成与问数才有可验收的标准。**

### 语义层如何复用已有数仓

按业务口径与数据粒度选来源，保留已有数仓的分层价值（P20）：

| 数仓层 | 适用 | 接入方式 |
|--------|------|---------|
| ODS 原始来源 | 追溯与核对 | 按需治理后接入 |
| DWD + DIM 明细事实与一致维度 | 灵活分析与下钻 | 直接作为语义模型来源 |
| DWS 汇总结果 | 兼容口径下复用计算 | 直接作为语义模型来源 |
| ADS 场景报表 | 限定场景直接使用 | 直接作为语义模型来源 |

统一汇入"按场景选择来源"的漏斗，产出面向业务的语义模型：指标口径、可用维度、合法关联、适用范围 → Data Agent。

销售额示例：昨天各门店销售额 → DWS 门店日汇总（复用已确认的汇总口径）；按商品类别拆分销售额 → DWD 订单商品明细 + DIM 商品维度（汇总未保留商品维度时使用）；经营日报里的销售额 → ADS 经营日报（沿用报表已确认的统计范围）。原则：**已有汇总覆盖需求时直接复用，缺少分析维度时补充明细模型。**

### 最终回答的评测与重复运行验证

流程：问题输入（业务问题与必要上下文）→ Agent 最终回答（面向用户的最终自然语言）→ 结构化抽取 AnswerStructurer（只提取回答中已有信息，不接收标准答案）→ 程序匹配（与 canonical 及已审核的答案变体匹配）。

等价答案示例：2013 年 SME 客户消费最高的月份——`04`、`April`、`201304` 是同一问题下经确认的等价答案表示；抽取字段 `peak_month`。

评测资产持续维护：发现正确表达被误判 → 人工核验后补充答案变体 → 固定版本后重新评测。

同一问题 × N 次独立运行，同时看两个指标：**正确性**（最终结果是否匹配）与**稳定性**（多次运行是否持续答对）；评测时固定数据、语义模型、LLM 配置与评测约定。原文定位：业务验收看最终回答，过程记录帮助定位错误。

### 正确回答与必要澄清

回答决策矩阵（P22）：

|  | 直接作答 | 发起澄清 |
|--|---------|---------|
| **信息足以作答** | ✅ 正确回答（结果仍需通过校验） | ⚠️ 多余追问（增加用户负担） |
| **缺少作答必需信息** | ❌ 无依据断言（猜测缺失口径） | ✅ 有效澄清（问到决定答案的缺口） |

澄清也需要验收标准：用户问"这个月客户数是多少？"，有效追问是"指全量客户，还是当月有记录的客户？"；验收要明确"本题是否需要澄清"与"补充信息后能否继续完成回答"。原则：**正确回答与有效澄清分别评估，不能只看回答率。**

### 业务共建与持续迭代

- **共同维护**：业务方（真实问题、权威口径、验收反馈）+ 技术方（语义建模、执行链路、问题定位）→ 问题集、语义定义、评测集。
- **推进节奏**：小范围试点（一个业务域，明确支持范围）→ 共同验收（正确回答与必要澄清）→ 逐步扩展（回归通过后增加覆盖）。
- **问题处理闭环**：记录问题 → 定位原因 → 修订定义或实现 → 回归验证 → 用户反馈回到问题集与评测集。
- **业务侧两种体验**：信任积累——边界清楚、修复可验证；信任消耗——承诺过大、同类错误反复。

原文收束：技术与业务持续协同，才能把一次演示变成长期可用。

## 经验与边界

### 可信问数的工程闭环

1. **语义与治理**：Gravitino 统一元数据 + Semantic Model（Ossie 兼容结构）+ 权限/RBAC/审计；
2. **可信执行**：Data Agent 分层识别与流程路由、受约束探索、工具契约与状态管理、错误分流；
3. **结果证据**：答案关联语义定义、查询调用、计算调用，形成可追溯链路；
4. **构建与维护**：Semantic Generator 的确定性处理 + LLM 语义推断 + 程序校验 + 人工审核；变更驱动维护与发布读回；
5. **评测**：最终回答评测（等价答案、正确性、稳定性）+ 澄清评测 + 业务共建问题集；
6. **组织前提**：业务共识（对象、粒度、时间范围、权威依据）先于建模。

### 原文反复强调的边界

- **执行成功 ≠ 业务理解正确**：SQL 跑通不代表口径选对。
- **安全执行 ≠ 业务计算正确**：权限拦截只保证不越权，不保证算法正确。
- **覆盖完整 ≠ 语义正确**：任务都跑完，语义仍可能错。
- **读回一致 ≠ 结果回归**：消费端读到新版本，不代表问数结果正确。
- **引用真实存在 ≠ 足以支持结论**：字段存在不等于能支撑业务判断。
- **Context 与语义永远需要人来确认**：LLM 只产出候选与预览，发布权在人。

- 原文未披露 Semantic Generator 的模型选型、抽取准确率、人工审核工作量。
