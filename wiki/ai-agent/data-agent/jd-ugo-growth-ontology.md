# 京东零售 UGO：用户增长本体论

> **核心主张：** 用户增长决策的难点不在模型能力，而在要素、策略、归因与经验之间的协作断裂。UGO 把增长对象、操作规则和验证依据组织成同一份可查询、可计算、可授权、可行动、可追溯、可学习的语义，让报表、指标、知识图谱与操作语义层围绕同一次决策协作；AI 只生成候选，人工确认、服务端授权校验后才执行，效果由实验验证后再决定是否复用。

## 背景与问题

### 团队定位

演讲者周默（京东技术总监）来自京东零售用户运营技术团队。团队定位围绕四个词展开：

- **组织**：业务与产研闭环协作
- **平台**：承接大盘用户运营任务
- **连接**：衔接既有系统及商家
- **策略**：服务增长决策及执行

其平台形态是 **UMC OS**，包含工作面、知识面、智能体面三个面。

### 增长决策的四大断裂

原文把一线运营中的协作断点归纳为四类：

| 断裂 | 原文描述 |
|------|---------|
| **要素断裂** | 数据、用户、场景等关键要素割裂，难以形成完整的决策基础 |
| **策略断裂** | 目标与策略脱节，策略无法有效承接业务目标与用户需求 |
| **归因断裂** | 归因链路不完整，因果关系模糊，导致决策依据不可靠 |
| **经验断裂** | 经验无法沉淀复用，知识断层，难以支撑持续优化与创新 |

四者对应"数据—逻辑—行动—回流"的循环：要素断裂在数据侧，策略断裂在逻辑侧，归因断裂在行动侧，经验断裂在回流侧。原文的图以断裂符号标在循环的四个连接点上。

### 一次召回任务：流程完成，增量仍待验证

一个典型的召回任务包含四步：**圈人 → 发券 → 触达 → 看报表**。流程本身可以走完，但每一步都留下问题：

- 圈人：给谁？
- 发券：怎么做？
- 触达/报表：怎么判断？
- 最终追问：到底是什么带来了增量？

原文的判断是：运营流程完成不等于增长效果被验证。

### 多平台协作需要一致的决策上下文

一次增长动作要跨 **CDP/DMP、供给中台、营销中台、触达平台、素材库、A/B 平台、BI** 七个平台。原文要求跨平台先对齐五件事：**给谁、发什么、何时触达、谁确认、如何验证**。缺少一致的决策上下文，平台各自配置与执行，无法拼出同一次决策的全貌。

### 增长智能化的三个常见误区

| 大家以为 | 原文的真相 |
|---------|-----------|
| 有了大模型 = 智能化 | 模型只是能力之一，不是智能本身；智能来自目标、数据、知识、工具与闭环的协同 |
| 能对话 = 能解决问题 | 对话是交互，不是结果；解决问题需要业务目标、上下文、数据验证与行动闭环 |
| 部署上线 = 智能落地 | 上线只是开始，持续迭代才是关键；智能需要在真实场景中持续学习、评估与优化 |

## 方案/架构

### UGO 的定义与定位

**UGO（User Growth Ontology，用户增长本体论）** 被定义为"面向用户增长的操作语义框架"，把增长对象、操作规则和验证依据组织起来，让各环节围绕同一份决策协作。

它强调六种能力：

- 可查询
- 可计算
- 可授权
- 可行动
- 可追溯
- 可学习

在技术栈演进上，原文把 UGO 放在一条递进链条的末端：

```
报表 → 指标层（Lookup） → 知识图谱（Reasoning） → 操作语义层（Action）
结果呈现   统一口径            关系推理                闭环探索
```

即从"看结果"到"统一口径"，再到"关系推理"，最后到"可闭环探索的操作语义"。

### 本体论的演进脉络

原文用一条时间线说明"操作本体"的来源：

- **哲学起源**：研究存在与分类
- **1993 · 知识工程**：显式描述概念与关系
- **2004 · 语义网**：OWL 成为 W3C 推荐标准
- **操作本体**：对象 + 逻辑 + 受控行动

并引用 Palantir 的三代产品作为工程参照：**Gotham**（政府与国防分析）→ **Foundry**（企业数据与运营）→ **AIP**（AI 接入业务流程）。其共同公式是：Ontology 用对象与关系统一语义，用受控动作连接业务系统。

### 三层语义职责、七类业务要素、五层工程架构

原文用一句话区分三个视角：**三层是语义职责；七要素是业务组合；五层架构是工程承载。**

三层语义职责：

| 层 | 内容 | 回答的问题 |
|----|------|-----------|
| **时间层** | Scenario（场景）/ Lineage（血缘）/ 历史版本；记录当时场景、分组、版本、动作与结果 | 当时依据什么？ |
| **动词层** | Function / Strategy / Action；计算函数 → 策略对象 → 受控动作 | 允许做什么？ |
| **名词层** | Object（对象）/ Property（属性）/ Link（关系）；统一身份、属性与关系，七类要素按需建模 | 业务里有什么？ |

七类业务要素（围绕"人群"组织）：

1. 人群
2. 商品供给
3. 权益
4. 触点
5. 素材创意
6. 时机
7. 空间位置

图中标注的关系包括：权益与商品供给之间"适配"、人群对商品供给的"偏好"、人群对触点的"承载"。

**判断建 Object 还是 Property 的五问**：

1. 能否被业务独立识别？
2. 能否有自己的生命周期？
3. 能否与其他对象发生关系？
4. 是否需独立动作或权限审计？
5. 是否需要跨场景独立复用？

### UGO 的边界：连接而非替代

原文没有给出"UGO 不是什么"的清单，而是用相邻概念逐项对照来界定边界：

| 相邻概念 | 它解决什么 | UGO 的不同 |
|---------|-----------|-----------|
| 用户画像/标签 | 描述身份、属性与状态，支撑圈选与分群 | 关联目标、状态与场景，为策略选择提供统一业务语义 |
| CDP/DMP | 打通并管理数据，统一 ID，沉淀数据资产支撑激活与触达 | 补"语义与关系"，定义用户增长本体与关系，让数据可理解、可推理、可复用 |
| 营销权益中台 | 管理权益/活动/预算，完成配置与发放，支撑营销执行 | 基于对象与约束组合候选权益策略，由实验验证效果 |
| A/B 实验平台 | 验证"做什么更好"，评估策略/文案/触达等方案的因果效果 | 连接策略、分组与结果；用实验或有明确假设的因果分析验证增量 |
| 指标/BI | 汇总与可视化结果，监控业务表现，支撑报表与分析 | 关联指标口径、决策与执行记录，让分析结果进入可追溯的策略闭环 |

因此 UGO 的定位是**共同语义之上的平台分工与协作**，不是再建一个圈人、发券或报表系统。

### 目标闭环

原文给出六段闭环：**机会洞察 → 策略生成 → A/B 实验 → 实验评估 → 血缘沉淀 → 审核复用**，并归纳为三条原则：

- **统一对象**：让目标、策略、实验与结果能够相互核对
- **受控执行**：AI 提出候选；人工确认、服务端授权校验后再执行
- **验证复用**：通过实验评估效果，保留适用条件与证据，再考虑复用

### 五层目标架构：读、算、写、学

| 层 | 工程分工 | 主要内容 |
|----|---------|---------|
| **应用层** | 业务场景落地与价值闭环 | 用户增长看板、人群运营、营销触达、商品运营、效果度量 |
| **决策进化层** | 学习反馈驱动策略进化 | 效果归因、模型训练、策略评估、强化学习、持续进化 |
| **策略编排层** | 策略生成与执行编排 | 策略生成、规则编排、任务调度、风险控制、策略监控 |
| **要素本体层** | 增长要素统一定义与关联 | 用户本体（身份/属性/行为）、商品本体（类目/属性/关系）、内容本体（主题/标签/向量）、渠道本体（触点/媒体/路径）、活动本体（目标/规则/奖励） |
| **数据接入层** | 多源数据接入与治理 | 业务数据（订单/交易/行为）、埋点数据（App/小程序/H5）、日志数据（服务/应用/系统）、外部数据（三方/公域/行业）、实时流数据（消息/事件/监控） |

右侧用四个动作串起闭环：**读**（数据读取、洞察现状）→ **算**（计算决策、生成策略）→ **写**（策略执行、影响业务）→ **学**（效果反馈、进化提升）。

### 名词层：先统一身份

对象的基本单元是 Object，配合 Property（键值对描述的属性与动态状态）和 Link（对象间关联，构成结构化网络）。身份统一通过 **OneID**：按规则关联多端身份，保留置信度与冲突；不确定时不强行合并。

原文举了"同一用户的四套 ID"：App 端 ID、小程序 ID、PC 端 ID、线下会员 ID，经"按规则关联"汇聚成统一对象标识，再挂载属性（基础属性、状态属性、业务属性）、关系（家庭关系、社交关系、业务关系）和可发生的动作（触达、服务、发券）。

对象结构示意（原文标注"非完整"）：

```
ObjectType User{
    identity: OneID;
    properties;
    links;
    actions;
    governance
}
```

### 对象关系示例：同一策略串起召回全流程

原文强调"策略不是孤立的一段文字，它引用业务对象，并连接审批、执行与实验"。以 `STR-RECALL-001 v1.0` 为例：

- **人群快照**：某类目近 30 天未支付购买、近期有浏览或加购 → 被策略"引用"
- **策略 v1.0**：引用人群、权益与时机
- **审批记录**：确认版本、范围与额度；关键变更须重新审批 → "批准"策略
- **触达动作**：服务端校验后执行，保存状态与业务回执 → 受策略"约束执行"
- **权益对象**：适用类目、有效期，执行前重查是否可用 → 被策略"引用"
- **实验与结果**：`EXP-RECALL-001` 关联分组、指标与结果 → 与触达动作"关联"

### 动词层：计算、绑定、受控执行

| 阶段 | 职责 | 原文要点 |
|------|------|---------|
| **Function｜计算候选** | 计算人群、评分与时机，返回候选结果及来源版本 | 不创建投放任务、不发券、不触达；只读业务状态；保存计算证据 ≠ 改业务；数据/模型/参数可追溯 |
| **Strategy｜绑定版本** | `STR-RECALL-001 · v1.0`，目标为 7 日该类目支付召回，关联 `EXP-RECALL-001` | 候选人群 → 发布人群快照；快照、参数、额度、期限共同绑定审批版本；关键变更重新审批 |
| **Action｜受控执行** | 服务端授权与执行前校验，占用预算/频控额度，调用既有发券、触达系统，接收回执并更新动作状态 | 已受理 ≠ 业务成功；部分失败先查状态再重试；跨系统按业务补偿 |

### 策略对象与服务端控制

Strategy 是"被审批的业务对象"，其契约包含：目标（分组后 7 日该类目支付召回率）、要素（人群快照、供给、权益、触点）、触发（时间/事件/条件）、动作（业务调用及回执规则）、护栏（预算、频控、成本与体验）、治理（ID、版本、状态）、Owner（责任人）。

服务端控制强调"审批不是权限的替代"，包含四条：

1. **授权**：调用者、对象/字段、具体动作
2. **绑定**：策略版本、快照、参数、额度、期限
3. **重查**：有效性、预算与频控；关键变更重审
4. **幂等**：同键同参 → 返回既有状态/结果；同键异参 → 拒绝；处理中/超时 → 先查状态；失败按业务补偿，不承诺跨系统原子回滚

状态机：**待确认 → 已批准 → 执行中 → 成功 / 部分失败 / 失败 / 结果待查**。

### 时间层：固定比较条件

原文对实验设计给出明确约束：

- 场景：固定问题、对象与观察窗
- 实验：先分流，后比较；"不是 Git 分支"
- 血缘：记录当时证据、版本与动作
- 回看：重建已记录状态，不重演反事实
- 先检查分流、样本与体验护栏；结果不足时保留不确定性

主案例 `EXP-RECALL-001`（原文标注为示例）：策略 `STR-RECALL-001 · v1.0`；人群为某类目购沉默老客并冻结同一快照；用户级 1:1 随机，每组 10,000 人；对照组为既有 Push 时机，实验组为候选时机；供给、权益、文案与渠道保持一致；主指标为分组后 7 日该类目支付召回率。原文给出的构造结果是 **10% → 12%，+2 个百分点（示意数据）**。

### 五类运营任务共用本体语义

机会洞察（发现增长机会、定位关键问题）、数据盯盘（监控核心指标、识别异常波动）、策略生成（生成增长策略、输出行动方案）、实验评估（评估净增量、保留不确定性）、复用（沉淀经验知识、优化方法模型）——五类任务都向下挂到名词层（用户/商品/渠道）、动词层（触达用户/发放权益/发布内容）、时间层（场景/实验/版本/血缘）。

### 候选生成：GAG 方法组合

原文明确说这不是独立新算法，而是借鉴本体增强生成 **OAG**，形成四步：

1. **列必需项**：目标与指标口径、人群/权益/供给、预算/权限/频控
2. **装配上下文**：按调用者权限检索，解析对象 ID 与版本，调用 Function 取结果
3. **生成候选**：Agent 组合方案，输出 Strategy 对象，保留引用与计算证据
4. **代码校验**：结构/对象引用、权益有效期/预算；失败则拒绝或追问

示例规则：缺预算 → 不生成可提交策略；券已过期 → 拒绝该引用并说明原因。校验通过仍只是候选；人工确认后，执行服务再次授权和校验。

### 受控执行：授权由业务服务端强制实施

动作经"意图识别/动作生成"进入**服务端闸门**（身份与权限、策略校验、参数约束、审计与可观测、限流与配额），再落到受控工具（系统工具、网络工具、执行工具、数据工具、业务工具）。

原文列出三种必须由系统拦住的情况：

- 读了不该读的数据
- 执行条件已经失效
- 同一动作被重复执行

安全对照参考 **OWASP LLM Top 10（2025）** 与 **AgentDojo** 评测方法，覆盖目标侦察、提示注入、能力探测、越权调用、数据窃取/滥用、持久化与扩散六类攻击链，对应资产暴露面管理、不可信输入隔离、服务端授权控制、闸门策略执行、数据保护与脱敏、审计与监控响应。

### 反馈闭环：DecisionSample

DecisionSample "不是一个成败标签"，包含六段证据：

- context：人群快照、规则与数据版本
- decision：策略版本、候选及审批记录
- assignment：实验组、分流单位与机制
- execution：业务调用、状态与回执
- outcome：支付、退款、成本与体验
- evaluation：增量估计、区间及适用边界

三类用途、三种判断：

- **预测**：学习"谁可能购买"；观察结果标签不等于因果增量
- **复用**：检索"何种条件下可参考"；保留版本、条件、Owner 与失败原因
- **策略优化**：比较"哪种干预更有效"；需实验或适当评估设计，不凭成功率自学习

## 关键工程做法

### UMC OS 目标设计

以"三面一体"为上层能力，以内部数据本体为底座，以统一确认闸和行动中枢驱动执行闭环。

- **三面一体**：工作面（目标与指标、任务与流程、工具与界面）、知识面（知识与内容、规则与策略、语义与关联）、智能体面（角色与能力、规划与决策、学习与进化）
- **人（运营）**：目标设定、策略配置、监控与反馈
- **Strategy**：目标与要素、护栏与版本、Owner 与状态
- **确认闸**：版本绑定、风险评估、人工确认
- **Agent**：目标理解、候选生成、校验与建议
- **Action**：服务端授权、调用业务系统、状态与回执
- **内部数据本体**：数据资产（统一接入/标准定义）、实体与关系（统一建模/关联映射）、指标与事件（统一口径/语义对齐）、权限与血缘（统一管控/溯源可追）、质量与治理（统一监控/持续优化）

### 内网部署：MCP 不授予权限

部署原则：

- **内网范围与边界**：在批准的内网范围内处理模型请求与业务数据；访问与执行仍需授权审计
- **协议桥接，安全可控**：本地智能体 → 协议桥接 → 内网大模型网关；通过协议桥接打通能力与数据，最小化权限与接口暴露面
- **工具驱动，策略闭环**：读策略、读预警、建策略均通过 MCP 工具；但 MCP 不授予权限，读取校验对象与字段，写入由服务端授权、校验并审计

### 知识更新：先停用失效规则

三步机制：

1. **任务必需知识清单**：定义对象、指标与适用窗口；记录来源、版本和有效期；缺项明确暴露，不猜答案
2. **变更触发回归检查**：定位引用该规则的策略；先标过期，暂停相关执行；检查权益、预算与频控
3. **责任人确认并发布**：定位 Owner 并请求确认；审核修订，验证后再发布；超时升级，必要时转人工

版本状态：**草稿 → 已验证 → 已发布 → 已失效**。发现关键规则失效时立即阻断相关执行；修订未发布前，不继续沿用旧规则。原文强调回归检查不替代实验与执行前校验。

### 落地治理的四个风险点

| 风险 | 应对 |
|------|------|
| 建模范围与成本 | MVO：先建必要对象 |
| 身份冲突与拆合 | 规则 / 拆合 / 责任人 |
| Agent 越权风险 | 统一读写授权与执行前校验 |
| 语义变更与责任 | Owner 审核 / 共同验收 |

## 经验与边界

1. **先统一关键语义**：从最小可用本体（MVO）起步，统一关键对象与指标口径，边验证边扩展。
2. **算改分离、分级授权**：当前聚焦报告与候选策略；接入执行需人工确认、服务端授权与校验；分级授权（低风险授权、高风险审批）是后续方向。
3. **让血缘沉淀决策**：以全链路血缘记录从数据到决策的路径，让每一次决策可追溯、可复盘、可优化。
4. **AI 只做候选，不直接改业务**：Function 只读业务状态，Action 才写；校验通过不等于获准执行。
5. **血缘线索不等于因果贡献**：后续扩展若同时改变供给与时机，单因素实验不能解释各要素贡献；应先定位候选因素，再用"供给×时机"因子实验与交互检验，保留不确定性，未识别的贡献不报精确比例。
6. **场景迁移复用对象与契约，但需重验口径与护栏**：新客首单、流失挽留、大促蓄水的差异在人群、供给、权益、时机四个要素上，方法可复用、条件需重验。
7. **落地范围有明确边界**：本次只验证购沉默老客召回，不代表全生命周期已落地；"购沉默"按类目购买定义，不能替换成全站无行为。
8. **生命周期是状态迁移，不是固定流水线**：新客 → 活跃老客 → 购沉默老客 → 召回后回流；风险标记横跨各状态，不是"沉默之后的下一站"。
9. **UGO 是整合方向而非完成清单**：查询理解、行动执行、决策追溯、实验反馈、学习复用五类能力，原文都表述为"整合方向"。
10. **行业共建仍在早期**：Apache Ossie（原 OSI，孵化中）推进语义互通；UGO 聚焦受控行动、实验与反馈。
