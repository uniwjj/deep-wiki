# 大数据值班 Agent

> 来源：DataFunSummit《为 Agent 重建数据层：网易智企产品 AI Native 演进路径》（蒋鸿翔，2026-11-03）第 3 节"故障诊断"部分与两张配图《怎么做的：把值班做成一条可定时、可复现、越用越准的流水线》《最终效果：134 实例命中率 100%，99 条未命中 100% 归因》。
> 原文对实现组合的描述："基于 **WorkBuddy** 和 **EasyData** 接口的值班 Agent"。

## 背景：值班的痛点不是"不会修"，而是"重复地重新想一遍"

| 痛点（配图原文） | 具体表现 |
|---|---|
| 靠人盯 | 失败只要人看，靠人问，夜岗与周末是盲区 |
| 归因靠经验 | 每次重新翻日志，重新推理，结论因人而异 |
| 知识不沉淀 | 同一个坑反复踩，经验只留在个人脑子里 |
| 通知靠手动 | 发现问题要人工整理、人工播报 |

配图把核心价值定为：**把个人经验变成团队规则库，让值班能力可复用、可传承、越用越准**——四个设计目标对应：自动化（全流程无人值守）、可复现（同日志同规则同一结论）、越用越准（人工确认即沉淀为规则）、可移植（配置适配多产品线）。

## 总体架构：五层

原文口径："五层，定位为**大数据任务失败的「一线诊断员 + 知识沉淀器」**；Agent 不硬编码诊断逻辑，可复现能力全部下沉到 Skill。"

| 层 | 组成（配图原文） |
|---|---|
| ① 交互层 | Agent 对话 + IM 机器人播报 + 自包含 HTML 报告 |
| ② 编排层 | 定时调度 **cron** + 能力封装 **Skill**（三通道：调度 / 规则库 / 护栏） |
| ③ 智能层 | Agent × 诊断器 + 大模型兜底 + 自主探索（聚类归因） |
| ④ 执行层 | EasyData CLI —— 采集 / 诊断 / 血缘 /（后续）修复 |
| ⑤ 存储层 | 数据库单文件 + 规则知识库（llm-wiki）+ 报告目录 |

## 核心机制一：主流永线每轮五步

配图原文标题："三大核心机制 · 主流永线每轮五步 · 诊断决策四层兜底 · 知识沉淀状态机"；配图顶部口径：**发现 → 日志取证 → 命中规则 → 诊断意见 → 知识沉淀 → 播报**；**全链路只读取证，零写操作**；**cron 决定"何时跑"，Agent 决定"怎么想、怎么说"，Skill 决定"具体怎么做"**。

| 步骤 | 内容（原文配图） |
|---|---|
| ① 发现 | **拉窗口内** `FAILED / FAILED_FINISHING`；`exec_id` 幂等去重 |
| ② 诊断 | **实例级三阶段** → 定位失败节点 → 节点五项诊断 → 日志全文取证（正文写作：按执行 ID 去重、定位节点、读取日志） |
| ③ 匹配 | priority 升序 → first-match-wins，**只认生效规则**（正文：优先匹配生效规则） |
| ④ 报备 | 自包含 HTML 报告 + 文字统计 → **POPO** 机器人（正文：Agent 组织分析和播报） |
| ⑤ 收敛 | `wal_checkpoint` 合并伴生文件，单文件干净落盘 |

## 核心机制二：诊断决策四层兜底

原文："未命中才交给模型归因和聚类。"

| 层 | 做法（配图原文） |
|---|---|
| 1 规则库命中 | priority 升序取第一条，确定性最强 |
| 2 大模型兜底归因 | 规则未命中时兜底 |
| 3 Agent 自主探索 | 多轮取证 + 错误签名聚类 |
| 4 生成候选草案 | 标注「未确认」，等待人工转正 |

**三条铁律**（配图小字原文）："三条铁律（严选·猛犸实测归纳）：具体规则抢位、通用靠后；「状态类」抢在「退出码类」兜底前（**KILLED/143**）；999 阈値按 code 升序。"

## 核心机制三：知识沉淀状态机

```
candidate（候选）  ──人工归因 + 补特征──▶  active（生效）  ──停用──▶  disabled（停用）
      │                                    │
      └── 永不命中，仅作提示                 └── 转正须留痕 approved_by / approved_at
```

配图给出的状态与流转线索：

- **实例状态机**：`DISCOVERED` → 诊断 → `DIAGNOSED` → 命中 → 出诊断意见
- `candidate` **永不命中，仅作提示**
- **无 features 的规则禁止转正**
- 转正必须留痕（`approved_by` + `approved_at`）
- `auto_fix` 恒为 `diagnose_only`：**命中也不执行修复**
- **大模型产出的规则一律先进候选，人工改一个字段即完成审核**

正文原话：**"新规则只进入 candidate 候选状态，补充特征、经人工审核后才能转成 active。"**

## 核心机制四：三闸 + 只读的安全边界

配图标题："三闸 + 只读：采集入库准入控制；除「播报」外无任何写动作，天然无副作用，可安全上线观察。"

| 闸 | 内容（可辨识部分） |
|---|---|
| 幂等闸 · 已启用 | `exec_id` 主键去重，重复实例去重 |
| 权限闸 · 待配白名单 | `owner` 不在授权名单 → 仅落库 + 只诊断 |
| 恢复闸 · Phase 2 启用 | 变更前复核实例当前状态，已成功则跳过 |
| 绝不做 | 自动修复（改配置 / 发布 / 重跑）· 代建定时任务 · 写业务系统 · 处理非授权 `owner` 任务 · 绕过规则状态机 |
| 必做 | 结论先行 · 命中即给三段式 · 未命中即生成候选 · 判定前先筛等去重 · 如实报告不编造 |

正文对应："当前 Phase 0 仅做发现、诊断、沉淀和通知，**不改配置、不发布、不重跑任务**。"

## 实测效果

### 三环境实测（配图"核心成果"）

| 指标 | 数值 |
|---|---|
| 平台线上规则命中率 | **100%**（单轮 134 实例，报告含 130 条明细） |
| 未命中实例归类归因 | **99 → 9 类**（业务线 36 小时，100% 给出归因方向） |
| 规则库 | **27 条**（26 生效 + 1 候选） |
| 并发写入零丢失 | **600 行**（多进程：4 进程 × 150 次提交同一库，WAL） |

### 三环境明细

| 环境 | 规模 | 结果 |
|---|---|---|
| 开发环境 | 40 个新增失败实例 | 命中 10、候选 30；报告与播报均为真实产出 |
| 线上 A 环境 | 单轮 134 实例 | 规则命中率 **100%**，报告含 **130 条明细** |
| 线上 B 环境 | 近 36 小时 111 实例 | 命中 12，其余 **99 条归 9 类待复核** |

**B 环境 99 条未命中的 9 类归类**（配图原文，按条数）：52 外部依赖未就绪 / 本职任务代码报错；31 Spark on YARN 应用失败（如在 kill / 137 上）；9 取消 / 超时 / 依赖未满足（调度原因）；5 权限管控 / 队列不匹配 / SQL 表不存在 / 路径 IO / 导出失败；2 用户代码异常退出 —— 配图注：**这也是规则的种子**：高频失败模式提炼为新规则；**建议机制**：已知问题优先走确定性规则，未识别先精确判定「未确认」，待人工复核后转正，成为规则库的长期资产。



### 稳定性与交付形态

- **并发安全**：4 进程 × 150 次提交同一库，600 行无丢失（WAL）
- **持久化 + 幂等**：新增跑重跑：新增 0 / 跳过 N，库内容不变
- **依赖极简**：仅 Python 标准库，无第三方 pip 依赖，可离线部署
- **规则库形态**：27 条（26 生效 + 1 候选），纯文本可 diff / git 追溯
- **交付物**：Agent 定义 · Skill · 数据表设计 · 部署配置 · 使用手册 · 知识库与示例

配图原话："不是玩具：多环境真实失败实例实测，命中、报告、播报都是真实跑出来的。"

## 分阶段路线

| 阶段 | 内容 |
|---|---|
| Phase 0（已完成） | 发现 → 诊断 → 沉淀 → 播报（只读） |
| Phase 1（规划中） | 规则库校准 · 通分红级 |
| Phase 2（规划中） | 修复子策略 + 护栏（灰度） |
| Phase 3（规划中） | 验闭环 + 案例沉淀 |

配图注：越用越准（每确认一次归因，下次自动命中）、风险可控（零写操作、只读取证、可安全上线观察）、可移植（多产品线与集群配置即复用）、能力可沉淀（沉淀成 Skill 与 Skill 平台资产，不同 Agent 复核）。

## 原文特别提醒的一处口径

正文："规则命中、聚类归因和存储稳定性是不同指标，**不能把 99 条待复核归因写成 99 次故障自动修复**。"
