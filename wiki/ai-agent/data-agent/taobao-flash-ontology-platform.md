# 淘宝闪购本体平台

> **一句话定位**：把业务对象、关系、术语、分析方法和约束组织成一份**可版本化的知识**，经确认与审批发布，再通过 Web、OpenAPI、HSF 与 MCP 交给人和 Agent。解决的问题是——数据团队对口径「人靠问、Agent 靠猜」：人遇到口径问题找人问一句就能解决，Agent 没有这个渠道，拿到一列数字无法知道它来自哪个指标、哪个版本、谁确认过。

来源：阿里技术公众号《淘宝闪购本体平台：让人与 AI Agent 共用一份实时可信的业务知识》（作者王浩迪，2026-11-18）。查询侧的引擎演进见 [[taobao-flash-query-evolution]]。

## 背景与问题

文章以门店周报的口径问题开场：「这周有多少订单」按下单时间还是按支付时间算，一笔周日下单、周一付款的订单会落进不同的周。两种算法都说得通，只是报表说明里写死了一种，业务负责人脑子里记的却是另一种——**写下来的总是少数，多数口径还得靠人记**。

光把口径写下来还不够：定义有没有被确认过、变更有没有被留住、查询跟不跟得上，这三件事才决定它能不能用。前两件在治理链路，第三件在查询链路。

## 平台架构：三层元模型与单向派生链路

### 三层元模型

平台把元模型压缩到三层，每层只用很少的几种类型：

| 层 | 内容 | 细节 |
|----|------|------|
| 实体层（3E） | 定义业务里有什么 | 业务对象（商户、门店、订单等业务名词）；语义数据集（由指标和维度组成）；表对象（指向真实落库的表）；指标（引用业务对象，再落到具体的表） |
| 关系层（1 Link） | 全平台只有一种边 | 起点、谓词、终点三样确定一条边；谓词取自受控词表，改谓词就等于换了一条边 |
| 策略层（7S） | 定义业务怎么做 | 术语、视角、事件、决策、方法论、行动、剧本七类，各自回答一个问题，彼此不能替代。例：事件是「单店退款率连续三天超过 5%」，决策是「把它放进复核名单」——前者判断要不要处理，后者决定怎么处理 |

三层之外还有一类特殊约束：**公理**——只划边界，不参与图遍历。

### 五个核心模块与职责隔离

整体能力拆解为五个模块：**挖掘、质量、场景、服务、管理**。管理模块负责建模与治理，决定什么能最终生效。

模块不合并的原因都是职责隔离：

- **挖掘 vs 质量**：挖掘只负责产出候选、不判断对错；质量在候选变成草稿之后才介入（命名不规范、缺归属、关系指向已废弃对象都在这一步被退回）。若合并，挖掘模块会开始「自我审查」——只抽那些肯定能过的，覆盖面先垮掉。
- **场景 vs 服务**：场景产出的是「范围」，服务产出的是「形态」。把范围硬塞进接口会长出一堆业务参数；把形态硬塞进场景会退化成一份固定的查询模板。

### 单向派生链路

生效的那一版定义统一存放在 MySQL 里，作为全平台唯一的事实源（目前规模已达**万级**的节点与关系）；下游所有的读模型全由它派生，最终通过四个入口对外提供服务。

三条流程共用同一份数据与同一套权限点：**知识生产**（文档 → 候选 → 草稿）、**变更发布**（草稿经确认与审批 → 发布）、**查询消费**（场景经检索与投影 → 交付给人、业务系统或 Agent）。落到数据层面，它们共同构成一条单向链路：上游是唯一的事实源，下游全是派生的读模型。

> 图数据库、倒排索引或向量索引损坏，都可以从事实源重建。但只要把读模型当源头用，改名、合并、回滚就得同时改两处；两边对不上时，没有第三方能判断谁对。

因此平台只把读模型当派生物：按哪个口径算，仍由业务决定；平台负责让这个决定被写下来、被确认、被查到。

### 与业界四类方案的对比

3E、1 Link、7S 的划分方式本身并不新鲜。业界四类主流做法各自解决了一段问题，也各自留下一段空白：

| 方案 | 长于 | 落不到的地方 |
|------|------|-------------|
| 通用知识图谱（OWL + 图数据库） | 类型与约束可形式化，标准成熟，校验与推理都有现成工具链 | 规范管得住怎么建模，管不住谁确认的、引用还对不对、范围外答不答 |
| GraphRAG | 把文本切成图再召回，能回答跨段落的问题 | 抽取结果由模型生成，校验落在抽取质量上，没有业务确认这一关 |
| BI 语义层 | 指标口径稳定，取数与报表一致 | 只管指标，不管对象、关系与做法 |
| 商业本体平台（如 Palantir Ontology） | 对象、关系、动作、权限一体，工程化最完整 | 实施重、绑定深，上线前要先把对象与权限的建模规范定下来 |

闪购本体平台选择后两类方案的融合路径：**定义交给本体管理，关系交给图库做读模型，生效交给治理链管控**。划分思想源头可追溯到 W3C 的 OWL 与语义网体系；真正做的改动是**把「谁确认过」嵌入主链路**，不只停留在规范层面。

## 生产与治理环节

审批只是治理链路的一个环节，真正的难点在于流程走完后的异常处置：回调丢失、并发修改同一字段、发布中途宕机。

### 变更入口与分流

变更来自两个方向：**人工发起**（表单、批量导入或接口提交）与**上游语义变更**（如数据集换来源、指标改口径）。按影响面与规则明确程度分流：影响面小、规则清晰的字段受控自动更新；需人工判断的转入草稿流程。

### 提交前查重

变更入口一多，语义冲突随之而来。以「有效订单」为例：它在数仓中是一个字段，在接口文档中是一段参数说明，在指标定义中是一串公式，在业务人员认知中是一套未成文的约定——名称相同，边界与责任人却无法对齐。人工评审尚可拍板，但 Agent 拿到任何一份都会全盘接收。

因此草稿提交前必须查重：平台将**已发布定义与在途草稿放在一起，按标识和名称双向比对**。若等发布后再合并，成本极高，脏数据也早已流入下游。

### Owner 确认与审批时序

- **Owner 确认**：通过互动卡片完成，卡片绑定的是该变更最终生效的版本，而非草稿编号——绑错则确认记录挂错版本。
- **审批时序约束**：**先落审批记录，再启动流程**。顺序颠倒时，若流程启动成功但记录写入失败，会产生一张找不到对应变更的审批单，事后只能人工清理。平台策略：记录写入失败直接终止。

### 发布前三方合并校验

同一字段可能同时被线上、草稿和上游同步修改。平台将**线上值、草稿值与基线值进行三方比对**：

| 情形 | 处理 |
|------|------|
| 三方一致 | 直接放行 |
| 仅草稿变更 | 取草稿值 |
| 线上与草稿均变更且不一致 | 列出冲突交由人工裁决，绝不静默覆盖任何一侧 |

> 在并发场景下，字段级合并是唯一能清晰界定「改动意图归属」的工程手段。

### 发布后对账与补偿

审批系统会掉回调、网络会超时、数据库会抖动。平台的做法：**状态仅由回调推进，拒绝前端轮询猜测**；同时对未收到回调的单据进行定期对账，对审批通过却停滞在中间态的单据执行发布补偿。对账与补偿必须保证幂等——无论重试多少次，版本号只递增一次。

### 稳定标识与外部标识分离

业务对象改名后，引用它的关系、场景和接口说明极易断裂。平台将**稳定标识与外部标识分离**：稳定标识终身不变，外部标识可修改；改名时仅更新外部标识，引用方无需重写。

### 治理数据与责任边界

以门店周报的「有效订单数」为例：需将算法从按下单时间改为按支付时间，并排除测试门店。改动先入草稿，经责任人确认与审批通过后，发布前合并发现上游同步也修改了同一指标的过滤条件——两处变更不冲突但均需保留，最终由人工确认合并结果。

上线以来的治理数据：

- 累计处理 **1477 张确认单**，从提交到闭环平均耗时 **3 个自然日**；
- 未确认单据每日晨间自动催办（领域 Owner 精力有限，等待必须有上限）；
- 已纳入评分的对象覆盖率达 **99.6%**，其中 A 级占 **98.3%**。

治理链路的责任止于发布那一刻：审批通过仅代表**有人为此次变更负责**，不保证改动绝对正确；当事实源已更新为新版本，查询侧需等待同步完成后才能读取。发布前人与 Agent 读到的并不同——人能在草稿中预览新算法，Agent 只能读到旧版本；发布后两者才真正拿到同一份定义，差别仅在投影格式。

## 接口账目：只提供定义，不承担计算

对外的四个入口（Web、OpenAPI、HSF、MCP），对内是一张严格对齐的能力清单：**18 个方法在四端一一对应，其中 7 个只读、11 个写入**。同一份定义从四个入口输出，内容、权限点与审计必须完全一致，差异仅存在于三处：鉴权、参数解析与响应投影。

平台做了一个刻意的取舍：**只保证定义和版本的准确性，在计算能力上做收敛**。平台可以返回指标的定义、维度和取数口径，但不会直接给出「这周的有效订单数是多少」这样的最终结果——因为一旦接口开始承担计算，口径变更、上游回刷、时区差异这类问题最终都会变成平台的责任。将计算留给业务系统，责任边界才足够清晰。

28 天窗口的实际调用数据（12 个业务应用接入生产环境）：

| 项 | 数据 |
|----|------|
| 业务侧调用 | 29637 次，占平台总调用量 **5.4%** |
| 头部两应用（销售侧智能洽谈助手、区域经营分析助手） | 合计 19929 次，占业务侧 **67%** |
| 商家营销 / 商品定价方向两应用 | 5402 次 / 3661 次 |
| 其余八个应用 | 最多仅 158 次 |
| 业务侧成功率 | **99.5%**（29483 次） |

两个事实：真实需求高度集中在少数几个分析场景，长尾极薄；业务侧仅占总调用 5.4%，说明平台当下的流量主体仍是上游语义平台的自动同步。近 28 天最高频的 12 个检索词里，有 **7 个是补贴与价格口径**（单品到手价目标匹配 1892 次、出资 628 次、阶梯暴涨 600 次、门槛 494 次）——被高频检索的，恰恰是业务口径中最容易产生歧义的部分。

## 核心承诺与工程代价

平台的四条核心承诺，每一条都有其必须支付的代价：

| 承诺 | 代价 |
|------|------|
| **单一生效版本**（单一事实源）：人与 Agent 读到的绝对是同一份 | 版本内容从 Git 仓改存数据库，换取了强一致性与低发布延迟，但失去了分支与回放能力，差异视图需自行实现 |
| **每次变更留痕**：谁改的、改了什么、何时生效、依据哪次审批全部可追溯 | 写入口收敛为一个，幂等仅需实现一次，但该入口位于关键路径上，必须自带对账与补偿机制 |
| **读模型可重建**：图库损坏可从零重建 | 图、倒排、向量三种索引均由同一次写入派生，写路径只能串行，且缺乏在线只读副本，容量存在硬上限，高负载任务只能排至低峰期 |
| **范围可限定**：范围外的答案绝不会伪装成范围内的结果返回 | 场景快照优先，模型修改后需等待下一次圈选才生效 |

四笔代价中，**第三笔的约束最强**：前两笔的代价尚可接受，第三笔付出的是硬性的运维限制（p99 数据见 [[taobao-flash-query-evolution]]）。

另有两项能力平台**不予覆盖**：

1. **图遍历不等于逻辑推理**——沿关系找到路径不等于能推出结论，形式化推理需单独实现；
2. **本体建模不等于业务判断**——平台负责定义知识与约束并保障其准确性与可追溯性，能否让使用者（或 Agent）将知识转化为实际业务价值，需要平台与业务侧共同完善。

## 避坑指南：四条可迁移的经验

这四条经验虽然源自当前平台的具体约束，但「换一套系统同样成立」：

1. **身份与地址分离**：不可变标识做身份，可读地址做引用——这在任何具有引用关系的系统中均成立。
2. **将约定做成构建门禁**：在构建时检查能力是否已真实接入，而不只是检查代码语法。在产物出口拦截静默退化，成本比上线后排查低一个数量级。
3. **数字必须带口径**：数据在哪运行就标注哪，生产库就写生产库；代理指标不能写成相关性结论；平台只输出自己能归因的量，不认领业务侧的收益。
4. **选型先看场景窗口，再看引擎能力**：变更到可查能容忍多久、查询是否需要跨引擎拼装、是否出现过跨引擎数据不一致的事故——这三个问题应排在引擎性能之前。

> 架构升级的触发条件应当是观测到的真实事故，而非新引擎的跑分。

## 机器可读性三问（结语）

过去业务知识以文档为载体，背后默认「只要打开，就是最新版本」。在人读文档的年代这个假设可以成立，因为人会自动核对版本与上下文；但 Agent 不会——它可能读到了上一版的定义，却对此毫无察觉。因此知识必须从「文档」演变为**「可引用、可追溯的定义」**。

判断一套知识是否具备「机器可读性」，只需追问三个问题：

1. 这一版是**谁确认的**？
2. 发生变更后，引用的上下游**是否能感知**？
3. 超出范围时，它**会不会给出错误答案**？

这三个问题能答上几个，就决定了这套知识能被信任到哪一步；如果一问三不知，那不过是把静态文档搬进了数据库而已。

回到门店周报的场景：Agent 现在能精准查到口径、版本、确认人和场景范围，但它依然查不到「这周该看哪个口径」。这个边界并非能力不足，而是系统分工的必然——**业务口径必须由业务侧拍板，而平台的核心职责，在于让每一次拍板都留下清晰的审计痕迹：生效的是哪一版、由谁确认、从何时开始生效。**

## 边界

- 这是**单一业务（淘宝闪购）的落地实践**，规模数据（万级节点与关系、1477 张确认单、99.6% 覆盖率）均为平台自身口径，原文未给出统计基准。
- 治理链路的责任止于发布：平台能厘清改动由谁发起、依据哪次审批、何时生效，但不保证改动绝对正确，也不保证 Agent 一定用对、模型不会把定义解释歪——后两者原文明确需依靠提示词、评测与业务复核。
- 平台明确不承担计算：原文未给出「这周有效订单数是多少」这类最终取数结果的任何实现。
- 公理「只划边界、不参与图遍历」的具体形式化规则，原文未展开。
