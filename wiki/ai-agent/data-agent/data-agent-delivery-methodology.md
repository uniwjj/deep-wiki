# Data Agent 项目落地方法论

> 来源：网易内部 PagesHub 方法论文档《Data Agent 项目落地方法论》（作者余聪勇，2026-08-31，页面标注"内部方法论"）。面向 Data Agent 项目的交付与运营全过程。
> 总纲一句话：**项目落地分两大阶段——交付阶段解决验收问题，运营阶段解决价值持续性问题；无论哪个阶段，用户都全程参与。**

## 核心命题：项目标准

一个 Data Agent 项目，第一件事是确定项目标准。

原文对痛点的描述：很多人不清楚项目标准是什么——团队凭感觉做，客户凭感觉验收，标准悬空，后期全是"预期管理"的拉扯。**标准不立，方法无效**。整个项目落地逻辑，从回答"什么叫成功"开始。

> 验收标准 = 核心问题列表 + 数值目标 + 双方签字

## 两种导向论

标准的两种定义方式，没有对错，只有选择：

| | 价值导向论 | 准确性导向论 |
|---|-----------|-------------|
| **尺度** | 客户使用者觉得好不好用 | 答案准不准 |
| **内涵** | 以体验和业务价值为尺度：能不能用起来、用起来顺不顺、有没有解决业务问题 | 以答案质量为尺度：问得对不对、答得准不准、错了能不能被识别 |
| **量化维度** | 使用率 / 活跃度 / 留存；任务完成率、操作效率；满意度评分；业务结果指标（工单时长、检索复用率等） | 准确率 / 命中率；置信度分布；反馈率、纠错闭环率；问题类型分布（检索 / 口径 / 规则 / 幻觉） |
| **风险** | 主观、难横向比较，容易被"感觉"带偏——今天说好明天说不好，无据可查 | 准确 ≠ 有用——答得全对但没人用，项目照样失败；盲目追求 100% 准确可能把项目拖死 |

**本方法论倾向准确性导向（不盲目追求 100% 准确），主张"价值定方向，准确性定量尺"。** 选择理由（原文两点）：

1. **价值导向的软肋**：场景的价值性由用户主导——用户觉得有价值，才有价值。但用户主导的价值未必得到所有人认可：使用者认可、管理者未必；业务认可、IT 未必。多方视角不同，价值共识难达成，量化的价值指标也难以获得一致背书。
2. **准确性导向的落点**：基于用户提出的问题进行回归性测试，得到一个客观数值。这个值可复现、可对比、可验收，不依赖任何人的主观认可——测试输入来自用户真实问题，结果由机器判定。

结论：以用户真实问题为测试输入，把价值变成可验收的数。项目标准因此**可定义、可执行、可争论、可服众**。

## 项目落地的两大阶段

| | 交付阶段 | 运营阶段 |
|---|---------|---------|
| **解决的命题** | 验收问题——做得对不对 | 价值持续性问题——价值能不能持续 |
| **核心手段** | 四支柱：沟通标准化 / 自动化构建场景 / 自动化测案例 / 标准化排错（见 [[data-agent-delivery-pillars]]） | 三支柱：价值监测 / 用户赋能 / 以点扩面（见 [[data-agent-ops-pillars]]） |
| **终点** | 数据化标准逐条达成，双方确认验收 | 价值持续增长，客户拥有创造场景的能力，以点扩面 |

**用户参与贯穿两阶段**：用户不是被服务的对象，而是共建者——交付阶段参与标准与验收（共同定义标准 · 确认口径 · 逐条验收），运营阶段参与使用与创造（使用中反馈 · 创造新场景 · 拥有能力）。

## 核心策略：以场景切入，以点扩面

场景是价值的载体，扩面是价值的放大。四步路径：点 → 线 → 面 → 全。

| 步骤 | 名称 | 说明 |
|------|------|------|
| 点 | 场景切入 | 选一个验证过的核心场景做出价值——AI 时代用户通过场景感知价值，"好用"来自具体场景里的真实体验 |
| 线 | 场景复制 | 把验证过的方法、标准、知识资产复制到相关场景，成本远低于从零开始 |
| 面 | 场景扩展 | 用户参与新场景的提出与创造——客户有能力，才能持续扩展 |
| 全 | 业务覆盖 | 从点到面覆盖核心业务，价值持续放大，客户拥有自主创造场景的能力 |

**关键认知**：场景会变化，未来场景需要客户有能力创造——项目落地不只是交付一个可用系统，而是让客户拥有持续创造价值的能力。以点扩面，点是切入点，面是客户自己的生长。

## 数据回流：校准标准，闭环自进化

标准不是一次定死的：**交付阶段用数据验证标准，运营阶段用数据校准标准**。

每个场景的运行数据都在回答"这个标准定得对不对、价值是否持续"——回流校准，越用越准。数据回流让标准更新，驱动下一轮扩展——这正是"以点扩面"能够持续的原因：每一次扩展，都带着已验证的标准和数据。

## 执行检查清单（七支柱最小动作）

原文以"项目启动即对照"的方式给出 8 项：

| 事项 | 内容 | 时机 · 执行方 |
|------|------|--------------|
| 项目标准 | 与客户共同定义验收标准（核心问题列表 + 数值目标），双方签字确认 | 启动时 · 客户 + 交付 |
| 沟通标准化 | 标准话术 / 问卷完成场景挖掘；推进模式（站会 / 周报内容）启动即定 | 启动时 · 交付 |
| 自动化构建场景 | 问题列表完成技术选型（宽表 / 指标）；指标批量创建走 CLI；测试 / 基线 / 生产业务助手分级发布 | 交付期 · 交付 + 产品 |
| 自动化测案例 | 问题列表录入测试集；校对规则设置（SQL 比对 + 思维链）；跑批拿到准确性 / 稳定性 / 收敛值 | 交付期 · 交付 |
| 标准化排错 | 问题分类 + 排错 SOP 就位；售后业务助手承载排错；留痕回流知识库 | 交付期 · 交付 + 售后 |
| 价值监测 | 可视化看板上线（活跃度 / 命中率 / 反馈数）；问题定位 → 优化 → 回归闭环在跑 | 运营期 · 交付 + 客户 |
| 用户赋能 | AI 培训 + 满意度调研启动；业务人员工作经验 SOP 化开启 | 运营期 · 交付 + 客户 |
| 以点扩面 | 扩散路径明确（小部门 → 多部门 → 多分公司）；场景收集机制（大赛 / 培训）建立 | 运营期 · 客户主导 |
