# 腾讯 DataBuddy 的 Text-to-Semantic-to-SQL 与 MetaRAG

> 来源：微信公众号「噪声之下」《拆解腾讯 DataBuddy 的 Text-to-Semantic-to-SQL 与 MetaRAG技术实现》，2026-09-21 07:00 发布。
> 原文结构为 7 节：01 Text-to-SQL 缺的是生产资格 → 02 统一语义层四要素与三层架构 → 03 SemQL 确定性编译 → 04 MetaRAG 双路召回 → 05 覆盖度决定路径 → 06 MCP 语义层出口 → 07 一点判断。

## 核心论点

原文的骨架是三条串联的因果：

1. **Text-to-SQL 的结构性缺陷**不在模型不够聪明，而在"让概率模型直接输出 SQL 字符串"这条路径本身——解法不是换更大的模型；
2. **口径的答案不在模型参数里**，在企业自己的实体、关系、指标和维度定义里，所以要把答案"显式地、机器可读地沉淀下来"——即统一语义层；
3. 语义层解决了"召回准确时 100% 写对 SQL"的问题，但**取数准确率还取决于另外两件事**：一套经过治理的、干净且 AI 友好的业务资产，加上一套可靠的召回方案——**缺一不可**（原文按语即摘要）。

原文引述腾讯云 WeData 产品总监唐晨（2026-06）的话："如果底层数据没准备好，上面跑什么 Agent 都是白搭。"并称腾讯云据此提出「**统一语义正在成为 AI 时代新的数据护城河**」。

## 01 · 企业落地的三类翻车现场

原文给出的背景：Text-to-SQL 的公开评测（BIRD、Spider）分数涨得很快，但企业落地普遍卡在 **60%~70%** 的准确率上。

| 陷阱 | 机理（原文） |
|---|---|
| 指标歧义 | 一个"收入"有八种口径——含不含退款、含不含内部调拨、按下单时间还是确认收入时间。模型不知道公司用哪一种，只能随机选，甚至每次选的还不一样 |
| JOIN 错乱 | 关联键靠猜。订单表与订单明细表是一对多，模型把金额字段直接 SUM：SQL 语法完全正确、跑得也快，但每行订单金额被明细行数膨胀 N 倍——"**不报错的错、跑得飞快的错、三天后才被业务发现的错**" |
| 查询条件随意匹配 | "上季度""华东区"这类过滤条件，模型很难知道它在企业数仓里对应哪个组织层级、哪张维表的哪个编码 |

## 02 · 统一语义层（Unity Semantics）

定位：介于"物理数据存储"与"分析应用（包括 AI Agent）"之间的抽象层，目标是 Single Source of Truth——"一次定义、处处可信"，解决"同名不同义、同义不同名"。官方称 Unity Semantics / DataBuddy Unity Semantics。

### 2.1 四要素

| 要素 | 含义 | 官方对应 |
|---|---|---|
| **Entity**（实体/概念） | 业务对象与标准术语：客户、订单、收入 | 概念：数据的业务含义 |
| **Relation**（关系） | 实体之间的关联与血缘，即对象之间怎么连接 | 关系：血缘 + 逻辑模型 |
| **Metric**（指标） | **在度量上叠加口径、窗口和同环比** | 指标：数据的计算口径 |
| **Dimension**（维度） | 按什么来分析：枚举、层级、范围、时间粒度 | 维度：数据的观测维度 |

原文强调 Metric 这一格的意义：语义层持有的不是"哪个字段是金额"，而是"**GMV = 已支付订单金额之和，按支付时间，不含退款**"这种完整计算逻辑——编译 SQL 所需全部信息都由语义层显式持有，**这是"确定性编译"能成立的前提**。

### 2.2 三层架构

| 层 | 内容 |
|---|---|
| L1 物理层 | 原始数据、湖仓引擎、计算引擎 |
| L2 业务层 | 指标、维度、实体、关系等语义资产 |
| L3 协议层 | **所有问数请求（无论是 BI、人还是 Agent）统一走这一层出口** |

原文补充的关键一点（来自 DataBuddy 团队 2026 AICon 分享）：**DataBuddy 自己也是语义层的消费方之一**，语义能力不封闭在 DataBuddy 产品里——BI、第三方 Agent 都可以通过 **JDBC 或 MCP** 消费同一套语义资产。

### 2.3 语义冷启动：机器出草稿，人来确认

企业普遍没有现成语义资产，这是落地的"第一个拦路虎"。两条抽取路径：

| 路径 | 输入 | 推断方式（原文） |
|---|---|---|
| 从元信息抽 | 表结构、字段注释、主外键、历史 SQL、BI 配置、血缘 | 表推断实体；主外键和 Join 频次推断关系；聚合列推断度量；**高频 group by 推断维度** |
| 从业务文档抽 | 数据字典、Wiki、PRD、口径说明 | 推断指标定义和维度 |

原文划定的红线：**LLM + 规则统计产出的只是草稿**。候选经过冲突检查、去重聚类后，**必须由 Owner 审核**才能进入权威语义资产库。官方原话："**DataBuddy 降的是人工录入的成本，不是人工治理本身。**"原文对此的解读是——语义治理的人工环节没有被取消，只是从"从零手写"变成了"审核确认"。

> 与数帆 EasyData 的"矛盾/歧义检测 → 待确认队列 → 人工仲裁入图并保留来源"是同一种治理形态，见 [[table-knowledge-graph]]。

## 03 · SemQL：从"概率性生成"到"确定性编译"

### 3.1 定义与唯一约束

SemQL（Semantic Query Language）是语义层对外的**类 SQL 查询语言，以 JDBC 方式提供查询能力**。核心约束只有一条：**标识符（指标 / 维度 / 时间）必须全部来自语义层**——模型不能自由发挥任何字段名、表名、JOIN 逻辑，只能"点菜"，从召回的语义资产里选。

Text2Semantic2SQL 即：自然语言 → 标准化语义查询 → 语义层编译为 SQL，替代 Agent 直接生成 SQL 的概率性猜测。

官方材料给出的 SemQL 形式：

```sql
query(
  metric   = [订单金额],
  where    = [Dimension(订单状态) = '已取消'],
  group_by = [Dimension(性别), TimeOutput(月)]
)
```

原文解读：这条查询里**没有任何物理表名、字段名和 JOIN 条件**。"订单金额"是指标资产，"订单状态""性别"是维度资产，`TimeOutput` 是语义层的时间标识符。JOIN 怎么写、金额要不要去重、按哪张维表关联，全部是语义层编译器的事，模型碰不到。

### 3.2 与传统 Text-to-SQL 的对比

| 维度 | 传统 Text-to-SQL | Text-to-Semantic-to-SQL |
|---|---|---|
| 生成物 | SQL 字符串 | SemQL（语义查询） |
| 模型自由度 | 表名 / 字段 / JOIN / 口径全部可自由发挥 | 只能在召回的语义资产中"点菜" |
| JOIN 逻辑 | 模型猜，一对多膨胀、错配全靠事后发现 | 语义层编译，按预定义关系确定 |
| 口径 | 无权威来源，同名指标可能每次不同 | 指标口径全局唯一，改一次处处生效 |
| 错误形态 | 静默错误多（跑得通但数是错的） | 点不到菜就**明确失败**，交给降级路径 |
| 结果一致性 | 同一问题两次可能两个答案 | 相同问题、相同口径，答案一致 |

### 3.3 完整链路：一个真实案例

原文引用的腾讯系内部"长尾案例"——用户输入 **"帮我查一下腾讯视频男性 dau 的变化趋势"**：

1. **意图识别**：核心诉求是趋势查询，对象"dau"，修饰条件"男性"
2. **语义检索（MetaRAG）**：并不去底层找叫 "dau" 的字段，而是把 "dau" 对齐为指标库中的 **"APP端活跃设备数"**，把"男性"解析为维度条件 **"性别-男"**
3. **生成 SemQL**：用对齐后的指标 + 维度组装标准化语义查询
4. **编译执行**：语义层把 SemQL 编译为 SQL——多表 JOIN、口径、同环比都在这一步被确定性展开——并下推执行；配图/原文提到 **Auto Acceleration 层**还会做 HBO/CBO **多级缓存、自动物化视图推荐与合并、谓词下推**
5. **返回结果**：Data Agent 拿到可信的趋势数据输出分析，官方概括为从"**表交付**"到"**知识交付**"

原文的关键判断："dau" 这种口语缩写与 "APP端活跃设备数" 这种正式指标名之间的映射，**是语义层资产，不是模型的常识**——换任何大模型，这个映射都不在模型参数里，这也回应了"换大模型提升微乎其微"。

## 04 · MetaRAG：为结构化元数据设计的双路召回

### 4.1 为什么传统 RAG 不够用

原文把"语义检索"称为整条链路里**最难的一环**：中大型企业的语义层可能有成千上万条指标、维度、实体定义。

传统 RAG 是为**非结构化文档**设计的（切 chunk、向量化、按相似度召回），而语义元数据是**结构化、组合性**的：一次查询 = 指标 × 维度 × 时间粒度 × 过滤条件的组合。组合爆炸之下，单条向量化召回要么召回了指标漏了维度，要么维度拼错了口径。

### 4.2 FlattenedRAG（F-RAG）：把组合"摊平"成问答库

- **做法**：枚举元数据组合，把结构化元数据转化为非结构化表示——**人工标注的核心模板 + 自动枚举**，把"指标 × 维度 × 时间粒度"的组合预先展开成一条条"问题 → 语义组合"的知识条目，构建离线问答知识库
- **规模**：官方给出的口径是**亿级别（Billion-level）**的离线元数据知识索引
- **强项**：展开后每个组合变成一条普通可检索知识，传统 RAG 的成熟基建全部可用，准确度高，特别适合核心高频问题（"GMV 是多少""上月 DAU 趋势"）
- **弱项**：枚举是排列组合，高频组合枚举得起，**长尾组合枚举不完**——由冷门维度、罕见过滤条件拼出来的查询覆盖不了

### 4.3 StructuredRAG（S-RAG）：利用结构特性分层召回

- **做法**：不预先枚举，利用元数据的结构特性在线召回——**先定位核心指标**（缩小到与问题相关的少数指标）→ **围绕该指标过滤召回相关维度与修饰条件** → **由大模型确定最优组合**
- **强项**：按结构分层走，冷门指标 + 罕见维度的长尾组合也能被拼出来
- **弱项**：**对结构化索引的质量依赖更高**

| 维度 | F-RAG | S-RAG |
|---|---|---|
| 机制 | 枚举元数据组合，结构化 → 非结构化问答库 | 先召回核心指标，再过滤召回维度，LLM 定组合 |
| 强项 | 高频核心需求，准确度高 | 长尾复杂问题，覆盖度高 |
| 弱项 | 长尾组合枚举不完 | 依赖结构化索引质量 |

原文结论：**双路并行、互为补位——这就是"混合架构"的含义**。

### 4.4 完整召回链路：千级 → Top 100 → Top 6

| 步骤 | 内容（原文） |
|---|---|
| 1 意图识别 | 理解用户问题的核心诉求 |
| 2 Query 改写与分解 | 把复杂问题拆成可检索的子问题 |
| 3 多路召回 | F-RAG 与 S-RAG 同时召回核心候选实体（指标） |
| 4 Cross Encoder 在线打分 | 把候选集从**千级别缩小到 100** |
| 5 精选策略 | 进一步从 **Top 100 收敛到 Top 6** |
| 6 LLM 终选 | 大模型从 Top 6 中选出最符合意图的"指标 + 维度"组合，生成 SemQL |

漏斗的目的（原文直白表述）：从根本上**去除噪音、抑制大模型幻觉**——进入生成环节的上下文越干净，模型"点错菜"的概率越低。

## 05 · 覆盖度决定路径：不是所有问题都走 SemQL

原文称这是 AICon 演讲里"容易被忽略、但工程上最关键的细节"：召回之后**并不直接生成 SQL，而是先判断语义覆盖度，分三级处理**。

| 覆盖度 | 路径 | 处理方式（原文） |
|---|---|---|
| **完整命中** | SemQL 确定性路径生成 SQL | 同时 **NL2SQL 并行跑一份作兜底比对** |
| **部分命中** | 受约束的 NL2SQL | 已召回的语义作为**参考上下文注入**；缺失的部分记录下来 |
| **完全未命中** | 加严防护的 NL2SQL | **收紧 schema 范围、只读限制、加强确认策略** |

三道校验与回流（无论走哪条路）：

- 候选 SQL 都要过 **静态检查、语义对齐、权限收敛**三重校验
- 失败的证据回到 **Agent Loop** 里修正重试
- 缺失的 case **离线聚类归因**，变成四要素候选**进入治理流程**

原文对此设计的评价："它的诚实之处在于，它不宣称语义层能覆盖 100% 的提问，而是把'覆盖不到的部分'显式圈出来，降级到受约束的生成路径，并把每一次降级都变成语义资产生长的输入——**覆盖度沿 Agent 的 ReAct 循环逐步收敛，越用越准**。"

### 配套分层记忆

Session（会话任务态）→ Personal（个人偏好）→ Team（业务空间共识）→ Enterprise（治理后的长期资产）。晋升必须过两道关口：**去重聚类 + 冲突质量检查**、**Owner 审核**。

官方原话："**不能因为一条经验被用得多，就自动把它当成企业真相。**"

## 06 · MCP：语义层的开放出口

语义层指标发布后，会**自动生成 MCP（Model Context Protocol）服务**。据腾讯云官方文档（WeData 产品文档 MCP 章节），指标 MCP 服务封装三个工具：

| 工具 | 功能 |
|---|---|
| `SearchMetric` | 指标定义检索：按关键字语义检索最匹配的指标和对应分析维度；多个匹配时由 Agent 或用户判断选哪个 |
| `QueryMetricData` | 根据 SearchMetric 返回的指标/维度 + 用户查询条件，直接返回指标计算结果 |
| `QueryMetricDataBySemQL` | 直接提交 SemQL 语句查询（与 QueryMetricData 作用相同、请求方式不同，**二选一**） |

服务以 HTTPS 端点形式提供：`https://api-{地域}.wedata.cloud.tencent.com/api/mcp/v1/metric`。

原文推论：任何支持 MCP 的 Agent（不限于 DataBuddy 自己）都能接入同一套口径；业务团队也可以基于这三个工具自行编写 Prompt，搭建自己场景的数据分析智能体，**不必依赖数据工程师排期**。

并在 07 节收口："这也是'统一语义层是护城河'这个判断的落地形态：**模型会换代、Agent 框架会换代，但语义资产和它对外的 MCP 出口是跨代复用的。**"

## 07 · 一点判断（原文结论）

> "语义层的出现，解决了召回准确的情况下，100% 可以写对一个对的 sql 问题。除此之外，影响取数准确率的关键因素还有是否已经有一套经过治理的、干净的、AI 友好的业务资产 + 一套可靠的召回方案，缺一不可"
