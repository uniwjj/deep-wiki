# 表知识图谱

> 来源：DataFunSummit《为 Agent 重建数据层：网易智企产品 AI Native 演进路径》（蒋鸿翔，2026-11-03）第 3 节的语义层部分。

## 问题的定位

原文："只有接口和 Skill，Agent 仍不知道**表、字段以及开发规范究竟代表什么**。"配图的措辞更直接：**大模型懂通用 SQL，但不懂企业真实表环境与口径黑话**——表知识库连接物理世界与 AI 世界。

配图还有一句总纲：**接口语义决定 Agent 能不能调用，数据语义决定 Agent 调得对不对。缺任何一层，Agent 都只能在平台上"盲操作"。**

## 流程：输入 → 图谱生成与质检 → 输出

### ① 输入：资产地图表详情（多源自动蒸馏）

"无需人工耗时填报，系统原生结合「数据资产地图 · 表详情」底座自动化提取"：

| 输入信息 | 内容 |
|---|---|
| 描述信息与技术元数据 | Hive/Spark DDL、字段类型 / 注释 / 分区 / 生命周期 |
| 产出信息与全链路血缘 | 上下游生产任务、依赖拓扑反推字段加工与派生逻辑 |
| 标准化标签与热度 | 维度建模标准化标签、主外键表关联、访问热度与检索频次 |
| 使用说明与外挂文档 | 业务知识说明、文档中心关联的口径与指标规范文件 |

### ② 核心：图谱生成与质检中枢

**Step 1 · 实体抽取与拓扑构建**

- **物理存储层**：Catalog → DB → Table → Col（配图写作 Col）
- **业务抽象层**：Concept（概念）→ Metric（指标）
- **关系链接网**：包含、血缘、派生、计算依赖
- 方法：从 DDL 抽物理拓扑，**LLM 从注释与文档提炼业务概念与指标，双向构建 6 类节点网络**

正文补充：表知识库读取 DDL、字段、分区、血缘、访问热度及文档，记录**包含、派生、计算依赖**等关系；**图谱连接实体，向量检索补充内容召回**。

**Step 2 · 质检防线**

- **矛盾检测 Conflict**：跨表 / 口径公式冲突（如财务与营销对同指标算法打架）
- **歧义检测 Ambiguity**：同名不同义、同义不同名（识别概念重叠，防 AI 混淆）

**Step 3 · 审核仲裁闭环与来源溯源**

- 无异常直接入图；触发防线的条目**强制阻断**，进「待确认队列」人工仲裁（合并 / 拆分 / 补全）
- 每条属性绑定**原始出处**
- 正文原话："公式冲突和同名异义需要进入人工确认队列，**经审核后入图，并保留来源**"

### ③ 输出：驱动多 Agent 生态

- **EasyAgent**：业务人员自然语言提问，顺着图谱直接命中真实物理表与指标
- **OpenClaw / 外部智能体**：通过标准 MCP / API 协议输出数仓语义
- **Claude Code / 开发者助手**：数仓工程师在 CLI/IDE 中秒级感知表全息语义
- 原文落地数据：**已在传媒场景挖掘 600 张表的知识**，通过 MCP 接入开发流程

## 为什么必须建图谱，而不是普通文档 / 向量检索

配图用业务最常见的问题「**活跃用户数多少**」做对照，分三个环节：

| 环节 | 普通检索的缺陷（配图原文） | 图谱机制支撑（配图原文） | 核心成效（配图原文） |
|---|---|---|---|
| 01 寻表与口径定位 | 只做文本相似度匹配，捞出一段零散话，可能只包含「活跃用户」字样，但**拿不到指标算法公式，也找不到对应的物理表**（如 dwd.user_login）。Agent 只能靠猜，或者写出错误的 SQL | LightRAG 采用 **Local**（低层实体检索：DAU/MAU/ 字段 / 表）+ **Global**（高层关系检索：计算依赖 / 业务口径）并行，顺着图谱做一跳 / 二跳邻居扩展，**一次性把 活跃用户 → DAU → COUNT(DISTINCT user_id) → dwd.user_login 的关系链完整拉出** | 业务概念与物理表无缝绑定，单次精准锁定目标资产 |
| 02 推理与上下文装配 | 因为没有现成的实体关系图，Agent 必须通过多次 Prompt 循环「先查这是什么 → 再查用哪张表 → 再查这张表有哪些字段 → 再查指标怎么算？」。多轮检索不仅 **Token 成本极高**，而且**每多跳一次，上下文丢失和模型脑补幻觉的概率就翻倍** | 图谱以种子节点直接展开关联网络，一步组装出包含【实体表 + 关系依赖 + 原始定义 Chunks】的三段式完整上下文，让推理过程收敛到**单次精准回答** | 多轮试错收敛为 1 步精准命中，推理成本直降，杜绝公式算错 |
| 03 变更感知与长效保鲜 | 客观事实：业界数仓口径多散落在 Git 或 Wiki 文档中，文档与底层数仓生产代码是割裂的；一旦开发改了表的字段、分区或加工逻辑，文档根本不会自动同步，导致 Agent 检索到**过时口径** | 图谱实现：知识图谱直接挂在底层数据资产地图之上，数仓表字段或链路变更时能**增量感知、自动重新学习**，确保 Agent 随时调用的都是与生产一致的有效知识 | 知识图谱与生产代码同频绑定，动态增量自演进，时刻保鲜 |
| — | 知识生命周期闭环 | 自动回流标记问答失败与口径打架的【质量问题知识】，同时度量条目调用热度，主动识别【长期闲置知识】，驱动图谱持续自净化与敏捷瘦身 | — |

> 表中「知识生命周期闭环」一栏在配图里排在第三列下方、无左侧缺陷栏，故单列一行。

正文对第 1–2 环节的简写："普通相似度检索可能找出相关说明，却**缺少 DAU 公式和对应物理表**。数帆使用 LightRAG 的 Local 实体检索与 Global 关系检索，沿**概念、指标、公式、字段、表**展开关联，同时提供原始定义。"

## 与语义层"两条内容线"的关系

原文把 EasyData 语义拆成两部分：

- **元数据语义**（本页主体）：从表结构、注释和血缘提炼业务概念——解决"**有什么**"
- **开发语义**：命名、建模、Git 变更和回滚要求——解决"**怎么做**"（配图另列 Git 集成、OpenSpec 类的数仓 SDD、平台开发语义层、回收站与可回滚，详见原文配图）
