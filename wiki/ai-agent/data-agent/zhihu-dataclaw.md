# 知乎 DataClaw：从 MetricFlow 到 AI 原生语义层

> 核心主张：**MetricFlow 保证了 SQL 的准确性，也限制了 AI 的想象力。** 语义层要经历三阶段演进——① MetricFlow 语义层（SQL 准确但不灵活）→ ② 知识库建设（AI 生产与消费数据资产）→ ③ 本体图谱（懂业务、能推理）。三条落地方法论：切片按知识的形状、检索按业务的优先级、图谱按问题的规模。

来源：DACon 2026 北京站演讲《知乎 DataClaw：从 MetricFlow 到 AI 原生语义层的演进实践》，演讲人汤晋瑄（知乎大数据部）。

## 背景与问题

### 业务痛点：80% 的时间花在体力劳动上

原文把取数分析的痛点归为三类，并各给一个标签：

| 痛点 | 具体表现 | 标签 |
|------|---------|------|
| ① 取数依赖分析师 | 业务方等待时间长；需求排队，口径来回确认 | 等待久 |
| ② SQL 编写成本高 | 技术门槛限制自助取数；非技术同学拿不到数 | 门槛高 |
| ③ 指标口径不一致 | 分析结果存在差异；同一指标两套答案 | 口径乱 |

一句话总结问题根源：**"大模型强得可怕，但它不了解业务知识和指标口径。"**

### 问题的本质

不是模型不够强，而是模型缺少企业业务知识与指标口径。整个演进围绕一个判断展开：语义层要成为 AI 可直接使用的数据资产，而不是只供人配置的规则文件。

## 方案/架构

### 三阶段演进总览

| 阶段 | 方案 | 核心特点 | 主要局限 |
|------|------|---------|---------|
| 第一阶段 | 基于 dbt MetricFlow 的语义层 | SQL 完全由 MetricFlow 引擎生成，准确性有保障 | 复杂、特殊指标支持成本高；不够灵活，无法充分发挥 LLM 能力；维护配置成本高 |
| 第二阶段 | AI 原生知识库 | 指标定义由 LLM 生成、人工确认后入库；生成→入库→检索→使用的闭环 | 多跳关系检索效果有限（如「用户→订单→商品」三跳答不上来） |
| 第三阶段 | 轻量级本体图谱 | AI 抽取本体、专家确认；L1 连接 / L2 理解 / L3 推理 | 只覆盖节点自带锚点，图计算限定跳数 |

### 第一阶段：dbt MetricFlow 语义层

技术架构为 `dbt Semantic Layer → MetricFlow 引擎 → BM25 指标检索`。

- **优势**：规范化、类型安全、SQL 准确。
- **局限**：MetricFlow 复杂，特殊指标支持成本高；不够灵活，无法充分发挥 LLM 的能力；维护 MetricFlow 配置成本高。

原文的判断是：**准确性有保障，但灵活性被引擎锁死。**

### 第二阶段：AI 原生知识库

设计原则：**让 AI 自动维护和使用数据资产。**

三个要点：

1. **指标定义由 LLM 生成**，人工确认后进入知识库；
2. **知识库是语义层核心**，是 AI 原生语义层的支撑底座；
3. **闭环自运转**：LLM 生成 → 知识库入库 → 增强检索 → LLM 使用。

设计理念原话：**"与其让 AI 遵守人的规则，不如让 AI 学会自己生产规则。"**

这一阶段暴露的新问题：多跳关系检索效果有限。例如「用户 → 订单 → 商品」三跳关系，靠知识库检索答不上来。这直接引出第三阶段。

### 第三阶段：轻量级本体图谱

设计原则：**让 AI 抽取本体图谱，最终由专家确认。**

本体图谱的三层价值：

| 层级 | 回答的问题 | 能力 | 局限/说明 |
|------|-----------|------|----------|
| L1 · 连接 | 知道「和谁有关」 | 用户→观看→内容多跳可达；解决跨表、跨实体「找不到」 | 仅连接层：有关系，不解释为什么 |
| L2 · 理解 | 懂得「业务是什么」 | 概念、属性、规则一起入图；口径、字段归属、规则都可查；Agent 直接读到语义，不用猜 | — |
| L3 · 推理 | 推出「结果会怎样」 | 沿 isa / about / 规则约束推导；口径自动展开到事实、维度、过滤条件；从「查数」到「下结论、讲原因」 | — |

原文的定位判断：**知识库回答「是什么」；本体图谱靠 L2/L3 真正回答「为什么、会怎样」——关系只是起点，不是终点。** "图谱的价值不在关系本身，而在关系之上长出来的业务判断。"

### 架构总览

演讲给出的大数据 AI 平台架构（P10）分为四层：

1. **统一入口层**：大数据 AI 平台 / Zwork 统一工作台 / Codex / Cursor / Workbuddy，承担一站式入口、任务调度、对话交互、结果展示。
2. **大数据 CLI**：安全管控、任务分发。
3. **Agent 层**：数据分析 Agent（数据分析·报表生成·洞察）、AB 实验 Agent（实验设计·数据分析·结论）、画像 Agent（用户画像·标签体系·画像洞察）、埋点 Agent（埋点分析·事件追踪·效果评估）；左侧为「AI 专家任务承接」。
4. **能力三层**：
   - **有资源 · 数据能力供给**：SQL 查询服务、计算引擎、存储引擎；
   - **懂业务 · 业务知识理解与映射**：知识检索服务 → 知识库、本体图谱、业务逻辑映射、产品功能映射；
   - **会干活 · 能力复用与任务执行**：数据 SKILL 市场。

底层数据来源包括：数据平台；表元数据、数仓代码、血缘关系；数据仓库 + 数据产品（业务数据）；业务产品 + 数据产品（业务应用）；埋点元数据、产品 PRD；以及「数仓 + 数据产品 + 数据分析 + 业务同学」的联合供给。

## 关键工程做法

### 知识库：混合检索五步

1. **用户查询**：自然语言提问，如「最近一周 DAU 变化情况」；
2. **并行召回**：全文检索（一路管准）+ 向量检索（一路管懂）同时发出；
3. **WRRF 加权融合**：两路 rank → `1/(k+rank)` 加权求和，不看原始分，只看排名；
4. **分数优化**：名称匹配加权（精确 / 包含 / 别名）、按知识类型独立检索；
5. **交给 LLM**：只送最相关的知识，上下文变干净，token 消耗同步下降。

一句话：**全文管准，向量管懂，WRRF 管谁排在前面。**

### WRRF 融合细节

```
WRRF_score = vectorWeight × 1/(k + vector_rank) + fulltextWeight × 1/(k + fulltext_rank)
```

只在一路出现的 chunk 只累加那一项；两路都召回到的 chunk 两项都加。

召回流程：

- **向量路**：`1 - COSINE_DISTANCE(查询向量, embedding)` 降序取前 N → 得 rank；
- **全文路**：`MATCH(...) AGAINST(... IN NATURAL LANGUAGE MODE)` 降序取前 N → 得 rank；
- **类别权重钩子**：进入 RRF 前，分数 × 类别权重 → 重排 → 重赋 rank（影响排名，不做分数后处理）；
- **calculateWRRF**：两路 rank 代入公式累加 → 按 WRRF 分数降序取 top-K。

参数与配置（P12）：

| 参数 | 默认值 | 环境变量 |
|------|--------|---------|
| vectorWeight | 1.0 | WRRF_VECTOR_WEIGHT |
| fulltextWeight | 1.0 | WRRF_FULLTEXT_WEIGHT |
| k | 60 | WRRF_K |
| perPathTopK | 20 | WRRF_PER_PATH_TOPK |

原文说明：k=60 是标准 RRF 经验值，抹平头部排名分差，让低排名结果也有贡献空间。核心判断：**融合的是排名不是分数——谁被两路同时认可，谁就排得靠前。**

### 定制化切片

| 知识类型 | 切片粒度 | 切片内容 |
|---------|---------|---------|
| 指标 | 一指标一切片 | 指标名称、描述、完整口径、物理表映射 |
| 表元数据 | 表级 + 字段级 | 表级：表名、描述、业务域；字段级：字段名、字段类型、业务描述 |
| SQL 模板 | 按语句切分 | SQL 语句、CTE 语句分别成片 |
| 业务知识 | 通用 Markdown 切片 | 通用逻辑兜底，兼容未知类型 |

原则：**"切片不是切得越碎越好，是按知识的形状下刀。"**

### 本体图谱：轻量化设计

逻辑层定义「是什么」，物理层只锚「去哪查」。

**逻辑层（本体）**：

| 概念 | 定义 | 对应 | 落表 |
|------|------|------|------|
| 实体 Entity | 业务对象：用户、内容 | OWL Class | dim_* 维度表 |
| 事实 Fact | 行为事件：观看、付费 | OWL Class | dwd_* / dws_* |
| 值概念 ValueConcept | 受控词表：性别、平台等枚举 | OWL Class | — |
| 属性 Attribute | 数据属性：字段名 / 类型 / 取值，实体与事实共用 | OWL DataProperty | — |
| 规则 Rule | 业务规则：条件分支、口径约束、衍生属性 | OWL Rule / SWRL | — |

本体论映射：概念 → `owl:Class`；属性 → `owl:DatatypeProperty` / `owl:ObjectProperty`；规则 → SWRL Rule（业务规则）。

**物理层（锚点，每个节点自带）**：

- 表锚点 `table_ref` / `table_refs`：实体、事实各自挂表（dim_* / dwd_*），多表按 priority；
- 字段映射 `column_maps`：事实用 measures + dimensions，度量与维度落到物理列；
- 取值与口径 `value_source` / `metrics`：枚举取值归值概念，指标口径挂在事实上；
- 属性锚点 `attribute.column_maps`：实体用 attributes；column → columns → column_maps；
- 规则锚点 `rule.inputs` / `cases`：规则声明输入列与条件分支，按属性路由不同列。

**关系层**：ObjectProperty，包括 isa 继承、about 关联实体、has_dimension 关联维度、自定义关系（遵循 OWL，自由定义）。

**示例链路（真实字段）**：

```
User(dim_user) --has_dimension(member_id)--> 观看事实(dwd_user_view_content) --about--> Content(dim_content)
事实自带表与度量：table_ref = dwd_user_view_content；
measures.viewDuration → column: view_duration；
指标口径 SUM(view_duration) 同样挂在事实上。
```

### 本体图谱：轻量级技术架构

| 维度 | 做法 | 细节 |
|------|------|------|
| 存储 | 核心数据用两张表承接 | nodes + edges；完整定义存 JSON（节点/边的定义整体放 properties 字段）；版本是 YAML 快照（快照存 BOS，DB 只留版本元数据） |
| 计算 | 递归 CTE 多跳 | `WITH RECURSIVE` 逐跳展开节点与边；邻居 1–4 跳（默认 1 跳，支持 in/out/both 与关系过滤）；路径默认 4 跳，上限 6 跳，超出返回未找到并给提示 |
| 接口 | MCP 统一出口 | 只读 7 个 `kg_*` + 编辑 5 个 `kge_*`；双视图返回（agent 视图瘦身给 LLM，full 视图给人看）；返回体带 `next_hint` 引导下一步查询 |

**轻量化的边界**：只维护节点自带的锚点，不做全量物理建模；查询侧用 Schema 匹配兜底；图计算限定在 4 跳内（路径上限 6 跳），换取可预期的查询耗时。

### 本体图谱：管理维护

流程：`kge_pull` 拉取版本 → LLM 编辑（加实体、补列映射）→ `kge_push` 生成预览版本 → 差异对比（可视化）→ 人工确认发布。

- **版本管理**：三段版本号——正式 X.Y｜工作线 X.(Y+1)｜预览 X.(Y+1).N；快照归档可回滚（版本 YAML 存 BOS，DB 存元数据）；状态机——正式版 published/archived，预览 draft/published/abandoned。
- **质量与审核**：图谱校验 `kg_validate` + 导入校验（缺表锚点、规则错误）；人工把关（LLM 只产出预览，发布权在人类审核）；可视化审核（图谱结构图 + 版本/预览详情，发布确认与回滚在同处完成）。

原则：**版本即契约——Agent 只读正式版本，所有编辑先落预览，避免误改线上图谱。**

| 原痛点 | 效果 |
|--------|------|
| 取数依赖分析师、等待久 | 等待时长从天级降到分钟级 |

### 真实测评

- 题集 = 核心指标改写问题 + 业务用户真实问题，两类题集合并计算；整体准确率 **95%**（P22）。
- 业务用户真实问题：知识库阶段 **70%**，本体图谱 + 知识库阶段 **92%**。原文在两者之间标注「提升 11pp」——与 70%→92% 的差值不一致，此处按原文呈现，具体口径**不确定**。
- 测评方法：题集来源为业务真实提问埋点数据；答案由专家团队标注；判定方式为 AI 辅助判断（意图匹配 + SQL 等价）。
- 评测链路已脚本化：真实提问提取 → 专家标注用例 → LLM 判定 → 报告归档；同一套用例可重复回归，结论可复核。

## 经验与边界

### 三条方法论

| 原则 | 内涵 | 回去怎么用 |
|------|------|-----------|
| 定制化切片 | 切片按知识的形状 | 先盘点知识类型，别用一套切片打天下 |
| 混合检索 | 检索按业务的优先级 | 给表资产分权重，核心宽表、认证表先进知识库 |
| AI 原生 | 图谱按问题的规模 | 先量化查询跳数，再决定要不要上图谱 |

总结句：**"切片按知识的形状，检索按业务的优先级，图谱按问题的规模——别让通用方案替你做判断。"**

### 两个落地挑战

**挑战一：四类知识共用一套切片。**

- 起因：四类知识初期共用一套切片 + 单一向量检索，先求上线。
- 踩坑：噪音最大的是表元数据——问「DAU 从哪张表取」，回来几十个同名字段，答非所问。
- 定位：表结构被按句子切碎了；核心宽表、认证表同权重，业务优先级没进检索。
- 改法：① 按知识类型定制切片，通用逻辑兜底；② 表元数据分层：先表级、再字段级；③ 表按业务优先级增加权重。

原文金句：**"上线那天是最便宜的一天，真正贵的是之后每天的 bad case。"**

**挑战二：差点上了图数据库。**

- 起因：多跳问题在纯向量检索下答不上来，第一反应是上重量级图数据库。
- 经过：原型验证后发现真实查询集中在 1–3 跳，图数据库的运维成本远超收益，最终方案被否掉。
- 改法：① LLM 抽取实体与关系，人工审核后入库（实体：指标、表、字段、业务概念；关系：指标依赖、表关联、字段引用、业务归属）；② 轻量图存储 + AI 友好的自然语言查询接口；③ 只承诺支持 1–3 跳查询；④ 图谱结果与知识库检索融合。
- 沉淀：判据变了——不再问「哪个技术更先进」，而是问「我们的问题有多大」。**"技术选型最贵的坑，是用先进性做判据，而不是用问题规模做判据。"**

### 避坑清单（原文称"交过的学费"）

1. 知识建设，人工参与的比例有多大？→ 关键不是比例，而是人工确认放在流程的哪个位置——**前移是成本，后移是事故**。
2. 切片策略，是四类知识共用一套，还是按类型定制？→ 共用一套会有较大噪音。
3. 技术方案，是按问题规模选的，还是按技术先进性选的？→ 我们真实查询集中在 1–3 跳。

### 展望：从「辅助人工构建语义」到「全自动构建知识飞轮」

路径：用户问题 → 判断知识是否缺失（检索本体图谱、知识库）；不缺失则回答用户问题，缺失则进入知识自动构建（自动构建知识并回测，人工审核后正式入本体图谱、知识库）。

未来方向：让本体图谱、知识库主动发现知识缺失，并构建新知识。原文收束：**"AI 原生不是技术选择，是设计理念。"**

### 边界与不确定项
