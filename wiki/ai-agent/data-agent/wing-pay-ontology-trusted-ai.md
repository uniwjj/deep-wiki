# 翼支付：本体落地对金融可信 AI 的挑战

> 核心主张：**口径只能有一份，存取可以有两种。** 语义映射与对象存储各有优劣，成本一个付在读、一个付在写；选哪条取决于时效、数据量、查询形态、回写、变更频率和读写比。「可信」落到工程上是三件事：**口径唯一、结论可追溯、过期不静默。**

来源：DACon 2026 北京站「金融可信 AI 实践」分论坛，徐德华（天翼征信有限公司总经理助理）《本体落地对金融可信 AI 的挑战——语义映射与对象存储的取舍》。PPT 标题为「翼支付」，页面署名单位为天翼征信有限公司。

## 背景与问题

### 数据访问的老分叉：同一份数据，两种负载

演讲先回到 OLTP 与 OLAP 的老分叉。演讲的判断是——**分叉的根源是负载不同，不是技术偏好。**

| 维度 | OLTP | OLAP |
|------|------|------|
| 面向 | 单个业务对象 | 大量记录的聚合 |
| 典型问题 | 这份合同现在什么状态？ | 上季度各地区交易额合计？ |
| 查询形态 | 点查 + 少量关联 | 大范围扫描 + 分组聚合 |
| 时延 | 毫秒 | 秒到分钟 |
| 写入 | 高频小写入，状态随时变 | 批量追加，基本只读 |
| 数据模型 | 规范化实体与关系 | 宽表 / 星型 + 指标口径 |

历史上发生过什么：

> 没有一个系统能同时把两种负载做好 → 分库 + ETL → 报表和业务系统「对不上数」 → 统一指标层 / HTAP

这条链条的终点是：报表和业务系统「对不上数」；第 8 页进一步点明：OLTP / OLAP 分库后最大的麻烦不是性能，是口径对不上。

### 智能体把两种负载塞进了同一个任务

演讲用一个关联研判任务说明：一次任务里会连续出现四种访问。

| 步骤 | 问题 | 访问模式 | 代价特征 |
|------|------|----------|----------|
| 1 偏离检测 | 哪些交易价格明显偏离同类均值？ | OLAP，全量扫描 + group by | 结果是聚合值 |
| 2 关联穿透 | 交易双方有没有股权或人员关联？ | 多跳遍历，沿关系走 3–5 跳 | 中间结果随度数指数增长 |
| 3 状态读取 | 合同签了没有、距发起隔了几天？ | OLTP 点查，按主键读当前状态 | 读当前状态 |
| 4 结果回写 | 标记待核查，派发复核 | 写入 | 新增一条带来源的事实（状态 + 证据） |

演讲用一句话概括：

> **一次研判 = 分析 + 穿透 + 状态 + 回写。**

人在 BI 和业务系统里是分开做这四件事的；智能体要在一个上下文里连着做。因此演讲给出一个方法论要求：

> 所以做本体 + 智能体之前，**先拆目标任务，看清负载画像**。

先拆目标任务，看清每一步的负载，再谈路线选择。

### 猜想：本体的分叉，也许是老分叉在语义层的重演

演讲提出一个核心问题：

> **本体是一层「翻译」，还是一份「数据」？**

由此分成两条路线：

| 对比项 | 语义映射 | 对象存储 |
|--------|----------|----------|
| 语义绑定时机 | 语义在查询时绑定 | 语义在写入时绑定 |
| 本体的形态 | 本体是一层元数据 | 实例、关系、状态物化成对象 |
| 执行方式 | 问题翻译成对数仓的 SQL，数据不搬家 | 智能体直接操作对象 |
| 技术血统 | OLAP 血统 · 近似指标层 / 语义层 | OLTP 血统 · 代表：Palantir Ontology |

演讲同时划出类比的边界：

> **OLTP / OLAP 分的是负载，本体分叉分的是语义何时绑定到数据——负载决定绑定时机。**

这句话把两条路线从「技术偏好」拉回到「负载特征」：不是哪种本体更先进，而是任务负载决定了语义应该在读时绑定还是写时绑定。

## 方案/架构

### 先分层：概念层管对不对，实例层管快不快

演讲给出的架构决策是先分层：

> **口径只能有一份，存取可以有两种。**

原因是：OLTP / OLAP 分库后最大的麻烦不是性能，是口径对不上。

| 层 | 管什么 | 变化特征 | 谁改 | 验收标准 |
|----|--------|----------|------|----------|
| 概念层 · 唯一一份 | 对象 · 属性 · 关系 · 口径 · 规则 · 决策逻辑 | 低频，按版本发布 | 业务专家 + 建模师 | 口径一致、可追溯 |
| 实例层 · 可以有两种实现 | 亿级实例 · 实时状态 · 历史链路 · 结果回写 | 高频，系统自动同步 | 系统 | 查得到、查得快、查得准 |

概念层向下生成两种实现：

- **语义映射**：查询时翻译成 SQL
- **对象存储**：写入时物化为对象

两层各管一件事：**概念层管对不对，实例层管快不快。**

### 口径要带生效时点

演讲用一个金额门槛类口径说明生效时点问题：

> 一个金额门槛类口径，新规则生效前后不同。判断一笔历史业务，要按「业务发生时」匹配口径版本，而不是用最新版。

实现方式是：

- 口径定义带 `valid_from` / `valid_to`
- 查询时按事实发生时间做 **as-of 匹配**

### 混做的两种结局

演讲用两个反例说明「概念与实例混建」的代价：

| 结局 | 演化链 |
|------|--------|
| A：实例塞进知识库 | 图谱膨胀 → 推理变慢 → schema 不敢改 |
| B：概念跟着表结构走 | 换一张底表 → 口径跟着变 → 智能体无感知 |

结局 A 的链条是：实例和概念放在同一个图谱里，实例一多，推理就慢，最后连 schema 都不敢改。结局 B 的链条是：概念绑定在表结构上，底表一换，口径跟着变，而智能体感知不到。

演讲还给出一个「从一层到两层」的常见演化路径：

| 阶段 | 状态 | 问题 |
|------|------|------|
| 起步：一层 | 「企业—股东—交易」的定义和实例放在同一个图谱，规则直接写在实例上 | 规模小时很顺手——早期这样最快 |
| 实例到千万级 | 改一次「关联方」定义 → 全量重跑推理；同一口径被多个场景各复制一份 | 规模变大后的状态 |
| 拆成两层 | 定义只改一处；实例层只管算和存；口径版本可追溯 | 分层后的状态 |

演讲对这段的表述是：规模小时一层很顺手——早期这样最快；到实例千万级后，才拆成两层。

## 关键工程做法

### 正面对比：各自赢在哪、输在哪

演讲用一张 11 维对比表把两条路线的取舍摊开。高亮的是相对占优的一侧。

| 维度 | 语义映射 | 对象存储 |
|------|----------|----------|
| 上线速度 | 快，周级 | 慢，要建同步链路 |
| 存储冗余 | 无 | 有，全量或核心子集 |
| 多跳穿透 | 弱，跳数一多 SQL 爆炸 | 强，关系已物化 |
| 查询时延 | 取决于数仓，秒到分钟 | 毫秒到秒 |
| 状态与回写 | 无处安放 | 原生支持 |
| 口径独立性 | 受底层表结构牵制 | 独立，但要对账 |
| 一致性 | 天然一致 | 同步延迟、增量出错 |
| 真值归属 | 源系统 | 要明确写死 |
| 执行位置 | 下推到数仓引擎 | 对象库 / 图引擎本地执行 |
| Schema 演进 | 改映射规则即可 | 迁移 + 回灌历史数据 |
| 权限与审计 | 继承源库权限 | 要在对象层重建行列级权限 |

这张表可以压缩成一句：

> **映射输在穿透和回写，对象存储输在一致性和成本。**

### 代价付在哪一端：读的时候，还是写的时候

演讲把两条路线的差异归结为「成本付在何时」，并类比数据库里的范式 vs 反范式、视图 vs 物化视图。

**语义映射：每次读都付**

> 源数据 → 语义 → 智能体
>
> 翻译 + 跨表关联 + 现场计算
>
> k 跳 ≈ k 次自连接，中间结果 ≈ 度数^k

**对象存储：每次写都付**

> 源数据 → 语义 → 智能体
>
> 同步链路 + 存储 + 增量一致性
>
> 写放大 ≈ 依赖扇出；读只付访问到的边

### 对象存储绕不开的问题：物化结果可能短暂过期

对象存储绕不开物化结果短暂过期。演讲给出两种处理方式：

| 做法 | 表现 | 后果 |
|------|------|------|
| ✗ 不带状态 | 股东已变更，对象库尚未同步完，系统回答「两者无关联」 | 一个错误的确定性结论 |
| ✓ 带口径状态 | 变更后标记「收敛中」，收敛前不给确定性结论，回答「暂未发现关联，股权数据同步中」 | 监管这类要求可追溯的场景，差别就在可信与否 |

这条对比给出的「可信」含义是：**系统要知道自己什么时候不最新，并在收敛前不给确定性结论。**

### 六个维度：什么样的需求走哪条路

演讲用六个维度区分情况：

| 维度 | 偏向语义映射 | 偏向对象存储 | 背后的原因 |
|------|--------------|--------------|------------|
| 时效要求 | T+1、小时级可接受 | 秒级、实时 | 映射的时延受数仓现场计算拖累 |
| 数据量 | 明细量大，只要聚合结果 | 核心对象可控，关系密集 | 物化的存储和同步成本随数据量增长 |
| 查询形态 | 扫描 + 聚合 | 点查 + 多跳（≥ 3 跳） | 多跳在 SQL 上是多次 join |
| 回写需求 | 只读 | 要记录状态、处置结果 | 映射没有地方放新产生的事实 |
| 变更频率 | 源表结构、口径常变 | 结构稳定 | 物化后每次变更都要重算回灌 |
| 读写比 | 查询少、问题分散 | 同一批对象被反复查询 | 物化是用一次写入换多次读取 |

演讲还给了一个粗略的直觉公式：

> **重复读取次数 × 每次现场计算的代价 ≫ 变更次数 × 每次变更要刷新的范围 → 物化划算；反之映射更省。**

### 一张情况地图

演讲把六个维度压缩成二维地图：横轴是查询形态（扫描聚合 → 点查多跳），纵轴是时效与状态要求（离线只读 → 实时有状态）。

| 象限 | 典型场景 | 判断 |
|------|----------|------|
| 聚合 + 离线只读 | 指标问数 · 报表 · 定期报送 | 语义映射比较自然 |
| 聚合 + 实时 | 实时指标监控 | 更像流计算问题？两条路都未必最优 |
| 多跳 + 离线只读 | 历史关联排查 · 专项回溯 | 看数据量和跳数，两条都有人走通 |
| 多跳 + 实时有状态 | 关联穿透 · 实时预警 · 处置闭环 | 对象存储比较自然 |

演讲标注：实线覆盖的左下、右上两个象限是「比较有把握」的；虚线覆盖的另外两个象限「待讨论」。

使用方法也给了：

> 把自己的智能体任务拆开，每一步点到图上，看点主要落在哪。

### 两种比较有把握的情况

演讲特别声明：用「可能更合适」而不是「应该」——这是目前的经验，不是定律。

**情况一：分析为主、口径常变 → 语义映射**

| 项 | 内容 |
|----|------|
| 典型需求 | 「上季度各分支机构某指标同比」，扫描 + group by |
| 为什么 | 问题分散，结果是聚合值；数据不搬家，口径一改立即生效 |
| 前提 | 映射规则本身版本化 |
| 要留意 | 第一个稳定出现的多跳需求，可能是负载开始迁移的信号 |

**情况二：穿透与处置为主 → 对象存储**

| 项 | 内容 |
|----|------|
| 典型需求 | 「A 的实际控制人还控制了哪些与 A 同场出现的主体」，k 跳遍历 + 集合求交 |
| 为什么 | 3–5 跳反复查询、要秒级返回；研判结果要回写成新的事实 |
| 前提 | 核心对象边界清楚、数据量可控、真值归属写清楚 |
| 要留意 | 同步链路的运维成本，以及口径状态标注 |

### 灰色地带：还没想清楚的几种情况

演讲列出三个灰色地带：

| 情况 | 目前的倾向 | 不确定的地方 |
|------|------------|--------------|
| 多跳但离线，数据量很大（百亿级关系） | 映射 + 预计算部分路径 | 物化成本很高、查询频率又低——够不够？ |
| 要多跳，口径又常变 | 只物化关系骨架，口径计算留在查询时 | 每次口径调整都要回灌吗？骨架和口径怎么切？ |
| 两种负载都很重 | 先确认是不是真的两种都重 | 两套都建、一个入口——两套链路和持续对账的代价值得吗？ |

页面最后向现场提问：「灰色地带里，你们是怎么选的？」演讲把这些称为「还没想清楚」的情况，并列出「目前的倾向」与「不确定的地方」。

## 数据与效果

演讲给出三个案例，其中案例二有明确的量化结论。

### 案例一：一个监管场景的本体实践

四个模块按访问模式分工：

| 模块 | 访问模式 | 职责 |
|------|----------|------|
| 本体语义基座 | 过滤 / 点查 + 多跳遍历 | 统一对象定义；按属性取数、沿关系探查 |
| LLM Wiki | as-of 检索 | 文本知识编译成可链接条目，按生效时点和适用范围匹配 |
| 推理引擎（OAG） | 受控调用 | 智能体只发受控调用，长链检索和确定性计算交给引擎 |
| 统一分析入口 | 轨迹 + 回写 | 记录推理轨迹与证据来源，人工反馈作为新事实回写 |

四个模块与第 5 页任务链一一对应：

> 偏离检测（扫描聚合）→ 关联关系（多跳遍历）→ 签约时点（点查状态）→ 风险落卡（回写）

同一个监管场景里，四个模块分别采用不同的访问模式，最后用统一分析入口串起来。

### 案例二：一次研判怎么走完

三步流程：

1. **沿 schema 探索路径**：读元数据决定走哪些关系
2. **按关系类型分别多跳遍历**：主体、流程、资金等关系分别遍历，结果在对象层合并
3. **结论写回为新对象**：结论 + 证据链 + 条文依据

量化结果有两项：

| 指标 | 结果 |
|------|------|
| 风险发现类型 | 从 4 类 5 子类扩展到 12 类 42 子类，补足既有规则未覆盖的风险类型 |
| 关键事实判断准确度 | 相较纯大模型方案 +80% |

演讲对「可信」的工程解释是：

> **每个结论都能沿 provenance 回到源数据。**

除风险类型计数外，+80% 是案例二中唯一的效果百分比。原文只说明它是「关键事实判断准确度（相较纯大模型方案）」，没有给出评测集规模、评分标准、置信区间或统计方法。

### 案例三：从单场景到平台

中国电信「星海 · 智能动态本体平台」把单域能力拆成八个组件式服务：

> `onto-schema`、`onto-wiki`、`onto-graph`、`onto-FL`、`onto-loop`、`onto-import`、`onto-domain`、`onto-monitor`

演讲的结论是：

> 单域跑通后，把能力拆成组件：下一个域从组件起步，而不是从零起步。

## 经验与边界

### 对智能体来说，接口最好长得一样

> 底层走哪条路不让智能体感知——将来改道，智能体侧不用重写。

调用链分四段：

| 层 | 内容 |
|----|------|
| 智能体 | 调用统一接口 |
| 对象查询原语 | 过滤 · 遍历 · 聚合 · 动作 |
| 编译层 | 按对象路由，下推到对应后端 |
| 后端 | 语义映射 → SQL 下推到数仓；对象存储 → 图查询 / 对象 API |

一次供数分四步：

1. **返回概貌**：本体先返回对象概貌（元数据），智能体选主对象
2. **按任务剪枝**：只给最小必要的属性和关系
3. **受治理取数**：只调原语，不自己拼 SQL、不自己遍历图
4. **明确降级**：上下文不足、超时或口径收敛中 → 人工确认或明确告知

演讲留下一个开放问题：

> 接口统一能把「不可逆」降低到什么程度？我们还在观察。

### 怎么证明建得比原来好：交付物与指标

每个业务域交付五件套：

| 交付物 | 内容 |
|--------|------|
| 本体片段 | 含实现方式：物化 / 映射 |
| 规则库 | 带版本和生效时点 |
| 案例库 | 已核实的正反案例 |
| 已验证查询 | 高频问题的标准查询 |
| 评测集 | 专家金标准 + 盲评，保留 hold-out |

每个正向指标配一个反向指标：

| 正向指标 | 配对的反向指标 |
|----------|----------------|
| 研判准确率 | 单次任务成本 / 时延 |
| 风险发现数 | 误报率 / 人工复核工时 |
| 穿透查询时延 | 同步延迟 / 存储成本 |
| 对象覆盖数 | 口径冲突数 |

跨域复用率也给了两种算法：

- ✗ 复用对象数 / 总对象数：容易虚高
- ✓ 第 N 个域的交付人力相对第 1 个域下降多少

### 常见的坑

演讲强调「当时为什么会这么做」比解法更有参考价值：

| 坑 | 当时为什么会这么做 | 现在的做法 |
|----|--------------------|------------|
| 概念与数据混建 | 早期规模小，一层最快 | 先拆两层，口径只留一份 |
| 只看到问数需求就定了实现 | 立项时只有分析类需求 | 先拆目标任务，看清负载再选 |
| 物化结果静默过期 | 默认同步链路可靠 | 失效传播 + 口径状态标注 |
| 把「混合」当默认答案 | 觉得两边都要更稳妥 | 先确认两种负载是否真的都重 |
| 建成了证明不了 | 验收时只有演示 | 金标准题库 + hold-out + 反向指标 |

### 小结与开放问题

演讲的四个判断：

1. **口径只能有一份，存取可以有两种**
2. **语义映射与对象存储各有优劣：成本一个付在读，一个付在写**
3. **选哪条，取决于时效、数据量、查询形态、回写、变更频率和读写比**
4. **「可信」落到工程上是三件事：口径唯一、结论可追溯、过期不静默**

留给现场的三个问题：

- 智能体的负载，会不会随着用法成熟而迁移——从问数走向研判？
- 统一接口，能把「不可逆」降低到什么程度？
- 灰色地带里，大家是怎么选的？

### 边界

- 这是**单一机构（天翼征信）的落地经验**，演讲明确说「这是我们目前的经验，不是定律」；六个维度、情况地图、两种有把握的情况都来自这份经验。
- 案例二的 **+80%** 只说明是「关键事实判断准确度（相较纯大模型方案）」，原文没有给出评测集大小、评分口径、统计方法或置信区间，不能当作可复现的基准。
- 案例一的四个模块、案例三的八个组件均是产品/平台截图与组件名，原文未给出部署规模、成本数据或时延数字。
- 「翼支付」出现在 PPT 标题中，讲者署名单位为天翼征信有限公司；两者关系原文未展开。
- 演讲没有回答灰色地带的三个问题，也没有给出「两种负载都很重」时的最终方案；这些属于开放问题，不是已结论。
