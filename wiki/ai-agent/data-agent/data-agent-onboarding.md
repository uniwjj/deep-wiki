# Data Agent 上岗标准：30 分钟上岗与四个上岗能力

> 核心主张：**Agent = f(Context)**。当模型能力快速拉齐、Harness 工程逐渐标准化之后，Agent 的差异收敛到 Context。企业对待 Data Agent 的方式也要从"买工具"变成"招员工"——**上线，看功能是否可用；上岗，看工作能否交付**。新标准是 **30 分钟上岗**，对应四个上岗能力：**摸得清、问得准、干得对、学得会**。

来源：DACon 2026 北京站演讲《30 分钟上岗：企业"招聘" Data Agent 的新标准》，演讲人周卫林（Aloudata 创始人 & CEO，原蚂蚁集团数据平台部总经理、原蚂蚁集团研究员 P10）。

## 背景与问题

### 从 Agent = f(LLM + Harness + Context) 到 Agent = f(Context)

演讲用一张"封装程度 × 时间"的图描述 2023–2026 的收敛：

- **技术范式层**：ReAct → Tool Calling → Planning；
- **开发框架层**：LangChain → AutoGen / LangGraph；
- **Agent 应用层**：Claude Code / OpenClaw / CodeX。

两条趋势同时发生：**模型能力快速拉齐**（左图引用 Artificial Analysis 的"帕累托前沿"：2026/03 全球主流厂商不断推进帕累托前沿，模型综合能力 vs 每任务成本，Claude Sonnet 4.6(max)、Gemini 3.1 Pro Preview、GPT-5.4 mini(high)、MiniMax-M2.7、Gemini 3.1 Flash-Lite 等分布其间），以及 **Harness 工程逐渐标准化**（封装程度沿 Agent 应用 → 开发框架 → 技术范式逐级上升）。

结论：当 LLM 与 Harness 都成为可获得的公共能力，**Agent 的差异就落在 Context 上**。

### Context 是什么：Agent 时代的决策基石

演讲用四层结构定义 Context：

| 层次 | 判断 |
|------|------|
| 平台承载 | **语义平台是分析决策 Context 的最高知识密度的表达方法** |
| 建设方法 | **Context Engineering 首先是信息学，其次是工程学** |
| 要求与现实 | 决策要求：Perfect decisions need perfect context；现实条件：Context is never complete、Context is alive |
| 本质定义 | **Context 不是能力，是事实**；**Context 是 Agent 的工作现场** |

这四句是整场演讲的世界观：Context 不是 prompt 技巧，而是企业事实的组织方式；它永远不完备，且在使用中不断生长。

### 从"上线"到"上岗"：两个不同的命题

演讲用"上个月销售为什么下降了？"对比两种工作方式：

| 产品已上线（人组织工作） | Agent 要上岗（人与 Agent 协作） |
|------------------------|-------------------------------|
| 人明确需求 | 业务同事交办任务（确认口径、采用结果） |
| 人拆解步骤 | Agent 探查并澄清 |
| 人操作软件（查数据、算指标、画图） | Agent 制订工作计划 → 调用工具 |
| 人核验解释 | Agent 核验并交付 |

原文判断：**上线，看功能是否可用；上岗，看工作能否交付。**

### 从"买工具"到"招员工"

| 买工具 | 定功能（做选型） | PoC（验功能） | 上线（部署软件） | 试运行（投产验证） | 验收（正式运行） |
|--------|----------------|--------------|----------------|------------------|----------------|
| 招员工 | 定岗位（招候选人） | 面试（验能力） | 入职（报到） | 试用（做真实工作） | 转正（承担岗位职责） |

原文判断：**Agent 是数字员工，企业不再是"买工具"，而是"招员工"。**

这套映射的方法论含义（按原文字面）：企业先"定岗位"（招候选人），再"面试"（验能力），随后"入职"（报到）、"试用"（做真实工作）、"转正"（承担岗位职责）；对应工具侧的"定功能（做选型）→ PoC（验功能）→ 上线（部署软件）→ 试运行（投产验证）→ 验收（正式运行）"。演讲没有展开每个阶段的验收标准与时长，只给出阶段对应关系。

### Agent 上岗，企业面临哪些新挑战

三类挑战 + 一个底层问题（P12）：

- **上岗**：如何快速上手真实工作？
- **协作**：如何学会双向沟通？
- **成长**：如何越干越好？
- **信任**（贯穿三者）：如何让人敢用 Agent 的工作成果？

## 方案/架构

### 新要求：像数据分析师一样入职，30 分钟开始上岗工作

演讲给出的标准是 **30 分钟上岗**——不是"30 分钟部署完成"，而是像一位数据分析师入职一样，30 分钟开始真正的工作。支撑这一标准的不是单点功能，而是四个上岗能力。

### 四个上岗能力的总逻辑

原文一句话概括：**把企业知识变成岗位理解，把用户需求变成明确任务，把明确任务变成可信结果，再把工作经验留在企业。**

| 能力 | 定位 | 在流程中的动作 | 产出 |
|------|------|--------------|------|
| ① 摸得清 | 自适应企业环境，自主探查数据 | 读取企业 Context | 形成岗位理解 |
| ② 问得准 | 自主澄清业务需求 | 补齐任务上下文 | 补齐任务上下文 |
| ③ 干得对 | 自主规划，可信执行 | 调用与核验 | 使用并验证上下文 |
| ④ 学得会 | 自学，受控自进化 | 确认后更新 | 沉淀经过确认的经验 |

底座是**企业 Context：语义层 + 知识库**。四个能力与底座之间形成循环：读取 → 补齐 → 调用与核验 → 确认后更新 → 用于下一个任务。原文收束：**Context is alive：在工作中被使用、被验证，也不断生长。**

### 一张图看懂 Data Agent 如何像分析师一样工作

演讲附了一张六泳道流程图（P28），泳道为：业务用户 / Aloudata Agent / 大模型 / CAN 指标平台 / 可选能力扩展 / 数据平台。四个环节与关键动作：

**环节一 · 摸得清**——先认识人、再认业务、语义、数据和权限：

- 业务用户提出业务问题；
- Agent 验证身份权限，组装业务与语义上下文，提交问题与可用分析技能、工具；
- Agent 启用问数技能；
- 向 CAN 指标平台检索指标、维度与语义模型，返回语义、可选值与数据覆盖；
- 大模型理解意图，拆解分析任务。

**环节二 · 问得准**——不急着取数，先把模棱两可收成唯一口径：

- Agent 返回候选指标与维度；
- 提供可用范围与能力边界；
- 存在歧义时发起人工确认；
- 判断指标、时间、维度、筛选和分母是否唯一；
- 一次性确认业务口径，带确认结果恢复执行。

**环节三 · 干得对**——在真实权限内执行，用可追溯证据交付。四个子步骤：

1. **查得出**：生成指标查询语句并提交查询意图；查询前检查权限、语法、时间范围、行数和成本；携带企业与真实用户身份提交正式查询；解析指标口径与权限，生成查询计划并访问数据源；返回数据行、字段、行数和数据时间；返回标准化查询结果，附数据、口径、数据依据与可复算计算的数值。
2. **算得准**：统一计算规则，确保结果稳定、可复算；按固定规则计算，必要时追加受控查询；对齐时间粒度、维度、单位和缺失值处理；可调用外部工具或其他智能体（不改变分析口径）。
3. **验得过**：交付前独立核验，让结论与证据一致；提交候选答案，发起独立核验；组装候选结论与数据依据；数据校验助手比对数据来源、加工链路、查询含义；同时核对时间、维度、公式、单位与数据引用；未通过则退回具体修订项，修订后再次核验；通过则形成已核验答案。
4. **说得清**：不只给结论，也讲清口径与依据；组织自然语言结论、图表与口径说明；交付结论、图表、口径说明、数据依据与可下载明细表；支持追问、纠正、紧接着导出。

**环节四 · 学得会**——让一次任务中的反馈，变成下一次做得更好的能力：

- 沉淀答案、过程、反馈与会话状态；
- 把有效经验沉淀为可治理资产（记忆 / 知识 / 技能 / 语义）；
- 经评测、审批、治理，通过后进入正式链路。

## 关键工程做法

### 摸得清之一：自动构建指标语义，将数据资产变 AI 资产

语义构建的完整流水线（P15）可拆为五段：

1. **静态逻辑分析 → 静态逻辑核验**：物理表/字段元数据、维度与指标识别、指标/维度加工逻辑、加工逻辑解析与优化（列级/行级/口径）、物理表关联、码值推导、物理表时间戳、非码值字段常用值推导；随后做可执行流程核验（配方/血缘/联动）、多源异构取数对比、唯一键一致、码值分摊验证与补全、字段常用值类型验证与补全。
2. **指标平迁**：指标、维度、数据集、表关联四类对象的重复判定、冲突消除、迁移建议；人工确认后进入语义挖掘。
3. **语义挖掘**：指标定义（指标、度量、数据集、表关联、SQL 表达式）、维度与实体（维度、实体属性、层级建议、口径建议）、AI Context（同义词、可用场景介绍）、口径与关联（口径 0%/1%、关联关系、维度组合、指标/维度 Agent）。
4. **语义建模**：指标、维度、数据集、表关联、SQL 表达式标准化（方案与函数）；语义决策（语义要素、决策依据、派生/融合、动态计算、维度值、时间窗口、权限、数据权限、对象归属、入库管控、存量兼容、入库推进）。
5. **语义消费**：智能问数、洞察分析、开发助手、资产运营。

底座是**数据语义知识图谱**：元数据管理（业务定义、关联关系、所属系统、其他元数据；父子级血缘、表级血缘）、维度定义（分析维度、衍生维度、一致性维度）、业务实体与群体（主体/访问/属性关系、群体定义、私密标签）、术语与码值（术语澄清、同义/近义映射、口径/业务含义、字段常用值）、数据画像（时间口径、加工逻辑/集合/默认、数据分布）、执行绑定与等价（血缘绑定、等价实现、口径模板）、质量与治理规划（列级数据质量、业务规划、质量稽核、口径线上化、可信数据）。

配套：**语义保鲜**流水线——资产变更监测（资产与口径变更）→ 资产探本（建立版本基线）→ 图谱召回（血缘与语义关联）→ 影响评估（口径与语义关联）→ 审计确认（登记差异）→ 协同变更与验证（链路协同变更）→ 链路更新（图谱与血缘更新）→ 确认回流。另有"初始化及回归数据集"：语义模型结构回归基准、语义生成事实与候选基准、语义决策策略基准、语义消费召回与行为基准、语义执行计划基准。

### 摸得清之二：算子级血缘（三代对比）

| 代际 | 能看清什么 | 看不清什么 |
|------|-----------|-----------|
| 第一代：表级血缘 | 输入表 A/B/C → 输出表 → 字段 T | 内部字段不可见，看不清字段影响 |
| 第二代：列级血缘 | 输入字段 A1–A4、B1–B3、C1–C2 → 输出字段 T | 作业脚本内部仍是黑盒，看不清加工逻辑 |
| 第三代：算子级血缘 | 作业脚本内部白盒化：临时表 D、`A2 + B2`、`inner join`、过滤条件 `C2 > 100`、字段映射 | 看清一切细节 |

原文的三句判断：**100% 精准的表血缘，业务应用也有限；绝大部分厂商不敢承诺准确率；Aloudata 可以交付高精准的算子级血缘。** 价值主张是"像 ETL 架构师一样看代码，提口径"，并"盘点生成血缘 100% 准确的全域数据资产图谱"（后者为产品主张，原文未给第三方验证）。

### 摸得清之三：指标平迁与语义自动配置

**自动生成同名不同义、同义不同名的指标列表**（P19）：指标平迁先识别相似关系，再形成指标配置建议；按名称、取值字段、聚合函数与加工逻辑识别相似关系。

- **指标重复 48 组**：名称相同、取值字段相同、聚合函数相同、加工逻辑相同。示例「销售额」：门店日报与经营日报都取 `orders.paid_amount`、SUM、已支付含退款 → 重复候选：报表不同，指标口径相同。
- **指标冲突 21 组**：名称相同、取值字段不同、聚合函数不限、加工逻辑不同。示例「销售额」：经营日报取 `orders.paid_amount` SUM 已支付含退款；财务日报取 `settlement.net_amount` SUM 已结算扣除退款 → 冲突候选：支付金额与结算净额，需确认业务口径。
- 证据风险提示：未发现要素缺口（两组示例均如此）。

**自动配置生成语义**（P20）：以「消费者数量 / 核心消费者数量」为例，表格列出指标名称、业务含义、指标定义逻辑、过滤条件、指标类型（原子指标 / 派生指标）、来源表名称、指标名称对应表字段、指标统计日期字段、可分析维度；并展示"需求确认文档 FineBI「分析主题」→ 语义层转换"：4 个组件 → 2 个指标 + 3 个维度 + 3 个数据集 + 2 个关系；文档含版本、来源 GUID、抽取 Job ID、目标、当前状态、用户独立目标（R-01 成功订单金额、R-02 区域销售额占比）。

### 问得准：像数据分析师一样主动反问

示例（P21）：用户问"这个月，企微流失了多少好友？"同一位顾客，月初是好友、月中删除好友、月底重新添加——算不算本月流失？

- **A 期间发生过删除**：算流失——本月发生过删除；
- **B 期初是好友，期末不是**：不算流失——月底已恢复好友。

Agent 的反问："你想看期间发生过的流失，还是期初好友到月底的流失？"

反问的三个原则：

1. **有歧义，先确认**——不把最接近的指标当答案；
2. **给选项，有依据**——每个选项都对应真实业务定义；
3. **缺信息，说清楚**——指出缺少什么，请用户补充。

原文判断：**知道有什么，才知道该问什么；把已有知识变成选项，把信息缺口变成明确的问题。**

### 问得准：认清四种信息状态

|  | 有知识 | 缺知识 |
|--|--------|--------|
| **已识别** | 知道自己知道什么：口径清楚，依据可用 → 有据可选，按确定的规则执行 | 知道自己不知道什么：发现歧义，或明确还缺什么 → 反问澄清，把缺口变成明确的问题 |
| **未识别** | 不知道自己知道什么：企业有答案，Agent 还没有拿到 → 发现并整理，让已有知识进入 Context | 不知道自己不知道什么：没有察觉缺口，把假设当成事实 → 通过评测、观察与追溯，暴露盲区 |

核心判断：**知道自己不知道什么，前提是知道自己知道什么；Context 永远不完备，信息边界要在工作中持续识别和拓宽。**

### 干得对：如何保障数据 100% 准确

演讲把"100% 准确"拆成业务方与 Agent 两边的理由与要求：

| | 业务人员 | Data Agent |
|--|---------|-----------|
| 主张 | "这是要拿去决策的数据，我要求 100% 准确。" | "目标、口径和背景上下文不足，我未必一次就理解对。" |
| 理由 | 数据要用于决策，错误可能影响业务行动 | 业务常识未必写进问题，同一指标可能有多种口径 |
| 要求 | 数字要准确，结论要可用，不能把全部检查工作交还给人 | 目标和背景需要说清楚，歧义与缺口需要双方确认 |

解法不是承诺模型不出错，而是**只有分析过程 100% 可信，才能保障数据 100% 准确**：

| 维度 | 要求 | 具体内容 | 回答的问题 |
|------|------|---------|-----------|
| 工作过程 | 可复盘 | 完整的思维链：工作规划、执行步骤、关键判断 | 看清：怎么做的？ |
| 分析结论 | 可追溯 | 完整的数据链：指标口径、来源引用、数据血缘 | 查清：依据什么？ |
| 全程操作 | 可审计 | 完整的审计记录：工具调用、操作留痕、依据复核 | 核查：做了哪些操作？ |

目标：**让用户看得懂过程、找得到依据、查得清操作。**

产品界面上的三个时段（P25）：

- **任务前**：口径不清晰，主动反问，并做主动口径澄清——新客定义（新客是"分析期内产生首笔认定交易的购买客户"）、老客定义、Mix 分母（各渠道内客户总数，渠道内占比）、渠道维度（销售渠道）、FY2021 老客数据为 N/A；形成"口径说明"。
- **任务中**：过程可复盘、可追溯、可审计——展示多步执行过程（Multi-Definition、Multi-Definition Baseline、Product/Term、Multi-Definition Collection 等）与 SQL 片段。
- **任务后**：数据有角标、有路径、有口径、有血缘，全链路端到端——明细表、指标口径、SQL、数据源/表/字段、指标定义与发布状态均可查。

### 学得会：改进可验证、经验可复用、进化可管控

主循环（P26）：**真实任务**（过程 · 结果 · 反馈）→ **可验证**（两级评测：开发态验证改进、运行态持续检验）→ **可复用**（三级知识沉淀：个人 → 项目/部门 → 公司，更新 Context）→ **下一次任务**（复用经验，做得更好）。

外围是**可管控**：评判效果（改进是否有效）、确认生效（哪些经验可以用）、控制共享范围（在哪个范围复用）；任务经验持续回流。

产品化呈现（P27）：

- **全量记录 Agent 运行行为，持续发现短板**：概览、问题明细、技能、知识、工具、反馈等维度；看板含任务数、活跃用户、对话数、失败任务、输入/输出 token、任务完成率、推理 token 等指标（截图为产品演示环境，具体数值与统计口径**不确定**，不作为落地效果引用）。
- **开发态 + 运行态两级评测，持续提升任务完成率和任务覆盖率**：评测集、逐条评测结果、耗时与通过情况。
- **个人—项目/部门—公司三级沉淀，让个体经验成为组织能力**：经验条目（如 FY22-2023Week 31-week 52、Multi-Definition、Calculation Logic、Vocabulary/Channel NPS、Method/Guest Profile 等）按适用范围与更新日期管理。

### 语义编织 / NoETL 与 Data Agent 的关系

演讲在个人简介中给出 Aloudata 的定位：**首创语义编织和 NoETL 技术，为当下企业级 AI 发展奠定数据土壤**；并称其为 Gartner 中国具有代表性数据基础设施供应商、Data Agent 领导厂商（任务完成率和任务覆盖率行业领先，均为其自述）。

从演讲内容看，二者的关系是：

- **NoETL / 语义编织提供"数据土壤"**——不搬数据、以语义方式组织和复用已有数仓资产，使企业 Context 可以被 Agent 读取；
- **摸得清是这一土壤的上层能力**——自动构建指标语义、算子级血缘、指标平迁、语义自动配置，把数据资产变成 AI 资产；
- **四层能力共用同一底座**——企业 Context：语义层 + 知识库（P14 图中明确标注）。

边界：本演讲**未展开 NoETL 的技术实现细节**（如何做查询下推、如何保证性能与一致性），只给出定位与能力主张；"语义编织"与 CAN 指标平台的关系也未在图中展开，属于**不确定**。

## 经验与边界

### 方法论要点

1. **先换视角，再谈能力**：把 Agent 当数字员工，问题就从"功能是否可用"变成"工作能否交付"——这会倒逼企业定义岗位、面试、试用、转正。
2. **Context 是工作现场，不是提示词**：Context 不是能力，是事实；它永远不完备且活着，所以要有"识别边界、主动澄清、持续沉淀"的机制。
3. **四个能力是闭环而非清单**：摸得清（读）→ 问得准（补）→ 干得对（用与验）→ 学得会（更新），循环回到底座。
4. **可信来自过程，不来自承诺**：以"过程 100% 可信"逼近"数据 100% 准确"，把不可验证的准确率承诺换成可复盘、可追溯、可审计的证据链。
5. **进化必须受控**：经验沉淀要经过两级评测与三级范围控制，避免"越学越偏"与错误经验全公司扩散。

### 边界与不确定项

- **产品主张 vs 第三方验证**：算子级血缘"100% 准确"、任务完成率/覆盖率"行业领先"均为演讲方表述，原文未提供第三方评测或审计。
- **30 分钟上岗缺少评测定义**：没有说明计时起点、任务难度、人工介入程度，不能等同于"30 分钟达到生产可用"。
- **NoETL 技术细节缺失**：只给定位，未讲实现；语义编织与 CAN 指标平台、Data Agent 的工程边界未展开。
- **"100% 准确"是业务要求而非工程承诺**：原文的解法是把检查前置到过程（可复盘/可追溯/可审计），并未声称模型输出永不出错。
- **演讲为厂商视角**：Aloudata 创始人 & CEO 主讲，案例与产品界面均来自其产品，需与独立落地报告区分。
