# 从对话式问数到组织级数据工作空间：京东广告数据分析 Agent

> **核心主张：** 对话式问数只解决了“问一句”，生产级数据分析要解决“分析如何进入生产”。京东广告数据分析 Agent 以**场景契约**约束业务语义，以**知识分层**在链路正确节点生效，以 **Graph-first** 把动态探索固化为可恢复、可复跑的执行图，再用**组织级 Workspace** 把聊天答案拆解为 Query、Dataset、Chart、Report/Snapshot 等可追溯资产。终点不是聊天框，而是一套可执行、可追溯、可复用的组织级执行系统。

## 背景与问题

### 演讲与场景定位

演讲者吴旭晶，分享主题为“从对话式问数到组织级数据工作空间”，副标题是“京东广告数据分析 Agent 的工程化实践”，出现在 DACon 2026 北京站“AI 驱动的客户全旅程：从营销获客到客服服务”专场。

原文开宗明义地划线：**不是 Demo，而是四类真实业务场景**。广告经营分析里的 Agent 要服务真实决策链路；讨论的是“分析如何进入生产”，不是“模型如何回答一句话”。

### 下一阶段不是造更多表，而是让数据形成认知

原文把数据能力拆成三段：

| 阶段 | 解决的问题 | 主要内容 |
|------|-----------|---------|
| **数据资产化** | 有没有数据 | 指标（统一口径字段）、报表（周期结果沉淀）、看板（监控与可视化）、数据集（表结构与分区） |
| **数据服务化** | 能否形成判断 | 理解问题（场景/目标/口径）→ 调用资产（指标/报表/数据集）→ 生成证据（查询/图表/计算）→ 形成判断（解释/归因/建议） |
| **业务认知生成** | 能否形成判断 | Why 解释（指标为什么变化）、Root 归因（主因路径可复盘）、Next 建议（动作优先级）、Trust 可信（证据链可追溯） |

原文的判断是：已有数仓“供给充分”，但“认知仍需生成”。Agent 的价值不是替代 SQL，而是把“数据”转化为“业务判断”。

### 数据不可消费，卡在解释、口径和复用

原文指出业务用户的痛点不是查不到数，而是**不知道如何正确使用数**：

- 去哪里找？（数据发现）
- 看哪个指标？（指标理解）
- 用什么口径？（口径治理）
- 如何解释涨跌？（异常解释）
- 哪些不能做？（分析边界）
- 下次能否复用？（资产复用）

因此真正要补的是**面向业务的消费层**，而不是再加一个输入框。消费层要把“如何正确使用数”产品化，并留下语义、证据、边界和模板；对应的系统能力包括：资产目录、语义知识、口径治理、证据解释、边界护栏、Artifact。

原文用一句广告业务问题串起这条链：“这波广告效果为什么变了？”同一句话需要被拆成**发现、理解、解释、复用**四类消费动作。

### 场景是最小数据服务单元

原文对“场景”的定义不是标签，而是**一组可执行的业务约束**：场景清楚，Agent 才知道查什么、怎么查、怎么解释。场景沉淀不是保存一个 Prompt，而是一组可治理资产。

场景契约（Scene Contract）由五要素组成：

| 要素 | 含义 | 在契约中的位置 |
|------|------|---------------|
| **问题** | 业务用户到底想判断什么（对象、时间） | 输入 |
| **语义** | 指标、维度、口径映射 | 输入 |
| **边界** | 权限、范围、风险控制 | 约束 |
| **目标** | 判断标准与成功条件（主因、机会） | 输出 |
| **动作** | 查询、下钻、报告、订阅 | 输出 |

原文的概括是：场景契约“不是给模型一个标签，而是给系统一份执行说明书”，让 Agent 明确查什么、怎么查、如何解释，并能持续复用治理。

### 以用带治：让业务问题反向驱动治理

原文反对“等所有资产治理完，再开始服务业务”，提出一条循环：

```
业务问题 → 执行分析 → 暴露缺口 → 沉淀复用 →（回到业务问题）
```

即真实使用暴露缺口，缺口反向沉淀为资产。这条路径被概括为“以用带治”。

## 方案/架构

### 为什么对话式问数不够：四类场景对应四种执行形态

原文把广告经营分析拆成四类场景，并指出“同样是数据分析，工程约束完全不同；场景决定 Agent 的执行模式”。

| 场景 | 形态 | 约束 | 执行 | 产出 |
|------|------|------|------|------|
| **智能问数** | 探索 / 响应，重理解 | 问题模糊，需追问澄清 | Query 改写 + 口径校验 | 解释型答案 + 引用来源 |
| **日报周报** | 复用 / 交付，重稳定 | 指标口径固定，结果需一致 | 并行查询 + 局部失败重跑 | 报告预览 + 自动归档 |
| **异常归因** | 证据，重证据 | 不能只报波动，要解释原因 | 行业 / 商品 / 流量逐层下钻 | 主因路径 + 证据链 |
| **订阅推送** | 调度，重调度 | 时间、人群、权限需定 | 模板复跑 + 通知编排 | 推送结果 + 审计留痕 |

原文还给出“能力地图”的流程：**识别场景 → 绑定口径 → 编排执行 → 交付归档 → 复用治理**。四类场景不是功能清单，而是广告经营真实决策链路的入口。

### Schema 只告诉字段，场景知识告诉含义

原文用 `participate_cnt` 举例说明“语义裂谷”：

- Schema 侧：`participate_cnt` BIGINT，表描述是“参与次数”；同表还有 `exposure_cnt`（曝光次数）、`user_id`（用户标识）、`dt`（分区日期）、`event_id`（活动 ID）。
- 知识侧要回答“什么算参与”：业务定义（参与 = 有效动作，不等于点击次数）、计算口径（参与率 = 去重参与用户 / 有效曝光用户）、过滤边界（剔除刷量、测试活动、异常流量）、时间窗口（按业务周期聚合、保留口径版本）。

结论是：**`participate_cnt` 不等于“参与率”**。知识工程补的是业务语义，不是把更多表塞给 RAG；只看字段名，无法判断“参与率”。

### 知识分层 × 链路注入：软知识帮助理解，硬知识交给系统执行

原文反对把知识堆进 Prompt，主张在链路中分层生效：

```
01 问题 → 02 意图理解 → 03 Query 改写 → 04 DSL 生成 → 05 结果解释
```

| 节点 | 注入的知识 | 类型 | 内容 |
|------|-----------|------|------|
| 02 意图理解 | Knowledge Pack | SOFT | 业务背景、术语黑话、分析经验、上下文 |
| 03 Query 改写 | Query 解读 | SOFT | 术语映射、意图消歧、改写策略、语义边界 |
| 04 DSL 生成 | Column List | HARD | 指标口径、权限规则、字段候选、映射、计算 |
| 05 结果解释 | 解释框架 | SOFT / HARD | 业务表达、分析经验、证据引用、口径检查 |

原文的边界很清楚：**SOFT 帮助模型理解与提炼**（背景/术语/经验/解释框架）；**HARD 由系统校验与执行**（口径/权限/字段/计算，测试 → 发布 → 回滚）。关键是放在正确节点。

### 生产级 Agent：从隐式对话走向可治理执行

原文把演进写成三段：

| 阶段 | 特征 |
|------|------|
| **BEFORE 隐式对话链路** | 上下文黑盒，失败难定位 |
| **OBJECT 显式执行对象** | 节点、依赖、状态、产物、证据 |
| **AFTER 生产级执行** | 可恢复、可追踪、可审计 |

对应的 Graph-first 主链路是：

```
01 场景识别 → 02 知识装配 → 03 编排执行 → 04 结果校验 → 05 风险关口 → 06 发布归档
   意图/边界/目标   验证知识/节点约束  Query/DSL/计算  口径/证据/快照  高风险→人工确认  报告/资产/审计
```

每一步都对应一种可治理能力：可定位、版本可追、局部重跑、证据可溯、显式暂停、全程留痕。

知识资产由三方协同构建：**Agent 提炼**（背景/经验/草案）× **Code 校验**（规则/测试/版本）× **Human 裁决**（口径/审批/责任），再经验证入库、版本化、注入节点契约。

高风险节点必须等待确认，原文列出的高风险类型是：**人、钱、权限、对外结论**。流程是：暂停执行 → 人工确认 → 通过则发布；拒绝则中止任务并留痕。

### Graph-first：从动态探索到稳定复用

原文把 Graph-first 定义为“把动态探索沉淀为可复用的 DAG”，路径是**探索 → 固化 → 复跑**。

- **动态探索**：未知问题，临时下钻、多分支、补上下文；发现新线索时可弹性增减分析节点；尝试多种路径时保留过程与执行状态；探索结果再验证固化。路径可变，过程可追踪。
- **可执行分析 DAG**：`DATA_REF A/B`（已有/补充数据引用）→ `QUESTION`（业务问题）→ `CONTEXT`（补全上下文）→ `DSL`（生成与校验）→ `COMPUTE A`（指标查询）/ `COMPUTE B`（维度查询）→ `ARTIFACT`（结果引用、归档）。并行、汇合、可恢复；失败节点只重跑对应分支；状态显式可见，结果可引用。
- **验证后静态复用**：`TEMPLATE v1` 固化节点、依赖、校验规则；执行实例 `#031 行业 A · 本周` 为 DONE，`#032 行业 B · 下周` 为 READY；支持周期触发、订阅、归档。

DAG 契约包含四项：**节点**（输入/输出）、**依赖**（先后/并行）、**状态**（执行/失败）、**结果引用**（DATA_REF/ARTIFACT）。原文的收束是：“探索要弹性，生产要稳定；复用经过验证的分析结构，而不是复制上次答案。”

### 三层 Graph：模板与执行各司其职

| 层 | 名称 | 生命周期 | 职责 | 内容 |
|----|------|---------|------|------|
| **L1** | Master Graph | 全局、长期有效 | 全局约束 | 业务场景与权限边界、指标/维度口径、通用校验规则；让权限、口径和规则跨会话保持一致 |
| **L2** | Session Graph | 会话、按需生成 | 本次计划 | 本次参数与问题、节点编排/分支、人机交互修正；把当前问题拆成可调整的节点与依赖 |
| **L3** | Graph Executor | 执行、按节点推进 | 调度执行 | 查询/计算/校验、状态/重试/日志、结果引用与归档；并行处理、跟踪状态、失败时局部恢复 |

原文强调“不同生命周期，各管各的事”：边界有归属（全局口径不混进 Prompt）、结构可治理（模板独立版本、复用验证路径）、运行可追踪（实例保留状态、日志与产物）。

模板与实例分离：`GRAPH TEMPLATE v3` 定义“应该怎么跑”（参数槽、DAG 节点、校验规则），结构与规则版本化、参数可替换；执行实例记录“这一次怎么跑”（参数绑定、节点状态、运行日志、结果引用、失败重试、复盘证据）。示例中 `EXEC #241` 行业 A 本周 DONE、结果已归档；`EXEC #242` 行业 B 下周 RETRY、只重跑失败节点。

### 节点契约与人工确认：让每一步可恢复

原文把节点定义为“不是图形，是执行协议”。节点契约记录：

- 依赖 / 输入：前置节点、DATA_REF
- 状态 / 进度：RUNNING / FAILED
- 恢复 / 重试：检查点、失败重跑
- 结果引用：DATA_REF / ARTIFACT

执行示例：`DATA_REF`（READY，输入数据引用）→ `COMPUTE`（DONE，指标计算、可重试）→ `WAIT_CONFIRM`（PAUSED，高风险结论、人工确认点）→ `ARTIFACT`（NEXT，确认后发布与归档）。

人工审核（HUMAN REVIEW）负责确认依据、修正假设，在“人、钱、权限、对外结论”处暂停。批准后从暂停点恢复、审批留痕（RESUMED），执行器保留状态、沿原图继续，而不是重新生成答案。

### 组织级数据工作空间：让分析资产留下来

原文区分两个能力：**Graph 解决怎么稳定做完，Workspace 解决做完之后如何继续使用**。聊天答案会消失，分析产物应该进入组织资产库；回答只是展示层，Artifact 才是可复用资产。

聊天答案被“拆解”后进入 Artifact Library：

| 资产类型 | 内容 |
|---------|------|
| **Query** | 查询记录 |
| **Dataset** | 结果表 |
| **Chart** | 图表 |
| **Report · Snapshot** | 报告与执行快照 |

Workspace 的四种复用方式：

1. **追溯让结论回到证据链**：业务结论 → 图表（可视化承载判断）→ 计算（口径、公式、聚合逻辑）→ SQL/DSL（可复跑的查询表达）→ 数据源（原始表、权限与时间切片）。原文的判断是：“可信不是‘模型说得像’，而是每句话都能回到证据。”
2. **复跑让一次分析变成模板工厂**：同一 Graph Template 换行业、时间、项目参数，生成新的执行实例（行业 A/零售/Q1、行业 B/金融/Q2、项目 C/复盘/本周），复用经过验证的分析结构，不是复制上次答案。
3. **订阅把模板变成持续服务**：每天 10:00 自动触发，选择模板 → 配置参数 → 生成报告 → 归档快照，再推送给负责人（IM/邮件/订阅）、自动归档 Report+Snapshot、异常提醒（缺数/失败/阈值）。原文的表述是“让数据在正确时间，找到正确的人”。
4. **分享让结果从个人问答变团队资产**：同一份分析资产被分析师（确认口径、验证证据链）、产品（定位问题、回看同一证据）、运营（推动行动、拿同一结论执行）、管理者（统一决策、基于同源事实）共同消费。协同的前提是大家看到同一份可追溯证据。

专家经验通过模板放大：1 位专家 → 专家分析（个人经验形成初始判断）→ 动态图验证（找到路径）→ 静态模板沉淀（固定结构）→ N 个团队复用、订阅、改造。复用不是复制报告，而是复用分析结构。

### 最终架构：Conversation 是入口，系统主体在四层能力

原文的总架构分六层：

| 层 | 名称 | 内容 | 定位 |
|----|------|------|------|
| 01 | **Conversation 对话入口** | 问题、意图、上下文 | 入口层 |
| 02 | **Scene 高频场景** | 场景识别、复盘模板、指标口径 | 业务约束 |
| 03 | **Knowledge 知识资产** | 指标字典、维度映射、业务规则 | 理解层 |
| 04 | **Graph 执行** | 节点契约、DAG、可恢复 | 执行系统 |
| 05 | **Workspace** | Artifact、证据绑定、订阅归档 | 资产与协同 |
| 06 | **Organization Reuse 组织复用** | 模板复跑、共享证据、治理迭代 | 组织能力 |

能力主线是：**高频场景 → 知识资产 → Graph → Workspace → 组织复用**。原文的结论是“对话只是入口，中间每一步都是可治理能力”。

## 关键工程做法

### 四个场景的落地链路

**智能问数：先理解，再约束查询。** 自然语言问题 → 场景识别（识别业务目标与口径）→ Query 改写（补全意图与上下文）→ DSL 生成（结构化表达分析计划）→ 校验（权限、口径、可执行检查）→ 解释（图表、证据与业务语言）→ 可信分析结论。旁路还有证据链（可回溯数据源）与执行契约（可恢复与可重试）。原文强调：NL2SQL 只是完整分析链路中的一步，要从“生成 SQL”升级为“生成可信分析”。

**日报周报：从手工拼报到可复跑资产。** 周期报告天然适合沉淀静态图模板；模板化约束行业结构与指标口径，减少重复规划，提升稳定性与口径一致性。示例链路：`M1 收入` DONE、`M2 消耗` FAILED、`M3 ROI` DONE → 局部重跑（only rerun M2 node）→ 聚合校验（merge + validate）→ 周报预览（定口径、自动更新、可归档）→ Snapshot 已归档。预览中的示例数字为收入 +12.4%、消耗 -3.1%、ROI 1.87。

**订阅推送：高频报告自动交付。** `D1 订阅模板` → `02 周期触发（每天 10:00）` → `03 自动生成（拉数、计算、出图）` → `04 通知归档（IM 推送 + 快照留痕）` → `05 服务反馈（失败提醒/补跑）`。示例报告为“重点行业收入变化”，每天 10:00 送达运营团队，渠道为工作台 + IM。订阅是数据服务化最直观的入口：从人找数据，变成数据找人。

**异常归因：从报警走向证据化根因。** 异常不只是发现波动，更要解释为什么；归因过程可复盘，结论才可信。示例链路：收入异常 ↓（先定位波动来源）→ 行业定位（锁定重点行业）→ 产品线 A（预算收缩 -18%）→ 商家 Top20（消耗同步收缩）→ 流量·转化（CVR -9.6%）→ 主因锁定（预算收缩 × 转化下滑）。页面同时列出排除项：其他行业（整体稳定）、其他产品线（贡献小）、长尾商家（影响小）、流量正常段（非主因）。归因产物包括附查询、图表、执行快照。

### 每个场景沉淀三类资产

| 资产 | 解决 | 内容 |
|------|------|------|
| **数据资产** | 查什么 | 数据表（主题域/分区/血缘）、指标（定义/口径/权限）、维度（业务枚举/层级） |
| **知识资产** | 怎么理解 | 口径（去重/周期/边界）、术语（同义词/业务含义）、规则（经验/风险/判断） |
| **Agent 资产** | 怎么执行 | 模板（场景卡/分析路径）、节点（可执行/可恢复）、策略（工具/校验/交付） |

三类资产之上是统一治理底座：**版本、权限、血缘、质量、审计**。原文强调“三支柱同时进入版本、权限、质量与证据治理”，让三类资产能被生产化使用；场景沉淀不是保存一个 Prompt，而是一组可治理资产。

### 边界护栏：不是所有任务都需要 Agent

原文给出六条边界设计原则：

1. **自动化要分级**：只让流程自动跑。
2. **权限不可绕过**：授权、审计、脱敏先行。
3. **产物必须留痕**：证据链可追踪、可复用。
4. **简单任务不必图化**：低价值场景保持轻量。
5. **高风险需确认**：关键动作保留人工介入。
6. **模板持续治理**：版本、口径、质量迭代。

原文的判断是：“不是所有东西都应该自动化，也不是所有任务都需要 Agent。边界不是限制，而是业务长期信任的前提。”

## 数据与效果

### 落地覆盖与效率

原文给出的落地数据：

| 维度 | 结果 | 口径/说明 |
|------|------|----------|
| 业务报告制作 | 3–5 小时 → 10 分钟 | 耗时减少约 94%–97% |
| 业务日报看数 | 30 → 2 分钟 | 耗时减少约 93.3%；PPT 未标注前一个“30”的时间单位 |
| 大促关键节点 | 问题发现时长缩短约 50% | 判断更及时 |
| 覆盖规模 | 13+ 场景、20+ 部门 | 服务上千人次，覆盖销售、采销、运营、分析及管理 |

原文把价值总结为三段角色变化：生产者“对话即可开始生产”，不再依赖专家每次从零搭建；共享工作空间“把过程沉淀成组织资产”，约束、执行、版本、证据留在同一条链路；消费者“数据在需要时找到人”，按同一口径获得可追溯结论。关键变化是降低生产门槛、加速成果交付，让一次分析沉淀为组织可反复使用的能力。

### 五项工程化指标

原文明确说：判断 Data Agent 是否生产化，不只看回答准不准；能被记录、能被追踪的指标，才能驱动持续治理。

| 指标 | 数值 | 说明 |
|------|------|------|
| **任务完成率** | 96% | 复杂链路可跑完 |
| **节点成功率** | 98% | 失败定位到节点 |
| **复跑率** | 42% | 同一链路被再次使用 |
| **模板沉淀率** | 37% | 路径固化为模板 |
| **人工确认率** | 18% ↓ | 介入节点逐步收敛 |

人工确认率另有一张收敛曲线：从 W1 的 62% 降到 W6 的 13%。原文的治理口径是“看工程指标，不看单点准确率”。

### 价值不止提效，而是复用能力

原文用五边形概括平台价值：效率（少重复规划）、复用性（模板化结构）、可信度（同源证据链）、协同（共享工作空间）、定性/可恢复执行。结论是：从个人效率提升，到组织分析能力沉淀；**用户开始自建、复用和订阅模板时，Agent 才成为生产力平台**。

## 经验与边界

1. **先定义场景，再谈模型**：场景不是标签，而是一组可执行约束；没有场景契约，Agent 不知道查什么、怎么查、怎么解释。
2. **知识要分层，不要堆 Prompt**：软知识用于理解，硬知识交给系统执行；关键是放在正确节点。
3. **把分析做成图，而不是做成一次回答**：节点、依赖、状态、产物、证据显式化，才能局部重跑、失败恢复、全程审计。
4. **模板与实例分离**：模板定义“应该怎么跑”，实例记录“这一次怎么跑”；复用结构，不复用答案。
5. **回答只是展示层**：Artifact 才是资产；没有 Query/Dataset/Chart/Report/Snapshot 的沉淀，聊天结束资产就消失。
6. **可信来自证据链**：每个结论都要能回到图表、计算、SQL/DSL 和数据源，而不是“模型说得像”。
7. **高风险必须人工确认**：人、钱、权限、对外结论四类节点显式暂停；边界是长期信任的前提。
8. **以用带治**：不要等资产治理完再服务业务；真实使用暴露缺口，缺口反向沉淀为资产。
9. **原文未披露的技术细节**：PPT 没有给出底层存储/计算引擎、模型选型、Graph 的具体实现框架、知识库的存储形态；也没有给出“任务完成率/节点成功率/复跑率/模板沉淀率/人工确认率”的完整计算公式与统计窗口。这些指标只附了一句话口径。
10. **示例数字与生产结果的边界**：日报周报页的收入 +12.4%、消耗 -3.1%、ROI 1.87 是“周报预览”中的示例；异常归因页的 -18%、-9.6% 是归因示例链路中的数字。原文未说明它们是否为真实生产数据，引用时应保留“示例”语境。
11. **四类场景不等于全部覆盖**：原文称已覆盖 13+ 场景，但只详细展开智能问数、日报周报、订阅推送、异常归因四类；其余场景未在 PPT 中列名。
12. **“对话式问数不够”的边界**：原文并未否定 NL2SQL，而是把它定位为完整分析链路中的一步；其限制在于缺少场景约束、知识分层、证据链与资产沉淀。
