# 行动闭环的两端：AgentCore 让 Agent 敢行动，Agentic 工作台让结果看得见

> 核心主张：Data Agent 的行动闭环真正卡住的不是中间（感知→分析→决策→执行，行业都在做深），而是**两端**——左端"不敢行动"（权限失控、调用跑飞、事后无法审计），右端"看不见"（结果停在技术侧，业务用不上）。左端由 Amazon Bedrock AgentCore 承接，把身份、策略、审计放到 Agent 代码之外；右端由数数 Agentic Engine + 智能体工作台（如 Amazon Quick）承接，把结果送到业务每天干活的地方。

演讲信息：DACon 2026 北京站「从分析闭环到行动闭环：Data Agent 的边界突破」专场，演讲嘉宾黄达（亚马逊云科技大中华区解决方案架构团队，合作伙伴解决方案架构师 PSA，负责与数数科技 ThinkingAI 共建联合方案）。

## 背景与问题

### 演讲者与视角

- 广度：先后服务于 40+ 家国内外 ISV 合作伙伴，其中很多来自游戏与数据分析领域
- 深度：帮助多家合作伙伴与 AWS 联合开发 Agent 产品
- 积累：15 年软件研发、4 年云原生解决方案、2 年 AI 智能体项目
- 关注方向：生成式 AI 与 Agent 在企业生产环境的落地；与 ISV 合作伙伴共建联合方案、PoC；AI-DLC 在软件企业中的实践

### 闭环卡在哪里

演讲把 Data Agent 的闭环画成一条链：**感知 → 分析 → 决策 → 执行**。

- 中间段：大家都在做深
- 左端：不敢行动——权限失控、调用跑飞、事后无法审计
- 右端：看不见——结果停在技术侧，业务用不上

行业信号："不是不想用，是不敢放手"——对完全自主 Agent 的信任度在一年内从 **43% 降至 27%**（凯捷研究院，1,500 位高管调研；来源标注为 Capgemini Research Institute，2025-07 新闻稿，调研于 2025 年开展）。

真实场景（原文举例）：Agent 分析做得很好，但没人敢让它直接改线上配置；或报告做出来了，业务方没打开过。

结论：**行动闭环真正卡住的不是中间，而是两端——不敢行动，和看不见。**

## 方案/架构

整体解法是把两端分别接上，中间交给数据与行业能力：

- 左端（敢行动）：企业 Agent 跑在 Amazon Bedrock AgentCore 上（身份 · 网关 · 策略 · 可观测），行动由它发起并受治理
- 右端（看得见）：数数 Agentic Engine + 智能体工作台（如 Amazon Quick），送到业务每天干活的地方
- 中间：数数 Agentic Engine —— 数据 + 实时信号 + 行业 Skills + A/B 验证
- 闭环：业务反馈回到感知，下一轮更准

### AgentCore：五项核心能力包住一个 Agent

各组件完全解耦，可单独使用也可任意组合；不绑定特定框架或模型。官方服务清单不止这五项：另有 Policy、Harness、Evaluations、Browser、Code Interpreter、Registry 等。

| 组件 | 角色 | 关键点 |
|------|------|--------|
| **Identity** | 身份与凭证 | 入站：谁能调用；出站：以谁的身份访问工具 |
| **Runtime** | 会话级隔离运行 | 你的 Agent（任意框架 · 任意模型）跑在独立 microVM |
| **Gateway** | 工具统一入口 | API / Lambda → MCP 工具；+ Policy 调用前先过规则 |
| **Memory** | 短期 + 长期记忆 | 跨会话上下文 |
| **Observability** | 贯穿全链路 | 追踪 · 指标 · 日志 |

调用方的两侧：业务用户与业务应用从左侧进入；右侧接企业 API / Lambda 与外部 MCP 服务（例如数数 Agentic Engine）。

模块化组合示例（原文给出两种）：只用 Runtime 做托管运行（不接 Gateway / Identity）；或 Gateway + Identity 做工具调用治理（不接 Memory）。

### Agentic 工作台：能力在数数，入口在工作台

| 层 | 数数 Agentic Engine（能力层 · 算对、算快） | 智能体工作台（前端 · 交到业务手里） |
|----|------|------|
| 定位 | 数据采集 → 分析引擎 → 运营策略 → 效果验证 | 如 Amazon Quick（专为工作打造的 AI 伴侣），也可以是 Claude Code、Kiro 等桌面 Agent |
| 能力 | 实时数据 → 实时决策；通过全链路 CLI / MCP 开放给任意 Agent；数十个行业 Skills | 业务用户用自然语言提问、看图、追问、分发；其他能力：研究、自动化、应用 |
| 场景 | 口径与计算由数数负责 | Quick：定制化需求、早期场景的快速验证 |

链路：业务人员提出问题 → 工作台经 MCP / CLI 调用数数 Agentic Engine 的数据、口径与 Skills → Amazon Quick 呈现看板与结论 → 业务人员追问、分发、反馈。

> 能力在数数 Agentic Engine，入口在智能体工作台：Agentic Engine 负责算对，工作台负责交到业务手里。

## 关键工程做法

### 1. Runtime：每个会话一台独立的 MicroVM

- 会话隔离：会话 A / B / C 各自拥有独立的 CPU、内存、文件系统，硬件级隔离
- 单次运行生命周期（默认值，均可配置）：创建（按请求启动）→ 运行中（单实例最长默认 8 小时）→ 空闲（默认 15 分钟回收）→ 结束（销毁 · 清理）
- 按需弹性：从零扩缩，不用预置；等模型回复的 I/O 时间不计 CPU 费
- 状态默认临时：跨会话要留下的上下文，交给 Memory
- 不绑框架：任意框架、任意模型，支持 MCP / A2A

> 在生产环境里，隔离不是选项，是默认值。

### 2. Identity：谁让它动的、它拿谁的钥匙

- 入站认证：Runtime、Gateway 各自配置 IAM 或 JWT，对接企业现有身份提供方
- 出站凭证：Token Vault 用 KMS 加密；凭证只给最初取得它的"Agent + 用户"组合

调用顺序示意：业务用户带 JWT 调用 → 入站校验"你是谁" → Agent（Runtime）→ Gateway → 按 Agent + 用户向 Token Vault 取凭证 → 带凭证调用工具（API / MCP）。

### 3. Gateway + Policy：规则写在代码外面

- Gateway 是工具统一入口，入站授权可配置
- Policy 是与 Gateway、Memory、Runtime 等**并列的独立 AgentCore 服务**（官方架构同级列出），不是 Gateway 的子功能
- 拦截点挂在 Gateway 的调用路径上：每次工具调用执行前先判定，规则写在 Agent 代码之外，默认拒绝
- 判定引擎：Cedar
- 调用可记录；Agent 步骤需埋点

> 身份跟着用户走，工具统一从网关进，规则写在代码外面。

### 4. Memory：记得住，更要记得准

AgentCore Memory 托管两层记忆：

- 短期记忆：按会话逐轮记录原始事件；事件按设定期限自动过期（3–365 天）
- 记忆策略：后台异步提炼
- 长期记忆：提炼偏好 / 事实 / 摘要，跨会话保留，按相关性检索；也支持通过 API 直接写入；可按策略配置最少 31 天的保留期（到期自动清除），不配置则不过期

与数数知识库与 Skills 互补：知识库沉淀企业指标口径、业务规则、工作方法和实践经验并复用。口径示例：付费率怎么算、哪些渠道算买量；规则示例：业务口径与数据治理规则写在知识库里；方法示例：数十个行业 Skills，如 LTV 曲线、付费归因。原文判断：两种设计风格互补，AgentCore Memory 实现了大部分 Agent 需要的记忆的底层需求，但不影响企业继续实现自己的独特逻辑。

接入方式（与模型、框架解耦）：

| 方式 | 内容 |
|------|------|
| 数据面 API | CreateEvent、ListEvents、RetrieveMemoryRecords、BatchCreateMemoryRecords |
| SDK / CLI / 控制台 | Python SDK、Strands Agents、AgentCore CLI、AWS 控制台、Boto3 |
| 运行位置不限 | Agent 不在 Runtime 内，也可以接入 Memory |

为什么直接用托管 Memory：提炼策略（用户偏好、语义事实、会话摘要、Episodic，也支持自定义策略）；多租户隔离（namespace 按 actorId / sessionId 分层，可前置 Gateway + OAuth 与细粒度访问控制）；治理（KMS 客户托管密钥、执行角色、元数据过滤与记忆记录流式投递）。

### 5. Harness 与 Runtime：配置优先 vs 代码优先

Harness 运行在 AgentCore Runtime 中，提供开箱即用的编排循环；Runtime 则让团队自己编写编排逻辑。

| Harness｜配置优先 | Runtime｜代码优先 |
|------|------|
| 模型：Bedrock / OpenAI / Gemini / LiteLLM | 每个会话有状态，运行在独立 microVM |
| 工具：Gateway、MCP、Browser、Code Interpreter | 自带文件系统和 shell，可写代码、执行代码 |
| 记忆：短期 + 长期，跨会话保留 | 不单收 Harness 费用，按底层能力实际用量计费 |
| 身份：Identity | 状态：GA |

演进路径：配置快速起步 → 配置不够用时导出 Strands 代码 → 部署到 Runtime 继续运行。

版本发布与 A/B：evaluations + optimization 可按会话测试 Agent 新版本，并输出显著性报告；immutable versions + named endpoints 支持安全发布和快速回滚。原文特别注明：这里测试的是 Agent 版本，与后文面向用户运营干预的 A/B 不同。

### 6. Observability + Evaluations：看见过程，量化质量

一次请求的执行追踪按"会话 › 调用链 › 步骤"展开：推理 → 调用工具（示意）→ 记忆检索 → 推理 → 输出。

- Observability 指标：会话数 · 延迟 · 时长 · Token 用量 · 错误率
- 默认进 Amazon CloudWatch，兼容 OpenTelemetry，可接现有监控工具
- harness 里的每一步动作也自动进入追踪视图，不需要额外埋点
- 接入 OpenTelemetry 埋点后，每一步的耗时、输入输出、工具调用都能回放
- Evaluations：大模型当裁判，提供一组内置评估器（正确性、工具选择准确率、目标达成……），其中含 2 个专门的 skill evaluators（技能选择准确性、技能指令遵循），并支持自定义；三种方式：在线抽样 · 按需 · 批量回归

> 决定 Agent 能不能上生产的，不是模型能力的上限，而是失控风险的下限。

### 7. 工作台侧：MCP 主通道 + CLI 代码通道

调用链路（原文示意）：

业务问题（哪个渠道最值钱？下一轮预算往哪投？）→ 数数 Agentic Engine（渠道新增、付费、留存数据，算出各渠道的单客价值）→ 分两条通道：

- **MCP（主通道）**：Quick 桌面版 ↔ 数数分析 MCP，只启用读工具
- **CLI（写代码 Agent 通道）**：AE CLI 只读导出 → CSV，接 Claude Code / Kiro 等写代码 Agent

→ Amazon Quick（看板 · 结论 · 建议）→ 业务人员拿到加投建议和风险。

口径归属：分析是数数 Agentic Engine 算的，口径是数数的；Quick 负责把结果交到业务手里。MCP 是主通道（标准协议接工作台 / AI 平台），CLI（AE CLI）是面向写代码 Agent 的通道。

实时链路：01 多端实时上报 → 02 秒级查询 → 03 信号识别 → 04 动作触发。工作台里"看见正在发生的"三件事：直接问当前数据；对话中生成可交互图表与报表；定时简报与推送。Skills 作为企业级 Agent 可调用的后台能力进入工作台，与 MCP server 属于同一类工具，示例包括实时分析、留存与 LTV、用户分层、埋点方案、A/B 实验和用户触达。

### 8. "图之后"：产物变成组织资产

原文把分界线放在结果生成之后：产物属于谁、保存在哪里、能否被组织安全复用。

01 对话生成（session tab 中生成 artifact）→ 02 组织归档（保存到账号云端 Library）→ 03 跨端复用（Web、移动端、桌面均可查看）→ 04 继续工作（从 Library Open in chat）。

成品形态直接可交付：对话中可以直接生成 Word / PPT / PDF 等文档，不停留在聊天框里。

> 把图画出来只是起点；让不写代码的人持续使用，让组织安全复用，才是最后一公里。

组织级治理与 AWS 身份打通（Amazon Quick Enterprise Edition）：

| 组织级平台能力 | AWS 身份与数据治理 |
|------|------|
| 发布：Skills / Chat agents 带版本，可按角色审批 | 身份：IAM Identity Center、AD、Entra ID、Okta |
| 统一管理：Connectors / MCP 的权限与开关 | 审计：CloudTrail |
| 团队空间：Spaces 组合知识、数据、Dashboard 与行动 | 内容防护：Amazon Bedrock Guardrails |
| 交付：Apps 一键发布给团队 | 防泄漏：Microsoft Purview DLP |
| 自动运行：云端 Routines 按计划执行 | 审批：知识库、Spaces、Chat agents 可配置 workflow；隔离：知识库按权限控制 |

原文注明：以上治理能力归属 Enterprise Edition 账号，覆盖 Professional 与 Enterprise 两档用户订阅。

### 9. 行为洞察 → 主动干预：用实验验证每一次行动

四步循环：

1. **观察**：实时识别异常与目标人群（付费率波动 · 流失风险）
2. **实验**：A/B 实验 Agent——提出假设，智能设计（含样本量计算）、一键分流
3. **干预**：智能运营 Agent——智能分层，AI 生成文案 → 多渠道触达（push / 弹窗）
4. **验证**：实时监控 + SRM 告警，贝叶斯统计 + CUPED → 显著性判断、策略推荐

结论回到观察，持续迭代：每一次干预都有实验证据。典型场景：礼包定价 · 首充引导 · 弹窗时机 · push 召回策略。

边界澄清（原文专门标注）：这是**运营侧实验**——给用户分组、比较策略，验证的是业务干预效果；和 AgentCore harness 页提到的 A/B（面向 Agent 版本迭代）是两件不同的事。

### 工作台侧实测（4 个演示）

说明：实测使用演示项目中的固定区间数据，不是实时流。以下结论与数字均来自演讲现场截图（数数科技 ThinkingData MCP × Amazon Quick 集成演示，数据为历史抓取快照，情景测算为假设推演，非预测承诺）。

**实测① 拉人最多的渠道，赚钱也最多吗？**

- 提问（投放运营）："上个月各渠道的用户和付费都齐了：拉人最多的渠道，是不是赚钱也最多？做个一眼看懂的看板。"
- 结论：基本成立——渠道 A 贡献 57% 新增和 57.5% 收入；但 G 的单客价值最高（ARPU 368 元）
- 截图中的大盘数字：总新增 7,348、总付费用户 3,841、总收入 181.8 万、整体 ARPU 247 元、整体付费率 52.3%
- 下一步可以对 Quick 说：存成 Skill 分享给全组 / 把这个查询逻辑做成 App 分享给全组 / 放进项目组的 Space，同事可以接着追问

**实测② 给老板的月度大盘**

- 提问（运营负责人）："用最近 30 天的新增、付费和留存，做一个给老板汇报的大盘：这个月涨得怎么样，用户留不留得住？"
- 结论：稳健持平，次日留存稳定在 40% 左右
- 下一步：这个查询以后每天早上 9 点跑一次 / 给张总发一封邮件，附上这个大盘 / 按这个思路生成一份汇报 PPT

**实测③ G 渠道该不该追投？**

- 提问（市场投放）："下一轮大促要不要给 G 渠道多投预算？和其他渠道比一比，做成一页汇报，给建议和风险。"
- 结论：建议小步试投、不要 all-in——G 单客价值第一，但样本只有 145 人
- 关键数字：G 的 ARPU 368 元（高出其他渠道均值 50%，其他均值 245 元；大盘均值 247 元）、首充率 61.4%（高出其他 9.3pp，其他 52.1%）、新增占比 2.0%、样本 145 人、收入占比 2.9%
- 风险与不确定性（截图明确列出四类）：样本太小（仅 145 个新增用户，统计上一次大促的放量可能让 ARPU/首充率向均值回归，当前高值未必可复制）；无成本/CAC 数据（高 ARPU ≠ 高 ROI，若 G 的获客单价也高，真实回报可能被吃掉）；人群天花板（高质量可能来自某个窄众精准人群，预算一旦加大、受众放宽，边际用户质量通常下滑）；渠道容量未知（G 能否承接 5–6 倍预算而不显著抬高 CAC，尚未验证）
- 建议的行动方案：小步试投（给 G 一个受控预算，如当前量级的 2~3 倍）；盯三个指标（ARPU、首充率、获客单价 CAC 是否随量上升而下滑）；设止损/加码线（ARPU 跌破 ~258 即预警收缩，若放量后仍稳住 300+，下一轮大胆加码）；补齐成本数据（向投放团队要 G 的 CAC）
- 放量情景测算（截图）：不衰减 → 31 万 | 衰减 15% → 26 万 | 衰减 30% → 21.7 万（仍跑赢"按大盘均价放量"的 20.9 万参考线）| 衰减 45% → 17 万（跌破）。含义：只要放量后质量衰减不超过 ~30%，追投 G 就比把同样预算投给平均渠道更划算，下行有安全垫

**实测④ 找出被忽略的潜力股渠道**

- 提问（增长分析）："有没有量不大、但用户特别值钱、被我们忽略的'潜力股'渠道？做个图，再列个加投清单。"
- 方法：按"规模 × 单客价值"切成四象限，一眼定位"量小但值钱、被忽略"的渠道。横轴 = 新增用户规模（对数），纵轴 = 单客价值 ARPU，气泡大小 = 首充率；十字虚线 = 大盘均值（ARPU 247 / 规模中位 386）；左上象限（量小值高）= 潜力股
- 结论：重点加投 G 和 H——量都只有约 140 人，却都比大盘更值钱
- G（头号潜力股，潜力分 36.3）：145 人 · ARPU 368 元 · 首充率 61.4%；单客价值和首充率双料第一，ARPU 超大盘 49%
- H（稳健潜力股，潜力分 3.7）：141 人 · ARPU 257 元 · 首充率 53.9%；ARPU 和首充率都略高于大盘，被忽略的稳健小渠道
- 反例（原文提醒"别被'量小'骗了"）：E 虽然量小但 ARPU 185 为全渠道最低，F 首充率仅 49.7%，属"鸡肋"象限而非潜力股
- 另一个发现：C 是"最被低估的准明星"——ARPU 264、首充率 54.6%，且已有 843 的规模，价值高且跑量能力已验证，可以稳步加投，风险比 G 更低

### 跨行业规模化挑战

三个共性问题：

1. 数据及时性：能不能在变化发生时就看到，不是等隔夜报表
2. 业务口径：同一个指标，各团队算法是否统一
3. 分析到行动的衔接：结论能不能直接变成下一步的动作，而不是停在报告里

| 行业 | 可复用场景 | 主要关注点 |
|------|------|------|
| OTA | 用户流失、价格与转化变化 | 实时性、跨系统协同 |
| 内容 | 活跃下降、推荐效果变化 | 人群分层、反馈速度 |
| 互联网 | 活动转化、生命周期运营 | 实验、触达、效果回收 |

游戏行业的例子：口径统一——"值钱"统一按 ARPU、首充率算；及时性——这次用的是固定区间的演示数据，不是实时流；行动衔接——结论直接变成"小步试投 + 盯指标"的动作。

## 经验与边界

### 三条带走

1. **先划边界，再放权**——Agent 进入生产，首先要解决安全运行与受控执行：身份、策略、审计放到 Agent 代码之外，交给底座
2. **洞察要进业务流**——数据、知识和 Skills 通过 MCP / CLI 进入工作流，才能让分析结果真正被业务使用
3. **从结果走向实验与回收**——从结果呈现继续走向实验、触达与效果回收，行动闭环才真正完成

> 底座让 Agent 敢行动，最后一公里让行动被看见。

### 边界与不确定处

- 43% → 27% 的信任度变化来自凯捷研究院（Capgemini Research Institute）2025-07 新闻稿，调研于 2025 年开展、样本 1,500 名高管；原文未给出分项口径与误差范围
- Cox Automotive 案例中，公开材料只明确提到 Memory，其余组件未细分，原文已明确不做单组件归因
- 四个工作台实测全部基于演示项目的固定区间数据，不是实时流；G/H 渠道的具体数值属于演示数据，不能当作真实行业基准
- 原文未给出 AgentCore 的价格、延迟、可用性 SLA 等运行指标；也未给出工作台侧"看懂看板"的准确率或人工替代率
- 原文区分了两类 A/B：AgentCore 侧的 Agent 版本 A/B（immutable versions + named endpoints）与运营侧的用户分组实验（A/B 实验 Agent + SRM 告警），两者不可混用
- 演讲未展开：AgentCore 各组件在混合云/私有化环境的可用性；工作台侧 MCP 只启用读工具时，写操作如何回到受控闭环（原文仅提示 CLI 通道为只读导出）
