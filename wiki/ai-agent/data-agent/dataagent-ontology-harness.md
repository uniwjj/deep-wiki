# DataAgent 的业务本体与 Harness

> 来源：DataFunSummit《为 Agent 重建数据层：网易智企产品 AI Native 演进路径》（蒋鸿翔，2026-11-03）第 4 节"DataAgent 的问数准确率，靠业务本体与 Harness 支撑"。
> 原文前置判断：开发治理主要面对工程师，DataAgent **直接回答业务人员的问题**，口径歧义更容易影响结果。

## 问题：模型再强也猜不出公司的口径

配图：《DataAgent 的核心：业务本体 + 语义层》，副标题"数十家真实客户场景 POC 实测验证——准确率的瓶颈，九成卡在「听不懂」"。

| 阶段 | 准确率 |
|---|---|
| 表结构导进去、AI 就开始答（数据初始化后） | **< 50%**（原文：部分场景不到 50%） |
| 经过本体构建、业务术语定义、提示词调优等环节 | **> 95%**（原文：部分场景超过 95%） |

配图列出的两个实际客户：**国企客户 A，准确率 95% 以上；制造业客户 B，财务用数测试准确率接近 100%**。

原文对口径的限定："这些数字对应具体场景，**不能视作模型的通用准确率**。"

### 四类语义歧义（配图）

| 类型 | 配图示例 |
|---|---|
| 计算口径歧义 | 「最近一个月的利润」——自然月本月至今，还是从今天往前推 30 天？ |
| 指标选择歧义 | 「上月的销售额」——销售额 / 销售收入 / GMV 三个都在，选错一个口径全错 |
| 业务术语歧义 | 「昨天的战报」——这家公司 = 销售额 + 订单数 + 客户数，换家公司完全是另一组数 |
| 分析思路缺失 | 「销售额为什么降了」——按时间、地域、品类还是渠道拆？没思路就把十几个维度全拆一遍 |

正文另举："'最近一个月利润'是本月至今还是过去 30 天？'销售额'是否等于 GMV？"

## 语义平台：四层架构 + 三类资产

### 四层架构（配图）

| 层 | 内容 |
|---|---|
| 01 数据接入 · 计算加速 | 支持 **40+ 数据源**，亿级数据秒级响应（正文：支持 40 余种数据源） |
| 02 语义资产 · 血缘图谱 | 四类语义资产，关系图谱可追溯 |
| 03 精准召回 · 语义增强 | 分层召回、多路检索，全量资产快速精准召回 |
| 04 语义打分 · 结果沉淀 | 语义打分 + 问答结果回流，越用越准 |

配图设计口号："让语义可定义、可检查、可消费、可反哺——四段首尾相接，**语义越转越厚**。"

正文对应表述：四层为"数据接入与计算加速、语义资产与血缘图谱、精准召回与语义增强、语义打分与结果回流"。

### 三类数据语义资产：什么场景，建什么资产

| 资产 | 定位 | 成本 / 可信度（配图） |
|---|---|---|
| 数据集 | 上面两层的地基 | 构建成本低 · 可信度高 |
| 业务本体语义 | 投入最大，覆盖最广 | 构建成本高 · 可信度最高 |
| 业务数据看板 | 历史已投入，直接可用 | 构建成本极低 · 可信度中 |

### 语义飞轮

配图原文："不必等语义建全再上线——**先挑一个高价值场景跑起来**，靠点赞点踩、澄清结果、badcase 回流把语义补厚，再接下一个场景。定义 · 检查 · 消费 · 反哺，四段闭环。"

正文：实际建设从具体场景开始，通过澄清记录、用户反馈和 badcase 补齐定义。

## Harness：模型负责推理，工程负责兜底

配图副标题："要上生产，必须把工程做扎实——**2026 年完成 100+ 优化，真实场景准确率半年内 66% → 95%+**"。

| 关 | 名字 | 做法（配图原文） | 正文对应 |
|---|---|---|---|
| 1 | **选数关** | 从上千个指标中圈定候选；召回与澄清阈值可灵活调配；低置信时唤起专属澄清工具 | 选数时从大量指标召回候选，低置信度则请求澄清 |
| 2 | **计算关** | 复杂计算下沉语义层（时点属性 / LOD / 窗口函数）；**模型只生成 Python + SQL**；数据转换全由代码执行，杜绝幻觉 | 时点属性、LOD 和窗口函数等复杂计算由语义层管理，模型生成 Python 或 SQL，代码负责执行 |
| 3 | **权限关** | 行 / 列 / 表权限动态绑定用户属性；拦截每次查询，把权限动态注入 DSL —— **换什么问法都绕不过** | 行、列、表权限与用户属性绑定，在查询 DSL 中校验 |
| 4 | **验证关** | 把不可见的推理过程变成可验证的证据链；执行失败可自动重试，结果可二次修改 | 执行失败可以重试、修复并留痕 |
| 5 | **评测关** | 每次换模型结果都不一样？给到用户的升级没有质量保障？基线用例取自线上真实问答，badcase 持续回流，**已累计 1000+ 用例**，驱动准确性由被动变主动 | 真实问答和 badcase 持续进入评测集；2026 年完成 100 余项工程优化、积累 1000 余条评测用例，真实场景准确率半年内从 66% 提升至 95% 以上 |

原文结论："结果涉及语义、选数、执行和评测等多项改造，**不能只归因于模型**。"

## 从问数到资产沉淀（配图）

配图《DataAgent：从问数到资产沉淀的全链路拆解》，副标题"不止是我问你答，我们希望把问的都沉淀为企业自己的资产，在发现问题时能够主动推送风险"。图中为 5 个环节（配图标注，含界面截图示意）：

1. **智能问数** —— 自然语言问数 · 信息不全主动澄清 · 口径长期记忆
2. **归因分析** —— 多维拆解 · 因子拆解 · 定位核心驱动因子
3. **结果交付** —— 一次问数，直接出报告 / 网页 / 办公文档
4. **技能沉淀** —— 把分析过程固化成技能 · 个人经验变组织能力
5. **定时推送** —— 自然语言创建定时任务，自动推送到企业 IM

正文对应："在一次问数之后，业务人员还可以继续拆解指标变化、追查原因、生成报告；**确认过的分析步骤可固化为 Skill**，通过定时任务推送到企业 IM。"

> 配图中各环节的界面小字（表格数值、报表字段）属截图示意，非结论性数据，本文不予转录。

## 制造业客户案例：订单全链路分析

配图《制造业订单全链路分析——从采购入库到客户签收，让订单数据从报表里真正"活"起来》。

| 部分 | 内容（配图原文） |
|---|---|
| ① 业务痛点 | **产销脱节**：销售接单与生产排产各算各的，达成率无人拉通；**交付阻塞**：订单卡在哪个环节、卡多久，靠人工逐层追查；**被动响应**：问题发现时损失已发生，等到月报才知道出了事 |
| ② 解法 | **全链路覆盖**：一条线打通六个节点（采购入库 → 生产排产 → 订单执行 → 仓储发货 → 物流在途 → 客户签收）；**语义图谱 + 智能归因**，把全链路串成一条可追查的线；**分钟级健康度诊断**（每个节点实时算达成率，异常自动标红并逐层下钻，直接定位到环节与责任人） |
| ② 解法（成果模块） | **产销计划与订单履行健康度**：指标图谱串联销售、生产、采购各节点，自动提取数据并计算达成率，支持根因分析与异常追查；**订单交付风险实时监控**：基于订单明细表实时监控交付风险，自动计算完美交付率，分析各环节耗时与瓶颈 |
| ③ 量化收益 | 问题排查效率提升 **90%**（从数天缩短到数分钟）；订单准时交付率提升 **10%+**（交付风险提前预警）；产销计划达成率提升 **15%**（销售与生产同口径可追） |
| ① 范式转变 | 被动响应 → 主动预警与预测治理：一线业务人员用自然语言直接提问，系统主动推送口语化改善建议——"听得懂、用得上" |

正文对应："采购入库、生产排产、订单执行、仓储发货、物流在途、客户签收六个环节被组织成分析链，统一计算产销计划达成率、订单履行和完美交付率，并沿环节定位延误。该项目披露，排查从数天缩短至数分钟，效率提升 90%；订单准时交付率提升 10% 以上，产销计划达成率提升 15%。**这些改善来自该客户项目，不能直接外推**。"

## 与开发治理平台的关键差异

原文第 5 节给出一张对照（配图《多种不同的策略问题》）：

| 维度 | 开发治理平台 | DataAgent |
|---|---|---|
| 建设范围 | 4 层架构：接口（MCP/CLI）、技能 Skill、语义、Agent；**建设重点到语义层基本上结束了** | 在语义之上做了很多 **Harness 工作**（意图识别、问题澄清等），确保回答准确 |
| 建设方式 | 主要依靠数仓**自底向上**建设，自动化层度很高，基本**上人工介入很少** | **自上而下**，需要先整理用户指标实体，然后构建整个语义本体，**需要比较多的人工辅助** |
| 主要考虑原因（配图） | 平台主要面向**已经通过工具治理的数据**，很多标准已经存在，更容易标准化 | **DataAgent 没法用这个作为假设前提** |
