# Skill 与 Agent 的边界：数据平台的分层架构实践

> 核心主张：不要给整条任务贴「Agent」标签，要拆开看每一个决定。平台已经确认、可以复用的事实（FACT）应作为平台资产供给；可以测试、会反复出现的步骤（METHOD）写进 Skill；机器可判定、影响大的约束（GUARDRAIL）交给 Gateway / 服务端；风险高且机器难以可靠判断的（ESCALATE）走澄清、人工审批或失败关闭；剩下的运行时判断（RUNTIME）才交给 Agent。一句话：**让 Agent 少猜，让平台多知道一点。**

> 演讲嘉宾：郭志浩，瓴岳信息（洋钱罐）· 数据平台数据应用负责人，负责数据应用平台建设（互联网金融场景）与 AI 数据应用落地（智能 SQL · 报告 · 语义资产）。
> 场合：DACon 2026 北京站「Data Engineering Agent：数据工程智能」
> 说明：本页依据 26 页 PDF 逐页 `pdftotext -layout` 取文本层并逐页视觉复核（含平台架构图、判定树、SQL 示例、Trace 回放与评测数据页）整理。案例与评测来自脱敏后的专项实践；演讲者声明「说明当前业务条件下的选择，不代表所有场景只有一种答案」。

## 背景与问题

### 用一条 SQL 请求走完平台、协作与边界

演讲路线分三段：**01 看全貌**（数据应用平台架构，P4–P5）→ **02 走一遍**（Tool、Skill 与 Agent 如何协作，P6–P14）→ **03 划边界**（哪些交给 Skill、Agent 与平台，P15–P20）。贯穿全程的是一条真实用户请求：

> 查询 2026 年 9 月 APP 渠道的新客转化率，并按周拆分

面对这条请求，先拆出里面的每一个决定：

| 来自请求中的 | 需要做的决定 | 归属 |
|-------------|-------------|------|
| 新客转化率 | 「新客」怎么定义？分子、分母各取什么？ | FACT 已知事实（指标定义） |
| APP 渠道 | APP 在字段里究竟存成什么值？ | FACT 已知事实（**本次缺失**） |
| 2026 年 9 月 · 按周 | 自然周怎么切？取哪个统计快照日？ | FACT 已知事实 |
| 整条任务 | 转化率 SQL 按什么步骤生成？缺枚举时先探查什么？ | METHOD 可复用方法 |
| 句中没有写 | 返回空集时，应该怎样解释？ | RUNTIME 运行时判断 |
| 句中没有写 | 当前用户有没有权限？能查哪些数据？ | GUARDRAIL 平台底线 |

这张表是整场演讲的缩影：**FACT 缺失会直接导致错误，而表面症状却出现在模型写 SQL 那一步。**

### 平台总览：一条任务如何被整个平台共同承接

平台分为四块：

- **真实场景**：智能 SQL（生成 · 纠错 · 优化）、语义资产推荐（指标 · 关系 · 映射）、定时报表（平台调度 · Skill）、报告交互（发布 · 评论 · 追问）。
- **一次任务的主链路**：任务入口与作用域（身份 · 空间 · 会话）→ Context 装配（检索 · 任务信息包）→ Agent Runtime（Skill · 编排 · 判断）→ Gateway / Tool（MCP · 策略 · 执行）→ 执行与成果（SQL · 报告 · 渠道）。
- **支撑当前任务的两类资产与一类控制**：事实资产（语义模型 · 元数据 · 数据状态）、方法资产（Skill · 版本 · 适用范围）、平台底线（权限 · 只读 · Explain · 资源范围）。
- **治理反馈闭环**：Trace / 回放（版本与轨迹）→ 候选资产（来源与证据）→ Owner 审核（冲突与时效）→ 评测（结果与过程）→ 版本化发布（事实或 Skill）。

总原则：**平台提供事实和受控能力，Agent 做现场判断，治理闭环沉淀长期资产。**

## 方案/架构

### 责任边界：同一条请求，四类责任必须分开放

从任务里取出一个决定，自上而下判断它该放在哪里：

| 顺序 | 判断问题 | 是 → 归属 | 例子 |
|------|---------|----------|------|
| Q1 | 是平台已经确认、可以复用的事实吗？ | FACT → 平台资产 | 指标定义 · 物理映射 · 已确认枚举 |
| Q2 | 是可以测试、会反复出现的步骤吗？ | METHOD → Skill | SQL 生成步骤 · 探查顺序 · 检查与输出方法 |
| Q3 | 是机器可判定、影响大的约束吗？ | GUARDRAIL → Gateway / 服务端 | 权限 · 只读 · Explain · 结果范围 |
| Q4 | 风险高，且机器难以可靠判断吗？ | ESCALATE → 澄清 / 人工审批 / 失败关闭 | 不强行自动化 |
| 否 | 以上都不是 | RUNTIME → Agent 现场判断 | 依赖当前证据：意图是否明确、缺什么、证据是否足够 |

一句话概括：**事实提供依据，Skill 提供方法，Agent 做现场判断，平台守住底线。**

### 平台能力分层（完整架构）

附录 A2 给出 DataLumina 完整平台架构，分为五层加一条治理闭环：

| 层 | 组成 |
|----|------|
| 用户与应用层 | 数据应用（Data Agent · 数据洞察 · 异动归因）、任务交互（自然语言请求 · 多轮任务）、智能 SQL（SQL 生成 · 纠错 · 优化）、项目空间（身份 · 会话 · 上下文管理）、报告应用（日报 · 周报 · 月报 · 分析报告）、成果物（SQL · 文档 · 报告 · 分析结论）、交互入口（Web · 桌面 · 企业微信 / 飞书 / 钉钉）、报告交互（评论 · 追问 · 补充分析） |
| 平台能力层 | Skill 资产（平台 / 项目 / 个人 · 版本管理）、统一检索（语义模型 + 元数据资产）、语义模型（指标 · 维度 · 关系 · 映射）、元数据资产（库表 · 分区 · 枚举 · 状态）、MCP / Tool（能力发现 · 参数化调用）、Gateway 策略（权限 · 只读 · Explain · 范围）、报告服务（调库 · 托管 · 版本 · 渠道） |
| Agent Runtime | 任务与工作流（任务拆解 · 编排 · 执行状态）、Context / Session（任务信息包 · 会话状态）、Model Runtime（模型调用 · 多模型路由）、Tool / MCP Runtime（技能调用 · 状态管理）、Skill Runtime（发现 · 过滤 · 按需加载）、运行时判断（缺口识别 · 探查 · 证据充分性） |
| 执行与资源层 | SQL 执行服务（只读校验 · Explain）、引擎路由（特征 · 队列 · 资源策略）、数据仓湖（数仓 · 湖仓 · 数据库）、报告托管（版本化成果物）、渠道服务（企业微信 · 钉钉 · 飞书） |
| 治理闭环 | 可观测（Trace · 日志 · Tool 调用 · 任务回放）、评测（结果 · 轨迹 · 确定性 · 成本）、资产发布（候选审核 · 版本 · 回滚）、审计与安全（脱敏 · 留存 · 访问合规）、运营管理（Skill · 报告 · 数据资产生命周期） |

平台能力层里有一条**一次能力调用的责任链**：身份 / 空间 → 任务信息包 → Skill → Agent 判断 → Tool → Gateway 策略 → 放开 / 拒绝 / 询问。安全执行域的原则是最小权限 · 只读与 Explain · 资源限制 · 结果范围 · 敏感信息治理。原页还标注：任一 Skill 都不能扩大 Tool 能力或数据权限；Runtime 不是最终授权点。

### 请求链路：Agent 决定是否探查，平台决定能否执行

一次任务的主链路上，五个环节依次是：任务入口与作用域 → Context 装配 → Agent Runtime → Gateway / Tool → 执行与成果。链路回放（后续页）会把每一步标成 OK / MISS / SKIP / WRONG / PASS / EMPTY。

## 关键工程做法

### Skill 分工：按场景拆分，各管一件事

每个 Skill 写清楚做什么，更写清楚不做什么（脱敏节选）：

| Agent | 做什么 | 不做什么 |
|-------|--------|---------|
| SQL Agent | SQL 生成、标签 / 人群取数、SQL 纠错、SQL 优化 | 纠错只修实证报出的错，不改需求；优化依据作业运行信息 |
| 数据探查 Agent | 单表探查（EDA） | 只探查一张表，不生成交付用 SQL |
| 定时报告 Agent | 按报告 Skill 产出 HTML，产出后自检 | 无人值守，不允许向用户提问 |
| 报告追问 Agent | 报告答疑：理解 · 口径复核 · 归因 | 只依据这版报告的口径与正文，本期不回源查库 |

另有**澄清组件**：唯一允许向用户提问；只在检索与裁决之后仍有关键歧义时调用；所有问题合并为一次提问，答完回到原流程。

记忆点：**Skill 的边界，写在「不做什么」里。**

### Skill 的骨架：五个阶段与探查规则

SQL 生成 Skill（平台内实际运行版本，脱敏）在同一次回复里连续完成五个阶段：

| 阶段 | 做法 |
|------|------|
| 01 解析查询要素 | 先写出指标、时间、维度、过滤、粒度五要素；**这一步不调用任何工具** |
| 02 匹配元数据 | 语义检索选表，按「就上取数」的优先级裁决用哪张表 |
| 03 数据探查（按需） | 只在分区缺失、元数据不足、枚举未知时才查数据 |
| 04 生成说明 | 先说明口径和取舍，再写 SQL |
| 05 生成 SQL | 先落盘，再做 Explain 和权限检查，通过后才输出 |

何时探查枚举（规则原文，节选）：

- **需要探查**：字段用于 WHERE / CASE，但用户和字段注释都没给出真实枚举值。
- **不探查**：用户或注释已给出取值；主键、时间、自由文本、连续数值。
- **约束**：每张表最多发一条枚举分布查询，多个枚举列合并。

共享规则一处定义、多个 Skill 引用：权限校验、SQL 安全、分区规则、选表规范、开发标准、代码风格、自检校验；同一套规则被生成、澄清、纠错、优化等 Skill 引用。

原则：**Skill 写的是方法和触发条件；事实本身，仍要由平台供给。**

### 写 Skill 踩过的坑：模型觉得合理，往往是错的

| 坑 | 模型的错觉 | 真相 | 写进 Skill 的规则 |
|----|-----------|------|------------------|
| 抢跑 | 「先调检索看看有哪些表，再写要素会更准」 | 要素是检索 query 的来源；先调工具，检索就失去了依据 | 先写五要素，零工具调用 |
| 自截断 | 「要素写清楚了，表名待定，先停下让用户补充」 | 没有 SQL 的回复对用户没有价值；「待定」不是终止信号 | 只认四个合法终止点 |
| 拆词检索 | 「整句太长，拆成几个关键词分别检索，召回更全」 | 切碎会丢掉修饰关系，召回质量反而更差 | 同类库只检一次，传整句 |
| 时间戳单位 | 「时间戳应该是秒，直接 from_unixtime」 | 秒和毫秒差 1000 倍，Explain 照样通过 | 先采样看位数，分不出就澄清 |

结论：**方法不能靠模型自觉，要写成可测试、可版本化的规则。**

### 脱敏示例：平台知道怎么算，却不知道 APP 对应哪个值

Agent 生成的 SQL 结构完整：按周截断 `apply_time`，用「成功放款新客数 ÷ 有效申请新客数」计算转化率，从申请表 `dwd_apply` 左关联放款表 `dwd_loan`（关联 `apply_id`、快照日 `dt`、`loan_status = 'SUCCESS'`、放款时间在申请后 7 天内），过滤快照日、新客、有效申请，最后 `GROUP BY 1`。

问题出在渠道过滤：

```sql
-- 修改前
AND a.channel = 'APP'
-- 修改后
AND a.channel = '0'
```

每一处依据来自哪里（原页标注）：

| 依据 | 状态 | 说明 |
|------|------|------|
| 指标定义 | ✓ | 成功放款新客数 ÷ 有效申请新客数 |
| 时间口径 | ✓ | 自然周 · 申请后 7 天内放款 |
| 物理映射 | ✓ | 申请表、放款表、关联关系与字段映射 |
| 数据状态 | ✓ | 两表全量快照 `dt = 2026-10-08` |
| 任务范围 | ✓ | 服务端注入，不出现在 SQL 里 |
| 已确认值字典 | ✗ | 缺失：APP 实际对应 `channel = '0'` |

执行结果：语法正确、权限通过、Explain 通过，但**返回 0 行**。记忆点：**空结果不等于转化率为 0%，执行成功也不等于业务正确。**

### 链路回放：问题不是发生在一层，而是沿链路传播

同一条用户请求的 Trace 共 8 步：

| 步 | 环节 | 状态 | 证据 |
|----|------|------|------|
| 01 | Skill 加载 | OK | `sql-generation@v3.4` |
| 02 | 解析要素 | OK | 指标、时间、维度、过滤、粒度 |
| 03 | 匹配元数据 | MISS | 已选表，但未返回 channel 枚举含义 |
| 04 | 数据探查 | SKIP | 未识别枚举缺口，未触发探查 |
| 05 | 生成 SQL | WRONG | `WHERE a.channel = 'APP'` |
| 06 | Gateway 校验 | PASS | 权限 · 只读 · Explain 均通过；只查可判定规则 ≠ 业务正确 |
| 07 | SQL 执行 | EMPTY | 执行成功，但结果集为 0 行 |
| 08 | 结果处理 | SKIP | 未触发「异常空结果 → 回退验证」 |

根因分三层：

- **ROOT CAUSE（根因 · 事实没有被供给）**：权威资产缺少当前作用域映射 `channel = '0' → APP`。
- **SYSTEMIC（系统性原因 · 没有兜底）**：未识别枚举缺口、未触发探查、无异常空结果回退验证。
- **SYMPTOM（表面表现 · 模型写错）**：业务名称直接写成物理枚举 `'APP'`。

结论：**模型写错只是最后一棒；事实未被供给、系统又未兜底，错误才最终到达用户。**

### 资产沉淀：一次探索如何变成长期资产

写回闭环六步，三个 GATE：

| 步骤 | 内容 | 关卡 |
|------|------|------|
| 01 探查结果 | Agent 按 Skill 调用 Tool | — |
| 02 候选资产 | 带来源、Trace 和适用范围 | — |
| 03 自动校验 | 来源、敏感性、对数、冲突与时效 | GATE |
| 04 Owner 确认 | 数据或领域负责人审核 | GATE |
| 05 评测 | 验证结果与生产适用性 | GATE |
| 06 版本化发布 | 进入项目元数据资产 | — |

任一关卡未通过 → 退回候选，不覆盖正式资产。

同一条任务的前后对比：这一次「统一检索 MISS（缺少 channel 枚举含义）→ 探查 Tool CALL（取得候选值与证据）→ 生成候选 DRAFT」；后续同类任务「统一检索 HIT（命中已发布事实 `channel = '0'`）→ 生成 SQL OK（不再重复补缺式探查）→ 平台检查 PASS（权限 · Explain · 数据状态照常检查）」。

原则：**Agent 只能生成候选；Owner 确认并通过评测后，才能版本化发布。**

### 专项评测：已确认事实注入是否真的有效

实验只改一个变量：A 组任务信息包缺少已确认枚举；B 组任务信息包包含人工确认后的枚举。结果：

| 指标 | A 组 | B 组 | 变化 |
|------|------|------|------|
| 执行准确率（按 case 统计，n = 300，3 次全对才算对） | 34.7% | 85.3% | +50.7 个百分点 |
| 平均 Tool 调用 / 次运行（含元数据、语义、探查、执行、Explain、权限校验） | 25 次 | 15 次 | 降低 40% |
| 生成耗时 P95（不含最终 SQL 执行） | 500 秒 | 200 秒 | 降低 60% |

评测设置：两组一致——模型、Skill、语义模型、Tool、执行引擎与采样参数均一致，无空结果回退；数据加固定时间边界。样本为专项集 300 条（持续扩充中），每条独立运行 3 次。判定标准：与参考查询结果一致（允许写法、用表不同），参考 SQL 人工复核，空结果单独标注、人工确认。

演讲者给出的边界：**在枚举缺口专项集上，结果支持事实注入带来收益；外部有效性仍需复验。**

### Skill Market：可以共享，但权限不能随它扩散

Market 的完整流程：

1. **作者 / 项目**编写方法，创建 Skill（个人 / 项目）。
2. **提交**：声明版本依赖。
3. **自动检查**：测试与安全。
4. **人工审核**：确认发布资格。
5. **版本化发布**：支持回滚。
6. Runtime **安装**（个人或项目）。
7. **加载**：按项目策略过滤。
8. **轨迹与评测**：升级或回滚。

生产轨迹与项目评测会反馈到 Market，触发升级、下架、回滚。三层职责必须分开：

| 层 | 职责 |
|----|------|
| Market | 管理分发与版本；**不授予数据权限** |
| Runtime | 管理发现与加载；按项目策略过滤 |
| Gateway / 服务端 | 管理可执行能力；权限由服务端判定；执行 Tool 时逐次判定权限 · 只读 · Explain |

记忆点：**安装 Skill 不授予新的数据权限；脚本、依赖与 Tool 能力仍需受控。**

### Agent 配置：能用什么写在配置里，不写在提示词里

SQL Agent 的工具开关（节选 · 脱敏）：

| 配置 | 值 | 含义 |
|------|----|------|
| `question` | true | 同轮澄清，问完再继续 |
| `write` | true | SQL 先落盘，再送检 |
| `webfetch` | false | 禁止外部抓取 |
| `task` | false | 关闭任务工具 |
| `apply_table_permissions` | false | 禁止自动帮用户申请权限 |
| `list_tables` | false | 表发现统一走语义检索 |
| `find_table_by_keyword` | false | 关键词兜底会伪装成「找到了」 |

两条教训：

- **能力白名单在配置里，不在提示词里**：Skill 写得再好，Agent 能调用哪些 Tool 由平台配置决定；像申请权限这种动作，直接不给。
- **删掉一个工具，换来诚实的「没有」**：语义检索落空时，模型会拿关键词检索兜底，带回一批不相关的表；关掉它，宁可明确返回「没找到」。

原则：**Agent 能做什么，由平台配置决定，不靠提示词约束。**

### 方案路径：三条数据智能路径，语义如何约束 SQL

只看一个轴：SQL 自由度放在建模阶段，还是保留到运行时。

| 路径 | 语义基础 | SQL 产生 | 约束 | 适合 |
|------|---------|---------|------|------|
| dbt Semantic Layer / MetricFlow（建模阶段 · 规则编译） | YAML 模型、实体、维度与指标 | MetricFlow 按合法关系规划 | 依赖前置建模；长尾需扩模 | 稳定 KPI、跨应用一致复用 |
| Snowflake Cortex Analyst / Agents（中间 · 语义接地） | Semantic View 与已验证样例 | Analyst 生成，Agent 编排工具 | 覆盖不足会回退，结果仍需审查 | 治理指标 + 自然语言问数 |
| Databricks Genie / Genie Code（运行时 · 生成式探索） | Unity Catalog 与域级知识 | Genie 生成并可迭代调用工具 | 需持续维护知识、样例与权限 | 湖仓自助问数与复杂分析 |

DataLumina 的定位是「语义接地 · Agent 生成 · 平台兜底」；在原页的示意轴上，它位于「建模阶段 · 规则编译」与「运行时 · 生成式探索」之间。结论：**多类任务并存时，固定 KPI 走规则编译；长尾分析保留受约束的生成式 SELECT。**（来源：Snowflake、dbt、Databricks 官方文档）

## 经验与边界

### 架构取舍：平台侧不天然正确，只是更可追责

| 收益 | 成本 |
|------|------|
| **责任更清晰**：已知事实、可复用方法与运行时判断分开放 | **持续维护**：语义模型、元数据资产、Skill 与评测集需要运营 |
| **问题可定位**：错误能够回放、评测，并定位到具体层 | **控制代价**：增加时延、误阻断与组织协作成本 |

采用前提（任一项不满足，就不宜直接照搬）：

- 有明确的 Owner
- 有权威语义来源
- 有审计体系
- 不是一次性低风险查询
- 能持续维护资产

结论：**平台让责任更容易被版本化、验证和追责，但不会自动变得正确。**

### 行动清单：明天回去，先复盘一条失败任务

复盘对象：取一条失败任务的 Trace，逐个列出其中的决定。

1. **归类决定**：把每个决定放进四个格子（FACT / METHOD / RUNTIME / GUARDRAIL）。不要先问「这是不是 Agent 任务」，先问每个决定属于哪一格。
2. **定位错层**：已知事实 → 平台资产；可复用方法 → Skill；运行时判断 → Agent；平台底线 → Gateway / 服务端；高风险且难判定 → 澄清 / 人工 / 失败关闭。
3. **校准边界**：用评测决定边界是否移动——结果正确、轨迹合理、减少无效探查、避免误阻断、成本与时延可接受，逐项打勾。
