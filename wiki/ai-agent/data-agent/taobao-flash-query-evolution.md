# 淘宝闪购查询链路：三代引擎演进与多模融合检索

> **一句话定位**：发布只是把数据写入了事实源，查询侧还需要一套对应的架构支撑。从事实源到查询侧，底层引擎经历了三次迭代，但**治理内核始终未变**——对象、关系、版本、审批、审计始终只有一份；改变的只是查询链路：数据刷新频率、检索任务执行方、结果合并位置。换引擎不换治理，知识可信度也就不再依赖任何一代引擎。

来源：同 [[taobao-flash-ontology-platform]]（阿里技术，2026-11-18）。平台总览与治理链路见该页。

## 三代架构演进

### 四维评价与优先级

评价一代架构的优劣，主要看四个维度：从发布到可查的**延迟**；能否按名称、语义或关系**检索**；多个读模型是否会导致数据**新旧混杂**；以及**排障与容量成本**。四者有明确的优先级：**新鲜度最核心**（决定人与 Agent 看到的是否为同一份数据）→ **表达力**（决定业务能提出多复杂的问题）→ **一致性**（决定出错时能否快速定位）→ **排障与容量**（前三个是架构底线，容量可以通过资源投入和工程手段解决）。

### 第一代：读写分离与离线建图（已退出主链路）

MySQL 既是事实源也是取数入口；DataWorks 在 ODPS 上按 ODS、DWD、ADS 逐层加工；DataX 按日将对象与关系批量同步至 GDB。**取数查 MySQL，关系查 GDB**，两个库各司其职。

这一代解决的是**数据有无**的问题：业务需要查对象、看关系，用两个成熟组件拼装是最快的路径；读写分离、按日分区，出了问题也能逐层回溯到具体批次。代价集中在新鲜度与表达力上：

- 数据变更**次日才可见**，图库与业务库独立刷新，时间点还需额外对齐；
- 查询仅支持名称与精确字段，业务口语、简称、同义词基本无法匹配（业务说「订单量」，系统里叫「有效订单数」，库里搜不到）；
- 两库缺乏统一的身份体系——查「这个指标关联了哪些对象」需先在图库定位节点再回业务库捞明细，两次查询由应用层拼接，任一侧未刷新就会导致结果错误。

### 第二代：跨引擎拼装与读写分离（现役）

MySQL 经 ODPS 分层加工后，同步至 **GDB、OpenSearch、Hologres** 三个读模型：OpenSearch 承担全文检索（BM25 倒排索引负责召回，精排表达式负责打分），GDB 承担关系查询，Hologres 承担明细与宽表，三份结果由应用层按对象标识拼接。这一代无需等待统一引擎成熟，召回与排序便能先行运转。

但补齐引擎不等于打通语义：

- OpenSearch 的召回仅有稀疏检索这一路：名称与 URI 进入 BM25 倒排索引，**向量相似度仅作为精排表达式中的打分项，不参与候选生成**——语义相近但字面对不上的查询没有召回路径，问题在于缺少稠密向量召回（dense retrieval）。
- 多副本一致性：一次「先搜名称、再展开关系」的查询需同时访问搜索和图库两个引擎。若指标改名、数据集更换，搜索索引先刷新而图库下一批次尚未到达，用户查到的就是新旧混杂的说明。缩短批次间隔只能收窄窗口，无法消除；只要窗口存在，两个引擎各自都报成功，结果拼起来却对不上，核对只能由应用层承担，最终靠人工比对索引、图库和应用层合并三处不同源的日志来定位。

### 第三代：实时多模与流式同源（部分替代）

第三代将拼装逻辑**收回数据层**：MySQL 变更经 CDC 进入 [[paimon]]，[[apache-flink]] 分两条作业处理向量与图同步，连接器将节点、关系和向量 MERGE 写入 **NeuG**——图遍历、BM25 全文、HNSW 向量三种索引共存于同一实例，应用层仅负责融合、范围过滤和可选精排。

在这条路径上，**检索结果直接成为图节点**：命中后无需换库、无需重新对齐身份，可直接从命中节点沿关系扩展，跨引擎拼装环节就此消失。

但复杂度并未消失，只是从应用层转移到了数据链路：流式投递带来至少一次语义，下游必须自行吸收重复数据；受图结构约束，节点必须严格先于边写入；一旦发生删除，变更需沿链路传播；若作业从检查点恢复，还需额外核对漏写与重复。向量与图的刷新节奏不一致会造成读取时的数据不同步；加上写入压力直接作用于读侧，容量存在硬上限。读写同实例还带来额外开销：批量回填与重建索引会占用查询的 CPU 和内存，用户能感知到变慢。平台目前的策略是接受这一现状，将重负载任务调度至低峰期。

第三代是**设计上的终态**，落地策略是**双跑**：同一批查询同时发往两套链路，比对对象集合与排序，差异收敛后再放量。双跑期间两套链路均需承担成本，换来的是切量阶段一旦出现问题，退回上一代只需修改一次路由。

### 三代表格

| 维度 | 第一代 | 第二代 | 第三代 |
|------|--------|--------|--------|
| 更新频率 | 按日 | 批量或增量，按批次 | 流式增量，图谱秒级更新，按场景启用 |
| 关系查询 | GDB | GDB | NeuG 图遍历 |
| 全文检索 | 无 | OpenSearch BM25 | NeuG BM25 |
| 向量检索 | 无 | 仅参与精排打分 | NeuG HNSW + 外部 embedding 服务 |
| 明细 | MySQL 直查 | Hologres | NeuG 明细 |
| 结果合并 | 页面按需 | 应用层编排 | 融合检索内一次出结果，主链路仍应用层编排 |
| 主要代价 | 新鲜度、表达力单一 | 多副本一致性、排障 | 流式复杂度、读写同实例、容量上限 |
| 现状 | 已退出主链路，GDB 在第二代继续使用 | 现役 | 部分替代，按场景并行 |

第三代的现状「部分替代」边界落在接口上。**已经切过去的三块**：管理台的融合检索（三路召回都打 NeuG，融合在应用层做）；场景发布后的闭包重算（走影子模式，固化结果仍以 MySQL 为准）；明细查询（按标识直接在图上取行）。**还没切的是检索与关系查询两条主干**：OpenAPI 的检索、MCP 与 HSF 的读接口仍然打 OpenSearch 与 GDB，宽表仍然打 Hologres。把这两条主干逐条切过去，才是这一代剩下的工程量。

> 第三代把复杂度从应用层挪到了数据链路——这意味着这一代的难点不在选型，而在如何把一条变更安全地写进图。引擎可以换，但写入路径换不了，这条路径必须跟底层数据库的变更节奏、幂等能力和恢复方式严格对齐。

## 第三代写入链路：节点先于边、三层幂等与写租约

这一代在写入侧的目标是一个**单实例的多模图数据库**：「多模」指三种索引建在同一份在线数据上，各对应一种查法。一份节点数据同时进入图存储、倒排索引与向量索引，平台不再维护三份派生数据，也就不存在各刷各的、刷到一半状态不一致的问题。**写入侧一致，是查询侧一致的前提。** 代价是链路变长：这条链路必须**可重放、写入必须幂等、并且能从检查点恢复**——这三个工程约束不仅决定了故障之后能不能把数据补对，也直接卡死了容量到顶时能不能平滑扩容。

### 节点先于边

一条关系要落到图上，必须先找到两端节点；缺了任何一端，写入语句可能正常结束，实际什么都没写进去——这类失败**不报错，只表现为「这条关系查不到」**。平台的规避办法是让节点和边共用一个写入端，同一批写入里先处理节点，再处理关系。

### MERGE 三层幂等

重试带来的重复投递靠 MERGE 吸收，幂等必须在三个层面上同时成立：

| 层面 | 表现 |
|------|------|
| 节点 | 基于固定标识重复写入后，图上仍然只有一个节点 |
| 属性 | 修改属性后再写入，按原标识也能读回新值 |
| 边 | 同一对端点重复写入，最终只保留一条边 |

### 时序、删除与漏写

- **「发布即一致」给不出**：索引与图不在同一刻就绪，平台只承诺「发布后可见」。
- **删除传播**：源库物理删除后，不仅要确认删除事件传到了图里，还要检查原先指向它的关系是否被妥善处理。
- **漏写陷阱**：如果作业跳过首次全量快照、直接从增量起点消费，监控会一直显示有进度，早已发布的对象却查不到——这类「看着在跑、其实漏了一截」的问题，比直接报错难排查得多。

### 写租约

同一时刻只能有一个写入端持有**写租约**（独占写入权限），避免两个写入端同时 MERGE 导致版本错乱。旧端一旦故障失联，从租约超时作废到新端接管之间，会有一段变更进不来的空窗期，长短取决于续期与检测策略。因此平台**只承诺写入最终会恢复，不承诺写入过程不中断**——写租约解决的是双写冲突，而接管之后的容量与恢复速度则是另一回事。

## 查询链路：三路协同、RRF 融合与降级契约

一次查询牵动**三段协同**，而非三条通道各自为战：关键词与向量**并行召回候选** → 图扩展以两者的候选集为**种子** → 融合之后再进行**可选精排**。

### RRF 倒数排名融合

三路通道的原始分处于不同尺度：BM25 随查询长度与语料分布漂移且无上限；余弦相似度限定于 [0,1]；图扩展分则按跳数衰减。若采用加权求和，需为每路设计固定的映射与权重，且这组参数往往只适配特定问法，泛化成本极高。**RRF（倒数排名融合）仅依赖名次**：三路各自排名后直接按倒数名次累加，无需额外标定；代价则是舍弃了绝对分差，换取了跨查询的稳定性。加权求和并未废弃，而是作为对比基线保留，支持按请求动态切换。

### 精排降级是接口契约

融合之后最容易出问题的是精排环节：一旦超时或失败，直接返回空结果会让用户误以为平台没有这份知识。因此平台会**保留融合顺序，并在响应中标记降级状态**——这个状态字段是接口契约的一部分，向调用方显式声明「可用性优先于排序质量」的取舍，确保下游能基于真实的降级情况做兜底，而不是去盲猜。

### 图内遍历 vs 应用层遍历

命中的标识直接对应图里的节点，平台无需在应用层做 ID 映射，这不仅省掉了一次网络调用，更规避了「两个引擎指代不同对象」的潜在风险。一次**两跳**的关联查询：放在应用层做广度优先，需要不断向图库发起 RPC 调用，6 次网络往返加上序列化开销累计耗时超过 5 毫秒；把这段逻辑下推到图引擎内部变成一次变长遍历后，应用层只需 1 次网络往返，总耗时仅 1.58 毫秒，**性能提升 3 倍**。

### 截断陷阱案例

引擎内的遍历虽然快，但一旦在过滤逻辑上出偏差，就会带来更隐蔽的灾难。排查中曾遇到的典型案例：

> 业务人员在图谱页面选择相邻对象查关联表时，能看到 **381 个表对象**；但调用方通过接口查同样两跳、目标类型设为表对象时，拿到的却是**空列表**。

原因：接口当时**只在最后一跳按类型过滤**。交易订单连出的关系很多，系统先按返回条数截断了一部分，再往外查时，恰好截掉了通往表对象的路径。这种「看着有路，实则截断」的返回对 Agent 存在严重误导——给 Agent 一个空列表，它无从判断是图里确实没有这样的表，还是路径根本没有查完。原本为了控制返回条数的性能保护，最终变成了知识检索的盲区。

### 四种提问方式的能力边界

| 读者的问题 | 用到的能力 | 能保证 | 不能保证 |
|-----------|-----------|--------|---------|
| 我知道名称 | BM25 全文检索 | 名称与关键词匹配 | 关键词相近不等于业务含义相同 |
| 我只知道大概意思 | HNSW 向量近邻 | 找到语义相近的候选 | 相似不等于相关，仍需排序与人工核验 |
| 我想知道它和什么有关 | 图遍历 | 沿已建关系找到邻近对象 | 路径存在不等于因果，也不等于逻辑推理 |
| 我想一次查全 | 多模索引同实例 | 结果直接是图节点，免去跨引擎关联开销 | 多模同源不等于跨作业强一致快照 |

## 效果评测：9511 条真实回放

用线上真实查询回放来量化三路组合的效果：将 **2026 年 10 月生产环境**里出现过的查询原样重放，比较融合检索与全局搜索基线的排序结果。回放集共 **9511 条**，分为两段：395 条页面检索与 9116 条 MCP 检索词。

**可用性差异**：在 395 条页面检索中，旧链路有 16 条返回空列表，而融合链路为 0——旧链路大约**每 25 次提问就有一次拿不到任何结果**。连结果都无法返回，排序质量便无从谈起。

**排序质量**（Top-1 字面命中率）：

| 段 | 融合链路 | 全局搜索基线 |
|----|---------|-------------|
| 页面检索 | **54.2%** | 42.8% |
| MCP 检索 | **14.5%** | 11.7% |

融合链路综合评分 **0.5103**，优于基线的 **0.4585**。

**失败样本归因**：失败样本并非均匀分布——395 条页面检索中有 **181 条**在两套链路的候选里都没有字面命中，占比高达 **45.8%**。对这批样本，排序策略是无效的，因为两侧本来就没有召回候选。拆解这 181 条：

| 场景 | 条数 |
|------|------|
| 中文短语与行业口头叫法 | 137 |
| 含空格混排 | 18 |
| 技术串与表名 | 14 |
| 拉丁缩写代号 | 12 |

归因不在排序，而在**语料**——别名没有归一、指标定义缺失。这类问题只能回到本体去补充内容，单靠调权重是解决不了的。

## 系统边界与当前上限

**读写干扰**：写入对读取的实际影响只能通过混合负载压测来量化。空载时详情查询的 p99 为 **54 毫秒**；当起两个写入端持续做节点与边的 MERGE、每秒处理 **11.6 条**语句时，p99 升至 **119 毫秒**。读取性能并未被拖垮，但余量仅剩一倍多——在写入量翻倍之前，容量必须先行扩容。

**单点瓶颈**：单实例架构没有在线只读副本，容量到顶时既无法通过增加副本分摊压力，也无法通过降级查询来绕过。

**时序错位**：向量与图不在同一刻就绪——向量由另一条作业先算，再并回同一次写入；并回之前，节点要么没有向量，要么还是上一版文本的向量，要等下一次变更或回填才补上。因此系统对外只能承诺「发布后可见」，无法承诺「发布即一致」。删除与恢复机制决定了运维动作不能只盯着源库：源库删除了，图里可能依然存在；检查点恢复后，也可能出现漏写或重复。

**后续演进**：读写同进程且缺乏在线只读副本是这一代架构的固有短板，下一步优先落地**周期检查点与冷备**，待恢复路径跑通后，再评估引入只读副本——在没有恢复机制的前提下直接上副本，只会将风险延后，而非消除。规则挖掘侧目前全靠人工预审兜底，尚未建立明确的准入标准，下一步需要建立评估集与准入规范，评估题目应从**线上真实问题**中抽取（自造题只能验证已知场景）。检索侧的首版人工标注集已经就位，足以支撑回归测试，但尚不足以作为上线准入的依据，目前主要缺失的是**负样本与同义改写问法**。

## 子图场景圈选与上下文交付

跨过「查得到」这道门槛后，一次查询要真正「用对」，还需满足四个要求：**范围准确、顺序合理、证据完整、上下文可控**。这些要求不能交由调用方自行拼装，在架构上分三处落地：范围由场景对象管理，顺序由检索策略约束，证据与上下文则由响应契约来承载。

### 圈定范围：用子图快照对抗模型变更

查询范围由**场景**决定，场景在平台上是可管理的对象，一份范围配置包含：圈选条件、子图快照，以及仅限该子图的访问凭证。具体做法：先在图上圈选策略对象作为**种子**，沿关系扩展至实体对象，最后固化为**子图快照**。

快照的核心价值在于**稳定性**：同一个场景今天和下周查到的必须是同一批对象，不能因为底层模型被他人修改，导致范围发生无声偏移。以零售商品定价场景为例：圈选起点 35 个，边界将 907 个实体对象收窄至 51 个，10709 个策略对象收窄至 1488 个，快照内合计 **1539 个节点、4398 条关系**。

圈选最容易出错的地方不在算法，而在条件逻辑：

- **条件组逻辑**：一个场景常由「所有对象」与「某业务线」两个条件组构成，组间是并集（OR），组内才是交集（AND）。若将两条限制写进同一组，交集会把方法论、行动等整批切掉，而预览里仍保留着几百个节点，极难察觉。
- **遍历方向**：正向扩展不会带入反向引用，需用两跳反向查询补齐；反向侧存在 **20000 个节点**的封顶限制，超限即会静默截断。

因此圈选必须算尽完整的子图，预览也必须能直观看出封顶是否被触发。快照的代价体现在时效性上：底层模型一旦修改，快照不会自动跟随更新；在重算的空档期内，新加的对象查不到，删掉的对象却依然存在。为此平台将**快照的生成时间一并带入响应**，让调用方明确知晓这份范围的时间截面。

### 守住边界：范围约束优先于召回数量

超出范围的查询会**直接返回不存在**，平台绝不会隐式将查询扩大到全库——因为 Agent 拿到范围外的答案会直接信以为真；人至少能在页面上通过场景标识判断这条知识的来源。

在范围内，检索顺序是固定的：**先按名称或语义定位对象 → 再沿关系展开 → 最后获取明细**；顺序倒置，后一步便失去可靠输入。这个顺序有数据支撑：在 395 条页面检索中，纯关键词有 258 条无结果，**加入向量召回后全部找回**（找回指候选集中有结果，不等于原词出现在结果中）；而在此基础上叠加图扩展，找回数为 0，甚至会将被命中的目标挤出前列。这说明**图扩展解决的是覆盖面，而非召回率，绝不能将其作为兜底方案**。

### 上下文交付：证据链无损传递

拿到准确的定义，不代表调用方就能「用对」。一条结果至少要能回答四个问题：**这是哪个对象、生效的是哪一版、上一次由谁确认、当前由谁维护**。这四项在底层库中都是现成字段，难点在于如何将它们无损地传递到响应中——中间任何一层如果为了压缩响应体积将其裁剪，调用方就只剩一个名称加一段描述，看似完整，实则无从核对。

因此 Agent 侧必须多做一件事：**按上下文预算裁剪返回**。默认仅提供摘要，全量字段由调用方显式声明；响应中需附带提示，说明还有哪些字段未取、下次如何补全。模型上下文存在硬性预算，若单次返回包含数百个字段的对象，不仅会耗尽预算，还会挤占其他关键证据。

以门店周报为例：Agent 的读取顺序是——先读基础约束，再读指标定义，然后读对应的表对象与取数口径，最后展开相关对象；而人打开页面时，看到的是定义、版本、责任人、引用它的报表与接口。**入口不同，路径不同，但最终指向的实体是一致的。**

平台能保证 Agent 拿到已生效版本，并知晓自身所处的检索范围；但无法保证 Agent 一定用对，也无法保证模型不会将定义解释歪——后两者需依靠提示词、评测与业务复核。平台能做且必须做的，是**将可核对的证据链完整交付**。
