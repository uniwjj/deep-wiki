# 网易数帆 AI Native 数据平台

> 来源：微信公众号 DataFunSummit《为 Agent 重建数据层：网易智企产品 AI Native 演进路径》，分享嘉宾蒋鸿翔（网易智企·数帆技术负责人），2026-11-03 18:00 发布。
> 原文结构为 5 节：① 从人工操作到 Agent 调用，数据平台面临三个变化 → ② 让 Agent 用好多模态数据，先统一存储与计算 → ③ EasyData 开放开发治理能力，执行必须受控 → ④ DataAgent 的问数准确率，靠业务本体与 Harness 支撑 → ⑤ 从开发治理到业务问数，人和 Agent 如何分工。

## 一句话概括

数帆的改造主线是：**把数据平台"面向人设计"的标准化动作，开放为 Agent 可以调用、也可以被平台约束的服务**——底层先统一存储与计算让数据"可见"，中间用 EasyData 的接口/技能/语义/场景/入口五层把事情"可做且受控"，上层用 DataAgent 的业务本体 + Harness 把问数"算对且可验证"。

> 原文对改造起因的表述：传统平台三层（NDH 等基础设施承载存储计算、开发治理平台负责集成/建模/质量/数据服务、上层 BI 消费）功能已比较完整，但**操作方式长期围绕人设计**——任务创建、SQL 编写、故障排查、报表解读都要在不同界面完成。

## 背景与规模

| 维度 | 数据 |
|------|------|
| 内部规模 | 服务网易内部 **EB 级数据**、约 **1 万台集群节点**、每天定时调度任务 **超过 50 万** |
| 外部客户 | **大几百家**中大型客户，覆盖金融、国企、制造、零售、物流 |
| 新增业务的负担 | 可能带来**数千乃至上万条任务**；告警能发现失败，但**根因仍需人工沿日志和依赖排查** |
| 外部差异 | 客户在合规、权限、组织流程上的差异，要求自动化能力**可复用、可配置** |

## 三个业务变化（原文标题）/ 三个判断（配图标题）

原文正文称"从基础设施到业务应用，数帆形成了**三个判断**"；配图《AI + Data 时代的 3 个判断》给出了更完整的措辞：

| 判断（配图标签） | 正文表述 | 要点 |
|---|---|---|
| 底座 · 多模态数据的价值会被放大 | 多模态数据会更多地**与库表联合处理**，OCR、语音识别、视觉质检不再只是孤立应用 | 配图列举：图片识别 OCR、语音转文字 TTS、产线质检 CV、电商图文检索、医疗影像、数字档案；判断"传统单点的多模态应用通过 AI/Agent 会被组合，用一套大脑同时看懂文字、图片、音视频，支持跨模态问答与内容生成" |
| 平台 · Agent 成为 AI 时代操作系统 | **MCP、CLI 等接口**让 Agent 可以组织软件服务，用户不必始终依赖 GUI | 配图：虽然很多 App 在抵抗豆包手机，但几乎所有 App/服务都在做 MCP、CLI；列举钉钉办公、千问办公、workbuddy、帝王蟹 |
| DataAgent · 高质量数据是 AI 时代的基础 | **业务口径需要企业自己明确** | 配图以"赢单率"为例：销售用"中标项目 / 投标总项目"，市场用"中标项目 / MQL"，其他团队用"中标项目 / SQL"或"中标项目 / 商机"；结论"现阶段，模型无法解决这些问题" |

正文对口径问题的原话：**口径没有统一，即使模型写出的 SQL 可以运行，答案也可能不对**。

## 主线一：统一存储与统一计算

即原文第 2 节"让 Agent 用好多模态数据，先统一存储与计算"。

### Unified Storage = LakeHouse + Unified Catalog

- **结构与非结构共存**：Iceberg、Paimon 承载结构化数据；Lance 等支持文档、图片、音视频和向量
- **Unified Catalog**：统一管理元数据、注册、权限与血缘——过去游离在数仓资产体系外的材料需要进入统一目录
- **为什么这是前提**（原文）：Agent 要自主规划任务，就得知道**有哪些数据、含义是什么、是否有权访问**。配图补充："没有统一 Catalog，Agent 的每一次探索都是盲猜；没有 Lance 这类非结构化原生格式，文档/图片/音视频就永远在数据体系之外"

### Unified Compute = Spark / Flink / OLAP + Ray / Daft + RAG

- 三类计算：数据计算（批流统一、OLAP 交互式分析、承载现有全部数据负载）/ AI 特征计算（分布式 Python，支撑多模态算子与 OCR、ASR、抽帧、向量化）/ 知识计算（RAG：把企业知识接入模型上下文、支撑语义召回与问答）
- 三者**共享同一套存储与调度**，Agent 无需感知底层差异；数据加工、AI 处理、知识检索可以在**同一条流水线**里编排

详见 [[unified-storage-unified-compute]]。

## 主线二：EasyData 的 Agent Native 改造

原文第 3 节，标题即立场：**开放开发治理能力，执行必须受控**。EasyData 被拆为五层：

| 层 | 内容（正文） | 配图补充 |
|---|---|---|
| 入口层 | 连接不同 Agent | 3 个入口：平台内置 EasyAgent / 第三方 Agent 平台 / IM 机器人；"不绑定任何一个 Agent 框架" |
| 场景层 | 组合任务 | 4 大场景：数据开发、任务运维诊断、数据治理、定开评估 |
| 语义层 | 解释数据与开发规则 | 元数据语义 + 开发语义："让 Agent 知道有什么数据、什么含义、怎么开发" |
| 技能层 | Skill 封装原子操作 | **1 + 4 + N**：1 个总控编排 + 4 个场景级技能 + N 个原子能力技能 |
| 接口层 | 开放命令与服务 | 1 网关 · 2 协议（OpenAPI / MCP）· 3 形态（CLI / Skill / OpenAPI），统一鉴权与命令级权限管控 |

设计取舍（正文）：**能力尽量放在平台侧维护，入口变化时不必重新实现整套业务逻辑**；配图进一步强调"能力只建一份，入口按需接入——框架会换，能力资产不会"。

### 两类落地场景与关键数字

| 场景 | 做法 | 原文数字 | 详见 |
|---|---|---|---|
| 存量表治理（冷表下线） | 以"表"为锚反向定位"任务"：解析任务 SQL → 三重过滤 → 四类动作建议，全程只读 | 36,996 个调度任务 → 17,045 个可解析单任务 → 7,320 个已调度 → **177 条建议 / 226 张表**；19,951 个任务组因缺只读详情接口无法解析；另两个集群分别 60 条、3 条 | [[easydata-cold-table-governance]] |
| 值班故障诊断 | 定时拉取失败实例 → 日志取证 → 命中规则优先 → 未命中交给模型归因聚类 → 新规则先进 candidate | 单轮 134 实例规则命中率 100%（报告 130 条明细）；线上 B 环境 36 小时 111 实例中 12 条命中、其余 99 条归为 9 类待复核；规则库 27 条（26 生效 + 1 候选） | [[bigdata-duty-agent]] |

另两类场景在原文中只有概述：数据开发（不只生成 SQL，还涉及 Git 变更与回滚）、定开评估（核查数据源兼容性、知识清单与工作量），由场景级技能编排多个原子 Skill。

### 受控执行的四条约束

1. **网关统一鉴权**：一个网关接入 OpenAPI 与 MCP，鉴权、限流、审计在网关处理（详见 [[easydata-agent-gateway]]）
2. **命令级权限分级**：读操作依授权执行，**写操作二次确认**，**禁止类删除操作直接拒绝**；"工具能被 Agent 发现，不等于 Agent 有权执行"
3. **只读优先**：冷表分析"全程只读，实际变更由负责人决定"；值班 Agent "Phase 0 仅做发现、诊断、沉淀和通知，不改配置、不发布、不重跑任务"
4. **人工审核闸门**：新规则只进入 candidate 候选状态，补充特征、经人工审核后才能转成 active

### 语义层的两条内容线

原文：只有接口和 Skill，Agent 仍不知道表、字段以及开发规范究竟代表什么。因此语义分两部分：

- **元数据语义**：从表结构、注释和血缘提炼业务概念；表知识库读取 DDL、字段、分区、血缘、访问热度及文档，组织 Catalog / DB / Table / Column 物理实体与 Concept / Metric 业务实体，记录包含、派生、计算依赖等关系；**图谱连接实体 + 向量检索补充内容召回**；**公式冲突和同名异义**进入人工确认队列，审核后入图并保留来源
- **开发语义**：整理命名、建模、Git 变更和回滚要求

原文案例：查询"活跃用户数"时，普通相似度检索可能只找出相关说明，缺少 DAU 公式和对应物理表；数帆使用 **LightRAG 的 Local 实体检索与 Global 关系检索**，沿概念、指标、公式、字段、表展开关联。落地数据：已在传媒场景挖掘 **600 张表**的知识，通过 MCP 接入开发流程。

详见 [[table-knowledge-graph]]。

### 三类入口

平台内置 **EasyAgent**、第三方 Agent 平台（配图：帝王蟹 ClawHive / WorkBuddy）、企业 IM 机器人。工程师在 CLI 或熟悉的 Agent 中开发，值班人员通过 IM 接收诊断结果；不同入口共享接口、Skill、语义和审计规则。

## 主线三：DataAgent 的业务本体 + Harness

原文第 4 节。面向业务人员直接回答问题，**口径歧义**的影响被放大："最近一个月利润"是本月至今还是过去 30 天？"销售额"是否等于 GMV？

| 阶段 | 原文口径 |
|---|---|
| 单纯导入表结构 | 数十家客户 POC 中观察，**部分场景准确率不到 50%** |
| 构建业务本体、明确术语、调整提示词后 | **部分场景超过 95%**；一位制造业客户的财务用数测试**接近 100%** |
| 持续工程优化 | 2026 年完成 **100 余项工程优化**、积累 **1000 余条评测用例**，真实场景准确率**半年内从 66% 提升至 95% 以上** |

原文明确限定："这些数字对应具体场景，不能视作模型的通用准确率。"

### 语义平台四层 + 三类资产

四层：数据接入与计算加速（支持 40 余种数据源）→ 语义资产与血缘图谱 → 精准召回与语义增强 → 语义打分与结果回流。三类资产：数据集（较容易接入）、业务本体语义（需人工确认口径）、业务数据看板（可复用已有成果）。实际建设从具体场景开始，通过澄清记录、用户反馈和 badcase 补齐定义。

### Harness：把"怎么得出答案"也约束住

- 选数时从大量指标召回候选，**低置信度则请求澄清**
- 时点属性、LOD 和窗口函数等复杂计算由**语义层管理**，模型生成 Python 或 SQL，**代码负责执行**
- 行、列、表权限与用户属性绑定，**在查询 DSL 中校验**
- 执行失败可以**重试、修复并留痕**；真实问答和 badcase 持续进入评测集

原文总结："结果涉及语义、选数、执行和评测等多项改造，不能只归因于模型。"

详见 [[dataagent-ontology-harness]]。

## 第 5 节：两条路线与人的分工

### 同样是"本体 + 语义"，两个产品起点不同

| 维度 | 开发治理平台（EasyData） | DataAgent |
|---|---|---|
| 面向对象 | 工程师 | 业务人员 |
| 语义建设方式 | 原有数仓工具已维护元数据、规范和任务流程，适合**自下而上抽取**，再向 Agent 开放接口与 Skill | 必须先**确认指标实体和业务口径**，再**自上而下建立本体** |
| Harness 需求 | 建设重点到语义层基本结束 | 语义层之上还需意图识别、澄清、选数、权限、执行验证与评测等 Harness 机制 |

两条路线**共用数据底座**：底层接纳结构化与非结构化数据，中间承接数据计算、AI 特征处理、知识检索及语义服务；开发治理 Agent 执行任务、诊断故障，DataAgent 解释指标、分析业务。业务对象和操作风险不同，但**数据可见性、权限和结果核验都需要由平台提供**。

### 分工结论

原文对已落地成果的表述：冷表治理能定位到具体任务，值班 Agent 能自动取证并提出归因，DataAgent 能沿确认过的指标口径分析业务。同时列出三条边界：

- 拿不到详情接口的任务组**仍无法纳入完整分析**
- **未经审核的归因不能成为正式规则**
- **有歧义的业务指标也无法交给模型自行裁决**

因此："Agent 承担更多执行工作后，人的职责会更多落在**定义规则、确认例外和批准高风险操作**上。数据平台则必须能说明，每一次调用**依据什么数据、使用了什么权限、执行结果怎样验证**。"

## 原文未说明 / 需注意

- 原文**没有给出**改造的时间线、团队规模、各阶段投入与改造前后的整体性能对比
- "三个变化"（正文标题）与"三个判断"（配图标题）是同一组内容的两种措辞，本文按配图的完整表述记录，正文更简略，未做合并推断
- 冷表治理"另两个业务集群分别给出 60 条、3 条建议"，原文未说明集群差异原因
- 值班 Agent 的"规则命中率 100%"仅指单轮 134 个实例全部命中规则，**不等于 100% 自动修复**；原文特别提醒"不能把 99 条待复核归因写成 99 次故障自动修复"
- 制造业客户的"排查从数天缩短至数分钟、效率提升 90%"等数字来自该客户项目，原文标注"不能直接外推"
