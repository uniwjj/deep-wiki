# 半自动构建与闪电行动：八周跑通一个闭环

> **一句话定位：** 第 7 章把"本体怎么建"拆成两件事——**用什么方法建**（半自动构建：信息抽取 → 信息组织 → 模型表示，机器提议、人工定夺）与**按什么节奏建**（闪电行动：锁定场景 → 画闭环 → 建最小对象集 → 定义状态与关系 → 接入数据，八周跑通一个闭环）。原文的结论句是：**"八周，一个闭环，一个可运行的最小世界。"**（第 7 章 7.8 节 / PDF 第 131—132 页）

本页是全书方法论篇的落地产，向上承接 [[ontology-six-step-method]]（六步法，回答"建什么"），向下指向 [[small-world-network]]（小世界网络，回答"从单闭环到多智能体协同"）。原文在第 7 章末尾明确划出这条跃迁线：八周跑通一个闭环只是"工程起点"，价值终点是"多个智能体围绕场景目标自主结伴、自主协同、自主执行"（PDF 第 132 页）。

## 1. 为什么需要半自动构建

### 1.1 手工建模的三个瓶颈（PDF 第 111 页 / 7.1.1 节）

传统本体构建依赖领域专家手工建模：专家阅读文档、梳理概念、定义属性、建立关系、编写公理。原文判断：这种方法在**小型本体（几十个类）**中可行，在**大型本体（几百个类以上）**中面临三个瓶颈。

| 瓶颈 | 原文给出的量化依据 | 结论 |
|---|---|---|
| **瓶颈一：耗时长** | 一位有经验的领域专家，一天最多定义 **5—10 个实体类型**；300 个实体类型仅概念定义就需 **30—60 个工作日**。加上属性定义、关系定义、公理定义、专家评审、修改完善，整个建模周期可能长达 **6—12 个月** | 周期不可接受 |
| **瓶颈二：成本高** | 一位资深工程师或行业专家的日薪通常 **2000—5000 元**；建模周期 6 个月时，仅专家人力成本就**高达数十万元**。加上项目管理、工具采购、数据映射等费用，本体库建设总成本**可能超过百万元** | 成本不可承受 |
| **瓶颈三：难以规模化** | 手工建模的经验难以复制；换一个行业、换一个场景，还需要重新学习、重新梳理 | 本体库建设**无法像软件开发一样实现规模化生产** |

### 1.2 AI 带来的四种新能力（PDF 第 111 页 / 7.1.2 节）

原文以"2024 年以来，大语言模型在知识抽取、关系识别、概念聚类等任务上展现出强大能力"为前提，列出四种能力：

| 能力 | 原文举例 |
|---|---|
| **概念抽取** | 给定设备手册，大模型可抽出"设备""部件""参数""操作""故障"等概念 |
| **关系识别** | 给定两个概念判断关系："设备"与"产线"可能是"属于"关系，"设备"与"故障"可能是"发生"关系 |
| **属性提取** | 给定"设备"概念和设备手册，抽出"设备编号""设备类型""额定功率""加工精度"等属性 |
| **公理生成** | 给定一组概念和关系，生成候选公理，如"设备必须属于一条产线""一个设备只能有一个设备编号" |

原文的表述是：这四种能力"为半自动构建提供了技术基础"。

### 1.3 半自动构建的定位：机器提议、人工定夺（PDF 第 112 页 / 7.1.3 节）

原文先划边界——"AI 不是万能的"：大模型存在**幻觉问题**，可能生成不存在的概念、错误的关系、不准确的属性；如果完全依赖 AI 自动构建本体，结果可能不可靠。

由此给出定位，以及分工的两组表述：

| 角色 | 职责 | 分工原则 |
|---|---|---|
| **机器** | 负责"提议"——从文档、数据库中抽取**候选概念、候选属性、候选关系、候选公理** | AI 负责"**广度**"、负责"**速度**" |
| **人工** | 负责"定夺"——审核候选内容，确认**哪些保留、哪些修改、哪些删除** | 人类负责"**深度**"、负责"**准确度**" |

原文对这一分工的评价：既利用了 AI 的效率优势，又保留了人类专家的判断力。

## 2. 半自动构建的三阶段（PDF 第 112—116 页 / 7.2 节）

三个阶段是：**信息抽取** → **信息组织** → **模型表示**。PDF 第 112 页的总图《半自动构建三阶段：机器提议、人工定夺》以"阶段 / 输入 / 核心任务 / 输出 / 人机分工"五行展开，逐格复述如下：

| 行 | ① 信息抽取（蓝） | ② 信息组织（绿） | ③ 模型表示（橙） |
|---|---|---|---|
| **输入** | 文档、数据库、知识库（图标三项，后接"…"） | 候选概念（彩色节点散点图） | 结构化网络（多色节点连成的网络） |
| **核心任务** | 漏斗图标：**七要素框架抽取 / 冗余剔除** | 语义关联（含虚线聚类圈）、聚类粒度（层级块状图）、**地下根技术** | OWL / RDFS / TTL 文档图标，标注 `@prefix`、`:Class a owl:Class .`、`:subClassOf`，说明文字为"**OWL/RDFS 形式化序列化**" |
| **输出** | 候选概念、属性、关系 | 结构化概念网络 | OWL / TTL / SHACL 三种文件图标，说明文字"**OWL/TTL/SHACL 文件**" |
| **人机分工** | 🤖 机器提议：信息抽取、冗余识别 ⇄ 👤 人工审核：结果审核、质量把控 | 🤖 机器聚类：语义计算、聚类建议 ⇄ 👤 人工确认：聚类确认、关系校验 | 🤖 机器生成：本体生成、序列化输出 ⇄ 👤 人工定稿：逻辑验证、本体发布 |

图例说明：机器 = 自动化能力；循环箭头 = 协同迭代；人 = 专业判断。**三个阶段的人机分工都是"机器人 + 人工"成对出现**，即每一个阶段都不是纯自动或纯手工。

### 2.1 第一阶段：信息抽取（PDF 第 112—114 页 / 7.2.1 节）

核心任务是"从文档、数据库中提取对象信息，并**剔除冗余**"。

**（1）数据源类型——三类（7.2.1.1）**

| 类型 | 原文列举 | 数据形态 | 内容特征 |
|---|---|---|---|
| **文档类** | 设备手册、工艺文件、标准规范、操作指南、维修记录、培训材料 | 非结构化 | 包含大量业务知识 |
| **数据库类** | ERP、MES、PLM、SCM 等业务系统的数据库 | 结构化 | 包含表结构、字段定义、数据字典 |
| **知识库类** | 已有的知识图谱、术语表、分类体系、行业本体 | 半结构化 | 包含概念、关系、属性 |

**（2）七要素框架（7.2.1.2）**

原文出处：**中国信通院自 2019 年起构建的工业本体语义建模体系**，提出用于高效抽取工业对象信息的"七要素框架"。

| 七要素 | 定义 | 原文举例 |
|---|---|---|
| 对象 | 业务世界中的实体 | 设备、物料、订单、人员 |
| 属性 | 对象的特征 | 设备编号、设备类型、设备状态 |
| 关系 | 对象之间的关联 | 设备属于产线，产线生产订单 |
| 事件 | 业务过程中的事件 | 设备故障、订单延迟、质量异常 |
| 状态 | 对象的当前状态 | 设备运行中、订单生产中 |
| 规则 | 业务规则 | 设备故障时必须停机、订单延迟时必须通知客户 |
| 行动 | 可执行的行动 | 设备切换、订单取消、质量返工 |

原文对七要素的作用写得明确：抽取时**不是漫无目的地找概念**，而是按七要素框架系统性识别对象、属性、关系、事件、状态、规则和行动。

**（3）信息抽取方法——三类（7.2.1.3）**

| 方法 | 机制 | 原文举例 |
|---|---|---|
| **基于规则** | 利用领域词典和模板规则 | 用"XX 属于 YY"模板抽出"设备属于产线"关系 |
| **基于统计** | 利用词频、共现、互信息等统计指标 | 识别文本中的核心概念和关系 |
| **基于大模型** | 利用大语言模型的语义理解能力抽取概念、属性、关系 | 提示词示例见下 |

原文给出的大模型提示词示例（逐字保留）：

> "请从以下工业设备手册文本中，抽取设备实体、设备属性（如设备编号、设备类型、技术参数等）、以及设备之间的关系（如'设备属于产线''设备包含部件'）。以 JSON 格式输出。"

**（4）冗余剔除——四种手段（7.2.1.4，PDF 第 113—114 页）**

原文前提：信息抽取会产生大量候选概念和关系，其中很多是冗余的。

| 手段 | 定义 | 原文举例 |
|---|---|---|
| **同义合并** | 识别含义相同或相近的概念，合并为一个 | "设备"和"机器"在多数场景下同义，可合并 |
| **上下位归并** | 识别上下位关系，将下位概念归并到上位概念 | "数控机床"是"设备"的子类，归并到"设备"下 |
| **低频过滤** | 删除出现频率极低的概念 | 低频概念可能是噪声，不是核心业务概念 |
| **无关过滤** | 删除与当前业务场景无关的概念 | 在"设备故障影响分析"场景中，"财务""人力"等概念无关，可删除 |

### 2.2 第二阶段：信息组织（PDF 第 114—115 页 / 7.2.2 节）

核心任务：通过**构建语义关联、确定聚类粒度**，完成数据的结构化整合。

**（1）构建语义关联——三种（7.2.2.1）**

| 类型 | 内容 | 原文举例 |
|---|---|---|
| **概念关联** | 建立概念之间的层级关系和关联关系；层级关系含上位概念和下位概念，关联关系含**对象属性和数据属性** | — |
| **实例关联** | 建立实例之间的关联 | 设备 EQ003 属于 A 产线，订单 O001 由 A 产线生产 |
| **属性关联** | 建立属性之间的关联 | 设备状态与风险等级之间的关联 |

**（2）确定聚类粒度——三组取舍（7.2.2.2）**

| 取舍 | 差异 | 原文举例 / 做法 |
|---|---|---|
| **粗粒度 vs 细粒度** | 粗粒度覆盖广但细节少；细粒度覆盖窄但细节多 | "设备"是粗粒度，"数控机床"是细粒度 |
| **核心概念 vs 边缘概念** | 核心概念是业务闭环**必需**的，边缘概念是非必需的 | 在最小世界模型方法论中，**优先建立核心概念，边缘概念暂时不建** |
| **稳定概念 vs 动态概念** | 稳定概念变化频率低，动态概念变化频率高 | 优先定义稳定概念，**动态概念通过状态属性表达** |

**（3）地下根技术（7.2.2.3，PDF 第 114—115 页）**

原文出处：中国信通院提出的"地下根技术"，是一种**借助分层网状结构实现复杂数据多维度关联**的方法。

| 要点 | 原文内容 |
|---|---|
| **核心思想** | 将复杂数据关系组织为"**根系结构**"：**主根 = 核心概念**，**侧根 = 关联概念**，**须根 = 属性** |
| **作用** | 通过根系结构，高效管理和查询复杂数据关系 |
| **工业场景用法** | 组织设备、产线、工艺、订单之间的复杂关系：**设备是主根，产线是侧根，订单是须根** |
| **故障传播** | 当设备发生故障时，可以沿着根系结构**快速传播影响** |

**（4）语义聚类（7.2.2.4）**

原文出处：中国信通院提出的"**基于熵理论的语义聚类技术**"。

- **核心思想**：通过计算概念之间的语义相似度，把相似概念聚到一起，把差异大的概念分开。
- **工业场景用途**：识别**同义概念**、区分**歧义概念**、发现**潜在概念**。

### 2.3 第三阶段：模型表示（PDF 第 115—116 页 / 7.2.3 节）

核心任务：借助适配的计算机语言实现标准化描述，输出**完整可用的本体模型**。

**（1）形式化语言选择（7.2.3.1）**

| 语言 | 表达能力 | 推理能力 | 学习成本 | 适用场景 |
|---|---|---|---|---|
| **OWL 2** | 最强 | 支持复杂推理 | 高 | 需要复杂推理的场景 |
| **RDFS** | 简单 | 弱 | 低 | 轻量级应用 |
| **SHACL** | — | 用于约束验证 | — | 可与 OWL/RDFS 结合使用 |

**（2）序列化格式选择（7.2.3.2）**

| 格式 | 优势 | 适用 |
|---|---|---|
| **Turtle（TTL）** | 可读性好 | 人工阅读、**Git 版本管理** |
| **JSON-LD** | 与 Web 技术兼容性好 | Web 应用 |
| **RDF/XML** | W3C 标准格式 | 工具交换 |

**（3）模型验证——三级（7.2.3.3，PDF 第 115—116 页）**

| 级别 | 检查内容 |
|---|---|
| **语法验证** | 模型是否符合 OWL/RDFS 的语法规则 |
| **语义验证** | 模型是否存在逻辑不一致 |
| **约束验证** | 使用 SHACL 验证**实例数据**是否符合本体约束 |

**（4）模型输出——四类交付物（7.2.3.4）**

| 交付物 | 内容 |
|---|---|
| **本体文件** | OWL/TTL 文件，含类、属性、公理的定义 |
| **SHACL 文件** | 约束文件，定义实例数据的约束规则 |
| **映射文件** | **R2RML** 映射文件，定义数据源到本体的映射规则 |
| **文档** | 本体库使用文档，含快速上手、建模指南、映射指南 |

## 4. 人机协作机制：四级闸门（PDF 第 117 页 / 7.4 节）

原文用四个小节（7.4.1—7.4.4）描述从机器到人的四级机制。语义顺序是：**机器提议 → 数据裁决 → 标准把关 → 人工定夺**，越往后越靠近"人"。

### 4.1 机器提议（7.4.1）

四类提议，**每一类都要求"标注来源和置信度"**：

| 提议 | 动作 |
|---|---|
| 概念提议 | 大模型从文档中抽取候选概念，标注来源和置信度 |
| 关系提议 | 大模型从文档中抽取候选关系，标注来源和置信度 |
| 属性提议 | 大模型从文档中抽取候选属性，标注来源和置信度 |
| 公理提议 | 大模型从文档中抽取候选公理，标注来源和置信度 |

### 4.2 数据裁决（7.4.2）

用真实数据给机器提议"打分"：

| 动作 | 内容 |
|---|---|
| **数据验证** | 将候选概念、关系、属性与**真实数据比对**，验证其准确性 |
| **数据补充** | 从真实数据中发现候选概念、关系、属性的**缺失项** |
| **数据统计** | 统计候选概念、关系、属性的**出现频率、分布情况** |

### 4.3 标准把关（7.4.3）

| 检查 | 内容 |
|---|---|
| **标准符合性检查** | 是否符合 **GB/T 48000.3—2026** 等标准的要求 |
| **术语规范性检查** | 术语是否符合**行业术语规范** |
| **命名一致性检查** | 命名是否**一致** |

### 4.4 人工定夺（7.4.4）

| 动作 | 执行者 | 内容 |
|---|---|---|
| **专家评审** | 领域专家 | 审核候选概念、关系、属性，确认**保留、修改或删除** |
| **业务验证** | 业务人员 | 验证本体**是否能够解决实际业务问题** |
| **迭代优化** | — | 根据专家评审和业务验证结果，持续优化本体 |

### 4.5 四级机制对照表（归纳）

| 层级 | 谁在做 | 判断依据 | 输出 |
|---|---|---|---|
| ① 机器提议 | 大模型 | 文档语义 | 带来源 + 置信度的候选集 |
| ② 数据裁决 | 数据系统 | 真实数据 | 准确性结论、缺失项、频率分布 |
| ③ 标准把关 | 标准 / 规则 | GB/T 48000.3—2026 等标准 | 符合性、术语规范性、命名一致性 |
| ④ 人工定夺 | 领域专家 + 业务人员 | 专业判断 + 业务效果 | 保留 / 修改 / 删除，并进入迭代 |

## 5. 从半自动构建到闪电行动（PDF 第 117—119 页 / 7.5 节）

### 5.1 半自动构建的边界：方法论需要节奏来落地（7.5.1）

原文先指出方法论缺口：半自动构建解决的是"**用什么方法建**"，但**没有回答**"按什么节奏建""先建什么、后建什么""做到什么程度算完成"。

再列出四类局限：

1. 大模型的**幻觉问题**
2. **领域知识**的深度问题
3. **数据安全与隐私**问题
4. 半自动构建的**适用边界**

由此推出三条必然：

| 局限 | 推出的必然 |
|---|---|
| 幻觉 | 不能完全依赖 AI 自动构建，**必须有人工定夺** |
| 领域知识深度 / 数据安全 | 不能等所有条件完备再开始，**必须在过程中逐步完善** |
| 适用边界 | 不能追求一次完美，**必须在迭代中持续优化** |

原文把结论收敛为一个工程节奏问题：**"在条件不完备、资源有限、周期紧张的现实约束下，如何用半自动构建的方法论，快速跑通一个闭环？"**

### 5.2 本体项目启动阶段的普遍困境（PDF 第 118 页）

原文用三段对话刻画"很多企业启动本体项目时面临的尴尬局面"，并明确"这不是某个企业的问题，而是本体项目启动阶段的普遍困境"：

| 角色 | 原文描述 |
|---|---|
| **业务部门说不清楚自己要什么** | 问"你们需要什么样的数据模型"，答"我也不懂，你们是专家，你们看着办"；问"你们现在最头疼的问题是什么"，能说出一堆问题，但说不清哪个最值得优先解决 |
| **IT 部门拿不出可用的数据** | "数据在 ERP 里，但 ERP 的数据库我们动不了"；"数据字典是十年前的，早就不准了"；"做个数据盘点？人手不够，至少要三个月" |
| **领导要求三个月内看到成果** | 需求调研刚做完，领导问进度，答"还在梳理概念"，领导说"三个月后我要看到东西" |

原文的预后判断：如果按传统方法按部就班推进（需求调研 → 概念模型 → 语义模型 → 数据映射 → 质量校验），很可能三个月后**只交付了一份"看起来很完整但没人用"的模型文档**。

### 5.3 闪电行动的核心逻辑（7.5.2）

| 问题 | 回答者 | 答案 |
|---|---|---|
| 用什么**方法**建 | 半自动构建 | 信息抽取、信息组织、模型表示；机器提议、人工定夺；AI 负责广度、人类负责深度 |
| 按什么**节奏**建 | 闪电行动 | 五步法：锁定场景、画闭环、建对象集、定义状态关系、接入数据，**八周跑通一个闭环** |

两者的互哺关系，原文写得对称：

- 半自动构建为闪电行动提供**效率工具**，让八周闭环**成为可能**；
- 闪电行动为半自动构建提供**应用场景**，让"机器提议、人工定夺"的方法论**有了工程落地的载体**。

核心逻辑句：**"不等条件完备，先用最小代价跑通一个闭环，用结果说话。"**（PDF 第 118 页）具体展开为三个"不等"（PDF 第 119 页）：

| 不等 | 改为 |
|---|---|
| 不等业务部门说清楚需求 | 主动去寻找痛点 |
| 不等 IT 部门准备好数据 | 先用可用的数据 |
| 不等领导给足够时间 | 用八周跑通一个闭环 |

原文的总结句是："**先证明价值，再争取资源；先跑通闭环，再扩展世界。**"并强调这与传统逻辑**完全相反**：传统是"先建好，再用"，闪电行动是"**先用好，再建好**"；传统是"先设计完整，再实现完整"，闪电行动是"**先跑通最小，再扩展完整**"。

### 5.4 闪电行动与传统方法的对比（PDF 第 119 页 / 7.5.3 节，原表八维度）

| 维度 | 传统方法 | 闪电行动 |

| 起点 | 需求调研 | 业务痛点 |
| 目标 | 建完整模型 | 跑通一个闭环 |
| 周期 | 6—12 个月 | 8 周 |

| 风险 | 高（一次性大投入） | 低（小步快跑） |
| 价值证明 | 后置 | 前置 |

PDF 第 128 页的总图《闪电行动五步法与八周节奏》，副标题为"不等条件完备，先用最小代价跑通一个闭环，用结果说话"，逐格复述如下：

### 6.2 第一步：快速锁定切入场景（1 周，PDF 第 119—121 页 / 7.6.1 节）

**（1）不要等，主动找（7.6.1.1）**

原文先批评常见做法：发通知要求各部门提交需求，等一周收到几份不痛不痒的反馈，再等一周收到几份敷衍回复，"一个月过去了，需求还没收齐"。然后给出主动寻找的**三个方向**：

| 方向 | 怎么找 | 原文案例 |
|---|---|---|
| **方向一：已有数字化项目中暴露的痛点** | 翻过去几年的数字化项目**验收报告、用户反馈、运维记录**；问哪些问题反复出现、哪些功能使用率最低、哪些系统对接最困难 | 某企业发现：设备故障诊断时，工程师需**跨五个系统查询信息，平均耗时 30 分钟**；该问题在多个项目中被提及但一直未解决 |
| **方向二：生态伙伴或行业用户提出的具体问题** | 问"你们最近在解决什么问题"，**不要**问"你们需要什么数据" | 一个供应链伙伴说"我们最近在做一个供应链风险预警的项目，但数据来源太杂，不知道怎么统一" |
| **方向三：政策文件或标准文件中明确的应用方向** | 关注**国家数据局、工信部、全国数标委**等机构的政策文件和标准文件 | 国家数据局"数据要素×"行动明确了**工业制造、现代农业、商贸流通等十二个重点方向** |

**（2）三个判断问题（7.6.1.2）**

| 问题 | 判"否"（不需要本体） | 判"是"（适合本体） |
|---|---|---|
| **问题一：这个问题不是简单查一个字段就能解决的？** | "这个月销售额是多少"——只需查一个字段或做一次聚合计算 | "为什么这个客户最近流失风险上升""这台设备故障后会影响哪些生产环节""如果减少这条产线的产能，会影响哪些订单"——涉及**对象、关系、状态、事件、规则和影响链** |
| **问题二：这个问题存在明显的业务上下文？** | "设备故障"本身没有太大意义 | 真正有意义的是：哪台设备、属于哪个工艺、承担什么能力、当前是什么状态、影响哪些对象、有没有替代设备 |
| **问题三：这个问题能够形成业务闭环？** | "查一下设备状态"，不涉及闭环，传统查询就够了 | 闭环 = 从"发现异常"到"处置完成"的完整过程 |

问题三给出的设备故障处置闭环链（八步）：**设备报警 → 确认状态 → 判断是否影响生产 → 寻找受影响工艺 → 判断风险等级 → 寻找替代设备 → 执行切换 → 重新观察生产状态**。

原文判据：**三个答案都是"是"，就是好的切入场景。**

**（3）场景选择评估矩阵（7.6.1.3）**

候选场景较多时用于排序，五个维度、每项 1—5 分，**选择综合得分最高的场景**：

| 评估维度 | 评估问题 | 5 分 | 1 分 |
|---|---|---|---|
| **业务紧迫性** | 业务方是否面临明确的痛点？ | 业务方主动提出需求 | 业务方无感知 |
| **数据可得性** | 是否已有可接入的数据源？ | 已有数据库且可对接 | 数据无法接入 |
| **边界清晰度** | 场景范围是否可控？ | 可明确界定本体覆盖范围 | 范围模糊 |
| **效果可量化** | 是否有可量化的验证指标？ | 有明确的成功标准 | 无法量化 |
| **合作方意愿** | 合作方是否愿意配合？ | 已有合作基础且意愿明确 | 无合作方 |

### 6.3 第二步：画业务闭环，不画类图（1 周，PDF 第 121—123 页 / 7.6.2 节）

**（1）先画流程，再建模型（7.6.2.1）**

原文的方法指令：锁定场景后，**不要打开建模工具，先拿一张白纸**，把业务人员实际做事的过程画出来。理由：本体建模最容易犯的错误就是**跳过业务理解、直接进入技术实现**——打开 Protégé、创建类、定义属性、画关系图，"看起来很专业，但业务人员看不懂，也不认可"。正确顺序：**先理解业务，再设计模型；先画业务闭环，再建本体结构。**

**（2）业务闭环的六个要素（7.6.2.2）**

| 要素 | 要回答的问题 |
|---|---|
| **触发事件** | 什么触发了这个业务过程？设备报警？订单延迟？质量异常？ |
| **参与角色** | 谁参与了？设备智能体？质量智能体？人工工程师？ |
| **业务步骤** | 包括哪些步骤？每一步的输入是什么、输出是什么？ |
| **决策节点** | 有哪些决策点？决策依据是什么？ |
| **行动执行** | 决策后执行什么行动？行动由谁执行？ |
| **结果反馈** | 行动后产生什么结果？结果如何反馈？ |

**（3）完整案例：设备故障影响分析（7.6.2.3，PDF 第 122 页）**

| 项 | 原文内容 |
|---|---|
| **触发事件** | 设备 EQ003 报警，振动值达到 **6.8 mm/s**，超过预警阈值 **4.5 mm/s** |
| **参与角色** | 设备监测智能体、故障诊断智能体、维护决策智能体、人工工程师 |
| **业务步骤** | ① 确认设备状态：是否真的故障？② 判断影响范围：影响哪些工艺单元、哪些产线、哪些订单？③ 评估风险等级：影响程度多大？需紧急处置吗？④ 寻找替代设备：有没有可用替代设备？替代条件是什么？⑤ 生成切换方案：步骤是什么？需要多长时间？⑥ 执行切换：由谁执行？如何执行？⑦ 重新观察：产能恢复了吗？订单交付风险降低了吗？ |
| **决策节点** | ① 设备是否真的故障？（依据：振动值、温度、电流等参数组合判断）② 是否影响生产？（依据：设备在产线中的位置、是否有缓冲库存）③ 是否需要切换？（依据：故障严重程度、替代设备可用性）④ 切换哪个设备？（依据：替代设备的能力匹配度、切换成本） |
| **行动执行** | 设备切换，由**维护决策智能体**调用工具执行 |
| **结果反馈** | 产线产能恢复，订单交付风险降低 |

**（4）这张图决定了一切（7.6.2.4，PDF 第 123 页）**

原文用三条"意味着"把业务闭环图直接映射为建模约束：

| 业务闭环中的动作 | 对本体的要求 |
|---|---|
| "判断是否影响生产" | 需要知道**设备与产线之间的关系** |
| "寻找替代设备" | 设备不仅要有属性，还要有**能力、兼容关系和替代关系** |
| "重新观察生产状态" | 对象必须具备**动态状态**，而不是一份静态知识 |

结论句：**"本体不是从概念出发，而应该从业务动作倒推模型。"**

### 6.4 第三步：建立最小对象集（2 周，PDF 第 123—124 页 / 7.6.3 节）

**（1）只建参与闭环的对象（7.6.3.1）**

原则：**"没有参与当前业务闭环的对象，暂时不要建。"** 设备故障影响分析场景所需对象（原表八项）：

| 对象 | 英文名 | 说明 |
|---|---|---|
| 设备 | Equipment | 产线中的生产设备 |
| 工艺单元 | ProcessUnit | 设备所属的工艺单元 |
| 产线 | ProductionLine | 工艺单元组成的产线 |
| 指标 | Metric | 设备运行的监测指标 |
| 报警 | Alarm | 设备发出的报警 |
| 事件 | Event | 业务过程中的事件 |
| 风险 | Risk | 业务风险评估 |
| 行动 | Action | 可执行的业务行动 |

**（2）只建参与闭环的关系（7.6.3.2，PDF 第 124 页）**

原文用**定义域 / 值域**的方式给出六条关键关系：

| 关系 | 英文名 | 定义域 | 值域 |
|---|---|---|---|
| 属于工艺单元 | belongsToProcessUnit | Equipment | ProcessUnit |
| 影响产线 | affectsProductionLine | Equipment | ProductionLine |
| 有报警 | hasAlarm | Equipment | Alarm |
| 可以替代 | canReplace | Equipment | Equipment |
| 影响设备 | affectsEquipment | Event | Equipment |
| 影响产线 | affectsProductionLine | Risk | ProductionLine |

（注：原文中设备→产线、风险→产线两条关系共用英文名 `affectsProductionLine`，分属 Equipment 与 Risk 两个定义域。）

**（3）不要急着增加（7.6.3.3）**

原文明确点名"这时候不要急着增加以下对象"：**客户、供应商、财务、人力、产品、物料、订单**——"这些对象以后可能都很重要，但只要它们没有参与当前问题，就没有必要第一期全部建进去"。判据句：**"最小对象集的目标不是'完整'，而是'够用'。"**

### 6.5 第四步：定义状态与关系，让本体可计算（2 周，PDF 第 124—126 页 / 7.6.4 节）

**（1）对象不是静态的（7.6.4.1）**

原文诊断：很多本体项目做到这一步，看起来已经有类和关系了，但真正运行起来"还是像一张知识图谱"，原因是"业务世界不是静态的"。三类对象的状态表（原表三张）：

| 设备状态 | 说明 | | 订单状态 | 说明 | | 风险状态 | 说明 |
|---|---|---|---|---|---|---|---|
| 运行中 | 设备正常运转 | | 待确认 | 订单已创建，等待确认 | | 正常 | 无风险 |
| 降额 | 设备在降低负荷下运转 | | 生产中 | 订单正在生产 | | 关注 | 需要关注 |
| 故障 | 设备发生故障，不能正常运转 | | 延迟 | 订单生产延迟 | | 预警 | 需要预警 |
| 维修中 | 设备正在维修 | | 部分交付 | 订单部分交付 | | 高风险 | 高风险状态 |
| 停机 | 设备停止运转 | | 已完成 | 订单全部交付 | | 已处置 | 已经处置 |

由此得出可运行本体应用的三问：**对象是什么？现在是什么状态？状态为什么发生变化？**

**（2）关系要能参与计算（7.6.4.2）**

原文的前提句："关系不是为了让画布看起来复杂。真正有价值的关系，应该能够参与计算。"

设备故障的**关系传播链**（逐环）：

> 设备 A 故障 → 所属工艺单元 B 能力下降 → 工艺单元 B 的下游工艺单元 C 受影响 → 产线 D 产能受限 → 订单 E 交付风险上升

原文评价：这时关系"就不再只是'链接'，它开始成为业务计算的一部分"。

**（3）建模时要不断问（7.6.4.3）**

原文给出的自检问句：**"这个关系建立以后，系统准备拿它算什么？"** 判据：如果一个关系**既不用于查询，也不用于规则、推理、影响分析或行动**，那它很可能只是"为了完整而存在"。

### 6.6 第五步：接入数据，让对象"活起来"（2 周，PDF 第 126—127 页 / 7.6.5 节）

**（1）不要继续扩充 Schema（7.6.5.1）**

本体模型完成后，下一步**不是继续扩充 Schema，而是尽快连接真实数据**。完成之后，AI 面对的不再是一堆孤立字段，而是一组**具有业务语义和关系的对象**。

**（2）数据接入的三个步骤（7.6.5.2）**

| 步骤 | 内容 |
|---|---|
| **① 数据源接入** | 连接 **MES、ERP、设备管理系统**等数据源，获取原始数据 |
| **② 数据映射** | 将数据库表、字段映射到本体中的**类、属性** |
| **③ 实例生成** | 根据映射规则，从原始数据生成 **RDF 实例** |

**（3）数据映射示例（7.6.5.3，PDF 第 127 页，MES 设备表）**

原始数据：

```
equipment_id: EQ003
equipment_type: 数控机床
equipment_status: 故障
vibration: 6.8
line_id: A
```

映射后的 RDF 实例：

```
Equipment(EQ003)
  equipmentType = "数控机床"
  equipmentStatus = "故障"
  vibration = 6.8
  belongsToProcessUnit = ProcessUnit(A)
```

注意映射的两处语义增量：`line_id: A` 由扁平字段变为**对象关系** `belongsToProcessUnit = ProcessUnit(A)`；`vibration` 从原始读数成为对象的**属性值**。

### 6.8 闪电行动的适用与不适用场景（PDF 第 128 页 / 7.6.7 节）

原文开头即声明"闪电行动不是万能的"。

| 适用（四种情形） | 原文理由 |
|---|---|
| 企业**刚开始做本体**，缺乏经验和数据积累 | 没有历史包袱，可以从零开始，快速试错 |
| 业务部门**对本体价值存疑**，需要用结果证明 | 不需要长篇大论地解释本体是什么，直接跑通一个闭环，让业务部门看到效果 |
| **项目周期紧张**，需要在短期内看到成果 | 八周出成果，满足领导对进度的要求 |
| **数据源不完善**，需要在使用中逐步完善 | 不等数据全部就绪，先用可用数据跑通闭环 |

| 不适用（四种情形） | 原文理由 |
|---|---|
| 企业**已有成熟的本体库**，需要进行大规模扩展 | 需要全局设计，不适合小步快跑 |
| 本体需要**覆盖多个业务领域** | 需要从全局视角设计本体架构 |
| 本体需要**跨组织协作**，需要多方协商 | 需要协调多方利益，不适合快速行动 |
| **数据安全要求极高**，不能快速接入数据 | 需要严格的安全评估和审批流程 |

## 7. 从闪电行动到持续生长（PDF 第 129—131 页 / 7.7 节）

### 7.1 跑通第一个闭环（7.7.1）

原文对目标的界定很克制：闪电行动的目标**不是"建一个完美的本体"**，而是"**跑通一个闭环，证明价值，然后自然生长**"。第一个场景跑通之后，才进入"真正有价值的扩展阶段"。

### 7.2 五期扩展路径（7.7.2，PDF 第 129 页）

以设备故障处置为例，每一期都是在前一个闭环基础上"自然生长"出来的：

| 期次 | 闭环内容 |
|---|---|
| **第一期** | 设备故障 → 生产影响 → 替代设备 → 故障处置 |
| **第二期** | 设备健康 → 预测性维护 |
| **第三期** | 设备能力 → 生产排程 |
| **第四期** | 生产排程 → 订单交付风险 |
| **第五期** | 订单交付风险 → 客户满意度 |

### 7.3 共享对象与关系（7.7.3）

原文的次序判断很重要：**不是**先设计一个"大本体"再把业务往里塞，**而是**多个经过验证的业务闭环在**共享对象和关系**之后**自然形成更大的本体**。

原文举例：设备故障闭环中的"**设备**"对象在设备健康闭环中继续使用；设备健康闭环中的"**健康指标**"对象在生产排程闭环中继续使用。结论：共享的对象和关系构成本体的"**骨架**"，新的闭环在这个骨架上继续生长。

**PDF 第 129 页图《从闪电行动到持续生长》逐格复述：** 副标题为"闪电行动是方法，最小世界模型是目标。多个验证过的闭环共享对象和关系，自然形成更大的本体。"图以一棵树为喻：

- **树冠五枝（五期）**：01 第一期 设备故障 → 生产影响 → 替代设备 → 故障处置；02 第二期 设备健康 → 预测性维护；03 第三期 设备能力 → 生产排程；04 第四期 生产排程 → 订单交付风险；05 第五期 订单交付风险 → 客户满意度。
- **树干标签**："**共享对象**"。
- **根系四个对象**：**Equipment、ProductionLine、Order、Risk**。
- **底部标签**："最小世界模型（持续生长的本体）"。

**PDF 第 130 页图（最小世界模型的闭环网络）逐格复述：** 中心是虚线圈出的"**共享对象层**"，内含四个核心节点 **Equipment / ProductionLine / Order / Risk**（图例：共享对象=核心节点）；外围环绕七个"闭环模块"（图例：闭环模块=最小世界模型），每个模块用"共享关系"边连到共享对象层：

| 闭环模块 | 图内流程 |
|---|---|
| 设备故障闭环 | 监测 → 诊断 → 维修 → 验证 |
| 设备健康闭环 | 感知 → 评估 → 预测 → 优化 |
| 生产排程闭环 | 计划 → 排程 → 执行 → 调整 |
| 订单交付闭环 | 接单 → 生产 → 交付 → 评价 |
| 客户满意度闭环 | 反馈 → 分析 → 改进 → 提升 |
| 质量追溯闭环 | 检验 → 记录 → 追溯 → 改进 |
| 供应链协同闭环 | 采购 → 物流 → 仓储 → 协同 |
| 能耗优化闭环（图内出现 **两处** 同名模块，左右各一） | 采集 → 分析 → 优化 → 控制 |

图例第四项为"**层级结构（中心+辐射+网状）**"。除"共享关系"外，设备故障闭环与生产排程闭环之间还标了一条"**依赖关系**"。

### 7.4 从闪电行动到最小世界模型（7.7.4）

原文的对偶句：**闪电行动是方法，最小世界模型是目标。** 闪电行动是"先跑通一个闭环"的方法论，最小世界模型是"让世界自然生长"的目标。口号式表述："**先做小闭环，再做大本体；先证明价值，再扩展世界。**"这一句与 [[minimal-world-model]] 一章同源，是两章之间的接缝。

### 7.5 四条核心原则（7.7.5，PDF 第 130—131 页）

| 原则 | 原文要点 | 落地证据 |
|---|---|---|
| **① 价值前置** | 不要等本体建完再证明价值，而是在**建设过程中**就证明价值；不要等所有数据接入再验证效果，而是接入部分数据后就验证 | 第 2 周有业务闭环图，第 4 周有本体草案，第 6 周有本体 V0.5，第 8 周有本体 V1.0 和实例数据——每个阶段都有可交付、可展示的成果 |
| **② 业务参与** | 本体建设不是 IT 部门的独角戏，而是业务部门与 IT 部门协同：业务提供**业务知识**，IT 提供**技术能力**；业务验证**准确**，IT 实现**可用** | 不是"需求调研阶段参与一次"，而是**全流程参与**，见下表 |
| **③ 快速迭代** | 不追求一次完美，先建立最小可用版本，在使用中持续完善 | 第 3—4 周的草案"不完美，但有比没有好"；V0.5"不完整，但可以支持核心业务闭环"；V1.0"不全面，但可以回答核心业务问题" |
| **④ 用结果说话** | 不用"我们建了一个模型"证明价值，而用"我们解决了一个业务问题"；不用"模型有多少个类"证明价值，而用"业务人员节省了多少时间" | — |

业务全流程参与的分工（原文逐周列出）：

| 周 | 业务方要做的事 |
|---|---|
| 第 1 周 | 锁定场景需要业务方**确认** |
| 第 2 周 | 画闭环需要业务方**参与** |
| 第 3—4 周 | 建对象集需要业务方**审核** |
| 第 5—6 周 | 定义状态需要业务方**验证** |
| 第 7—8 周 | 接入数据需要业务方**测试** |

## 8. 本章小结（PDF 第 131—132 页 / 7.8 节）

原文的核心判断：**半自动构建是方法，闪电行动是节奏；方法需要节奏来落地，节奏需要方法来支撑。**

**两者协同的三个机制：**

| 机制 | 内容 |
|---|---|
| ① 机器提议嵌入五步法 | 让八周跑通一个闭环成为可能 |
| ② 人工定夺贯穿八周节奏 | — |
| ③ 迭代反馈形成闭环 | — |

人机分工的核心原则复述为："机器负责'广度'，人工负责'深度'；机器负责'速度'，人工负责'准确'。"

**一个闭环证明的三件事：**

1. 本体能够**回答**业务问题；
2. 本体能够**解释**业务问题；
3. 本体能够**支撑业务判断和行动**。

原文把这三点合起来指向更根本的目标——**智能协同**：

| 智能体角色 | 它"知道"什么 | 知道从哪里来 |
|---|---|---|
| 设备监测 Agent 发现异常时 | 该通知谁 | 本体 |
| 诊断 Agent 分析故障时 | 该沿哪条关系链传播影响 | 本体 |
| 决策 Agent 生成方案时 | 该查询哪些可替代设备 | 本体 |
| 执行 Agent 调用接口时 | 自己的权限边界在哪里 | 本体 |

结论句（对照句，体现本页与 [[ontology-driven-action-loop]] 的接缝）：

> "没有本体，智能体之间的协同就只是**协议层面**的数据交换；有了本体，智能体之间的协同才是**语义层面**的可信互操作。没有本体，一个闭环跑通只是'单点智能'的证明；有了本体，一个闭环跑通才是'群体智能'的起点。"

原文最后划出跃迁线：八周跑通一个闭环是本体构建的**工程起点**，智能协同是**价值终点**；从起点到终点还需要一次关键跃迁——"从'一个闭环'到'多个智能体围绕场景目标**自主结伴、自主协同、自主执行**"，这正是第四篇 [[small-world-network]] 的主题。

## 10. 原文未说明 / 边界

- **八周是否包含专家评审与标准把关**：7.4 的四级协作机制（尤其"标准把关"与"专家评审"）在 7.6 的逐周要点里只出现"业务方确认/参与/审核/验证/测试"，**原文未说明**标准符合性检查与专家评审具体落在哪一周、占多少工作量。
