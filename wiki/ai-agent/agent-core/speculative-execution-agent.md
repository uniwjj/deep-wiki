# 投机执行：Agent 在结果被采用前提前行动

在 [[agent-event-driven-triggering|事件驱动]] 的链路里，事件经过过滤与路由后进入目标会话。但 Agent 不必等到"确认需要它"才动手——原文借鉴计算机系统中的**投机执行（Speculative Execution）**思想提出：

> Agent 可以在还不确定结果是否会被采用时，根据环境信号在后台提前尝试，通过消耗额外的后台算力来减少人类的等待与介入成本。结果有价值就交付，没有价值就丢弃。

借用的是"结果是否被采用尚不确定时提前计算"这一结构：用**后台算力**置换**人的等待**。这与 [[super-agent]] 四个特征中的"主动"直接相关，也是它区别于"等指令再执行"的关键。

## 两个场景

### 个人助手：先备好，再请用户过目

当收到一封会议邀约邮件或待办消息时，Agent 可以先在后台完成：

1. 核对日程冲突；
2. 搜集相关背景资料；
3. 备好回复草稿。

待用户过目后即可直接确认发出——用户看到的是一个"已经准备好"的结果，而不是一连串待办动作。

### 研发协作："静默复现并修复"

原文团队在 DeepSeek Harness 的内部用户群中配置了一条**"静默复现并修复"**策略：

> 当群里有人反馈问题或讨论改动方案时，Agent 先在后台尝试复现并寻找修复方案，只有在**确认问题并找到简单的修复方案**后，才会把结果交付给用户，否则**全程保持安静**。

这条策略有两个要点，缺一不可：

| 要点 | 含义 |
|------|------|
| **提前做** | 不等被 @、不等讨论收敛，先复现、先找方案 |
| **收敛后才说** | 交付的准入条件是"确认问题 + 简单修复方案"；未达条件则静默，不打扰群聊 |

原文配图给出的例子：用户群里有人反馈"模型输出中的波浪号被渲染成了删除线"，群内还在争论"应该在训练中解决，还是修改渲染规则"，Agent 已经提交了 Pull Request——只有 `~~文字~~` 渲染为删除线，单个 `~`（如 `10~20`）保持原样；面对"单个波浪号也是常见写法，依据是什么"的追问，它给出 Pandoc 与 markdown-it 只支持 `~~`、GFM 额外接受单个 `~` 的对比，并指出模型输出中的单个 `~` 多用于表示范围，正是误渲染的来源。

## 与"静默监听"的关系

投机执行与 [[super-agent]] 开篇展示的"静默监听"是同一取向的两个侧面：

- **静默监听**（第 1 节示例）：持续观察公共群聊，在无人 @ 的情况下主动识别缺陷并提交修复 Pull Request——解决"要不要介入"的判断；
- **投机执行**（3.4 节）：在是否介入尚不确定时，先把后台工作做完——解决"介入的等待成本"。

两者的共同约束都是**不制造噪音**：不需要介入时保持安静，结果没有价值就丢弃。

## 代价与边界

- **成本形态**：消耗的是**额外的后台算力**，换取人类等待与介入成本的下降；原文没有给出这部分算力的量化数据。
- **质量门槛**："有价值就交付"需要一个可执行的收敛条件。在"静默复现并修复"中，条件被显式写成"确认问题 + **简单的**修复方案"——复杂度上界由策略本身设定。
- **与安全的关系**：更广泛的环境驱动意味着更多不可信输入，原文把由此带来的安全与隐私问题列为开放问题（见 [[super-agent]] 8.4 节）。
