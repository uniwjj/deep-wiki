# 异步 ReAct Loop：从半双工到全双工交互

[[super-agent-dual-layer-architecture|双层架构]] 从上下文层面保证了跨信道的连续性；但要在实际人机交互体验中同时做到"连续"与"高效"，还需要解决两个交互问题：

1. **如何消除后台耗时操作对前台对话的阻塞**——本页的异步 ReAct Loop；
2. **当交互发生在用户熟悉的不同工作信道时，输出方式如何匹配该信道的带宽与人的使用习惯**——本页后半部分的多信道交互。

## 阻塞从哪里来

在经典的 ReAct Loop 中，模型发起一次**同步的 `run()` 工具调用**后，循环会阻塞，直到工具执行完毕并返回最终结果——在此期间会话无法响应任何新的用户输入：

```
经典 ReAct Loop（半双工）
用户消息 1 ──► LLM Call 调用 run() ──► 同步执行耗时工具 ──► 工具结果返回 ──► LLM Call 回复用户
                              └────────── 前台阻塞等待（期间无法接收新指令）──────────┘
```

这正是 [[super-agent]] 四个特征中"高效"的反面：必须先等上一个命令或任务完成，才能接受下一条指令。

## 异步 ReAct Loop

改造方式是把**耗时的命令与子任务工具调用改为异步的 `start()` 和 `stop()`**：

| 机制 | 行为 |
|------|------|
| `start()` | 模型调用后**立即收到"已启动（Started）"的返回**，循环不再等待该工具；后台异步执行 |
| 结果投递 | 后台工具执行完成后，系统把最终结果**作为一条新的事件消息投递进会话** |
| `stop()` | 模型可以根据上下文主动终止执行时间过长的后台命令 |

```
异步 ReAct Loop（全双工）
用户消息 1 ──► LLM Call 调用 start() ──► 立即返回 Started 通知 ──► 用户消息 2 ──► LLM Call 即时回复
                    │                                                              ▲
                    └──► 后台异步执行耗时工具 ──► 完成结果作为新消息投递 ──────────┘
```

由此，**前台对话响应与后台任务执行得以解耦**：Agent 在后台运行耗时任务的同时也能响应人类输入；新输入在当前推理步结束后即被处理，不必等待后台工具完成。这一步把对话从"一问一答的半双工"变成"全双工"。

**实现状态**：原文说明这一异步任务机制**已经在 DeepSeek Harness 中实现，但尚未默认开启**。

## 多信道交互：输出要匹配信道带宽

不同工作信道具有不同的信息密度与交互习惯。如果把面向单人终端的交互方式直接搬进群聊——把冗长的推理过程与密集的工具调用原样输出——在多人协作中极易造成信息过载。

双层架构已经解决了其中一部分：具体任务中冗长的推理过程和密集的工具调用都被隔离在 Worker Session 内部，不会直接输出到外部信道，而由 Router 层统一负责对外交互。在此之上，还需要**接入用户日常使用的各类工作环境，并通过提示词针对不同信道定制交互规范**：

| 信道类型 | 输出取向 | 具体规范 |
|---------|---------|---------|
| **IM 等即时通讯信道** | 低打扰的轻量沟通 | 像人类同事一样**只在需要决策或验收时发送通知**；只问直接问题、给简短结论。原文验证过的一条简单有效的硬性规定是：**单次回复不超过 100 词** |
| **GitHub、邮件与文档等异步信道** | 结构化、高信息密度的异步交付 | 创建或更新 Pull Request 时按项目规范撰写完整的问题背景、改动说明与验证结果；个人助手场景下直接起草结构化的邮件与文档摘要 |

这条分工是"面向人的交互"在系统设计上的落点：**同一个 Agent，在不同信道上表现为不同的交付形态**，而不是把同一种输出广播到所有渠道。
