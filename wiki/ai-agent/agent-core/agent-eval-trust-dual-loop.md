# Agent 评测如何落地：可信标准与双 Loop 演进实践

> 核心主张：评测是在 Agent 能力和业务结果之间搭桥——把业务目标转成可检验的标准，为上线、扩量和持续改进提供依据。要让分数可信，必须先做到「人人一致」（不同的人按同一标准得出同一判断），再做到「人机一致」（机器复现人的判断，支撑规模化）；要让 Agent 持续变好，需要两条 Loop 同时运转：一条迭代 Agent，一条校准评测体系本身。

> 演讲嘉宾：高诗梦（美团 · 专家工程师，负责美团 AI Agent 评测平台，协助业务建设 Agent 评测体系）
> 场合：DACon 2026 北京站「Agent 评测工程：从度量到改进的闭环」
> 说明：本页依据 28 页 PDF 逐页阅读整理；PDF 为纯图片版，全部页面经 150dpi 渲染后视觉复核。演讲以教学示例和真实（匿名化）案例为主，未给出统一的业务 ROI 数字。

演讲开场把全场收束为三个问题：

| 问题 | 追问 |
|------|------|
| 01 评什么？ | 业务目标与完整任务交付 |
| 02 怎样评得可信？ | 分数涨了，Agent 真的变好了吗？ |
| 03 怎样持续改进？ | 持续评 Agent，谁来检查评测本身？ |

## 背景与问题

### 开场案例：用户没说，为什么变成了"你提到"？

用户原话只有「某景区漂流门票」，未提及同行人或学生身份。Agent 的回复却写着「注意到你提到同行有一位学生」，并给出成人票（¥143 起）与儿童优惠票（¥59 起）两个方案。这类问题靠三个动作发现和解决：

| 动作 | 作用 |
|------|------|
| 评测 | 上线前发现并拦截 |
| 归因 | 沿 Trace 核查原因 |
| 回测 | 确认修复，没有改坏其他任务 |

### 搭一个 Agent 越来越容易，推到全量仍然很难

**搭建门槛持续下降**来自三条趋势：

- **模型能力持续进化**：格式输出、工具调用等能力更多由模型承担，减少 Prompt 打磨与工程兜底。
- **框架与协议持续完善**：规划、记忆、工具与状态逐步组件化，接工具、加 Skill 更省力。
- **落地场景更多、更发散**：前两条趋势共同降低搭建门槛，推动 Agent 进入更多业务场景。

**规模化却有三道障碍**：

| 障碍 | 表现 |
|------|------|
| 停在 Demo | 演示时挺好，一接真实流量，各种问法、脏数据、没考虑到的场景就来了。团队一直打补丁，项目却很难往前走 |
| 卡在扩量 | 出了问题，不知道该改哪里；想改，又怕把原来做对的地方改坏。于是改也担心，不改也不行 |
| 说不清价值 | 模型换了、Prompt 也改了，感觉效果越来越好，但到底给业务带来什么改善，拿不出证据，后续投入就很难继续 |

演讲把问题收束为一句：**评测分数涨了，就能扩大流量吗？** 答案需要定标准、做回测、线上验证，为业务决策提供依据。

### 评测要覆盖 Agent 的整个生命周期

评测把业务目标转成可检验的标准，贯穿三个阶段：

| 阶段 | 要做的事 |
|------|---------|
| 01 冷启动 | 明确业务价值与任务目标，定义成功标准，建立核心场景种子评测集 |
| 02 上线扩量 | 检验真实流量中的效果，根据线上 Case 补充样本，修正标准和评测方法 |
| 03 全量运营 | 随业务与用户需求变化，重新审视业务目标与评测目标，持续校准评测体系 |

链路是：**业务目标**（以店长经营分析 Agent 为例：少花时间整理数据，更快看懂经营问题）→ 定义预期 → **产品理想态**（数据取全、分析有依据，结果用得起）→ 检验差距 → **Agent 实际表现**（数据取全了吗？分析有依据吗？结果可用吗？）。

## 方案/架构

### 评测对象是完成任务的整个系统

| 评测类型 | 主要评测对象 | 核心问题 |
|---------|------------|---------|
| 传统机器学习评测 | 单模型的预测表现 | 预测得准不准 |
| 大模型能力评测 | 模型的通用与专项能力 | 模型能力强不强 |
| Agent 评测 | 模型、工具与流程构成的任务系统 | 任务能否稳定完成 |

**任务系统 = 模型 + Prompt / Skill + 工具链 + 记忆与状态管理 + 业务流程**

贯穿案例是「店长月度经营复盘」：给定条件为已上传门店数据、已配置商家账号权限、投放数据查询工具可用；系统执行「获取投放数据 → 结合门店数据分析 → 生成经营分析 PPT」。评测要回答的是：整个任务系统能否在给定条件下，稳定交付符合业务要求的结果。

### 不只看结果，还要看行为和过程

同样完成任务，两条路径的质量完全不同：

- **路径清晰、稳定完成**：理解 → 规划 → 调用 → 交付；工具调用稳定、耗时可控、可重复复现。
- **反复试错、偶然命中**：理解 → 重试 → 绕路 → 误调 → 交付；路径混乱、额外消耗、结果难以复现。

评测因此分四层：

| 层 | 关注点 |
|----|--------|
| 01 结果层 | 任务是否完成，输出是否可用 |
| 02 过程层 | 规划是否合理，步骤是否稳定 |
| 03 效率层 | 耗时、Token、调用次数是否可接受 |
| 04 风险层 | 是否越权、误操作或存在安全隐患 |

要判断行为和过程，就需要可追溯的执行证据。

### 观测是评测的基石

Trace 关联模型调用、工具交互与关键状态，为评测和问题定位提供证据。PDF 展示的真实界面节选中，第 1 轮 LLM 模型调用耗时 3.9s、skill-load 48ms；第 2 轮 LLM 9.6s、bash mkdir 112ms、bash find 19.6s（截图为脱敏示例，与右侧门店案例不是同一任务）。

Trace 的价值在开场案例中被具体演示：

1. **看输入**：用户没说有学生；平台画像有「学生」标签，用户这次没提到学生。
2. **看参数**：分析写着「用户未提及」，参数却是「学生 1 人、身份确定」——把画像里的推测，当成了事实。
3. **看回复**：又说成了「你提到同行有一位学生」——把画像信息说成了用户原话。

有了执行证据，就能追着一条信息往回查，看它在哪一步发生了变化。

### 客观评测与主观评测并行

| 维度 | 客观评测 | 主观评测 |
|------|---------|---------|
| 看什么 | 看「准不准」 | 看「好不好」 |
| 依据 | 对照事实、目标状态和明确约束，核验结果是否正确、要求是否满足 | 结合用户需求与业务场景，依据评价标准判断质量和价值 |
| 例子（同一份经营分析 PPT） | PPT 能否打开？投放金额是否与源数据一致？取数与操作是否符合授权？ | 经营变化是否解释清楚？分析能否帮助店长理解问题？建议是否具体、可执行？ |
| 怎么判断 | 核对源数据、实际产物与执行记录，按明确规则逐项检查 | 专家先明确评价标准，由人工或 LLM Judge 评判，再用样例校准，减少判断分歧 |

结论：同一个任务，既要核验是否做对，也要判断是否有用；**主观评测的标准需要先对齐**。

### 可信的两层：人人一致，再人机一致

主观评测真正困难的不是「没有人会评」，而是「不同的人评得不一样，机器和人评得也不一样」。

以店长月度经营分析 PPT 为例，各方对「这份 PPT 是否达到本次经营复盘的整体验收要求」的通过依据并不相同：

| 角色 | 各自采用的通过依据 | 倾向 |
|------|------------------|------|
| 产品 | 图表齐全，内容完整 | 倾向通过 |
| 运营 | 没有解释清楚经营变化 | 倾向不通过 |
| 研发 | 数字与源数据都能对上 | 倾向通过 |
| QA | 原因判断缺少核查证据 | 无法确认因果结论 |

各方采用的验收依据不同，必须先统一标准，再检验人人一致。

- **人人一致**：统一各方评测标准，降低判断方差。
- **人机一致**：机器评测与人工评测一致，支撑规模化提效。

标准需要对齐，首先要明确**谁对标准负责**。

### 1 个"独裁者"好过 10 个"民主者"

承担标准负责人角色的，是**最懂业务和评测的人**：可以来自产品、算法或运营，结合评测经验与行业专家判断。需要拉齐的参与方是产品 / 运营 / 研发 / QA。负责人的三项职责：

| 职责 | 内容 |
|------|------|
| 征求并整合意见 | 多方征求意见，整合指标与 Rubric，让团队遵循同一套评测体系 |
| 分歧时拍板 | 项目方观念无法对齐时作最终裁决，避免各自为政与内部拉扯 |
| 组织目标与标准演进 | 依据真实 Good / Bad Case 修正评测目标，同步更新规则、正反例与评测样本 |

## 关键工程做法

### 人人一致：把共同标准变成可复现的判断

团队采用同一版标准，用背靠背标注暴露分歧，再裁决、细化与复测，共四步：

| 步骤 | 具体做法 |
|------|---------|
| 01 独立盲标 | 依据同一版标准，独立判断同一批评测样本，分别记录标签与依据 |
| 02 对照分歧与依据 | 逐条核对不同判断，区分规则理解不同、规则不清或证据缺失 |
| 03 负责人裁决并细化 | 整合意见、明确判定口径，把模糊指标下钻为 Rubric，尽量转成是 / 否 / 未知 |
| 04 新样本复测 | 换一批评测样本独立标注，检查每条 Rubric 的一致率与 UNKNOWN 占比 |

教学示例「数字都对，这份报告就算'分析有帮助'吗？」演示了分歧如何收敛。报告写道：「本月广告费增加 20%，营收增长 10%，说明加广告带动了营收增长。」

- A 判是：「两个数字都对。」只检查了数字对不对。
- B 判否：「还没证明营收增长是加广告带来的。」还看原因有没有证据。

负责人明确的共同要求是：数字要对，原因也要有依据；没证据时写「可能有关，还需验证」，不能写成定论。换一份仅有降价与营收数据的新报告后，X「全靠降价」两人均判否，Y「可能有关，待验证」两人均判是。

### 人机一致：让机器复现人的判断

做法是把模糊标准拆成可判断的检查项。以某外呼 Agent 的口语化评测为例，原始标准是「请判断模型回复是否口语化，并按 0–10 分打分」，无法稳定执行。下钻后：

| 下钻方向 | 具体检查项 | 判断方式 |
|---------|-----------|---------|
| 称呼对象 | 模型是否用「您」称呼通话对象？ | 是 / 否 |
| 口语表达 | 是否使用「甭客气」「明儿见」等口语交流词汇？ | 是 / 否 |
| 语气词 | 是否包含「吧」「呢」「那个」等语气词？ | 是 / 否 |

演讲同时提示：这些是示例检查项，需要按业务场景校准；**出现某个词，不等于整体表达自然**。

### 一套评测体系的 4-3-2-1

| 数量 | 内容 |
|------|------|
| 4 个模块 | 离线评测、在线评测与监控、Case 挖掘与归因、观测基建 |
| 3 种能力 | 发现问题、定位问题、驱动演进 |
| 2 条 Loop | Agent 迭代、评测体系迭代 |
| 1 套资产 | 评测集：样本、预期与标准 |

### 两条 Loop 如何咬合

两条 Loop 共用「同一批线上真实样本」，中心是「Case 挖掘与归因（沿 Trace 定位问题）」：

- **评测体系迭代（让评测持续可信）**：线上评测与监控 → 复核验证（检查评测判断质量）→ 补样本、校准标准与 Judge → 回到线上评测与监控。
- **Agent 迭代（让能力持续变好）**：修复 Agent → 离线回测 / 发布门禁 → 上线验证（检查任务表现与业务效果）→ 回到 Case 挖掘。

分流规则是：覆盖缺口 / 判断偏差进入评测体系 Loop；Agent 行为问题进入 Agent 迭代 Loop。同一个 Case 可能同时进入两个 Loop。评测集是两条 Loop 的共享资产：评测体系迭代「更新」它，Agent 迭代依赖它「支撑回测」。

这也回答了「Agent 改完后，怎样在上线前确认变好了，也没有把原来做对的任务改坏？」——靠离线回测与发布门禁。

### 离线评测：在受控条件下检验 Agent

流程是：**评测集**（预先准备任务，明确输入与成功标准）→ **Agent 执行**（在受控环境中运行，记录过程与交付物）→ **按标准评判**（检查结果与关键过程，形成可复核的判断）→ **结果与问题**（判断任务表现，识别不足与改进方向）。要求多次独立运行，观察通过率与波动；每次恢复约定的初始状态。

典型用途是版本变更后的回测：模型、Prompt、知识库或 Skill 变更后，对比 Agent vN 与 vN+1，做到同样本、同标准、同初始环境，记录 Agent、评测集与环境版本，最终判断是否发布或灰度——检查核心链路失败、高风险问题、旧能力退化与业务风险容忍度。

### 评测集的构成与分类

一条样本由三部分组成：

| 组成 | 内容 |
|------|------|
| 任务输入 | 用户需求、上下文与任务约束 |
| 参考答案 / 预期结果 | 目标产物、最终状态与必要行为 |
| 评价标准 | 指标、Rubric 与通过条件 |

执行与管理还需配套初始环境、工具权限和数据快照，并记录样本与标准的版本。

按用途分为五类：

| 分类 | 主要收录 | 核心用途 |
|------|---------|---------|
| 必过集 | 核心链路、质量底线与高风险场景 | 检查底线要求，支撑发布门禁 |
| 黄金集 | 经过复核、预期与标准清晰的核心任务 | 提供质量参照，比较版本表现 |
| 挑战集 | 多约束、长交互及复杂边界任务 | 检验困难任务，观察能力边界与提升 |
| 错题集 | 历史失败及经复核的正确预期 | 验证问题修复，防止再次发生 |
| 需求专项集 | 围绕新需求、新工具或新能力的样本 | 检验本次变更，支撑需求验收 |

管理边界：不同集合按用途组织，同一条样本可以属于多个集合；**调优样本与验收留出样本分开管理，留出样本不参与 Prompt 调优或 Judge 校准**。

### 离线守住已知，在线发现未知

固定评测集未覆盖的场景，反复回测也测不到；需要在线评测发现新 Case，再补入离线评测集。教学示例中，评测集覆盖的是「根据本店数据，制作一份经营分析 PPT」，线上新出现的是「帮我对比三家门店的数据」；前者回测通过，后者尚未覆盖。评测集不会自动跟着真实需求一起变化，继续重跑旧任务也补不上跨门店比较的验证。闭环是：**发现线上新 Case → 补充离线评测集 → 回测验证**。

### 上线后如何知道 Agent 做得怎么样

在线评测回答「线上任务是否符合评测标准」，在线监控回答「表现有没有变化」：

| 在线评测 | 做法 |
|---------|------|
| 影子模式 | 候选版本面对真实请求，做得怎么样？复制请求给候选版本执行，结果不返回用户 |
| A/B 实验 | 新版本是否带来实际收益？分流真实请求，对比任务质量与业务指标 |
| 周期巡检 | 线上核心能力是否保持稳定？用代表性固定任务，定期检查线上 Agent |

| 在线监控 | 关注 |
|---------|------|
| 运行变化 | 工具失败率、耗时、成本是否出现异常 |
| 质量变化 | 任务通过率、巡检结果是否出现下降 |
| 需求变化 | 任务类型与输入分布是否出现变化 |

两者的产出（评测结果、问题样本、异常线索）汇入 **Case 挖掘**：结合评测结果、监控异常、用户反馈、业务规则与主动采样，筛选代表 Case，产出值得分析的任务及其输入、交付物与执行记录。

### Case 挖掘与归因：把线上发现转成可验证的改进

触发时机是异常信号触发或例行采样。五项核心能力与产出：

| 能力 | 具体产出 |
|------|---------|
| 01 高价值 Case 挖掘 | 从四类渠道筛出的代表样本 |
| 02 问题复现与证据组织 | 任务输入、关键状态、工具响应与版本 |
| 03 失败模式归并 | 问题簇、发生频率、影响范围与处理优先级 |
| 04 分层定位与归因验证 | 有证据和验证结果支持的原因判断 |
| 05 修复协作与资产沉淀 | 诊断单、责任方、复测结果与回归样本 |

Case 的四类来源：**用户反馈**（从投诉、纠错和建议中找线索）、**监控与巡检**（从运行、质量与需求异常中筛选）、**业务规则**（聚焦高风险、高价值任务复核）、**随机真实采样**（主动抽样，补充其他渠道盲区）。

归因三步：

1. **铺开执行全链路**：把 Agent 的执行过程展开，串起计划（如有）、工具调用、数据流、关键状态与交付物。
2. **沿 Trace 逐一排查**：像看日志查 bug 一样，检查各环节输入、输出与异常，对照任务要求，定位偏差。
3. **定位核心问题环节**：结合证据形成原因判断；区分 Agent 行为问题与评测标准问题，明确修复方向。

归因高度依赖 Trace 观测基建；人工可以排查，机器也可以辅助完成。产出为问题环节、证据、修复方向与责任方、验证计划；相似 Case 归并后按优先级排序，可减少重复分析。

## 数据与效果

- 开场 Trace 截图中，模型调用 3.9s / 9.6s，skill-load 48ms，bash mkdir 112ms，bash find 19.6s（脱敏示例，与右侧案例非同一任务）。

### 综合案例：三店经营复盘

**任务**：店长问「帮我对比三家门店近两个月的经营与投放表现，给出下月建议，并生成复盘 PPT。」初始条件为经营数据已上传、账号已授权、投放查询工具可用；仅分析，不修改投放配置。

**客观核验**：Agent 报告摘录「C 店营收 120 万元最高，下月增投 C 店」；源数据显示 C 店 120 万元是退款前成交额、退款 40 万元，净营收 80 万元，低于 B 店 95 万元。结论是口径混用，「C 店最高」不成立。本例客观验收规则：三店同口径比较、正确扣除退款、排名结论与数据一致。

**主观核验**（假设口径已修正，报告建议「B 店净营收最高，建议下月增加 B 店投放」）：

1. **评测负责人定标准**：先定建议的依据、约束、执行与验证要求；再看本例，净营收排名不足以支持增投；实际适配性未知时，不给确定性行动结论。
2. **先检验人人一致**：两位评审按同版 Rubric 独立盲标同批建议，比较各项判定与依据，定位分歧；负责人裁决并细化标准，再用新样本复测。
3. **再检验人机一致**：Judge 按同版 Rubric 评同批建议，对照人工裁决，分析不一致样本，调整提示词或 Rubric，留出样本复测。

本案例的重点是：**净营收第一，不等于值得增投**；先把「好建议」说清楚，再看人和 Judge 能否评得一致。

**怎么改**：

| 改 Agent：先算对，再给建议 | 改评测：让两类问题被识别 |
|---------------------------|------------------------|
| C 店排名：报告统一按净营收排名，净营收 = 成交额 − 退款 | C 店排名：检查净营收计算与同口径排名规则，核对原评测当时是否检出 |
| 报告建议怎么生成：核对数据依据、业务目标与约束，写清怎么做、怎么验证；证据不足时说明待确认 | 报告建议怎么评：按依据、目标与约束、执行方案、效果验证四项 Rubric 检查；先对齐人工判断，再检查 Judge |
| 修后怎么验：同一输入对照新旧版本，检查排名是否正确、建议是否有依据且可执行 | 改后怎么验：已知口径题检验客观规则；用留出报告建议对照人工裁决检验 Judge |

下次更新重测这两类问题：C 店能否算出净营收 80 万元并正确排名；报告建议能否有依据、顾及约束、可执行且可验证，证据不足时能否说明待确认。每次改动都重测这些问题，也检查原有任务有没有退步。

### 业务如何把双 Loop 持续跑起来

以经营规划分析 Agent 为例：**每日评样本，每周检查 Judge，每两周综合评 Agent。**

| 节奏 | 链路 |
|------|------|
| 每日评线上样本（共同输入） | 清洗线上数据（对话、Trace 与节点记录）→ Judge 按指标评测（机器标签与错误类型）→ 关联原始记录（通过 Trace ID 落库）→ 可追溯的评测数据（供每周抽检、双周汇总） |
| 每周检查 Judge（评测体系 Loop） | 抽取机标样本（人工复核同一批样本）→ 比较人机判断（一级标签与错误类型）→ 检查分歧与衰退（核对规则与统计口径）→ Judge 可靠性判断（校准问题与分歧样本） |
| 每两周综合评 Agent（Agent 迭代 Loop） | 汇总两周数据（端到端与过程评测）→ 人工补标与质检（融合机标、人标与质检）→ 报告与 Bad Case（研发分领域 RCA）→ Agent 调优方向（重点场景、问题与修复依据） |

两条 Loop 的收尾：评测体系 Loop 按需校准 Rubric / Judge，进入下一轮每日机评；Agent 迭代 Loop 修复与回测，产出新运行数据与回归样本。

### 成熟度自查：用一张表找到短板与错配

| 模块 | 维度 | L0 准备阶段 | L1 冷启动阶段 | L2 扩量推全阶段 | L3 自进化阶段 |
|------|------|------------|--------------|----------------|--------------|
| 观测基建 | 观测 | 只有入参出参日志 | 有完整 trace，可人工回放 | 结构化埋点，支持自动提取 | 含环境快照，可自动判定 outcome |
| 离线评测 | 评测集 | 没有固定评测集 | 有端到端种子集，人工维护 | 分层评测集，含黄金集与错题集 | 线上 case 自动回流，版本化管理 |
| 离线评测 | 评测标准 | 凭感觉判断 | 有 rubric | rubric 二元化，人人一致率达标 | 人机一致率达标，机评规模化 |
| 离线评测 | 回测门禁 | 不做回测 | 发版前手工跑一次 | 回测自动化，有分层门禁 | 嵌入 CI/CD，不通过无法发布 |
| 在线评测与在线监控 | 在线评测 | 无 | 有人工抽查 | 有周期性巡检，含报警 | 巡检 + AB + 影子模式组合使用 |

| case 挖掘与归因 | case 挖掘 | 靠用户投诉 | 有 bad case 收集渠道 | 四类来源齐备，有 case 池 | 自动挖掘 + 自动分类入池 |

## 经验与边界

- **先让最小闭环转起来**：第一轮从高频核心场景开始，少量关键标准、一批种子样本；遇到真实问题，再补能力。用少量关键标准跑通闭环，让真实 Case 持续推动评测体系演进。
- **评测是一门实践科学**：标准要靠真实业务来检验，改动要靠验证来证明效果。每一轮都留下可复用的评测资产（样本、标准、回归用例），支撑下一轮回测。
- **标准负责人不可缺位**：1 个「独裁者」好过 10 个「民主者」——不是不要民主意见，而是必须有人对标准负责、在分歧时拍板。
- **主观标准必须先对齐再规模化**：否则无法判断迭代后的分数上涨，是评测波动还是真实效果提升。
- **评测集不会自动跟上业务**：只做离线回测会漏掉线上新场景，必须让在线发现持续补充离线评测集。
- **归因依赖观测基建**：没有 Trace，就只能知道「考得差」，无法定位到具体环节；Trace 让「一条信息在哪一步发生变化」可被追查。
- **演讲未展开的部分**：未给出评测平台的具体技术栈、Judge 模型的选型与版本管理方案、各业务线的准确率基线，也未给出双 Loop 运行后的人力投入变化；PDF 中大量页面为教学示例或脱敏界面，不能当作生产统计。

### 结尾四条结论

1. 评测是在 Agent 能力和业务结果之间搭桥。
2. 人人一致，让标准可信；人机一致，让评测规模化。
3. Agent 评测是一门实践科学。
4. 一个 Loop 改进 Agent，一个 Loop 校准评测。

原页的收束语是「MEASURE · ALIGN · EVOLVE」：把评测做成能够持续自我校准的工程体系——一套成熟的评测体系，既要持续测量 Agent，也要持续校准自己。
