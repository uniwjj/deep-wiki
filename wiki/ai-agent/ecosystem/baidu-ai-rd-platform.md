# 百度 Flower：研发角色融合下的一站式产研平台实践

> 核心主张：**编码只占研发时间的两成多，单点提效已接近上限，瓶颈是协同消耗。** 角色融合不是让人直接越过工程条件，而是用一站式平台补齐「共同上下文、可执行环境、可验证的质量机制」，让小团队办大事；Agent 每次都会失忆，经验必须沉淀到 Harness 里。

来源：DACon 2026 北京站「AI 时代的研发范式与组织进化」专场，百度移动生态事业群组 AI 创新平台研发「全栈 Agent 工程师」孟小萱《角色融合下的一站式产研平台实践》（45 页，纯图片版 PDF，逐页视觉复核 + OCR 交叉核对）。讲师简介：主力建设 Flower 一站式产研全链路提效平台，10+ 业务线 AI 提效落地经验。

标题页副标题：**直面角色融合中的经验差异与环境难题，用一站式产研平台让小团队办成大事。**

## 背景与问题

### 开发环节提效明显，全局交付提升有限

| 指标 | 数值 | 含义 |
|---|---|---|
| AI 代码生成率 | 80% | 编码环节已被 AI 大幅加速 |
| 需求交付提效 | 20%+ | 端到端交付的提升远小于编码环节 |

页面用两条长度悬殊的条形对比，并标注：**「这部分差距耗在了编码之外的沟通、等待和返工上」**。

### 写代码只占两成多，时间主要花在沟通、等待和返工上

| 时间去向 | 占比 |
|---|---|
| 即时沟通 | 26.2% |
| 编码调试 | 22.4% |
| 技术方案与文档 | 21.1% |
| 会议 | 17.7% |
| 等待（审批／环境） | 12.6% |

两项来自真实需求的观察：

- **18 轮沟通 · 9 天相互等待**——一个需求的沟通成本。
- **3—4 天排期错位 · +2 周错过班车**——赶不上双周班车。

### 团队慢在信息失真、频繁交接和流程阻塞

| 问题 | 表现 |
|---|---|
| 01 信息流转 | 层层转述，越传越走样；需求经过几轮口头转述，到研发手里已经变了样 |
| 02 频繁交接 | 问题在角色之间来回转；产品、设计、研发、测试之间反复确认，一个问题要转好几手 |
| 03 流程阻塞 | 卡在排期和审批上；文档越写越多，审批要排队，错过班车就再等两周 |

### 破局方向：更少的人，办更大的事

演讲给出的因果链：

| 环节 | 内容 |
|---|---|
| 现状 | 单点提效接近上限——编码已被 Agent 大幅加速 |
| 瓶颈 | 协同消耗成为主因——大部分时间花在沟通、等待和交接上 |
| 手段 | 减少沟通与等待——拓展技术栈，打破角色边界 |
| 目标 | 提升全局交付效率——看端到端的交付结果 |

### 一次失败的角色融合尝试

1. **产设做出原型**：能演示，业务方向得到验证。
2. **交给工程侧**：期待接入现有生产系统。
3. **发布受阻**：代码、架构与验证门禁没过。
4. **返工与争执**：预期落空，双方重新补齐工程工作。

页面的判断：**返工只是表象，消耗的是协同与信任。**

### 角色融合涉及哪些角色

演讲中明确出现的是**产品、设计、研发**三类角色：失败案例是「产设做出原型」后「交给工程侧」；平台效果写「一人承担产研多角色」；交付结果页仍把「产品 → 前端 → 服务端 → 测试」的传统链路作为对照。

因此，这里的角色融合更准确地说是**跨角色能力扩展 + 同一现场协作**：产品／设计借助平台补齐工程上下文与可执行环境，工程师借助 Agent 承担更多产研环节。原文没有给出岗位合并清单、职级变化或组织架构调整方案，也没有说测试角色被取消——不应据此推断百度进行了正式的角色撤并。

### 大家都很努力，缺的是生产条件

| 缺失 | 内容 |
|---|---|
| 缺失 01 共同上下文 | 产品和工程环境隔离，其他角色不了解工程规范 |
| 缺失 02 可执行环境 | 代码能编译，但在正式工程环境里跑不起来 |
| 缺失 03 可验证的质量机制 | 对「什么才算对」没有共同标准 |

结论：**AI 可以跨越角色边界，但不能越过缺失的生产条件。**

### 能跨栈做出功能，离直接交付还差一步

> Agent 已具备「跨栈做出功能」＋ 仍然缺少「真实业务生产条件」（可信的业务上下文 · 可运行的真实环境 · 可判定的验证机制）＝ 目标「直接交付」。

少了中间这一项，结果只能停在「能演示」。

### 技术栈融合：「能写」不等于「能交付」

| 阻碍 | 原文描述 |
|---|---|
| 01 复杂环境 | 涉及多个库和系统，很难准备好能跑起来的环境 |
| 02 技术陌生 | 拿到非自己领域的代码，不知道该看哪里、按什么规范改 |
| 03 代码掌控力 | 控制每一行代码已然不现实，质量风险上升 |

页面结论：**人在不熟悉的领域往往举步维艰。**

## 方案/架构

### Flower：一站式全链路交付平台

平台分七层（自下而上）：

| 层 | 名称 |
|---|---|
| 01 | 系统沙盒 |
| 02 | 环境定制 |
| 03 | Agent |
| 04 | 策略 |
| 05 | Harness |
| 06 | 知识 |
| 07 | 体验 |

六项平台能力：

| 能力 | 说明 |
|---|---|
| 01 云化环境 | 一次配置，处处运行 |
| 02 多库协同 | 多个代码库汇聚同一环境 |
| 03 信息共享 | 全流程在同一空间执行 |
| 04 质量左移 | 从需求阶段介入 |
| 05 上通下达 | 连接上下游 |
| 06 长程执行 | 开发、验证、修复自动循环 |

### 环境：云化 & 工程知识建设

| 过去的问题 | 平台的解法 |
|---|---|
| 环境全靠日积月累；新人前三天光配环境 | **All In One 沙盒提供完整且可定制环境**：多技术栈、多代码库汇聚同一环境，一次配置处处运行，不再逐人逐项搭建 |
| 细节全在人脑里；提的代码打回又打回 | **让 Agent 高效操作环境**：工程规范、目录结构、启动与调试方式沉淀为知识，Agent 知道去哪儿看、按什么规范改 |
| 代码一看好像对；编译过了跑不起来 | **真正跑起来，而不只是编译通过**：沙盒连通 IDC 网络与上下游，面向真实运行时验证 |

### 验证：打通 Loop & 结果导向

| 过去的做法 | 平台的要求 |
|---|---|
| 3 分钟 1000 行代码；没人看得懂是不是能跑 | **以运行结果验证，而非功能演示**：验收看真实链路上的结果，而不是本地能不能演示出来 |
| 开发代码 3 分钟；人去验证折腾 3 小时 | **开发—验证—修复**：在环境的基础上叠加长程 Loop，Agent 反复自证，直到结果正确再交出来 |
| 代码又多又复杂；跟不上了线上质量崩溃 | **开发者关注结果，做好自测**：人始终是需求的第一责任人，送测标准不因「代码由 Agent 产出」而下降 |

### 产设研融合：跨角色协作容易失控

产品、设计、研发构成三角，三条边各有一个问题：

| 边 | 问题 |
|---|---|
| 产品—设计／研发 | **质量标准不同**：「功能演示通过」与「线上运行正确」是两套标准 |
| 设计—研发 | **信息不对称**：彼此不懂对方领域，又各用各的环境，产物交不过去 |
| 三角中心 | **责任边界模糊**：组织要求打破职责边界，用平台支撑大家把事情做完 |

### 左移：提前澄清 & 风险消除

| 过去的痛点 | 平台的做法 |
|---|---|
| 需求不行；返工延期问题一大堆 | **Agent 协助把需求写清楚**：几轮对话补齐边界与场景，产出结构完整的需求；人只管表达与拍板 |
| 基于真实代码做原型；避免上下文污染 | **基于真实代码生成可交互界面**：原型直接在线工程上生成，产设看到的就是之后会跑起来的样子 |
| 细节随便写写；真开发测试吃大亏 | **让需求过得了「评审」**：由 Agent 独立审视需求和界面，结合线上业务现状，澄清并完善 |

### 接力：工程底座 & 协同工作

| 过去 | 现在 |
|---|---|
| 拉不到代码库；拿出来的页面上不了线 | **统一环境天然具备工程前提**：代码库、工程规范、Harness 与知识已经就位，不会做出能看但不可发布的产物 |
| Agent 说做得很好；放真实环境里只剩白屏 | **在真实环境里体验与验收**：系统在沙盒中跑起来，产品和设计直接上手体验，按真实结果验收 |
| 技术难题看不懂；得抱着电脑四处找人 | **遇到困难，请专家进现场**：专家通过共享会话进入任务，直接分析、给方案，不用搬环境到别处 |

### 底座能力 + 业务建设，才能「能写」变「能交付」

| 底座能力 | 业务建设 | 效果结果 |
|---|---|---|
| 沙盒环境、知识托管、远端浏览器、高质量需求生产、上下文共享、任务协同接力 | 环境定制、知识建设、优秀工程底座、验证 Loop | 结果导向的高质量产出；一人承担产研多角色；全链路端到端交付 |

### 生产方式的三个建设阶段

| 阶段 | 动作 | 说明 |
|---|---|---|
| 01 搬上来 | 把代码、知识和环境放进 Workspace | 先让工作发生在同一空间 |
| 02 跑起来 | 用真实任务和 Harness 跑通端到端交付 | 以真实结果验证，而不是演示 |
| 03 留下来 | 把验证过的经验和能力留下来复用 | 让每次任务都成为下一次的资产 |

### 交付链路最后只看两件事

- **产品侧**：需求有没有想清楚。
- **研发侧**：实现有没有做对。

### 业务工程的变化：从「业务工程 ≈ 编码」到「业务负责补齐生产条件」

| 要素 | 现在业务要补齐的内容 |
|---|---|
| 环境 | 可重复启动的运行环境 |
| 知识 | 网络拓扑、环境配置、上下游依赖 |
| Harness | 验证要求、架构约束、Review 规则 |
| 协作方式 | 任务 Owner、Harness Owner、专家 |

底座支撑是 Flower 一站式平台：Workspace、沙盒、工具、协作。

### 研发效率度量的变革：从看过程产出，到看交付结果

| 过去（看 Agent 做了多少） | 现在（看需求交付得怎样） |
|---|---|
| 代码生成速度 | 端到端交付时长 ↓ 越短越好 |
| Agent 使用次数 | 人工投入 ↓ 越少越好 |
| — | 交接等待 ↓ 越少越好 |
| — | 返工次数 ↓ 越少越好 |
| — | **核心指标 ↑：交付到用户的吞吐**——一定时间内真正交付到用户手中的需求量 |

## 关键工程做法

### 一项看似简单的需求：「要上一个活动入口」

这句一句话需求里藏着两类未写明的细节：

- **开发前·隐藏细节（需求里没写，但必须做）**：三端同步、数据防刷、游客不展示、登录态同步。
- **测试时·新增边界（跑到测试环节才冒出来）**：重复操作、断网重试、记录回查。

这说明需求澄清不能只靠一句话，必须补齐边界与场景。

### 需求生成：在对话中补齐边界和场景

平台把需求对话与完整 PRD 并排：左侧是 AI 与人的多轮澄清（原文示例是漫剧工作台「剧本详情」的展示调整，涉及展示正文前 200 字、正文为空时展示空状态并支持重新上传），右侧实时生成结构化 PRD 与流程图。

流程图示例：打开工作台项目页 → 请求剧本详情接口 → 解析状态 → 解析成功且内容非空时展示正文前 200 字摘要；解析失败／内容为空／请求失败时展示空状态 + 重新上传入口；点击卡片跳转详情或打开弹窗；重新上传并触发解析；显示解析中 loading。

### 原型模式：在真实工程代码上制作可交互原型

不是另做一套演示页，而是用真实的 `vite dev server` 以独立后台进程启动，PM 看到的就是系统原本的产品界面（真实 Logo、空间切换器、tiptap 输入框、快捷操作、侧边栏），页面正常加载并自动落到真实路由，侧边栏、快捷操作全部真实渲染，无报错、无登录跳转。

原型预览入口直接推送给产设；打开就是运行中的真实前端，可以直接点选元素、改文字、加评论做微调；在真实代码里改，`vite` 热更新后刷新即可看到。页面把这种做法概括为「基于真实代码做原型，避免上下文污染」。

### 需求预检：对照真实代码逐条澄清问题

原文示例 Q-001「离场后生成失败无反馈」：

- **原文引用**：生成任务完成后，结果自动绑定并落位到该任务所属画布；用户离开、切路由、关标签页都不影响素材结果上面布。
- **风险说明**：离场后生成失败态未定义；PRD 只写成功后自动落位，未说明用户离开页面时生成失败如何反馈与重试；研发定了失败占位逻辑，用户回来可能面对一直卡在「生成中」的占位。
- **备选方案**：A. 失败也落位为可重试的错误占位，用户回来能一键重试；B. 失败不占位，仅在通知／消息中提示，画布保持干净；C. 失败静默丢弃、用户无感知（体验最差，不建议）。

右侧进度为 6/6 已完成（5 已验证、1 已跳过、0 待确认），其余待确认项包括：完成是否主动通知、并发改动后落位归属、登录失败后回跳、并发覆盖是否提示、新建后标签被拦截。

### 技术方案：定位相关代码，列出待确认项

原文示例是「讨论 HTML 技术方案复用 Markdown 评论与修正功能」。方案按四个分层拆解：

| 层 | 关键内容 |
|---|---|
| 数据与网络层 | `api / queries / mutations`；后端 `DocumentCommentThread`（`schema.prisma:1595`），`target_id` = 节点主键，`parent_id` 承载回复 |
| 锚点层 | `extractAnchorFromSelection` 采 `anchorText + prefix + suffix + offset`；`locateAnchor` 归一化模糊匹配；`applyThreadHighlights` 用 `range.surroundContents` 注入高亮 |
| 交互装配层 | `CommentAnchorPopover` / `CommentThreadPanelSuspense` / `CommentConnectorOverlay` 均假设评论层与正文同 document、同坐标、同一个 `getSelection()` |
| refx 流 | 选中评论 → `buildSelectedCommentsPrompt` → Composer → 同一 Agent → 完成后 `resolveComments` 置 RESOLVED |

iframe 适配的关键判断：现有组件假设「同 document、同坐标、同一个 `getSelection()`」，iframe 打破了这三点；需要新增一层壳适配——iframe 内选区监听、rect 叠加 + iframe 偏移做浮层定位、往 iframe 注入高亮样式并在每次探活重载后重放。原文还提示 Mermaid 图元锚点是「非纯文本锚点」的先例：不新增数据库字段，把结构化锚点编码进 `anchorPrefix`（`mermaid:v1:`），高亮改为在 SVG 上打属性标记，这是后续方案 B 可复用的关键范式。

### 编码实现：变更看得见，结果可验证

平台提供「Git Diff 可视化与原型设计」：左侧按服务端／前端分包列出改动概览（新增 `src/services/outputVersioning.ts`、改 `src/analysis/technicalPlan.ts`、改 `src/routes/tasks/sandboxCommonRoutes.ts` 与 `technicalPlanSandboxRoutes.ts`；前端新增 `features/technicalPlan/sandboxApi/sandboxQueries.ts` 等，改 `DocumentPreviewToolbar.tsx`、`TechnicalPlanDocumentPanel.tsx` 及 Workspace），右侧逐行展示 diff，并标注「两个包 tsc／构建均通过」。

## 经验与边界

### 角色融合的前提是生产条件，而不是「让人越界干活」

- 失败案例说明：产设能做出可演示的原型，不等于能接入生产系统；发布门禁、架构约束、验证标准仍在工程侧。
- 三项缺失——共同上下文、可执行环境、可验证的质量机制——是角色融合的硬前提；AI 可以跨越角色边界，但不能越过缺失的生产条件。
- 「能写」与「能交付」之间隔着复杂环境、技术陌生、代码掌控力三道阻碍；平台的作用是把这些条件产品化，而不是要求每个人都成为全栈专家。

### 人的责任不因 Agent 产出而下降

- 人始终是需求的第一责任人，送测标准不因「代码由 Agent 产出」而下降。
- 开发者要关注结果、做好自测；平台用真实环境与长程 Loop 帮助 Agent 自证，但验收仍在人。
- 任务 Loop 中「人只在验收和高风险决策时介入」；这要求验收标准、回归 Case 与高风险边界事先定义清楚。

### Agent 会失忆，经验要留在 Harness

四个反复出现的场景：

| 场景 | 表现 |
|---|---|
| 环境架设步骤很长 | 几十轮试错才跑起来，下个任务照旧 |
| 文档与事实不符 | 接口早改了、目录早撤了，Agent 照着旧文档走偏 |
| 代码检索效率低 | 几十个代码库找一个模块，找入口比改代码还慢 |
| 人工反复介入修正 | 这里不对、那里要注意，口头纠偏只存在于这一次会话 |

能积累的是 Harness：持续调整整个 Harness，把脚本、镜像、知识、规则、验证 Case 留下来，下一次任务用得上、效果好——**把失败转成资产**。

### 将会话视为知识，让 Agent 自我进化

度量三个维度：**质量**（是否通过验收标准与回归 Case，做对是前提）、**成本**（模型轮次、Token、端到端耗时，暴露试错浪费）、**人工介入**（被打断几次、专家答疑几次，依赖是否下降）。

六步流程：

1. **会话托管**：任务在线执行，自动记录任务过程。
2. **分析**：回看缺陷、消耗、人工介入等特征。
3. **聚类**：批量归并，分清偶发与共性。
4. **提案**：Agent 给出具体修改，附证据。
5. **人把关**：判断是不是真问题。
6. **放行后优化**：Agent 落进 Harness，回测验证。

### Harness 持续改进的闭环

01 执行任务（真实任务在沙盒跑通）→ 02 度量（质量、成本、人工介入）→ 03 分析问题（批量归因，分清共性）→ 04 改进建议（附证据，具体到改哪）→ 05 采纳（人判断是不是真问题）→ 06 自动改进（Agent 修改，可回退）→ 回到 Harness 建设（代码、知识、技能、环境、策略）。

两条支路：人工直接修正回到 Harness；手动改进单独进入；被拒绝的建议进入「记忆归档」，不再重复提出。

### 任务在跑，Harness 也在跑

- **内层 · 任务 Loop**：编码 → 启动 → 操作 → 观察 → 修正 → 再验证；人只在验收和高风险决策时介入。
- **外层 · HARNESS LOOP**：提案 → 改进 → 分析 → 度量（每轮供数据）；改进可以让下一次「少绕一次路」。
