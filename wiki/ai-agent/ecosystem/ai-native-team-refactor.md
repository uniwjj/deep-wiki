# 重构协同——AI Native 团队的思考

> 微信公众号「天猫技术团队」文章，作者**书牧**（淘天集团-天猫技术团队），发表 2026-08-14。观点文章（作者自述"不是要给出一套具体的解决方案，而是讲讲我的理解"），公司内尚无成熟最佳实践。

核心命题：当前 AI 提效陷入"**单点优化、全局低效**"困境的根源在**协同缺失**；破局不是把某个环节再调快一点，而是**把流程串联者从人换成 Agent，围绕新前提重建生产侧**——以一个完整业务单元为边界，构建"**知识底座 + Agent + 人**"三层闭环。文章判断：核心瓶颈不在协同工具，而在**为存量业务构建可持续更新的知识底座**。

## 问题诊断：单点遍地提效，全局不见增量

公司内 AI 项目遍地开花（技术侧 AI Coding、业务侧运营 AI 化），但单点各有提效、全局效果不明显。作者判断：**公司真正的效率问题从来不是单点产能，而是协同；这一年的 AI 提效恰恰大多没碰到协同**。两种最典型的"拆碎"：

- **业务被横向切碎**：为扛住系统和规模复杂度，完整业务被拆成平台、横向产品、垂直业务等团队，各有 KPI、目标不一致——A 业务 GMV 增长实质可能只是吃掉 B 业务份额，全局看甚至是负的，因为缺共同的全局目标。
- **产研流程被纵向拆碎**：需求、产品、研发、测试各管一段，中间靠人来回传递；现在大多只盯着最小的一段（个人 AI Coding 提效），端到端算下来整体提升有限。

## 消费侧与生产侧：串联者从人换成 Agent

一切生产活动为满足人的需求，人的原始需求稳定（马斯洛），变的只是满足需求的方式。据此把事情切成两类，它们在 AI 面前命运不同：

| | 消费侧 | 生产侧（B 端） |
|---|---|---|
| 定义 | 直接面向人、满足人的需求 | 背后组织和串联生产 |
| 演进逻辑 | 交互方式升级（报纸→门户→信息流→AR 眼镜），终端永远是人，"以人为本"不动摇 | 没有"终端是人"的锚，有什么技术就长什么流程/分工/系统，技术每升级一轮就被重写一次 |
| AI 时代走向 | 个人助理（贾维斯式，高度个性化，它适配你） | **串联者从人换成 Agent**，整个形态围绕新串联者重构 |

一条业务流程靠什么"串"起来？曾经的答案一直是**人**：需求评审会上人把上下文从产品传给研发，工单系统里人把上一环节结论手动录进下一环节。过去几十年绝大多数生产侧软件都在给"人来串联"打辅助——表单让人填、看板让人看、审批流让人点，共同设计前提是"人是串联者"。

**AI 辅助 vs AI Native 的判定**（文章的核心区分）：

- **AI 辅助**：流程骨架不动，串联者还是人，只在某个环节塞一个 AI 功能让人写得快一点——本质在旧流程上加挂能力。
- **AI Native**：把串联者整个换掉，由 Agent 承担传递、判断和衔接，并围绕"Agent 是串联者"这个新前提重建流程本身。

由此推断：会消亡的不是"软件"这个笼统概念，而是**把"人是串联者"当作设计前提的软件**——表单、报表、审批流，以及大量内部系统里"等人来操作下一步"的环节。运营侧大量 AI 提效诉求（取数、做日报周报、横向小二向行业小二"收作业"）本质都是信息传递和协同——若串联本身交给 Agent，这些"人传人"的工作也许压根不必存在。

## AI Native 协同形态：三层闭环

以一个完整业务单元为边界，理想形态大致三层（原文架构图见 sources 同名 `-images/img-05.png`）：

1. **底层：统一的知识底座**——沉淀该业务所有的业务规则、业务流程、领域知识和规范约束，即"这个业务究竟是怎么运转的"这件事本身。
2. **中间：一群各司其职的 Agent**——业务运营、产品/研发 coding、测试、运维、客服等，各自承接并串联起自己环节的工作；依赖一组**工具和技能**才能真正干活（查数据、调系统、跑流程、触发变更）。**知识底座决定它"知道什么、该怎么做"，工具和技能决定它"能做到什么"**。
3. **顶层：人**——业务、产品、技术等角色，位置变了：不再是逐个传递信息的"接力棒选手"，而是围绕同一业务目标定方向、做判断、处理 Agent 搞不定的例外，并把新产生的知识沉淀回底座。

**为什么拆成多个 Agent 而不是一个大而全**：不同 Agent 需要感知的知识范围、能提供的服务范围、被授予的权限和安全要求往往都不一样；拆开后每个 Agent 上下文相互隔离，评测和优化可独立进行、独立迭代。原文例子：帮工程师排查线上问题的运维 Agent 既要感知代码层知识、又要能调用运维工具（normandy、sunfire、arthas 等）；面向内部员工的答疑 Agent 可以直接回复到代码级错误定位；面向外部用户的客服 Agent 则要更专业得体的话术——能看到的知识、能动的东西、出错的代价都不一样。

**角色边界**：业务/产品/技术的边界也许会变模糊（已有技术团队做"全栈融合"尝试，如前后端不分家），但融合目前主要发生在执行层面；真正需要专业度的地方差异不会完全抹平——**一个角色的专业深度决定了他面对 AI 产出时能做哪一层的专业判断**，这种判断力未来更稀缺、更重要，不是"全栈"能覆盖的。

**闭环目标**：今天的串联靠人开会、拉群、手动同步，未来的串联靠 Agent；今天的知识散在各人脑子里和对不齐的文档里，未来的知识沉淀在能被 Agent 直接使用的底座里。人负责目标和判断，Agent 承担串联和执行。

### 文中给出的运行示例

一个业务需求进来：不再业务写 MRD 给 PD、PD 转 PRD 丢给研发、反复拉会对齐——而是 MRD/PRD 的产出本身由业务和 PD 借助**业务/产品 Agent**、基于知识底座协同完成；**研发 Agent** 基于知识底座定位涉及的领域/应用/规则、拆解技术方案；人在协作空间（如项目群）与 AI 澄清、在关键节点确认判断；编码、测试、发布由对应 Agent 串起来执行，过程中新产生的决策和知识回流底座。同时：线上监控报警触发**运维 Agent** 自动排查定位、给出止血操作由人决策；**答疑 Agent** 基于底座自动答疑，不确定时在内部群 at 项目成员确认后再回答（参考 Qteam 团队的 Q仔 实践），遇到 bug 自动记录到 Aone 缺陷并触发**研发 Agent** 拉变更修复；**运营 Agent** 基于底座结合业务目标分析产出业务状况报告供老板决策，并给出运营动作。

## 两件事：知识底座是瓶颈，协同工具是基建

要让形态跑起来，公司要面对的核心命题就两件：**把知识底座建起来；把"知识底座、人、Agent 三者协同"的工具建起来**。

**协同工具**——长期看不会是瓶颈，但非常重要，且是通用基础能力（跨团队协同需要无缝），不适合各业务重复造；但当下基础团队没有完整方案可用，业务侧选型困难、有时不得不自建。公司内已有探索：Aone 团队的 **Devix**、Qteam 团队的 **Qoder 系列**（Qoder、QoderWake 等）、企业智能的**数字员工账号**、**ideawork** 等，都还不完善。作者认为很多号称"数字员工"的方案应跳出数字员工本身，把重心放在 **Agent 和人的协同形态**上。已能看到的关键概念雏形：

| 概念 | 含义 |
|------|------|
| **业务空间** | 划定一个业务闭环边界的核心容器（Devix 的产品空间类似） |
| **参与者** | 空间里的人类成员和各类 Agent（概念上类似数字员工），关联技能和知识 |
| **任务** | 对应一个项目、一个需求、或一个讨论的话题 |
| **频道** | 人与 Agent 协同的入口：IM、Web，甚至 QoderWork 这样的通用助手（传统协同入口在钉钉，未来也许在通用助手） |
| **产物** | 协同过程中沉淀下来的结果 |
| **知识底座** | 每个业务空间管理的知识+数据，**这是业务的护城河** |

**别被"Coding 变快"的幻觉带偏**：企业级业务真正的复杂度和瓶颈往往不在写代码这段——拿半托管超链这类跨团队项目来说，光是把商业逻辑、方案取舍在多个角色间讨论清楚就极其耗时。简单需求哪怕 AI 全自动交付，对全局提升也有限；甚至研发为"完美地写代码"反过来要求 PD 给出更完整规范的 PRD，本身就是把产品设计和研发割裂，中间的协同成本一点没省。所以协同工具不该只停在研发流程（AI Coding），真正的 AI Native 协同要往更左侧的需求侧、业务侧走。

**知识底座**——真正难的一关：不通用、不可复制，每块业务都得自己长出一套，做得越久的传统业务越难。详见 [[legacy-business-knowledge-foundation]]。

## 结论：遮羞布被揭开

把一个业务彻底讲清楚、让它可被复用——一直都难，并不是 AI 才带来的。过去因为串联者是人，这个难题被人"扛"过去了：知识不全、流程不清、文档过期，靠一个个的人在中间补位、对接、救火，谈不上高效但业务照样转。**串联者换成 Agent 后，Agent 没法靠经验和默契补位，它只能在知识底座上运转——底座有多清楚，它就能跑多远**。"把知识底座建起来"从可以一直拖着的事变成绕不开的必选项。若大公司迈不过这道坎，迟早会有没有历史包袱的创业公司用"知识底座＋Agent"跑出数倍效能——创业公司的优势不在更聪明，而在它是张白纸，形态一旦跑起来，数据和知识的飞轮自然转动。

作者收束：公司效率问题的根源多年没变——业务、产品、组织怎么真正配位、对齐共同目标、减少内耗、降低协同成本；技术架构的目标也没变过（机器码→汇编→高级语言→DDD→上云→Serverless，每一步都是把人从琐碎里解放出来）。AI 只是把这个线索又往前推了一大步。
