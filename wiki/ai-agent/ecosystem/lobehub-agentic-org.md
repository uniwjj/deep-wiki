# LobeHub 的 Agentic 组织实验

一篇对谈记录：作者带着「怎么把 super agent 这类东西融进工作、让一群人协作产出」的问题，和 LobeHub 创始人文彬聊了两小时。LobeHub 是一款知名 Agent 工具，拿了两家头部机构投资，DeepSeek v3.2 发布时用 LobeChat 做工具调用演示；他们一直在探索 Agent 的原生使用方式（比如让 Agent 集体进 Discord 群「上班」、自动接活、写代码）。

本页只记录这次对谈给出的主张与案例，其中的数字均为 LobeHub 自述。

## 诊断：单点都快了，交接没变快

Agent 让每件事的实现都变快了，但**任务之间的沟通成本没有被压缩**——团队协作卡在交接。文章的描述是：调研、设计、开发各自都变快了，中间两次「转述」还是那么长。LobeHub 把这里的时间黑洞分三类：

| 类型 | 内容 | 为什么可以交给 Agent |
|------|------|---------------------|
| 执行类 | 把工作交给张三时的背景同步、任务说明、成果验收 | 这些耗时的事恰好是 Agent 最擅长的 |
| 决策类 | 需要拍板时把支撑材料摆在人眼前 | Agent 可以在工作过程中提前整理好，决策时直接拿出来 |
| 盲区类 | 没人发现的隐患，比如某处兼容性 bug，拖到某个节点才炸 | 靠 Agent 按周期主动巡检，发现异常就上报 |

## 主动的边界：既要在线，又不能吃掉注意力

前提是**人的注意力极为有限**：Agent 无论干什么都插一嘴，很快就把人的注意力吃光。所以 Agent 只该在职责边界内主动。LobeHub 的做法与 DeepSeek Harness 相仿：**先规则过滤（关键词/频道…），再交给模型判断**（通过 Agent 自身的职责状态判断要不要管）。

此外 Agent **每小时巡一遍频道**，看有哪些事被漏下来。给了一个具体案例：一天晚上文彬在群里看了眼训练页，随口说「这个 UI 太 vibe 了，得想想怎么 refine」，然后大家各忙各的——55 分钟后，设计 Agent 自己把这事接了过来，挑出三处问题，当晚交了改版稿。

## 持续在线：把 Agent 循环、会话状态、执行环境拆开

Agent 要当同事，得一直在线、不被「热心的保洁阿姨和上电脑盖子」打断。若 Agent 和某台机器绑死，机器自动更新时正在跑的任务就完了。文章列的底线是四层：

- **被 @ 只是入口**；关掉电脑，任务照样跑；
- **组织空间**：一个 Agent 学会的，全组都能用；
- **权限审计**：出了问题找得到负责的人；
- **验收完成**：以人的验收为准。

技术上的选择与 DeepSeek「想到了一起」：把 Agent 的循环、会话状态、执行环境拆开来放（2025 年 9 月开始做，今年 1 月随 2.0 上线）。**动机是被逼的**——很多服务跑在 Vercel 上，而 Vercel 云服务单次执行最多 300 秒，远不足以支撑 Agent 的长程调用。于是：

- 把每一步（调一次模型或工具）拆成一次单独调用，步与步之间靠**队列和 Redis** 推进；
- 工具也没法在 Vercel 上跑，于是**工具调用被发去 AWS 沙箱**执行，结果再传回来；Agent 自己意识不到，「它以为自己就活在沙箱里」；
- 在这套结构下，切换运行电脑本质上只是**换一个执行工具的地方**（文中示意：云端沙箱 / Mac mini / 你电脑上的 `~/project`）。

文章称这套架构现在每天承受几万次 Agent 执行。

## 两处与 DeepSeek 不同

### 一是 Router：每个 Agent 有自己的岗位

DeepSeek 用一个常驻 Router 统一接活、再分给下面的 Worker。LobeHub 的判断是：中间的事全塞进一个 Router，**下面干得怎么样很难看清，更不知道从哪插手**。他们的探索是让每个 Agent 都有自己的岗位——名字、职责、记忆、工具都是它自己的。

理由不是模型能力不够或工程问题，而是**运行环境和输出产物的回复要求不一样**：比如把排版规范、风格参考、素材流程做成专用设计 Agent，别人求设计帮助时就能获得即时反馈；再做一个 Deck Agent，BD 要做客户案例时直接跟它说，省掉排队等设计的时间——「设计师沉淀一次，BD 之后随时直接用」。

### 二是直通：汇报只走主管

DeepSeek 的设计里，同一话题的后续消息可以绕过 Router 直接送到在干活的 Worker。LobeHub 试过类似做法，结果**群里的干扰一下子多了起来**——相当于人越过主管直接微操干活的 Agent。于是他们把汇报分成三层：

| 层 | 角色 | 职责 |
|----|------|------|
| 第 1 层 | Personal Agent（每人一个） | 替人过滤信息，只带回你关心的 |
| 第 2 层 | 主管 Agent（每个项目一个） | 派活与验收 |
| 第 3 层 | 执行 Agent（Claude Code、Codex 等） | 真正干活 |

人只听自己的 Personal Agent，活由项目主管 Agent 去派。人要中途插手，就在 Task 卡片上开工单让 Agent 去执行。文章用一个比喻描述这个演进：**Agent 能力弱的时候人坐主驾；能力强了，人就退到副驾负责审核**。

## Agent 之间直接交接

交接两头都是 Agent 时，上下文可以原封不动递过去。文中案例（10 月 15–16 日）：上游项目的主管 Agent 发现暗色主题只能硬改全局样式，于是直接给组件库 lobe-ui 的主管 Agent 提需求；第二天 lobe-ui 加好组件、Release CI 自动发版 6.0.1，再回头通知上游升级——**两天、三条消息，两个项目的主管 Agent 直接谈完**，人只在中间确认。

## 新瓶颈：验收

Agent 干活越来越快，人验收的速度没跟上，瓶颈就挪到了验收。文彬说他已三个月没在本地起过 dev：看完 Agent 交上来的验收报告，没问题直接合，**开发速度至少快 3 到 5 倍**（作者本人的对照：年后买的电脑到现在没装 IDE，后台放台 Mac mini 挨个验收，结果用飞书发过来）。

验收工具 **Acceptance**（已开源）做三件事：

1. Agent 先把一条需求拆成几个**看得见的检查项**，再到真实产品里逐项跑一遍，附截图、录屏和日志；
2. 人可以整体通过，也可以部分打回，负责的 Agent 收到推送去改；
3. **每次打回都会沉淀成一条标准**，Agent 下次交付前先自查。

## 组织自己变聪明

团队经验被写进 Agent 的任务和标准里，每天自我迭代。两个可量化的例子：

- **Agent Vent**：Agent 干活遇到问题会随手吐槽，每天有个任务把吐槽聚类、建 Task 去修，第二天再对比。10 月 29 日那天，新增上报从 84 条降到 49 条（high 级从 32 降到 11）。
- **harness 自调**：Lobe Agent 自主优化 harness 后，在 FrontierHarness 上通过率 70%、单任务成本中位数 1.68 美元；对照 Codex 66.7% / 3.47 美元、Claude Code 63.3% / 18.34 美元。

## 组织也有自动驾驶分级（L1–L5）

LobeHub 把 AI 组织的演进看作「把人一步步从执行里拿掉的过程」，按自动驾驶分了五级：

| 级别 | 名称 | 人的角色 |
|------|------|---------|
| L1 | 问答工具 | 问一句答一句，关掉窗口就结束 |
| L2 | 个人助手 | 能帮个人干活，但能力跟着个人走，同事用不上 |
| L3 | 团队成员 | 人和多个 Agent 在同一现场协作，能 @、能派活 |
| L4 | 自治业务单元 | Agent 之间自己接力，人只设目标和边界 |
| L5 | 自演进组织 | 组织在运行中自己改进，人只管方向和担责 |

关键判断：上文那些交接问题正是大家在 **L2** 遇到的卡点——每个流程都被 Agent 提速了，靠人还是无法高效转述和对齐。LobeHub 认为自己目前在 **L3**，项目之间直接提需求已经有了 L4 的雏形；再往后，他们希望各家企业部署的 Agent 能相互协作、对接并实现需求。
