# 数据任务全量→增量优化的 SDD 实践——反垃圾大宽表案例

> 来源：KM 文章《Sdd数据开发实践分享 — 数据任务优化》（作者罗霄，2026-04~05），基于 Claude Code + 猛犸 EasyData CLI 的端到端数据开发流程。方法论框架见 [[raven-sdd-data-development]]。

## 背景与挑战

**需求**：反垃圾大宽表 `ads_security_antispam_dd` 每天全量计算耗时 4-5 小时，优化为增量计算。

**挑战**：

- **表结构复杂**：87 列，10 个 biz_type 分区，116 亿行数据
- **计算逻辑复杂**：7 表 LEFT JOIN，3 个 dwd 子查询扫描 3 年历史数据
- **验证要求高**：必须保证增量结果与全量完全一致
- **平台操作多**：涉及建表、上传任务包、执行、日志分析、数据对比

**AI 辅助方式**：Claude Code 作为开发 Copilot，通过 EasyData CLI Skill 直连猛犸平台 API，实现从方案设计到上线准备的全流程自动化辅助。

## AI 价值与提效分析

### 核心价值：从"人干活"到"人做决策"

开发者角色从"执行者"变为"决策者"——传统模式 80% 时间花在执行性工作（写 SQL、调 API、等结果、写文档）、20% 花在思考性工作；AI 辅助后反转为 20% 确认 + 80% AI 执行，人只需在关键节点做判断。

### AI 擅长的六项

1. **SQL 理解与生成**：370 行线上 SQL 秒级理解全部逻辑、识别 7 个 JOIN 关系（人工需 30-60 分钟）;增量版保持 87 列顺序/类型/命名完全一致；test 版精确替换输出表名；修复排序问题只改需要改的地方
2. **自动化数据验证**：传统流程每轮 2-3 小时、3 轮需 1.5-2 天；AI 辅助每轮约 1.5 小时（主要是 Spark 执行时间），人只需看结论。本次实际执行 22 条 Impala 验证查询（全自动构造+提交+解析）。深层价值：验证维度不遗漏（5 维度）、差异自动下钻、根因分析（V3 中主动设计"线上 28 号 vs 29 号对比"实验证明差异是线上自身不稳定）
3. **问题诊断与迭代**：V1→V2 诊断出"边界值 create_time = date_sub(etlDay, 30) 被增量和存量同时覆盖"并给出三条修改建议；V2→V3 从"2851 行差异"定位到"version=NULL 排序不确定"根因
4. **文档生成**：DESIGN.md 1-2h→5min、TEST-REPORT.md 2-3h→5min、README.md 2-3h→5min、PROGRESS.md 自动更新。优势不止于快：数据与代码完全一致（不抄错 execId/行数）、不遗漏章节（回滚方案、异常处理）、文档中的 SQL 都是真正执行过的
5. **平台 API 编排**：用自然语言描述意图 → AI 自动选 API → 构造参数 → 调用 → 解析 → 处理异常。本次共发起 32 次 API 调用全自动完成（手动估算 160-320 分钟）
6. **上下文记忆与状态管理**：记住所有 execId、每轮差异原因和决策；跨天延续进度（PROGRESS.md）；记住 NeiAPI 认证信息

### 隐性提效

降低心智负担（不记命令参数/API 格式/表结构）、减少低级错误（列对齐/路径/拼写）、加速学习曲线（新人无需掌握猛犸 API 细节）、知识沉淀（踩坑写入 Skill 文档团队共享）、流程标准化（每次同样 10 步）、可复现性（PROGRESS.md 完整操作历史）、并行能力（多条验证 SQL 并行提交）。

### 必须人工把控的五项

| 环节 | 原因 | AI 能提供的辅助 |
|------|------|----------------|
| **方案确认** | 60 天窗口是否覆盖申诉追溯是业务判断 | 提供数据支撑（历史申诉时间分布） |
| **测试结论** | 2851 行差异（0.0017%）是否可接受需要人判断 | 给出差异占比、影响范围、根因分析 |
| **资源配置** | 成本和稳定性的 tradeoff | 提供历史执行数据作为参考 |
| **发布上线** | 高风险操作 | 生成完整操作步骤和回滚方案 |
| **git push** | 需要认证凭证 | 本地完成所有 git 操作，只留 push 给人 |

> 核心理念：**AI 负责"做到位"，人负责"拍板"。**

### 踩坑与 AI 自我修正

| 踩坑 | 教训 | AI 的自我修正 |
|------|------|--------------|
| zip 中放独立 .sql 文件 | 猛犸只读 `hive.query.1` | 发现后自动重新打包，更新 Skill 文档 |
| 文件名用 alias | 文件名 = job ID | 验证发现不一致后自动修正 |
| 文件名含 `$$` | 节点名不能含 `$` | 收到错误码后自动调整格式 |
| 30 天窗口 | 边界重复 | 分析数据后建议扩大到 60 天 |
| `ORDER BY version DESC` | NULL 排序不确定 | 设计验证实验证明根因后建议修复 |
| Monitor 异步获取结果 | 可能拿到不完整数据 | 切换为同步轮询模式 |

**AI 的自我进化能力**：每次踩坑后不仅修复当前问题，还会**主动更新 Skill 文档和 CLAUDE.md**，确保同样的坑不会再踩第二次——纯人工开发通常修完 bug 就完事，不会主动更新团队规范文档。

### 效率对比

**整体对比**：

| 步骤 | 纯人工预估 | AI 辅助实际 | 提效倍数 |
|------|-----------|------------|---------|
| 方案设计 | 2h | 30min | **4x** |
| 代码开发 | 4h | 30min | **8x** |
| 建表+任务创建 | 1h | 10min | **6x** |
| 上传+执行 | 30min | 5min | **6x** |
| 测试验证（3 轮） | 3 天 | 1.5 天 | **2x** |
| 性能验证 | 1h | 15min | **4x** |
| 文档输出 | 4h | 10min | **24x** |
| 上线准备 | 1h | 20min | **3x** |
| **总计** | **~5 天** | **~2 天** | **2.5x** |

**按工作性质**：编写代码/SQL 9x、API 调用/平台操作 12x、等待执行结果 1x（不可压缩）、数据分析/根因定位 3x、写文档 19x、沟通确认 1x（人工确认不可压缩）、环境/配置调试 4x。

**关键数字**：AI 自动构造并执行 25+ 条 SQL；自动生成 ~15,000 字文档（4 份）；32 次 API 调用全自动；3 轮迭代每轮自动定位根因；从发现问题到修复代码平均 <30 分钟。

### 对数据团队的长期价值

- **知识自动沉淀**：踩坑 → AI 修复 → 更新 Skill 文档 → 下次自动规避（如 `$$` 文件名问题第 2 次直接一步到位）
- **标准化输出**：目录结构/文档格式/验证维度/操作流程统一，降低 review 和审批成本
- **可扩展性**：同一框架可扩展到新建 ETL、数据质量修复、表结构迁移、指标口径调整

## 开发流程（SDD 10 步法）

```
1.方案设计 → 2.代码开发 → 3.建测试表 → 4.创建猛犸任务 → 5.上传包
    ↓
6.执行测试 → 7.数据验证 → 8.性能验证 → 9.上线文档 → 10.上线准备
```

每一步都有**人工确认门控**，AI 不会自动跳到下一步。（对应 [[raven-sdd-data-development]] 中 8 步法的更细粒度表述：建表/创建任务/上传拆为第 3-5 步。）

### 各步骤实践要点

**步骤 1 方案设计**：分析 370 行线上 SQL 识别瓶颈（dwd 三个子查询扫描约 3 年）；确认 `create_time` 可作为增量划界字段；评估下游影响（只改 1 个文件）。核心决策：增量窗口 60 天（覆盖申诉追溯）、存量沿用昨天结果不做 JOIN、UNION ALL 按 create_time 严格互斥、资源配置不变。

**步骤 2 代码开发**：基于线上 SQL 生成 test 版本（输出到 `security_tmp.tmp_xxx_luoxiao01`）与 production 版本（输出到正式表）。四处关键改动：dim 表增加 create_time 过滤（只取近 60 天）；dwd 窗口从 3 年缩至 60 天；排序修复（`ORDER BY version DESC, send_time DESC`，消除 version=NULL 不确定性）；新增存量部分（UNION ALL 直读昨天结果 `create_time < date_sub(etlDay, 60)`）。

**步骤 3 创建测试表**：通过 EasyData CLI 执行 `CREATE TABLE IF NOT EXISTS`，87 列 + dt/biz_type 双分区与线上完全一致。

**步骤 4-5 创建任务 & 上传**：CLI 创建开发任务、NeiAPI 上传 Azkaban 格式 zip 包。三个踩坑：zip 内 `.sql` 不被读取（猛犸只读 `.job` 中的 `hive.query.1`，SQL 需编码写入 job 文件）；节点名含 `$$` 被拒；上传后 job ID 不一致（文件名被当作 job ID）。

**步骤 6-7 测试执行 & 数据验证（3 轮迭代）**：

- **V1（30 天窗口 + 存量关联申诉）**：结果 +4 行、2851 行字段差异；根因是边界值重复 + 窗口不够宽 → 决策：窗口扩大到 60 天，存量不关联申诉
- **V2（60 天窗口 + 存量不关联申诉）**：0 行差异，但 2851 行 machine_anti_status 差异；根因是 version=NULL 排序不确定（线上自身每天结果不同）→ 决策：排序增加 send_time 作为二级排序
- **V3（修复排序）**：0 行差异，剩余 2851 行差异经"线上 28 号 vs 29 号对比"实验（线上自身有 2852 行差异）确认是线上问题，非增量引入 → **通过**

**步骤 8 性能验证**：执行时间 ~51 分钟 vs 线上全量 ~265 分钟（**快 5.2 倍**）；dwd 扫描量 60 天 vs ~3 年（**减少 95%**）；资源参数（maxExecutors 600、executor-memory 16000m）不变。

**步骤 9 上线文档**：AI 自动生成 `docs/README.md`——人工操作步骤、SQL diff + Job diff、上线后验证 SQL、回滚方案、异常处理场景。

**步骤 10 上线准备**：production 文件复制到正式路径 → commit 合并 master → NeiAPI 上传到线上任务开发模式 → 验证 job ID 一致。**禁止 AI 做**：`git push`（需用户手动）、`release_task`（必须人工在猛犸 UI 操作）。

## 工具链与规范

### 工具链架构

Claude Code（mammut-api Skill + spark-sql-review + mammut-task-analysis）→ EasyData CLI / NeiAPI（easyolap SQL 执行 / easydev 任务管理 / NeiAPI 上传执行）→ 猛犸平台（自助分析 Spark/Impala、离线开发、任务运维）。

### 四种 API 接入方式

| 类型 | 认证 | 用途 | 使用场景 |
|------|------|------|---------|
| CLI | AKSK（团队公用） | SQL 执行、任务管理 | 日常开发首选 |
| OpenAPI | AKSK（同 CLI） | HTTP REST 网关 | 批量操作 |
| NeiAPI | apiKey+masterKey（个人私有） | 任务包上传、开发模式执行 | 步骤 5/10 |
| SHS | 无认证 | Spark History Server | 性能分析（mammut-task-analysis 封装） |

### 核心规则（10 条）

1. **配置隔离**——只通过 CLI 管理配置，不直接读写配置文件
2. **实现黑盒**——禁止查看 CLI 内部实现
3. **显式配置**——配置项只能由用户显式提供
4. **禁止猜测**——缺参数必须询问用户
5. **Schema 优先**——先执行 `schema` 命令查询参数定义
6. **敏感确认**——敏感操作必须用户授权
7. **分区感知**——查询分区表前先了解分区含义并与用户确认
8. **结果必等**——同步轮询异步查询结果，禁止异步回调
9. **用户优先**——用户指定的参数值优先级最高
10. **系统只读**——禁止修改系统配置

### 适用与不适用

- **适用**：数据表优化（全量→增量、分区调整、窗口调整）、SQL 开发 + 多维度数据验证、多轮迭代测试（快速定位差异根因）、标准化文档输出
- **不适用**：需要深入业务理解才能做的决策、涉及多人协作的实时沟通、需要登录 UI 的操作（发布、权限申请等）

### 复用价值

1. **mammut-api Skill**——封装完整的猛犸 API 接入（CLI + NeiAPI），可直接复用
2. **SDD 10 步流程**——标准化数据开发流程，写入 `CLAUDE.md` 供后续需求复用
3. **NeiAPI 上传规范**——踩坑后总结的 zip 打包规则，已更新到 Skill 文档
4. **数据验证模板**——多维度验证 SQL 可作为其他表优化的模板
